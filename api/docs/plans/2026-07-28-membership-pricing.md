# 멤버십·지역화폐 반영 — 계획 (미구현)

- 날짜: 2026-07-28
- 상태: 화면(UI)만 배치, 로직 대기

## 배경

프론트(`web/src/App.jsx`)에 `MembershipPanel` 체크박스 4개가 이미 떠 있다 —
배민클럽, 쿠팡 와우, 요기패스, 땡겨요 지역화폐. 지금은 상태만 토글될 뿐
표시 금액에 영향을 주지 않는다("준비 중" 배지로 표시). 이 문서는 그 로직을
나중에 어떻게 붙일지 계획만 적어둔다 — 지금 구현하지 않는다.

## 왜 로직이 별도 작업인가

각 멤버십/지역화폐가 할인에 영향을 주는 방식이 서로 달라서, "체크박스 =
%할인 곱하기"처럼 균일하게 처리할 수 없다.

- **배민클럽**: 배달팁 무료·특정 쿠폰 제공. 브랜드 할인 자체엔 안 붙는 경우가
  많고, 있어도 캡처 화면에 "배민클럽 전용" 표기가 별도로 있어야 판독 가능.
- **쿠팡 와우**: 와우 회원 전용 쿠폰함이 따로 있다(§ADR-010에서 확인한 랜덤
  쿠폰함과 같은 종류). 지금 캡처는 회원 여부와 무관하게 보이는 화면 기준.
- **요기패스**: 무료배달 위주라 브랜드 할인 금액 자체엔 영향이 적을 수 있음.
- **땡겨요 지역화폐**: 결제 수단(지역화폐 카드/포인트)에 따라 별도 캐시백이
  붙는 구조로 알려져 있음(브랜드 할인과는 다른 layer).

즉 "체크하면 X원 추가 할인"이 아니라 **앱마다 다른 계산 규칙**이 필요하고,
그 규칙 자체가 아직 캡처·판독되지 않았다(§CONTRACT.md에 멤버십 화면 판독
절차가 없음).

## 될 때 어떻게 붙일지 (초안)

1. **데이터**: `export.json`의 레코드에 멤버십 조건부 필드를 추가한다.
   예: `membershipDiscounts: [{membership: "baemin_club", amount: 1000}]`.
   이건 파이썬 판독 단계(`parse/CONTRACT.md`)에 멤버십 화면 판독 절차가
   먼저 생겨야 한다 — 지금 캡처엔 없는 화면이라 새 캡처 대상 추가가 선행.
2. **API**: `Offer`에 `membershipAdjustments` 같은 필드를 얹거나,
   `POST /api/brands?membership=baemin_club,ddangyo_local` 같은 쿼리로
   서버가 재계산한 금액을 내려주는 방식 중 택일. 서버 계산 쪽이 로직을
   한 곳에 모아두므로 더 낫다(프론트는 체크 상태만 쏘고 표시만).
3. **프론트**: 지금 `MembershipPanel`의 로컬 `useState`를 API 호출
   파라미터로 승격. 체크박스 바뀔 때마다 `/api/brands`를 그 쿼리로
   다시 부른다(디바운스 없이도 됨 — 브랜드 수가 적어 응답이 빠름).
4. **표시**: 반영 후 금액이 원래 금액과 다르면 `offer.amount` 옆에
   취소선 원래가 + 반영가를 같이 보여준다("확정" 배지는 반영가 기준으로
   재판정).

## 지금 하지 않는 이유

- 멤버십별 계산 규칙 확인(실제 화면 캡처·판독)이 선행 작업이라 이 문서
  하나로 끝나지 않는다 — 별도 브레인스토밍·캡처 사이클이 필요하다.
- 지금 붙이면 "체크박스 있는데 숫자가 안 바뀐다"보다 더 나쁜 "숫자가
  바뀌는데 근거가 부정확하다"는 상태가 될 위험이 있다. UI를 먼저 놓고
  기대치를 "준비 중"으로 명시하는 지금 상태가 더 안전하다.
