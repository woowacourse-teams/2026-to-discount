# ADR-006. 오퍼 중복 정리 시 진 쪽의 상세 필드를 병합한다

- 상태: 채택
- 날짜: 2026-07-29
- 관련: [ADR-003](ADR-003-offer-detail-fields.md), tracker
  [ADR-016](../../../delivery-discount-tracker/docs/decisions/ADR-016-confirmed-beats-recency-on-dedup.md)

## 맥락

같은 (브랜드, 앱)에 오퍼가 둘 있을 때 `Offer.preferredOver`는 확정을
우선하고 진 쪽은 통째로 버렸다. 별칭을 잘못 묶어 서로 다른 가게가 한
브랜드로 합쳐지는 충돌에 대비한 규칙이었다.

이 규칙이 실제로 데이터를 잃게 만드는 걸 확인했다. 기존 확정값(예:
5,000원)에는 상세(최소주문금액·조건)가 없는 상태에서, 나중에 같은
브랜드를 재확인하며 조건만 추가로 캡처한(`needs_review`) 오퍼가 있으면,
확정값이 이겨서 화면에 남는 건 맞지만 그 조건은 진 쪽과 함께 통째로
사라졌다. 어렵게 캡처한 상세가 API 응답에 아예 나타나지 않는 결과였다.

## 결정

승자를 고르는 규칙(확정 우선, 동률이면 금액 큰 쪽)은 그대로 두고,
승자에 `minOrderAmount`/`tiers`/`conditions`가 비어 있으면 진 쪽에서
채운다. 승자가 이미 상세를 갖고 있으면 그대로 유지한다.

```java
public Offer preferredOver(Offer other) {
    // ... 승자 판정은 그대로 ...
    return winner.withDetailFrom(loser);
}
```

## 근거

- **판정 규칙과 상세 보존은 서로 다른 관심사다.** "누구를 믿을 것인가"와
  "무엇을 보여줄 것인가"를 하나의 승자-독식 규칙으로 묶을 이유가 없다.
- 원장 쪽(tracker ADR-016)도 같은 규칙으로 고쳤다. 두 레이어 중 어느
  한쪽만 고치면, 원장 단계에서 이미 사라진 데이터를 API가 살릴 수
  없거나(이번에 실제로 겪음), API 단계에서만 병합해도 원장이 먼저
  하나만 남기면 무의미해진다 — 두 곳 다 같은 규칙이어야 한다.

## 결과

`Offer.withDetailFrom` 추가, 필드별로 승자에 없는 값만 진 쪽에서
채운다. 테스트 2건: 확정이 이겼는데 진 쪽 조건이 살아남는지, 승자가
이미 상세를 가진 경우 안 덮어쓰는지.

## 뒤집을 조건

없음. 데이터 손실을 막는 성격이라 되돌릴 이유가 생기기 어렵다.
