# 배달앱 브랜드 할인 정리/바로가기 — 프로젝트 기획서

> **최종 목표**: 유저가 있는 서비스를 만들고 유지·보수·운영한다.
> **1차 목표**: 가설을 세우고, 실험하고, 사용자 반응을 관찰한 뒤 반영한다.
> **2차 목표**: 실제 사용자를 모집한다.
>
> 지금은 **1차 목표 구간**이다. 기능을 늘리는 게 아니라 가설을 검증한다.

## 1. 문제와 가설

배달앱 4개(배민·쿠팡이츠·땡겨요·요기요)는 같은 브랜드에 서로 다른
할인을 건다. 어디서 시키는 게 이득인지 알려면 앱 4개를 번갈아 열어야
하고, 대부분은 그냥 쓰던 앱에서 시킨다.

**핵심 가설**: 합리적 소비(절약) 성향의 커뮤니티 유저는, 브랜드별
앱 간 할인 비교를 한 화면에서 볼 수 있으면 **주문 전에 한 번 들러본다.**

부가 가설: 실제 절약액이 크면(치킨 한 마리 5,000원 차이) 재방문·공유가
일어난다.

## 2. 타겟

할인 정보 공유 커뮤니티 유저 — 금전적 이득에 민감하고, 배달을 주기적으로
소비하며, 정보 공유에 적극적이다. 이들은 이미 커뮤니티에서 할인 정보를
찾아 다니고 있다(= 니즈가 이미 검증된 집단).

## 3. 해결 방식 — 뷰를 가져오는 브릿지

앱별 브랜드/결제/특별 할인을 취합해 브랜드 단위로 비교시키고, 실제
주문 페이지로 바로 보낸다. 정보 탐색 비용을 줄여주고 그 대가로 뷰를
가져온다.

## 4. MVP 범위 — 가설 검증에 필요한 최소

**포함 (구현 완료)**
- 브랜드 단위 앱 간 할인 비교 (73개 브랜드, 4개 앱)
- 확정 금액 / 불확실(`최대`) 구분 표시 — 잘못된 정보로 신뢰 잃는 게 최대 리스크
- 땡겨요 브랜드별 쿠폰 페이지 바로가기 (36개)
- 지역화폐 +2,000원 추가 할인 표시
- 카테고리 필터(치킨/피자/패스트푸드/카페/편의점)
- 판독 원본 캡처 공개 — 값이 의심되면 사용자가 직접 검증 가능

**의도적 제외**
로그인·회원가입, 알림, 개인화, 즐겨찾기, 검색, 매장 단위 할인,
멤버십 가격 자동 계산(UI만 배치, 로직 보류).
→ 가설이 틀리면 전부 버릴 것들이다. 검증 후에 만든다.

## 5. 검증 방법

평소 이용하는 커뮤니티 게시판에 프로토타입 공유 후 관찰한다.

| 관찰 대상        | 의미                 |
|--------------|--------------------|
| 조회수          | 관심 자체가 있는가         |
| 추천·댓글        | 유용하다고 느끼는가         |
| 재방문          | 일회성 호기심인가 실사용인가    |
| **오류 지적 댓글** | 정보 신뢰도 — 가장 중요한 신호 |

**가설 기각 조건**: 반응은 있는데 재방문이 없다 = 정보 탐색 비용이
생각보다 문제가 아니었다는 뜻. 그때는 기능 추가가 아니라 가설을 다시
세운다.

## 6. 리스크

| 리스크             | 대응                                                                                                                |
|-----------------|-------------------------------------------------------------------------------------------------------------------|
| **데이터 불일치·오정보** | 확정/불확실 명시 구분, 원본 캡처 공개, 요기요는 전량 보류 처리. 신뢰를 잃으면 서비스 자체가 무의미                                                        |
| 할인 구조 변경        | 판독을 사람+비전으로 유지 — 구조가 바뀌어도 사람이 보면 읽힌다                                                                              |
| 배달앱 법적 대응       | 공개 화면 정보만 사용, 내부 API 미사용([ADR-010](../decisions/ADR-010-reject-internal-api.md)), 트래픽을 뺏는 게 아니라 각 앱으로 보내는 브릿지 포지션 |
| 운영 부담           | 수동 캡처 + 반자동 판독([ADR-013](../decisions/ADR-013-manual-capture-scope-freeze.md)) — 무인 자동화에 자원을 쓰지 않는다               |

## 7. 현재 상태

배포 운영 중 — 프론트 `beggars-five.vercel.app`, API `bebeggars.duckdns.org`.
3레포 구조([ADR-012](../decisions/ADR-012-three-repo-split-and-deployment.md)):
판독(Python) → 가공(Spring Boot) → 화면(React).
