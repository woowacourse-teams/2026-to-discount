# 운영 API 무중단 배포

배포할 때 API가 약 5초 끊기던 것(`systemctl restart`)을 없앤다. 새 jar로 임시 인스턴스(8089)를 먼저 띄우고, 그 사이 본 인스턴스(8088)를 교체한다.

## 순서

1. 임시 인스턴스를 새 jar로 시작하고 준비될 때까지 기다린다(`/api/brands`가 200이고 목록). 안 뜨면 내리고 끝낸다. 본 인스턴스는 건드리지 않는다.
2. 본 인스턴스를 새 jar로 재시작한다. 재시작하는 5~8초 동안은 nginx가 upstream의 `backup`인 임시 인스턴스로 넘긴다.
3. 본 인스턴스가 준비되면 15초 기다린 뒤 임시 인스턴스를 내린다.
4. 본 인스턴스가 30초 안에 준비되지 않으면 이전 jar로 되돌려 재시작한다.

푸시 알림이 11:00~11:30(KST)에 나가므로, 두 인스턴스가 함께 떠 있는 이 스크립트는 그 시간대에 11:35까지 기다린다. 긴급할 때만 `--no-window-guard`.

## 쓰는 법

```bash
python3 deploy/prod/stage_deploy.py <새 jar> --deploy-dir <jar와 링크가 있는 폴더>
```

폴더에는 `current.jar`(본 인스턴스가 읽는 링크)와 `stage.jar`(임시 인스턴스가 읽는 링크)가 생긴다. 링크는 원자적으로 바꾼다. 최근 jar 3개만 남기고, 링크가 가리키는 jar는 지우지 않는다.

종료 코드: `0` 성공, `1` 임시 인스턴스가 안 떴음(본 인스턴스 그대로), `2` 본 인스턴스가 안 떠서 이전 jar로 복구, `3` 복구도 실패(임시 인스턴스를 켜 둔 채 끝남) 또는 임시 인스턴스를 못 내림(수동 확인).

## 서버 쪽 준비

임시 인스턴스의 서비스 유닛, 환경 파일, sudoers, nginx upstream의 `backup` 줄은 서버에 한 번 설치해야 한다. 설치 스크립트와 설계, 검증 결과는 비공개 운영 저장소(beggars-ops)의 `deploy/provision_stage.py`와 `docs/design/zero-downtime-deploy.md`에 있다. 서버 경로와 계정이 들어 있어 이 공개 저장소에는 두지 않는다.

임시 인스턴스는 환경 파일로 포트(`SERVER_PORT`, `DISCOUNT_METRICS_PORT`)를 바꾸고 푸시 발송(`DISCOUNT_PUSH_ENABLED`)과 PostHog 서버 전달(`DISCOUNT_POSTHOG_ENABLED`)을 끈다. 두 인스턴스가 같은 상태 파일을 쓰는 스케줄러를 함께 돌리면 푸시가 두 번 나가거나 같은 이벤트가 두 번 전송될 수 있어서다.

## 시험

```bash
python3 -m unittest discover -s deploy/prod -p 'test_*.py'
```

서버 없이 순서와 실패 처리를 확인한다. 임시 인스턴스가 준비되기 전에는 본 인스턴스를 재시작하지 않는 것, 임시 인스턴스가 안 뜨면 본 인스턴스를 그대로 두는 것, 본 인스턴스가 안 뜨면 이전 jar로 되돌리는 것, 복구도 실패하면 임시 인스턴스를 켜 두는 것, 푸시 시간대에 기다리는 것을 시험한다.
