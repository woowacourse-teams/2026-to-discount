# ADR-003. 홈은 요청 시점 데이터로 서버에서 그린다(SSR)

- 날짜: 2026-10-01
- 상태: 확정
- 대체: `docs/TECH-CHOICES.md`, `docs/DEV-ENVIRONMENT.md`, `docs/SEO-ACTIONS.md`, `docs/CAPABILITIES.md`의 "SSR 안 씀" 판단(홈에 한해)

홈(`/`)은 Vercel 함수가 요청 시점의 API 데이터로 첫 화면을 그려 보낸다. 브라우저는 그 화면을 버리지 않고 동작만 붙인다. 운영 프리뷰 측정에서 홈 LCP(최대 콘텐츠 표시 시간, 첫 화면에서 가장 큰 글자나 그림이 뜨기까지 걸린 시간)가 3.47초에서 2.69초로 줄었다. 브랜드 페이지(`/brand/<이름>`)는 지금처럼 빌드 때 만든 HTML을 쓴다.

## 용어

| 용어 | 뜻 |
|---|---|
| CSR(클라이언트 렌더링) | 빈 HTML을 보내고, 브라우저가 JS를 받아 화면을 처음부터 그리는 방식 |
| 사전 렌더링 | 빌드할 때 검색엔진이 읽을 HTML을 미리 만들어 두는 방식. 이 저장소는 `web/scripts/prerender.mjs`가 한다 |
| 교체 렌더링 | 사전 렌더링 HTML을 먼저 보여 주고, JS가 오면 버리고 다시 그리는 방식. 2026-08-25부터 홈이 이 방식이었다 |
| SSR(서버 렌더링) | 요청이 오면 서버가 React로 실제 앱 화면을 HTML로 만들어 보내는 방식 |
| 하이드레이션 | SSR로 받은 화면을 버리지 않고 그 위에 클릭 같은 동작만 연결하는 단계. 다시 그리지 않으므로 요소가 자리를 옮기지 않는다 |
| CLS(누적 레이아웃 이동) | 이미 보이던 요소가 예고 없이 자리를 옮긴 정도. 좋음 기준 0.1 이하 |
| TBT(총 차단 시간) | 페이지가 뜨는 동안 브라우저가 계산에 묶여 입력에 반응하지 못한 시간의 합 |

## 과거: SSR을 쓰지 않은 이유

2026-07에 웹을 세울 때부터 2026-09까지 세 가지 이유로 SSR을 쓰지 않았다.

1. **서버가 필요한 기능이 없었다.** `docs/TECH-CHOICES.md`는 Vite를 고른 이유로 "라우터도 SSR도 API 라우트도 안 쓴다"를 들었다. Next.js의 값어치가 전부 안 쓰는 기능에 있었다.
2. **코드가 서버에서 돌지 못했다.** `web/src/variant.js`가 모듈을 불러오는 순간 `localStorage`를 읽었다. 서버에는 `localStorage`가 없어 실행 자체가 안 됐다(`docs/SEO-ACTIONS.md`).
3. **데이터를 빌드에 박을 수 없었다.** 금액이 하루 세 번(00:01, 10:55, 15:55 수집 뒤) 바뀐다. 빌드할 때 HTML에 금액을 넣으면 다음 배포까지 낡은 금액이 나간다.

처음에는 CSR이었다. 배포된 `index.html`이 1.1KB였고 본문이 비어 있어 검색엔진이 읽을 내용이 없었다. 2026-08-25 `425a950`이 사전 렌더링을 넣어 검색엔진용 본문과 브랜드 페이지 110장을 빌드 때 만들게 했다. 브라우저에서는 React가 그 본문을 버리고 다시 그렸다(교체 렌더링). 카드는 12장씩 150ms 간격으로 나눠 그려 첫 화면 비용을 줄였다.

## 현재: 다시 SSR을 검토한 이유

2026-09-30~10-01 성능 측정이 교체 렌더링의 한계를 보여 줬다. 측정 방법과 전체 실험은 [`docs/metrics/WEB-PERFORMANCE-20260930.md`](../../../docs/metrics/WEB-PERFORMANCE-20260930.md)에 있다.

- **방문의 98.2%가 홈이다.** 최근 30일 방문자 4,823명 중 4,735명이다(PostHog `$pageview`, 봇 제외). 홈의 첫 화면이 서비스의 첫인상이자 검색 품질 평가 대상이다.
- **LCP의 대부분이 기다림이었다.** 홈 LCP 요소는 맨 위 배너의 금액 글자다. 배너 데이터는 0.5초에 도착했다. 그런데 화면에 그려지기까지 약 2.9초를 더 기다렸다. 앱 JS를 받아 실행하고 첫 렌더를 마칠 때까지 배너를 그릴 수 없는 구조였다.
- **다른 수단은 LCP를 못 움직였다.** 아래를 모두 10회씩 재서 기준과 비교했다. 어느 것도 LCP를 줄이지 못했다.
  - 카드 수를 12장으로 줄이기
  - 카드 상세를 늦게 그리기
  - 계속 도는 애니메이션 끄기
  - 사전 렌더링 본문 비우기
  - 위치를 즉시 재는 코드 빼기
- **교체 렌더링에는 경쟁 상태가 있었다.** 브라우저가 사전 렌더링 HTML을 먼저 그린 뒤 React가 교체하면 본문 전체가 움직였다. 브랜드 페이지에서 20~40%의 실행이 CLS 0.8을 냈다.

세 가지 막힘도 풀려 있었다.

1. **서버 기능:** Vercel 함수 하나(`web/api/ssr.js`)로 충분하다. 라우터나 프레임워크를 바꾸지 않는다.
2. **서버에서 못 도는 코드:** `variant.js`는 실험이 끝나 상수가 됐다. 남은 브라우저 의존(`localStorage`, `matchMedia`, 화면 폭, 기기 시계)은 첫 렌더에서 빼고, 화면이 뜬 뒤 effect에서 읽게 고쳤다.
3. **낡은 데이터:** 빌드 때가 아니라 요청 때 API를 받아 그린다. CDN 캐시는 60초에 재검증 60초라 낡은 금액이 보일 수 있는 시간은 최대 약 2분이다.

## 실행

| 자리 | 하는 일 |
|---|---|
| `web/vercel.json` | `/`를 `/api/ssr`로 보낸다. 함수 리전은 서울(`icn1`) |
| `web/api/ssr.js` | 요청마다 `/api/brands`, `/api/banners`를 받아 그린다. 데이터는 `window.__SSR__`로 같이 보낸다. 실패하면 사전 렌더링 HTML을 대신 보내고 CDN에 두지 않는다 |
| `web/src/entry-server.jsx` | 서버 렌더 진입점. 트리 모양을 `main.jsx`와 같게 둔다. 다르면 `useId` 값이 어긋난다 |
| `web/src/main.jsx` | `__SSR__`가 있으면 `hydrateRoot`, 없으면(브랜드 페이지, SSR 실패) 예전처럼 `createRoot` |
| `web/scripts/ssr-template.mjs` | 빌드 끝에 `dist/index.html`을 함수용 모듈로 옮기고 원본을 지운다. 파일이 있으면 Vercel이 함수보다 파일을 먼저 내보낸다. 앱 CSS는 HTML 안에 넣는다 |
| `web/middleware.js` | 홈 캐시 키에서 `utm_*`, `dev`를 뗀다. 브라우저 주소는 그대로라 분석 도구는 utm을 읽는다 |
| `web/index.html` | Pretendard 글꼴을 첫 페인트를 막지 않게 받는다 |

변경을 하나씩 따로 재서 조합을 골랐다. 각각 기준과 번갈아 10회 측정했다.

| 변경(1차 SSR 위에 하나씩) | LCP 변화(모바일 가정) |
|---|---|
| 캐시 60초 + 재검증 60초 | −0.47초 |
| HTML 축소(아이콘 주소화, 첫 화면 데이터만) | −0.39초. 첫 콘텐츠 표시를 늦춰 뺐다 |
| 글꼴 비차단과 CSS 인라인 | −0.43초 |
| **최종(캐시, 글꼴과 CSS, 미들웨어)** | **−0.78초** |

### 운영 반영 뒤 다시 잰 값 (2026-10-02)

위 표의 프리뷰 측정에는 빠진 조건이 있었다. 프리뷰 보호를 넘으려고 붙인 우회 헤더가 jsdelivr(글꼴을 내려 주는 외부 서버) 요청에도 붙어, 교차 출처 요청 차단(CORS)으로 글꼴이 받아지지 않았다. 운영에서는 글꼴(약 480KB)이 받아진다. 그래서 운영 홈을 세 방식으로 다시 쟀다.

| 측정 방식 | 최대 콘텐츠 표시 시간(LCP) | 첫 콘텐츠 표시 시간(FCP) | 비고 |
|---|---|---|---|
| Lighthouse 시뮬레이션(느린 4G와 CPU 4배 감속을 계산으로 가정, 15회) | 4.63초 | 4.33초 | 글꼴 전송을 첫 화면 대기로 계산해 부풀린다 |
| 같은 실행의 실제 관측값(15회) | **1.32초** | 1.32초 | 브라우저가 실제로 그린 시각 |
| 실제 속도 제한(`--throttling-method=devtools`, 6회) | **1.75초** | 1.06초 | 네트워크와 CPU를 실제로 늦춰 잰 값 |

- 실제 관측과 실제 속도 제한 모두 구글의 "좋음" 기준(2.5초) 안이다. 시뮬레이션 값만 기준을 넘는다.
- 글꼴 처리를 바꾸는 변형 셋(글꼴 표시 방식 `optional`, 쓰는 글자만 담은 138KB 글꼴, 대체 글꼴 크기 보정)을 15회씩 짝지어 쟀다. 실제 관측 LCP 차이는 −28~+6ms였고 승패가 반반이었다. 셋 다 채택하지 않았다.
- 실제 속도 제한에서 총 차단 시간(TBT)은 3.08초였다. 화면이 뜬 뒤 카드를 채우며 스타일과 배치를 계산하는 시간이다. 다음 개선 대상은 첫 표시가 아니라 이 반응성이다.

### 반응성 개선 (2026-10-02)

SSR 뒤 남은 병목인 총 차단 시간을 두 커밋으로 줄였다. 둘 다 프리뷰에서 실제 속도 제한 방식으로 기준과 번갈아 12회 재고, 같은 회차끼리 짝지어 판정했다.

| 커밋 | 바꾼 것 | 총 차단 시간 짝차이 | 그 밖 |
|---|---|---|---|
| `ad6a5d5` | 카드는 첫 24장만 타이머로 채우고, 나머지는 목록 끝 표지가 화면 아래 1,500px 안에 들어올 때 12장씩 채운다 | −0.97초, 11/11 개선 | 화면 요소 6,339개에서 2,899개. 최대 콘텐츠 표시와 레이아웃 이동은 그대로 |
| `8059a0f` | 글꼴 표시 방식을 `swap`에서 `optional`로. 글꼴 설정 파일은 우리 도메인(`/fonts/pretendard-optional.css`)에 둔다 | −1.22초, 8/8 개선 | 첫 표시, 최대 콘텐츠 표시는 ±15ms |

- **카드 지연 로딩이 이번에는 된 이유:** 2026-09-01에는 세 방식이 모두 실패했다(관찰 콜백 되풀이, `scrollTo`에 반응, 거리 잠금 뒤 렌더 멈춤). 이번 판은 세 가지를 피한다.
  - 관찰을 카드 수가 바뀔 때마다 새로 세우고, 한 번 불리면 끊는다.
  - 스크롤 이벤트를 쓰지 않는다.
  - 표지가 여전히 보이면 다음 관찰이 바로 다음 묶음을 부른다.
- **글꼴 `optional`이 반응성을 줄인 이유:** `swap`은 글꼴이 도착하는 순간 페이지 글자를 전부 다시 배치했다. 카드가 많은 홈에서는 이 재배치가 1초 넘는 작업이었다. `optional`은 늦게 온 글꼴로 바꾸지 않는다. 화면 도중에 글꼴이 바뀌어 보이던 현상도 같이 사라졌다.
  - 대가: 첫 방문에 글꼴이 늦으면 그 방문은 기기 글꼴로 보인다. 재방문부터는 캐시된 Pretendard로 보인다.
- **기각한 것:** 글꼴 설정 파일을 다시 첫 페인트 전에 받는 판은 첫 콘텐츠 표시를 1.68초에서 3.71초로 늦췄다(최대 콘텐츠 표시 짝차이 +1.09초, 12회 중 10회 악화). CSS 선택자 비용은 실행당 약 56ms라 원인이 아니었다.

운영 홈, 실제 속도 제한, 모바일 측정의 전후는 아래와 같다.

| 시점 | 첫 콘텐츠 표시 | 최대 콘텐츠 표시 | 총 차단 시간 | 화면 요소 | 레이아웃 이동 | 성능 점수 |
|---|---|---|---|---|---|---|
| 2026-10-02 01시, SSR만 (6회) | 1.06초 | 1.75초 | 3.08초 | 약 6,300 | 0.012 | 70 |
| 2026-10-02 12시, 지연 로딩과 `optional` 뒤 (8회) | 1.02초 | 2.15초 | **1.54초** | 2,894 | 0.001 | 72 |

- 최대 콘텐츠 표시가 0.4초 늘어 보이는 것은 측정 시각과 맨 위 배너가 달라진 영향으로 본다. 같은 시각 짝비교에서는 두 커밋 모두 최대 콘텐츠 표시 차이가 없었다(+45ms, −15ms).

## 감수한 것

사용자가 2026-10-01에 다섯 가지를 받아들였다.

- **낡은 금액 최대 약 2분.** 그날 금액 대부분이 00:01 수집에서 들어온다. 그 수집이 실패하는 경우만 아니면 2분 지연은 문제가 되지 않는다.
- **글꼴 교체 때 화면 이동.** 시스템 글꼴로 먼저 그렸다가 Pretendard로 바꾼다. 글자 폭이 달라 화면이 움직일 수 있다. 상단에 보이는 글자가 일부라 영향이 작다고 봤다. 측정 환경에서는 글꼴이 받아지지 않아 이 이동은 숫자로 확인하지 못했다.
  - 2026-10-02 `8059a0f`가 글꼴 표시 방식을 `optional`로 바꿔 도중 교체 자체를 없앴다(위 "반응성 개선").
- **함수와 미들웨어 비용.** 홈 요청마다 미들웨어가 돌고, 캐시가 빌 때 함수가 돈다. 2026-10-01 Edge Requests 사용률은 66.5%로 내려가는 추세다.
- **홈 HTML의 브랜드 링크 83개가 12개로 준다.** 뒤쪽 카드는 원래 거의 노출되지 않는다. 브랜드 페이지와 `sitemap.xml`은 그대로다.
  - 2026-10-02 점검에서 실제로는 0개였다. 카드에는 브랜드 페이지로 가는 링크가 없고, 링크가 들어 있던 사전 렌더링 본문은 `#root`와 함께 교체됐다. `prerender.mjs`의 `brandNav`가 `#root` 밖 바닥글에 브랜드 페이지 링크 전체를 다시 넣는다.
- **숨긴 브랜드가 있는 사용자.** 서버는 숨김 목록을 모른다. 화면이 뜬 직후 숨긴 카드가 빠지며 아래 카드가 한 번 올라간다.

## 예정

1. **브랜드 카드 개편.** 카드를 기본으로 접는 안(`feat/card-minorder`)은 화면이 휑해진다는 이유로 보류됐다(2026-10-02). 반응성은 지연 로딩과 글꼴 `optional`로 먼저 줄였다.
2. **운영 관측.** 배포 뒤 2주 동안 세 가지를 본다.
   - Vercel Speed Insights와 서치콘솔의 실사용자 LCP, CLS
   - Edge Requests와 함수 실행 수
   - `x-ssr: 0`(SSR 실패) 응답 비율
3. **브랜드 페이지.** 방문이 1.8%라 지금은 SSR을 하지 않는다. 경쟁 상태로 생기는 CLS 0.8은 남아 있다. 브랜드 페이지 유입이 늘면 같은 방식으로 옮긴다.
4. **되돌리는 법.** `web/vercel.json`의 rewrite 한 줄을 지우고 `ssr-template.mjs` 단계를 빌드에서 빼면 교체 렌더링으로 돌아간다. `main.jsx`는 `__SSR__`가 없으면 예전처럼 동작한다.
