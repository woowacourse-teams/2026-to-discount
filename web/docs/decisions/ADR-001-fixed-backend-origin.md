# ADR-001. 백엔드 주소를 고정값으로, 프록시·환경변수 없이

- 날짜: 2026-07-28
- 상태: 확정

## 맥락

`delivery-discount-api`를 이 레포에서 분리하면서, 정적 빌드가 백엔드를
어떻게 찾을지가 문제가 됐다. 시도한 순서:

1. **상대경로(`/api/brands`) + vite dev proxy.** 개발 중엔 됐지만,
   정적 빌드엔 프록시가 없다. `vite preview`로 로컬에서 프로덕션
   빌드를 띄워도 프록시가 안 붙어 상대경로가 프론트 자기 자신에게
   요청을 쏘는 걸로 나타난다.
2. **`VITE_API_BASE_URL` 환경변수 + `.env.production`.** 빌드
   모드·배포 파이프라인에 따라 값이 실제로 번들에 박히는지가 갈렸다.
   로컬(`vite preview`)이든 배포든 값이 안 박히면 다시 1번과 같은
   증상(자기 자신에게 요청)으로 떨어졌다.

## 판단

`src/api.js`에 백엔드 주소를 상수로 고정한다:

```js
const API_BASE = 'https://bebeggars.duckdns.org'
```

프록시·환경변수 둘 다 제거했다(`vite.config.js`의 `server.proxy`,
`.env.production`).

## 근거

- 이 프로젝트는 백엔드가 하나뿐이고 자주 안 바뀐다. env var로
  얻는 유연성(환경별 다른 주소)을 쓸 일이 없는데, 그 유연성 때문에
  빌드 모드에 따라 조용히 실패하는 경로가 생기는 게 손해가 더 컸다.
- 실패 모드가 "빈 화면"이 아니라 "완전히 조용한 빈 화면"이었다 — fetch가
  상대경로로 나가 200을 받거나 404를 받아도 에러 상태로 안 잡히니
  뭐가 잘못됐는지 알기 어려웠다. 고정값은 이 실패 모드 자체를 없앤다.

## 대가

- 백엔드 주소가 바뀌면 코드를 고쳐서 재배포해야 한다(전엔 배포
  플랫폼의 환경변수 UI만 바꾸면 됐을 것). 바뀔 일이 거의 없다고
  보고 감수한다. 정말 잦아지면 다시 env var로 되돌리되, 이번엔
  fallback을 `''`(상대경로)가 아니라 빌드 실패로 만들어 조용히
  새는 걸 막아야 한다.

## 관련: 땡겨요 오퍼 클릭 동작

같은 날 `OfferChip`의 클릭 동작도 바꿨다 — 눌러서 원문/캡처 파일명을
펼쳐 보여주던 아코디언을 없애고, 땡겨요 오퍼는 브랜드별 실제 쿠폰
공유링크(앱 전용 딥링크)로 새 탭 연결하도록 했다(`DDANGYO_LINKS` in
`src/App.jsx`). 링크 없는 오퍼(다른 플랫폼, 매핑 안 된 땡겨요 브랜드)는
그냥 정적 표시로 남는다. 별도 ADR 없이 여기 기록만 남긴다 — 백엔드
주소 결정만큼 되돌릴 여지가 있는 결정이 아니라서.

**(2026-08-01 갱신)** `DDANGYO_LINKS` 상수는 이후 제거됐다. 땡겨요
브랜드별 링크는 지금 delivery-discount-api의 `brands.yml`에
`links.ddangyo`로 이관돼 `brand.links`로 내려온다 —
프론트는 `OfferChip`에서 `brandLinks?.[offer.platform]`으로 그대로 읽는다.
