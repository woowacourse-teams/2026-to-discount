# 판독 계약

롱스크롤 캡처 이미지 한 장을 읽고 **브랜드 카드 하나당 레코드 하나**를 만든다.
자동(비전)과 수동(사람)에 동일하게 적용된다 ([ADR-008](../docs/decisions/ADR-008-manual-fallback-parity.md)).

산출물은 `schema.validate_record()`가 받아들이는 dict여야 한다.

## 절차

1. **브랜드 데이터 카드만 추출한다.** 아래는 브랜드가 아니므로 레코드를 만들지 않는다.
   - 순수 프로모션 타일 — `WOW! 와우 컬렉션`처럼 카드 자리에 끼어 있는 배너
   - 하위 페이지로 보내는 버튼 — `이츠셰프컬렉션 보러 가기`, `장보기 쿠폰북 받으러 가기` ([ADR-005](../docs/decisions/ADR-005-main-page-only.md))
2. **매장 카드와 브랜드 카드를 구분한다.** 지점명·별점·최소주문금액·거리가 붙어 있으면 매장이다
   (`처갓집양념치킨 동판교점 ★4.7 최소주문 18,000원`). 1차 범위는 브랜드뿐이므로 매장 카드는 건너뛴다.
3. 카드마다 읽는다 — 브랜드명, 카드가 속한 섹션 제목, 할인 문구 **원문 그대로**.
4. 할인 문구에서 `qualifier`(`최대`/`최소`/없음)와 숫자를 **분리해** 담는다.
5. 할인이 아니면 금액을 비우고 종류를 표시한다 (아래 §금액 판정).

## 금액 판정 — 여기가 유일한 실질 위험 지점

`최대`와 `최소`는 **큰 숫자 옆에 아주 작은 글씨로** 붙는다. 놓치면 의미가 뒤집힌다
([ADR-004](../docs/decisions/ADR-004-preserve-qualifier.md)).

- 숫자만 보고 넘어가지 말고 숫자 **왼쪽 위·왼쪽**의 작은 글자를 반드시 확인한다
- **쿠팡이츠 와우 컬렉션의 브랜드 카드**는 `최`/`대`를 가로로 안 붙이고
  숫자 왼쪽에 **세로 두 글자**(최 위, 대 아래)로 쌓아 놓는다. 카드 배율이
  작으면 이 두 글자가 통째로 안 보이거나 장식 문양처럼 뭉개져 지나치기
  쉽다(2026-08-17 실측: 30개 카드 판독에서 처음엔 놓쳤다가 재확인으로
  잡았다). 이 화면에서는 **모든 카드를 한 번 확대해서** 숫자 왼쪽에
  세로 글자가 있는지 없는지부터 확인한다 — 있으면 `최대`, 진짜 없으면
  `qualifier: null`(정액 확정. 실제로 한 화면 안에 두 종류가 섞인다).
- 확대해도 판독이 안 되면 **추측하지 말고** `qualifier: null`, `needs_review: true`
- `amount`는 정수(원). `7천원` → `7000`, `4,000원` → `4000`
- 정액이 아니면(`최대 15%`, 금액 없음) `amount: null`, `needs_review: true`
- `raw_text`는 화면 문구를 **손대지 않고** 그대로 옮긴다. 판독이 의심스러울 때 되짚을 유일한 근거다

| 화면 | qualifier | amount | offer_type |
|---|---|---|---|
| `최소 4,000원` | `"최소"` | 4000 | discount |
| `최대 7천원 할인` | `"최대"` | 7000 | discount |
| `10,000원 브랜드 할인` | `null` | 10000 | discount |
| `한정판 굿즈 증정!` | `null` | `null` | gift + `needs_review` |
| `쿠폰 받기` | `null` | `null` | coupon + `needs_review` |
| 판단 불가 | `null` | `null` | unknown + `needs_review` |

## 필드 채우는 법

`docs/specs/2026-07-26-design.md` §5 스키마를 따른다.

| 필드 | 채우는 방법 |
|---|---|
| `platform` | `baemin` / `coupangeats` / `ddangyo` |
| `page` | 캡처한 화면 이름. 예: `"브랜드관 > 오늘의 할인"` |
| `section` | 화면에 보이는 섹션 제목 **그대로** ([ADR-006](../docs/decisions/ADR-006-section-as-data.md)) |
| `brand` | 카드의 브랜드명 |
| `qualifier` `amount` `raw_text` `offer_type` `needs_review` | 위 §금액 판정 |
| `scope` | 브랜드 카드는 `"brand"` |
| `captured_at` | 캡처 시각. `YYYY-MM-DDTHH:MM:SS+09:00` |
| `target_address` `capture_mode` `screenshot_path` | 캡처 메타데이터에서 그대로 |
| `min_order_amount` `tiers` `conditions` | 쿠폰 상세를 열었을 때만 채운다 — 아래 §쿠폰 상세 판정 |
| `badge` | 목록 액면 금액이 실제로는 못 받는 상태(재고 소진)거나 매일 바뀌는 상태(랜덤박스)면 짧은 상태 라벨("선착순", "선착순 품절" 등)을 넣는다. `conditions`처럼 문장이 아니라 칩에 그대로 얹을 한두 단어. |
| `sold_out` | 브랜드 카드에 대표로 뜨는 `amount`가 품절이면 `true` — `tiers` 없이 정액 하나뿐인데 그게 품절인 경우만 쓴다. **`tiers`가 있으면 이 최상위 필드 대신 각 tier 안에 `"sold_out": true`를 넣는다** — `amount`/`min_order_amount`는 항상 지금 실제로 받을 수 있는 값이어야 하니, 품절 티어가 있어도 그게 대표값이 되면 안 된다. 예(쿠팡이츠 메가MGC커피, 2026-08-03 실측): "최대 20,000원" 티어는 품절이고 6,000원/3,000원 티어는 살아있음 → 카드 대표 `amount: 6000`, `tiers: [{"min_order": 16000, "amount": 20000, "sold_out": true}, {"min_order": 16000, "amount": 6000}, {"min_order": 16000, "amount": 3000}]`. 품절 표시는 상세(토글 펼침)에서 그 티어에만 뜬다. |

## `conditions`는 사용자에게 보이는 글이다

화면 상세에 그대로 뜨는 문장이다. **판독 과정에서 알게 된 사정은 절대
넣지 않는다.** 실제로 이런 것들이 들어가 사용자 화면에 노출됐다.

- `브랜드관/배짱할인 중복 관측, 더 큰 금액 채택` — 어느 화면에서
  주웠고 왜 그 값을 골랐는지는 판독자의 사정이다. 주문하려는 사람에게
  아무 뜻이 없다.
- `쿠폰 2종(4,000원, 6,000원) - 해당 쿠폰의 최소주문금액은 21,000원과
  30,000원입니다` — 이건 설명이 아니라 **데이터**다. `tiers`에
  `[{min_order: 21000, amount: 4000}, {min_order: 30000, amount: 6000}]`로
  들어가야 화면이 구간별로 보여줄 수 있다. 문장으로 박아두면 그 값으로
  아무것도 못 한다.

넣어도 되는 것은 **주문 전에 알아야 실제로 손해를 안 보는 조건**뿐이다 —
메뉴 한정, 채널 한정(배달/포장), 가맹점이 정한 최소주문금액이 우선한다는
안내 같은 것.

판단 기준: *그 문장을 앱 화면에서 그대로 볼 수 있는가, 아니면 우리가
작업하며 알게 된 것인가.* 후자면 넣지 않는다. 굳이 남겨야 하면 커밋
메시지나 ADR에 쓴다.

비울 때는 `null`이 아니라 빈 문자열을 쓴다 — `null`이면
`store._prefer`가 진 쪽(옛 레코드)의 값을 되채워 지운 문장이 되살아난다.

### 날짜를 쓰지 않는다

`conditions`에 `8월 11일 땡데이 이벤트` 같은 시점이 박힌 안내를 넣지
않는다. 기간 한정은 `expires_at`(구간마다 다르면 tier의 `expires_at`)이
담는다.

같은 이유가 위의 빈 문자열 규칙과 이어진다. 병합은 같은 (앱, 브랜드)
안에서만 일어나지만, 그 안에서는 옛 레코드의 문장이 새 레코드로 계속
따라온다 — 승자의 `conditions`가 비어 있고 금액이 같으면 옮겨 붙기
때문이다(`store._prefer`). 구조화된 값(`tiers`, `min_order_amount`)은
그래도 되지만 **날짜가 박힌 문장은 그러면 안 된다.** 실제로 배민
자담치킨에서 08-05에 적힌 "8월 11일 땡데이 이벤트"가 08-10 관측으로
넘어와, 그 날이 지난 뒤에도 화면에 남았다(2026-08-16 정정).

날짜를 `expires_at`으로 옮기면 만료 판정(`is_live`)이 알아서 내린다.
문장에 적으면 아무도 안 내린다.

## 쿠폰 상세 판정 — 목록에 없고 상세를 열어야 보이는 값

목록 화면의 "최대 N원"은 상세를 열어야 진짜 조건(최소주문금액 또는
그 대신 붙는 예외 조건)이 드러난다. 상세 화면에서 본 쿠폰마다 아래
넷 중 **정확히 하나**로 분류해 채운다 — 섞어 채우지 않는다.

1. **단일 최소주문금액** — `"OO원 이상 주문 시 사용 가능"` 형태로 금액
   하나만 조건이면 `min_order_amount`에 정수(원)로 넣는다. `tiers`·
   `conditions`는 `null`.
   예: `"5,000원 할인 · 25,900원 이상 주문 시 사용 가능"` →
   `min_order_amount: 25900`.
2. **구간 할인(여러 쿠폰)** — 같은 브랜드에 최소주문금액이 다른 쿠폰이
   여러 장 캐러셀로 있으면(예: 3,000원/17,000원 이상, 5,000원/30,000원
   이상) `tiers`에 `[{"min_order": 17000, "amount": 3000}, {"min_order":
   30000, "amount": 5000}, ...]`로 넣는다. 이번 파이프라인은 캐러셀
   스와이프를 자동화하지 않으므로(위 "다루지 않는 것"), 화면에 이미
   보이는 카드까지만 넣고 잘려서 안 보이는 나머지는 `conditions`에
   `"추가 쿠폰 있음, 미확인"`으로 남긴다. `min_order_amount`는 `null`.
3. **예외 조건(금액 조건이 아님)** — 최소주문금액이 아예 없고 대신
   "특정 메뉴 주문 시에만 사용 가능", "1일 1회" 같은 다른 형태 조건이면
   `min_order_amount`·`tiers`는 `null`로 두고 `conditions`에
   **`"메뉴 한정: "` 접두어 + 화면 문구 그대로**를 넣는다. 접두어로
   상세를 안 열어본 미수집(`conditions: null`)과 확인했더니 금액
   조건이 아니었던 경우를 구분한다.
   예(훌랄라참숯바베큐치킨, 배민, 2026-07-31 실측):
   `"12,100원 할인 · (순살) 참숯구이 1.5마리 (순살 반마리 증정) 사용
   가능"` → `min_order_amount: null`, `tiers: null`,
   `conditions: "메뉴 한정: (순살) 참숯구이 1.5마리 (순살 반마리 증정)
   사용 가능"`.
4. **정률(%) + 상한액** — 배민·땡겨요는 항상 정액이었지만 요기요는
   "OO% 할인, 최대 N원"(정률에 상한을 씌운 쿠폰) 형태가 있었다(실측
   2026-07-31). `tiers`에 넣되 `amount`엔 **상한액**(실제로 최대 얼마
   깎이는지)을 넣고, `percent`를 추가로 채운다:
   `{"min_order": 25000, "amount": 3000, "percent": 5}`.
   `amount`가 항상 "이 구간 최대 할인액(원)"을 뜻한다는 규칙은 정액이든
   정률+상한이든 그대로 유지된다 — `percent` 유무로 정액/정률만
   구분한다. 이 케이스는 `min_order_amount`는 안 쓴다(단일이어도
   `tiers`로 넣는다 — `percent`를 실을 자리가 `min_order_amount`엔
   없어서).
   예(굽네치킨, 요기요, 2026-07-31 실측): "25,000원 이상 주문 시 5%,
   최대 3,000원 할인" →
   `tiers: [{"min_order": 25000, "amount": 3000, "percent": 5}]`.

상세를 아직 안 열어봤으면 셋(위 1~3) 다 `null`로 둔다(현재 원장 대부분의
상태) — "미수집"과 "확인했지만 조건이 없음"을 스키마상으로 구분하지
않는다. 이번 예외 조건 처리는 이 구분까지는 넓히지 않는다(범위 밖).

5. **채널별 별개 쿠폰(배달/포장/매장식사)** — 같은 `min_order`에 `amount`만
   다른 카드가 여러 장이면 구간 할인(위 2번)이 아니다. 구간 할인은
   `min_order`가 달라야 성립한다 — 같은데 금액만 다르면 배달/포장/매장식사
   등 주문 채널마다 금액이 다른 별개 쿠폰이 한 브랜드에 묶여 보이는
   것이다. 이때 `tiers`의 각 항목에 `channel`을 추가한다:
   `{"min_order": 19900, "amount": 4000, "channel": "배달"}`. 화면에 채널
   배지가 안 보이면(카드에 라벨이 없거나 확인 못 했으면) `channel`을
   비우지 말고 상세를 다시 확인하거나 `conditions`에 "채널별 상이 쿠폰
   의심, 채널 미확인"으로 남긴다 — 라벨 없이 임의로 배달/포장을
   추측해 채우지 않는다.
   예(바른치킨, 땡겨요, 2026-08-01 실측): "바른치킨 4,000원 할인 /
   5,000원 할인 / 해당 쿠폰의 최소주문금액은 19,900원 입니다." →
   `tiers: [{"min_order": 19900, "amount": 4000, "channel": "배달"},
   {"min_order": 19900, "amount": 5000, "channel": "포장"}]` (앱에서
   직접 확인해 순서=채널 매핑 확정).
   예(도미노피자, 땡겨요, 2026-08-01 실측): "도미노피자 8,000원
   할인(포장)/7,000원 할인(배달) / 해당 쿠폰의 최소주문금액은
   21,900원입니다." → 화면 문구에 채널이 명시돼 있으므로 그대로
   `tiers: [{"min_order": 21900, "amount": 8000, "channel": "포장"},
   {"min_order": 21900, "amount": 7000, "channel": "배달"}]`.

## 최소주문금액이 화면 어디에 있나 — 앱별 (2026-08-24 실측)

위 넷 중 무엇인지 고르려면 먼저 **화면에서 그 값을 찾아야** 한다. 앱마다
자리가 다르고, 잘못 찾으면 남의 값을 그 브랜드 것으로 적게 된다.

### 요기요 — 브랜드 할인 박스 안에서만 본다

상세 화면은 위에서부터 이렇게 생겼다.

```
네네치킨
최대 6,000원 할인            <- 헤드라인. 상한이지 확정값이 아니다
3,000원 추가할인  18,000원 이상 주문 시   <- 브랜드 조건
최대 3,000원 쿠폰            [쿠폰받기]
─────────────────────────────────────
브랜드 할인 외에 가게별로 추가 할인이 있을 수 있어요.   <- 경계
내 주변 가까운 가게
  네네치킨-삼송역점  3,000원 추가할인       <- 가게별. 여기를 읽으면 안 된다
```

**경계 아래는 가게 층위다.** 경계를 안 두고 화면 전체에서
`"N원 이상 주문 시"`를 찾으면, 브랜드 조건이 없는 화면에서 어느 가게의
값을 브랜드 값으로 집는다. 2026-08-17 세븐일레븐이 그렇게
`"23,000원 이상 500원"`으로 기록됐다 — 실제 브랜드 할인은 "최대 5,000원"
이고 500원은 어느 가게 값이었다. 게다가 "최대"가 떨어져 불확정 헤드라인이
확정 정액이 됐다.

경계 문구는 `"브랜드 할인 외에"` / `"내 주변 가까운 가게"`다
(`capture/yogiyo.py`의 `DETAIL_BRAND_BOX_END`).

**쿠폰 시트는 두 모양이다.** `쿠폰받기`를 누르면 뜨는데, 정률 쿠폰은
한 줄로 붙어 있고 편의점 계열은 노드로 쪼개져 있다.

```
정률(한 줄)   20,000원 이상 주문 시 최대 3,000원 할인

정액(쪼개짐)  할인 쿠폰 (2)
              배달  5,000원  20,000원 이상 주문 시  쿠폰받기  26.08.23까지
              포장  4,000원  14,900원 이상 주문 시  쿠폰받기  26.08.31까지
```

쪼개진 쪽은 채널별로 여러 장이고 만료일도 쿠폰마다 다르다. 한 정규식으로
못 묶어 `parse_coupon_sheet`(정률)와 `parse_coupon_rows`(정액)로 나뉜다.
2026-08-23에 편의점 여섯 브랜드가 통째로 값 없이 나왔는데, 화면에는 조건이
멀쩡히 있었다.

**조건이 아예 없는 브랜드가 있다.** 편의점·일부 패스트푸드는 상세에
최소주문금액 문구가 없고 헤드라인만 있다. 그때는 `"최대 N원"`을
`qualifier: "최대"`로 적는다 — 상한이라 확정 정액으로 적으면 안 된다.
맥도날드처럼 `"최대 9% 할인 / 배달 9% 메뉴할인, 할인랭킹 메뉴 한정"`이면
정률이고 최소주문금액 형태가 아니다.

### 땡겨요 — 목록에 다 있다

목록 행이 `"18,900원 이상 5,000원(배달/포장)"` 꼴이라 카드를 열지 않는다.
채널이 괄호 안에 명시되고, 채널마다 금액·문턱이 다르면 슬래시로 나뉜 두
줄이 된다.

```
21,900원 이상 8,000원(포장) / 21,900원 이상 7,000원(배달)
```

원장 `raw_text`는 이 표기를 그대로 쓴다. 대조할 때도 이 표기를 되읽으므로
바꾸지 말 것 — 채널을 안 펼치면 다채널 브랜드마다 가짜 불일치가 뜬다.

### 배민 — 딥링크 상세에만 있다

브랜드관 목록에는 대표 할인액만 있고(`"3,000원 브랜드 할인"`) 최소주문금액이
없다. 조건은 `brands.yml`의 딥링크로 상세를 열어야 나온다.

그래서 둘을 겹쳐 쓴다 — **브랜드관이 "무엇이 있는가", 딥링크가 "조건이
무엇인가"**를 답한다. 브랜드관은 딥링크 없는 브랜드도 보여주므로 전수
확인에 쓰고(2026-08-24: 93개, 딥링크는 69개), 조건이 필요한 브랜드만
딥링크로 판다.

딥링크가 브랜드 상세가 아니라 공용 쿠폰 목록으로 가는 경우가 있다. 그러면
`tiers`는 비고 `exceptions`에 남의 브랜드 조건이 통째로 딸려 온다
(2026-08-24 유가네닭갈비: 13개 브랜드 조건). **`exceptions`만 있고
`tiers`가 비면 값을 읽은 게 아니다.**

## `conditions`·`badge` 문구는 핵심만 — 산문 금지

`conditions`와 `badge`는 화면에 보여줄 안내문이지 조사 리포트가 아니다.
**핵심 사실 한둘만, 짧은 명사구로.** "확인 시점", "~로 보인다", "~였음"
같은 서술형 문장·시제·조사 과정 서술을 넣지 않는다. 구조화 가능한
값(금액·최소주문금액·구간·채널)은 절대 `conditions` 산문 안에 묻지
않는다 — 위 1~5번대로 `min_order_amount`/`tiers`/`badge`에 각각
채우고, `conditions`엔 그 필드들로 못 담는 나머지 한 줄만 남긴다.

- 나쁜 예: `"와우회원 전용 랜덤박스 쿠폰 — 매일 무작위 금액 지급,
  \"최대 2만원\"은 상한 표기일 뿐. 2026-08-03 확인 시 3,000원
  당첨(18,000원 이상 주문 시, 당일 08-03까지만 사용 가능)"`
- 좋은 예: `min_order_amount: 18000`, `badge: "쿠팡와우 대상, 최대
  20,000원 랜덤박스"`, `conditions: null`(더 남길 핵심이 없으면 비운다)
