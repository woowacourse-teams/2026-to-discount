# ADR-016. 같은 (앱, 브랜드) 중복 정리는 확정을 최신보다 우선하고, 상세는 병합한다

- 날짜: 2026-07-29
- 상태: 확정
- 관련: [ADR-004](ADR-004-preserve-qualifier.md), API
  [ADR-006](../../../delivery-discount-api/docs/decisions/ADR-006-dedup-merges-loser-detail.md)

## 맥락

`store.latest_per_brand`는 같은 (앱, 브랜드)에 원장 줄이 여럿이면
`captured_at`이 최신인 것만 남겼다. 재확인 캡처가 곧 최신 정보라는
가정이었다.

이 가정이 깨지는 경우를 실제로 겪었다. 기존에 확정(금액 있고
`needs_review` 아님)으로 잡힌 큰 금액이 있는 상태에서, 나중에 같은
브랜드를 재확인하며 조건 설명만 추가로 캡처(`needs_review: true`)했더니,
그게 "더 최신"이라는 이유만으로 예전의 확정된 금액을 완전히 밀어내고
`export.json`에 들어가 버렸다. API가 받기도 전에 원장 단계에서 이미
손실된 것이었다 — API 쪽 `Offer.preferredOver`가 확정을 우선하도록
고쳐놨어도, 애초에 원장 단계에서 확정 레코드 자체가 사라졌으니 소용이
없었다.

## 판단

`latest_per_brand`(정확히는 새 헬퍼 `_prefer`)가 다음 규칙으로 승자를
고른다.

1. 확정(`amount`가 있고 `needs_review`가 아님)이 보류를 이긴다 — recency와
   무관하게.
2. 같은 등급이면 `captured_at`이 최신인 쪽이 이긴다(기존 동작 유지).
3. 진 쪽의 `min_order_amount`/`tiers`/`conditions`는 이긴 쪽에 그 값이
   비어 있을 때만 옮겨 붙인다.

## 근거

- **"최신"과 "확실함"은 다른 축이다.** 재확인 캡처가 항상 더 정확한 게
  아니다 — 이번 사례처럼 조건만 급하게 캡처하며 `needs_review`로
  표시한 기록이 오히려 신뢰도가 낮을 수 있다.
- **3번(상세 병합)이 없으면 2번짜리 캡처가 무의미해진다.** 이미 확정된
  숫자를 재확인하며 조건만 새로 알아낸 경우, 그 조건을 남길 방법이
  "밀어내기"뿐이라면 항상 확정값을 희생해야 한다. 병합은 그 트레이드
  오프를 없앤다.
- API의 `Offer.preferredOver`도 같은 규칙으로 고쳤다(API ADR-006). 두
  레이어가 다른 규칙을 쓰면 어느 쪽을 거치느냐에 따라 결과가 달라지는
  버그가 다시 생긴다.

## 결과

- `store.py`: `_is_confirmed`/`_prefer` 헬퍼 추가, `latest_per_brand`가
  이를 사용.
- 기존 테스트(`test_latest_per_brand_picks_most_recent`, 둘 다 확정인
  케이스)는 그대로 통과 — recency 우선은 "같은 등급일 때"로 좁혀졌을
  뿐이다.
- 새 테스트 2건: 확정이 최신 보류를 이기는 경우, 승자가 이미 상세를
  갖고 있으면 병합하지 않는 경우.

## 뒤집을 조건

"재확인 캡처는 항상 더 정확하다"고 신뢰할 수 있는 별도 신호(예: 사람이
명시적으로 "정정" 표시를 다는 기능)가 생기면, 그 신호가 있는 캡처는
확정 여부와 무관하게 최신을 우선하도록 예외를 둘 수 있다. 지금은 그런
신호가 없다.
