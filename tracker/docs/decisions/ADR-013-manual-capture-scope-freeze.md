# ADR-013. 자동 스크롤 캡처는 배민에서 멈추고, 나머지는 수동 캡처+비전 판독으로 확정

- 날짜: 2026-07-27
- 상태: 확정
- 관련: [ADR-008](ADR-008-manual-fallback-parity.md), [ADR-011](ADR-011-deeplink-entry-over-tap-path.md)

## 맥락

원래 계획(README·설계 명세)은 배민·쿠팡이츠·땡겨요 3개 앱 모두에 대해
`capture(platform)` 자동 롱스크롤 캡처를 구현하는 것이었다. 배민은
됐다(`capture/baemin.py`, 딥링크 진입 + 스크롤 스티칭). 쿠팡이츠·땡겨요는
아직이었다.

구현 도중 이 자동화의 실제 비용이 드러났다. 앱마다 화면 구조가
다르고(쿠팡이츠는 WebView+이미지 혼재, 땡겨요는 100% 이미지 배너 —
추출 가능한 텍스트가 아예 없음), 화면 진입 경로도 앱마다 새로 조사해야
하고, 프로모션 모달이 그날그날 떠서 고정 좌표 탭이 깨지는 문제가
이미 배민에서도 나왔다(ADR-011의 배경).

## 판단

배민 외 나머지 앱(쿠팡이츠·땡겨요·요기요)은 자동 스크롤 캡처를
구현하지 않는다. 사람이 폰 화면을 직접 캡처(스크린샷)하고, 그 이미지를
비전으로 판독해 표준 레코드로 바꾸는 경로로 확정한다. `capture_mode:
manual`은 ADR-008이 이미 정의한 대로 자동 산출물과 동일한 계약(이미지 +
메타데이터)을 따르므로, `parse` 이후 파이프라인은 코드 변경이 없다.

## 근거

- **판독(비전)이 유일한 실질 비용**이라는 게 이 프로젝트의 핵심
  전제(README "알아둘 것 세 가지" #1)였다. 스크롤 자동화는 그 비용을
  줄이지 못한다 — 어차피 비전이 이미지를 읽어야 한다. 자동화가 아끼는
  건 "사람이 스크린샷 찍는 수고"뿐인데, 이 프로젝트의 갱신 주기(하루
  2회 정도로 설계됨)에서 그 수고는 무시할 만큼 작다.
- 반면 앱별 자동화 비용은 크다 — 화면 진입 경로 조사, 좌표 실측,
  프로모션 모달 대응, 앱 업데이트마다 재검증. 배민 하나에서도 이미
  액티비티 판정을 앱 버전에 견디게 완화해야 했다(커밋
  `e3d4c48`).
- 사용자의 명시적 판단(2026-07-27): "화면 스와이프/캡처 자동화 힘들면
  그냥 이미지 인식만 해라 — 캡처해서 넘겨주는 건 얼마든지 가능하니까."
  자동화에 들어갈 자원을, 캡처된 이미지들을 판독해 브랜드별로 취합해
  보여주는 MVP 쪽에 쓰는 게 낫다는 판단.

## 대가

- 무인 스케줄 실행이 불가능하다 — 사람이 매번 화면을 열고 캡처해야
  한다. 이 프로젝트 규모(브랜드 할인 배너, 하루 몇 회)에서는 감수할
  만하다.
- 데이터 신선도가 사람 손에 달린다. 2026-07-28에 이미 한 번,
  땡겨요의 "오늘 땡길만한 브랜드" 목록을 재확인해 기존 캡처(07-27)와
  값이 동일함을 확인한 사례가 있다 — 하루 단위로는 안정적이었다.

## 뒤집을 조건

브랜드 할인 갱신 빈도가 하루 여러 번으로 잦아지거나, 캡처할 매장 수가
많아져 사람이 감당 못 하는 규모가 되면 재검토한다. 그때는 ADR-002/009가
남긴 실기 기반 인프라를 그대로 재사용할 수 있다 — 코드가 안 바뀌므로
(ADR-009 근거 참고).
