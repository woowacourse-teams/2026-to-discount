# ADR-032. 브랜드 페이지 전수조사는 하루 한 번, 죽은 링크는 주간 주기로

- 날짜: 2026-09-17
- 상태: 확정 (사용자 결정, 브레인스토밍 뒤)
- 관련: [ADR-025](ADR-025-single-source-for-sweep-targets.md), [ADR-031](ADR-031-open-baemin-brand-pages-by-resolved-url.md),
  `docs/setup/ROUTINE-TIMING.md`, `docs/superpowers/specs/2026-09-17-audit-runtime-design.md`

## 맥락

예약 실행 한 바퀴 70~90분 중 4단계 전수조사가 48분(55%). 그중 배민 29분은
링크 오류 30곳을 하루 3번 × 2회씩 두드리는 낭비였다. `last_checked`가 값 읽힌
브랜드만 적어서 실패한 브랜드는 영원히 "미확인"이었다. 낮 실행(10:55, 15:55)도 같은
전수조사를 돌아 폰을 하루 4시간 잡았다. 브랜드관 값은 하루 안에 안 바뀐다(주간 주기).

## 결정

1. **전수조사(단계 4)는 00:01 실행만.** 낮 실행은 건너뛰고 로그에 `-- 4) full_audit
   건너뜀` 한 줄(판정 PASS). **월요일은 세 번 다**. 주간 주기가 새로 열려 대상이 몰린다.
   `run_routine.py`의 `RUN_AUDIT` = 시각 < 03시 또는 월요일.
2. **죽은 링크 장부** `data/dead_links.json`: 링크 오류가 3회 연속(하루 1회로 셈)이면 그
   브랜드는 `last_checked`와 같은 **주간 주기(월요일)** 에만 다시 본다. 값이 읽히면
   장부에서 지운다. 재시도 패스는 링크 오류를 뺀다.
3. **사람 몫이 명확하다**: 로그 `죽은 링크 장부 N곳`, `check_routine` 판정에 수 표기,
   `audit-<날짜>.md` 끝 표(앱, 브랜드, 연속 실패, 처음, 마지막, 오류) → 사람이 `brands.yml`
   링크를 고침 → 다음 월요일 확인 → 되살아나면 자동 삭제. ROUTINE-SPEC 단계 4.

## 결과

- 실측(09-17 02:57): 4단계 48 → 25.5분, 배민 29 → 18분, 판독 실패 35 → 5.
  낮 실행 90 → 25분(03:24, 03:51 실기). 00:01 실행 예상 ~55분.
- 장부가 낭비를 줄이는 동안 **산출이 0인 진짜 원인**(단축링크 라우팅)은 따로
  드러났다. ADR-031이 다룬다. 장부 규칙은 그 뒤에도 유효하다.

## 하지 않은 것

- 브랜드를 두 폰에 쪼개는 병렬(접근 C). 산출 0 문제와 무관하고 같은 계정 동시
  로그인 위험. 앱 단위 병렬은 조율기(`run_routine.py`)가 맡는다.
