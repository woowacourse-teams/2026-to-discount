# ADR-019. 겹쳐 쓰는 쿠폰은 `tier_mode`로 표현하고, 정률 상한액은 `cap`으로 분리한다

- 날짜: 2026-08-13
- 상태: 확정
- 관련: [ADR-004](ADR-004-preserve-qualifier.md), [ADR-014](ADR-014-coupangeats-record-guaranteed-floor.md),
  [ADR-016](ADR-016-confirmed-beats-recency-on-dedup.md),
  api [ADR-010](../../../delivery-discount-api/docs/decisions/ADR-010-domain-judges-representative-amount.md),
  설계: [겹쳐 쓰는 쿠폰 설계](../superpowers/specs/2026-08-13-cumulative-coupons-design.md)

## 맥락

요기요는 브랜드 하나에 쿠폰을 두 장 건다 — 고정 메뉴할인과 정률 쿠폰이고,
**둘을 겹쳐 쓸 수 있다.** 굽네치킨 실측(2026-07-31):

```
"4,000원 메뉴할인, 17,000원 이상 구매 시
 / 5%, 25,000원 이상 주문 시 최대 3,000원 할인"
```

그런데 `tiers`는 "주문금액 구간별 **차등** 할인"이라는 뜻으로 정의돼 있다
(`DiscountTier` javadoc: "그 중 가장 큰 amount가 곧 그 최대 n원"). 겹침을
표현할 자리가 없어서 API가 둘 중 큰 값 하나만 고른다.

여기에 두 번째 문제가 겹쳐 있었다. **정률 tier의 `amount`는 그 문턱에서
받는 금액이 아니라 상한액(cap)이다.** 25,000원의 5%는 1,250원이고 3,000원에
닿으려면 60,000원을 시켜야 한다. 같은 필드가 정액 tier에서는 "받는 금액",
정률 tier에서는 "최대로 받을 금액"을 뜻한다.

이 모호함은 이론적인 게 아니다. 이 ADR을 쓰는 세션에서 실제로 25,000원
주문의 할인을 4,000 + 3,000 = 7,000원으로 잘못 읽었다. 사람이 틀리는
스키마다.

## 판단

**1. 레코드에 `tier_mode`를 둔다.**

```
tier_mode: "exclusive"(기본) | "cumulative"
```

`exclusive`는 지금까지의 택일 해석이고, `cumulative`는 문턱을 넘을수록
쿠폰이 겹친다는 뜻이다. 기본값이 `exclusive`라 기존 원장 170건은 한 줄도
안 고친다.

tier 레벨이 아니라 레코드 레벨이다 — 읽는 쪽이 tier를 하나씩 살펴
"이건 겹치나"를 판단하지 않고 레코드 한 번에 갈래를 정한다.

**2. 정률의 상한액을 `cap`으로 분리한다.**

`amount`는 이제 어느 tier에서든 **"이 문턱에서 실제 받는 금액(원)"** 하나만
뜻한다.

```
{min_order: 25000, amount: 1250, percent: 5, cap: 3000}
```

`percent`와 `cap`은 동반 필수다 — 한쪽만 있으면 스키마가 거부한다.

**3. 카드 대표값은 사다리의 최저 문턱 값이고, `qualifier`는 `"최소"`다.**

```
17,000원 이상 → 4,000
25,000원 이상 → 4,000 + 1,250 = 5,250
```

대표값 4,000원. 이보다 적게 받는 경우가 없다.

## 근거

- **ADR-014와 같은 사고방식이다.** 쿠팡이츠에서 헤드라인(상한)을 버리고
  보장 바닥값을 기록하기로 한 것과 똑같이, 여기서도 조건부 상단이 아니라
  누구나 받는 금액을 대표로 삼는다.
- **과대 표시가 과소 표시보다 나쁘다.** 25,000원 문턱값(5,250원)을 대표로
  쓰면 17,000~24,999원 주문자에게 거짓말이 된다. 앱에 가서 확인했을 때
  액면보다 적게 받으면 그게 곧 신뢰 상실이고, 이 프로젝트가 1순위로 꼽는
  리스크다. 반대 방향 오차는 "생각보다 더 받았다"라 해가 없다.
- **`cap` 분리는 데이터 손실을 막는 게 아니라 오독을 막는다.** 필드 하나가
  두 뜻을 가지면 다음 사람이(또는 미래의 내가) 틀린다. 이미 한 번 틀렸다.
- **기본값을 `exclusive`로 둬서 마이그레이션을 정률 tier 7건으로 가둔다.**
  전수 변환이 필요한 설계였다면 이 시점에 치를 비용이 아니었다.

## 대안과 기각 사유

**tier 레벨 `stacks: true`** — tier마다 개별 표시. "무엇에 겹치는가"가
모호해지고 `channel`처럼 해석 규칙을 주석으로 버텨야 한다. 레코드 레벨이면
그 질문 자체가 생기지 않는다.

**tier에 `group` 키를 두고 같은 그룹은 택일, 다른 그룹은 합산** — 가장
일반적이고 "메뉴할인 3장 중 택일 + 정률 겹침" 같은 미래 구조까지 커버한다.
지금 필요한 건 2단뿐이라 과잉이다.

**`tiers`를 쿠폰 배열로 승격하는 전면 재설계** — Medusa와 schema.org는 둘 다
"조건이 다른 혜택은 별개 엔티티"로 모델링한다(schema.org는 `priceSpecification`
배열, 멤버십 조건까지 `validForMemberTier`로 표준화). 방향은 이쪽이 맞고
[브랜드 상세 수집 계획](../plans/2026-07-29-offer-detail-collection.md)의
중단된 sealed 타입 방향이 사실상 그것이다. 다만 요기요 2단 하나 때문에 원장
363건과 테스트 48개를 전면 개편할 때가 아니다. `tier_mode`는 나중에 그쪽으로
갈 때도 그대로 "쿠폰이 여러 장"이라는 뜻이라 버려지지 않는다.

## 결과

- 원장 7건 수정(요기요 6건에 `tier_mode: cumulative`, 정률 tier 7개에 `cap` 분리).
- 화면에 보이는 변화는 배민 커피앳웍스 하나 — 대표값 5,000원 → 1,800원.
  5,000원은 10% 상한이라 50,000원어치를 시켜야 받는 금액이었다.
- 요기요 6건은 2026-08-10 스윕에 안 잡혀 지금 export에 없다. 이 설계는 그
  재수집분이 들어올 자리를 먼저 만드는 것이다.

## 부칙 — 단일 tier 정률 레코드의 qualifier

`tier_mode: cumulative` 레코드는 `qualifier: "최소"`가 스키마로 강제된다.
반면 커피앳웍스(배민)처럼 `exclusive`이면서 tier가 하나뿐인 정률 레코드는
`amount: 1800`(18000 × 10%, `cap: 5000`)도 "더 시키면 더 받는" 값이라는
점에서 성격은 같지만 `qualifier`는 `null`로 남는다. 이는 의도된 비대칭이다.

`cumulative`에 `"최소"`가 필요한 이유는 여러 쿠폰 문턱을 하나의 대표값으로
뭉쳐서 보여줄 때, 앱 자체는 그 뭉친 숫자를 한 번도 보여준 적이 없기
때문이다 — 그 모호함을 해소할 라벨이 필요하다. 반면 단일 tier 레코드는
뭉갤 것이 없다. 숫자는 하나뿐이고, 앱도 그 숫자를 별도로 qualify하지
않았다. ADR-004의 raw text 충실성 원칙대로 앱이 보여준 그대로 두는 것이
맞고, `qualifier`를 강제로 채우는 것은 앱이 말하지 않은 것을 지어내는
셈이다.

## 뒤집을 조건

- 한 레코드 안에서 "택일 쿠폰과 겹침 쿠폰이 섞이는" 사례가 실제로 나오면
  레코드 레벨 `tier_mode`로는 못 담는다. 그때 tier 레벨 `group` 키로 옮긴다.
- 겹침 조합이 앱마다 달라져 규칙이 갈라지기 시작하면 전면 재설계(쿠폰 배열)
  시점이다.
- 정률 쿠폰이 상한 없이 나오면 `cap` 동반 필수 규칙을 완화해야 한다.


## 갱신 (2026-08-19): 대표값을 사다리 꼭대기로, 배지를 `최적`으로

위 "판단 3"(대표값 = 사다리 최저 문턱, `qualifier: "최소"`)을 뒤집는다.

**왜.** 최저 문턱을 쓰면 굽네치킨 카드가 4,000원으로 뜬다. 그 숫자만으로는
정률 쿠폰을 겹칠 수 있다는 사실이 화면 어디에도 없다 — 겹침을 따로
모델링한 의미가 사라진다.

**바뀐 것.**

```
대표값  = 사다리 꼭대기(쿠폰을 다 겹쳤을 때)   4,000 -> 5,250
배지    = "최소" -> "최적"
```

`export_data.ladder_floor()` -> `ladder_best()`,
API `DiscountLadder.floorAmount()` -> `bestAmount()`. 두 레이어는 여전히
같은 숫자를 내야 한다(ADR-016).

**과대 표시 우려는 배지와 상세로 막는다.** 원안이 걱정한 것은
"17,000~24,999원 주문자에게 5,250원은 거짓말"이라는 점이었고 그 지적은
지금도 옳다. 다만 답이 숫자를 낮추는 것일 필요는 없다 — `최적`은 조건을
다 맞췄을 때의 값이라는 뜻이고, 칩을 펼치면 문턱별 사다리가 그대로 보여
4,000원만 받는 구간이 감춰지지 않는다. `최대`가 `불확정`으로 표시되는
것과 같은 계열의 라벨이다.

**원장은 append-only라 과거 `최소` 행이 남는다.** 스키마는 두 값을 다
통과시키고(`CUMULATIVE_QUALIFIERS`), 지금 화면에 나가는 레코드가 `최적`을
쓰는지는 `test_live_cumulative_records_use_the_optimal_qualifier`가 승자만
골라 검사한다. 규칙이 바뀔 때마다 역사 전체가 무효가 되면 검증이 역사를
깨뜨리는 셈이다.
