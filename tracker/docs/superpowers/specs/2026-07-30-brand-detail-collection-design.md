# 브랜드별 쿠폰 상세 수집 파이프라인 (배민·땡겨요)

작성일: 2026-07-30 · 상태: 설계 승인, 구현 계획 전 단계

## 왜 필요한가

원장 107건 중 `min_order_amount`가 채워진 건 0건이다. 화면엔 "최대
N원"까지만 뜨고 실제 얼마를 아끼는지 모른다. 이 값은 목록 화면에 없고
**쿠폰 상세를 열어야** 보인다 — 지금까지는 사람이 폰에서 직접 브랜드
카드를 눌러가며 캡처했다(`docs/plans/2026-07-29-offer-detail-collection.md`).
이 수동 세션에서 실제로 사고가 났다: 뒤로가기 직후 다른 카드를 눌러
직전 상세로 되돌아가는 현상 반복, recents 오탭으로 배민 캡처를 땡겨요로
잘못 재분류(원복 완료), ADB 연결 두 차례 끊김.

## 범위

**대상**: 배민·땡겨요만(쿠팡이츠·요기요는 이번 범위 밖).

**우선순위 브랜드**: 원장에서 앱 2개 이상에 걸린 브랜드 18개(계산
결과, 아래 "우선순위 산출" 참고). needs_review+"최대" tier는 배민·
땡겨요엔 사실상 1건(땡겨요 피자헛, 이미 18개 안에 포함)이라 별도로
안 다룬다.

- 땡겨요: 18개 중 17개가 걸림 — 그러나 **전수를 훑는다**(아래 이유)
- 배민: 18개 중 8개(꾸브라꼬숯불치킨·네네치킨·도미노피자·뚜레쥬르·
  파스쿠찌·프레드피자·피자헛·훌랄라참숯바베큐치킨) — **이 8개만
  타겟팅**

**전수 대신 targeted로 안 가는 이유(땡겨요)**: 땡겨요 브랜드관은 카드가
100% 이미지 배너라 UI 트리에 브랜드명 텍스트가 전혀 없다(실측 확인,
아래 "현장 조사" 참고). 특정 브랜드 카드를 이름으로 찾아 탭하는 게
원천적으로 불가능하다. 반면 브랜드 수가 적고 대부분 같은 패턴("최대
N원 할인")이라 전수 캡처 비용이 낮다 — 사용자 판단(2026-07-30).

**타겟팅으로 가는 이유(배민)**: 배민 브랜드관은 웹뷰라 카드에 실제
텍스트가 있다(`"{브랜드명} 찜하기"` content-desc로 확인). 이름으로
바로 찾아 탭할 수 있으니 관계없는 브랜드까지 다 열 이유가 없다.

## 현장 조사 (2026-07-30, 실기 e7f06aaf 확인)

- 땡겨요(`com.shinhan.o2o`) 브랜드관 UI 덤프: 카테고리 탭 라벨 외엔
  텍스트 없음. 카드는 `clickable="true" focusable="false"`로 균등
  간격 배치된 풀폭 블록(예: `[49,336][1029,687]`, `[49,714][1029,1068]`,
  ...) — 브랜드명은 몰라도 **카드 목록을 위치로는 안정적으로 enumerate
  가능**.
- 배민(`com.sampleapp`) 브랜드관 UI 덤프: `"훌랄라참숯바베큐치킨
  찜하기"`, `"피자헛 찜하기"` 등 브랜드명이 그대로 텍스트로 잡힘 —
  이름으로 노드 검색 가능.
- 기존 `capture/baemin.py`의 `open_brand_lounge()`(딥링크 진입)는 이번
  조사에서 정상 동작 재확인 — 그대로 재사용.
- 땡겨요는 진입 딥링크가 없다(`docs/plans/2026-07-29-offer-detail-collection.md`
  기록) — 앱을 이미 브랜드관에 띄워둔 상태에서 시작한다는 전제.
  (오늘 세션도 마찬가지로 두 앱 다 이미 실행 중인 상태에서 조사함.)

## 아키텍처

`capture/common.py`의 기존 유틸(run_adb, dump_ui/find_node_bounds,
wait_for_activity, screenshot)을 그대로 재사용한다. 새 코드는 두
플랫폼별 순회 로직 + 공용 뒤로가기 검증 헬퍼.

```
capture/
  common.py          (기존, 무변경)
  baemin.py          (기존 open_brand_lounge 재사용, 상세 수집 함수 추가)
  ddangyo.py          (신규 — 리스트 카드 enumerate, 전수 순회)
  detail_sweep.py     (신규 — 공용: 뒤로가기+검증, 캡처 저장, 두 플랫폼 진입점)
```

**계약은 기존과 동일하게 유지한다**: 이 파이프라인의 산출물은
스크린샷(+파일명에 담긴 메타데이터)까지다. 브랜드 식별·금액 판독은
이번에도 비전(나 자신)이 사람이 캡처한 것과 똑같이 읽고
`tracker.py append-record`로 원장에 넣는다. `parse/CONTRACT.md`의
계약이 안 바뀐다 — capture 결과물이 늘어날 뿐.

## 플랫폼별 흐름

### 배민 — 타겟팅

1. `open_brand_lounge()`로 브랜드관 진입(기존 함수)
2. 대상 브랜드 8개를 순회. 각각:
   - `dump_ui()`에서 `"{브랜드명} 찜하기"` 텍스트를 가진 노드 검색
   - 못 찾으면(스크롤 더 필요) 아래로 스크롤 후 재시도, N회 실패 시
     해당 브랜드 스킵 + 로그
   - 찾으면 그 카드 영역(찜하기 버튼이 아니라 카드 컨테이너) 탭
   - 상세 화면 캡처(스크린샷, 필요하면 짧게 스크롤)
   - 뒤로가기 → **검증**: `dump_ui()`에 브랜드관 타이틀
     `"배달의민족 브랜드관"`이 다시 보이는지 확인. 안 보이면 재시도(최대
     3회), 그래도 안 되면 전체 중단(원장을 이상한 상태로 계속 진행하지
     않는다)

### 땡겨요 — 전수 순회

1. 이미 브랜드관 화면이라고 가정(진입 딥링크 없음 — 전제 조건, 아래
   "전제 조건" 참고)
2. `dump_ui()`에서 카드 컨테이너(균등 간격 blocks, 위 조사 결과 패턴)를
   화면에 보이는 순서대로 목록화
3. 순서대로: 탭 → 캡처 → 뒤로가기 → **검증**(타이틀
   `"오늘 땡길만한 브랜드"` 재확인, 배민과 동일한 재시도/중단 규칙) →
   다음
4. 화면 하단까지 가면 스크롤 후 다시 카드 목록화, 이미 처리한 카드와
   안 겹치게(스크롤 전/후 카드 bounds가 완전히 같으면 바닥으로 보고
   종료)

### 공용: 뒤로가기 검증

기존 사고(뒤로가기 직후 엉뚱한 상세로 재진입)의 재발 방지가 핵심이라
별도 함수로 뽑는다:

```python
def go_back_and_verify(serial, expected_title_text, retries=3):
    for _ in range(retries):
        run_adb(serial, "shell", "input", "keyevent", "KEYCODE_BACK")
        time.sleep(1.5)
        if expected_title_text in dump_ui(serial):
            return
    raise RuntimeError(f"뒤로가기 검증 실패: {expected_title_text!r} 안 보임")
```

## 전제 조건 / 사람이 할 일

- 두 앱 모두 **브랜드관 화면에 미리 띄워둔 상태**에서 스크립트를 시작한다
  (땡겨요는 진입 딥링크가 없어 자동화 밖 — 기존에도 그랬음)
- 실행 전 로그인 상태 확인(기존 원칙, 사람이 1회 수행)
- ADB 연결 끊김: 스크립트가 자동 복구하지 않는다. 실패하면 멈추고
  에러 메시지로 알린다 — 사람이 `adb kill-server`/`start-server`로
  살리고 재실행. 이미 처리한 브랜드는 캡처 파일이 남아있으므로 처음부터
  다시 돌 필요는 없다(멱등성은 "이미 파일 있으면 스킵" 정도로 단순하게)

## 다루지 않는 것 (명시적 제외)

- **캐러셀(다중 쿠폰) 스와이프**: 자동화 안 함. 보이는 첫 쿠폰만
  캡처하고, 추가 쿠폰이 있어 보이면(캐러셀 인디케이터 등) 그건 비전이
  읽을 때 판단할 몫 — 기존 컨벤션(`conditions`에 "추가 쿠폰 있음,
  미확인" 식) 그대로
- **쿠팡이츠·요기요**: 이번 파이프라인 대상 아님
- **브랜드 판독/금액 파싱**: 캡처까지만. 비전이 읽어서 원장에 넣는 건
  기존 수동 흐름 그대로(자동화 안 함)
- **무인 스케줄 실행**: ADR-013 기조 유지 — 사람(나)이 트리거해서
  돌리는 도구. 크론 등으로 무인 실행하지 않는다

## 우선순위 산출 (재현 가능한 쿼리)

앞으로 재실행할 때를 위해 계산 로직을 남긴다 — 하드코딩한 브랜드
목록이 아니라 원장에서 매번 다시 뽑는다:

```python
by_brand = defaultdict(set)
for r in records:
    by_brand[r['brand']].add(r['platform'])
targets = {b: platforms for b, platforms in by_brand.items() if len(platforms) >= 2}
baemin_targets = [b for b, p in targets.items() if 'baemin' in p]
```

땡겨요는 타겟 없이 전수라 이 쿼리는 배민 타겟 목록에만 쓰인다.

`ref/delivery/detail/` 신설(현재 `ref/delivery/`는 목록 화면 캡처

## 검증 기준

- 배민 8개 타겟 브랜드 전부 스킵 없이 캡처됨(스킵된 게 있으면 왜
  스킵됐는지 로그로 남음)
- 땡겨요는 스크롤 두 번 연속 돌려 카드 목록이 겹치지 않고 늘어나는지
  확인(기존 `device-setup.md`의 "결과 이미지 높이가 같은지" 검증과
  같은 정신 — 중복/누락 없이 훑었는지)
- 뒤로가기 검증 실패로 중단된 적이 있다면, 그 지점까지 캡처된 파일은
  보존되고 재실행 시 스킵됨
