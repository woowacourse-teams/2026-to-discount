# MVP 설계 — 브랜드 할인 교차 비교 웹

- 날짜: 2026-07-27
- 상태: 설계 확정, 구현 전

## 1. 목적과 가설

이 프로젝트의 궁극적 목표는 **유저가 있는 서비스를 만들어 운영하는 것**이다. 1차
목표는 가설을 세우고, 최소 자원으로 프로토타입을 만들어 실험하고, 사용자 반응을
관찰해 서비스에 반영하는 것이다. 따라서 이 MVP는 기능을 넓히는 것이 아니라,
**하나의 가설을 검증하는 데 필요한 최소한**만 만든다.

**검증할 가설**

> 배달앱마다 같은 브랜드의 할인이 제각각이고, 사용자는 "오늘 이 브랜드를 어디서
> 시키면 가장 이득인지"를 한눈에 보고 싶어한다.

가설의 전제(할인이 앱마다 다르다)는 이미 수집 데이터로 확인됐다. 예: 도미노피자
5,000~8,000원, 청년피자 5,000~17,000원. 검증할 것은 **"그래서 사용자가 이걸
쓰는가"**이다.

## 2. 범위

### 넣는 것 (가설 검증에 꼭 필요한 것)

- 수집된 전체 브랜드를 목록으로 보여준다 (교차 브랜드 + 단일 앱 브랜드 모두)
- 각 브랜드의 **앱별 할인을 한 행에 나란히** 보여준다 (교차 비교가 핵심)
- **최고 확정 할인 큰 순** 정렬 (기본 하나, 정렬 UI 없음)
- 확정/미확정 값을 시각적으로 구분한다
- 모바일에서도 볼 수 있는 반응형 웹

### 빼는 것 (사용자 반응을 본 뒤에 판단)

- 검색창, 카테고리 필터, 정렬 옵션 선택
- 시계열·할인 변화 추적
- 로그인·즐겨찾기·알림
- 브랜드→배달앱 바로가기 딥링크
- 데이터베이스 (JSON 파일을 읽는다)
- 자동 캡처 (수집은 기존 수동 파이프라인 유지)

## 3. 아키텍처

```
[현재 레포: 파이썬]            [신규 레포: 스프링 (메인)]        [React (Vite)]
 캡처 → 판독 → store            export.json 읽기                 fetch → 화면
   → export.json 산출     ──▶   별칭으로 브랜드 묶기        ──▶   교차 비교 목록
   (데이터 공급자)              확정/미확정 판정 → REST          (모바일 반응형)
```

두 레포, 하나의 경계(`export.json`).

- **현재 레포(파이썬)** = 데이터 공급자. 판독 결과를 정제 JSON으로 뽑아 전달만 한다.
- **신규 스프링 레포** = 이 서비스의 메인. 데이터를 소비해 비즈니스 로직(별칭
  묶기, 신뢰도 판정, 정렬)을 수행하고 REST로 낸다. React 프론트를 포함한다.
- 스프링이 파이썬을 호출하거나 그 반대는 없다. 계약은 `export.json` 파일 하나뿐이다.

### 책임 경계

| 하는 일 | 어디서 | 이유 |
|---|---|---|
| 캡처·판독·원장(JSONL) | 파이썬 (기존) | 이미 동작함. 건드리지 않음 |
| `export.json` 생성 | 파이썬 (신규 스크립트 1개) | 공급자의 유일한 신규 책임 |
| 별칭으로 브랜드 묶기 | 스프링 | 비즈니스 로직은 메인 레포에 |
| 확정/미확정 판정 | 스프링 | 표시 규칙은 소비자 쪽 |
| 정렬·교차 비교 계산 | 스프링 | 〃 |
| 화면 렌더 | React | 〃 |

## 4. 데이터 계약 — `export.json`

파이썬이 `latest_per_brand`(플랫폼·브랜드별 최신 1건)를 정제해 배열로 낸다.
**브랜드명은 판독된 원본 그대로 둔다** — 정규화(별칭 묶기)는 스프링의 몫이다.

```json
[
  {
    "platform": "baemin",
    "brand": "도미노피자",
    "amount": 5000,
    "qualifier": null,
    "needsReview": false,
    "offerType": "discount",
    "section": "오늘의 할인",
    "rawText": "5,000원 브랜드 할인",
    "capturedAt": "2026-07-27T14:20:00+09:00",
    "screenshotPath": "ref/delivery/baemin_2026-07-27.jpg"
  }
]
```

전달은 프로토타입이라 **수동 복사**한다(파이썬이 파일 생성 → 스프링 레포로 옮김).
자동 파이프라인은 범위 밖.

같은 스크립트가 별칭 작업용 부산물 `brands-sorted.txt`(전체 고유 브랜드명, 이름
오름차순)도 함께 낸다. §5의 별칭 묶기에서 쓴다.

## 5. 스프링 — 비즈니스 로직

### 별칭 묶기

`resources/brand-aliases.yml`에 대표 브랜드명과 별칭을 사람이 손으로 적는다.

```yaml
멕시카나: [멕시카나, 멕시카나치킨]
BBQ: [BBQ, BBQ치킨]
빽보이피자: [빽보이피자, 빽보이피자 오구샌]
```

- 별칭표에 없는 브랜드는 원본 이름을 그대로 대표명으로 쓴다.
- 별칭표는 작게 시작해, 데이터를 보며 명백한 것만 추가한다(자동 정규화는 오매칭
  위험이 있어 쓰지 않는다).

**작성을 돕는 도구**: 파이썬 데이터 공급자가 `export.json`을 뽑을 때, 수집된
**전체 고유 브랜드명을 이름 오름차순으로** 정리한 목록도 함께 낸다
(`brands-sorted.txt`). 사람은 이 목록을 보며 같은 브랜드의 다른 표기를 찾아
`aliases.yml`에 묶는다. 웹 관리 화면(체크박스로 묶기)은 프론트·API가 늘어 MVP
범위를 벗어나므로 만들지 않는다 — 별칭 작업은 1회성에 가깝고, 목록 산출물로 충분하다.

### 확정 / 미확정 판정

`export.json`의 `needsReview`를 그대로 신뢰도로 쓴다.

- **확정**: `amount`가 있고 `needsReview`가 false — 배민 정액, 땡겨요(5천 차감),
  쿠팡이츠 정액
- **미확정**: `needsReview`가 true — 요기요 전체, 쿠팡이츠 `최대`(랜덤 쿠폰)

미확정도 교차표에 **표시하되 구분**한다(회색 + `최대` 배지). 비교에서 빼면
요기요가 거의 사라져 비교가 반쪽이 되기 때문이다.

### 정렬

**최고 확정 할인 큰 순.** 각 대표 브랜드의 offer 중 확정값의 최댓값 기준.
확정값이 없는 브랜드(요기요만 있는 경우 등)는 미확정 최댓값으로 그 아래에 둔다.

> 대안으로 검토했으나 뺀 것: "앱 간 할인 차이 큰 순". 가설을 더 강하게
> 보여주지만 단일 앱 브랜드를 목록 아래로 밀어 데이터를 죽인다. 사용자 반응을
> 본 뒤 정렬 옵션으로 추가할 후보.

## 6. API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/brands` | 대표 브랜드별 교차 비교 목록 (아래 응답) |
| POST | `/api/reload` | 판독 갱신 후 `export.json`을 다시 읽는다 |

`GET /api/brands` 응답:

```json
[
  {
    "name": "도미노피자",
    "maxConfirmedAmount": 8000,
    "offers": [
      {"platform": "ddangyo",     "amount": 8000, "qualifier": "최대", "status": "confirmed", "rawText": "최대 13,000원 할인"},
      {"platform": "yogiyo",      "amount": 7000, "qualifier": "최대", "status": "held",      "rawText": "최대 7,000원 할인"},
      {"platform": "coupangeats", "amount": 5000, "qualifier": null,   "status": "confirmed", "rawText": "5,000원"},
      {"platform": "baemin",      "amount": 5000, "qualifier": null,   "status": "confirmed", "rawText": "5,000원 브랜드 할인"}
    ]
  }
]
```

## 7. 화면 (React, 1페이지)

- 상단: 제목 + 수집 시각(가장 최근 `capturedAt`)
- 본문: 브랜드 목록. 각 행 = 대표 브랜드명 + 4개 앱(배민·쿠팡이츠·땡겨요·요기요)
  할인 셀. 있는 앱만 값, 없으면 빈칸
- 확정값은 진하게, 미확정값은 회색 + `최대` 배지
- 최고 확정 할인 큰 순. 모바일 반응형(좁은 화면에서 4열이 접히거나 카드형)

화면은 한 페이지이며 상호작용은 없다(스크롤만). 클릭·검색·필터는 넣지 않는다.

## 8. 성공 기준

기술 완료 기준과 가설 검증 기준을 나눈다.

- **기술 완료**: `export.json` → 스프링 REST → React 화면까지, 실제 수집
  데이터(107건)로 교차 비교가 뜬다. 모바일에서 읽힌다.
- **가설 관찰**: 프로토타입을 사람에게 보여주고 "오늘 뭐 시킬 때 이걸 보겠는가"에
  대한 반응을 관찰한다. 이 관찰이 다음 이터레이션(검색·시계열·알림 등)의 우선순위를
  정한다.

## 9. 미해결 · 기록해둘 것

- **브랜드당 여러 혜택**: 한 브랜드가 한 앱에서 금액 할인과 굿즈 증정을 동시에
  가질 수 있다(땡겨요 BBQ). 현재 `latest_per_brand`는 (플랫폼, 브랜드)당 1건만
  남겨 금액 할인을 대표로 쓴다. 굿즈 등은 원장에만 남는다. MVP 범위에서는 이대로
  둔다.
- **수집 주기**: 하루 2회 수동 판독을 전제한다. `export.json` 갱신과 `/api/reload`
  호출도 수동. 자동화는 사용자 반응을 본 뒤.
