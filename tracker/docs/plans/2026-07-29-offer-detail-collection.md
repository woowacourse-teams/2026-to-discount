# 할인 상세(최소주문금액·구간) 수집 계획

작성일: 2026-07-29 · 상태: 진행 중(땡겨요 3건 수집·반영 완료)

## 왜 필요한가

지금 원장 107건 중 최소주문금액이 적힌 건은 0건이다. 그래서 화면에는
"최대 7,000원 할인"까지만 뜨고, 실제로 얼마를 아끼는지는 알 수 없다.

**"최대 n원"의 정체가 곧 구간표다.** 요기요 브랜드 쿠폰은 주문금액 구간마다
할인이 갈리고 목록에는 그중 최댓값만 적힌다. 구간을 채우면 "최대"라는
군더더기가 사라지고, 22건의 `needs_review`도 상당수 해소된다.

## 왜 아직 못 채웠나

목록 화면에는 없다. 앱에서 **쿠폰 상세를 열어야** 보인다.
현재 수집은 목록 화면 수동 캡처가 전부다(ADR-013).

브랜드 73개 × 앱 4개면 최대 292번을 열어야 한다. 전수는 비현실적이다.

## 스키마 (준비 완료)

원장 `log.jsonl`의 선택 필드. 안 쓰면 `None`으로 남고, 넣으면 그대로
export → API → 화면 상세 패널까지 흘러간다.

```json
{
  "min_order_amount": 15000,
  "tiers": [
    {"min_order": 15000, "amount": 3000},
    {"min_order": 25000, "amount": 7000}
  ],
  "conditions": "1일 1회, 배달 주문만"
}
```

`tiers`는 손으로 채우는 값이라 `schema.py`가 모양을 검증한다
(리스트여야 하고, 각 항목에 `min_order`·`amount`가 있어야 한다).

반영 절차는 데이터만 갈아끼우면 끝이다 — API·프론트 재배포 없음:

```
python export_data.py
scp data/export.json ubuntu@bebeggars.duckdns.org:~/delivery-discount-api/data/
curl -X POST https://bebeggars.duckdns.org/api/reload
```

## 수집 범위 — 전수 대신 상위권부터

가설 검증에 필요한 건 "어느 앱이 제일 싼가"이고, 그건 상위 브랜드에서
갈린다. 그래서 순서를 정한다.

1. **`needs_review`이면서 "최대"가 붙은 건** (22건) — 여기가 가장 안 보이는
   구간이고, 해소 효과가 가장 크다
2. **한 브랜드에 앱 2개 이상 걸린 건** — 비교가 실제로 일어나는 지점
3. 나머지는 요청이 있을 때

전수를 채우지 않는다는 결정 자체를 화면에 드러낸다. 안 채운 자리는 감추지
않고 "미확인"으로 남고, 카드 하단에 왜 비어 있는지 한 줄 붙는다.

## 앱별 주의점

- **쿠팡이츠**: 목록 화면 금액을 그대로 옮기면 안 된다. 헤드라인은 하위
  쿠폰들의 최댓값이고, `최대` 배지도 목록/상세가 서로 어긋난다. 상세를
  열어 **보장 바닥값**을 확인해야 확정으로 내릴 수 있다
  ([ADR-014](../decisions/ADR-014-coupangeats-record-guaranteed-floor.md),
  [해부 문서](../research/2026-07-29-coupangeats-discount-anatomy.md)).
  랜덤박스는 금액을 만들지 말고 `amount: null`로 둔다.

- **땡겨요**: BBQ류 쿠팡이츠와 같은 함정이 있다 — 목록/브랜드 카드의
  헤드라인 금액이 **최소주문금액 할인이 아니라 특정 메뉴 한정 쿠폰**인
  경우가 있다(훌랄라참숯바베큐치킨: "12,100원 할인"이 사실은 "(순살)
  참숯구이 1.5마리"에만 적용). 이 경우 `min_order_amount`를 채우지 말고
  `conditions`에 메뉴 제한을 적고 `needs_review: true`로 둔다 —
  최소주문금액 조건과 메뉴 한정 조건은 성격이 달라 섞으면 안 된다.
  브랜드 하나에 쿠폰이 여러 장 쌓여 있는 경우도 있다(피자헛: 7,000원·
  6,000원이 둘 다 22,000원 이상 조건으로 동시에 존재) — 화면의 가로
  캐러셀이 자동화 스와이프에 반응하지 않아 전체를 못 넘겼다. 이럴 땐
  확인된 한 장만 기록하고 `conditions`에 "추가 쿠폰 있음, 미확인"이라고
  남긴다.

### 땡겨요 브랜드관 진입 경로

앱을 열면 보통 홈 화면이고, 브랜드별 쿠폰이 모인 곳은 **홈 상단
카테고리 아이콘 → 임의의 브랜드 배너/카드를 한 번 클릭 → 뒤로가기** 식의
간접 경로로만 도달했다(정식 메뉴 경로는 미확인 — 이번엔 사용자가 이미
열어둔 상태에서 시작했다). 일단 **브랜드관** 화면에 들어가면:

- 상단 탭: `오늘의 할인 / 신규 / 요즘 핫한 / 상품권 / 치킨 / …`
  (`오늘의 할인`이 기본 선택)
- `가까운 가게만 보기` 체크박스가 기본 체크됨
- 브랜드 카드를 탭하면 상세로 들어가고, 상세 화면의 쿠폰 카드에
  `N,000원 할인` + `min_order,000원 이상 주문 시 사용 가능`(또는 특정
  메뉴명)이 나온다. 코너에 `보유 쿠폰`이면 이미 받은 상태.
- **뒤로가기(←) → 목록 재진입 시 주의**: 뒤로 갔다가 바로 다른 카드를
  탭하면 방금 봤던 상세로 되돌아가는 현상을 반복 관찰했다(원인 미상 —
  웹뷰 전환 애니메이션이 안 끝난 상태에서 탭한 게 원인일 수 있음). 뒤로
  간 다음 **스크린샷으로 목록 상태를 확인하고 나서** 다음 카드를 탭할 것.
- 캐러셀형 다중 쿠폰(피자헛류)은 `input swipe`가 안 먹혔다 — 다른 접근이
  필요하면 좌표를 카드 자체보다 살짝 위/아래로 바꿔보거나, 쿠폰함 진입
  경로(있다면)를 따로 찾아야 한다.

**반려 사유(사용자 피드백, 2026-07-29)**: conditions 필드에 "화면에 일부만
노출, 확인 실패" 같은 내부 확인 상태를 그대로 사용자 화면에 노출했다 —
이런 불확실한 내용은 화면에 올리지 말고 정리해서 다시 물어보거나, 구조로
표현 가능하면(`tiers`) 그걸 쓰고, 애매하면 사용자에게 직접 물어야 한다.
다중 쿠폰을 어떻게 모델링·표시할지는 별도 브레인스토밍으로 다시 정한다.

ADB 연결이 세션 중 두 번 끊겼다(USB `offline` 상태, `adb kill-server` →
`adb start-server`로 복구). 재연결 후에도 recents(최근 앱 전환)에 있던
땡겨요·배달의민족 세션은 살아있어 처음부터 다시 로그인/탐색할 필요는
없었다 — 다만 recents에서 카드를 잘못 눌러 다른 앱으로 들어가는 실수가
있었고(빽보이피자 건이 그 결과로 보인다), **탭 직후 헤더/타이틀바로
어느 앱인지 반드시 재확인**해야 한다는 교훈이 남았다.

## 열린 문제

- **요기요 퍼센트 할인**: 맥도날드 "최대 9% 할인", 파파존스 "최대 5% 적립"은
  구간표를 채워도 원 단위로 못 바꾼다. `tiers`에 넣을 수 없는 유일한 형태라,
  별도 표기가 필요한지 판단이 남아 있다. 쿠팡이츠에서 "전 메뉴 N원"이 사실
  정률 할인이었던 걸 보면, 요기요의 `최대 n원`도 같은 구조일 가능성이 있다.
- **배민 브랜드별 바로가기**: 확보 완료 — `brands.yml`의 `links.baemin`에
  들어갔다([API ADR-004](../../../delivery-discount-api/docs/decisions/ADR-004-per-platform-brand-links.md)).
  쿠팡이츠는 브랜드 프로모션에 공유 버튼이 없어 링크를 못 만들었다.
