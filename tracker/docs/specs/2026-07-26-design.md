# 배달앱 브랜드할인 추적기 — 설계 명세

- 작성일: 2026-07-26
- 상태: 1차 설계 확정
- 관련 의사결정기록: `docs/decisions/`

## 1. 목적

배민·쿠팡이츠·요기요·땡겨요·배달특급 5개 배달앱의 **브랜드 단위 할인**(브랜드할인/주간할인/슈퍼딜 등 앱마다 명칭 상이, 실질은 동일)을 하루 2회 자동 수집하여, 하나의 대시보드에서 비교·추적한다.

- 1차 목표: **대시보드에서 전체 현황 확인**
- 2차 목표(부가): 변화 발생 시 알림

## 2. 배경 — 왜 앱 자동화인가

웹으로 확인 가능한지 5개 앱을 실제 브라우저로 전수 확인한 결과:

| 앱 | 웹 확인 가능 여부 |
|---|---|
| 요기요 | 로그인 없이 매장 목록·상세에서 할인 배지 노출 (유일하게 가능) |
| 배달의민족 | 불가 — 앱 다운로드 랜딩만 존재 |
| 쿠팡이츠 | 불가 — 앱 다운로드 랜딩만 존재 |
| 땡겨요 | 불가 — 앱 다운로드 랜딩만 존재 |
| 배달특급 | 불가 — 소비자 사이트에 서비스 소개만, 매장 할인 없음 |

요기요만 웹에서 가능하나, **웹에는 앱 전용 금액대별 쿠폰이 노출되지 않고 실제 구매 창구도 앱**이므로 요기요를 웹 경로로 분리하지 않는다. 5개 앱 모두 동일한 앱 기반 파이프라인을 적용한다. → `ADR-007`

## 3. 수집 대상 화면

앱마다 **브랜드 할인을 한 페이지에 모아놓은 화면**이 존재한다. 매장을 개별 순회하지 않고 이 페이지 하나만 캡처한다.

| 앱 | 화면 | 구조 |
|---|---|---|
| 배달의민족 | `브랜드관` → `오늘의 할인` 탭 (+ `가까운 가게만 보기` 체크) | 네이티브 1열 롱스크롤 리스트 |
| 쿠팡이츠 | `와우컬렉션` | WebView 프로모션 페이지, 섹션별 2열 그리드 |
| 땡겨요 | `오늘 땡길만한 브랜드` | 이미지 배너 1열 리스트 |
| 요기요 | (미조사) | 1차 구현 시 실물 확인 필요 |
| 배달특급 | (미조사) | 1차 구현 시 실물 확인 필요 |

### 3.1 실물 관찰 결과 (2026-07-26 캡처 기준)

**배달의민족 — 브랜드관**
- 카드 = 로고(이미지) + 브랜드명(텍스트) + `가까운 가게`/`쿠폰` 뱃지 + 소개문 + **`N,000원 브랜드 할인`(네이티브 텍스트)** + 메뉴 썸네일
- 할인 표기 형식이 매우 일관됨: 항상 `N,000원 브랜드 할인`, 수식어 없음
- `가까운 가게만 보기` 필터가 존재 → **수집 결과는 위치 종속적**

**쿠팡이츠 — 와우컬렉션**
- 페이지 타이틀이 `와우컬렉션_COPIED` (내부 CMS 복제 흔적) → 마케팅이 주기적으로 갈아끼우는 WebView 페이지
- 섹션 구성: `오늘의 위클리 슈퍼딜` / `놓칠 수 없는 인기 브랜드 할인` / `치킨·버거 브랜드 할인` / `피자 브랜드 할인` / `기타 인기 브랜드 할인` → **주 단위로 구성·순서가 바뀔 것으로 예상**
- 카드 = 로고 + 브랜드명 + 금액. 단 **브랜드 카드 사이에 순수 프로모션 이미지 타일(`WOW! 와우 컬렉션`)이 섞여 있음** → 데이터 카드와 구분 필요
- 하단은 이미지 배너 + `보러 가기` 링크 → 하위 프로모션 페이지(`이츠셰프컬렉션`, `장보기 쿠폰북`)로 분기

**땡겨요 — 오늘 땡길만한 브랜드**
- **모든 카드가 통째로 디자인된 이미지 배너.** 브랜드명·금액·`할인` 문구가 전부 이미지에 구워져 있음
- 네이티브 요소는 상단 카테고리 칩(`전체`/`치킨`/`피자`…)과 카드 하단 `배달`/`포장` 칩뿐
- 형식은 시각적으로 일관: `[로고] [브랜드명 전 메뉴] [최대 N원 할인]`
- **예외 존재**: BBQ 카드는 `한정판 굿즈 증정!` + 배너 구석에 `+4천원 쿠폰까지!` → 할인금액이 아닌 사은품형

### 3.2 금액 수식어 — 의미가 뒤집히는 지점

관찰된 표기:

```
배민   "10,000원 브랜드 할인"      수식어 없음(정액)
쿠팡   "최대 6,000원"              상한
쿠팡   "최소 4,000원"  (반올림피자)  하한 ← 정반대 의미
쿠팡   "최대 7천원"    (노랑통닭)    한글 수사 표기
땡겨요 "최대 9,000원 할인"          상한
```

`최대`/`최소`는 큰 숫자 옆에 아주 작은 2줄 글자로 렌더링되어 오독하기 쉬운데 의미는 정반대다. **단일 숫자로 정규화하지 않고 별도 필드로 보존한다.** → `ADR-004`

## 4. 아키텍처

```
capture(platform)  → 앱별 화면 진입 + 롱스크롤 캡처 → 스크린샷(들)
      ↓ [산출물: 롱스크롤 이미지 + 메타데이터]
parse(evidence)    → 판독 → 표준 레코드
      ↓ [산출물: 표준 레코드 JSON]
store(records)     → append-only 원장(JSONL)
      ↓
dashboard(log)     → 정적 HTML 재생성
```

**계층 간 계약이 유일한 결합점이다.** `capture`는 앱마다 완전히 다른 구현이지만 산출물은 항상 "롱스크롤 이미지 + 메타데이터"로 동일하고, `parse`는 그 이미지를 받아 항상 동일한 표준 레코드를 낸다. 이 두 계약만 지키면 위/아래 계층은 서로를 모른다.

## 5. 표준 레코드 스키마

```json
{
  "platform":        "baemin | coupangeats | yogiyo | ddangyo | specialdelivery",
  "page":            "브랜드관 > 오늘의 할인",
  "section":         "인기 브랜드 할인",
  "brand":           "반올림피자",
  "qualifier":       "최소 | 최대 | null",
  "amount":          4000,
  "unit":            "KRW",
  "raw_text":        "최소 4,000원",
  "scope":           "brand | store",
  "offer_type":      "discount | gift | coupon | unknown",
  "needs_review":    false,
  "target_address":  "서울특별시 강남구 역삼동 858 강남역",
  "captured_at":     "2026-07-26T11:22:00+09:00",
  "capture_mode":    "auto | manual",
  "screenshot_path": "captures/baemin/20260726-1122/full.png"
}
```

**필드 설계 원칙**
- `qualifier`를 `amount`에 절대 흡수하지 않는다 (`ADR-004`)
- `section`은 설정 상수가 아니라 **캡처 시점에 화면에서 읽은 값**이다. 새 섹션이 생기면 자동으로 따라온다 (`ADR-006`)
- `raw_text`는 항상 원문 그대로 보존한다. 판독 오류 사후 검증의 유일한 근거다
- 규격에 안 맞는 항목(사은품형, 처음 보는 문구)은 억지로 끼워맞추지 않고 `offer_type: gift|unknown` + `needs_review: true`로 남긴다
- `capture_mode`로 자동/수동 출처를 구분해 기록한다 (품질 추적용)

## 6. 자동화 비용 지도

이 프로젝트의 모든 유지보수 판단은 이 표를 기준으로 한다.

### 6.1 단계별 비용

| 단계 | 자동화 비용 | 근거 | 반자동 전환 시 |
|---|---|---|---|
| 페이지 진입 | **낮음** | 앱당 고정 경로 2~3탭. 앱 구조 변경 시에만 수정 | 사람이 앱 열고 해당 페이지로 이동 |
| 롱스크롤 캡처 | **낮음** | `screencap` + `swipe` 반복, 완전 결정론적 | 폰 기본 스크롤캡처 1회 |
| **판독** | **높음** | **유일한 실질 비용.** 비전 호출 필요, 앱별 난이도 상이 | 사람이 보고 CSV 입력 |
| 저장·집계·대시보드 | **없음** | 순수 결정론적 코드, 외부 의존 없음 | 변경 없이 그대로 동작 |

### 6.2 앱별 판독 난이도

| 앱 | 화면 형태 | 텍스트 추출 | 저비용 교차검증 경로 |
|---|---|---|---|
| 배민 | 네이티브 리스트, 할인=실제 텍스트 | 가능 | `uiautomator dump`로 대조 가능 |
| 쿠팡이츠 | WebView + 이미지 타일 혼재 | 부분 가능 | 부분 대조 |
| 땡겨요 | **100% 이미지 배너** | **불가** | **없음 — 비전이 유일 경로** |
| 요기요 | 미조사 | 미조사 | 미조사 |
| 배달특급 | 미조사 | 미조사 | 미조사 |

**함의**: 판독 정확도가 문제가 될 경우, 배민은 저비용 교차검증을 붙일 수 있으나 땡겨요는 그 경로가 없다. 땡겨요는 정확도 이슈 발생 시 곧바로 반자동 후보다.

## 7. 반자동(수동) 전환 보장

**자동 경로와 수동 경로의 산출물이 물리적으로 동일하다.**

- 자동: `adb screencap` + swipe 반복 + 이어붙이기 → 롱스크롤 이미지
- 수동: 폰의 스크롤 캡처 기능으로 1장 촬영 → 롱스크롤 이미지 (본 설계의 근거가 된 `ref/delivery/*.jpg`가 바로 이 산출물이다)

따라서 반자동 전환은 별도 모드 구현이 아니라 **"캡처 단계를 사람이 수행"** 일 뿐이다.

**전환 단위는 앱별로 독립적이다.** 특정 앱만 수동으로 내리고 나머지는 자동 유지할 수 있다.

**전환 절차**
1. `config/target.json`에서 해당 플랫폼의 `capture_mode`를 `manual`로 변경
2. 사람이 해당 앱의 대상 페이지를 스크롤 캡처하여 `captures/<platform>/<timestamp>/full.png`에 저장
3. 이후 파이프라인은 자동과 완전히 동일하게 동작

**전환 트리거 기준** (아래 중 하나면 반자동 검토)
- 판독 오류가 1주 내 2회 이상 발생
- 앱 UI 변경으로 페이지 진입이 2회 연속 실패
- 에뮬레이터 탐지로 앱 실행 자체가 차단

## 8. 실행 환경

- 언어: Python, ADB는 CLI 서브프로세스 호출 (`ADR-001`)
- 에뮬레이터: Android SDK `emulator` (헤드리스). BlueStacks는 Windows/Mac 전용이라 리눅스 서버에서 동작 불가하므로 채택하지 않음 (`ADR-002`)
- 실행 위치: 로컬 Windows PC 또는 오라클 클라우드 리눅스 서버 — **양쪽에서 동일 동작 보장이 요구사항**
- 스케줄: 하루 2회. 트리거는 Windows Task Scheduler 또는 cron, 어느 쪽이든 동일한 진입점 명령 하나를 호출

## 9. 오류 처리

- **플랫폼 단위 격리**: 한 앱이 실패해도 나머지 앱은 계속 수집한다. 실패한 앱은 실패 레코드를 남긴다
- **침묵 실패 방지**: 각 캡처 후 "기대한 화면인지" 확인한다. 확인 실패 시 판독으로 넘기지 않고 즉시 실패 처리한다. 엉뚱한 화면을 판독해 그럴듯한 오답을 저장하는 것이 가장 위험한 실패 양상이다
- **원본 보존**: 모든 스크린샷을 보관한다. 판독 결과가 의심스러울 때 되짚을 유일한 근거다

## 10. 1차 범위

**포함**
- 배민·쿠팡이츠·땡겨요 3개 앱의 **메인 할인 페이지만**
- 캡처 → 판독 → 저장 → 대시보드 전 구간
- 반자동 전환 경로 및 문서

**제외 (확장 후보로 기록만)**
- 하위 프로모션 페이지 (`이츠셰프컬렉션`, `장보기 쿠폰북` 등 `보러 가기` 링크 이하) — `ADR-005`
- 요기요·배달특급 — 대상 화면 미조사. 실물 확인 후 동일 구조로 추가
- 매장 단위(`scope: store`) 할인 — 스키마에는 자리를 두되 수집하지 않음
- 변화 알림 — 대시보드 안정화 이후

## 11. 관측 규율 — 한 번 보고 단정하지 않는다

> 이 절은 2026-07-27 구현 중에 추가되었다. 앱 화면을 상대로 한 관측은 한 번의 결과가 그럴듯해 보여도 틀리기 쉽다. 실제로 그날 하루에만 단일 관측에서 나온 결론 네 건이 뒤집혔다.
>
> | 단정했던 것 | 실제 | 왜 틀렸나 |
> |---|---|---|
> | `current_activity()`가 이 기기에서 동작 안 함 | 정상 동작 | 출력 첫 줄만 보고 판단 |
> | 웹뷰 내부는 뷰 트리에 안 나옴 | 다 나옴 | 덤프가 엉뚱한 화면에서 찍힘 |
> | 체크박스가 화면 열 때마다 초기화됨 | 사람이 직접 바꾼 것이었음 | 조작 이력을 모른 채 상태만 봄 |
> | 스크롤 이동량 = 1049px | 그 기기 그 조건에서만 | 1회 측정 |

### 11.1 관측을 사실로 채택하는 기준

화면에서 얻은 값을 코드나 문서에 사실로 적을 때는 아래를 만족해야 한다.

- **독립 반복** — 최소 2회, 서로 다른 시점에 같은 결과가 나와야 한다. 앱을 새로 띄운 뒤 다시 재는 것을 1회로 친다
- **교차 확인** — 가능하면 서로 다른 경로로 같은 사실을 확인한다. 예: 체크박스 상태는 뷰 트리의 `checked` 속성과 해당 영역의 픽셀 밝기 두 경로로 봤고, **둘이 어긋나서** `checked`가 못 쓸 값임을 알았다
- **관측 조건 기록** — 기기, 앱 버전, 해상도, 방향을 값과 함께 적는다. 조건 없는 숫자는 다음 사람에게 함정이다
- **사람의 개입 배제** — 사람이 화면을 만졌을 수 있는 상태에서 관측한 값은 사실로 채택하지 않는다

한 번만 본 것을 적어야 할 때는 **한 번만 봤다고 같이 적는다.**

### 11.2 방지턱 — 틀린 전제가 조용히 지나가지 않게 한다

관측은 언제든 틀릴 수 있으므로, 코드가 관측 결과에 의존할 때는 아래 형태를 지킨다.

- **전제를 믿지 말고 매번 확인한다** — "화면을 열면 체크박스가 켜져 있다"를 믿고 무조건 누르지 않는다. 지금 상태를 읽고, 필요할 때만 누르고, 누른 뒤 다시 읽어 확인한다
- **상수 대신 도출** — 기기·앱에 따라 달라지는 값(좌표, 스크롤 이동량, 화면 영역)은 상수로 박지 않고 실행 시점에 뷰 트리나 측정으로 얻는다. 도출이 불가능해 상수로 둘 때는 그 사실과 재측정 절차를 [기기 설정 문서](../setup/device-setup.md)에 남긴다
- **조용한 실패보다 시끄러운 실패** — 확인에 실패하면 그 자리에서 예외를 던진다. §9의 "침묵 실패 방지"와 같은 원칙이다. 부분적으로 잘못된 캡처를 판독으로 넘기지 않는다
- **결과의 자기 일관성 검사** — 같은 화면을 두 번 캡처하면 결과 이미지 높이가 같아야 한다. 다르면 전제 어딘가가 깨진 것이다. 실제로 이 검사가 체크박스 토글 버그를 잡아냈다(29프레임 / 11프레임)

## 12. 검증

- 결정론적 영역(스키마 검증, 레코드 적재, 대시보드 집계)은 자동 테스트로 검증한다
- 캡처·판독은 실제 화면이 필요하므로 자동 테스트 대신 **`ref/delivery/`의 실물 캡처를 고정 입력으로 삼는 판독 회귀 검증**을 둔다. 알려진 정답(예: 반올림피자 = `최소` 4,000원)을 기준으로 판독 품질 저하를 감지한다
- 캡처 코드 변경 후에는 §11.2의 자기 일관성 검사(같은 화면 2회 캡처 → 높이 동일)를 돌린다
