# 오케스트레이션 계약

세 층이 한 방향으로만 흐른다. 각 층이 무엇을 보장하고 무엇을 가정하는지,
그리고 층을 가로지르는 작업에서 반복해서 사고가 났던 지점을 적는다.

앱 안에서 끝나는 세부는 각 디렉터리의 `docs/ORCHESTRATION-CONTRACT.md`에
있다. 여기는 **층을 가로지를 때만** 필요한 것을 담는다.

```
화면(배달앱)  →  tracker  →  export.json  →  api  →  /api/brands  →  web
                 판독·원장     파일 드롭      가공·판정              화면
```

## 1. 데이터가 흐르는 규칙

**원장은 `tracker/data/log.jsonl`, 배포되는 산출물은 `tracker/data/export.json`.**
export는 원장의 파생물이고, `store.latest_per_brand()`가 (앱, 브랜드)당
하나만 남긴다.

승자 규칙은 **확정 > 최신 캡처 > 금액** 순이다. 이 규칙이 tracker
(`store._prefer`)와 api(`Offer.preferredOver`) **양쪽에 중복 구현돼 있다**
— 한쪽만 고치면 같은 원장이 경로에 따라 다른 결과를 낸다. 실제로 어긋나
있었다(2026-08-06: tracker가 상세 3개만 병합, api는 5개).
`tracker/docs/decisions/ADR-016`이 이 중복을 명시적으로 허용하되 동기화를
의무로 못박은 문서다.

## 2. 필드를 늘릴 때는 API를 먼저 배포한다

세 저장소가 각자 워크플로로 독립 배포된다. tracker가 먼저 끝나면 구버전
API가 모르는 필드를 받는다.

지금은 `OfferRepository`의 ObjectMapper가
`FAIL_ON_UNKNOWN_PROPERTIES=false`라 무시하고 넘어간다. 그 전엔 Jackson이
`UnrecognizedPropertyException`을 내고 `/api/reload`가 500으로 죽었다 —
같은 사고가 세 번 반복되고서야 고쳤다.

**무시된다는 건 깨지지 않는다는 뜻이지 값이 전달된다는 뜻이 아니다.**
그래서 순서는 여전히 API 먼저다.

## 3. 배포는 파일을 통째로 갈아치운다

`tracker`의 워크플로가 `cp data/export.json`으로 서버 파일을 덮고
`POST /api/reload`를 부른다. 커밋이 서버보다 낡았으면 **푸시 한 번에, 사람
개입 없이 서버 데이터가 사라진다.**

2026-08-05에 실제로 그렇게 잃었다(청년피자 땡겨요의 tiers 2건과 badge).
로컬 사본이 서버와 같다고 **가정하고 표본 몇 건만 대조**한 것이 원인이다.

`tracker/check_deploy.py`가 두 가지를 검사한다.

- 들어오는 파일의 최신 `capturedAt`이 서버보다 이르면 중단
- 서버에 채워져 있던 상세(`tiers`·`badge`·`minOrderAmount`·`conditions`·
  `expiresAt`)가 비면 중단

**건수로는 재지 않는다.** 프로모션이 끝나면 레코드는 정당하게 줄고, 정상
만료마다 오탐을 뱉는 가드는 결국 꺼진다.

## 4. `export_data.py`를 그대로 돌리면 안 된다

원장에 **"이 프로모션은 끝났다"를 적을 자리가 없다.** 종료된 프로모션 제거가
`export.json`에서만 일어나서, 원장으로 재생성하면 그것들이 되살아난다
(2026-08-06 기준 20건).

원장에 새 관측을 넣을 때는 `tracker/ingest.py`를 쓴다. 원장은 append-only라
**정정은 삭제가 아니라 덮어쓰기**다 — 더 최신 시각의 새 관측이어야 하고,
`needs_review=false`여야 확정을 이긴다. `--dry-run`이 이길지 미리 보여준다.

## 5. `tiers`는 "구간 누진"만 뜻하지 않는다

같은 `minOrder`에 `amount`만 다른 항목들은 구간이 아니라 **채널·멤버십별
별개 쿠폰**이다.

| 신호 | 뜻 |
|---|---|
| `channel` | 배달/포장/매장식사별 별개 쿠폰 |
| `percent` | 정률+상한. `amount`는 그 상한액 |
| `soldOut` | 이 구간만 재고 소진 |
| `expiresAt` | 이 구간만 따로 끝남. 비면 레코드 값을 따름 |

**대표 금액(`amount`)은 "가장 큰 구간"이 아니라 "조건 없이 실제로 받을 수
있는 최대"다.** 품절 구간에서 뽑지 않고, 멤버십 전용 구간에서도 뽑지 않는다.
그래서 API는 대표값을 처음부터 다시 만들 수 없다 — 만료로 도달 불가능해진
경우에 **내리기만** 한다(`api/docs/decisions/ADR-008`).

한 (앱, 브랜드)에 쿠폰이 여럿이면 **레코드를 늘리지 말고 tiers를 늘린다.**
레코드를 늘리면 `latest_per_brand`가 하나만 남겨 나머지가 조용히 사라진다.

## 6. `qualifier`는 금액 수식어 전용이다

`{null, "최대", "최소"}`만 온다. `최대 4,000원`과 `최소 4,000원`은 정반대
의미이고, 그 구분이 `amount` 해석을 바꾼다
(`tracker/docs/decisions/ADR-004`).

조건 라벨을 여기 넣으면 그 구분이 영구히 사라진다. 짧은 상태·조건 표시는
`badge`에 넣는다.

## 7. 만료는 요청 시점에 판정된다

`api`가 `/api/brands`를 처리할 때마다 한국 날짜로 판정한다. 원장은 push할
때만 바뀌지만 날짜는 계속 바뀌기 때문이다.

**이 저장소를 push하지 않아도 응답이 바뀐다**는 뜻이다. 대신 만료는 조용히
일어난다 — 관측이 없어서 언제 재수집해야 하는지 알 수 없다
(`api/docs/decisions/ADR-008`의 "아직 안 한 것").

# 세션 제약 — 층을 가로지를 때

이 프로젝트에서 실제로 사고가 났던 방식들이다. 규칙이 아니라 **재발 방지
목록**으로 읽는 게 맞다.

## 로컬 사본이 서버와 같다고 가정하지 않는다

배포 전 비교는 **라이브 응답 전수 대조**로 한다. 표본 몇 건이 맞다고 전체가
같지 않다 — 2026-08-05의 데이터 유실이 정확히 이 착오였다. 표본 3~4건이
우연히 일치해서 "같다"고 결론냈고, 서버에만 있던 편집을 덮어썼다.

되돌릴 수 있었던 건 덮어쓰기 **직전에 받아둔 API 응답 스냅샷** 덕분이다.
파괴적 작업 전에는 현재 상태를 먼저 받아둔다.

## 필드 하나만 보고 레코드를 지우지 않는다

레코드 만료일이 지났어도 그 안의 쿠폰이 다 끝난 건 아니다. 2026-08-06에
`expiresAt` 하나만 보고 청년피자 땡겨요를 통째로 지웠는데, 그 레코드엔
쿠폰이 둘 있었고(청피데이 9,000원 만료 / 상시 5,000원 생존) `rawText`에
"5,000원 할인"이라고 적혀 있었다.

## 문서 수치는 손으로 옮기지 않는다

계약서의 필드 수·허용값·건수는 **코드와 실데이터에서 뽑아서** 쓴다. 손으로
옮기면 다음 변경에서 어긋나고, 어긋난 문서는 읽는 사람을 잘못된 확신으로
데려간다. 세 저장소의 계약서가 08-01에서 멈춰 필드를 13개로 적어둔 채
실제는 16개였다.

**줄 번호는 적지 않는다.** 화면을 한 번 고칠 때마다 표 전체가 어긋나서,
문서가 맞는지 확인하는 비용이 읽는 이득보다 커진다.

## 결정을 코드로만 뒤집지 않는다

확정된 ADR을 코드로 뒤집었으면 ADR도 같이 고친다. `api/ADR-007`이 그렇게
방치됐다 — 픽스처를 합성 샘플로 바꿔놓고 ADR은 "운영 데이터 107건을
커밋한다"로 남아 있었다.

## 안전장치는 자기 의존성으로 배포를 막지 않게

배포 가드를 `python check_deploy.py`로 넣었다가 러너에 python이 PATH에 없어
배포가 끊겼다. 이 워크플로는 원래 bash와 curl만 쓰고 있었다. 판정이
문자열 비교라 coreutils로 충분했다.
