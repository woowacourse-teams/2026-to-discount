# 의사결정기록 (ADR)

되돌리기 어려운 판단과 그 근거만 남긴다. "무엇을 했다"가 아니라 **"왜 다른
길을 버렸는가"**를 적는다 — 나중에 같은 갈림길에 다시 서는 사람이 이미
검토한 선택지를 처음부터 다시 밟지 않게.

## 어디에 쓰는가

| 위치 | 담는 것 |
|---|---|
| `docs/decisions/` (여기) | **오케스트레이션 층** — 앱 하나로 끝나지 않는 결정 |
| `tracker/docs/decisions/` | 판독·캡처·데이터 모델 (17건) |
| `api/docs/decisions/` | 응답 계약·중복 정리·만료·배포 경로 (9건) |
| `web/docs/decisions/` | 화면·백엔드 주소·계측 (2건) |

**번호는 위치마다 1부터다.** 합치면서 통합하지 않았다 — 앱 단위 결정은 그
디렉터리 안에서 완결되고, 상호 링크를 전부 고치는 비용이 이득보다 크다
([ADR-001](ADR-001-monorepo-consolidation.md)). 다른 앱의 ADR을 가리킬 때는
`api/docs/decisions/ADR-006-...`처럼 경로를 붙여 쓴다.

## 목록 (루트)

| 번호 | 제목 | 상태 |
|---|---|---|
| [ADR-001](ADR-001-monorepo-consolidation.md) | 3레포를 한 저장소로, 트래커는 일부만 | 확정 |

## 상태 표기

- **확정** — 지금 이 규칙대로 동작한다
- **대체됨** — 더 나은 판단으로 바뀌었다. 대체한 ADR을 머리에 링크하고
  **원문은 지우지 않는다**. 왜 그때 그렇게 판단했는지가 다음 판단의 재료다
  (예: `api/docs/decisions/ADR-007` → `ADR-009`)
- **폐기** — 전제가 사라져 더 이상 의미 없다

## 쓸 때

전제를 적는다. ADR이 낡는 건 대부분 결론이 틀려서가 아니라 **전제가 조용히
바뀌어서**다. `api/ADR-007`이 그 예다 — "저장소가 private이라 노출 리스크
없다"를 근거로 삼았는데 저장소가 public이 되면서 근거가 사라졌고, 그 사실을
아무도 눈치채지 못한 채 결정만 남아 있었다.

되돌릴 조건을 적는다. "이것이 참이면 이 결정을 다시 본다"가 있으면 낡았는지
스스로 드러난다.
