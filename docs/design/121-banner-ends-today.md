# 배너 카드: 종료일이 오늘이면 오늘 마감을 보여 줄지

결론: 보여 줄 만하다. 서버가 요청 시각 기준으로 기간 문구를 만들고, 웹은 고치지 않는다. 다만 새 문구라서 구현 전에 개발자가 문구를 정해야 한다(아래 "결정 대기").

- 상태: 제안 (2026-10-21)
- 이슈: #121 (설계 119 워크플로 시험. 설계만 하고 구현하지 않는다)
- 관련: `api/.../banner/BannerText.java`, `BannerCatalog.java`, `BannerOffers.java`, `web/src/EventBanner.jsx`, `docs/COPY-STYLE.md`

## 무엇이 문제인가

여러 날짜에 걸친 배너의 기간 칸은 `~9/30`처럼 종료 날짜만 보인다(`BannerText.period`의 마지막 줄). 오늘이 9/30이어도 같은 글자다. 사용자가 오늘 날짜와 직접 견주어야 오늘 끝나는지 안다.

하루짜리 배너(`9월 30일 하루`)는 이미 오늘이면 오늘이 읽힌다. 문제가 되는 것은 **며칠짜리 배너의 마지막 날**뿐이다. 시작 시각이 자정이 아닌 배너(`오전 11시 오픈`)와 매일 오픈 배너(`매일 오전 11시 오픈`)는 기간 칸이 날짜를 안 말하므로 이번 설계 밖이다(아래 "열린 질문" 1).

## 지금 어떻게 만들어지나

- 기간 문구는 `BannerText.period(Banner)`가 만든다. 시계가 없다. 인자는 배너 하나뿐이다.
- 이 값은 파일을 읽을 때 한 번 만들어 `Banner.period`에 박힌다(`BannerCatalog` 466행). 묶음에서 여는 시각이 갈릴 때만 `active()`에서 다시 만든다(206행).
- `Banner.period`는 두 곳으로 간다. 배너 카드(`EventBanner.jsx`의 `banner.period`)와 배너 오퍼의 `badge`(`BannerOffers.common`). 뒤쪽은 원장 모양의 오퍼 레코드로 나간다.
- 응답에는 `endsAt`이 이미 들어 있다(`banner-cases.json`의 `responseKeys`). 웹은 지금 안 읽는다.
- 시계는 `Clock` 빈이 `Asia/Seoul`로 하나 있다. `BannerCatalog`가 이미 받는다.

## 대안

| | 어디서 만드나 | 장점 | 단점 |
|---|---|---|---|
| A. 서버가 요청 시각으로 | `BannerText`에 시각을 받는 기간 메서드를 더하고 `active()`에서 덮어쓴다 | 문구를 한 곳(`BannerText`)에서 만든다. 시간대가 서버 KST로 고정된다. 웹 변경과 프리뷰가 없다 | 값이 요청 시각에 따라 바뀌므로 응답 캐시가 있으면 자정 뒤에도 낡은 값이 나갈 수 있다(확인 필요) |
| B. 웹이 `endsAt`으로 | `EventBanner.jsx`가 `endsAt`과 기기 날짜를 견줘 `period`를 갈아 낀다 | 캐시와 무관하다 | 문구 만드는 자리가 둘이 된다(설계 25가 없애려던 상황). 기기 시간대가 KST가 아니면 틀린다. 웹 변경이라 프리뷰 절차를 탄다 |
| C. 하지 않는다 | | 변경 없음 | 문제가 그대로다 |

**선택: A.** 문구를 만드는 곳이 `BannerText` 하나라는 원칙(클래스 머리말: 파싱을 없앤다)과 시간대 문제 둘 다 A가 낫다. B는 같은 규칙이 서버와 웹 두 곳에 생긴다.

## 설계 (A)

1. `BannerText`에 시각을 받는 기간 메서드를 더한다. 기존 `period(Banner)`는 그대로 둔다. 새 메서드는 기존 결과가 `~M/D` 꼴일 때만 종료일이 오늘(서버 시계, `Asia/Seoul`)이면 오늘 마감 문구로 바꾼다. 나머지 분기(오픈 시각, 하루짜리)는 건드리지 않는다.
2. `BannerCatalog.active()`가 반환하는 배너의 `period`를 이 메서드로 덮어쓴다. 묶음(206행)에서 다시 만드는 자리도 같은 메서드를 쓴다. 묶음 구성원은 규칙상 `endsAt`이 같으므로(`groupRuleBreak`) 대표 것으로 충분하다.
3. 오퍼의 `badge`(`BannerOffers`)는 이번에 바꾸지 않는다. 박힌 `period`를 계속 쓰므로 `~9/30` 그대로다. 오퍼 칩에도 오늘 마감을 보이게 할지는 열린 질문 2.
4. 웹은 고치지 않는다. `banner.period`를 그대로 그린다. `period` 길이가 `~9/30`과 비슷하거나 짧으므로 360px 줄바꿈 위험은 문구가 정해진 뒤 확인한다.

## 결정 대기 (개발자)

`docs/COPY-STYLE.md` §3에 따라 새 문구는 세션이 정하지 않는다. 구현자는 이 둘이 답으로 오기 전에 문구를 넣지 않는다.

1. 기간 칸에 오늘 마감 표시가 들어가는 것이 맞는가.
2. 맞다면 어떤 문구인가. 후보는 `오늘 마감`, `오늘까지`. 명사구 또는 짧은 조건 하나, 45자 안이라는 형식 규칙(`COPY-STYLE` §1)은 둘 다 지킨다. 후보일 뿐 결정이 아니다.

## 열린 질문

1. 마지막 날에 `매일 오전 11시 오픈` 같은 오픈 시각 문구를 오늘 마감으로 바꿀지, 둘을 함께 보일지. 이 설계는 둘 다 건드리지 않는다고 가정한다. 날짜를 말하지 않는 기간 칸이라 같은 문제가 남는다.
2. 오퍼 `badge`도 따라갈지. 따라가면 원장에 나가는 `badge`가 요청마다 달라진다. 이 설계는 따라가지 않는다고 가정한다.
3. 응답 캐시(CDN, 브라우저, Spring)가 있는지. 있으면 자정을 넘긴 응답이 낡은 날짜로 나가는지 구현 전에 확인한다. 이 설계에서 확인하지 못했다.

## 확인 방법 (구현 때)

테스트는 반대편을 같이 본다는 원칙을 따른다.

- `BannerTextTest`: 종료일이 오늘인 며칠짜리는 새 문구, 내일인 것은 `~M/D`, 하루짜리와 오픈 시각 배너는 기존 그대로. 자정 경계(`23:59:59`와 다음 날 `00:00`)를 한 건씩 넣는다.
- 계약 파일 `banner-cases.json`은 `now`가 `2026-09-29T12:00`으로 고정이다. 이 날 끝나는 며칠짜리 배너가 있으면 기대값이 바뀌므로 Java, JS, tracker, beggars-ops 네 곳 사본이 같이 읽는 파일임을 고려해 구현 전에 해당 사례가 있는지 본다. 없으면 이 파일은 안 바꾼다.
- `BannerCatalogTest`: 묶음 카드와 묶음 아닌 카드 둘 다 마지막 날에 새 문구가 나가는지.
- 부재 주장은 양성 신호로 박는다. "오늘 마감이 안 뜬다"를 확인할 때 같은 시험에서 오늘 끝나는 배너가 뜬다는 것을 먼저 보인다(`AGENTS.md` 먼저 알 것 1번).
- 구현 뒤 운영 API 응답에서 마지막 날 배너의 `period`를 직접 본다.

## 범위 밖

- 시간 단위 카운트다운(`n시간 남음`).
- 종료 임박 강조 색이나 배지.
- 배너 말고 오퍼 칩, 오퍼 상세의 `expiresAt` 표기.
