# Design: 브랜드 검색어 자동완성

> 관련 이슈: #16 `[WEB] feat: 브랜드 검색어 자동완성 추가`
>
> 상태: 설계 및 구현 계획

## 1. 문제

### 배경

현재 브랜드 검색은 사용자가 검색어를 Enter 또는 검색 버튼으로 제출한 뒤,
`applyFilters()`가 API 응답의 대표 브랜드명에 `includes`를 적용하는 방식이다.
사용자가 브랜드명의 일부만 기억하거나 영문 표기를 입력하면 서비스에 등록된
대표명과 일치하지 않아 검색 결과를 얻기 어렵다.

브랜드 지식의 단일 출처인 `brands.yml`에는 원장 정규화용 `aliases`가 있지만,
이 값은 `/api/brands` 응답에 포함되지 않으며 사용자 검색을 위한 별칭과도 목적이
다르다.

### 해결하려는 문제

사용자가 서비스의 정확한 대표 브랜드명을 모르더라도 입력 중 후보를 확인하고
선택할 수 있게 한다. 영문 검색 별칭도 대표 한국어 브랜드와 연결해 검색 실패를
줄이고, A/B 검색 UI 어디서든 같은 검색 결과와 조작 방식을 제공한다.

## 2. 목표

- 브랜드 대표명과 검색 별칭을 이용해 입력 중 최대 10개의 후보를 제공한다.
- 영문 별칭으로 검색해도 대응하는 한국어 브랜드 후보를 제공한다.
- 한영 전환을 놓친 영문 입력은 원문 후보가 없을 때 두벌식 한국어로 변환해
  후보를 제공한다.
- 후보 선택 시 기존 검색 제출 경계를 사용해 해당 브랜드 검색을 즉시 적용한다.
- A/B 검색 UI가 동일한 후보 계산과 선택 규칙을 사용한다.
- 검색 별칭을 `brands.yml`에서 다른 브랜드 지식과 함께 관리한다.
- `brands.yml`의 모든 브랜드에 최소 하나의 영문 `searchAliases`를 제공한다.

## 3. Non-goals

이번 작업에서 하지 않는 것:

- 일반적인 오타 교정, 한글 초성 검색, 형태소 분석
- 검색 기록이나 사용자별 행동에 기반한 추천 순위
- 외부 검색 서비스 또는 검색 전용 API 도입
- 자동완성 노출이나 후보 이동을 위한 신규 분석 이벤트 추가
- 브랜드 검색 이외의 메뉴, 카테고리, 지점 통합 검색
- 원장 정규화용 `aliases`의 의미나 기존 정규화 동작 변경

## 4. 요구사항

### 필수

- 입력한 검색어와 일치하는 브랜드 후보를 검색창 아래에 최대 10개 표시한다.
- 검색 대상은 대표 브랜드명과 `searchAliases`다.
- 검색어와 검색 대상의 앞뒤 공백을 제거하고 영문 대소문자를 구분하지 않는다.
- 영문 원문으로 일치하는 후보가 없을 때만 두벌식 자판 기준으로 한국어로
  변환한 값을 다시 검색한다.
- 영문 원문 후보가 하나 이상 있으면 두벌식 변환 후보를 섞거나 대신 표시하지
  않는다.
- 후보 우선순위는 정확히 일치, 앞부분 일치, 포함 일치 순서다.
- 같은 우선순위의 후보는 `/api/brands`가 제공한 브랜드 순서를 유지한다.
- 한 브랜드의 여러 검색 대상이 일치해도 후보에는 대표 브랜드를 한 번만 표시한다.
- 후보에는 대표 한국어 브랜드명을 표시한다.
- 후보를 포인터로 선택하면 해당 대표명으로 검색을 즉시 제출한다.
- 위쪽과 아래쪽 방향키로 활성 후보를 이동하고 Enter로 선택할 수 있다.
- 활성 후보가 없는 상태에서 Enter를 누르면 기존 직접 검색을 제출한다.
- Escape 또는 검색창 외부 선택 시 후보 목록을 닫는다.
- 후보 선택은 기존 `brand_search_submitted` 이벤트에
  `submitMethod=autocomplete`로 기록한다.
- 검색어 원문, 검색 별칭, 선택한 브랜드명은 분석 이벤트에 넣지 않는다.
- A/B 검색 UI에서 같은 규칙으로 동작한다.

### 선택

- 적절한 ARIA combobox, listbox, option 속성으로 입력과 활성 후보의 관계를
  보조 기술에 전달한다.

## 5. 제약사항

- 기술적 제약: 현재 브랜드 목록은 `/api/brands` 요청 한 번으로 모두 내려오며,
  별도 자동완성 API를 호출하지 않는다.
- 데이터 제약: `aliases`는 수집 원장의 이름 통합용이고 `searchAliases`는 사용자가
  입력할 검색 표현용이므로 서로 대체하지 않는다.
- 기존 시스템 제약: 검색 결과 필터링과 `resultCount`의 단일 출처는
  `applyFilters()`이고, 검색 제출과 분석 이벤트 발생 경계는 App의
  `submitSearch()`다.
- UI 제약: A안은 열고 닫는 검색 패널이고 B안은 상시 노출 검색창이지만 후보
  계산과 키보드 선택 의미는 같아야 한다.
- 운영 제약: 검색 별칭은 브랜드 정보를 관리하는 운영자 또는 개발자가
  `brands.yml`에 직접 추가한다.
- 품질 제약: 공식 또는 널리 통용되는 영문명을 우선하고, 확인할 수 없는 경우에는
  일관된 로마자 표기를 사용한 뒤 검토 가능한 형태로 남긴다.

## 6. 성공 조건

- [ ] 검색어 입력 중 일치하는 브랜드 후보가 최대 10개 표시된다.
- [ ] 영문으로 검색해도 대응하는 한국어 검색어와 동일한 브랜드 후보가 표시된다.
- [ ] 한영 전환을 놓친 영문 입력은 원문 후보가 없을 때 한국어로 변환되어 후보가
  표시된다.
- [ ] 후보 선택 시 선택한 브랜드명으로 검색 결과가 반영된다.
- [ ] 자동완성 선택은 `submitMethod=autocomplete`로 기록된다.
- [ ] 검색어 원문과 브랜드명은 분석 이벤트에 포함되지 않는다.
- [ ] A/B 검색 UI에서 동일하게 동작한다.
- [ ] 웹 테스트와 빌드가 통과한다.
- [ ] 검색 별칭이 API 응답에 포함되고 관련 API 테스트가 통과한다.
- [ ] `brands.yml`의 모든 브랜드에 비어 있지 않은 영문 `searchAliases`가 있다.

## 7. 고려한 접근 방식

### A. 기존 브랜드 응답에 검색 별칭 포함 후 웹에서 후보 계산

설명: `brands.yml`에 `searchAliases`를 추가하고 `/api/brands` 응답에 포함한다.
웹은 이미 받은 브랜드 목록에서 입력과 일치하는 후보를 계산한다.

장점:

- 입력할 때 추가 네트워크 요청이 없어 즉시 후보를 갱신할 수 있다.
- 현재 수십에서 수백 개 규모에서는 전체 순회 비용이 작다.
- 브랜드 데이터와 검색 별칭을 `brands.yml`에서 함께 운영할 수 있다.
- 기존 브랜드 요청의 로딩과 오류 처리를 그대로 사용한다.

단점:

- 검색 별칭만큼 `/api/brands` 응답 크기가 늘어난다.
- 검색 순위 규칙이 웹에 위치하므로 다른 클라이언트가 생기면 재구현할 수 있다.

### B. 검색 전용 자동완성 API 추가

설명: 웹이 입력값을 `/api/brand-suggestions`에 보내고 서버가 순위를 계산한 최대
10개의 후보를 반환한다.

장점:

- 검색 규칙을 서버에서 통합하고 여러 클라이언트가 재사용할 수 있다.
- 검색 대상이 커져도 서버 인덱스와 캐시로 확장하기 쉽다.
- 향후 인기 검색어, 개인화, 오타 교정을 서버에서 적용하기 쉽다.

단점:

- 입력 중 네트워크 지연, 요청 취소, 디바운스, 실패 상태를 처리해야 한다.
- 브랜드 목록을 이미 받은 현재 구조에서는 별도 요청의 효용이 작다.
- 현재 브랜드 규모와 단순 일치 규칙에 비해 구현과 운영 복잡도가 크다.

### C. 웹에 검색 별칭을 별도로 하드코딩

설명: API는 변경하지 않고 웹 소스에 대표명과 영문 별칭의 대응표를 둔다.

장점:

- API 계약을 변경하지 않고 웹만으로 구현할 수 있다.
- 초기 구현 범위가 작다.

단점:

- `brands.yml`과 웹의 브랜드 정보가 중복된다.
- 브랜드 추가와 변경 시 두 위치가 어긋날 수 있다.
- 브랜드 지식의 단일 출처라는 현재 구조를 훼손한다.

## 8. 선택

선택한 방법: A. 기존 브랜드 응답에 검색 별칭 포함 후 웹에서 후보 계산

선택 이유: 현재 브랜드 수와 일치 규칙에서는 클라이언트 전체 순회 비용이 작고,
브랜드 목록을 이미 내려받기 때문에 검색 전용 요청의 이점이 없다. 추가 네트워크
상태 없이 즉각 반응하면서 `brands.yml`을 단일 출처로 유지할 수 있다.

원장 통합에 쓰이는 기존 `aliases`와 사용자 검색에 쓰이는 `searchAliases`는
역할이 다르므로 분리한다. 향후 검색 대상이 수천에서 수만 개로 늘거나 오타 교정,
개인화, 서버 기반 순위가 필요해지면 B안으로 전환한다.

## 9. 설계

### Architecture

```text
brands.yml
  name, aliases, searchAliases, category, links
                    |
               BrandCatalog
                    |
             GET /api/brands
                    |
        name, searchAliases, offers, ...
                    |
       shared autocomplete matcher
             /                 \
    SearchControlA          SearchControl
             \                 /
       App.submitSearch(name, "autocomplete")
                    |
       applyFilters + brand_search_submitted
```

### Components

#### `api/src/main/resources/brands.yml`

- 책임: 대표 브랜드별 사용자 검색용 영문 별칭을 `searchAliases`로 관리한다.
- 제약: 원장 정규화 표현은 기존 `aliases`에 두고 사용자 검색 표현과 섞지 않는다.
- 운영 규칙: 필요한 영문 표현만 명시하고 대소문자 중복은 만들지 않는다.

#### `BrandCatalog`와 브랜드 API 모델

- 책임: `searchAliases`를 읽어 대표 브랜드 정보에 보존하고 `/api/brands` JSON에
  배열로 포함한다.
- 기본값: 필드가 없거나 알려지지 않은 브랜드는 빈 배열을 반환한다.
- 검증: trim 후 빈 별칭은 무시하고, 같은 정규화 별칭이 서로 다른 브랜드에
  중복되면 테스트 또는 시작 경고로 발견할 수 있게 한다.
- 기존 계약: `aliases`를 이용한 원장 대표명 변환은 변경하지 않는다.

#### 자동완성 후보 계산 모듈

- 책임: 브랜드 목록과 입력값을 받아 순위가 적용된 최대 10개의 대표 브랜드를
  반환한다.
- 정규화: `trim()` 후 `toLocaleLowerCase()`로 비교한다.
- 한영 전환 보완: 정규화한 영문 원문으로 후보를 먼저 계산하고 결과가 없을 때만
  두벌식 한국어 변환값으로 후보를 다시 계산한다.
- 점수: 정확히 일치 0, 앞부분 일치 1, 포함 일치 2, 불일치는 제외한다.
- 중복 제거: 브랜드별로 가장 높은 일치 점수 하나만 사용한다.
- 안정성: 점수가 같으면 원래 브랜드 배열의 순서를 유지한다.
- 빈 입력 또는 브랜드 미로딩 상태에서는 빈 배열을 반환한다.

#### 공통 자동완성 UI

- 책임: 후보 목록, 활성 인덱스, 방향키 이동, Enter 선택, Escape 닫기, 외부 선택
  닫기의 공통 동작을 제공한다.
- 입력 변경: 후보를 다시 계산하고 활성 인덱스를 초기화한다.
- 후보 선택: 대표 브랜드명을 검색 초안으로 반영한 뒤
  `onSubmit(name, 'autocomplete')`를 한 번 호출한다.
- 직접 제출: 활성 후보가 없으면 기존 `enter` 또는 `button` 계약을 유지한다.
- A안: 검색 패널 자체가 닫힐 때 후보도 함께 닫는다.
- B안: 상시 입력은 유지하고 후보 목록만 닫는다.

#### `App.submitSearch()`

- 책임: 선택한 대표 브랜드명을 기존 필터에 반영하고 `resultCount`를 계산하며
  `brand_search_submitted`를 기록한다.
- 개인정보 경계: 기존과 같이 `inputLength`, `resultCount`, `submitMethod`만 보내고
  입력값과 브랜드명은 보내지 않는다.

### Data Flow

1. API가 `brands.yml`을 읽어 대표명과 `searchAliases`가 포함된 브랜드 목록을
   반환한다.
2. 사용자가 검색창에 입력하면 웹이 영문 원문을 포함한 입력 그대로 로컬 브랜드
   목록에서 일치 점수를 계산한다.
3. 원문 후보가 없고 입력이 두벌식 변환 가능한 영문이면 한국어로 변환해 일치
   점수를 다시 계산한다.
4. 웹은 점수와 기존 브랜드 순서로 정렬한 최대 10개 후보를 표시한다.
5. 사용자가 후보를 선택하면 공통 UI가 대표 브랜드명과 `autocomplete` 제출 방식을
   App 경계로 전달한다.
6. App은 대표명을 검색 필터에 적용하고 기존 `brand_search_submitted` 이벤트를
   검색어 원문 없이 기록한다.

### Error Handling

- 브랜드 목록 미로딩 또는 API 실패 -> 후보를 표시하지 않고 기존 로딩 또는 오류
  화면을 유지한다.
- `searchAliases` 누락 -> 빈 배열로 취급하고 대표명 검색은 유지한다.
- 빈 입력 또는 공백 입력 -> 후보를 닫고 제출하지 않는다.
- 후보가 없는 입력 -> 자동완성 목록만 표시하지 않고 기존 직접 제출을 허용한다.
- 두벌식 변환이 불가능하거나 변환 결과에도 후보가 없음 -> 기존 원문 입력과 직접
  제출 동작을 유지한다.
- 같은 별칭이 한 브랜드 안에서 중복 -> 후보 계산 단계에서 브랜드 한 건으로 합친다.
- 활성 후보가 목록 갱신으로 사라짐 -> 활성 인덱스를 초기화한다.

## 10. 테스트 전략

- Unit:
  - 대표명과 별칭의 정확 일치, 앞부분 일치, 포함 일치 순서를 검증한다.
  - 영문 대소문자와 앞뒤 공백 무시를 검증한다.
  - 영문 원문 후보가 없으면 두벌식 한국어 변환 후보가 표시되는지 검증한다.
  - 영문 원문 후보가 있으면 두벌식 변환 결과를 적용하지 않는지 검증한다.
  - 한 브랜드의 중복 일치 제거, 최대 10개 제한, 동일 점수의 안정 순서를 검증한다.
  - 빈 입력과 브랜드 미로딩 입력을 검증한다.
- API:
  - `brands.yml`의 `searchAliases`가 브랜드 모델과 `/api/brands` 응답에 포함되는지
    검증한다.
  - 별칭이 없는 브랜드와 알려지지 않은 브랜드가 빈 배열을 반환하는지 검증한다.
  - 기존 `aliases` 정규화가 그대로 동작하는지 회귀 검증한다.
- Component:
  - 입력에 따라 후보가 열리고 Escape와 외부 선택으로 닫히는지 검증한다.
  - 방향키 이동과 Enter 선택, 포인터 선택을 검증한다.
  - 후보가 활성화되지 않은 Enter는 기존 직접 제출로 동작하는지 검증한다.
- Analytics:
  - 후보 선택이 `submitMethod=autocomplete`로 한 번 기록되는지 검증한다.
  - 이벤트 props에 입력 원문, 검색 별칭, 브랜드명이 없는지 검증한다.
- Acceptance:
  - A/B 검색 UI에서 한국어, 영문 별칭, 한영 전환을 놓친 영문 입력으로 같은
    브랜드를 선택하고 결과가 반영되는지 확인한다.
  - 웹 테스트와 빌드, 관련 API 테스트를 실행한다.
