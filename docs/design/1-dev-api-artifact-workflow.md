# Design: 개발 API 산출물 워크플로

## 문제와 목표

기존 API CI는 PR과 main을 검증하지만 dev push의 실행 JAR를 보관하지 않는다.
dev 변경을 테스트한 뒤 개발 서버 배포에 사용할 JAR와 식별 정보를 생성한다.

## 요구사항과 성공 조건

- dev의 API, 계약 파일, 워크플로 변경 및 dev 수동 실행을 감지한다.
- GitHub-hosted runner에서 기존 CI와 같은 Java 17로 테스트하고 bootJar를 생성한다.
- 테스트 또는 빌드 실패 시 산출물을 업로드하지 않는다.
- JAR, 체크섬, 커밋과 실행 정보를 GitHub Artifact에 14일 보관한다.
- 운영 미러링과 기존 PR CI는 변경하지 않는다.

## 접근과 선택

S3는 IAM과 보관 정책 관리가 추가되므로 보류한다.
기존 CI의 전면 재구성 대신 독립된 dev 워크플로를 추가한다.
검증 명령은 기존 CI와 맞추고 개발 배포에 필요한 실행 JAR만 패키징한다.

## 설계와 오류 처리

build-api-dev.yml이 테스트, 실행 JAR 빌드, 산출물 준비, 업로드를 순서대로 수행한다.
실행 JAR가 정확히 하나인지 검사하고 체크섬을 검증한다.
수동 실행은 dev에서만 허용하며 새 dev 빌드는 이전 빌드를 취소한다.
산출물 이름에 커밋, 실행 ID, 재실행 번호를 넣어 재실행도 구분한다.

## 검증

워크플로 정적 검사, 셸 구문 검사, Gradle test 및 bootJar를 수행한다.
GitHub 실제 실행은 워크플로가 dev에 반영된 뒤 확인한다.

## 다음 단계

self-hosted runner 등록, 서버 실행 설정, 다운로드와 배포 및 롤백은 별도 작업이다.
이 단계는 서버 배포를 수행하지 않는다.

## 개발 배포 연결 (2026-10-07)

사용자 승인에 따라 같은 워크플로에 self-hosted 배포 job을 추가한다.
개발 EC2의 별도 runner 계정은 root 소유 배포 스크립트만 sudo로 실행한다.
실행 계정, 데이터와 키는 운영과 분리하며 초기 데이터는 저장소 샘플을 사용한다.
배포를 취소하지 않고 직렬화하며 배포 직전 최신 dev SHA를 확인한다.
잘못된 산출물은 서비스 변경 전에 거부하고, 시작 실패는 이전 버전으로 복원한다.
구성과 설치 절차는 `api/deploy/dev/README.md`에 기록한다.
