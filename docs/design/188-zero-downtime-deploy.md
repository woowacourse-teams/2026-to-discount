# 188. 무중단 배포와 롤백 (2026-10-29 작성)

운영 API 배포가 끊김 없이 돌고, 잘못된 배포는 자동으로 또는 커밋 한 번으로 되돌아간다. 2026-10-29에 운영에서 시험을 두 번 해 확인했고 실패한 요청은 0건이다.

용어를 먼저 풀어 둔다.

- 본 인스턴스: 평소 요청을 받는 API 서버 프로세스다.
- 임시 인스턴스: 배포 중에만 잠깐 띄우는 같은 API의 복제 프로세스다. 본 인스턴스를 교체하는 동안 요청을 받는다.
- jar: 자바 앱을 실행 파일 하나로 묶은 것이다.
- 종료 코드: 프로그램이 끝날 때 남기는 숫자이고 0이 성공이다.
- 미러 저장소: mono의 `api/` 폴더를 옮겨 싣고 서버 배포를 돌리는 저장소(`nn98/delivery-discount-api`)다.
- push: 내 커밋을 원격 저장소에 올리는 일이다.
- 되돌림 커밋: `git revert`로 만드는, 앞선 변경을 취소하는 새 커밋이다.

시험 결과는 다음과 같다.

- 시험 1: 배포 한 번과 되돌림 한 번. 읽기 요청(GET) 462건 중 실패 0건이었고 되돌림은 16:19:47에 시작해 16:21:35에 끝났다.
- 시험 2: 본 인스턴스만 시작에 실패하는 jar를 일부러 배포해 자동 복구(종료 코드 2)를 일으켰다. 읽기 요청과 쓰기 요청(POST)을 함께 보냈고 각 450건 중 실패 0건이었다. 배포 단계 61초 안에 이전 jar로 복구가 끝났다.

이 문서는 기록이 있는 것과 없는 것을 나눠 적는다.

### dev와 prod 양쪽에서 동작하는 것을 무엇으로 확인하는가

개발 서버와 운영 서버를 나누지 않았다. 서버는 운영 서버 한 대이고 임시 인스턴스도 같은 서버에서 잠깐 뜬다. 그래서 시험도 운영에서 했다.

- 응답: 외부에서 `/api/brands`(GET)와 `/api/events`(POST)에 1초 간격으로 요청하고 상태 코드를 CSV(쉼표로 나눈 표 파일)로 남겼다.
- 배포 로그: 임시 인스턴스 준비, 본 인스턴스 재시작, 복구 여부가 줄로 찍힌다.
- 종료 코드: 0은 정상, 1은 임시 인스턴스가 안 뜸, 2는 이전 jar로 복구, 3은 사람이 확인해야 한다는 뜻이다.

### 두 환경의 배포 파이프라인 위치

개발과 운영 파이프라인을 나누지 않았다. 한 경로가 운영 서버로 간다.

| 단계 | 하는 일 | 실행 위치 |
| --- | --- | --- |
| 1 | mono main에 변경을 병합한다 | GitHub |
| 2 | 미러 작업이 `api/` 폴더를 미러 저장소로 옮겨 싣는다 | GitHub 러너(자동 작업을 실제로 실행하는 컴퓨터) |
| 3 | 미러 저장소의 `Build and Deploy`가 `./gradlew build`(빌드와 시험)를 돌리고 `stage_deploy.py`를 실행한다 | 운영 서버 위 러너 |

API 러너는 운영 서버 위에서 돌아서 빌드하는 동안 서버 자원을 같이 쓴다. 이 문서의 시험은 2단계를 건너뛰고 미러 저장소 main에 직접 push했다.

### 장애: 배포 때 재시작으로 요청이 끊김 (2026-10-13 추정)

- 무엇이: 요청 ID 작업 배포 직후 21:39:30과 21:39:32 KST에 `/api/banners`가 502(nginx가 뒤쪽 서버에 연결하지 못했다는 응답)를 2건 냈다. 출처는 `docs/design/67-request-id-correlation.md` 218줄이다. 줄에 날짜가 없어 같은 절의 반영 승인일로 본 추정이다.
- 원인: 배포가 `systemctl restart`였다. 새 프로세스는 원장(수집한 할인 정보를 모은 파일) 첫 읽기 3~7초를 마쳐야 답한다. 우아한 종료(처리 중인 요청을 끝내고 내리는 설정)를 켜도 약 5초는 연결이 거부됐다.
- 조치: 임시 인스턴스 교대 배포로 바꿨다(PR #188, 2026-10-28 적용). 본 인스턴스가 30초 안에 안 뜨면 이전 jar로 자동 복구한다.
- 조치 뒤 확인한 지표: 2026-10-28 첫 배포는 외부 조회 75건 중 비정상 응답 0건이다. 2026-10-29 시험 1은 462건 중 0건, 시험 2는 GET 450건과 POST 450건 중 0건이다.

## 실험 프로세스 (요약)

### 배경과 문제

배포가 `systemctl restart`라 배포마다 약 5초 동안 요청이 실패했다. 하루 방문은 수백 명이지만 미러 저장소는 이틀 사이 8번 배포했다. 2026-10-14에는 "5초 끊김은 유지"로 정했다가 2026-10-27에 사용자가 뒤집어 무중단 배포를 진행하라고 지시했다.

### 대안과 선택

| 대안 | 선택 | 이유 |
| --- | --- | --- |
| 평소 구성은 두고 배포 중에만 임시 인스턴스를 띄운다 | 선택 | 서비스 이름과 포트를 그대로 둔다. 서버 쪽 변경이 작다 |
| 두 포트를 번갈아 쓰고 nginx 서버 목록만 바꾼다 | 버림 | 서비스 이름과 포트를 하나로 가정한 곳이 열 군데 넘게 깨진다 |
| 임시 인스턴스의 푸시 발송과 PostHog 전달을 끈다 | 선택 | 같은 상태 파일을 쓰는 스케줄러가 둘 다 돌면 푸시가 두 번 나갈 수 있다 |

### 실행

1. 배포 스크립트 `stage_deploy.py`와 시험 27개를 작성했다(PR #188, 2026-10-28 병합).
2. 2026-10-28 첫 무중단 배포 한 번을 실행하고 외부 조회로 확인했다.
3. 2026-10-29 시험 1: 빈 테스트 커밋을 push해 배포하고 되돌림 커밋으로 되돌렸다.
4. 2026-10-29 시험 2: 본 인스턴스 포트에서만 시작에 실패하는 커밋을 push해 자동 복구를 일으키고 되돌렸다. GET과 POST를 15분 동안 보냈다.

### 결과

- 요청 실패 0건: 시험 1은 GET 462건, 시험 2는 GET 450건과 POST 450건이다.
- 되돌림은 push부터 완료까지 1분 48초 걸렸다.
- 자동 복구는 배포 단계 61초 안에 끝났고 종료 코드 2가 찍혔다.
- 한계: 관측 간격이 1초이고, 자동 복구는 인위적으로 만든 실패이며, 복구 단계의 줄별 시각은 없다. 자세한 내용은 "빠진 증거"에 있다.

### 학습

- 근거 없이 쓴 문장이 후속 문제를 만들었다. "임시 인스턴스는 상태 파일을 쓰지 않는다"는 가정이 틀려 이슈 #192(프로세스 간 파일 락)가 필요해졌다.
- 되돌림과 자동 복구는 절차를 적는 것과 실제로 해 보는 것이 다르다. 시험용 변경 한 건으로 운영에서 두 경로를 모두 확인했다.
- 부하를 세게 보낸다고 좋은 측정이 되지 않는다. 0.2초 간격은 운영 nginx의 요청 제한(HTTP 429)에 걸려 401건이 거절됐고, 그 로그로는 뒤쪽 서버 상태를 알 수 없었다.
- 실행 로그는 단계 끝에 한꺼번에 찍혀 단계 안의 시각이 사라진다. 복구 시간을 알려면 스크립트가 줄마다 시각을 찍어야 한다.

## 빠진 증거

- 자동 복구(종료 코드 2)는 인위적으로 만든 실패다. 본 인스턴스 포트(8088)에서만 시작에 실패하는 시험용 클래스를 넣어 운영에서 그 경로를 일으켰다. 실제 사고로 jar가 깨진 경우의 기록은 아니다.
- 복구 단계의 줄별 시각은 없다. 실행 로그가 단계 끝에 한꺼번에 찍혀 전부 17:29:18로 보여서, 단계 전체 61초(17:28:17~17:29:18)만 안다. 복구 재시작이 몇 초 걸렸는지는 모른다.
- 끊긴 시간은 1초 간격 관측이다. 운영 nginx의 요청 제한(HTTP 429) 때문에 이 PC에서 초당 1건보다 촘촘히 보낼 수 없었다. 1초보다 짧은 끊김은 이 방식으로 잡히지 않는다. 시험 2는 GET과 POST를 번갈아 보내 종류별로는 2초에 한 건이다.
- POST는 `/api/events` 한 종류, 시험 표시(`dev=true`)를 붙여 보냈다. 서버에 저장된 이벤트 수를 보낸 수와 대조하지 않았고, 집계에서 `dev=true`가 빠지는지도 확인하지 않았다.
- 2026-10-28 첫 배포 뒤 미러 저장소의 5번 더 배포(실행 296부터 300)는 요청 실패 수 기록이 없다.
- 시험 1에서 되돌린 대상은 빈 테스트 한 건이고, 시험 2에서 되돌린 대상은 시험용 클래스 한 개다. 둘 다 되돌림 전후 앱 동작이 같다. 절차가 동작한다는 증거이고 "잘못된 기능을 되돌려 고쳤다"는 증거는 아니다.

## 배경

배포가 `systemctl restart`(리눅스 서비스 관리자에게 서비스를 껐다 켜게 하는 명령)라 재시작 순간마다 요청이 실패했다. 실제 사례와 근거는 아래와 같다.

- 요청 ID 작업 배포(운영 API PR #69) 직후 재시작 시점인 21:39:30과 21:39:32 KST에 `/api/banners` 502가 2건 기록됐다(`docs/design/67-request-id-correlation.md` 218줄). 이 줄에 날짜는 없고, 같은 절의 운영 반영 승인일이 2026-10-13이라 그날로 보지만 날짜는 추정이다.
- 502는 nginx(요청을 받아 API 서버로 넘기는 웹 서버)가 뒤쪽 서버에 연결하지 못했다는 응답이다.
- 새 프로세스는 원장 첫 읽기(로컬 3~7초)를 마쳐야 `/api/brands`와 `/api/survey`에 답한다. 우아한 종료(처리 중인 요청을 끝까지 처리하고 내리는 설정)를 켜도 새 요청이 연결 거부되는 약 5초는 그대로다(`api/docs/decisions/ADR-012-spring-boot-4-jackson-3.md` 60줄).
- 2026-10-14에는 "5초 끊김은 지금은 유지"로 정했다. 2026-10-27에 사용자가 기존 설계를 검증해 무중단 배포를 진행하라고 지시해 뒤집었다(PR #188, 이슈 #189).
- 하루 방문이 수백 명이라 한 번 끊기는 영향은 작다(이슈 #192). 다만 배포가 잦다. 미러 저장소는 2026-10-27 21:25 UTC부터 2026-10-29 05:07 UTC까지 이틀 사이 배포 실행 8건이 모두 성공했다(실행 293부터 300). 배포마다 끊기면 그만큼 502가 난다.

# load.py: 사용법 python load.py <주소> <초> <csv경로> [간격초]
import sys, time, urllib.request, datetime as dt
url, secs, out = sys.argv[1], float(sys.argv[2]), sys.argv[3]
STEP = float(sys.argv[4]) if len(sys.argv) > 4 else 0.2
KST = dt.timezone(dt.timedelta(hours=9))
end = time.time() + secs
with open(out, "w", encoding="utf-8", newline="\n") as f:
    f.write("kst,utc,code,ms\n")
    while time.time() < end:
        t0 = time.time()
        try:
            code = urllib.request.urlopen(url, timeout=3).status
        except urllib.error.HTTPError as e:
            code = e.code
        except Exception as e:
            code = type(e).__name__
        ms = int((time.time() - t0) * 1000)
        n = dt.datetime.fromtimestamp(t0, dt.timezone.utc)
        f.write(f"{n.astimezone(KST).strftime('%H:%M:%S.%f')[:-3]},{n.strftime('%H:%M:%S.%f')[:-3]},{code},{ms}\n"); f.flush()
        time.sleep(max(0, STEP - (time.time() - t0)))

### 수동 되돌림: 무중단 방식을 걷어낼 때

미러 저장소 `nn98/delivery-discount-api`의 `.github/workflows/deploy.yml`을 직전 판으로 되돌린다. 미러 이력으로 확인한 사실은 다음과 같다.

- 무중단 교체는 미러 커밋 `0268857`(2026-10-28 06:51:04 UTC, "ci: 배포를 임시 인스턴스 교대(무중단)로 바꾼다") 한 번이다.
- 직전 판은 커밋 `1484898`(2026-09-17)의 `deploy.yml`이다. 부모 커밋은 `9170bcf`다.
- 두 판의 차이는 `Deploy new jar`, `Health check`, `Rollback on failed health check`, `Prune old jars` 네 단계가 `Deploy (임시 인스턴스 교대, 무중단)` 한 단계로 바뀐 것이다.

절차:

1. 미러 저장소에서 `0268857` 커밋을 되돌리는 커밋을 만들어 `main`에 올린다(`git revert 0268857`).
2. 올리면 미러 배포가 돌아 옛 방식(`systemctl restart`, 약 5초 끊김)으로 배포한다.
3. 배포가 끝난 뒤 서비스 응답과 임시 인스턴스 상태를 확인한다.
4. 서버의 임시 유닛, 환경 파일, sudoers 설정, nginx `backup` 줄은 그대로 두어도 무해하다. 임시 인스턴스가 떠 있지 않으면 `backup`은 쓰이지 않는다(요약 메모와 beggars-ops #27 영향 절).

이 절차는 미러 이력으로 대상 커밋을 확인했을 뿐, 실제로 실행하지 않았다.

### 직전 앱 버전으로 되돌리기

되돌릴 변경을 `git revert`로 되돌리는 커밋을 main에 올리면 미러가 새로 빌드해 같은 무중단 순서로 배포한다. 위 시험으로 확인했다. 평소에는 mono main에 되돌림 커밋을 병합하면 미러가 같은 방식으로 따라온다. 이번 시험은 배포 한 번을 빨리 일으키려고 미러 main에 직접 push했다. 미러에 직접 넣은 변경은 다음 mono 미러에 덮이는데(`mirror-deploy-repos.yml`), 이번에는 되돌림 뒤 작업 트리가 mono와 같아 덮일 것이 없었다. 미러의 `workflow_dispatch`(수동 실행)는 켜져 있으나 특정 jar를 고르는 입력이 없어 같은 main 최신만 다시 배포한다.

## 한계와 후속

- 두 인스턴스가 겹치는 10~20초 동안 같은 파일을 쓰는 요청이 오면 한쪽 변경이 사라질 수 있었다. 푸시 상태 파일(`PushStateStore`)과 기프티콘 발급 파일(`GifticonStore`)이 대상이다. 이슈 #192가 프로세스 간 파일 락으로 풀었고 PR #193 병합으로 2026-10-29에 닫혔다. 설계는 `docs/design/192-inter-process-file-lock.md`, 결정은 `ADR-013`이다.
- PR #188 본문의 "임시 인스턴스는 푸시 상태 파일을 쓰지 않는다고 본다"는 코드로 확인한 말이 아니었다. #192 설계에서 구독 해지, 알림 추적, 배너 reload 세 경로가 `enabled=false`여도 상태 파일을 쓴다고 코드로 확인해 바로잡았다.
- 락이 들어간 첫 배포 한 번은 본 인스턴스가 옛 jar라 보호되지 않는다. 배포 뒤 푸시 상태 파일과 `gifticon-issues.jsonl`을 한 번 대조해야 한다. 이 대조 기록은 찾지 못했다.
- 운영자의 `gifticons.yml` 직접 업로드는 락이 막지 못한다(이슈 #192 결과, 범위 밖).
- 본 인스턴스가 재시작하는 5~8초 동안 임시 인스턴스는 푸시 발송을 끄고 있어, 이 사이 푸시 구독 요청은 실패할 수 있다(PR #188 리뷰 포인트).
- 배포 시작 시점에 본 인스턴스가 이미 준비 상태가 아니면 이 배포는 무중단이 아닐 수 있다(스크립트가 경고를 남긴다).
- 운영 nginx에 요청 제한이 있어 이 PC에서 초당 1건 가까이만 보낼 수 있다. 짧은 끊김을 더 촘촘히 보려면 서버 안에서 재야 하고, 이것은 사용자가 직접 실행해야 한다.
- 미러 저장소 `deploy.yml`은 mono가 미러로 옮기는 대상이 아니어서, 배포 워크플로 교체를 따로 했다(PR #188 영향 절, 변경 전파 묶음 8).
- 이 방식을 걷어내는 되돌림은 미러 저장소 커밋 한 건으로 끝나지만, 무중단 방식의 서버 쪽 준비물(임시 유닛, 환경 파일, sudoers, nginx 줄)은 별도 저장소가 관리한다.

## 배운 점

- 근거 없이 쓴 문장이 후속 문제를 만들었다. "임시 인스턴스는 푸시를 끄므로 상태 파일을 쓰지 않는다"는 가정이 틀려 #192가 필요해졌다. 가정은 코드를 읽어 확인한 뒤에 적는다.
- 관측 방법의 한계도 기록에 같이 남겨야 한다. 1초 간격 조회의 "0회"는 1초 미만 끊김이 없다는 뜻이 아니다.
- 이슈, 설계 승인 없이 PR을 먼저 올려 소급 이슈(#189, #190)를 열어야 했다. 개발 워크플로(`docs/design/119-dev-workflow-asbuilt.md`)를 먼저 따르는 편이 추적이 쉽다.
- 처음 안(두 포트 번갈아)은 영향 범위를 조사하자 쓸 수 없다고 드러났다. 구조를 바꾸기 전에 서비스 이름과 포트를 가정한 곳을 센 것이 큰 재작업을 막았다.
- 두 프로세스가 잠깐 함께 뜨는 방식은 공유 파일 쓰기 문제를 새로 만든다. 무중단 배포의 비용을 설계 때 같이 적어야 한다.
- 되돌림은 절차를 적는 것과 실제로 한 번 해 보는 것이 다르다. 2026-10-29에 시험용 변경 한 건으로 해 보니 revert 한 번과 push 한 번으로 1분 48초 만에 직전 내용으로 돌아왔다.
- 부하를 세게 보낸다고 좋은 측정이 아니다. 0.2초 간격은 운영 nginx의 요청 제한에 걸려 401건이 429였고, 그 로그로는 뒤쪽 서버의 상태를 알 수 없었다. 측정 전에 요청 제한이 있는지 먼저 본다.
- 되돌림 시험은 앱 동작을 바꾸지 않는 시험용 변경으로 하면 서비스에 영향 없이 절차를 확인할 수 있다. 대신 기능 되돌림 효과는 증명하지 못한다.
- 자동 복구 같은 실패 경로도 커밋 한 건으로 운영에서 일으킬 수 있다. 서버 설정을 건드리지 않고, 본 인스턴스 포트에서만 시작에 실패하게 하면 임시 인스턴스가 요청을 받는 사이 복구가 돈다. 빌드 시험은 이 조건을 못 보므로 통과한다.
- 실행 로그는 단계 끝에 한꺼번에 찍혀 단계 안의 시각이 사라진다. 복구가 몇 초 걸렸는지 알려면 스크립트가 줄마다 시각을 찍어야 한다.
