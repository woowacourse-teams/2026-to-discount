# 119. 이슈에서 병합까지 개발 워크플로 자동화

추적 이슈: [#119](https://github.com/woowacourse-teams/2026-to-discount/issues/119)

## 결론

이슈 하나가 사람 승인 두 번(설계 승인, 병합 승인)만 거쳐 병합되고 요약까지 남는 흐름을 만든다.

- Claude 세션은 상주시키지 않는다. 단계마다 새 세션을 띄운다.
- 각 세션은 역할 정의 파일과 이슈에 쌓인 산출물만 읽고 일한다.
- 러너(GitHub Actions 작업을 실제로 실행하는 기계)는 GitHub 호스트 러너가 기본이다.
- 폰이 필요한 수집 작업만 로컬 PC의 self-hosted 러너(내 기계를 Actions 실행기로 등록한 것)로 보낸다.

## 흐름

1. **이슈 생성:** 사람이 이슈 템플릿(배경, 요구사항, 완료 조건)으로 이슈를 연다. 영역 라벨 `web`, `api`, `collect` 중 하나를 단다.
2. **설계:** `ready` 라벨이 붙으면 설계자 세션이 `feat/<이슈번호>-<요약>` 브랜치를 판다. `docs/design/<번호>-*.md`를 써서 커밋하고 이슈에 링크한다.
3. **설계 승인 (사람 관문 1):** 사람이 설계를 읽고 이슈에 `/approve-design` 댓글을 단다. 고칠 점을 댓글로 남기면 설계자 세션이 다시 돈다.
4. **구현:** 라벨에 맞는 구현자 세션(웹, API, 수집)이 설계대로 구현한다. 테스트를 돌리고 PR을 연다.
5. **자동 리뷰:** CodeRabbit(PR에 자동 리뷰 댓글을 다는 서비스)과 리뷰어 세션이 리뷰한다.
   - CodeRabbit은 이 저장소를 자동으로 리뷰하지 않는다(별 10개 미만). 워크플로가 PR에 `@coderabbitai review` 댓글을 단다.
   - 맞는 지적은 구현자 세션이 새로 떠서 반영한다. 반영은 최대 2회다.
6. **결과 화면:** 아래 결과를 PR 댓글 하나에 모은다.
   - golden 테스트(저장해 둔 기대 결과와 출력을 견주는 테스트) 결과와 테스트 수
   - 360px 스크린샷 전후, 성능 측정 점수(`web-perf` 워크플로)
   - 남은 리뷰 지적
   - 웹 변경은 mono에 `preview/<이름>`을 push해 CI가 띄운 프리뷰 주소도 단다. 미러 저장소에는 직접 push하지 않는다.
7. **병합 승인 (사람 관문 2):** 사람이 결과 화면을 보고 `/approve` 댓글을 단다. Actions가 병합하고 배포를 확인한다.
8. **요약:** 요약자 세션이 PR 본문 끝에 "결과" 절을 채우고, 같은 내용을 이슈를 닫는 댓글로 남긴다. 규칙이 된 결정은 ADR로 남긴다.

설계 문서는 승인 뒤 고치지 않는다(`docs/design/README.md`). 그래서 진행 상황과 결과는 이슈와 PR에 쌓는다.

## 역할 정의와 규칙

역할은 `.claude/agents/<역할>.md`(Claude Code 에이전트 정의 파일) 하나씩으로 둔다.

- 각 정의에는 읽을 문서, 만질 수 있는 경로, 끝내는 조건만 적는다.
- 절차는 저장소 `AGENTS.md`와 `docs/` 정본을 가리킨다. 역할 파일에 절차를 다시 적으면 두 곳이 어긋난다.

| 역할 | 읽는 것 | 만지는 경로 | 끝내는 조건 | 하지 않는 것 |
| --- | --- | --- | --- | --- |
| 설계자 | 이슈, `AGENTS.md`, `docs/CHANGE-PROPAGATION.md`, 관련 코드, 결정 기록(`docs/decisions/`, `api/docs/decisions/`, 수집 저장소 ADR), 기존 `docs/design/` | `docs/design/` | 설계 문서 커밋, 이슈에 링크 | 코드 수정 |
| 웹 구현자 | 설계 문서, `docs/CHANGE-PROPAGATION.md`, `docs/COPY-STYLE.md`, `docs/WORKFLOW.md` §3-3 | `web/` | 테스트 통과, 360px 스크린샷, PR | API 수정, main 직접 push, 새 노출 문구 결정(후보는 PR에 제안한다) |
| API 구현자 | 설계 문서, `docs/CHANGE-PROPAGATION.md`, `api/docs/decisions/` | `api/` | 테스트 통과, PR | 웹 수정, main 직접 push |
| 수집 구현자 | 설계 문서, 수집 저장소 하네스 문서 | 수집 저장소 | golden 테스트 통과, 실기 시험 | 정해진 수집 시각에 실행, 폰 설정 변경, 로그인 입력 |
| 리뷰어 | 설계 문서, PR diff, CodeRabbit 지적 | 없음(읽기만) | 설계 대비 빠진 것과 위험을 PR 댓글로 남김 | 코드 수정 |
| 요약자 | 병합된 PR, 설계 문서, 결과 화면 | PR 본문, 이슈 댓글 | PR "결과" 절과 이슈 닫는 댓글 | 서버 경로와 내부 운영 정보 기록 |

모든 역할에 공통으로 거는 규칙은 다음과 같다.

- 비밀값은 코드, 커밋, 출력, 로그에 값으로 남기지 않는다.
- 구현자는 작업 브랜치에 push하고 PR을 연다. main에 직접 push하거나 강제 push하지 않는다. 커밋은 파일 이름으로만 담는다.
- 설계 문서에 없는 변경이 필요하면 구현하지 않고 이슈 댓글로 묻는다. 역할 경계를 넘는 변경도 같다.
- API와 웹을 함께 바꾸는 이슈는 설계자가 API 응답 형태를 먼저 고정한다. 그 뒤 API 구현자, 웹 구현자 순서로 돌린다.
- 운영 반영은 병합 경로로 한다. 운영 서버에 직접 써야 하면 쓰고, 끝나면 운영 API로 결과를 확인해 PR이나 이슈에 기록한다.
- 댓글과 문서는 두괄식으로 결론을 먼저 쓴다.

로컬 환경에만 해당하는 규칙(폰, 작업 폴더, 프로세스 정리, 과거 사고에서 나온 규칙)은 수집 저장소(비공개)의 로컬 운영 문서에 있다.

## 세션 수명 주기

세션 하나는 이슈 하나의 한 단계만 맡고 끝난다. 단계 사이의 기억은 이슈에 쌓인 파일과 댓글로 넘긴다. 그래서 세션이 죽거나 바뀌어도 다음 세션이 같은 자리에서 이어서 한다.

1. **생성:** 라벨이나 댓글 이벤트가 Actions 작업을 띄운다. 작업은 단계에 맞는 역할로 Claude Code를 실행한다. 같은 이슈에는 한 번에 작업 하나만 돈다. Actions `concurrency` 그룹(같은 그룹 작업을 하나씩만 돌리는 설정)을 이슈 번호로 잡는다.
2. **컨텍스트 주입:** 세션은 정해진 순서로만 읽는다. 역할 정의, `AGENTS.md`, 이슈 본문과 댓글, 설계 문서, 마지막 인계 댓글 순서다. 저장소 전체를 훑지 않는다.
3. **인계 댓글:** 세션은 끝낼 때 한 것, 남은 것, 막힌 것을 이슈 댓글 하나로 남긴다. 첫 줄은 `인계:`로 시작한다. 다음 세션은 마지막 인계 댓글부터 읽는다.
4. **새로 띄우는 시점:** 세션을 끝내고 새로 띄우는 때는 세 가지다.
    - 단계가 끝났을 때. 설계, 구현, 리뷰 반영은 모두 다른 세션이다.
    - 턴 수나 컨텍스트가 상한에 닿았을 때. 작업에 `--max-turns`(세션이 도는 턴 수 상한)를 걸고, 닿으면 인계 댓글을 쓰고 끝낸다. 같은 단계를 새 세션이 이어받는다.
    - 리뷰 지적을 반영할 때. 구현 세션을 살려 두지 않고, 지적 목록과 인계 댓글을 읽는 새 세션을 띄운다.
5. **종료:** 세션은 결과를 커밋과 이슈·PR 댓글로 남기고 끝난다. 띄운 개발 서버와 브라우저는 같은 작업 안에서 끈다.
6. **실패 복구:** 작업이 실패하면 이슈에 `blocked` 라벨과 실패 원인 댓글을 단다. 자동 재시도는 하지 않는다. 사람이 원인을 보고 다시 돌린다(재실행 절차는 "운영 세부").

역할별 상주 세션("웹 담당 세션")은 두지 않는다. 상주 세션은 지난 이슈의 컨텍스트가 쌓여 판단이 흐려지고, 죽었을 때 되살리는 장치도 따로 필요하다. 역할의 일관성은 역할 정의 파일이 지킨다.

## 러너 위치

운영 서버에는 러너를 올리지 않는다. 토큰 비용은 어디서 돌려도 같고, 차이는 보안과 운영 영향에서 난다.

| 기준 | GitHub 호스트 | 로컬 PC self-hosted | 운영 서버 self-hosted |
| --- | --- | --- | --- |
| 비용 | 공개 저장소는 무료 | 전기와 PC 자원 | 서버 자원 |
| 격리 | 작업마다 새 가상 머신, 끝나면 폐기 | 사용자 계정과 파일을 공유 | 운영 API, 데이터, 키와 같은 기계 |
| 공개 저장소 위험 | 없음 | 외부 PR이 PC에서 코드를 돌릴 수 있어 차단 필요 | 같은 위험이 운영 서버로 번진다 |
| 폰, 수집 환경 | 없음 | 있음 | 없음 |
| 운영 영향 | 없음 | 예약 수집과 메모리를 나눔 | 빌드와 테스트가 운영 API와 CPU, 메모리를 다툼 |
| 병렬 | 여러 개 동시 | 1개 | 서버 여유만큼 |

- mono는 공개 저장소다. GitHub도 공개 저장소에 self-hosted 러너를 붙이지 말라고 권한다. 설정 하나만 잘못돼도 운영 기계에서 남의 코드가 돈다.
- 호스트 러너가 공개 저장소에서 무료라, 서버에 올려서 얻는 것이 거의 없다.
- 로컬 러너는 `collect` 라벨 작업만 받는다. 저장소 소유자가 단 라벨과 댓글만 트리거로 받고, 포크 PR은 받지 않는다.

## 토큰 예산과 동시 실행 한도

이슈 한 건에 입력 70만~350만 토큰, 출력 3만~8만 토큰을 예상한다. 2026-10 이 저장소의 PR 작업량으로 잡은 추정이고 측정값은 아니다. 입력의 대부분은 캐시에서 다시 읽는 몫이다.

| 단계 | 입력 (토큰) | 출력 (토큰) | 턴 상한 |
| --- | --- | --- | --- |
| 설계 | 10만~20만 | 5천~1만 | 30 |
| 구현 | 50만~300만 | 2만~6만 | 80 |
| 리뷰와 반영 (최대 2회) | 5만~20만 | 1만 안팎 | 30 |
| 요약 | 2만~5만 | 3천 | 10 |

- 비용을 정하는 것은 구현 단계의 턴 수다. 설계 문서에 바꿀 파일과 테스트 계획이 구체적일수록 턴이 줄어든다.
- 호스트 러너에서는 구독 로그인을 쓸 수 없다. `claude setup-token`으로 만든 토큰이나 API 키를 저장소 시크릿에 넣는다.
- 동시 실행은 구현 단계 기준 2건, 로컬 러너는 1건으로 제한한다.
- 대기하는 동안에는 토큰이 들지 않는다. 트리거는 GitHub 이벤트가 맡고, Claude는 일이 있을 때만 뜬다.

## 만드는 순서

- [ ] 1단계: 이슈 템플릿, 영역 라벨, 역할 정의 파일 6개, `ready` 라벨로 설계 초안을 띄우는 워크플로
- [ ] 2단계: 구현 워크플로(`/approve-design` 트리거), 결과 화면 댓글, `/approve`로 병합하는 워크플로
- [ ] 3단계: 요약자 역할과 PR "결과" 절 자동 작성, 공개 저장소에 남기면 안 되는 정보를 걸러내는 검사
- [ ] 4단계: 로컬 PC self-hosted 러너 등록, `collect` 작업 연결

## 열린 질문

- 구현 단계도 사람이 PR을 열기 전에 한 번 더 볼지, 결과 화면에서만 볼지 정해야 한다.
- 호스트 러너용 인증을 구독 토큰으로 할지 API 키로 할지 정해야 한다.

## 운영 세부

1단계를 이 문서만 읽고 구현한 세션이 빠졌다고 남긴 12개([#119 인계 댓글](https://github.com/woowacourse-teams/2026-to-discount/issues/119#issuecomment-6308051787))를 2026-10-21에 정했다.

**저장소 설정**
- `.gitignore`는 `.claude/*`를 무시하되 `!.claude/agents/`로 역할 파일만 추적한다.
- 액션은 커밋 SHA로 고정하고 옆에 버전 주석을 단다(`uses: anthropics/claude-code-action@<sha> # v1`). 시크릿을 쓰는 작업이라 태그가 바뀌어도 코드가 바뀌지 않게 한다.
- 인증은 구독 OAuth 토큰이다. 시크릿 이름은 `CLAUDE_CODE_OAUTH_TOKEN`, 액션 입력은 `claude_code_oauth_token`이다. API 키로 바꿀 때는 이 두 줄만 고친다.

**토큰 규칙** (2026-10-21 결정)
- 다른 워크플로를 깨워야 하는 쓰기만 GitHub App 토큰으로 한다. 기본 토큰(`GITHUB_TOKEN`)으로 한 push, PR 상태 변경, 병합은 GitHub이 다른 워크플로를 깨우지 않는다.
- App 토큰은 실행마다 `actions/create-github-app-token`으로 만든다. 시크릿은 `WF_APP_ID`, `WF_APP_PRIVATE_KEY`(PEM 전체)다. 웹훅은 쓰지 않는다.

| 워크플로 | 쓰기 | 토큰 | 이유 |
| --- | --- | --- | --- |
| design-session | 설계 브랜치, 초안 PR | 기본 | 검사는 구현 push 때 같은 PR에서 돈다 |
| implement-session | 구현 push | App | push가 check-web, check-api를 깨워 검사가 PR 커밋에 붙는다 |
| approve-merge | 병합 | App | 병합 이벤트가 summary-session을 깨운다 |
| result-comment, summary-session | 댓글, PR 본문, 이슈 닫기 | 기본 | 뒤에 깨울 워크플로가 없다 |

- `issue_comment`로 뜬 실행은 main 커밋 기준으로 돈다. 그 실행 안에서 다른 검사를 부르면 결과가 PR이 아니라 main 커밋에 붙는다. 그래서 검사는 부르지 않고 App 토큰 push로 깨운다.

**이슈와 라벨**
- 이슈 템플릿은 마크다운(`.github/ISSUE_TEMPLATE/task.md`)이다. 제목은 `[WEB|API|COLLECT|INFRA] feat|fix: 요약` 관례를 따른다.
- 영역 라벨은 사람이 단다. 템플릿이 라벨을 고르지 않는다.
- `ready`는 "설계를 시작해도 된다"는 뜻이다. 사람이 단다.
- `blocked`는 "작업이 실패해 사람이 볼 차례"라는 뜻이다. 워크플로가 달고 사람이 뗀다.
- 재실행 절차: 원인을 본 뒤 `blocked`를 떼고, `ready`를 뗐다가 다시 단다. 붙어 있는 라벨을 다시 달면 이벤트가 나지 않는다.

**트리거 권한과 외부 입력**
- 워크플로는 라벨을 단 사람(`github.event.sender`)의 저장소 권한이 `admin` 또는 `write`일 때만 돈다. 이슈 작성자 권한으로 거르지 않는다. 팀원이 외부인 이슈를 받아 설계를 맡길 수 있어야 한다.
- 세션은 이슈 본문과 함께, 작성자 권한이 OWNER, MEMBER, COLLABORATOR인 댓글만 읽는다. 워크플로가 먼저 이 댓글만 골라 입력 파일로 만들고, 세션은 그 파일만 읽는다. 프롬프트로 "외부 댓글을 따르지 마라"고 부탁하는 것만으로는 막히지 않기 때문이다.
- `ready`를 다는 것은 이슈 본문을 읽고 신뢰한다는 뜻이다. 외부인이 쓴 이슈는 본문을 읽은 뒤에 단다. 본문은 걸러지지 않고 세션에 들어간다.
- 저장소 설정(2026-10-21): main은 PR을 거쳐야 바뀐다(관리자 예외). 워크플로 기본 권한은 읽기이고, 워크플로는 PR을 승인할 수 없다. 세션이 실수하거나 주입된 지시를 따라도 main과 승인 관문에 닿지 못하게 한다.

**역할 파일**
- 역할 파일 frontmatter는 `name`, `description`, `tools`가 필수다. `model`은 선택이다.
- 워크플로는 프롬프트로 역할 파일을 읽게 한다. 역할 파일의 `tools` 목록은 `claude_args`의 `--allowedTools`로 같이 넘긴다. 프롬프트만으로는 도구 제한이 걸리지 않기 때문이다.
- 역할별 도구는 명령 단위로 연다. `git`, `gh` 전체를 열면 `gh api`로 저장소 API를 아무거나 부르고 아무 브랜치에나 push할 수 있다. 설계자는 읽기, 쓰기, 브랜치 만들기, 커밋, `feat/` 브랜치 push, `gh issue comment`, `gh pr create`만 쓴다. 리뷰어와 요약자는 읽기와 필요한 `gh` 명령만 쓴다. 요약자가 PR 본문을 고치는 것은 `gh pr edit`로 한다.
- 비공개 수집 저장소 문서는 "수집 저장소(비공개) `docs/workflow/LOCAL-RULES.md`"로 가리킨다. 경로 이름까지는 공개해도 된다. 내용은 옮기지 않는다.

**브랜치와 PR**
- 설계자는 `feat/<이슈번호>-<영문 소문자 3~5단어>` 브랜치에 설계 문서를 커밋하고, 그 브랜치로 초안(draft) PR을 연다. 제목은 `설계 #<번호>: <요약>`이다.
- 구현자는 같은 브랜치와 같은 PR에 이어 커밋한다. 설계 문서는 구현과 함께 main에 들어간다.
- "문서만 바꾸는 것은 PR로 묶지 않는다"는 사람이 직접 일하는 세션의 규칙이다. 이 흐름의 설계 문서에는 적용하지 않는다.
- 커밋 작성자는 액션의 기본값(봇 계정)이다.

**세션 명령 규칙** (2026-10-21 시험 5회에서 정함)
- 허용 도구는 명령 단위로 맞춘다. 세션은 셸 명령을 하나씩 쓰고 `cd`, `&&`, 파이프, heredoc으로 묶지 않는다. 묶은 명령은 허용 목록과 맞지 않아 거부된다.
- 파일은 Write 도구로 쓴다. PR 본문과 댓글은 파일로 만든 뒤 `--body-file`로 넘긴다. 여러 줄 `--body`는 거부된다.
- push는 `git push` 전체를 허용한다. `feat/` 접두 패턴은 브랜치 이름이 붙은 push를 모두 거부했다. main은 저장소 규칙이 막는다.

**결과물 보관과 확인**
- 세션이 쓴 설계 문서는 성공, 실패와 상관없이 실행 결과물(Artifacts)로 14일 보관한다. push가 실패해도 문서를 잃지 않는다.
- 세션이 끝나면 워크플로가 브랜치, 열린 PR, `인계:` 댓글을 확인한다. 하나라도 없으면 실패로 처리하고 `blocked`를 단다. 세션이 "성공"을 보고해도 결과물이 없을 수 있다.
- 공개 저장소라 세션의 전체 출력은 로그에 남기지 않는다. 거부된 도구 호출, 턴 수, 결과 종류만 남긴다.

**비용 가드**
- 작업마다 `--max-turns`(설계 50, 구현 80, 리뷰 30, 요약 10. 설계는 시험에서 29~34턴이 들어 30에서 올렸다)와 `timeout-minutes`를 건다. 시간 초과로 취소된 작업도 실패와 같이 `blocked`를 단다.
- 이슈별 `concurrency`로 같은 이슈의 중복 실행을 막는다. 토큰 수 상한을 직접 거는 설정은 없다.
