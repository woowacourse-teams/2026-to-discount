# PMF 설문 운영과 참여 흐름

상태: 구현 전 설계 검토

기준일: 2026-11-04

## 1. 문제

기존 설문은 누적 접속일 7일과 할인 링크 및 배너 클릭 5회를 기준으로 참여자를 고른다.
응답 완료는 쿠폰 지급 여부와 연결되어 있고 설문별 참여 및 닫기 기록을 구분하지 않는다.
새 PMF 설문을 단순히 문항만 교체해 열면 과거 참여자가 제외되거나 보상 없는 응답을 완료로 처리하지 못할 수 있다.

## 2. 목표

- 최근 2주 내 핵심 가치를 경험하고 재방문한 팀 밖 사용자에게 PMF 설문 참여를 안내한다.
- 우측 하단 안내를 누르면 중앙 모달에서 응답한다. 모달을 자동으로 열지 않는다.
- 닫기 확인 후에는 같은 사용자에게 해당 설문과 안내를 다시 표시하지 않는다.
- 기존 설문 응답과 쿠폰 링크를 보존한다.

## 3. Non-goals

- 쿠폰 지급, 보상 재고 관리, 연락처 수집
- 로그인 도입이나 여러 기기를 같은 사람으로 연결하는 기능
- 다른 설문을 관리하는 범용 운영 콘솔
- GitHub 이슈 생성, PR 생성, push, 병합, 배포

## 4. 요구사항

### 대상

- 현재 시각 기준 최근 14일 안에 `offer_link_click` 또는 `banner_click`을 한 번 이상 기록한 사용자
- 해당 행동 이후 시작된 다른 세션으로 재방문한 사용자
- 개발 및 봇 트래픽 제외. 팀 밖 여부는 기존 개발 트래픽 식별을 활용하되 미표시 팀 기기까지 식별한다고 주장하지 않는다.
- 누적 접속일 7일과 전환 5회 조건은 적용하지 않는다.
- 같은 PMF 설문에 응답했거나 닫기를 확정한 사용자는 제외한다.

### 화면

- 대상에게 주황색 계열 우측 하단 안내를 표시한다.
- 안내를 누르면 중앙 모달을 연다. 기존 할인 목록 안에는 설문 카드를 넣지 않는다.
- Figma `오늘의 할인 디자인 시스템`의 `03-Exploration / REVIEW / PMF 설문 / Beggars`를 배치 참고로 사용한다.
- 과거 설문의 안내 형태를 참고하되 민트색 및 보상 문구는 사용하지 않는다.
- 기본 강조색은 기존 `--sale`, 옅은 배경은 `--sale-weak`를 재사용한다. 밝은 주황색 위 작은 흰 글자 조합은 피한다.
- `잠시 닫기`와 `다시 보지 않기`는 `닫기` 하나로 합친다.
- 안내의 닫기, 모달의 닫기, Escape, 배경 클릭은 모두 같은 닫기 확인 흐름을 사용한다.
- 확인 팝업 문구: `이 설문을 닫으면 다시 표시되지 않습니다. 닫으시겠습니까?`
- 확인 팝업 버튼: `계속 응답하기`, `설문 닫기`
- `계속 응답하기`를 누르면 이전 화면과 작성 상태로 돌아간다.
- `설문 닫기`를 확정하면 해당 설문의 안내와 모달을 숨긴다. 재방문해도 다시 표시하지 않는다.
- 제출 중에는 중복 제출과 닫기 확정을 막는다.
- 완료 시 감사 안내 후 설문 안내와 모달을 숨긴다.

### 문항

첫 문항과 선택지는 변경하지 않는다.

> 이 제품을 더 이상 쓸 수 없다면 어떻겠습니까?
>
> - 매우 실망
> - 약간 실망
> - 실망하지 않음
> - 더 이상 쓰지 않음

추가 문항은 선택 응답으로 둔다.

1. `이 제품에서 가장 도움이 되는 점은 무엇인가요?`
   - 새로운 할인 확인
   - 여러 배달앱의 할인 비교
   - 더 저렴하게 주문할 할인 찾기
   - 할인율이 적용된 금액과 조건 확인
   - 아직 도움이 되는 점을 느끼지 못함
   - 기타
2. `이용하면서 가장 아쉬웠던 점은 무엇인가요?`
   - 원하는 브랜드나 할인이 부족함
   - 이미 끝난 할인이 표시됨
   - 원하는 할인을 찾기 어려움
   - 할인 조건을 이해하기 어려움
   - 제공되는 할인 혜택이 기대보다 작음
   - 특별히 아쉬운 점이 없음
   - 기타

두 추가 문항은 단일 선택이다. `기타`를 선택하면 직접 입력란을 표시한다.
기타를 선택한 채 제출할 때는 공백이 아닌 내용을 요구하며 기존 200자 제한과 서버 개인정보 정제 규칙을 적용한다.
자유 입력은 PostHog로 전달하지 않는다.

## 5. 제약사항

- 사용자 구분은 기존 익명 `visitorId` 기준이다. 브라우저 저장소 삭제나 다른 기기까지 동일 사용자로 식별하지 못한다.
- 기존 설문의 응답 토큰과 쿠폰 저장값은 덮어쓰지 않는다.
- PMF 응답 완료는 쿠폰 발급 및 재고와 무관하게 기록한다.
- 종료 검사는 저장값과 개발용 표시보다 먼저 적용한다.
- 신규 문항 토큰과 서버 검증 목록은 함께 변경한다.
- 서버를 먼저 배포하고 웹을 나중에 반영한다. 웹은 360px 확인과 프리뷰 승인 후 main 반영 절차를 따른다.

## 6. 성공 조건

- [ ] 최근 14일, 핵심 행동, 이후 다른 세션의 순서를 모두 만족할 때 안내한다.
- [ ] 같은 세션의 새로고침이나 14일 이전 행동만으로 안내하지 않는다.
- [ ] 기존 설문 참여와 닫기 기록이 PMF 설문 참여를 막지 않는다.
- [ ] 안내 클릭 전에는 중앙 모달이 자동으로 열리지 않는다.
- [ ] 닫기 확인 취소 시 답변이 유지된다.
- [ ] 닫기 확정 후 새로고침 및 재방문에도 해당 설문을 표시하지 않는다.
- [ ] 보상 없이 응답을 저장하고 중복 참여를 막는다.
- [ ] HTTP 실패 시 작성한 답변을 유지하며 재시도할 수 있다.
- [ ] 필터 변경으로 모달과 작성 중인 응답이 초기화되지 않는다.
- [ ] 360px에서 안내, 모달, 확인 팝업이 화면 밖으로 나가지 않는다.

## 7. 고려한 접근 방식과 선택

| 접근 | 장점 | 한계 |
| --- | --- | --- |
| 기존 쿠폰 설문의 문항과 상수만 교체 | 변경량이 작음 | 기존 참여 기록과 보상 완료 규칙이 새 설문에 섞임 |
| PMF 설문 ID로 상태를 분리하고 기존 구성 재사용 | 기존 기록을 보존하면서 대상과 완료 규칙 변경 가능 | 서버와 웹 계약 및 상태 전이 검증 필요 |
| 범용 설문 운영 시스템 신규 도입 | 여러 설문 운영에 유리 | 현재 단일 PMF 설문에 필요한 범위보다 큼 |

선택: PMF 설문 ID로 상태를 분리하고 기존 구성 재사용.

선정 근거: 기존 데이터 보존과 보상 없는 설문 운영을 함께 만족한다.

감수한 제약: 익명 브라우저 식별의 한계를 유지한다.

## 8. 설계

### 서버

- PMF용 고정 설문 ID를 사용하고 요청과 기록에 포함한다.
- 이벤트 원장에서 최근 핵심 행동과 세션 시작 순서를 판정한다. 누적 횟수만으로 대체하지 않는다.
- 현재 세션 이벤트가 원장에 반영되기 전이라는 이유로 재방문을 영구 탈락시키지 않는다. 세션 기록과 대상 조회 순서를 구현에서 함께 검증한다.
- 닫기 확정과 응답 완료는 설문 ID 및 visitorId로 구분해 서버에 기록한다.
- 응답과 닫기 확정 요청에서도 서버 상태를 재검증한다. 브라우저 조회 결과만 믿지 않는다.
- 서버 재시작 및 이벤트 집계 스냅샷 복원 후에도 14일 경계와 설문별 상태가 유지돼야 한다.
- 기존 쿠폰 조회 경로 및 기존 원장의 의미는 보존한다.

### 웹

- `useSurvey`가 안내, 모달, 닫기 확인, 제출 상태와 응답 초안을 관리한다.
- `SurveyDock`은 우측 하단 열기 및 닫기 요청을 전달한다.
- `SurveyCard`는 중앙 모달 내부 질문과 제출 UI를 담당한다.
- 할인 목록의 필터와 설문 초안 수명을 분리한다.
- 닫기를 확정하면 설문 ID별 브라우저 기록을 남기고 즉시 숨긴다. 서버 저장이 실패해도 같은 브라우저에서는 다시 표시하지 않고 실패 이벤트를 남긴다.
- 응답 저장이 실패하면 안내하고 재시도하도록 한다.
- 키보드 포커스는 설문 모달에서 닫기 확인으로 이동하고 취소 시 원래 위치로 복원한다.

### 변경 전파

- `docs/CHANGE-PROPAGATION.md`의 행동 이벤트 묶음: 웹 전송, API 허용 목록, 계약 검사를 함께 확인한다.
- 새 문항의 서버 검증, 응답 저장, 웹 문항 설정을 함께 변경한다.
- 오퍼 판정, 배너 분류, 브랜드 링크 묶음은 이번 변경 대상이 아니다.

## 9. 구현 순서와 검증 계획

1. 설계 승인 후 `feat/pmf-survey` 브랜치를 생성하고 실제 이름을 확인한다. 기존 사용자 변경은 보존한다.
2. 서버 설문 ID와 무보상 완료 및 닫기 상태 저장을 먼저 구현한다.
3. 최근 14일과 세션 순서 판정, 재시작 및 스냅샷 복원 회귀 테스트를 추가한다.
4. 웹의 설문 초안을 상위 상태로 이동하고 중앙 모달과 통합 닫기 확인 흐름을 구현한다.
5. 문항 및 기타 입력, 주황색 안내와 모달 스타일을 적용한다.
6. 대상 판정, 응답 검증, 중복 요청, 종료 상태, HTTP 실패 및 모달 상태 전이를 테스트한다.
7. `web/package.json`의 test 명령에 새 테스트를 포함한다.
8. 웹 테스트 및 빌드, 관련 API 테스트, 행동 이벤트 계약 검사, 구조 문서 검사와 `git diff --check`를 실행한다.
9. 360px에서 대상 노출, 닫기 취소 및 확정, 기타 입력, 제출 완료와 실패를 확인한다.
10. push 및 프리뷰 배포는 별도 승인 범위에서 진행한다.

## 10. 미해결 사항

- 설계 전체에 대한 구현 전 승인
- 실제 모집 기간과 종료 시점은 운영 반영 전에 확정한다. 구현 중 운영 설문을 임의로 활성화하지 않는다.
