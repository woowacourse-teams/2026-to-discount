# 26. 운영 관측 한 곳으로 — 수집·API·웹·배포·서버를 한 화면과 한 알림 채널에 (2026-09-17)

상태: 1단계(수집 현황·슬랙 알림) 구현 완료, 2단계(서버 탭) 계획 승인·착수.
계획 문서: tracker `docs/superpowers/plans/2026-09-17-ops-status-and-alerts.md`(1단계),
`2026-09-17-ops-server-tabs.md`(2단계).

## 1. 배경

이 서비스는 네 곳에서 돈다 — 집 안 수집 PC(폰 판독, 하루 3회), OCI 서버(API·nginx·데이터
파일), Vercel(웹), GitHub Actions(테스트·미러·배포). 각각이 제 로그를 제 자리에 남긴다.

| 무엇 | 어디에 남나 | 누가 볼 수 있나 |
|---|---|---|
| 수집 실행 로그·판정 | 수집 PC `logs/after-open-<날짜>.log`, `check_routine.py` | 그 PC 앞에 앉은 사람, 또는 이 세션 |
| API 오류·재시작·reload | OCI `journalctl -u delivery-discount-api` | ssh 키가 있는 사람 1명 |
| 웹 트래픽·4xx/5xx·rate limit | OCI `/var/log/nginx/access.log` | 같음 |
| 배포 성공/실패 | GitHub Actions | **워크플로 실패 메일은 액션 소유자에게만** |
| 웹 배포·프리뷰 | Vercel 대시보드 | 소유자 계정 |
| 사용자 행동 | PostHog | 초대된 사람 |

## 2. 현재 상황과 문제

1. **실패를 아는 사람이 한 명이고, 그마저 늦게 안다.** CI 실패 메일은 액션 오너에게만 간다.
   09-16 18:16부터 `Check Project Structure`가 **7회 연속 실패**했는데 09-17 11:25에야
   사용자가 발견했다(최근 60회 중 실패 7회 전부 이 부류). 09-07에도 API 배포 실패 2회,
   구조 검사 실패 2회가 같은 방식으로 늦게 알려졌다.
2. **수집 실패는 아무에게도 안 간다.** 예약 실행이 FAIL로 끝나도 로그 파일에만 남는다. 09-16
   00:05 커밋 단계 크래시, 09-17 00:01·10:55·15:55 배민 쿠폰함 실패 전부 사람이 로그를 열어야
   알 수 있었다(이 세션이 대신 읽고 있었다).
3. **팀원이 서버에 직접 들어가기 어렵고 부담스럽다.** ssh 키·sudo·journalctl·nginx 로그 위치를
   알아야 하고, 실수하면 운영이 멈춘다. 그래서 "서버 어때요?"가 한 사람에게 몰린다.
4. **한 사건을 보려면 네 곳을 돈다.** "오늘 아침 배민 쿠폰이 왜 없지?" → 수집 로그(PC) →
   export 반영 여부(GitHub) → API reload(journal) → 웹 번들(Vercel). 각각 다른 로그인.

## 3. 근거 — 왜 이게 지금 우선인가

- 사고 30건(tracker `COLLECTION-INCIDENTS.md`) 중 "늦게 알아서 커진 것"이 반복 부류다:
  구조 검사 7회 연속, CE 대표값 닷새 동안 0, 브랜드관 산출 0을 사흘 뒤 인지.
- 수집 PC는 인바운드가 없다(집 안). 그래서 "들어가서 본다"는 애초에 안 되고, **밖으로
  밀어내는 구조**가 유일한 답이다(설계 §4).
- 서버·nginx·Basic Auth·ssh 키가 이미 있다 — 정적 파일 몇 개와 cron 하나면 된다. 새
  서비스(Grafana·Sentry·Datadog)를 세울 규모가 아니다(팀 3명, 요청 하루 수천).

## 4. 대안과 선택

| 대안 | 내용 | 판단 |
|---|---|---|
| A. 서버에 올린 정적 JSON + 한 페이지 대시보드 + 슬랙 알림 (**선택**) | 수집 PC는 scp로 밀어 올리고, 서버는 cron으로 제 상태를 JSON으로 쓴다. nginx Basic Auth 아래 정적 HTML 한 장이 탭으로 보여준다. 슬랙은 알림만 | 새 서비스 0, API 코드 0, 팀원은 URL+비번만. 실시간성은 5초(수집)·5분(서버) 폴링으로 충분 |
| B. 수집 PC로 들어가기 (Tailscale + OpenSSH) | 로그 원문·adb를 원격에서 직접 | 관리자 설치·로그인이 사람 손, 폰에 터미널 필요. 대시보드가 없다. **보류, 절차만 기록** (tracker `MINIPC-HANDOVER §4-b`) |
| C. 관측 SaaS (Sentry·Grafana Cloud·Better Stack) | 에러 추적·로그 수집·알림 일체 | 계정·에이전트·비용, 수집 PC 로그를 넣으려면 결국 A의 업로드가 필요. 규모 대비 과함 |
| D. GitHub Actions 알림을 슬랙으로만 | 실패 메일 대신 슬랙 | 배포 실패는 해결되지만 수집·서버·트래픽은 그대로. A의 한 탭으로 흡수 |
| 카카오톡 알림 | "나에게 보내기"만, 토큰 6시간 만료 | 팀 채널 불가 → 슬랙 |

선택 A + 슬랙. 슬랙 밀도는 `alert`(시작·실패·재시도·완료만) — 내용은 대시보드가 맡는다.
D는 A의 "배포" 탭 + GitHub 워크플로에 슬랙 알림 스텝 하나로 흡수한다.

## 5. 실행 — 1단계 (완료, 09-17)

```
수집 PC  run_routine ─이벤트─▶ capture/ops.py ─▶ logs/state.json
                                   ├─ SlackSink  (~/.slack_ops, alert)
                                   └─ UploadSink (scp) ─▶ OCI /var/www/ops/{state.json, steps/, runs/, logs/}
팀원 ──▶ https://<api host>/ops/  (Basic Auth)  ── 대시보드 index.html 5초 폴링
개발자 ─▶ python scripts/status.py [--remote] [--history] [--run <id>] [--log <단계>]
```

- 이벤트 6종(run_start·step_start·step_progress·step_end·retry·guard·run_end)이 한 파일을
  갱신하고, 싱크는 큐 스레드 하나로 단계 진행을 막지 않는다. 싱크 실패는 로그 한 줄, 수집은
  계속.
- 단계 로그가 줄 단위로 실시간 저장·업로드된다. 대시보드는 단계마다 제목("배민 쿠폰함")과
  설명("마이배민 → 쿠폰함, 보유 쿠폰 전부")을 스크립트 이름 옆에 보여준다.
- 지난 실행: 대시보드 "최근 실행" 클릭(`?run=`), 단계별 로그 링크, `/ops/logs/` 통합 로그
  원문(날짜별).
- 슬랙 봇: 매니페스트로 5분(tracker `docs/setup/SLACK-SETUP.md`). 권한 `chat:write`·
  `files:write`만, 읽기 없음.

## 7. 학습

- **원천을 하나로**(state.json)가 핵심이었다. 슬랙·CLI·대시보드가 같은 파일을 읽으니 서로
  어긋날 수 없고, 밀도 전환이 설정값 하나다.
- 알림은 "실패했다"까지만, 자세한 건 링크. 채널에 단계마다 쓰면 아무도 안 읽는다.
- 테스트가 실 세계(서버·폰)를 건드리지 않게 하는 것은 첫 커밋에 넣어야 한다 — 두 시간 살아
  있던 pytest가 폰에 adb를 두드렸다.
- 점검표에 적힌 검사는 사람이 안 돌린다 → 훅으로 강제(mono pre-push). 관측도 같다: "가서
  본다"가 아니라 "오게 한다".

## 8. 다음 스텝 — 2단계 서버 탭 (승인, 착수)

서버가 cron(5분)으로 제 상태를 `/var/www/ops/server/*.json`에 쓰고, 대시보드에 탭이 는다.
API 코드 0줄, 개인정보 0(IP·UA 저장 안 함 — 집계만).

| 순서 | 탭 | 원천 | 보여줄 것 |
|---|---|---|---|
| 1 | API | `journalctl -u delivery-discount-api` | 최근 ERROR/WARN, 마지막 재시작, export 로드 건수·시각, reload 시각 |
| 1 | 데이터 | `data/export.json`, `banners.yml`, `events.jsonl` | 오퍼 수·최신 capturedAt, 라이브 배너(종료일·매진), 오늘 이벤트·클릭 수 |
| 1 | 서버 | `df`·`free`·`uptime`·인증서 만료 | 디스크·메모리·업타임·certbot 만료일 |
| 2 | 웹 트래픽 | `/var/log/nginx/access.log` | 시간대별 요청, 4xx/5xx/429, 상위 경로, 봇 비율(집계만) |
| 3 | 배포 | GitHub Actions | 최근 워크플로 결론·시각·커밋(gh 토큰 서버 보관 필요) + **실패를 슬랙 채널로**(워크플로 스텝) |

보완점: 알림이 슬랙 한 채널이라 채널이 죽으면 조용하다 → 대시보드 상단에 "마지막 수집 시각"
경고(6시간 넘으면 빨강)를 둬 침묵도 보이게 한다. 2단계에 포함.

## 9. 하지 않는 것

- 로그 원문을 통째로 공개 경로에 두지 않는다(Basic Auth 아래만). IP·UA 원문은 대시보드에도
  안 올린다.
- 수집 PC로 들어가는 길(B)은 절차만. 필요해지면 그때.
- SaaS 관측 도구 도입은 팀·트래픽이 지금의 10배가 될 때 다시 본다.
