# 26. 운영 관측을 한 화면과 한 알림 채널로 모은다 (2026-09-17)

결정: 수집 PC와 서버의 상태를 서버의 정적 파일로 모아 대시보드 한 장으로 보여 주고, 슬랙에는 실패와 완료 알림만 보낸다. 1단계(수집 현황과 슬랙 알림)는 2026-09-17에 구현을 마쳤다. 2단계(서버 상태 탭)는 계획을 승인받아 시작한다.

계획 문서는 tracker 저장소에 있다.
- 1단계: `docs/superpowers/plans/2026-09-17-ops-status-and-alerts.md`
- 2단계: `docs/superpowers/plans/2026-09-17-ops-server-tabs.md`

## 1. 배경

| 어디 | 무엇을 하나 | 로그가 남는 자리 | 볼 수 있는 사람 |
|---|---|---|---|
| 수집 PC (집 안 Windows) | 폰으로 배달앱 화면을 읽어 원장에 쌓는다. 하루 3회(00:01, 10:55, 15:55) | `logs/after-open-<날짜>.log`, 판정기 `check_routine.py` | 그 PC 앞에 앉은 사람 |
| OCI 서버 | API, nginx, 데이터 파일(export.json, banners.yml, events.jsonl) | `journalctl -u delivery-discount-api`, `/var/log/nginx/access.log` | ssh 키를 가진 사람 1명 |
| Vercel | 웹 화면 배포와 프리뷰 | Vercel 대시보드 | 소유자 계정 |
| GitHub Actions | 테스트, 미러 저장소 복사, API 배포, 데이터 배포 | 워크플로 실행 기록 | 실패 메일은 워크플로 소유자에게만 간다 |

## 2. 문제

1. 실패를 아는 사람이 한 명이고, 그 한 명도 늦게 안다. GitHub Actions의 실패 메일은 워크플로 소유자에게만 간다. mono 저장소의 `Check Project Structure` 워크플로가 2026-09-16 18:16부터 7회 연속 실패했는데, 소유자가 2026-09-17 11:25에야 발견했다. 최근 60회 실행 중 실패 7회가 전부 이 워크플로였다. 2026-09-07에도 API 배포 실패 2회와 구조 검사 실패 2회를 같은 방식으로 늦게 알았다.
2. 수집 실패는 아무에게도 알려지지 않는다. 예약 실행이 실패로 끝나도 수집 PC의 로그 파일에만 남는다. 2026-09-16 00:05의 커밋 단계 충돌, 2026-09-17 00:01과 10:55와 15:55의 배민 쿠폰함 실패는 모두 사람이 로그 파일을 열어야 알 수 있었다.
3. 팀원이 서버에 직접 들어가기 어렵다. ssh 키, sudo, journalctl 사용법, nginx 로그 위치를 알아야 하고, 실수하면 운영이 멈춘다. 그래서 "서버 괜찮아요?"라는 질문이 한 사람에게 몰린다.
4. 한 사건을 보려면 네 곳을 돈다. "오늘 아침 배민 쿠폰이 왜 비었나"를 알려면 수집 PC의 로그, GitHub의 export.json 반영 여부, 서버 journal의 reload 기록, Vercel의 웹 번들을 차례로 봐야 한다. 로그인이 각각 다르다.

## 3. 근거

- tracker 저장소 `docs/setup/COLLECTION-INCIDENTS.md`의 사고 30건 중 "늦게 알아서 커진 사고"가 반복된다. 구조 검사 7회 연속 실패, 쿠팡이츠 대표값이 닷새 동안 0이었던 사고, 배민 브랜드관 산출이 0인 것을 사흘 뒤에 안 사고가 그 예다.
- 수집 PC는 집 안에 있어 밖에서 들어올 수 없다. 그래서 "들어가서 본다"는 방법이 없고, 수집 PC가 상태를 밖으로 밀어내야 한다.
- 서버, nginx, Basic Auth, 수집 PC의 서버 ssh 키가 이미 있다. 팀은 3명이고 웹 요청은 하루 수천 건이다.

## 4. 대안과 선택

| 대안 | 내용 | 판단 |
|---|---|---|
| A. 서버의 정적 JSON과 대시보드 한 장, 슬랙 알림 | 수집 PC가 scp로 상태를 올리고, 서버는 cron으로 자기 상태를 JSON으로 쓴다. nginx Basic Auth 아래 정적 HTML 한 장이 탭으로 보여 준다. 슬랙은 알림만 | 선택. 이미 있는 서버와 nginx에 정적 파일 몇 개와 cron 하나만 더한다. API 코드는 바꾸지 않는다. 팀원은 주소와 비밀번호만 알면 된다. 갱신 주기는 수집 5초(단계가 수십 초에서 수 분 단위로 바뀐다), 서버 5분(디스크나 오류 수는 분 단위로 보면 충분하다) |
| B. 수집 PC로 들어가기 (Tailscale과 OpenSSH) | 로그 원문과 adb를 원격에서 직접 다룬다 | 보류. 관리자 권한 설치와 로그인이 사람 손이고 폰에서는 터미널이 필요하다. 절차만 tracker `docs/setup/MINIPC-HANDOVER.md` 4-b절에 적었다 |
| C. 관측 SaaS (Sentry, Grafana Cloud, Better Stack) | 오류 추적과 로그 수집과 알림을 한 서비스가 맡는다 | 기각. 계정과 에이전트와 비용이 들고, 수집 PC 로그를 넣으려면 결국 A와 같은 업로드가 필요하다 |
| D. GitHub Actions 실패를 슬랙으로 | 실패 메일 대신 슬랙 채널 | A의 배포 탭과 워크플로의 슬랙 알림 스텝으로 흡수한다 |
| 카카오톡 알림 | 공식 API는 "나에게 보내기"만 되고 토큰이 6시간마다 만료된다 | 기각. 팀 채널을 만들 수 없다 |

슬랙에 보낼 이벤트 범위(설정값 `mode`)는 `alert`로 정했다. 실행 시작, 실패, 재시도, 완료만 보내고 내용은 대시보드가 맡는다. 단계마다 채널에 쓰면 아무도 읽지 않는다. 처음 하루는 `verbose`(단계마다 한 줄)로 보고 나서 정했다.

## 5. 실행 (1단계, 2026-09-17 완료)

```
수집 PC  run_routine.py ─이벤트─▶ capture/ops.py ─▶ logs/state.json
                                     ├─ SlackSink   (~/.slack_ops, alert 모드)
                                     └─ UploadSink  (scp) ─▶ 서버 /var/www/ops/{state.json, steps/, runs/, logs/}
팀원     https://<API 호스트>/ops/  (Basic Auth)  대시보드 index.html, 5초 폴링
개발자   python scripts/status.py [--remote] [--history] [--run <실행 id>] [--log <단계>]
```

- 예약 실행기 `run_routine.py`가 이벤트 7종(run_start, step_start, step_progress, step_end, retry, guard, run_end)마다 `capture/ops.py`를 부른다. `ops.py`는 `logs/state.json`을 통째로 다시 쓰고 같은 이벤트를 싱크 둘(슬랙 `SlackSink`, 서버 업로드 `UploadSink`)에 넘긴다.
- 싱크 둘은 스레드 하나의 큐로 이벤트를 받는다. ssh나 HTTP가 느려도 단계 진행을 막지 않는다. 싱크가 실패하면 로그 한 줄만 남기고 수집은 계속한다.
- 단계 로그를 줄 단위로 저장하고 올린다. 브랜드관 순회처럼 한 시간짜리 단계의 진행(`[31/89]`)이 실행 중에 보인다.
- 대시보드는 단계마다 사람이 읽는 제목("배민 쿠폰함")과 설명("마이배민에서 쿠폰함으로 들어가 보유 쿠폰 전부")을 스크립트 이름 옆에 보여 준다.
- 지난 실행은 세 곳에서 본다. 대시보드의 "최근 실행" 목록, 단계별 로그 링크, `/ops/logs/`의 날짜별 통합 로그 원문.
- 슬랙 봇은 매니페스트로 5분 안에 만든다. 절차는 tracker `docs/setup/SLACK-SETUP.md`. 봇은 메시지와 스크린샷을 보내기만 하므로 권한은 `chat:write`와 `files:write`만 주고 읽기 권한은 주지 않는다.

## 6. 결과 (첫 실전, 2026-09-17 15:55 예약 실행)

- 수집 PC 옆에 없어도 실행 진행이 보였다. 배민 쿠폰함 단계의 재시도까지 대시보드에 나타났다. 슬랙 연결은 16:29에 확인했다.
- 실행이 끝난 뒤 `ops.py`가 큐를 비우며 기다리는 상한 20초를 ssh 왕복 대여섯 번(손으로 재보니 한 번에 1초에서 3초)이 넘겨 `runs/` 보관 파일이 빠졌다. 상한을 90초로 늘리고 원격 디렉터리 생성 명령은 한 번만 보내도록 캐시했다.
- 테스트 하네스가 실제 슬랙 싱크와 실제 화면 가드(폰 화면을 4초마다 검사해 재난문자 같은 남의 창을 닫는 스레드)를 띄워 서버의 `state.json`을 덮고 폰에 adb 명령을 보냈다. 하네스가 가짜 싱크와 가짜 가드를 끼우도록 고쳤다.

## 7. 학습

- 상태 파일 하나를 모든 소비자가 읽게 하면(5절) 알림 범위 전환이 설정값 하나로 끝난다.
- 테스트가 실제 서버와 폰을 건드리지 않게 하는 장치는 첫 커밋에 넣어야 한다.
- 사람이 돌리기로 한 검사는 돌리지 않는다. `docs/HARNESS.md` 11절 점검표에 있던 구조 문서 검사가 그랬고, mono 저장소의 pre-push 훅으로 강제했다. 관측도 같다. 사람이 보러 가는 구조가 아니라 상태가 사람에게 오는 구조여야 한다.

## 8. 다음 단계 (2단계, 승인됨)

서버가 5분마다 cron으로 자기 상태를 `/var/www/ops/server/*.json`에 쓴다. API 코드는 바꾸지 않는다. IP와 User-Agent 원문은 저장하지 않고 집계만 한다.

| 우선순위 | 탭 | 원천 | 보여 줄 것 |
|---|---|---|---|
| 1 | API | `journalctl -u delivery-discount-api` | 최근 ERROR와 WARN 줄, 마지막 재시작 시각, export.json 로드 건수와 시각, reload 시각 |
| 1 | 데이터 | `data/export.json`, `banners.yml`, `events.jsonl` | 오퍼 수, 가장 최근 capturedAt, 노출 중인 배너와 종료일과 매진 여부, 오늘 이벤트 수와 클릭 수 |
| 1 | 서버 | `df`, `free`, `uptime`, 인증서 만료일 | 디스크, 메모리, 업타임, certbot 만료일 |
| 2 | 웹 트래픽 | `/var/log/nginx/access.log` | 시간대별 요청 수, 상태 코드 분포(2xx, 3xx, 4xx, 5xx, 429), 상위 경로, 봇 비율 |
| 3 | 배포 | GitHub Actions | 최근 워크플로 결론과 시각과 커밋. 실패는 슬랙 채널로도 보낸다(워크플로에 알림 스텝 추가) |

보완할 점: 알림 채널이 슬랙 하나라서 채널이 죽으면 조용해진다. 대시보드 상단에 "마지막 수집 시각"을 두고 12시간을 넘기면 빨간 띠를 띄운다. 예약 실행 간격이 최대 11시간(00:01에서 10:55)이라 12시간이면 한 회 빠진 것을 잡고 정상 간격에는 울리지 않는다. 2단계에 포함한다.

## 9. 하지 않는 것

- 로그 원문을 공개 경로에 두지 않는다. Basic Auth 아래에만 둔다. IP와 User-Agent 원문은 대시보드에도 올리지 않는다.
- 대안 B(수집 PC 접속)와 C(관측 SaaS)는 4절의 판단대로 보류와 기각이다. 팀과 트래픽이 지금의 10배가 되면 C를 다시 본다.
