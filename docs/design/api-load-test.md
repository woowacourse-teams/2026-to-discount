# Design: API 부하 테스트와 병목 1건 개선

상태: 2026-10-14 사용자 승인. 개선 전 3회 측정 완료, 개선 후 측정 보류.
작성일: 2026-10-14.
실행 결과: [설계와 개선 전 측정 보고서](../metrics/API-LOAD-TEST-20261014.md).

## 1. 문제와 목표

현재 운영 요청량에서 여유를 둔 부하를 개발 API에 가하고 성능 저하의 원인을 측정한다.
측정으로 확인한 병목 1건을 개선하고 동일 조건의 전후 결과를 비교한다.
개선된 동작은 CI 자동 테스트로 회귀 검증한다.
운영과 개발의 서버 사양 차이가 크므로 핵심 판단은 동일 개발 환경의 개선 전후 효과다.
개발 서버의 최대 처리량을 운영의 처리 능력으로 환산하거나 운영 성능 보장으로 사용하지 않는다.

## 2. 근거와 범위

운영 전용 Nginx 접근 로그의 최근 7일을 집계했다. 최초 관측 시각은
2026-10-07 17:43:21 KST다. API 경로의 모든 상태 코드와 OPTIONS를 포함한다.

| 관측 항목 | 결과 |
|---|---:|
| API 요청 수 | 35,496 |
| 최대 1분 요청 수 | 93, 약 1.55 RPS |
| 최대 1초 요청 수 | 30 |
| POST /api/events 200 | 15,016 |
| GET /api/brands 200 | 6,629 |
| GET /api/banners 200 | 6,281 |
| GET /api/survey 200 | 3,283 |

홍보 및 출시로 인한 추가 유입 계획은 없다. 순간 30건의 지속 시간과 유입 주체는
확인하지 않았으므로 30 RPS를 실제 지속 트래픽이라고 주장하지 않는다.

첫 실험의 범위는 홈 진입에 사용하는 `GET /api/brands`, `GET /api/banners`다.
두 경로의 정상 응답 비율이 비슷하고 웹이 두 경로를 조회하므로 50:50으로 구성한다.
각 iteration은 GET 한 건을 보내며 RPS는 두 경로를 합한 요청 수다.

이벤트 저장, 설문, 알림, reload 및 관리 요청은 부하 대상에서 제외한다.
이벤트 기록 오염이나 외부 전송을 피하며 결과는 조회 API의 처리 능력으로 한정한다.
운영 부하, 웹 렌더링 성능, 전체 사용자 여정의 처리 한계는 이번 범위에 포함하지 않는다.

## 3. 고려한 대안과 선택

| 대안 | 장점 | 한계 |
|---|---|---|
| k6 요청 도착률 기반 실험 | 응답이 느려져도 목표 요청량을 유지하고 미발행 요청 확인 가능 | 생성기 자원과 VU 상한 관리 필요 |
| 고정 동시 사용자 실험 | 실제 동시 실행 흐름 구성에 간단 | 서버가 느려지면 발행 요청량도 줄어 포화를 가릴 수 있음 |
| 단일 메서드 벤치마크 | 코드 구간 비교가 빠름 | HTTPS, Nginx, 직렬화와 서버 포화를 반영하지 못함 |

선택: k6의 constant-arrival-rate로 개발 HTTPS API를 측정한다.
Grafana에서 서버 내부 상태를 대조하고 필요한 코드 구간은 후속 프로파일링으로 좁힌다.
테스트 전 코드를 읽는 것만으로 개선 대상을 확정하지 않는다.

## 4. 제안 목표

| 항목 | 기준 |
|---|---|
| 예상 지속 부하 | 합계 10 RPS, 관측 최대 분당 요청의 약 6.5배 |
| 여유 검증 부하 | 합계 30 RPS를 지속적으로 발생시켜 순간 유입이 이어지는 상황 검증 |
| 정상 응답 | 각 경로 HTTP 200 및 기대 JSON 구조 |
| 응답 시간 | 각 경로 k6 전체 요청 시간 p95 ≤ 300ms, p99 ≤ 1,000ms |
| 실패율 | 각 경로 비정상 상태, 네트워크 실패 및 타임아웃 합계 < 0.1% |
| 생성기 | dropped_iterations=0, 목표 요청량 발행 성공 |

수치는 기존 보장값이 아닌 이번 실험의 승인 대상 목표다.
절대 지연 목표 충족 여부는 보조 결과로 보고한다. 태스크의 핵심 성과는
병목의 원인 확인, 동일 부하에서의 개선 효과와 정확성 유지다.
타임아웃은 5초로 고정하고 실패 요청도 성능 보고에서 제외하지 않는다.
정확한 합격 판정은 k6 결과를 사용한다. Grafana p95/p99는 고정 버킷의 추정값이다.
데이터 없는 구간이나 요청 없는 구간은 0ms 또는 오류율 0으로 해석하지 않는다.

운영에서 관측한 최대 초당 요청 수는 30건이다. 테스트에서는 30 RPS를 지속적으로 발생시켜 순간 유입이 이어지는 상황을 검증한다. 전체 API에서 관측한 피크를 두 조회 API에 집중시키는 실험이며 전체 서비스의 실제 이용 비율을 재현한 부하는 아니다.

### 목표 수치의 선택 이유

아래 값은 기존 서비스 보장이나 실측 결과가 아닌 실험 기준이다. 기준 측정 후 조정이 필요하면 이유를 기록하고 개선 전후 모두 같은 기준을 적용한다.

| 결정 | 선택 이유 |
|---|---|
| 10 RPS | 관측 최대 분당 요청량 1.55 RPS에 약 6.5배 여유를 둔 반올림 값이다. 추가 홍보 계획이 없는 현재 규모에서 평상시보다 높은 지속 부하를 만든다. |
| 30 RPS | 관측한 1초 최대 요청량을 지속시켜 순간 유입이 이어지는 조건의 개선 효과를 비교한다. 실제 지속 트래픽의 추정값은 아니다. |
| p95 300ms | 홈의 두 조회가 대부분 수백 ms 안에 끝나도록 정한 초기 지연 예산이다. 사용자 조사나 기존 SLO에서 도출한 값은 아니다. 이를 넘더라도 상대 개선율과 원인을 함께 보고한다. |
| p99 1초 | p95만으로 보이지 않는 느린 일부 요청을 확인하는 보조 기준이다. 작은 개발 서버의 간헐적 지연과 지속 포화를 구분할 시작값이며 운영 보장으로 사용하지 않는다. |
| 실패율 0.1% 미만 | 요청 실패로 응답 시간을 낮추는 개선을 막는다. 30 RPS로 5분 실행하면 경로별 약 4,500건이며 실패 5건부터 기준을 넘는다. 실패 수와 비율을 함께 보고한다. |
| 타임아웃 5초 | p99 목표보다 길게 두어 느린 요청을 관측하면서 무한 대기와 VU 점유를 제한한다. 타임아웃은 실패로 집계한다. |

전체 지연은 요청 호출 직전부터 완료까지 별도 k6 Trend로 기록한다.
`http_req_duration`에는 연결과 TLS 대기가 포함되지 않으므로 전체 지연으로 부르지 않는다.
전체 지연, HTTP 처리 시간, 연결 및 TLS 시간을 함께 보존한다.

## 5. 환경과 재현 조건

- 대상: `https://dev-api-todiscount.duckdns.org`. 운영 주소는 실행 스크립트에서 거부한다.
- 생성기는 API 서버와 분리한다. 동일 생성기, 지역, k6 버전과 네트워크 경로를 전후에 유지한다.
- 생성기 위치와 자원은 실행 전 확정하고 기록한다. 생성기가 포화되면 서버 결과로 해석하지 않는다.
- dev의 코드 SHA, JAR, JVM 옵션, CPU 및 메모리 제한, Nginx 설정을 기록한다.
- 오퍼, 브랜드, 배너 및 이력 파일의 해시와 건수를 고정한다. 전후 같은 영업 날짜 조건을 유지한다.
- 비교 중 자동 배포와 데이터 동기화 및 reload가 일어나지 않는 시간대를 확보한다.
- 같은 캐시 조건으로 워밍업한다. 캐시 개선을 선택하면 만료와 reload 후 갱신도 별도 검증한다.
- 외부 모니터 등 배경 요청은 기록하고 k6 요청을 User-Agent로 구분한다. 요청별 ID를 지표 라벨에 추가하지 않는다.
- 실행 시작과 종료 UTC 시각, run ID와 중단 이유를 남긴다.

## 6. 실행 절차

1. API 200, 지표 `up=1`, 서버 자원, 데이터 해시 및 생성기 상태를 사전 확인한다.
2. 2 RPS로 2분 워밍업한다. 비교 통계에서는 제외한다.
3. 탐색: 2, 10, 30 RPS를 각 3분 실행한다. 단계 사이 2분 회복한다.
4. 30 RPS에서 목표를 충족하면 60, 100 RPS를 각 3분까지 추가 탐색한다. 중단 조건을 우선한다.
5. 성능 저하가 관측된 단계와 목표 30 RPS에서 정상 구간 및 저하 구간을 비교한다.
6. 개선 전 30 RPS를 5분씩 3회 측정한다. 매회 동일 워밍업 및 회복 조건을 사용한다.
7. 병목을 확인한 뒤 개선 1건을 구현하고 CI 회귀 검증한다.
8. 같은 30 RPS 조건으로 5분씩 3회 재측정한다. 병목 단계가 다르면 해당 단계도 동일하게 반복한다.
9. 원시 결과, 경로별 통계와 Grafana 시간 범위를 함께 보존한다.

30 RPS 비교의 VU 상한은 200, 60 RPS 탐색은 400, 100 RPS 탐색은 600으로 제안한다.
dropped_iterations가 있으면 생성기와 VU 여유를 먼저 확인한다. 제한을 바꾸면 개선 전
측정도 같은 제한으로 다시 수행한다.
100 RPS까지 병목이 확인되지 않으면 병목 발견 완료로 처리하지 않는다.
측정 결과를 보고 추가 부하 또는 데이터 규모 확대의 범위를 다시 합의한다.

### 실행 조건의 선택 이유

| 결정 | 선택 이유와 한계 |
|---|---|
| 2 RPS, 2분 워밍업 | 약 240건으로 JVM 초기 실행과 연결 준비의 영향을 줄인다. 자원과 지연이 안정되지 않으면 시간을 늘리고 전후 같은 워밍업을 적용한다. 2분만으로 충분한 JIT 안정화를 보장하지 않는다. |
| 탐색 단계 3분 | Alloy의 15초 수집 기준 약 12개 시점으로 변화 추이를 확인하면서 과부하에 오래 노출하지 않는다. 장시간 안정성의 증거로 사용하지 않는다. |
| 단계 사이 2분 회복 | 약 8개 수집 시점으로 이전 부하의 영향을 확인한다. 자원과 지연이 회복되지 않으면 다음 단계를 시작하지 않는다. |
| 60, 100 RPS 탐색 | 30 RPS의 약 2배와 3.3배로 단계적으로 부하를 늘린다. 100 RPS는 초기 실험 범위를 제한하는 상한이며 운영 요구량이나 서버 최대 처리량으로 정한 값이 아니다. |
| 5분 비교 | 30 RPS에서 약 9,000건, 경로별 약 4,500건과 약 20개 수집 시점을 확보한다. 경로별 상위 1%는 약 45건으로 짧은 탐색보다 꼬리 지연 비교에 유리하다. p99의 통계적 신뢰성을 보장하는 표본 수라는 뜻은 아니다. |
| 반복 3회 | 단일 실행의 우연한 영향을 줄이고 중앙값과 범위를 비교할 최소 반복 수다. 편차가 개선 폭과 비슷하면 반복을 늘리며 유리한 실행만 선택하지 않는다. |
| VU 상한 200/400/600 | 요청 한 건의 iteration 점유 시간을 타임아웃 5초로 가정하면 30/60/100 RPS에 평균 약 150/300/500개의 동시 실행이 필요하다. 약 20~33% 여유를 둔다. JSON 검사와 스케줄링 비용으로 더 필요할 수 있으므로 저부하에서 생성기 자원과 실제 점유 시간을 확인한다. |

## 7. 중단과 회복

- 최근 30초 실패율이 1% 이상이고 실패가 5건 이상이면 중단한다.
- 최근 30초 p99가 3초를 넘는 상태가 2개 구간 연속 관측되면 중단한다.
- 가용 메모리 10% 미만이 30초 지속되거나 OOM 또는 서비스 재시작이 발생하면 즉시 중단한다.
- CPU 95% 이상과 p99 3초 초과가 60초 지속되면 중단한다.
- 생성기 dropped_iterations 발생 시 해당 구간을 무효로 하고 원인을 확인한다.

### 중단 기준의 선택 이유

- 실패율 1%는 목표의 10배로, 개선 관측보다 서비스 회복을 우선할 수준으로 정했다. 5건 이상 조건은 낮은 요청량에서 실패 한 건만으로 중단되는 것을 줄인다.
- p99 3초는 목표 1초의 3배이며 타임아웃 5초에 가까워지기 전 중단하기 위한 값이다. 30초 구간 2회로 일시적인 지연과 지속적인 악화를 구분한다.
- 메모리 10%는 고갈 전에 중단할 초기 여유 기준이다. 30초는 Alloy 수집 약 2회에 해당한다. OOM 또는 재시작은 지속 시간과 관계없이 즉시 중단한다.
- CPU 95%만으로는 병목 관측을 막지 않는다. p99 악화가 함께 60초 지속될 때 중단해 자원 포화와 실제 응답 악화를 연결한다.
- dropped_iterations는 요청량이 목표보다 낮아졌다는 뜻이므로 해당 구간을 유효한 전후 비교로 사용하지 않는다. VU 부족과 생성기 포화를 먼저 구분한다.

위 기준은 운영 SLO가 아니라 개발 실험의 중단 기준이다. 사전 저부하 점검에서 감시 지연과 중지 동작을 확인한다.

실패율 조건은 30초 집계 감시로 구현한다. k6의 전체 실행 누적 threshold는 최근 30초 조건을 대신하지 못한다.
서버 자원 조건은 별도 감시로 실행 프로세스를 중지한다. 실행 전에 중단 경로를 저부하로 검증한다.
중단 후 요청 발행을 멈추고 API 200, 자원 회복, 서비스 상태를 확인한다.
알림 수신 여부는 기록하되 알림을 임의로 비활성화하지 않는다.

## 8. 병목 판단과 개선 선택

| 관측 | 확인할 원인 |
|---|---|
| CPU와 brands 처리 시간 동반 증가 | 요청마다 비교, 정렬, 객체 생성 및 직렬화 비용 |
| GC 정지와 메모리 증가 | 할당량, 객체 생존 및 반복 생성 |
| Tomcat 사용 중 스레드 포화 | 처리 지연, 잠금, 대기 구간 |
| k6 지연만 증가하고 API 지연은 안정 | 생성기, 네트워크, TLS 또는 Nginx |
| 디스크 I/O 또는 네트워크 증가 | 로그 기록 또는 응답 크기 |

BrandComparisonService.compare()는 요청마다 비교를 수행하므로 후보로 조사한다.
CPU 연관성이 확인되지 않으면 캐시를 선제적으로 추가하지 않는다.
진단은 엔드포인트별 RPS, p95/p99와 CPU, JVM, GC, Tomcat, I/O를 같은 시간 구간에서 비교한다.
필요하면 제한된 시간의 JFR 또는 구간 측정을 추가한다. 수집 비용도 기록한다.

병목 1건은 반복 실험과 코드 또는 프로파일 증거로 처리 비용의 위치를 설명할 수 있어야 한다.
외부 네트워크가 병목이면 API 코드 개선으로 꾸미지 않고 재현 환경부터 조정한다.

## 9. 전후 비교와 CI

- 경로별 실제 발행량, 완료량, 실패 수, dropped_iterations, p50/p95/p99를 표로 비교한다.
- 같은 조건 3회 결과의 중앙값과 범위를 제시한다. 성공한 실행만 골라 보고하지 않는다.
- CPU, 최대 heap, GC 누적 정지와 스레드 사용도 함께 비교한다.
- 제안 개선 목표: 병목 경로의 p95 중앙값 20% 이상 감소 또는 같은 조건의 실패 제거와 목표 충족.
- 다른 경로의 p95 10% 초과 악화, 응답 내용 변경 또는 실패율 증가가 없어야 한다.
- 측정 오차나 run 간 변동으로 개선을 설명할 수 없으면 추가 비교 후 결론을 내린다.
- CI에는 개선의 정확성을 검증하는 단위 또는 통합 테스트를 추가한다. 환경 의존적인 벽시계 성능 수치를 일반 CI 합격 조건으로 쓰지 않는다.
- 기존 API 테스트 및 빌드를 유지한다. 부하 스크립트는 명시적 수동 실행으로 분리한다.

### 개선 판정 기준의 선택 이유

p95 20% 감소는 측정 잡음 수준의 작은 차이로 개선을 선언하지 않기 위한 초기 목표다.
관측에서 도출한 보편적 기준은 아니므로 실행 간 변동과 함께 판단한다.
목표를 만족하는 실패 제거도 가치가 있으므로 지연 감소 외의 개선 경로로 인정한다.
다른 경로의 p95 악화 10%는 한 경로 개선의 비용이 다른 경로로 전가되는지 확인할 초기 기준이다.
10% 이내라도 응답 정확성 또는 실패율이 악화되면 수용하지 않는다.
개선 폭과 실행 간 변동이 겹치면 추가 반복하며, 위 기준을 사후에 낮춰 완료로 만들지 않는다.
