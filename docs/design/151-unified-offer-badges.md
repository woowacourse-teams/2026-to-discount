# 151. 카드와 상세의 배지를 한 목록에서 뽑기

추적 이슈: [#151](https://github.com/woowacourse-teams/2026-to-discount/issues/151)

## 결론

오퍼 하나의 칩 목록을 `couponModel.js`의 함수 하나(`chipsOf`)가 만들고, 카드와 상세는 그 목록에서 뽑아 그린다. 칩마다 어디에 뜨는지는 표 하나(아래 "표시 위치 표")가 정하고, 테스트가 그 표를 따른다.

- `badgesOf`(오퍼 단위)와 `conditionTable`의 칩(구간 단위)을 `chipsOf`가 합친다. `badgesOf`는 그대로 둔다. 운영 칩(`OfferChip.jsx`)이 쓰고 `offerChip.test.js`가 HTML 불변을 지키고 있어서다.
- 멤버십 상속 규칙은 함수 하나(`membershipOf(offer, tier)`)로 모은다. 카드와 상세가 같은 함수를 부른다.
- "첫 주문"처럼 구조화할 수 있는 조건은 `qualifiers`(문자열 배열) 필드로 내려준다. 내보내기, API, 웹 세 영역으로 나누고 순서는 내보내기 → API → 웹이다.
- 카드에 "첫 주문"을 띄울지, 상세 줄에 "중복 할인"을 띄울지는 사용자 결정이다. 이 문서는 기본안을 정해 두고 "열린 질문"에 올린다. 기본안으로 구현을 시작하지 않고 답을 받은 뒤 시작한다.

## 배경

이슈가 짚은 원인을 코드에서 다시 확인했다.

- 카드: `CouponCard.jsx:100`의 `Tags`가 `badgesOf(o)`(`couponModel.js:55`)를 부른다. 오퍼 단위 필드(`qualifier`, `badge`, `membership`)만 본다. `conditions`는 보지 않는다.
- 상세: `conditionTable`(`couponModel.js:91`)이 구간 단위 칩(`channel`, 멤버십, 구간 `note`, 구간 기한)만 만든다. 오퍼의 `conditions`는 줄 아래 문장(`note`)으로만 나온다(121행).
- 멤버십 상속이 둘이다. 카드는 `membership`을 오퍼 값으로 본다(`badgesOf` 63행). 상세는 구간 하나라도 멤버십을 밝히면 나머지 구간이 오퍼 값을 안 물려받는다(`tierSays`, 97행).
- API는 `conditions` 문자열 하나만 내려준다. `Offer` 레코드(`api/.../offer/Offer.java:19`)와 `OfferRecord`에 `qualifiers` 칸이 없다. "첫 주문"을 칩으로 만들 구조화 값이 웹에 오지 않는다.

**확인하지 못한 것:** 화면(360px)과 2026-10-22 `export.json`은 이 세션에서 보지 못했다. 저장소의 `api/src/main/resources/data/export.json`은 테스트 스냅샷이라 CU, 푸라닭의 운영 행과 같다고 볼 수 없다. 사례(CU 첫 주문, 푸라닭 중복 할인과 와우)는 이슈 본문을 믿는다. 구현자가 고정 데이터로 현재 동작을 먼저 재현한다(아래 "테스트").

### 어긋남의 종류

| 어긋남 | 원인 | 이 설계의 해결 |
|---|---|---|
| CU 카드에 "첫 주문" 칩 없음, 상세엔 문장 | `conditions`가 문자열이라 `badgesOf`가 못 읽음 | `qualifiers`로 구조화하고 `chipsOf`가 칩으로 만듦 |
| 푸라닭 상세 줄에 "중복 할인" 없음 | 줄 칩은 구간 필드만 읽음 | 표시 위치 표로 줄 칩 여부를 명시하고 테스트로 박음 |
| 멤버십 상속이 카드와 상세에서 다름 | 규칙이 두 함수에 따로 있음 | `membershipOf` 하나 |
| "운영 OfferChip, OfferDetail과 같다" 주석 | 규칙 복제 | 아래 "운영 콘솔" |

## 변경

### 웹: `web/src/couponModel.js`

`chipsOf(offer)`를 더한다. 반환은 칩 배열이고 칩은 `{ kind, text, scope, tier? , platform? }`이다.

- `scope: 'offer'`: 오퍼 전체의 칩. `badgesOf(offer)` 결과(불확정, 랜덤, 특정메뉴, 중복 할인, 정률, 멤버십, 한정)에 `qualifiers`에서 만든 `kind: 'condition'` 칩(예: "첫 주문")을 더한다.
- `scope: 'tier'`: 구간의 칩(`channel`, `note`, `until`, 구간이 말한 멤버십). `conditionTable`의 `rowOf`가 지금 만드는 칩과 같다.
- `placement`: 표시 위치 표를 상수 `CHIP_PLACEMENT = { [kind]: { card, detail } }` 하나로 둔다. 값은 `'head'`(카드 머리 줄이나 오퍼 머리), `'row'`(상세 표 줄), `false`다. 카드는 `card`가 있는 칩, 상세는 `detail`이 있는 칩을 그린다.
- 카드의 `Tags`는 `chipsOf(o).filter(card)`, 상세의 오퍼 머리와 표 줄은 `chipsOf(o).filter(detail)`로 바꾼다. 어느 칩도 두 호출에서 따로 계산하지 않는다.

`membershipOf(offer, tier)`를 더하고 `badgesOf`, `conditionTable`이 둘 다 부른다.

- 구간이 멤버십을 말하면 그 값.
- 아니고 오퍼의 구간 중 하나라도 말하면 `null`. 상시 구간의 멤버십이 선착순 구간에 붙은 일의 되풀이를 막는다(2026-10-16, PR #85 주석).
- 아니면 오퍼 값(`membership` 필드, 없는 옛 행은 `badge` 끝말 "전용쿠폰").
- 카드의 멤버십 칩은 대표 구간(`tier.amount === offer.amount`)의 `membershipOf`로 정한다. 구간이 없으면 오퍼 값이다. 구간 일부만 멤버십을 말하는 오퍼에서 카드 칩이 대표 금액의 자격과 맞게 된다. 지금은 오퍼 값을 그대로 붙여 대표가 비멤버 구간인데도 칩이 뜰 수 있다.

`conditionTable`의 `note`(121행)는 `qualifiers`에서 칩으로 올린 문구와 같은 문장이면 뺀다. 칩과 문장이 같은 말을 되풀이하지 않게 한다.

### 웹: `web/src/CouponCard.jsx`

`Tags`(97행)와 `conditionTable`을 쓰는 세 자리(386, 458, 495행)를 `chipsOf`로 바꾼다. 시트(495행)와 펼친 목록(458행)의 오퍼 머리 `Tags`는 카드와 같은 함수 결과를 쓴다. `DetailTable`의 줄 칩 모양(`kind`별 CSS)은 바꾸지 않는다.

### 웹: 과도기 대비(옛 API 응답)

API가 `qualifiers`를 아직 안 보낼 때도 웹이 깨지면 안 된다(배포 순서 8번의 되풀이 방지).

- `qualifiers`가 없거나 비면 `conditions`가 알려진 한 토큰("첫 주문")과 **정확히 같을 때만** 그 토큰을 `qualifiers`로 본다. 부분 문자열 검색은 하지 않는다("첫 주문만 가능" 같은 문장을 칩으로 오독하지 않으려고).
- 이 대체 경로는 내보내기가 `qualifiers`를 싣기 시작한 뒤 걷어낸다(후속 조치).

### API: `OfferRecord`, `Offer`

- `OfferRecord`에 `List<String> qualifiers`를 더한다. 키가 없는 옛 `export.json`을 읽어야 하므로 nullable이다. Jackson 3의 파싱 오류는 `IOException`이 아니다(`api/docs/decisions/ADR-012`). 구현자가 ADR-012를 읽고 키 없음, `null`, 빈 배열 세 경우를 `OfferRecord` 읽기 테스트로 박는다. 칸이 21개라 빌더(`OfferRecord.builder`)에도 더한다.
- `Offer`에 같은 이름으로 싣는다. 해석하지 않고 넘긴다(ADR-003: 판단은 화면 몫). `null`은 빈 목록이 아니라 `null` 그대로 내려가 "모름"을 구분한다.
- 같은 (브랜드, 앱) 중복을 합칠 때(`Offer.java:162` 근처의 `mergedConditions`) `qualifiers`도 `conditions`처럼 승자가 값을 가지면 승자 것, 없으면 패자 것으로 잇는다(ADR-006). 빠뜨리면 합쳐진 오퍼에서 "첫 주문" 칩만 조용히 사라진다.
- 배너에서 세운 오퍼(`BannerOffers`)는 `qualifiers`를 비운다. 배너에는 그 칸이 없다.

### 내보내기: tracker `export_data.py` (비공개 저장소, 이 PR 범위 밖)

- 원장의 `qualifiers`(예: `["첫 주문"]`)를 export 오퍼 행에 그대로 싣는다. 키는 `qualifiers`, 값은 문자열 배열이다.
- `conditions`는 이번에 바꾸지 않는다. 같은 말이 `conditions`에도 남지만 웹이 위 규칙으로 중복을 뺀다. `conditions`에서 "첫 주문"을 걷어내는 것은 웹이 `qualifiers`를 읽는 것이 운영에서 확인된 뒤 다른 변경으로 한다.
- 이 변경은 tracker 저장소 이슈로 따로 만든다(후속 조치). mono 설계 세션은 tracker 코드를 싣지 않는다(ADR-002).

### 하지 않는 것

- `badgesOf`의 반환과 옵션(`showBestFit`, `shortTime`) 변경. 운영 칩 HTML이 바뀌면 안 된다.
- 새 칩 문구. "첫 주문"은 기존 `conditions` 문자열에 이미 있는 말이다. 새 문구가 생기면 `docs/COPY-STYLE.md`와 개발자 확인이 먼저다(CHANGE-PROPAGATION 6번).
- 계산식(`formulaOf`) 표시 위치 변경. "계산식은 배지 아래에 이미 있으니 표에 넣지 않는다"는 의도를 유지한다.

## 표시 위치 표

기본안이다. 굵은 글씨는 사용자 결정이 필요한 칸이다. 결정 전까지 "기본안"으로 읽는다.

| 칩 (`kind`) | 단위 | 카드 머리 | 상세 오퍼 머리(시트, 펼친 목록) | 상세 표 줄 |
|---|---|---|---|---|
| 불확정, 특정메뉴 (`qualifier-plain`) | 오퍼 | 표시 | 표시 | 안 함 |
| 랜덤 (`qualifier-random`) | 오퍼 | 표시 | 표시 | 안 함 |
| 중복 할인 (`best-fit`) | 오퍼 | 표시 | 표시 | **안 함(기본안)** |
| 정률 (`rate`) | 오퍼 | 표시 | 표시 | 안 함(줄은 `extra`에 `n%`가 있다) |
| 멤버십 (`membership`) | 오퍼, 구간 | 표시(대표 구간 기준) | 표시 | 구간이 말할 때 표시 |
| 한정, 열림 시각 (`limited`) | 오퍼 | 표시 | 표시 | 안 함(구간 시각은 `note` 칩) |
| **첫 주문 (`condition`)** | 오퍼 | **표시(기본안)** | 표시 | 안 함 |
| 채널 (`channel`) | 구간 | 대표 구간의 채널만(`channelOf`) | 안 함 | 표시 |
| 구간 메모 (`note`) | 구간 | 안 함 | 안 함 | 표시 |
| 구간 기한 (`until`) | 구간 | 안 함 | 안 함 | 표시(오퍼 기한과 다를 때) |

읽는 법

- "같은 목록에서"의 뜻: 카드 머리에 뜨는 칩은 모두 상세 오퍼 머리에도 뜬다(카드 ⊆ 상세). 카드에만 있고 상세에 없는 칩이 없다. 지금은 `conditions` 문장 때문에 CU에서 어긋난다.
- 오퍼 단위 칩이 표 줄에 안 뜨는 것은 의도다. 줄은 구간의 차이만 보이고 오퍼 전체의 성격은 오퍼 머리가 말한다. 같은 칩을 줄마다 반복하면 360px에서 좁은 칸이 넘친다.
- 표의 정본은 이 문서가 아니라 `CHIP_PLACEMENT`이다. 이 문서의 표와 값이 같음을 테스트가 맞댄다.

## 운영 콘솔

코드 주석이 "운영 OfferChip, OfferDetail과 같다"고 적은 자리는 둘이다(`CouponCard.jsx:22`, `couponModel.js:93`).

- 이 저장소 `web/src/OfferChip.jsx`는 `badgesOf`를 그대로 쓴다. `chipsOf`를 얹어도 `badgesOf`가 안 바뀌므로 이 칩은 영향이 없다. `offerChip.test.js`가 이를 지킨다.
- beggars-ops 콘솔(`web/`)의 `OfferChip`, `OfferDetail`은 다른 저장소라 이 세션에서 읽지 못했다. **같은 규칙을 따로 구현했는지 확인되지 않았다.** 이 변경으로 `membershipOf`(대표 구간 기준)와 `qualifiers` 칩이 생기므로 콘솔이 옛 규칙을 따르면 어긋난다.
- 이번 PR에서 콘솔을 고치지 않는다. 콘솔 쪽 확인과 맞춤은 후속 이슈로 둔다. 주석 두 줄은 "같다" 대신 "`chipsOf`를 따른다, 콘솔은 #후속 이슈"로 고친다. 주석이 거짓이 되는 것을 막으려는 것이다.

## 변경 전파 확인

`docs/CHANGE-PROPAGATION.md`의 묶음 중 닿는 곳을 짚는다.

- **배너 모양(2번):** 닿지 않는다. 배너 칸을 바꾸지 않는다. 다만 이 변경은 문서에 없는 묶음 하나를 만든다(아래).
- **화면에 나가는 글자(6번):** 닿는다. 새 문구는 없다. "첫 주문"이 칩 문구가 되므로 개발자가 이 문구를 칩에 써도 되는지 확인한다(열린 질문 1).
- **배포 순서(8번):** 닿는다. 내보내기 → API → 웹 순서다.
  - 내보내기가 먼저 `qualifiers`를 실어도 API가 모르는 키를 무시하는지 구현자가 확인한다(ADR-012). 무시하지 않으면 API가 먼저다.
  - API가 먼저 나가면 웹은 옛 방식(`conditions` 정확 일치)으로 돈다. 칩은 그대로다.
  - 웹이 먼저 나가는 일은 막는다. 먼저 나가도 대체 경로가 있어 깨지지 않지만, 칩이 `conditions` 정확 일치에만 의존한다.
  - 웹은 프리뷰 먼저다(`docs/WORKFLOW.md` §3-3).
- **새 묶음(문서에 없음):** 칩 목록 · 표시 위치 표 · 상세 표 줄이 같은 규칙을 읽어야 한다. 한쪽만 고치면 카드와 상세가 다시 어긋난다. `chipsOf`와 `CHIP_PLACEMENT`로 한 곳에 모으는 것이 이 묶음을 없애는 수단이다("묶음을 줄이는 법" 2번). 구현이 끝나면 CHANGE-PROPAGATION.md에 한 줄을 더할지 구현자가 정한다.

## 테스트

테스트 파일은 새로 만들지 않는다. 기존 `couponModel.test.js`와 API의 `OfferRecord` 읽기, 중복 합치기 테스트에 더한다(`web/package.json`의 `test` 변경 없음). 구현자는 새 테스트 이름이 출력에 나오는지 본다.

고정 데이터는 합성 픽스처다(ADR-009). 운영 스냅샷을 복사하지 않는다. 형태만 이슈의 CU, 푸라닭과 같게 만든다.

- **푸라닭:** 같은 브랜드의 앱 3개.
  - 요기요: `qualifier: '최적'`, `conditions`에 식(`+`, `=` 포함), 금액 6,000.
  - 쿠팡이츠: `membership: 'coupangEats'`, 금액 7,000.
  - 땡겨요: 금액 5,000.
- **CU:** 쿠팡이츠 7,000, `conditions: '첫 주문'`. 한 벌은 `qualifiers: ['첫 주문']`이 있고 한 벌은 없다(옛 응답).

테스트 목록

1. **재현(고치기 전에 실패해야 한다):** CU 픽스처에서 카드 칩에 "첫 주문"이 없고 상세 `note`에 있음을 현재 코드로 확인한다. 푸라닭 요기요에서 상세 표에 "중복 할인"이 없음을 확인한다. 재현이 안 되면 원인을 잘못 짚은 것이니 멈추고 이슈에 적는다.
2. **같은 목록:** 두 픽스처에서 `chipsOf(offer).filter(card)`의 모든 칩이 `chipsOf(offer).filter(detail)`에 들어 있다.
3. **표를 따름:** `CHIP_PLACEMENT`가 이 문서의 표와 같은 값임을 테스트 안의 표 리터럴과 맞댄다. 표를 바꾸면 테스트가 깬다. 표의 모든 `kind`가 `CHIP_PLACEMENT`에 있는지(빠진 칩 없음)도 본다.
4. **중복 없음:** `qualifiers: ['첫 주문']`이면 상세 `note`에서 "첫 주문" 문장이 빠지고 칩 하나만 남는다. 옛 응답(`qualifiers` 없음, `conditions: '첫 주문'`)에서도 칩이 같다. `conditions: '첫 주문만 가능'`은 칩으로 올리지 않고 문장으로 남는다.
5. **멤버십 규칙:** 구간 일부만 멤버십을 밝히는 오퍼에서 대표 구간이 비멤버면 카드 칩이 없다. 대표 구간이 멤버면 있다. 구간이 없으면 오퍼 값을 따른다. 옛 행(`badge` 끝말 "전용쿠폰")도 같다. 기존 `tierSays` 테스트(`couponModel.test.js`의 멤버십 구간 케이스)는 그대로 통과해야 한다.
6. **불변:** `badgesOf` 기존 테스트와 `offerChip.test.js`가 변경 없이 통과한다.
7. **API:** `OfferRecord` 읽기에서 `qualifiers` 키 없음, `null`, `[]`, `["첫 주문"]`이 각각 의도대로 `Offer`까지 간다. 중복 합치기에서 패자의 `qualifiers`가 승자에 값이 없을 때 이어진다.
8. **360px 스크린샷(필수):** CU, 푸라닭을 카드, 펼친 목록, 시트 세 자리에서 찍는다. 카드 머리 줄에서 칩이 늘어 넘치거나 이름이 밀리지 않는지 본다. 푸라닭 요기요처럼 칩이 이미 둘인 오퍼에 "첫 주문"이 겹치는 경우를 합성 데이터로 한 장 더 찍는다.

## 열린 질문

1. **카드에 "첫 주문"을 띄울까?** 기본안은 띄운다. 첫 주문만 쓸 수 있는 쿠폰은 불확정, 특정메뉴처럼 누가 쓸 수 있는지의 조건이라 액면 금액만 보고 누르면 낭패다. 다만 카드 머리 줄은 넘치면 자른다(overflow hidden). 칩이 셋 넘을 때 무엇을 자를지(예: "첫 주문"을 먼저 남기고 한정 칩을 줄인다)도 함께 정해 달라. 개발자가 "첫 주문" 문구를 칩에 써도 되는지도 확인한다(COPY-STYLE).
2. **상세 표 줄에 "중복 할인"을 띄울까?** 기본안은 띄우지 않는다. 오퍼 머리에 이미 있고 계산식은 줄의 `extra`에 있다. 줄마다 반복하면 360px에서 좁다. 줄에도 필요하다면 알려 달라.
3. **카드 멤버십 칩을 대표 구간 기준으로 바꿔도 되나?** 기본안은 바꾼다. 대표 금액이 비멤버 구간인데 "쿠팡와우" 칩이 뜨는 오퍼가 지금 있을 수 있으나(데이터를 못 봤다) 있다면 칩이 사라져 보이는 변화가 생긴다. 이 변화를 원치 않으면 카드는 오퍼 값을 그대로 쓰고 상세만 `membershipOf`를 쓴다(규칙은 한 함수에 두되 카드가 구간을 안 넘긴다).
4. **beggars-ops 콘솔을 같이 맞출까?** 기본안은 이번에 안 맞추고 후속 이슈로 둔다. 같이 맞추려면 콘솔 저장소의 `OfferChip`, `OfferDetail`을 읽은 뒤 설계를 보탠다.
