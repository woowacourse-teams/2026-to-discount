# 215. 무중단 배포 쓰기 시험의 저장 수 대조와 188 문서 정정 (2026-10-30 작성)

2026-10-29 시험 2가 보낸 POST `/api/events` 450건이 서버 이벤트 원장에 몇 건 저장됐는지 세어 대조하고, 시험 표시 `dev=true`가 집계에서 빠지는지 확인한다. 그 결과와 설계 188의 틀린 문장 둘의 정정을 [설계 188](188-zero-downtime-deploy.md)에 채운다. 이 문서는 무엇을 어떻게 셀지, 무엇이 증거가 되고 무엇이 증거가 아닌지를 정한다. 숫자는 아직 없다.

## 먼저 풀어 둔 말

- 원장: 서버가 받은 방문 이벤트를 한 줄에 하나씩 이어 적는 파일(`events.jsonl`)이다. 서버 코드는 `EventLog.append`가 쓴다.
- 시험 이벤트: 시험 2가 보낸 POST 본문의 이벤트다. 이벤트 이름 `scroll_to_top`, 방문자 `zdd-probe`, 경로 `/zdd-probe`, `dev: true`.
- 대조: 보낸 수와 저장된 수를 나란히 놓고 차이를 구하는 일이다.

## 배경

200 응답은 받았다는 뜻이지 저장됐다는 뜻이 아니다. 코드에서 확인한 사실은 다음과 같다(`EventController.collect`).

- 본문이 비었거나 JSON으로 읽히지 않으면 `accepted: 0`으로 200을 준다. 저장은 0건이다.
- 허용 목록에 없는 이벤트 이름은 조용히 버린다. 그래도 200이다.
- IP별 분당 120건을 넘으면 429를 준다. 시험은 POST를 2초에 한 건 보냈으므로 분당 30건 안팎이라 걸리지 않는다.
- 시험 2의 CSV는 상태 코드만 남겼고 응답 본문의 `accepted` 값을 남기지 않았다. 450건의 200이 450건의 저장을 뜻하는지 CSV로는 알 수 없다.

두 인스턴스(본 인스턴스 8088, 임시 인스턴스 8089)가 함께 뜨는 구간은 두 프로세스가 같은 원장 파일에 이어 쓴다. `EventLog.append`의 `synchronized`는 프로세스 안에서만 줄을 지킨다. 이 구간에 원장에서 줄이 빠지거나 섞였는지가 이 시험의 핵심 증거다. 시험 2에서 임시 인스턴스가 POST를 받은 구간은 자동 복구 배포 단계(17:28:17~17:29:18)와 되돌림 배포 단계(17:31:15~17:31:46)다.

## 결정

### 1. 저장 수는 서버 원장에서 읽기 전용으로 센다

서버 읽기는 사용자가 허용했다(2026-10-30, 이슈 #215). 허용 범위는 읽기다. 명령은 파일을 열어 읽고 세기만 하며 쓰기, 이동, 삭제, 서비스 재시작을 하지 않는다.

세는 기준은 구조다. 문구가 아니라 필드로 건다.

- 대상: 방문자 `visitorId == "zdd-probe"`이고 경로 `path == "/zdd-probe"`인 줄.
- 서버가 적은 시각 `ts`(한국 시각 오프셋이 붙은 ISO 문자열)로 시험 구간을 나눈다. 시험 2는 2026-10-29 17:27~17:42 KST다. 클라이언트 시각 `clientTs`는 시험 PC 시계라 기준으로 쓰지 않는다.
- 세는 값 셋: 대상 줄 전체, 구간 안 줄, 구간 밖 줄. 구간 밖 줄이 있으면 시험 2 전의 연습 전송이거나 시험 외 전송이다. 합산에서 빼고 따로 적는다.
- 중복 확인: 같은 `eventId`가 둘 이상인 줄 수. 서버는 `eventId`를 클라이언트가 안 주면 UUID로 만들므로 시험 이벤트는 서로 다르다. 같은 값이 나오면 두 프로세스가 같은 줄을 두 번 쓴 것이다.
- 형식 확인: 대상 줄 중 JSON으로 읽히지 않는 줄 수. 두 프로세스가 같은 파일에 쓸 때 줄이 섞이면 여기서 보인다.

명령은 원장이 177MB(2026-10-14 기준)로 크므로 먼저 `grep -F`로 `zdd-probe`가 든 줄만 거르고 그 결과에만 `jq`를 쓴다. 명령 형태는 다음과 같다. 경로는 공개 저장소에 쓰지 않으므로 `<원장>`으로 둔다.

```bash
# 읽기 전용: grep과 jq는 파일을 바꾸지 않는다
ssh <서버> "grep -F zdd-probe <원장>" > zdd-probe.jsonl
jq -s 'map(select(.visitorId=="zdd-probe" and .path=="/zdd-probe")) | length' zdd-probe.jsonl
jq -s 'map(select(.visitorId=="zdd-probe" and .path=="/zdd-probe" and .ts >= "2026-10-29T17:27" and .ts < "2026-10-29T17:43")) | length' zdd-probe.jsonl
jq -s 'map(.eventId) | length - (unique | length)' zdd-probe.jsonl
```

- 줄을 로컬로 받아 세는 이유: 서버에서 도는 명령을 최소로 하고, 같은 파일로 세는 방법을 여럿 시험할 수 있어서다. 받는 줄은 시험 이벤트뿐이라 방문자 정보가 없다. 시험 PC의 IP 해시(`ipHash`)는 들어 있으므로 받은 파일은 저장소에 올리지 않는다.
- 시각 비교는 문자열 비교다. `ts`의 오프셋이 `+09:00`이 아니면 구간이 틀린다. 첫 줄의 `ts`를 눈으로 보고 오프셋을 확인한 뒤 구간을 잡는다.

### 2. "0건"과 "읽지 못함"을 구분한다

AGENTS.md의 첫 규칙을 따른다. 세어 보지 못한 것을 0으로 적지 않는다.

- 양성 신호: 같은 파일에서 시험 이벤트가 아닌 줄(방문자가 `zdd-probe`가 아닌 줄)이 시험 구간에 있는지 센다. 구간에 일반 사용자 줄이 있으면 파일을 제대로 읽은 것이다. 이 신호 없이 시험 이벤트 0건이 나오면 "저장되지 않음"이 아니라 "읽은 파일이 틀렸을 수 있음"으로 적는다.
- 파일이 회전·압축되어 시험 구간이 현재 파일에 없을 수 있다. 원장 파일의 첫 줄 `ts`가 시험 시작(17:27)보다 이르면 구간이 파일 안에 있다. 이르지 않으면 보관본을 찾는다. 찾지 못하면 미확인이다.
- 서버를 읽지 못했으면(접속 거부, 권한 없음, 파일 없음) 188에 "읽지 못함. 사유: …"을 적고 대조 칸은 미확인으로 둔다.

### 3. 차이가 나오면 문서에서 끝내지 않는다

- 차이 = 보낸 수 450 − 구간 안 저장 수. 0이면 "450 중 450 저장"으로 쓴다. 0이 아니면 188에 차이와 함께 줄이 빠진 시각 분포를 적고(분 단위로 센다), 원인 분석 이슈를 따로 연다.
- 원인을 이 이슈에서 추정하지 않는다. 빠진 시각이 두 인스턴스가 함께 뜬 구간에 몰렸는지만 적는다. 몰렸다면 이슈 #192(프로세스 간 파일 락)가 `EventLog`를 포함하지 않은 것이 원인 후보다. **#192가 `EventLog`를 다루는지는 이 설계에서 코드로 확인하지 않았다. 구현자가 `docs/design/192-inter-process-file-lock.md`와 `ADR-013`에서 확인한다.**
- 보낸 수 450은 188의 기록(GET과 POST 각 450건)이다. 시험 PC의 CSV(`load_post.py` 출력)는 저장소에 없으므로 이 수는 188 문서가 출처다. CSV를 가진 사람이 POST 줄 수가 450인지 한 번 더 센다. 못 하면 "보낸 수는 188의 기록을 따름"이라고 적는다.

### 4. `dev=true` 제외는 두 방법으로 확인한다. 시험 이벤트만으로는 증명이 안 된다

시험 이벤트는 `scroll_to_top`이다. 코드를 읽으면 이 이벤트는 어느 집계에도 들어가지 않는다.

| 집계 | 세는 이벤트 | 시험 이벤트가 들어가는가 |
| --- | --- | --- |
| 인기 순위(`PopularityIndex`) | `offer_link_click`, `banner_click`만, 그리고 `props.brand`가 있어야 함 | 아니오. 이름이 달라 `dev` 검사 이전에 걸러진다 |
| 활성 방문자(`scripts/active_users.py`) | 성공 신호 `offer_link_click`, `banner_click` | 방문자 수에는 들어갈 수 있으나 `dev` 방문자는 `keep`에서 뺀다 |
| 설문 대상 판정(`SurveyEligibility`) | 방문 일수와 전환 | `dev`가 한 번이라도 있으면 대상에서 뺀다 |
| PostHog 전달(`PostHogEventMapper`) | 전체 | `dev`가 참이면 빈 값을 돌려 보내지 않는다 |

그래서 "인기 순위 화면에 시험 이벤트가 안 보인다"는 관측은 `dev` 제외의 증거가 아니다. 이벤트 이름 때문에 `dev`가 거짓이어도 안 보인다. 양성 신호가 없다.

확인은 둘로 나눈다.

- 원장 수준(운영, 읽기 전용): 시험 이벤트 전체 줄 수와 `select(.dev != true)`를 거친 줄 수를 둘 다 센다. 전체가 450이고 거친 뒤 0이어야 "시험 줄이 모두 `dev: true`로 저장되고 원장 집계 명령이 모두 뺀다"가 증명된다. 거친 뒤 0이 아니면 `dev`가 저장되지 않은 줄이 있는 것이다. 이 방법은 `docs/ANALYTICS.md`의 직접 보기 명령과 같은 필터를 쓴다. `scripts/active_users.py`와 `scripts/experiments.py`는 `dev`를 방문자 단위로 보고(`e.get("dev") is True`) 같은 사람의 줄이 하나라도 `dev: true`면 그 방문자를 뺀다. 두 규칙은 시험 이벤트에서 같은 답을 낸다.
- 화면 수준(개발 서버, 쓰기 포함이지만 운영 아님): 운영에 가짜 클릭을 넣지 않는다. 개발 서버(`todiscount-be-dev`, 외부 주소는 `api/deploy/dev/README.md`)에서 `offer_link_click`에 `props.brand`를 붙인 이벤트를 `dev: true`와 `dev` 없음 두 벌 보내고 인기 순위(`/api/brands` 응답의 인기 값)를 비교한다. `dev` 없음만 순위에 오르고 `dev: true`는 오르지 않으면 양성 신호가 있다. 개발 서버는 푸시와 PostHog 전송이 꺼져 있고 별도 원장을 쓴다. **개발 서버의 원장이 운영과 분리돼 있다는 것은 `api/deploy/dev/README.md`의 서비스 구성으로 읽었을 뿐 파일 경로로 확인하지 않았다. 구현자가 `development.env`에서 이벤트 원장 경로가 운영과 다른지 먼저 확인한다.**

화면 수준 확인은 `PopularityIndex`의 기존 시험(`PopularityIndexTest`, `dev: true` 줄 포함)이 이미 단위로 막고 있다. 개발 서버 확인은 배포된 바이너리와 설정에서도 같은지 보는 일이다. 못 하면 단위 시험 이름을 근거로 적고 "배포본에서는 미확인"이라고 쓴다.

### 5. 188 문서를 이렇게 고친다

모두 `docs/design/188-zero-downtime-deploy.md`다. 줄 번호는 이 설계를 쓴 시점의 것이다.

| 자리 | 지금 | 바꿀 것 |
| --- | --- | --- |
| 51줄 "개발 서버와 운영 서버를 나누지 않았다." | 틀림 | 개발 경로가 있다고 고친다. 개발 서버는 `api/deploy/dev`의 `todiscount-be-dev` 서비스이고 배포는 dev push → 개발 러너다. 무중단(임시 인스턴스) 배포 시험은 운영 경로에만 했고 개발 경로는 그 방식이 아니다. 개발 경로가 같은 임시 인스턴스 방식을 쓰는지는 이번 시험에서 확인하지 않았다고 적는다 |
| 51줄 이어지는 "서버는 운영 서버 한 대이고 … 시험도 운영에서 했다." | 개발 경로를 무시한 서술 | 운영 서버에 임시 인스턴스가 같이 뜬다는 사실만 남기고 "운영에서 했다"는 이유를 고친다. 시험을 운영에서 한 이유는 임시 인스턴스 교대가 운영 경로에만 있기 때문이다 |
| 59줄 "개발과 운영 파이프라인을 나누지 않았다." | 틀림 | 개발은 별도 경로(dev push → 개발 러너 배포, `api/deploy/dev/README.md`)이고 이 문서의 무중단 경로는 운영 하나라고 고친다 |
| 109줄 "복구 시간을 알려면 스크립트가 줄마다 시각을 찍어야 한다." | 원인을 틀리게 짚음 | 원인은 실행 로그의 출력 버퍼링이다(짝 이슈). 줄마다 시각을 찍어도 버퍼링되어 한꺼번에 나오면 소용없다. 처방을 "출력을 바로 내보내게 하고(버퍼링 해제) 줄마다 시각을 찍는다"로 고친다 |
| 357줄, 372줄 같은 처방 | 같은 오류 | 109줄과 같게 고친다 |
| 116줄 "빠진 증거"의 POST 줄 | 대조 안 함 | 결과를 채우거나 미확인 사유를 적는다 |
| 233줄, 264줄의 쓰기 요청 결과 | "0회 실패"만 있음 | 저장 수 대조 결과를 같은 표에 열로 더한다 |
| 366줄 "남은 일 1"의 대조 항목 | 남은 것 | 끝냈으면 "한 일"로 옮기고, 못 했으면 사유와 함께 남긴다 |
| 코치용 안내 표 27줄 | POST 450건 중 실패 0건 | 저장 수 대조 결과를 한 문장 더한다 |

로그 버퍼링 문장의 짝 이슈 번호는 이 설계가 알지 못한다. 이슈 본문이 "짝 이슈"라고만 한다. **구현자는 번호를 넣기 전에 이슈를 열어 확인하거나, 번호 없이 "별도 이슈"라고 쓴다. 번호를 추측해 적지 않는다.**

채울 때 규칙:

- 결과마다 날짜(조회한 2026-10-30 또는 그날의 실제 날짜), 출처(원장 조회, 명령 형태), 세는 기준(방문자, 경로, 구간)을 같이 적는다.
- 조회한 사람이 읽은 값만 적는다. 구현자가 서버를 읽지 못하면 숫자를 지어내지 않는다.
- 188의 "시험 2는 실패 0건"과 "집계" 문장은 지우지 않는다. 실패 0건은 응답 코드 기준이라는 한정을 한 번 더 붙인다.

## 변경 전파

`docs/CHANGE-PROPAGATION.md`의 묶음 중 이 작업이 건드리는 것은 7번(행동 이벤트)뿐이다. 이벤트 이름의 허용 목록과 대조 스크립트를 바꾸지 않으므로 묶음의 나머지를 고칠 일은 없다. 이 작업은 문서만 고치고 코드, 허용 목록, 웹을 바꾸지 않는다. 8번(저장소 경계와 배포 순서)도 건드리지 않는다. 188은 mono 문서이고 미러 대상이 아니다.

`docs/design/README.md`에 설계 문서 목록이 있으면 215를 더한다. **목록이 있는지는 이 설계에서 열어 보지 않았다. 구현자가 확인한다.**

- 차이가 있으면 원인 분석 이슈의 번호가 188에 있다.
- 서버를 읽지 못했으면 188의 대조 칸이 "미확인"이고 사유가 있다.
- 틀린 문장 둘이 고쳐졌다. `rg "나누지 않았" docs/design/188-zero-downtime-deploy.md`가 0건이고, 줄마다 시각을 찍는다는 처방이 버퍼링 해제와 함께 나온다.
- `python scripts/generate_project_structure.py`를 돌려 `docs/PROJECT-STRUCTURE.md`가 새 설계 문서를 반영하는지 본다. 푸시 훅이 안 하면 막는다.

## 하지 않는 것

- 원장을 고치거나 시험 이벤트를 지우지 않는다. 시험 줄은 `dev: true`라 집계에서 빠지고, 지우면 증거도 사라진다.
- 서버에서 쓰기 명령, 서비스 재시작, 배포를 하지 않는다.
- 운영에 가짜 클릭 이벤트를 새로 넣지 않는다.
- 시험 2를 다시 돌리지 않는다. 다시 돌린다면 이번 대조에서 차이가 나왔을 때 원인 분석 이슈에서 정한다. 그때는 POST 응답의 `accepted` 값을 CSV에 남긴다.
- `EventLog`를 고치지 않는다. 쓰기 손실이 확인되면 별도 이슈에서 고친다.

## 리뷰 포인트

- 서버 읽기를 누가 실행하는가. 이 설계는 읽기 허용만 알고 있다. 실행 주체가 ssh를 못 쓰면 대조 칸이 미확인으로 남는다.
- 시험 이벤트를 `ts` 구간으로 나누는 기준(17:27~17:43)이 시험 2의 시작·끝(15분)과 맞는가.
- 화면 수준 `dev` 확인을 개발 서버에서 하는 것으로 충분한가, 단위 시험 근거만 적고 넘어가도 되는가.
