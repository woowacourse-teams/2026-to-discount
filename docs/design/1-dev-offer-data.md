# Design: 개발 환경의 실제 오퍼 데이터 적용

- 이슈: https://github.com/woowacourse-teams/2026-to-discount/issues/62
- 상태: GitHub Actions 수동 실행 방식 승인 및 구현 중

## 1. 문제

개발 웹과 개발 API는 분리됐지만 개발 API는 최초 설치한 샘플 오퍼 6개를 반환한다. 실제 브랜드 구성과 다양한 할인 조건을 검증하려면 운영 원장의 사본이 필요하다.

## 2. 목표

- 개발 웹이 개발 API를 통해 실제 오퍼를 표시한다.
- 운영 데이터에 쓰기 작업을 하지 않고 개발 데이터만 갱신한다.
- 갱신 실패 시 이전 개발 데이터로 복구하고 실패를 확인한다.

## 3. Non-goals

- 개발 웹의 API 주소 변경 및 관리 버튼 추가
- 운영 데이터 또는 테스트용 합성 픽스처 변경
- 배너, 방문 기록, 푸시 구독, 설문 및 사용자 데이터 복사
- 정기 동기화와 실시간 최신성 보장

## 4. 요구사항

### 필수

- 운영 오퍼 원장의 사본을 개발 API의 외부 데이터 파일로 적용한다.
- 개발에서 오퍼를 수정하거나 재로드해도 운영은 변경되지 않는다.
- 다운로드와 검증 실패 시 현재 파일을 보존한다.
- 적용 후 개발 API의 오퍼 응답과 개발 웹을 확인한다.

### 선택

- 정기 갱신은 수동 갱신의 필요 빈도를 확인한 뒤 별도로 검토한다.

## 5. 제약사항

- 개발 API는 DISCOUNT_EXPORT_PATH로 외부 파일을 읽는다.
- 저장소 설정의 개발 경로는 /var/lib/todiscount-be-dev/export.json이다. 실제 서버 환경과 운영 원장 경로는 구현 전에 확인한다.
- API의 /api/brands는 가공 응답이므로 원장 export.json으로 그대로 저장하지 않는다.
- 원장 사본은 공개 저장소와 Actions 공개 산출물에 넣지 않는다.
- 운영 원장은 읽기만 하고 개발 전용 경로만 갱신한다.

## 6. 성공 조건

- [ ] 개발 API에서 복사한 실제 브랜드와 오퍼가 반환된다.
- [ ] 개발 웹의 브라우저 및 SSR이 개발 API를 계속 사용한다.
- [ ] 적용 전후 운영 원장의 내용은 같다.
- [ ] 잘못된 원장이나 전송 실패 시 기존 개발 데이터가 유지된다.
- [ ] 개발 재배포 후에도 적용한 외부 데이터가 유지된다.

## 7. 고려한 접근 방식

### A. 운영 원장을 개발 서버에 수동 복사

기존 외부 파일 읽기 기능을 사용한다. 추가 변경이 적고 갱신 시점을 선택할 수 있다. 운영 최신 데이터와 자동으로 일치하지는 않는다.

### B. 운영 원장을 정기 복사

개발 데이터의 최신성을 자동으로 유지한다. 스케줄, 인증 정보, 실패 알림과 동시 실행 관리가 추가로 필요하다.

### C. 개발 웹에서 운영 API 직접 호출

데이터는 즉시 최신이지만 개발 트래픽과 쓰기 기능이 운영으로 향할 수 있고 현재 개발 API 분리를 유지하지 못한다.

## 8. 선택

선택한 방법은 A를 GitHub Actions의 Run workflow 버튼으로 실행하는 방식이다. 현재 목적은 실제 화면 검증이며 자동 동기화 요구는 없다. 최초 복사와 반복 가능한 수동 갱신 절차부터 마련한다. 일정 실행과 개발 웹 버튼은 추가하지 않는다.

## 9. 설계

### Architecture

운영 export.json 읽기 → 임시 사본 검증 → 개발 외부 파일 교체 → 개발 API 재로드 → 개발 웹 확인.

### Components

- 수동 Actions: dev 브랜치와 development 환경에서 개발 전용 러너를 실행한다. 운영 원장 읽기 전용 SSH 키로 파일을 받아 임시 파일을 정리한다.
- root 소유 갱신 도구: 개발 파일 백업, 원자적 교체, 내부 재로드, 실패 시 복원을 담당한다. 기존 배포 도구와 서버 잠금을 공유한다.
- 개발 API: 기존 OfferRepository와 외부 파일 설정으로 사본을 읽는다.
- 개발 웹: 기존 개발 API 호출을 유지한다.

### Data Flow

1. 실제 운영 및 개발 원장 경로와 접근 권한을 확인한다.
2. 운영 원장을 읽어 개발 서버의 임시 파일로 전달한다.
3. JSON 구조와 API가 읽을 수 있는 데이터인지 검증한다.
4. 개발 기존 파일을 백업하고 같은 파일시스템에서 원자적으로 교체한다.
5. 개발 API만 재로드하고 결과를 확인한다.
6. 오퍼 응답과 화면을 확인하고 갱신 시각과 건수를 기록한다.

### Error Handling

- 원본 읽기 또는 검증 실패: 교체하지 않고 실패를 보고한다.
- 개발 재로드 또는 응답 검증 실패: 백업 파일을 복원하고 다시 재로드한다.
- 운영 API 응답을 원장으로 변환하는 임의의 경로는 추가하지 않는다.

## 10. 테스트 전략

- Unit: 갱신 자동화 스크립트를 추가한다면 잘못된 JSON과 전송 실패의 기존 파일 보존을 확인한다.
- Integration: 개발 API 재로드 후 오퍼 구조와 반환 데이터를 검증한다.
- Acceptance: 개발 웹에서 실제 브랜드 구성을 확인하고 호출 대상이 개발 API인지 확인한다.
- 기타: 운영 원장 해시 보존, 개발 재배포의 데이터 보존, git diff --check를 확인한다.

## 11. 미해결 사항

- 수동 실행 방식은 2026-10-12 사용자 승인
- 운영 원장 /home/ubuntu/delivery-discount-api/data/export.json 및 ubuntu 읽기 권한 확인 완료
- 운영 원장 읽기 전용 SSH 키와 호스트 키 시크릿 등록
- 개발 서버 SSH가 현재 시간 초과되므로 갱신 도구 설치 확인 필요
- 수동 실행 버튼 등록을 위한 main 워크플로 파일 반영 필요
- 개발 서버의 실제 외부 파일 경로 확인


## Implementation Plan

- `.github/workflows/sync-dev-offers.yml`: 수동 트리거와 dev 가드, development 환경, 원장 전송 및 내부 갱신 도구 호출.
- `api/deploy/dev/sync_offers.py`: 개발 서비스의 실제 환경 및 소스 검증, 백업과 원자적 교체, 재로드 검증과 실패 시 복구.
- `api/deploy/dev/test_sync_offers.py`: 정상 적용, 잘못된 원장, 재로드 실패, 복구 실패, 링크 파일 차단 검증.
- `api/deploy/dev/provision.sh`, `api/deploy/dev/README.md`: root 소유 도구 설치와 제한 sudo 권한, 읽기 전용 SSH 설정 및 버튼 실행 안내.
- 구현 PR은 dev 대상, 수동 버튼 등록 PR은 main 대상의 워크플로 파일만으로 분리한다.
- 검증: Python 배포 도구 테스트, bash 문법 검사, workflow YAML 가드, 구조 문서 검사, git diff --check. 서버 설정 후 수동 실행 결과 및 개발 API 응답 확인.
