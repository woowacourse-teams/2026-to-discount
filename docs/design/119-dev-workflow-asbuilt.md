# 설계 119 실제 구현 정리 (2026-10-21, 2026-10-22 갱신)

[설계 119](119-dev-workflow.md)(이슈에서 병합까지 개발 워크플로 자동화)를 실제로 만들고 시험한 결과를 정리한다. 설계대로 된 것과 바뀐 것을 나누고, 바뀐 것에는 결정, 대안, 이유, 근거를 붙였다. 자세한 시행착오는 수집 저장소(비공개)의 워크플로 트러블슈팅 문서에 있다.

## 지금 상태 (2026-10-22)

이 저장소(mono)와 수집 저장소(tracker, 비공개)가 같은 흐름을 쓴다. 워크플로 본문은 이 저장소 `.github/workflows/wf-*.yml` 한 곳에 있다.

| 순서 | 단계 | 누가 | 무엇이 남나 |
| --- | --- | --- | --- |
| 1 | 이슈 작성 | 사람, 또는 후속 이슈 워크플로 | 이슈(영역 라벨) |
| 2 | 설계 | `ready` 라벨(사람) → 설계 세션 | 설계 문서, `feat/<이슈>-*` 브랜치, 초안 PR, `인계:` 댓글 |
| 3 | 설계 승인 | 사람: 이슈 댓글 첫 줄 `/approve-design` | |
| 4 | 분기 | 로컬 PC가 1분마다 확인해 먼저 잡으면 `local` 라벨. 클라우드는 2분 기다려 라벨이 있으면 물러남. `collect`는 안내만 | |
| 5 | 구현 | 로컬 대화형 세션(사람이 지켜봄) 또는 클라우드 세션 | 같은 PR에 커밋, 초안 해제, `인계:` 댓글 |
| 6 | 리뷰 | 사람. CodeRabbit은 이 저장소만, PR마다 마지막 push 뒤 `@coderabbitai review` 한 번 | 리뷰 지적 |
| 7 | 리뷰 반영 | 사람: PR 댓글 첫 줄 `/reflect` → 반영 세션(최대 2회) | 커밋, `반영:` 댓글 |
| 8 | 병합 승인 | 사람: PR 댓글 첫 줄 `/approve` → App 토큰 병합 | |
| 9 | 마무리 | 자동: 요약 세션(결과 절, 이슈 닫기), 후속 이슈 세션(본문 `### 후속 조치` 절이 있을 때) | 결과 절, 후속 이슈 |

- 승인 댓글은 첫 줄만 본다. 둘째 줄부터 의견을 적어도 된다. 댓글을 고쳐서는 다시 돌지 않는다(새 댓글을 단다).
- 검사가 끝날 때마다 결과 댓글 하나를 고쳐 쓴다.

## 설계대로 된 것

| 항목 | 구현 |
| --- | --- |
| 사람 관문 둘 | `/approve-design`(이슈 댓글), `/approve`(PR 댓글). 권한자(admin, write)만 받는다 |
| 단계마다 새 세션 | 설계, 구현, 반영, 요약이 각각 다른 워크플로와 세션이다. 단계 사이는 `인계:` 댓글로 넘긴다 |
| 외부 입력 거르기 | 세션 입력 파일에는 OWNER, MEMBER, COLLABORATOR 댓글만 넣는다 |
| 실패 처리 | 실패나 취소면 이슈에 `blocked`와 원인 댓글. 자동 재시도 없음 |
| 이슈당 한 작업 | `concurrency` 그룹을 이슈 번호로 잡았다 |
| 액션 고정 | Claude, checkout, App 토큰 액션은 커밋 SHA로 고정했다 |
| main 보호 | 저장소 규칙으로 PR 필수, 관리자만 예외. 워크플로 기본 권한은 읽기 |
| 공개 정보 검사 | 요약 결과 절과 댓글을 다시 받아 서버 경로, 비밀 파일 이름, 키 모양 문자열을 grep한다 |
| 반영 최대 2회 | `반영:` 댓글 수로 상한(PR #135) |

## 바뀐 것

### 결과물을 세션 보고가 아니라 워크플로가 확인한다

- **결정:** 세션이 끝나면 워크플로가 브랜치, PR, `인계:` 댓글(구현은 새 커밋)을 직접 확인한다. 하나라도 없으면 실패다. 설계 문서는 실행 결과물로 14일 보관한다.
- **대안:** 세션의 "성공" 보고를 믿는다.
- **이유:** 세션은 push가 전부 거부돼 결과물이 0개여도 "성공"을 보고했다.
- **근거:** 설계 시험 3·4회차. 결과물 없이 성공으로 끝나 `blocked`도 안 붙었다.

### 허용 도구는 명령 단위로 두되 push는 전체를 연다 (2026-10-22 바뀜: 아래 "세션은 커밋만 하고 push는 워크플로가 한다")

- **결정:** `Bash(git push:*)`. main은 저장소 규칙이 막는다. 세션에는 "명령은 하나씩, 파일은 Write, 본문은 `--body-file`"을 지시한다.
- **대안:** (1) 브랜치 이름까지 맞춘 패턴 (2) 셸 전체 허용.
- **이유:** (1)은 세션이 정하는 브랜치 이름과 계속 어긋난다. (2)는 안전 판정이 막았고, 명령 모양 제한만으로는 어차피 안전해지지 않는다.
- **근거:** `Bash(git push -u origin feat/:*)`가 `feat/121-…`와 맞지 않아 push 4번이 모두 거부됐다. 묶은 명령과 여러 줄 본문도 거부됐다.

### 세션 출력은 숨기고 거부 내역과 턴 수만 남긴다

- **결정:** `show_full_output`은 끈다. 실행 결과 파일에서 턴 수와 거부된 도구만 뽑아 로그에 남긴다.
- **대안:** 전체 출력을 켠다.
- **이유:** 공개 저장소라 세션 출력이 공개 로그에 남는다. 원인 진단에는 거부 내역이면 충분했다.
- **근거:** 거부 내역 단계를 넣은 뒤 push 패턴 원인을 바로 찾았다.

### 셸 격리 설정은 쓰지 않는다

- **결정:** `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`과 bubblewrap을 걷었다. 신뢰는 "`ready`는 본문을 읽은 권한자만 단다"는 운영 규칙과 외부 댓글 거르기에 둔다.
- **대안:** 러너에 필요한 도구를 설치해 격리를 살린다.
- **이유:** 기본 러너에서는 격리가 추가 도구를 계속 요구했고, 도구가 하나라도 빠지면 세션의 셸 명령이 전부 실패했다. 사용자가 공개 저장소 노출은 감수하기로 했다.
- **근거:** 시험 이슈 #123에서 세 번 실패했다. 걷어낸 뒤 #125에서 정상으로 돌았다.

### 구현 push와 병합은 GitHub App 토큰으로 한다

- **결정:** 짧은 수명의 App 토큰(`actions/create-github-app-token`)으로 구현 push와 `/approve` 병합을 한다. 그 밖의 쓰기는 기본 토큰이다.
- **대안:** (A) 기존 검사 워크플로를 `workflow_call`로 불러 쓴다. (B) 개인 액세스 토큰을 쓴다.
- **이유:** 기본 토큰이 만든 push와 병합은 다른 워크플로를 깨우지 않는다. (A)는 검사 결과가 PR 커밋이 아니라 main 커밋에 붙어 결과 댓글이 복잡해졌다. (B)는 수명이 길어 관리 위험이 크다.
- **근거:** App 토큰으로 바꾼 뒤 PR head 커밋에 check, gitleaks, Vercel, shot 검사가 붙었다. App 병합이 요약 워크플로를 깨웠다(PR #132, #134).

### 요약 세션은 App 봇이 일으킨 실행을 허용한다

- **결정:** 요약 워크플로에만 `allowed_bots`로 이 App 하나를 허용한다.
- **이유:** App 병합이 일으킨 실행은 봇 실행이라 Claude 액션이 기본으로 거부한다.
- **근거:** `Workflow initiated by non-human actor: … (type: Bot)`로 요약이 실패했고, 허용 뒤 #134에서 통과했다.

### 턴 상한은 시험값으로 맞췄다

- **결정:** 설계 50, 구현 80, 반영 30, 요약 20.
- **이유:** 설계 문서의 처음 추정(설계 30, 요약 10)이 모자랐다.
- **근거:** 설계 시험 29~34턴, 요약 11턴.

### 결과 댓글의 성능 점수는 PR 단계에 없다

- **결정:** 결과 댓글에는 검사 표, 테스트 수, 남은 리뷰 지적, 프리뷰 주소, 360px 스크린샷 실행 링크를 단다. 성능 점수는 "병합 뒤 측정"이라고 적는다.
- **대안:** PR마다 `web-perf`를 돌린다.
- **이유:** `web-perf`는 main 배포 뒤에만 돈다. PR마다 돌리면 비용과 러너 편차가 크다. 스크린샷은 실행 아티팩트라 댓글에 그림으로 넣을 수 없어 링크로 단다.

### 워크플로 정본은 이 저장소 하나다 (2026-10-22)

- **결정:** 설계, 구현, 반영, 승인 병합, 요약, 후속 이슈, 결과 댓글 7개를 재사용 워크플로(`wf-*.yml`)로 두고, 두 저장소의 `design-session.yml` 등은 언제 부를지와 저장소 설정만 담는다. 수집 저장소는 이 저장소 main을 부른다.
- **저장소 설정:** 설계 문서 위치, 영역 라벨과 구현자·도구·테스트 환경, 테스트용 추가 체크아웃, 공개 저장소 검사 여부.
- **대안:** 저장소마다 복사본을 둔다.
- **이유:** 고칠 때마다 두 PR을 맞춰 병합해야 했고 한쪽만 고친 채 어긋났다.
- **비용:** 이 저장소 main의 실수가 수집 저장소에 바로 번진다.

### 세션은 커밋만 하고 push는 워크플로가 한다 (2026-10-22)

- **결정:** 두 저장소 모두 세션에 `git push`와 PR 생성을 주지 않는다. 세션이 끝나면 워크플로가 커밋을 패치로 보관하고, `feat/<이슈>-<소문자>` 이름을 검사한 뒤 App 토큰으로 push한다.
- **기존:** 이 저장소는 세션이 push했다(위 "push는 전체를 연다").
- **이유:** 수집 저장소는 무료 비공개라 저장소 규칙이 없어 세션 push를 막을 장치가 없다. 두 저장소를 같은 정본으로 묶으며 엄격한 쪽으로 맞췄다. Claude 액션이 끝나며 체크아웃의 git 자격을 지우므로 다시 체크아웃해 push한다.

### 구현은 로컬 PC가 먼저 맡는다 (2026-10-22)

- **결정:** 로컬 PC의 감시 스크립트(수집 저장소에 있음)가 1분마다 승인 댓글을 찾아 `local` 라벨을 달고 대화형 세션 창을 띄운다. 클라우드 구현은 2분 기다려 라벨이 있으면 물러나고, 라벨 조회가 실패하면 실패로 끝난다.
- **이유:** 클라우드 세션은 사람이 진행을 보거나 개입할 수 없다. PC가 꺼져 있거나 팀원이 승인할 때는 클라우드가 예비로 돈다.
- **근거:** tracker #22, mono #141에서 로컬이 맡고 클라우드가 물러났다.

### 후속 조치는 이슈로 자동으로 만든다 (2026-10-22)

- **결정:** 병합된 PR 본문에 `### 후속 조치` 절이 있으면 세션이 이슈 계획(JSON)을 쓰고, 단계가 저장소별 App 토큰으로 이슈를 만든다. 같은 일은 묶고, 고칠 곳의 저장소와 영역 라벨을 고른다. 항목마다 표식을 달아 다시 돌아도 같은 이슈를 만들지 않는다.
- **이유:** 손으로 만든 후속 이슈는 출처 링크 한 줄이라 설계 세션이 일할 수 없었다(세션은 PR을 열지 않는다).
- PR 본문과 후속 이슈의 글쓰기 규칙 정본은 `.claude/skills/pr-body-ko/SKILL.md`다.

## 남은 것

- 4단계 수집 로컬 러너(`collect` 영역). 구현 로컬 우선 구성 위에 폰 잡기 규칙을 얹는 방식으로 정한다.
- 같은 `/approve-design`을 다시 달 때의 동작(재실행 의미)이 정해지지 않았다.
- 로컬 세션이 사용자 계정으로 `/approve`를 PR 댓글로 달면 자동 모드 분류기(Claude Code가 도구 호출을 자동으로 허용하거나 막는 판정기)가 자기 승인으로 보고 막는다(2026-10-28 tracker #41). 기본은 사용자가 직접 단다. 사용자가 외부나 원격 건이라고 명시하면 세션이 대신 달 수 있어야 하므로, 사용자가 `gh pr comment` 허용 규칙을 설정에 넣는다.
- 리뷰 세션은 PR이 `ready_for_review`로 바뀔 때만 돌아 그 뒤 푸시한 코드는 리뷰를 받지 못한다(tracker #41의 `61470fc`). 이슈 #210에서 다룬다.
- 로컬 세션은 사용자 계정으로 돌아 댓글 작성자가 `claude[bot]`이 아니다. 반영 횟수는 `claude[bot]` 댓글만 센다(로컬은 반영을 하지 않아 지금은 영향 없음).

## 이 작업에서 배운 것

- **세션의 자기 보고를 믿지 않는다.** 결과물은 워크플로가 기계로 확인한다.
- **원인을 보려면 무엇이 거부됐는지부터 남긴다.** 거부 내역 한 줄로 시험 회차가 줄었다.
- **검사가 안 깨어나면 누가 push했는지를 본다.** 신분(토큰)만 바꾸면 기존 검사가 그대로 붙는다. 우회 경로를 덧대는 것은 그다음이다.
- **방어 설정은 켜기 전에 실행 환경에서 한 번 돌려 본다.** 문서만 보고 켠 격리가 세션을 통째로 멈췄다.
- **사람 관문은 자동 판정도 관문으로 본다.** 병합과 `/approve`는 사람이 직접 하고, 세션은 결과를 폴링해 다음으로 넘어간다.
