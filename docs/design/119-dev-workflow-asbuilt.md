# 설계 119 실제 구현 정리 (2026-10-21)

[설계 119](119-dev-workflow.md)(이슈에서 병합까지 개발 워크플로 자동화)를 실제로 만들고 시험한 결과를 정리한다. 설계대로 된 것과 바뀐 것을 나누고, 바뀐 것에는 결정, 대안, 이유, 근거를 붙였다. 자세한 시행착오는 수집 저장소(비공개)의 워크플로 트러블슈팅 문서에 있다.

## 지금 상태

- 이슈 #133 → PR #134에서 전체 흐름이 끝까지 돌았다. 사람이 단 것은 `ready` 라벨, `/approve-design`, `/approve` 셋이다.
- 1~3단계(설계, 구현·검사·병합, 요약)는 GitHub 호스트 러너에서 돈다. 4단계(수집 로컬 러너)는 아직 없다.
- 리뷰 반영(`/reflect`), api 구현자 JDK, 결과 댓글 보강은 PR #135에 있다. 병합 뒤 실제 이슈로 처음 확인한다.

## 설계대로 된 것

| 항목 | 구현 |
| --- | --- |
| 사람 관문 둘 | `/approve-design`(이슈 댓글), `/approve`(PR 댓글). 권한자(admin, write)만 받는다 |
| 단계마다 새 세션 | 설계, 구현, 반영, 요약이 각각 다른 워크플로와 세션이다. 단계 사이는 `인계:` 댓글로 넘긴다 |
| 외부 입력 거르기 | 세션 입력 파일에는 OWNER, MEMBER, COLLABORATOR 댓글만 넣는다 |
| 실패 처리 | 실패나 취소면 이슈에 `blocked`와 원인 댓글. 자동 재시도 없음 |

| 공개 정보 검사 | 요약 결과 절과 댓글을 다시 받아 서버 경로, 비밀 파일 이름, 키 모양 문자열을 grep한다 |
| 반영 최대 2회 | `반영:` 댓글 수로 상한(PR #135) |

## 바뀐 것

### 결과물을 세션 보고가 아니라 워크플로가 확인한다

- **결정:** 세션이 끝나면 워크플로가 브랜치, PR, `인계:` 댓글(구현은 새 커밋)을 직접 확인한다. 하나라도 없으면 실패다. 설계 문서는 실행 결과물로 14일 보관한다.
- **대안:** 세션의 "성공" 보고를 믿는다.
- **이유:** 세션은 push가 전부 거부돼 결과물이 0개여도 "성공"을 보고했다.
- **근거:** 설계 시험 3·4회차. 결과물 없이 성공으로 끝나 `blocked`도 안 붙었다.

### 허용 도구는 명령 단위로 두되 push는 전체를 연다

- **결정:** `Bash(git push:*)`. main은 저장소 규칙이 막는다. 세션에는 "명령은 하나씩, 파일은 Write, 본문은 `--body-file`"을 지시한다.
- **대안:** (1) 브랜치 이름까지 맞춘 패턴 (2) 셸 전체 허용.
- **이유:** (1)은 세션이 정하는 브랜치 이름과 계속 어긋난다. (2)는 안전 판정이 막았고, 명령 모양 제한만으로는 어차피 안전해지지 않는다.
- **근거:** `Bash(git push -u origin feat/:*)`가 `feat/121-…`와 맞지 않아 push 4번이 모두 거부됐다. 묶은 명령과 여러 줄 본문도 거부됐다.

### 세션 출력은 숨기고 거부 내역과 턴 수만 남긴다

- **결정:** `show_full_output`은 끈다. 실행 결과 파일에서 턴 수와 거부된 도구만 뽑아 로그에 남긴다.
- **대안:** 전체 출력을 켠다.
- **이유:** 공개 저장소라 세션 출력이 공개 로그에 남는다. 원인 진단에는 거부 내역이면 충분했다.
- **근거:** 거부 내역 단계를 넣은 뒤 push 패턴 원인을 바로 찾았다.

### 셸 격리 설정은 쓰지 않는다

- **결정:** `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`과 bubblewrap을 걷었다. 신뢰는 "`ready`는 본문을 읽은 권한자만 단다"는 운영 규칙과 외부 댓글 거르기에 둔다.
- **대안:** 러너에 필요한 도구를 설치해 격리를 살린다.
- **이유:** 기본 러너에서는 격리가 추가 도구를 계속 요구했고, 도구가 하나라도 빠지면 세션의 셸 명령이 전부 실패했다. 사용자가 공개 저장소 노출은 감수하기로 했다.
- **근거:** 시험 이슈 #123에서 세 번 실패했다. 걷어낸 뒤 #125에서 정상으로 돌았다.

### 구현 push와 병합은 GitHub App 토큰으로 한다

- **결정:** 짧은 수명의 App 토큰(`actions/create-github-app-token`)으로 구현 push와 `/approve` 병합을 한다. 그 밖의 쓰기는 기본 토큰이다.
- **대안:** (A) 기존 검사 워크플로를 `workflow_call`로 불러 쓴다. (B) 개인 액세스 토큰을 쓴다.
- **이유:** 기본 토큰이 만든 push와 병합은 다른 워크플로를 깨우지 않는다. (A)는 검사 결과가 PR 커밋이 아니라 main 커밋에 붙어 결과 댓글이 복잡해졌다. (B)는 수명이 길어 관리 위험이 크다.
- **근거:** App 토큰으로 바꾼 뒤 PR head 커밋에 check, gitleaks, Vercel, shot 검사가 붙었다. App 병합이 요약 워크플로를 깨웠다(PR #132, #134).

### 요약 세션은 App 봇이 일으킨 실행을 허용한다

- **결정:** 요약 워크플로에만 `allowed_bots`로 이 App 하나를 허용한다.
- **이유:** App 병합이 일으킨 실행은 봇 실행이라 Claude 액션이 기본으로 거부한다.
- **근거:** `Workflow initiated by non-human actor: … (type: Bot)`로 요약이 실패했고, 허용 뒤 #134에서 통과했다.

### 턴 상한은 시험값으로 맞췄다

- **결정:** 설계 50, 구현 80, 반영 30, 요약 20.
- **이유:** 설계 문서의 처음 추정(설계 30, 요약 10)이 모자랐다.
- **근거:** 설계 시험 29~34턴, 요약 11턴.

### 결과 댓글의 성능 점수는 PR 단계에 없다

- **결정:** 결과 댓글에는 검사 표, 테스트 수, 남은 리뷰 지적, 프리뷰 주소, 360px 스크린샷 실행 링크를 단다. 성능 점수는 "병합 뒤 측정"이라고 적는다.
- **대안:** PR마다 `web-perf`를 돌린다.
- **이유:** `web-perf`는 main 배포 뒤에만 돈다. PR마다 돌리면 비용과 러너 편차가 크다. 스크린샷은 실행 아티팩트라 댓글에 그림으로 넣을 수 없어 링크로 단다.

## 남은 것

- 4단계 수집 로컬 러너. 공개 저장소라 self-hosted 러너보다 로컬 폴링 스크립트와 `claude -p`를 권한다. 방식은 아직 정하지 않았다.
- 같은 `/approve-design`을 다시 달 때의 동작(재실행 의미)이 정해지지 않았다.
- `result-comment.yml`에 아무도 부르지 않는 `workflow_call` 부분이 남았다. 동작에는 영향이 없다.

## 이 작업에서 배운 것

- **세션의 자기 보고를 믿지 않는다.** 결과물은 워크플로가 기계로 확인한다.
- **원인을 보려면 무엇이 거부됐는지부터 남긴다.** 거부 내역 한 줄로 시험 회차가 줄었다.
- **검사가 안 깨어나면 누가 push했는지를 본다.** 신분(토큰)만 바꾸면 기존 검사가 그대로 붙는다. 우회 경로를 덧대는 것은 그다음이다.
- **방어 설정은 켜기 전에 실행 환경에서 한 번 돌려 본다.** 문서만 보고 켠 격리가 세션을 통째로 멈췄다.
- **사람 관문은 자동 판정도 관문으로 본다.** 병합과 `/approve`는 사람이 직접 하고, 세션은 결과를 폴링해 다음으로 넘어간다.
