# 34. 라이브 오퍼 상시 확인 봇: 링크를 열어 값이 유효한지 보고, 없으면 내린다 (2026-09-19)

계획만 둔다. 착수는 사용자가 주기와 자동 내림 여부를 정한 뒤다(7절). 추적 이슈 [#34](https://github.com/woowacourse-teams/2026-to-discount/issues/34).

## 1. 배경

웹에 뜨는 오퍼(할인 한 건)는 수집 PC의 폰이 배달앱 화면을 읽어 원장(`data/log.jsonl`. 수집한 값을 전부 적는 기준 장부)에 적고, `export_data.py`가 살아 있는 것만 골라 서버에 올린 것이다. 지금 살아 있는지 다시 보는 길은 예약 실행(하루 세 번, 00:01·10:55·15:55)의 4단계 전수조사뿐이다. 그 4단계는 00:01에만 돌고, 배민 브랜드관은 이번 주에 값을 읽은 브랜드를 다음 월요일까지 건너뛴다(주기 스킵). 그래서 배민 브랜드관 쿠폰이 화요일에 사라져도 다음 월요일까지 웹에 떠 있다.

2026-09-18에 드러난 일: 4단계 결과가 아흐레 동안 원장에 안 들어갔다(`tracker/docs/setup/REPORT-20260918-audit-ingest-gap.md`). 고친 뒤에도 "값이 있는지 다시 확인하는 주기"는 위와 같다.

## 2. 문제

1. 사라진 오퍼가 최대 6일 떠 있을 수 있다(배민 브랜드관).
2. 확인이 수집 실행에 묶여 있어 "지금 이 오퍼가 유효한가"를 따로 물을 수 없다.
3. 배너 링크는 아무도 열어 보지 않는다(배너가 가리키는 화면에 그 할인이 있는지).

## 3. 제안: 서버가 내보내는 라이브 오퍼 전부를 도는 확인 루프

`scripts/verify_live.py`. 폰 한 대에서 돈다. 수집 코드를 그대로 쓴다.

| 앱 | 확인 방법 | 재사용 |
|---|---|---|
| 배민 | 라이브 브랜드의 브랜드관 딥링크를 열고 쿠폰 시트를 읽는다 | `full_audit.audit_baemin(only=라이브 브랜드)` |
| 땡겨요 | 혜택 목록을 끝까지 훑는다 | `full_audit.audit_ddangyo` |
| 요기요 | 할인 탭 목록과 쿠폰받기 시트를 읽는다 | `full_audit.audit_yogiyo` |
| 쿠팡이츠 | 허브의 고정 쿠폰 목록을 읽는다(쿠폰은 받지 않는다) | `capture.coupangeats.read_weekly_deals(force_claim=False)` |
| 배너 | 배너마다 링크를 열고 그 화면 글자에 금액과 브랜드가 있는지 본다 | `banner_routine.extend_expiring`의 링크 열기 |

판정은 셋이다.

- 읽은 값이 라이브 값과 같다: 확인 시각만 적는다(`data/verified.jsonl`).
- 값이 다르다: 새 관측으로 원장에 넣는다(`ingest.py`. 최신 관측이 이긴다).
- 페이지는 열렸는데 쿠폰이 없다, 또는 목록에 브랜드가 없다: 원장에 판단 행을 적는다(ADR-030 제외 행, 사유 `verified_gone`, 증거 png 경로). 이 사유는 **비지속**이다. 다음 관측에서 다시 보이면 되살아난다. 지속형 제외(limited, targeted, duplicate)와 다르다.
- 페이지를 못 열었다(링크 오류): 판단하지 않는다. 죽은 링크 장부(`data/dead_links.json`)에만 센다.

결과는 `export_data.py` → `deploy_export.py`로 웹까지 간다. 사라짐은 관측이라 승인 없이 내리는 쪽을 추천한다(배너와 다르다. 배너는 사람이 쓴 문구라 승인을 받는다).

## 4. 비용과 주기

폰 한 대, 2026-09-18 실측 기준.

| 앱 | 대상 | 소요 |
|---|---|---|
| 배민 | 라이브 브랜드관 오퍼 66곳 × 42초 | 46분 |
| 땡겨요 | 목록 한 번 | 4분 |
| 요기요 | 목록과 시트 | 10분 |
| 쿠팡이츠 | 허브 한 번 | 5분 |
| 배너 | 7장 × 25초 | 3분 |
| 합 | | **약 68분** |

예약 실행이 폰을 쓰는 시간: 00:01 약 100분, 10:55와 15:55 각 30분. 남는 시간에 넣으면 하루 세 바퀴(03:30, 13:00, 18:30 안팎)가 상한이다. 폰 가동은 하루 8~9시간이 된다. 두 번째 폰이 있으면 이 봇을 전담시켜 2시간 주기로 상시 돌릴 수 있다(설계 32의 조율기가 앱 단위로 폰을 나눈다).

## 5. 보는 곳과 알림

- 콘솔 데이터 탭: 마지막 확인 시각, 확인됨/바뀜/사라짐/못 엶 건수, 오퍼별 마지막 확인 시각(`data/verified.jsonl`을 서버 `ops_collect.py`가 읽는다).
- 슬랙: 사라짐이나 바뀜이 있을 때만 요약 한 통(예약 실행의 완료 문장과 같은 문체).
- 8단계 보고서와 같은 모양의 `reports/verify-<날짜>.md`.

## 6. 하지 않는 것

- 쿠폰 받기(클릭)는 하지 않는다. 읽기만. 받기는 예약 실행 3단계가 한다.
- 예약 실행과 같은 시각에 돌지 않는다. 조율기(`run_routine.py`)의 기기 잠금을 같이 쓴다.
- 사람이 손으로 넣은 오퍼(`capture_mode: manual`)는 8단계와 같은 규칙으로 보류한다.

## 7. 결정이 필요한 것

1. 주기: 폰 하나로 하루 세 바퀴인가, 두 번째 폰 상시인가.
2. 사라짐을 승인 없이 내리는가(추천), 배너처럼 콘솔 승인을 거치는가.
3. 배민 브랜드관의 주기 스킵을 이 봇이 대신하면 4a를 월요일 전수만 남길지.
