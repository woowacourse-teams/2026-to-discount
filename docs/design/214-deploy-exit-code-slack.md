# 214. 배포 결과를 종료 코드별 슬랙 알림으로 보낸다 (2026-10-30 작성)

운영 배포가 끝나면 종료 코드(0~3)에 맞는 문구가 슬랙으로 간다. 성공도 알린다. 문구와 코드의 대응은 mono의 파이썬 스크립트 하나에 두고 시험으로 박는다. 미러 저장소 `deploy.yml`은 그 스크립트를 부르기만 한다.

용어를 먼저 풀어 둔다.

- 종료 코드: `api/deploy/prod/stage_deploy.py`가 끝날 때 남기는 숫자다. 0 성공, 1 임시 인스턴스 안 뜸, 2 이전 jar로 복구, 3 수동 확인.
- 미러 저장소: mono의 `api/`를 옮겨 싣고 운영 배포를 돌리는 `nn98/delivery-discount-api`다.
- 단계(step): GitHub Actions 작업 안의 한 칸이다. `if:` 조건으로 돌지 말지 정한다.

## 이 문서에서 확인한 것과 못 한 것

- 확인함: 종료 코드 정의(`stage_deploy.py` 25~29줄), 설계 188의 배포 순서와 종료 코드 설명, `mirror-deploy-repos.yml`이 `.github/`를 미러에서 제외함(85~86줄), `check-api.yml`이 `deploy/prod`의 `test_*.py`를 돌림(36줄).
- 못 봄: 미러 `deploy.yml`의 현재 내용. 이 저장소에 없고 이 세션은 미러를 읽지 못했다. 현재 실패 알림 단계의 이름, 조건, 슬랙으로 보내는 방식, 지금 문구("GitHub Actions 실패") 전체는 구현자가 미러에서 읽어 확인한다. 아래 YAML은 구조 스케치이고 그대로 붙이는 파일이 아니다.

## 배경

- 성공 알림이 없다. 배포가 이틀에 8번 나갔는데(설계 188) 성공은 어디에도 안 남는다. 슬랙이 조용하면 "성공"인지 "알림 자체가 안 감"인지 구분되지 않는다.
- 실패 문구가 하나라 코드 1, 2, 3이 구분되지 않는다. 운영 상태가 셋 다 다르다.
  - 1: 본 인스턴스 그대로. 급하지 않다.
  - 2: 옛 버전이 정상 운영 중. 새 버전이 안 뜬 원인을 봐야 한다.
  - 3: 임시 인스턴스가 켜진 채일 수 있다. 바로 사람이 봐야 한다.

## 결정

| 결정 | 선택 | 버린 대안 | 이유 |
| --- | --- | --- | --- |
| 코드와 문구의 대응을 두는 곳 | `api/deploy/prod/deploy_message.py` (mono, 미러로 따라간다) | `deploy.yml` 안에 `case` 문 | 미러 `deploy.yml`은 mono 시험이 닿지 않는다. 스크립트로 빼면 `check-api.yml`이 이미 `deploy/prod`의 시험을 돈다 |
| 종료 코드를 알림 단계로 넘기는 법 | 배포 단계가 코드를 `$GITHUB_OUTPUT`의 `code`로 적고 0으로 끝낸다. 알림 단계가 읽고, 마지막 단계가 코드가 0이 아니면 작업을 실패시킨다 | 배포 단계를 실패시키고 알림 단계에서 `if: failure()`로 코드를 찾음 | 실패한 단계의 종료 코드는 뒤 단계에서 읽을 수 없다. 코드를 적어 두는 수밖에 없다 |
| 알림 한 건 보장 | 기존 실패 알림은 `steps.deploy.outputs.code == ''`일 때만 돈다 | 두 알림이 다 돌게 두고 문구로 구분 | 코드가 적혔으면 종료 코드 알림이, 안 적혔으면(빌드 실패 등) 기존 알림이 간다. 조건이 서로 배타라 한 실패에 알림이 둘 가지 않는다 |
| 0~3 밖의 코드 | 기존 실패 문구를 쓴다 | 새 문구 | 문구는 사용자 확인 없이 바꾸지 않는다. 새 문구를 만들지 않는다 |
| 알림 실패 | 알림 단계가 실패해도 배포 결과는 안 바뀐다(`continue-on-error`) | 알림 실패로 작업 실패 | 알림이 안 갔다고 이미 끝난 배포를 실패로 보이게 하면 틀린 신호가 된다. 단계에 경고가 남는다 |

### 문구 (사용자 확정 2026-10-30, 변경 금지)

| 종료 코드 | 문구 |
| --- | --- |
| 0 | 정상적으로 배포가 완료되었습니다 |
| 1 | 임시 인스턴스가 구동 실패했습니다 |
| 2 | 배포 중 예외가 발생해 이전 버전으로 복구됐습니다 |
| 3 | 오류가 발생했습니다. 직접 확인이 필요합니다 |

각 알림은 문구 아래에 저장소, 커밋 7자리, 실행 주소를 붙인다. 항목 이름(`저장소`, `커밋`, `실행`)과 줄 모양은 이 문서가 정한다. 운영자만 읽는 슬랙 글이라 화면 문구 규칙(`docs/COPY-STYLE.md`)의 대상은 아니라고 보지만, 항목 이름이 마음에 안 들면 구현 전에 알려 달라.

```text
정상적으로 배포가 완료되었습니다
저장소: nn98/delivery-discount-api
커밋: 3936a03
실행: https://github.com/nn98/delivery-discount-api/actions/runs/<번호>
```

## 구현

### 1. 스크립트와 시험 (mono, `api/deploy/prod/`)

`deploy_message.py`

- `MESSAGES`: 종료 코드를 키로, 위 문구를 값으로 가진 딕셔너리.
- `build(code, repo, sha, run_url) -> str | None`: 코드가 `MESSAGES`에 없으면 `None`. 있으면 문구와 세 줄을 붙여 돌려준다. 커밋은 `sha[:7]`.
- 명령줄: `python3 deploy_message.py <code> <repo> <sha> <run_url>`. 문구를 표준 출력에 찍는다. `None`이면 아무것도 안 찍고 종료 코드 3이 아닌 별도 값(10)으로 끝낸다. 호출한 쪽이 "기존 문구로 가라"를 판단하는 신호다.
- 정수가 아닌 코드가 들어와도 같은 길(`None`)로 간다. 예외로 죽으면 알림이 통째로 사라진다.

`test_deploy_message.py` (`check-api.yml`의 기존 `unittest discover -s deploy/prod`가 돈다. 새 CI 단계는 필요 없다)

- 0~3 각각이 위 문구 표와 글자 그대로 같은가. 문구가 바뀌면 깨진다.
- 문구 아래에 저장소, 7자리 커밋, 실행 주소가 붙는가. 40자리 sha를 줘서 7자리로 잘리는지도 본다.
- `MESSAGES`의 키 집합이 `stage_deploy.py`의 `OK, STAGE_FAILED, ROLLED_BACK, NEEDS_HUMAN`과 같은가. 한쪽이 코드를 더하거나 바꾸면 깨진다(값의 커네선스를 시험으로 묶는다).
- 4, 255, `-1`, 빈 문자열, `abc`가 `None`인가. "대응이 없는 코드가 조용히 성공 문구가 되지 않는다"를 박는다.
- 명령줄 진입점이 `None`일 때 표준 출력이 비고 종료 코드가 10인가.

### 2. 미러 `deploy.yml` (직접 커밋, mono 밖)

구조 스케치. 단계 이름과 슬랙 호출 방식은 현재 파일에서 가져온다.

```yaml
- name: Deploy (임시 인스턴스 교대, 무중단)
  id: deploy
  run: |
    set +e
    python3 deploy/prod/stage_deploy.py "$JAR"
    echo "code=$?" >> "$GITHUB_OUTPUT"
    exit 0

- name: 배포 결과 알림
  if: always() && steps.deploy.outputs.code != ''
  continue-on-error: true
  run: |
    TEXT=$(python3 deploy/prod/deploy_message.py "${{ steps.deploy.outputs.code }}" "$GITHUB_REPOSITORY" "$GITHUB_SHA" "$RUN_URL") || TEXT=""
    # TEXT가 비면 기존 실패 문구(지금 파일의 것)를 쓴다
    # 슬랙 전송은 지금 실패 알림 단계와 같은 방식으로

- name: 배포 실패면 작업 실패
  if: steps.deploy.outputs.code != '' && steps.deploy.outputs.code != '0'
  run: exit ${{ steps.deploy.outputs.code }}

- name: (기존) 실패 알림
  if: failure() && steps.deploy.outputs.code == ''
```

- 배포 단계가 `exit 0`으로 끝나므로 뒤 단계가 일반 흐름으로 돈다. `set +e`는 필수다. 기본 셸은 `-e`라서 코드가 0이 아니면 `echo`까지 못 간다.
- 알림 단계에서 스크립트가 `None`을 돌려주면(0~3 밖) 기존 실패 문구를 보낸다. 이때도 알림은 한 건이다.
- 스크립트를 `deploy.yml`이 `deploy/prod/`에서 읽으려면 작업 폴더가 `api/` 내용인 미러 루트여야 한다. `stage_deploy.py`를 지금 부르는 경로와 같은 기준으로 맞춘다.
- 코드가 `$GITHUB_OUTPUT`에 안 적히는 경우(빌드 실패, 러너 중단, 파이썬 자체가 못 뜸)는 `code`가 비어 기존 알림으로 간다. 이 경로가 "종료 코드 밖의 실패"다.

## 변경 전파 (묶음 8)

`docs/CHANGE-PROPAGATION.md` 묶음 8은 "mono/api → 미러"를 main 푸시 시 미러로 적는다. 미러 `deploy.yml`은 이 흐름 밖이다.

| 자리 | 파일 | 이번 작업 |
| --- | --- | --- |
| 종료 코드 정의 | mono `api/deploy/prod/stage_deploy.py` | 바꾸지 않음 |
| 코드와 문구 대응 | mono `api/deploy/prod/deploy_message.py` (새 파일) | 추가. 키 집합이 정의와 같은지 시험이 대조 |
| 알림 호출 | 미러 `.github/workflows/deploy.yml` | 직접 커밋. mono PR로는 안 닿음 |
| 설명 | mono `api/deploy/prod/README.md`, 설계 188 | README에 알림 절 추가. 188은 승인 뒤 고치지 않는 규칙이라 그대로 둠 |

- **끊기면 무엇이 보이나**: 스크립트만 병합하고 미러 `deploy.yml`을 안 고치면 알림은 그대로다. 시험은 초록이고 슬랙은 여전히 "GitHub Actions 실패" 하나다. 반대로 `deploy.yml`만 고치고 스크립트 병합 전이면 미러에 `deploy_message.py`가 없어 알림 단계가 실패한다. `continue-on-error`로 배포는 지켜지지만 알림이 한 건도 안 간다. 순서는 **mono PR 병합 → 미러 반영 확인 → 미러 `deploy.yml` 커밋**.
- **종료 코드가 늘면**: `stage_deploy.py`에 코드를 더하면 `test_deploy_message.py`의 키 집합 시험이 깨진다. 그때 문구를 사용자에게 묻는다. 시험이 없으면 새 코드가 기존 실패 문구로 조용히 떨어진다.
- 새 파일이므로 `python scripts/generate_project_structure.py`로 `docs/PROJECT-STRUCTURE.md`를 다시 만든다(묶음 9).
- `docs/CHANGE-PROPAGATION.md` 묶음 8 표에 "배포 알림 문구 ↔ `stage_deploy.py` 종료 코드 ↔ 미러 `deploy.yml`" 줄을 더한다. 미러 쪽은 시험이 못 닿는다고 적는다.

## 알려진 한계 (문구는 못 바꾸므로 사용자에게 알린다)

- 종료 코드 1은 임시 인스턴스 안 뜸 말고도 나온다. "다른 배포가 돌고 있다"(잠금 충돌), jar 파일이 없음, 파이썬 예외 종료(기본 종료 코드 1)다. 이때 "임시 인스턴스가 구동 실패했습니다"는 틀린 문구가 된다.
- 종료 코드 2는 `argparse`(명령줄 인자 해석기)의 사용법 오류도 2다. 인자가 빠진 호출이 "이전 버전으로 복구됐습니다"로 알려지면 실제로는 아무것도 배포되지 않았는데 복구됐다고 말하게 된다. `deploy.yml`이 인자를 고정해 부르므로 가능성은 낮지만 없지는 않다.
- 종료 코드 3은 "복구도 실패"와 "배포는 됐는데 임시 인스턴스를 못 내림" 두 경우를 함께 가진다. "직접 확인이 필요합니다"는 둘 다에 맞는다.
- 1과 2의 겹침은 `stage_deploy.py`가 사용법 오류와 잠금 충돌에 다른 코드를 주도록 고치면 풀린다. 이번 범위 밖이고 문구도 건드리지 않는다. 후속으로 둘지 사용자가 정한다.

## 완료 조건과 확인 계획

| 조건 | 어떻게 확인하나 | 누가 |
| --- | --- | --- |
| 종료 코드와 문구 대응 시험 | `python3 -m unittest discover -s deploy/prod -p 'test_*.py'` (`api/`에서) | API 구현자 |
| 성공 배포 한 건의 알림이 슬랙에 옴 | 미러 `deploy.yml` 커밋이 일으키는 배포 한 건의 실행 번호, 슬랙 글 확인, 이슈 댓글에 남김 | 사용자(슬랙 확인) |
| 자동 복구(종료 코드 2) 알림 확인 | **운영에서 일부러 실패를 만들지 않는다.** 아래 | 해당 없음 |

**종료 코드 2를 운영에서 일으키지 않는 이유.** 설계 188에서 2026-10-29 17:28에 한 번 일으켜 자동 복구가 요청 실패 0건으로 끝나는 것을 확인했다. 그 경로는 이미 검증했다. 이번에 새로 확인할 것은 "2번이 문구 2번으로 간다"뿐이고, 그것은 시험(대응표)이 박는다. 운영에서 다시 하면 시험용 커밋 둘(실패 클래스와 되돌림)이 배포 세 번을 만들고 15분 동안 부하를 보내야 한다. 얻는 것은 "알림 단계가 코드 2를 받아 슬랙으로 보낸다"는 배선 확인 하나다.

배선은 운영 실패 없이 확인할 수 있다. 미러에서 `workflow_dispatch`가 켜져 있다(설계 188). 대신 구현자가 둘 중 하나를 쓴다.

1. 성공 배포 한 건으로 0번 경로를 확인한다. 알림 단계는 코드 값만 다르고 같은 단계를 지나므로 같은 배선을 증명한다.
2. 단계의 `run` 안 스크립트 호출을 시험 슬랙 채널이나 표준 출력으로 돌려, 코드 1, 2, 3을 손으로 넣은 출력(`echo "code=2"`)으로 알림 단계만 돌려 본다. 운영에 영향이 없다.

이 선택은 배선만 증명하고, "배포 스크립트가 실제로 2를 내는 순간 단계가 코드를 받는다"는 증명하지 못한다. 후자는 `set +e`와 `$?` 한 줄이라 설계 188의 실제 복구 기록(종료 코드 2에서 실패 알림이 나감)에 기대어 생략하는 선택이다. 이를 뒤집고 운영에서 직접 2를 일으키려면 사용자가 정한다. 운영 실패를 만드는 일이라 세션이 정하지 않는다.

## 배포 주의

- 미러 `deploy.yml`을 push하면 그 푸시로 운영 배포가 한 번 돈다(같은 코드 재배포). 이 배포가 성공 알림 확인용 한 건이 된다.
- 푸시 요약 시간대 11:00~11:35 KST와 수집 시각 00:01, 08:30, 15:55를 피한다. 스크립트는 11시대에 11:35까지 기다리므로(`stage_deploy.py`의 창 대기) 겹치면 알림도 그만큼 늦는다.
- 미러에 직접 넣은 변경은 다음 mono 미러에 덮인다(`mirror-deploy-repos.yml`). `.github/`는 `--exclude`라 `deploy.yml`은 안 덮인다. `deploy_message.py`는 `api/deploy/prod/`에 있으니 mono에서 오면 덮이지 않고 그대로 따라온다.
- 되돌림: 미러에서 `deploy.yml` 커밋을 `git revert`한다. 알림이 옛 모양(실패만)으로 돌아간다. 스크립트는 남아도 무해하다.
