# 설계 문서 목록과 상태

문서 종류는 셋이고 역할이 다르다.

| 종류 | 자리 | 무엇 | 언제 쓰나 |
|---|---|---|---|
| **설계(design)** | `docs/design/N-*.md` | 문제·대안·선택·근거. "무엇을 왜" | 결정 전. 브레인스토밍 산출물 |
| **계획(plan)** | `docs/superpowers/plans/YYYY-MM-DD-*.md` | 순서 있는 작업 목록(체크박스), 파일·테스트·검증 | 설계가 승인된 뒤. 이걸 보고 구현한다 |
| **결정(ADR)** | 트래커 `docs/decisions/ADR-NNN-*.md` | 이미 정한 것과 그 이유 | 구현이 끝나 규칙이 된 뒤 |

설계는 "할지 말지·어떻게 할지"를 고르는 문서라 투두가 아니다. 승인되면 계획으로
옮기고(`writing-plans`), 계획은 체크박스로 진행을 적는다. 설계 문서 자체는 승인 뒤
고치지 않는다 — 결과는 ADR과 계획에 남긴다. 다만 문서가 적은 배포 경로나 파일 자리가
없어지면 머리에 갱신 줄을 달고 그 줄만 고친다(2026-09-29, 22·27·32·35). 도입하지 않고
접은 설계와 끝난 계획은 지운다. git 이력에 남는다. 다만 일부가 나중에 다시 쓰일 수 있는 설계는
`../archive/design/`로 옮기고 머리에 무엇이 대체됐고 무엇이 남았는지 적는다(2026-09-29, 28·29·30).

문서 번호는 GitHub 이슈 번호와 같다. 설계 하나를 시작하면 이슈를 먼저 열고 그 번호로 파일을 만든다. 2026-09-17에 21~27로 매긴 문서 일곱 개는 이슈 번호와 어긋나 있었는데(그 사이 PR 번호가 앞서 나갔다), 2026-09-18에 이슈 번호 27~33으로 파일 이름과 제목을 바꿨다. 상태 변화와 논의는 이슈에, 결정과 근거는 문서에 적는다.
