# 146. iOS 스크린샷 검사: 운영 데이터 장면과 카테고리·스크롤 장면 추가

추적 이슈: [#146](https://github.com/woowacourse-teams/2026-to-discount/issues/146)

## 결론

고정 데이터는 그대로 두고 그 옆에 운영 데이터 장면을 더한다. 고정 데이터 갱신 PR(후보 1)은 하지 않는다.

- `ios-shot`의 local 모드가 찍기 직전에 운영 API 응답(`/api/brands`, `/api/banners`)을 받아 러너에 저장한다. 가짜 API(`layout-report.py serve`)는 고정 응답과 운영 응답을 둘 다 들고, 장면 사이에 러너가 어느 쪽을 줄지 바꾼다.
- 기존 장면 셋(`expect=carousel`, `sheet=KFC`, `home=old`)은 고정 데이터로 남는다. 넘김 카드가 맨 위에 있어야 하는 판정은 운영 데이터로 못 한다.
- 새 장면 셋은 운영 데이터로 찍는다: 첫 화면, 다른 카테고리, 첫 화면 맨 아래까지 스크롤. 카테고리 전환과 스크롤은 `layout-check.js`가 주소 파라미터(`tab`, `scroll`)를 읽어 자바스크립트로 한다.
- 데이터 날짜는 `shots/index.txt`에 장면마다 적는다. 운영 응답을 못 받았거나 비었으면 고정 데이터로 조용히 대체하지 않고 실패로 끝낸다.
- 결과 댓글의 스크린샷 링크 형식은 바꾸지 않는다.

## 배경

현재 구조는 이슈가 적은 대로다. 확인한 것만 적는다.

- 검사용 빌드는 `VITE_API_BASE_URL=http://localhost:8099`로 가짜 API를 부른다(`ios-shot.yml` 53행). 응답은 `web/scripts/dev/fixtures/brands.json`(브랜드 18곳), `banners.json`(배너 3장)이고 `layout-report.py`의 `GET` 표(18행)가 읽는다.
- `banners.json`의 배너는 모두 2026-10-15 하루짜리(`endsAt` 10-15, 10-31)라 화면에 낡은 오퍼가 보인다. 이슈가 말한 "10-15쯤 화면"과 맞다.
- 고정 데이터를 쓴 이유는 `layout-report.py` 머리 주석에 있다. 운영 데이터는 날마다 바뀌어 넘김(동점 최고) 카드가 첫 화면에 없는 날 검사가 헛돌았다(2026-10-15). 그래서 `layout-check.js`의 `?expect=carousel`, `?sheet=KFC`는 고정 데이터에 푸라닭(넘김 카드), KFC·두찜(선착순 구간)이 있다는 전제에 기대고 있다.
- 지금 찍는 것은 장면당 주소 하나다. 열고 20초 뒤 캡처한다(`ios-shot.yml` 89~90행). 스크롤도 탭도 없다.
- 카테고리는 주소로 못 고른다. `App.jsx`의 주소 파라미터는 `photo`, `compact`, `guide`, 해시(`#brand-…`)뿐이고, 카테고리는 상태(`filters.categories`)이며 분류 바(`MenuBar.jsx`)의 버튼 `onClick`으로만 바뀐다. 스크롤을 주소로 하는 방법도 없다(해시는 카드 하나로 가는 용도).
- 목록은 한 번에 다 그리지 않는다(`App.jsx` 453~492행). 첫 묶음 뒤에는 목록 끝 표지가 화면 아래 1,500px 안에 들어올 때 한 묶음씩 더한다. 그래서 "맨 아래"는 한 번 `scrollTo`로 닿지 않는다.

## 확인한 것

- 운영 API 주소는 `web/src/apiBase.js`의 `PRODUCTION_API`(`https://bebeggars.duckdns.org`)다. 읽기 요청이라 비밀값이 필요 없다. 구현자는 이 상수를 워크플로에 옮겨 적지 말고 파일에서 읽어 쓴다(주소가 두 곳에 적히면 값의 커네선스).
- `ios-shot.yml`의 local 모드는 `pull_request`(web을 고친 PR)와 수동 실행에서만 돈다. 운영 데이터를 받는 단계도 같은 조건에 건다. main 배포 뒤 운영 주소를 찍는 경로(`workflow_run`)는 원래 운영 데이터를 보므로 건드리지 않는다.
- 고정 데이터의 분류는 chicken, fastfood, convenience, cafe, pizza다. 분류 바의 분류 목록(`CATEGORIES`, `filters.js`)과 같은지는 이번에 확인하지 않았다. 분류 바 버튼은 분류 키를 속성으로 들고 있지 않고 글자(라벨)만 있다.
- `layout-check.js`는 빌드한 `index.html`에만 들어가고 운영 빌드에는 없다. 여기에 장면 동작을 넣어도 운영 번들은 달라지지 않는다.

## 대안

### 데이터를 어떻게 최신으로 하나

| 안 | 내용 | 평가 |
| --- | --- | --- |
| 1. 주기 갱신 PR | 운영 응답을 받아 fixtures를 고치는 PR을 주기적으로 연다. 사람이 확인하고 병합 | 고정 데이터 성질은 유지한다. 그러나 새 자동화(스케줄, PR 생성, 병합 승인)가 필요하고, 병합 전까지는 다시 낡는다. 낡음을 없애는 것이 아니라 주기를 줄일 뿐이다. 받은 응답을 넘김 카드가 맨 위에 오도록 잘라 붙이는 일은 사람 손이 든다 |
| 2. 찍을 때 운영 응답 | 찍기 직전에 운영 응답을 받아 쓴다. 판정용은 고정 유지 | 선택. 낡음이 구조상 없다. 판정 장면이 운영 데이터에 흔들리지 않게 장면별로 데이터를 가른다 |
| 3. 전부 운영 응답 | 고정 데이터를 없앤다 | 2026-10-15에 겪은 헛돎(넘김 카드가 첫 화면에 없음)이 돌아온다. 하지 않는다 |

2안의 약점은 운영 API가 죽었거나 비었을 때다. 이때 고정 데이터로 대체하면 사진은 나오지만 최신이 아닌데 최신처럼 보인다. 그래서 대체하지 않고 실패로 끝낸다(AGENTS.md "먼저 알 것" 1번: 못 본 것을 본 것처럼 내지 않는다).

### 카테고리 전환과 스크롤을 어떻게 하나

| 안 | 내용 | 평가 |
| --- | --- | --- |
| 주소 앵커 | `#…`로 이동 | 카테고리는 상태라 해시로 못 바꾼다. 해시는 카드 하나로 가는 용도라 의미도 다르다. 하지 않는다 |
| 쿼리 파라미터를 앱이 읽음 | `?cat=chicken`을 앱 코드가 읽어 초기 필터로 | 운영 앱에 검사용 입구를 만든다. 이 검사 하나를 위해 제품 코드를 바꾸는 것이라 하지 않는다 |
| 자바스크립트 주입 | 검사용 스크립트가 분류 버튼을 `click()`하고 `scrollTo` | 선택. `layout-check.js`가 이미 `?sheet=`로 카드의 "자세히"를 `click()`한다. 같은 방식이고 운영 번들은 그대로다 |
| `simctl`로 터치 | 시뮬레이터에 좌표 터치를 보냄 | `xcrun simctl`에는 터치·스와이프 명령이 없다(`io`는 화면 캡처·녹화용). 별도 도구가 필요해 하지 않는다 |

## 변경

### 워크플로: `.github/workflows/ios-shot.yml`

1. **운영 응답 받기 단계 추가**(local일 때, "이 브랜치 web 띄우기" 뒤, "시뮬레이터 켜기" 앞).
   - `curl -sf`로 `/api/brands`, `/api/banners`를 `$RUNNER_TEMP/live/`에 저장한다. 실패하면 단계가 실패한다.
   - 양성 신호 확인: `brands`가 JSON 배열이고 길이가 1 이상, 각 브랜드에 오퍼가 있는 브랜드가 하나 이상. 못 넘으면 실패(빈 배열을 "정상"으로 보지 않는다).
   - 받은 시각(UTC, 날짜)을 `LIVE_AT` 환경변수로 남긴다.
2. **가짜 API에 운영 응답 폴더 전달**: `layout-report.py serve "$RUNNER_TEMP/reports" --live "$RUNNER_TEMP/live"`.
3. **장면 목록 확장**: 기본 `paths`에 운영 데이터 장면 셋을 더한다. 장면마다 데이터 종류를 주소 밖에서 정해야 하므로 `paths` 항목 앞에 `live:`를 붙이는 표기를 쓴다.
   - 기본값: `/?home=a&expect=carousel /?home=a&sheet=KFC /?home=old live:/?home=a live:/?home=a&tab=1 live:/?home=a&scroll=end`
   - 첫 화면은 `home=a`를 유지한다. 이슈가 말한 "첫 화면"과 기존 `home=a` 장면의 운영 데이터판이다.
   - `live:` 접두사는 주소를 만드는 반복문(60~61행)에서 떼어 낸다. 접두사를 못 떼면 주소가 깨지므로 `case "$p" in live:*)`로 가른다.
4. **찍기 반복문**: 장면을 열기 전에 `curl -sf -X POST "localhost:8099/data?set=live|fixture"`로 가짜 API의 데이터를 바꾼다. 응답이 204가 아니면 그 장면을 실패로 센다. `index.txt`에는 `<번호> <주소> data=<fixture|live> at=<날짜>`로 적는다.
   - `fixture`의 `at`은 `fixtures/` 폴더가 마지막으로 바뀐 날이 아니라 `fixtures/DATE`(새 파일, 한 줄 `2026-10-16`)에서 읽는다. 사람이 고정 데이터를 고칠 때 같이 고친다. 이 값이 있어야 사진에 "고정 데이터, 10-16"이 남는다.
   - `live`의 `at`은 1단계의 `LIVE_AT`.
   - `index.txt` 줄은 `layout-report.py summary`가 공백 한 번 기준으로 주소를 자른다(`line.split(" ", 1)[1]`). 주소 뒤에 덧붙이면 `expected` 주소 비교가 깨진다. 아래 "요약기" 항목을 같이 고친다.
5. **인터랙션 대기**: 스크롤 장면은 목록을 더 채워야 하므로 지금의 20초 뒤 캡처를 늘리지 않고 `layout-check.js`가 끝났다고 알린 뒤 찍는다(아래 "검사 스크립트"). 구현자는 러너가 보고를 기다릴 수 있는 방법(`report` 폴더에 해당 주소의 보고가 생길 때까지 최대 40초 폴링)을 쓰되, 안 오면 그 장면은 기존처럼 20초 뒤 찍고 요약기가 "보고 없음"으로 실패시킨다.

### 가짜 API: `web/scripts/dev/layout-report.py`

- `serve`가 `--live <폴더>`를 받는다. 폴더가 있으면 `/api/brands`, `/api/banners`를 그 폴더의 `brands.json`, `banners.json`으로 줄 수 있다.
- 현재 데이터 종류는 메모리 상태 하나다. 기본은 `fixture`. `POST /data?set=live`는 `--live`가 주어졌고 두 파일이 있을 때만 바꾸고 204, 아니면 409를 돌려준다(`live`를 달라는데 없으면 고정 데이터를 주지 않는다).
- 상태 바뀜은 한 번에 한 장면만 열리는 순차 찍기에 기댄다. 장면들이 병렬이 되면 깨지므로 머리 주석에 쓴다.
- 요약기(`summary`): `index.txt` 줄에서 주소만 뽑아 비교하고(`data=` 앞까지), 요약 줄에 `data=live at=2026-10-22`를 표시한다. 마크다운 요약 맨 위에 "운영 데이터 받은 시각"과 "고정 데이터 기준일"을 한 줄씩 적는다. 이것이 이슈의 "날짜 표시로 확인"이다.
- 보고(`/report`)에 `live`가 있으면 `scene` 정보(아래)를 요약에 함께 적는다.

### 검사 스크립트: `web/scripts/dev/layout-check.js`

주소 파라미터 둘을 더한다. 두 파라미터는 `?sheet=`처럼 카드가 뜬 뒤(`ready`)에 동작하고, 측정은 그 뒤 3초에 한다.

- `?tab=<n>`: `.menu-bar__item` 목록에서 `n`번째(0이 "전체") 버튼을 `click()`한다. 문구가 아니라 위치로 고른다(앱 문구는 바뀐다).
  - 누르기 전 카드 이름 목록(`article[data-brand]`의 `data-brand`)을 저장한다.
  - 누른 뒤 1초 안에 `aria-pressed="true"`가 되고, 카드가 1장 이상이며, 카드 이름 목록이 달라졌는지를 본다. 하나라도 아니면 실패: `다른 카테고리 장면이 전환되지 않았다(검사 대상 없음)`.
  - 어느 분류가 눌렸는지 보고에 `scene.tab = { index, pressedText }`로 남긴다. 사진 아래 상자에도 적는다(문구는 판정에 쓰지 않고 사람이 읽는 용도).
  - 1번 분류에 카드가 없는 날은 실패다. 운영 분류 중 맨 앞이 비는 일은 드물다고 보지만 확인하지 않았다. 열린 질문 2번.
- `?scroll=end`: 목록 끝까지 반복해서 내린다.
  - 150ms 간격으로 `scrollTo(0, document.documentElement.scrollHeight)`를 하고, `scrollHeight`가 연속 5번(약 750ms) 같아지면 멈춘다. 최대 15초.
  - 멈춘 뒤 `scrollY + innerHeight >= scrollHeight - 2`이면 맨 아래에 닿은 것이다. 못 닿았거나 15초를 넘기면 실패: `맨 아래까지 못 갔다`.
  - 보고에 `scene.scroll = { y, height, steps }`를 남긴다. `height`가 첫 화면 높이(`innerHeight`)보다 커야 스크롤이 있는 장면이라는 양성 신호다. 아니면 실패(내릴 것이 없으면 이 장면이 의미 없다).
  - 앱의 "맨 위로" 버튼(`scrolledFar`)이 400px 넘게 내려가면 뜬다. 사진에 보이는 것이 정상이다.
- 기존 판정(가로 넘침, 카드 폭, 금액 겹침 등)은 두 장면에서도 그대로 돈다. 아래로 내린 장면에서는 `top < innerHeight`로 거르는 기존 규칙이 화면 위로 지나간 카드를 빼는데, 이는 "화면에 보이는 카드"만 보는 기존 의도와 같아 건드리지 않는다.
- `expect=carousel`은 운영 데이터 장면에 붙이지 않는다. 운영 장면은 "카드가 0장"과 가로 넘침 같은 구조 판정만 진다.

### 새 파일

- `web/scripts/dev/fixtures/DATE`: 고정 데이터 기준일 한 줄. `ios-shot.yml`이 읽는다. 고정 데이터를 바꾸는 사람이 같이 고친다는 규칙은 `web/scripts/dev/README.md`에 한 줄로 적는다.
- 테스트는 아래 "테스트".

## 어디까지 번지나

`docs/CHANGE-PROPAGATION.md` 표에 이 변경이 직접 걸리는 묶음은 없다. 가짜 API는 화면 모양을 흉내 내는 시험 도구이고 표의 묶음(확실성, 배너 모양 등)의 구현 쪽이 아니다. 다만 가까운 묶음 둘을 적는다.

- **배너 모양(2번)**: `fixtures/banners.json`이 배너 칸 이름(`firstCome`, `amountSpec` 등)을 흉내 낸다. 이번에는 운영 응답을 그대로 줘서 오히려 최신 모양을 본다. 운영 응답에 새 칸이 생겨도 가짜 API가 걸러내지 않는다. 고정 데이터 쪽은 낡은 칸 이름을 그대로 둔다. 이번에 고정 데이터를 갱신하지 않는 이유 중 하나이고, 낡은 모양은 기존 장면에서만 쓰인다.
- **배포 순서(8번)**: 이 검사는 PR 브랜치 web을 운영 API(이미 배포된 것)에 맞대어 보게 된다. API를 먼저 올리고 웹을 나중에 올리는 순서 그대로이므로 순서 위반은 아니다. 반대로 API를 바꾸는 PR이 병합 전이면 이 검사는 옛 API 응답으로 새 웹을 본다. API와 웹을 함께 바꾸는 PR은 이 장면이 거짓으로 통과/실패할 수 있다. 문서(`web/scripts/dev/README.md`)에 한 줄 적는다.
- **새 파일(9번)**: `web/src/*.test.js`는 새로 만들지 않는다. `fixtures/DATE`는 `web/` 아래 새 파일이라 `docs/PROJECT-STRUCTURE.md`를 다시 만들어야 한다(`python scripts/generate_project_structure.py`). 푸시 훅이 막으므로 구현자는 잊지 않는다.
- 같은 묶음이 아니라 같은 워크플로를 건드리는 다른 일: `ios-shot.yml`의 `workflow_run`(main 배포 뒤 운영 찍기) 경로는 `URLS` 기본값을 쓰고 이번 변경에서 값이 안 바뀐다. 구현자가 `if: env.LOCAL == 'true'` 조건을 새 단계에 빠뜨리면 이 경로에서 `$RUNNER_TEMP/live`가 없어 깨진다.

## 테스트

기존 테스트 인프라가 가짜 API용으로 없다(`layout-report.py`에 테스트 파일이 없음을 확인). 이번 변경에서 테스트로 박을 것:

- `web/scripts/dev/test_layout_report.py`(새 파일, 표준 라이브러리 `unittest`): 
  - `serve`를 임시 포트로 띄워 기본 상태에서 `/api/brands`가 고정 응답, `POST /data?set=live` 뒤 운영 응답을 주는지.
  - `--live` 없이 `set=live`를 요청하면 409이고 다음 `/api/brands`가 여전히 고정 응답인지(조용한 대체 금지).
  - `summary`가 `index.txt`의 `data=`, `at=` 덧붙임을 주소 비교에서 떼고, 보고가 없는 장면을 실패로 세는지. 날짜 줄이 요약 맨 위에 나오는지.
  - 포트 8099가 고정이라 테스트용으로 포트를 인자로 받게 `serve(out, port=8099)`로 바꾼다.
- 이 테스트를 어디서 돌리는지가 비어 있다. `web/package.json`의 `test` 사슬은 JS 전용이다. 구현자는 `.github/workflows/`에서 web을 고친 PR에 이미 도는 단계가 있는지 보고, 없으면 `ios-shot.yml`의 local 모드 "배치 검사 결과" 단계 앞에 `python3 -m unittest`를 한 줄 더한다(맥 러너에 파이썬 있음). AGENTS.md의 "안 넣으면 안 돌고, 안 도는 줄도 모른다" 때문에 이 줄이 빠지면 테스트는 장식이다.
- `layout-check.js`는 브라우저 안에서만 도는 코드라 단위 테스트가 없다. 대신 실제 판정은 `ios-shot` 실행이다. 구현 PR에서 수동 실행(`gh workflow run ios-shot.yml --ref <브랜치> -f local=true`)으로 확인하고 아티팩트를 본다.

## 구현 확인 목록

구현자는 PR에 아래를 그대로 증거로 남긴다.

1. 아티팩트 `ios-shots`에 장면 여섯(고정 셋, 운영 셋) 사진이 있고, `index.txt` 각 줄에 `data=`, `at=`이 있다.
2. 운영 장면 사진에 운영의 현재 오퍼가 보인다(예: 배너가 10-15가 아님). 눈으로 보고 PR에 날짜를 적는다.
3. 다른 카테고리 사진의 분류 바에서 "전체"가 아닌 버튼이 선택돼 있고 카드 목록이 첫 화면과 다르다.
4. 스크롤 사진이 목록 끝(바닥글 쪽)이고 "맨 위로" 버튼이 보인다.
5. 일부러 `PRODUCTION_API` 읽기를 틀린 주소로 바꿔 한 번 돌려, 운영 응답 받기 단계가 실패로 끝나고 고정 데이터로 대체되지 않는 것을 확인한다(양성 신호의 반대편). 이 임시 변경은 커밋하지 않는다.
6. `python3 -m unittest`가 CI에서 돈다(Actions 로그에 실행 줄이 보임).

## 위험

- 운영 데이터 장면이 PR과 무관한 이유로 실패할 수 있다(그날 운영 데이터에서만 나는 배치 깨짐). 운영에서도 사용자에게 보이는 깨짐이므로 실패로 잡는 쪽을 택한다. 반복해서 PR을 막으면 운영 장면의 실패를 경고로 낮춘다. 열린 질문 1번.
- 운영 API는 요청이 늘면 부담이다. PR 푸시마다 두 번(brands, banners) 받는다. `concurrency`가 앞 실행을 끊고 macOS 작업이 하나씩이라 요청량은 작다. 운영 API 부하 시험 문서(`docs/metrics/API-LOAD-TEST-20261014.md`)의 규모와 비교하지는 않았다.
- 분류 바 첫 분류 이름이 바뀌어도 위치로 고르므로 장면이 안 깨진다. 분류 바의 첫 버튼이 "전체"가 아니게 바뀌면 `tab=1`이 엉뚱한 분류가 된다. `TopBarB.jsx`의 `leading`(전체, 신규 자리)에 항목이 더해지면 `tab` 번호가 밀린다. 보고의 `pressedText`가 사진에 남아 사람이 알아본다. 자동으로 막지는 않는다.
- 맥 러너에서 사파리가 `localhost:8099`로 `POST`하는 CORS는 기존 `/report`와 같은 방식이라 문제가 없다. 러너의 `curl`은 CORS와 무관하다.

## 열린 질문

1. 운영 데이터 장면의 배치 판정 실패를 PR 실패로 둘지, 경고로만 남길지. 이 문서는 실패로 둔다.
2. "다른 카테고리"를 `tab=1`(분류 바의 첫 분류)로 고정해도 되는지. 특정 분류(예: 치킨)를 고르려면 라벨 글자로 골라야 하고 그 글자는 바뀐다.
3. 이슈의 "최근 일주일 안"은 운영 데이터 받은 날이 오늘이라 항상 만족한다. 일주일 기준이 필요한 것은 고정 데이터 장면뿐인데, 고정 장면 날짜를 일주일 넘으면 요약에 경고로 표시할지(실패는 아님).
