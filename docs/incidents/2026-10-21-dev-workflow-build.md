# 에이전트 개발 워크플로를 만들며 막힌 것 (2026-10-21 ~ 10-22)

**요약:** 이슈에서 병합까지를 에이전트 세션이 채우고 사람은 승인 댓글 두 번(`/approve-design`, `/approve`)만 다는 워크플로를 만들었다. 설계 단계만 시험 이슈 3개에서 9번 돌렸고, 이슈 #133 → PR #134에서 처음 끝까지 돌았다. 가장 큰 교훈은 세션의 "성공" 보고를 믿으면 안 된다는 것이다. 세션은 결과물이 하나도 없어도 성공을 보고했다. 그래서 완료 여부는 워크플로가 브랜치, PR, 인계 댓글을 직접 확인한다. 설계는 [`design/119-dev-workflow.md`](../design/119-dev-workflow.md), 실제로 바뀐 것과 그 근거는 [`design/119-dev-workflow-asbuilt.md`](../design/119-dev-workflow-asbuilt.md)에 있다. 이 문서는 그 사이의 시행착오를 사건마다 증상, 원인, 선택, 결과 순으로 적는다. 원인을 확인하지 못한 문장에는 "추정"을 붙였다.

## 어디서 막을지 정한 기준

| 조건 | 막는 자리 | 예 |
| --- | --- | --- |
| 워크플로 안에서 생기고 기계로 판정된다 | 워크플로 단계 | 결과물 확인 단계, 거부 내역 로그 |
| 세션의 명령 습관에서 생긴다 | 워크플로 프롬프트와 역할 파일 | 명령은 하나씩, 본문은 파일로 |
| 저장소 설정이 원인이다 | 저장소 설정(사람이 바꾼다) | main 보호 규칙, 워크플로 기본 권한 |
| 여러 세션에서 두 번 넘게 나오거나 규칙끼리 부딪친다 | 모든 로컬 세션에 걸리는 공통 규칙과 훅 | 경로 없는 커밋 차단 |

공통 규칙은 모든 세션에 걸려 비용이 크다. 한 번 나온 문제는 그 자리의 단계로 막고, 되풀이될 때만 올린다.

## 1단계: 설계 세션

### 결과물 0개인데 "성공" (3 ~ 4회차)

- **증상:** 3회차는 턴 상한 30을 넘겨 끝났고, 4회차는 16턴 만에 "성공"으로 끝났다. 4회차 설계 내용은 좋았다(대안 3개 비교, 영향 범위 분석). 그런데 둘 다 브랜치, 초안 PR, 인계 댓글이 없었다. 설계 문서는 실행 환경과 함께 사라졌다.
- **원인:** 세션 출력을 숨겨 둬서 처음에는 거부 횟수(3번)만 보였다. 실행 결과에서 거부된 명령만 뽑아 로그에 남기는 단계를 넣자 원인이 보였다.
  - push 허용 패턴 `git push -u origin feat/:*`가 `feat/` 바로 뒤에 붙는 브랜치 이름과 맞지 않았다.
  - `cd … && git checkout … && cat > …`처럼 묶은 명령은 허용 목록과 통째로 맞지 않았다.
- **더 큰 문제:** 결과물이 없는데 실행이 성공으로 끝나 실패 표시(`blocked` 라벨)도 붙지 않았다.
- **선택:**
  - push 허용을 브랜치 이름별 패턴 대신 `git push` 전체로 넓혔다. main은 저장소 보호 규칙이 막는다. 브랜치 이름은 세션이 정하므로 패턴을 정교하게 써도 다시 어긋난다.
  - 프롬프트에 "셸 명령은 하나씩, 파일은 Write 도구로"를 넣었다.
  - 설계 문서를 실행 결과물로 14일 보관한다. push가 실패해도 문서가 남는다.
  - **결과물 확인 단계:** 브랜치, PR, 인계 댓글 중 하나라도 없으면 실패로 처리한다.
- **결과:** 5회차에서 처음 끝까지 통과했다(29턴, 초안 PR #122).

### 여러 줄 본문 PR 생성 거부 (5회차)

- 줄바꿈이 많은 본문을 `--body "…"`로 넘긴 `gh pr create`가 한 번 거부됐다. 줄바꿈이 든 명령은 명령 단위 허용 목록과 맞지 않는 것으로 보인다(추정).
- 본문은 파일로 쓰고 `--body-file`로 넘기게 했다. 턴 상한은 시험 결과(29 ~ 34턴)에 맞춰 50으로 정했다.

### 셸을 얼마나 열 것인가

- 명령 모양마다 허용 규칙을 붙이는 방식이 무거워졌다. 셸 전체를 열고, 경계는 실행 환경(작업마다 버려지는 가상 머신, 저장소 한정 토큰, main 보호 규칙)으로 삼는 안을 냈다.
- 에이전트 권한을 에이전트가 넓히는 변경이라, 자동 판정이 이 안을 막았다. 이슈 본문에 숨은 지시가 토큰을 밖으로 보내게 할 수 있다는 이유였다.
- 따져 보니 명령 모양을 제한해도 유출 경로가 0이 되지는 않는다. 그래서 명령 단위 목록은 유지하고, 피해 크기를 줄이는 쪽(사람이 본문을 읽고 `ready`를 다는 운영 규칙)에 기대기로 했다.

### 격리 설정이 셸을 통째로 죽임 (#123, 3회)

- 셸 명령 환경에서 시크릿을 지우는 격리 설정을 켰다.
  - 1회차: 격리에 필요한 도구가 러너에 없어 세션이 뜨지도 못했다.
  - 2회차: 그 도구를 설치하자 19턴을 거부 없이 돌았지만 push를 하지 않았고, 로그에 이유가 없었다.
  - 3회차: 전체 출력을 켜자 원인이 보였다. 격리가 또 다른 도구를 요구해 Bash 명령이 전부 실패했다. 결과물 확인 단계가 이것을 실패로 잡았다(의도대로).
- **선택:** 러너에 도구를 쌓아 격리를 살리는 대신, 격리를 끄고 운영 규칙에 기댔다. 공개 저장소라 노출 걱정이 작고, 운영 규칙이 더 가볍다. push 허용, 설계 문서 보관, 결과물 확인은 남겼다.
- **결과:** 이슈 #125에서 초안 PR #126까지 정상으로 나와 1단계를 확정했다.

### 재실행이 통째로 건너뛰어짐

- 앞 실패에서 붙은 `blocked` 라벨이 남아 있으면 워크플로가 돌지 않는다. 재실행은 `blocked`와 `ready`를 함께 뗀 뒤 `ready`를 다시 단다.

## 2단계: 구현, 검사, 병합

### 봇 토큰으로 push하면 검사가 깨어나지 않음

- **증상:** 구현 세션이 기본 토큰으로 push하면 PR 검사(`check-web`, `check-api`)가 돌지 않았다. 병합 근거가 비었다.
- **원인:** GitHub은 기본 토큰이 만든 커밋으로는 다른 워크플로를 깨우지 않는다(순환 방지).
- **1차 선택(실패):** 기존 검사를 재사용 호출로 불렀다. 검사 결과가 PR이 아니라 main 커밋에 붙어, 결과를 끌어오는 경로가 둘로 갈렸다. 덧댄 우회가 더 깨지기 쉬운 구조를 만들었다.
- **2차 선택:** push 신분을 GitHub App의 짧은 수명 토큰으로 바꿨다. 검사 파일은 원래대로 되돌렸다.
- **결과:** PR head 커밋에 check, gitleaks, Vercel, 화면 캡처 검사가 붙어 돌았다.

### 실행 전 실패에서 실패 표시가 안 붙음

- 저장소를 내려받기 전에 끝난 실패에서는 `gh`가 어느 저장소인지 몰라 `blocked` 라벨과 원인 댓글을 달지 못했다. job에 저장소를 지정했다.

### 세션의 자기 승인은 막힌다

- 세션이 `/approve` 댓글을 달려 하면 자동 판정이 자기 승인으로 막는다. 사람 승인 관문이 의도대로 동작한 것이라 우회하지 않았다. 사람이 댓글을 달고, 세션은 병합 결과를 확인해 다음으로 넘어간다.

## 3단계: 요약, 이슈 닫기

- **봇이 일으킨 실행 거부:** 병합을 App 토큰으로 해야 다음 단계(요약)가 깨어난다. 그런데 요약 세션은 봇이 일으킨 실행을 기본으로 거부했다. 모든 봇이 아니라 이 App 하나만 허용했다.
- **재실행은 옛 파일로 돈다:** 실패한 실행을 다시 돌리면 병합 당시의 워크플로 파일을 쓴다. 수정은 다음 병합에서야 확인됐다(#133 → PR #134).
- **실패 댓글이 원인을 잘못 짚음:** 어디서 실패하든 같은 문장을 달아, 공개 금지 패턴 검사가 걸린 것처럼 읽혔다. 실제로 실패한 단계 이름을 적게 바꿨다.
- **요약 턴 상한:** 내용은 다 만들고 11턴으로 상한 10을 넘겨 실패로 찍혔다. 20으로 올렸다.

## 로컬 구현과 운영 (10-22)

| 증상 | 원인 | 처리 |
| --- | --- | --- |
| 고친 `/approve` 댓글이 무시됨(#139) | 워크플로는 댓글이 새로 달릴 때만 돈다 | 승인은 새 댓글로 단다. 첫 줄만 보게 바꿈 |
| 본문 문장에 "후속 조치"라는 글자만 있어도 후속 이슈 워크플로가 돎 | 조건이 문자열 포함만 봤다 | 줄 맨 앞 제목만 인정(#144) |
| 로컬 세션이 끝나지 않아 push가 멈춤(#141) | 세션은 `/exit`를 스스로 칠 수 없다 | 지시문을 "사람에게 닫아 달라고 말한다"로 |
| 새 리뷰 워크플로가 열린 PR에서 안 돎(#150) | PR 이벤트는 PR의 병합 시험 커밋에 든 워크플로로 돈다. 그 커밋이 리뷰 워크플로보다 먼저 만들어졌다 | 브랜치를 갱신해 병합 시험 커밋을 새로 만듦 |
| 설치 단계가 요청 과다(429)로 실패 | 설치 서버의 요청 제한(추정: 동시 실행 둘이 겹침) | 그대로 다시 돌려 통과 |
| 다른 저장소 CI가 하루 동안 실패(아무도 못 봄) | 이 저장소에 넣은 검사 정규식이 다른 저장소의 민감 문자열 검사에 걸림 | 그 검사의 제외 목록에 이유와 함께 추가. 글자를 바꿔 피하지 않음 |
| 새 저장소에서 첫 실행이 토큰 단계에서 실패 | 시크릿은 맞았지만 App이 그 저장소에 설치돼 있지 않았다 | 저장소를 붙일 때 시크릿과 App 설치를 같이 확인 |

## 자동 판정이 막은 것

로컬 세션의 명령을 Claude Code 자동 판정(도구 호출을 허용하거나 막는 판정기)이 막은 경우가 10건 넘었다. 막히면 우회하지 않고 사람에게 명령을 넘겼다.

- 사람 리뷰 없는 병합, 권한 부여, 보안 설정 완화, 에이전트 권한을 에이전트가 넓히는 변경, 그 변경의 커밋이 막혔다. 모두 사람이 직접 했다.
- 세션 전체 출력을 공개 로그에 켜는 변경도 막혔다. 그래서 거부된 명령과 턴 수만 남기는 단계를 만들었고, 이 단계가 이후 원인 찾기의 핵심이 됐다.
- 두 번 넘게 나온 것은 병합과 자기 승인 거부뿐이었다. 사람 관문이 의도대로 동작한 것이라 막을 대상으로 보지 않았다.

## 배운 것

- **세션의 자기 보고를 믿지 않는다.** 결과물은 워크플로가 기계로 확인한다.
- **원인을 보려면 무엇이 거부됐는지부터 남긴다.** 거부 내역 한 줄로 시험 회차가 줄었다.
- **검사가 안 깨어나면 누가 push했는지를 본다.** 신분만 바꾸면 기존 검사가 그대로 붙는다. 우회 경로를 덧대는 것은 그다음이다.
- **방어 설정은 켜기 전에 실행 환경에서 한 번 돌려 본다.** 문서만 보고 켠 격리가 세션을 통째로 멈췄다.
- **사람 관문은 자동 판정도 관문으로 본다.** 병합과 승인은 사람이 하고, 세션은 결과를 확인해 넘어간다.
