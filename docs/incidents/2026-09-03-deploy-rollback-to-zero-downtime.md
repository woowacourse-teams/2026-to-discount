# API 배포: 덮어쓰기에서 자동 롤백, 무중단 교대까지 (2026-09-03 ~ 10-30)

**요약:** API 배포는 실행 파일(jar)을 같은 이름으로 덮어써서, 새 버전이 안 뜨면 돌아갈 원본이 없었다. 2026-09-03 버전별 파일과 링크 교체로 되돌릴 길부터 만들었다. 09-14 첫 실제 롤백이 오탐이어서 헬스체크를 고쳤다. 재시작 중 약 5초 끊김은 10-14에 "지금은 유지"로 두었다가, 필요해진 10-28에 임시 인스턴스 교대로 없앴다. 10-29에는 일부러 실패를 넣어 자동 복구를 운영에서 확인했다.

## 1. 링크 교체와 자동 롤백 (09-03)

서비스는 늘 `current.jar`라는 이름만 실행한다. 이 이름은 실제 파일이 아니라 다른 파일을 가리키는 심볼릭 링크다.

1. 배포 전, 지금 링크가 가리키는 jar를 이전 버전으로 적어 둔다.
2. 새 jar를 커밋 해시를 붙인 이름으로 따로 두고, 링크만 새 파일로 옮긴다(`ln -sfn`). 링크 교체는 한 번에 일어나서 반쯤 쓴 파일이 남지 않는다.
3. 헬스체크가 실패하면 링크를 이전 버전으로 되돌리고 재시작한다.
4. 성공하면 최근 3개 버전만 남긴다.

검토한 대안: 덮어쓰기 유지(되돌릴 원본 없음), 이전 jar를 `.bak`으로 복사(한 세대만 남고 복사 중 실패 위험), 블루그린(서버 한 대에 과함), 컨테이너 태그(당시 Docker를 안 씀).

커밋: [`36640ab`](https://github.com/nn98/delivery-discount-api/commit/36640ab6f482da98ba0e869f8e66ea63e9de878b)

## 2. 첫 롤백은 오탐이었다 (09-14)

- 09-03 ~ 09-15 배포 실행 33번 중 실패 3번. 둘은 빌드 실패라 롤백 단계가 "이전 버전 기록 없음"을 찍고 링크를 안 건드렸다. 맞는 동작이다.
- 09-14 실행은 헬스체크가 연결 거부로 실패해 링크를 되돌렸다. 그런데 새 버전은 멀쩡했다. 헬스체크가 5초 뒤 한 번만 확인했고, 앱은 4.3초에 떴지만 확인이 그보다 조금 먼저 들어갔다.
- 2분 뒤 1초마다 최대 30초 확인하는 방식으로 고쳤고, 다음 배포는 롤백 없이 통과했다.
- 배운 것: 되돌릴 길을 만들면서 "언제 되돌리나"를 정하는 판정은 다시 보지 않았다. 롤백과 판정 기준은 한 묶음이다.

커밋: [`1e512f9`](https://github.com/nn98/delivery-discount-api/commit/1e512f9dfd66a6853e4b3e0d02a83ee178b872d3), 알림 [`1484898`](https://github.com/nn98/delivery-discount-api/commit/1484898f59f6019d55dba5f10fdd5038cd6f41e3)

## 3. 5초 끊김은 필요해진 때 없앴다 (10-14 → 10-28)

재시작 동안 약 5초 502가 났다. 10-14에는 비용 대비 효과가 작아 유지하기로 했다. 10-27에 진행을 정했다.

설계에서 정한 것:

- 평소 구성(포트, 서비스 이름)은 그대로 두고 배포 중에만 임시 인스턴스를 띄운다. 두 인스턴스를 번갈아 쓰면 서비스 이름과 포트를 하나로 가정한 곳이 열 군데 넘게 깨진다.
- 본 인스턴스가 재시작해 연결을 거부하는 동안 nginx가 `backup`인 임시 인스턴스로 넘긴다. 배포 때 nginx 설정은 바꾸지 않는다.
- 임시 인스턴스는 푸시 발송과 분석 이벤트 전달을 끈다. 두 인스턴스가 같은 상태 파일로 스케줄러를 돌리면 푸시가 두 번 나갈 수 있다.
- 푸시 시간대(11:00 ~ 11:30)에는 배포를 기다린다.

배포 순서와 종료 코드:

| 단계 | 실패하면 |
|---|---|
| 임시 인스턴스를 새 jar로 띄우고 최대 60초 확인 | 임시 인스턴스를 내리고 종료 코드 1. 본 인스턴스는 그대로 |
| 본 인스턴스 링크를 새 jar로 바꾸고 재시작, 30초 확인 | 이전 jar로 되돌려 재시작, 종료 코드 2 |
| 본 인스턴스 준비 뒤 15초 기다려 임시 인스턴스를 내림 | |
| 되돌리기도 실패하거나 되돌릴 곳이 없음 | 임시 인스턴스를 켜 둔 채 종료 코드 3 |

서버 없이 순서, 실패, 롤백, 푸시 시간대 대기, jar 정리를 확인하는 시험 16개를 붙였다. 서버 쪽 설정(nginx `backup`, 임시 유닛)은 비공개 운영 저장소에 있고, 실제 nginx로 본 인스턴스를 껐을 때 GET과 POST가 임시 인스턴스로 넘어가는 시험이 CI에서 통과했다.

## 4. 운영에서 확인한 것

- 첫 무중단 배포(10-28): 배포 동안 공개 API를 약 1초 간격으로 75번 조회해 200이 아닌 응답 0번. 1초보다 짧은 끊김은 이 방식으로 못 잡는다.
- 배포 뒤 서버: 임시 유닛 꺼짐, 본 유닛 실행 중, 두 링크가 같은 최신 jar를 가리킴.
- 실패 주입(10-29): 본 인스턴스 포트에서만 시작에 실패하게 한 커밋을 배포했다. 임시 인스턴스 준비(8초) → 본 인스턴스 30초 안에 준비 안 됨 → 이전 버전으로 복구, 임시 인스턴스 내림 → 종료 코드 2 → 슬랙 알림. 그 커밋을 되돌린 배포는 정상 통과했다.
- 재확인(10-30): 빈 커밋 배포에서 임시 8초, 본 8초로 교대 끝.

## 남은 한계

- DB나 데이터 파일 상태는 되돌리지 않는다. 되돌리는 것은 jar뿐이다.
- 무중단은 1초 간격 조회로 확인했다. 그보다 짧은 끊김은 재지 않았다.
- 임시 인스턴스가 받는 동안 푸시 구독 요청은 실패할 수 있다(5 ~ 8초).

## 배운 것

- 되돌릴 길을 먼저 만들고, 끊김 제거는 필요가 숫자로 보일 때 했다. 처음부터 블루그린을 들였다면 서버 한 대에서 포트와 서비스 이름 가정을 열 군데 넘게 고쳐야 했다.
- 복구 경로는 일부러 밟아 봐야 믿을 수 있다. 09-14 롤백은 오탐으로 처음 밟혔고, 10-29에는 실패를 넣어 의도대로 밟았다.
