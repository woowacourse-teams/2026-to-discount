# 프로젝트 하네스: 무엇이 반복해서 깨지고, 무엇이 그걸 붙들고 있나

- 갱신: 2026-09-29
- 범위: ADR 27건, 장애기록 14건, 인수인계 7건, 2026-07-26 ~ 09-28 작업 기록
- 읽는 사람: 이 저장소에서 다음 작업을 하는 사람(또는 에이전트)

## 이 문서는 무엇인가

버그 목록이 아니다. **같은 모양으로 되풀이된 실패**와, 그걸 막으려고 세워
둔 장치를 한자리에 모은 것이다. 새 작업을 시작하기 전에 §0을 읽고, 무언가
이상하면 §다음 할 일의 표에서 해당 패턴을 찾는다.

문서가 여럿이라 역할을 갈라 둔다. **여기서 같은 말을 반복하지 않는다.**

| 문서 | 맡는 것 |
|---|---|
| **이 문서** | 패턴. 왜 반복되나, 무엇이 막고 있나 |
| `setup/COLLECTION-INCIDENTS.md` | 증상 → 확인 명령 → 조치. 지금 깨졌을 때 여기부터 |
| `decisions/ADR-*.md` | 판단. 왜 그렇게 정했나 |
| `public/ARCHITECTURE.md` | 구조. 저장소, 도는 길, 2026-09-29 결정의 이유. 공개 문서라 mono로 나간다 |

## §0. 먼저 읽을 세 문장

이 프로젝트에서 지금까지 나온 실패의 대부분은 이 한 문장의 변주다.

> **"없다 / 0 / 통과"를 출력할 때, 그것이 관측인지 미관측인지 구분되지 않는다.**

수집이 깨지는 방식은 **틀린 값이 나오는 게 아니라 값이 조용히 사라지는
것**이다. 순회는 정상 종료하고 "성공 N / 실패 0"을 찍는다. 그래서:

1. **부재를 주장하기 전에 "제대로 봤다"를 양성 신호로 증명한다.**
   앵커가 그려졌는지, 그 브랜드 이름이 화면에 있는지, 목표 화면에
   닿았는지를 따로 확인한다.
2. **글자가 아니라 구조로 짚는다.** 앱 문구는 바뀐다. 좌표, 열, 구역 관계는
   덜 바뀐다.
3. **결론은 테스트로 박는다.** 주석과 문서는 안 읽으면 그만이다. 이
   프로젝트에서 실제로 되돌림을 막은 것은 전부 테스트였다.

## §1. 못 본 것을 없는 것으로 적는다

가장 많이, 가장 비싸게 되풀이됐다.

| 날짜 | 무슨 일 | 결과 |
|---|---|---|
| 08-10 | 손 투입 5건을 "오늘 수집함"으로 오인 | 진행 중 프로모션 6개가 종료로 밀림 |
| 08-16 | 정정 5건을 두 번 넣어 정확히 10건 | **배민 브랜드 69개 소멸**, export 160→91 |
| 09-07 | 브랜드 페이지 개편, 파서가 옛 문구를 찾음 | 69곳 전부 "값 없음" |
| 09-07 | 순회 대상이 사본(68곳) | 새 링크 42곳이 대상에 없음, "성공 68 / 실패 0" |
| 09-10 | 배짱할인 탭을 안 눌러 버튼 0개 | "브랜드 할인 0곳" |
| 09-11 | 딥링크가 안 먹어 배민 **홈**을 판독 | 미스터피자, 요아정이 "만료 후보" |
| 09-11 | 핫딜 구역 넉 장 중 첫 장만 읽음 | "오늘 핫딜 없음" |
| 09-12 | 쿠폰함 웹뷰가 덜 그려진 화면을 읽음 | "보유쿠폰 0장" (같은 화면에 34장 있었다) |

**왜 되풀이되나.** 부재는 관측이 아니라 추론이다. "화면에 없다"와 "내가 못
봤다"가 같은 출력(빈 값)으로 떨어지는데, 코드에는 둘을 가르는 자리가
기본적으로 없다. 가르려면 매 화면마다 양성 신호를 새로 만들어야 한다.

**막고 있는 것**

- ADR-020 전수 수집은 기록한다(건수로 추정하지 않는다)
- ADR-025 순회 대상은 단일 출처(`brands.yml`)에서만
- `hotdeal_state()` 다음 구역을 앵커로 "없다"와 "못 읽었다"를 가른다
- `wait_for_baemin_brand_page()` 표식 **+ 그 브랜드 이름**을 봐야 판독
- `has_no_deliverable_store()` "이 주소에 가게가 없다"를 만료와 가른다
- `full_audit` 리포트가 **만료 후보 / 확인 불가**를 갈라 센다
- 쿠폰함이 0장이면 파일을 만들지 않는다
- `BARREN_LIMIT` 연속 무수확이면 멈춘다(흔적이 있는 경우만 센다)

**아직 없는 것**: 없다. 2026-09-12에 요기요 상세에도 브랜드 이름 확인을
넣었다(`on_brand_detail`). 땡겨요는 브랜드 상세를 열지 않아 이 구멍이
애초에 없다. 목록에 다 있고, 바닥 판정도 두 번 연속 같을 때만 인정한다.

## §2. 한 장만 본다 / 첫 것만 집는다

| 날짜 | 무슨 일 | 결과 |
|---|---|---|
| 09-07 | 배민이 같은 쿠폰을 네 모양으로 준다 | 한 모양만 보다 두 번 연달아 틀림 (ADR-026) |
| 09-10 | 첫 금액 + 마지막 최소주문을 짝지음 | 피자헛 `7,000/24,000`. **화면에 없는 조합** |
| 09-10 | `_identity`가 (앱,브랜드,시각)만 봄 | 14건 중 6건이 중복으로 버려짐 |
| 09-11 | 핫딜 구역을 "맨 위 한 장"으로 앎 | 넉 장 중 한 장 |
| 09-11 | 읽는 쪽만 고치고 쓰는 쪽을 안 고침 | 4건 읽고 1건만 배너로 |
| 09-12 | 브랜드당 쿠폰 한 장만 남김 | 빽다방 배달/픽업 두 조건 중 하나 소실 |

**왜 되풀이되나.** 처음 본 화면이 하나짜리였고, 그 관찰이 그대로 구조
가정이 됐다. 나중에 여럿이 돼도 코드는 조용히 첫 번째만 집는다. 오류가
아니라 **누락**이라 티가 안 난다.

**특히 위험한 조합: 읽는 쪽만 고치고 쓰는 쪽을 안 고치는 것.** 화면은
그대로다.

**막고 있는 것**: ADR-026(모양은 합집합), 복수형 파서(`parse_*s`),
`as_banners`, 채널별 `tiers`, `_identity`가 금액, 최소주문까지 본다.

**아직 없는 것**: 쿠팡이츠 배너 4장은 여전히 사람이 손으로 관리한다.

## §3. 검사는 초록인데 값이 틀렸다

가드가 **보는 것과 틀린 것이 다른** 경우. 초록불이 확인을 멈추게 해서
§1보다 발견이 늦다.

| 날짜 | 초록불 | 실제 |
|---|---|---|
| 08-16 | `MIN_SWEEP_RECORDS = 10` 통과 | 정정 5건 ×2 = 10건 → 69개 소멸 |
| 09-10 | `bannersOk: True` | 배너 제목과 내용이 다른 행사 |
| 09-11 | `bannersOk: True` | 브랜드 이름에 `&amp;` |
| 09-11 | `bannersOk: True` + `unknownBrands` 2건 | **메뉴 행사가 브랜드로 등록** |
| 09-10 | 스케줄러 "마지막 결과 0" | 쿠팡이츠 수집이 딥링크 실패로 죽음 |
| 09-11 | HogQL 결과 100행 | 기본 LIMIT 100 → "개발 트래픽 0" |
| 09-12 | `--verify` "배너가 화면과 같다" | 같은 실행이 "핫딜 없음"이라 판정했는데 통과 |
| 09-18 | 4단계 PASS "플랫폼 3개 요약 있음", 8단계 보고서 표 | 전수조사가 8단계 출처 목록에 없어 **9일 동안 원장에 0건**. 표에는 없는 출처의 빈 줄이 없었다 |
| 09-18 | 스윕 "브랜드 0 · 만료 후보 0 · 판독 실패 0" | "이번 주 이미 확인"으로 결과를 비운 것. 세 0이 조용했다 |

**왜 되풀이되나.** 가드는 만들 때 알고 있던 실패만 본다. 그런데 출력은
한 줄(`True`)이라 **안 본 것과 괜찮은 것이 같은 모양**이다. §1이 가드
층위에서 반복되는 것이다.

**막고 있는 것**: ADR-020(임계값 방식 폐기), `.cmd`가 종료 코드를 전파,
HogQL에 항상 명시 LIMIT, `--verify`가 `hotdeal_absent`를 넘겨받는다.

**아직 없는 것**: 없다. 2026-09-12에 `bannersOk = 파싱됨 && unknownBrands
비었음`으로 바꾸고, `bannersParsed`를 따로 실어 "파일이 깨진 것"과 "이름을
못 찾은 것"을 갈랐다. `reload_server()`도 이제 실패로 돌려준다.

## §4. 휘발성 문구에 동작을 매단다

| 날짜 | 바뀐 글자 | 결과 |
|---|---|---|
| 09-01 | "쿠폰 받기"가 사라짐 | 행사 0건, KFC 8,000원 누락 |
| 09-05 | 탭 "주말핫딜"→"배짱할인" | 그날 배너 루틴 3회 전부 실패 |
| 09-10 | 제목 "오늘의 핫딜"→"웰컴 핫딜" | 앵커는 보이니 **자신 있게** "핫딜 없음" |
| 09-11 | 굽네 머리줄/브랜드줄 불일치 | 행사 셋 중 하나 누락 |
| 09-11 | 쿠폰 받은 뒤 "주문하기"로 바뀜 | **브랜드가 넷 다 "주문하기"** |

**왜 되풀이되나.** 문자열 일치는 쓰기 쉽고 한동안 잘 된다. 깨질 때
**예외가 아니라 빈 결과**로 깨진다(§1과 같은 뿌리).

금지어, 별칭을 늘리는 방식은 다음 변경에서 또 깨진다. `HOTDEAL_SKIP_WORDS`에
"쿠폰 받기"를 넣어 뒀는데 "주문하기"가 오자 그대로 뚫렸다.

**막고 있는 것**: ADR-003(구조로 판독), 좌표를 박지 않고 라벨로 찾기,
`HOTDEAL_TITLE_RE`(제목이 바뀌어도 구역을 찾는다), `_same_brand()`,
그리고 **`_text_cells()`의 열(x) 비교**: 지금까지 중 가장 튼튼하다.

## §8. 실패하지 않고 멈춘다

| 날짜 | 무슨 일 | 결과 |
|---|---|---|
| 09-12 | `banner_routine --apply` 09:30분 실행이 ssh에서 멈춤 | **11시간 38분** 살아 있는 채로 아무것도 안 함 |
| 09-12 | 그걸 모르는 11:46 실행이 위에 겹쳐 뜸 | 같은 자리에서 또 9시간 22분 |
| 09-12 | 21:00 `full_audit`까지 붙어 폰 한 대를 셋이 다툼 | 쿠팡이츠 순회가 계속 `'My 이츠'를 못 찾았다`로 죽음 |

**무슨 일이었나.** 둘 다 서버의 `banners.yml`을 백업하는 ssh에 매달려
있었다. **서버는 멀쩡했다**: uptime 54일, API `active`, 그 사이 13:57에
다른 실행이 같은 파일을 정상으로 고쳤다. 끊긴 것은 TCP 세션 한쪽뿐이고
(가정망 NAT + duckdns에서 흔한 half-open), ssh는 죽은 소켓을 영원히
기다렸다. `ConnectTimeout`으로는 못 잡는다. 연결은 이미 끝났다.

**왜 §1보다 나쁜가.** §1(못 본 것을 없는 것으로)은 틀린 값이라도 남기고
끝난다. 멈춤은 **아무 출력도 남기지 않는다.** 로그 파일이 35바이트인
채로 11시간이 지났고, 다음 스케줄 실행은 앞엣것이 끝났는지 묻지 않고
그 위에 떴다. 오늘 배너가 한 번도 적용되지 않았다는 사실을 사람이
프로세스 목록을 보고서야 알았다.

**막고 있는 것**

- `scripts/_ssh.py`. 옵션이 한 자리에 있다. `ServerAliveInterval=10` ×
  `ServerAliveCountMax=3`이면 죽은 세션이 30초 안에 **실패**로 돌아온다.
  `BatchMode=yes`로 비밀번호 프롬프트(답할 사람이 없는 멈춤)도 막는다.
- `run_ssh`/`pipe_ssh`의 `timeout`. 세션은 살아 있는데 원격 명령이 안
  끝나는 경우는 keepalive가 못 잡는다. 마지막 그물이다.
- `tests/test_ssh_options.py`. ssh 명령줄을 직접 짜는 자리가 생기면
  깨진다. 고칠 곳이 일곱 파일 아홉 군데였다(전부 같은 줄을 복사한 것).

**아직 없는 것**: **겹쳐 뜨는 것을 막는 장치가 없다.** 스케줄 작업이
앞 실행이 아직 도는지 묻지 않는다. 잠금 파일이든 Task Scheduler의
`MultipleInstances` 설정이든 필요하다. 그리고 폰 한 대를 여러 수집이
동시에 쓰면 서로 앱을 앞뒤로 뺏는데, 그것도 막는 자리가 없다.

## §9. 기계가 사람 것과 자기 것을 못 가른다

| 날짜 | 무슨 일 | 결과 |
|---|---|---|
| 09-12 | 사람 배너를 기계가 "표기 통일"하며 덮음(두 번) | 사람이 다시 살림 |
| 09-13 | 스냅샷이 사람 수정을 한 번만 보호. 살려둔 값을 "내가 쓴 것"으로 기록 | 다음 실행이 덮음 |
| 09-15 00:05 | 화면 브랜드를 덮임 필터 **뒤** 목록으로 세서 사람 묶음이 "화면에 없다"로 판정 | ssh 타임아웃으로 쓰기 전에 죽어 무사 |
| 09-15 10:55 | 사람이 내린 타겟딜 배너를 `이어진다`로 되살리고 낱장을 새로 세움 | **사람이 다시 내림. 배너 자동 반영을 껐다** |

**왜 되풀이되나.** 서버 파일 한 장에 사람이 쓴 값과 기계가 쓴 값이 **같은
모양으로** 섞여 있다. 기계는 "내가 마지막에 쓴 것"과 지금 값을 견줘 사람
것을 추론하는데, 그 추론은 자기 쓰기 한 번에 깨진다(살려둔 값을 자기 것으로
기록). 원장은 append-only + `capture_mode: manual` + 날짜로 가르니 같은
날 막혔는데(10:55 반영에서 4건 `보류`), 배너 파일엔 그런 **출처 표식이 값
자체에** 없다.

**막고 있는 것**

- **배너는 사람이 반영한다**(09-15 결정). 루틴은 읽고 대조해 보고만 한다.
  기계가 못 가르는 판단을 기계에 안 맡긴다.
- 원장: `reflect_daily`가 같은 (앱, 브랜드)에 **사람이 오늘 넣은** 대표가
  있으면 보류한다. 값이 아니라 출처와 날짜로 가른다.
- 스냅샷 `_human_fields`(필드 단위), 접어 둔 배너(`endsOn < startsOn`)는
  되살리지 않음. 배너 자동 반영을 다시 켜는 날의 최소 조건이다.

**09-29 예외: 되풀이 배너만 자동 반영.** 사용자 결정. 루틴이 매일 같은 꼴의
id로 만드는 두 종류만 서버가 제안을 받자마자 반영한다(beggars-ops
`ops_apply.auto_apply`, README "되풀이 배너 자동 반영").

- 대상: `coupangeats-open-<오늘>-…`(쿠팡이츠 선착순 오픈. 09-20~09-29 열흘 모두
  제안됐다)와 배민 오늘의 핫딜 `<브랜드>-<오늘>`(platform baemin, 사유 `배민 핫딜이
  화면에 있다`).
- 하는 일은 둘뿐: **없는 id를 새로 올리기**, 그리고 **서버가 자동으로 올렸고 사람이
  안 건드린 배너 내리기**. 고치기(set)는 하지 않는다. 그래서 사람 값을 덮을 길이 없다.
- 출처는 추론하지 않고 기록으로 가른다: 서버 원장 `auto_applied.jsonl`(기계가 올린
  id), `edits/*.jsonl`(사람이 콘솔에서 손댄 id), 스냅샷 `_human_fields`, 파일 값과
  스냅샷의 일치. 하나라도 모르면 제안으로 남긴다.
- 검사는 사람 승인과 같다(`console_problem`, 브랜드 카탈로그). 걸리면 보류.
- 끄기: `OPS_AUTO_APPLY_REPEATING=0` 또는 `<콘솔 폴더>/auto_apply.off`.

**10-15 넓힘.** 사용자 결정("넓혀도 괜찮을 거 같다, 바로 하고 예후를 본다", REFACTOR-BACKLOG 6).
종류가 아니라 출처로 가른다(beggars-ops e0e5fd7, README "배너 자동 반영").

- 새 id의 add는 종류와 상관없이 올린다.
- set과 expire는 기계 배너에만 한다. 스냅샷 행이 있고 `_human_fields`가 없고 편집 이력에 없고 파일 값이
  스냅샷과 같은 배너다. 사람이 승인한 제안으로 올라간 배너도 값은 기계가 쓴 것이라 넣는다.
- 그래도 제안으로 남긴다: 사람이 같은 배너에 같은 일을 거부한 적이 있다, 되풀이가 아닌 알림 켜기,
  되풀이가 아닌 expire가 한 번에 4장 이상.
- 운영 스위치는 2026-09-30 02:32에 콘솔에서 꺼졌고(계정 glen) 10-15 현재도 꺼져 있다.

**아직 없는 것**: 배너 파일에 **출처 표식**(누가 썼는지)이 값 옆에 없다.
자동 반영을 다시 켜려면 그것부터다. 스냅샷으로 추론하는 방식은 세 번
깨졌다.

## §10. 유지할 것: 되풀이할 대목

실패만 적으면 무엇을 지켜야 하는지가 안 남는다.

### 사실로 버티기: 동조하지 않는다 (09-12)

핫딜 카드가 `피자 / 10,000원`으로 읽혔다. 로고는 Pizza Hut인데 글자는
`피자` 두 자였다. 사용자가 **"니가 잘못읽은거 아니고? 재확인"**이라고
물었다.

동조하는 대신 스크린샷을 2배로 확대하고 뷰 트리를 다시 떴다. **둘 다
`피자`였다**: 앱이 그렇게 쓰는 것이었다. 그리고 "로고는 못 읽으니
`피자→피자헛`은 관측을 표로 박은 것"이라고 한계까지 같이 밝혔다.

**왜 중요한가.** §1~§7의 대부분이 "확인 안 하고 말한 것"이다. 동조도 같은
종류다. 확인 없이 상대 말에 맞추는 것이라, 틀린 방향으로 틀리는 것만
다르다. 되묻는다고 답을 바꾸지 않는다. **다시 확인하고, 확인한 방법을 같이
적는다.** 확인해서 내가 틀렸으면 그때 바꾼다.

### 지우지 않고 고친다 (09-12)

브랜드가 아닌 이름으로 올라갔던 옛 배너 행을 지우지 않고 `brand`만 고쳤다.
`banners.yml`은 화면을 만드는 파일이면서 **기록**이기도 하다. 기간이 지나
화면에 영향이 없는 행을 지우면 그때 무슨 일이 있었는지가 같이 사라진다.
`data/_retired/` 수납 방식과 같은 취지다.

### 사람 수정을 기계가 이기지 않는다 (09-12)

"오늘 있는 건 안 건드린다"로는 부족하다. 금액이 진짜로 바뀐 날에도 못
고친다. **기계가 쓴 내용을 스냅샷으로 남기고, 서버가 그것과 다르면 사람이
손댄 자리로 본다.** 스냅샷이 없으면(첫 실행, 손으로 만든 배너) 사람 것으로
친다. 모르면 남의 것으로 치는 쪽이 안전하다.

### 실패하면 다음 것으로: 고르고 끝내지 않는다 (09-12)

같은 폰이 USB와 무선으로 두 번 잡힌다. 어느 쪽이 살아 있는지 미리 알 수
없고 알 필요도 없다. `run_with_device()`가 차례로 시도하고, 전부 실패하면
**마지막 예외를 그대로 올린다**(실패를 삼키지 않는다).

00:05 실행이 넷 실패했다. 재시도부터 하지 않고 하나씩 원인을 봤다.

### 전수로 대조한다 (09-15)

`brands_of` 규칙을 단위 테스트만으로 두지 않고 서버 배너 74장 전부에

### 결정이 뒤집히면 둘 다 남긴다 (09-15)

09-10 "웰컴 핫딜은 전체 노출, 올려라"와 09-15 "다른 계정엔 없다"를
`HOTDEAL_CREATES_BANNERS` 주석에 나란히 적었다. 한쪽만 남기면 다음
사람이 왜 그런지 모른 채 되돌린다(§6).

### 프론트는 프리뷰로 먼저, 승인 뒤 배포 (09-16)

웹 변경을 main에 바로 밀어 운영에 냈다가 하루에 여러 번 되돌렸다. "최고"
탭이 칩 밖으로 삐져나오고 배지를 덮었고, 도크에 화살표를 달아 로고를
가렸고, 닫기 버튼이 트랙과 같이 흘렀다. 전부 **운영에서 사용자가 발견**했다.

**규칙(사용자 결정 2026-09-16, 따로 말하지 않아도 기본값):** 경로, 올리기 전 360px 확인, 승인, 예외는 [`docs/public/WORKFLOW.md` 7-1, 7-2](public/WORKFLOW.md#7-규칙과-가드-이-문서가-단일-진실)에만 적는다. 여기에는 왜 생겼는지만 둔다.

"승인받아서 배포"는 사용자가 매번 말하지 않는다. 안 말했어도 프리뷰다.

### mono 변경은 PR로 올린다 (10-15)

사용자 결정 2026-10-15: "코드래빗도 활용하려면 바로 푸시 말고 PR 보내는 게 좋겠다". API처럼 화면이
아닌 변경도 mono main에 바로 push하지 않는다. 같은 날 API 변경을 main에 바로 올리려다 자동 판정에도
막혔다(PR #85).

PR의 단위는 기능 변화나 실험 하나다(사용자 2026-10-16). 문서만 바꾸는 것은 PR로 묶지 않는다.
같은 날 화면 이력 문서와 그 요약을 PR #93, #94로 따로 올렸다가 "문서를 굳이 묶어서 PR 보내는 게
맞나"는 말을 들었다.

절차(PR 열기, CodeRabbit 부르기, 병합 전 점검)는 [`docs/public/WORKFLOW.md` 7-1, 7-3](public/WORKFLOW.md#7-규칙과-가드-이-문서가-단일-진실)에 있다. API 병합은 배포라 예약 수집이 도는 동안을 피한다.

### 파생 이슈는 바로 띄우지 않는다 (11-13)

이슈를 바로 만들면 중복, 충돌 이슈가 쌓여 정리 비용이 늘었다(열린 이슈가 150건 가까이였다). 버퍼에 쌓고 한 번에 정리해 올린다. 절차는 [`WORKFLOW.md` 7-5](public/WORKFLOW.md#7-5-파생-이슈는-버퍼에-쌓고-한-번에-올린다).

### 브레인스토밍 승인은 구현 승인이 아니다 (09-17)

"A+B 맞다고 보고" 를 구현 승인으로 읽고 코드까지 밀었다. 사용자: "브레인스토밍하랬는데
작업까지 다 해버린 거?". 설계 승인 → 스펙 문서 → 검토 → 구현이 순서다(superpowers
brainstorming). 승인의 범위는 말한 만큼이다. 사후에 스펙을 쓰고 실측으로 메꿨지만
순서가 틀렸다.

### 점검 명령을 백그라운드 `&`로 띄우지 않는다 (09-17)

`cmd //c scriptsfter_open_daily.cmd ... &` 를 "존재 확인"으로 쓰다가 실제 한 바퀴를
돌렸다(03:51, 반영, 커밋까지). 폰이 비어 있어 해는 없었지만 예약 시각과 겹쳤으면 폰을
두 프로세스가 잡았다. 실행 파일은 `--dry-run`, import, 문법 검사로만 본다.

### 원인은 이력에서 나온다 (09-17)

"링크 오류 30곳"을 사흘 봤는데 낭비 줄이기(장부)부터 했다. `reports/audit-*.json`을
날짜순으로 보니 09-08 75곳 값 → 09-10 0곳. **어느 날 통째로 끊긴 것**이었고, 링크를
HTTP로 풀어 던지니 열렸다(ADR-031). 증상 완화 전에 "언제부터"를 본다.

### 세션 셸 환경변수는 스케줄러 환경이 아니다 (09-17)

이 세션 셸엔 `ADB_SERIAL=<내부 IP>:5555`가 남아 있어 손 실행이 무선 시리얼로 죽었다.
예약 실행은 그 변수 없이 돈다. 손으로 돌릴 땐 `env -u ADB_SERIAL`.

### 수집을 고치면 예약을 끄고 실제로 돌린다 (10-01)

수집에 관련된 변경(capture/, 수집 scripts/, 가드, 기기 배정)은 단위 테스트가 초록이어도 끝이 아니다. 그 부분만이라도
실제 폰으로 돌려 확인한다. 이때 예약 수집(`discount-after-open`, 시각은 `docs/setup/ROUTINE-SPEC.md`)과 폰을 나눠 쓰면 둘 다 망가진다 —
2026-10-01 08:38 손 실행이 08:30 예약과 겹쳐 2단계가 두 번 죽었다.

- 시험은 `scripts/collect_trial.ps1 -Command "<수집 명령>"`로 돌린다. 예약을 끄고, 시험하고, 실패하거나 끊겨도 다시 켠다.
- 예약이 이미 돌고 있으면 시작하지 않는다(종료 코드 2). 도는 예약은 끊지 않고 끝나길 기다린다.
- **같은 폰을 쓰는 다른 시험**(종료 코드 3)이나 검증 봇의 폰 검사(종료 코드 4, `verify_bot.lock`)가 있으면 시작하지 않는다. 몇 분 뒤 다시 돌린다. 시험 잠금은 **폰 단위**다(이슈 #268, `scripts/trial_lock.py`): 쓰는 폰은 `-Serials a,b`(없으면 명령의 `--serial`, 그것도 없으면 "전체"로 예전처럼 전부 막는다). 폰이 다른 시험은 같이 돈다. 예약은 첫 시험이 끄고 **마지막 시험이 끝날 때만** 켠다(원래 꺼져 있던 예약은 안 켠다).
- **회차 표(이슈 #92, 1단계)**: `run_routine`은 회차 동안 쓰는 폰을 같은 레지스트리에 `collect_trial.d/<pid>.routine`으로 적고 `PHONE_LOCK_OWNER=<pid>`를 단계 스크립트에 물려준다(시험은 `collect_trial.ps1`이 같은 변수를 싣는다). 회차 표는 겹침 판정에만 들어가고 예약 참조 세기, `collect_trial.lock`에는 안 들어간다. 토큰 없이 폰 명령(`capture/phone_lock.py` `note_use`)을 부르는 프로세스가 잠긴 폰에 들어오면 `[phone-lock] 경고` 한 줄, 슬랙, `logs/phone-lock.jsonl`만 남기고 막지 않는다. 막기(2단계)는 한 주 관찰 뒤 별도 이슈.
- 시험 중에 예약 시각이 지나가면 그 회차는 안 돈 것이다 — 스크립트가 알려 준다. 빠진 단계는 시험 결과로 채우거나 다시 돌린다.
- 끝에 찍히는 "예약 수집 상태"가 Ready인지 본다. Disabled로 남으면 사람에게 알린다.
- **수집 로직이 아니어도 예약 수집이 부르는 코드를 바꿨으면 다음 예약 전에 그 단계만 돌려 본다(사용자 2026-10-15).** 조율기(`run_routine.py`)의 순서와 선행 조건, 판정기(`check_routine.py`), 링크 커밋(`publish_brand_links.py`), `banner_ops.py` 사본이 그렇다. 단위 테스트가 초록이어도 예약 실행에서 처음 드러나면 하루를 잃는다.
  - 그 단계만 남기고 나머지는 `--skip`으로 뺀다. 먼저 `--dry-run`으로 어느 폰에서 무엇이 도는지 본다.
    예: `python scripts/run_routine.py --force-audit --skip 2 3 3s 3w 4a 4g 4b 4d 5 5a 5b 6 7 8 --dry-run`(요기요 4c, 4f, 4e, 5y만)
  - 원장 반영(8)과 배너 제안(6, 7)은 빼는 것이 기본이다. 뺀 단계는 상태가 "조건"이라 뒤 단계의 선행 실패로 치지 않는다.
  - 2026-10-15: 4e 선행 조건을 고친 뒤 요기요가 로그아웃인 채로 4c, 4f, 4e만 돌려 "4c 실패, 4f 건너뜀, 4e 돎"을 실제로 봤다(15분).
### 자라는 파일을 요청 길에서 통째로 읽지 않는다 (10-14)

API의 설문 판정이 판정마다 이벤트 원장(방문 이벤트를 한 줄씩 덧붙이는 `events.jsonl`) 전체를 훑었다.
2026-08-29에 3.9만 줄이라 "1초 미만, 부담 없다"고 클래스 주석에 적고 두었다.
원장은 하루 약 5천 줄씩 늘어 2026-10-14에 34만 줄이 되었고 한 번에 1.9초가 걸렸다. 웹은 첫 화면마다 그 판정을 불렀다.
아무 경보도 없었다. 느려지는 것은 실패로 찍히지 않아 §8처럼 조용하다.

- 규모 가정(줄 수, 건수, "1초 미만")은 주석이 아니라 측정으로 남기고, 커지는 쪽이면 읽은 위치를 기억해 새 줄만 읽는다(api ADR-011).
- 점검할 때는 바깥에서 같은 경로를 여러 번, 캐시 주기(10분)를 넘겨 잰다. 한 번 재면 주기마다 오는 느린 요청을 놓친다.
  2026-10-14에는 12분 동안 15초 간격 50번으로 10분마다 오던 2,058ms를 찾았고, 고친 뒤 같은 방법으로 사라진 것(가장 느린 것 698ms)을 확인했다.

### 판 올림은 두 jar를 같은 입력으로 띄워 맞대 본다 (10-14)

2026-10-14 Spring Boot 3.3.5에서 4.1.1로(JSON 라이브러리 Jackson 2에서 3으로) 올릴 때, 컴파일과 테스트 434개가 초록이어도 동작이 바뀔 자리가 넷 있었다.
Jackson 3은 파싱 오류가 `IOException`이 아니어서, 파일 읽기와 같이 묶인 `catch (IOException)`은 컴파일되면서 파싱 오류만 놓친다(§3).

- `python scripts/compare_api_jars.py <기준 jar> <새 jar>`: 배포된 jar와 새 jar를 같은 export, 이력, 운영 배너 사본,
  이벤트 원장으로 띄워 GET 응답을 키 정렬로 비교한다. 쓰는 경로(`POST /api/events`)는 원장에 적힌 줄을 비교한다.
- 예외 종류가 바뀌는 판 올림은 `catch` 블록을 전부 훑는다. 컴파일 오류가 난 자리만 고치면 안 된다.

### 문서는 글쓰기 스킬로, 공유 문서는 검토 단계로 (09-17)

주어가 많았고 문장이 대화 기억에 기대고 있었다. 사용자 지적으로 규칙을 스킬 둘로 고정했다.

  에이전트가 부를 수 없다. 사용자가 `/writing-ko`를 부르면 그 규칙으로 쓰고 고친다(공용 `CLAUDE.md`).
  부르지 않았어도 아래 규칙은 지킨다. 결론을 먼저 쓴다. 지시대명사를 이름으로
  바꾼다. 가운뎃점과 롱대시와 이모지를 쓰지 않는다. 표에 라벨을 붙이지 않는다.

## §13. 사용자에게 보이는 문구에 수집기의 말이 나간다

| 날짜 | 나간 문구 | 자리 |
|---|---|---|
| 09-03 | "쿠팡와우 회원 전용(일반 회원 화면엔 안 뜬다, 2026-09-03 실측)" | conditions |
| 09-07 | "목록/상세 헤드라인 금액만 확보, 최소주문금액·쿠폰 상세조건 미확인(편의점형 레이아웃, 자동 파서 실패)" | conditions (세븐픽업, 웹에 노출) |
| 09-18 | "뽑기 쿠폰. 받는 값이 사람마다 다르고 매일 다시 뽑는다(허브 랜덤 표기, 쿠폰함 대조)" | conditions (5건, 웹에 노출) |

**왜 되풀이되나.** 세션이 "왜 이 값인지"를 적을 자리를 찾다가 사용자에게 보이는 칸에 적는다. 근거와 날짜와 수집기 용어가 붙은 서술형 문장은 에이전트가 쓴 티가 그대로 난다. 원장의 `conditions`, `badge`, 배너의 `period`, `extra`, 콘솔이 아닌 웹의 모든 글자가 그 자리다.

**규칙.**
- 사용자에게 보이는 칸에는 **앱이 쓰는 짧은 말**만 적는다("1일 1회, 배달만", "매일 랜덤 뽑기", "18,000원↑"). 문장(…다.)과 괄호 안 근거, 날짜, "확인·대조·표기·파서·관측·수집·판독·추정" 같은 수집기 말은 안 쓴다. 근거는 코드 주석, 문서, 원장의 `raw_text`나 별도 필드에 둔다.
- 사용자에게 보이는 문구를 **새로** 만들 일이 생기면, 그 문구가 들어가는 것이 맞는지부터 개발자에게 묻고 문구를 보여 준 뒤 넣는다. 세션이 정해서 넣지 않는다.
- 형식은 mono `docs/COPY-STYLE.md`가 정한다(칸마다 예와 금지 예). 막는 코드: `schema.validate_record(..., user_facing_copy=True)`(ingest), `ops_apply.check_ops_copy`(배너 편집기와 제안 반영), `check_deploy`(규칙에 어긋난 옛 conditions가 비는 것은 손실이 아니다). 옛 원장 행은 고치지 않는다.

## §14. 화면에는 값이 있는데 누르면 아무 데도 안 간다

| 날짜 | 무엇이 끊겼나 | 어떻게 알았나 |
|---|---|---|
| 09-11 | 배민 단축링크가 브랜드관 대신 홈으로 갔다 | 전수조사가 홈 화면을 읽고 브랜드 전부를 만료 후보로 적었다 |
| 09-20 | 요기요 오퍼 33곳 중 20곳에 브랜드 링크가 없었다 | API가 그 오퍼들을 숨기고 있었다(`discount.hide-unlinked-platforms`) |
| 09-21 | 땡겨요 링크 13건이 전부 `이벤트 준비중` | 링크 점검 봇을 처음 한 바퀴 돌렸다 |

**왜 되풀이되나.** 수집은 값을 읽고 링크는 따로 채운다. 값은 매일 갱신되는데 링크는 사람이
한 번 넣고 잊는다. 이 서비스의 전환은 앱으로 나가는 것이라(`offer_link_click`), 링크가
끊기면 카드가 떠 있어도 값이 없다. 그런데 끊김은 화면에서 안 보인다 — 누르기 전까지는.

**규칙.**
- 링크는 **기계가 받아서 기계가 확인한다.** 요기요는 브랜드관에 들어간 동안
  `dumpsys activity top`에 찍히는 `fr_id`를 줍고(`scripts/yogiyo_links.py`), 땡겨요는
  공유 시트까지 눌러 받는다(`scripts/ddangyo_links.py`). 받은 링크는 그 자리에서 열어
  착지를 확인하고, 통과한 것만 `brands.yml`에 쓴다.
- 확인 없이 쓰지 않는다. 받은 값이 곧 맞는 값은 아니다(09-21 오븐마루치킨 `fr_id=300`은
  착지하지 않아 버렸다).
- 점검은 **상시로 조금씩** 돈다(`scripts/link_watch.py`). 한 번에 다 도는 도구는 폰을
  20분 넘게 잡아서 "생각날 때 한 번"이 됐고, 그 사이 끊긴 링크가 화면에 남았다.
- 판정은 `fail`과 `no_store`를 가른다. 주변에 매장이 없어 목록에서 빠지는 것은 링크
  문제가 아니다(2026-08-20 청주 대조 실측). 뭉치면 멀쩡한 링크를 지운다.
- `brands.yml`은 사람이 읽는 단일 출처다. 기계가 고칠 때도 **그 줄만** 고친다.
  `yaml.safe_dump`로 다시 쓰면 주석과 순서가 사라진다(09-21에 1,014줄 diff가 나왔다).

## §15. 어느 문서가 이기는지 모른 채 읽는다

§6이 "결정을 잊는 것"이라면 이것은 한 겹 앞이다. **결정은 적혀 있는데, 읽는
사람이 그 문서에 닿지 못한다.** 문서가 층으로 쌓여 있고 어느 층이 이기는지가
어디에도 안 적혀 있으면, 성실하게 읽어도 틀린 층을 읽는다.

| 날짜 | 무슨 일 | 결과 |
|---|---|---|
| 09-28 | 배너 구조를 코드에서 역추적. 확정 규칙(`decisions/`)을 안 읽음 | 그 문서가 **"오기다"라고 못 박은 `T23:59`**를 예시에 그대로 쓸 뻔했다. 마지막 날 59초가 잘린다 |
| 09-28 | `banners.yml` 머리말이 재설계로 없어진 칸을 계속 가르침 | 콘솔은 새 칸만 그리는데(테스트가 지킨다) 파일을 손으로 고치는 사람은 옛 칸을 봤다. 여섯 달 가까이 아무도 안 걸렸다 |
| 09-28 | 설계 22가 자기 자신을 옛 번호 `28-api-pr-ci.md`로 가리킴 | 28번 자리는 "검수 화면"이 쓰고 있었다 |

**왜 되풀이되나.** 층마다 이기는 힘이 다른데 파일 이름은 다 비슷하다.
요약(`reports/`)이 제일 읽기 좋아서 먼저 닿고, 거기엔 결론만 있고 함정은 없다.
함정은 확정 규칙에 적혀 있다 — 그 문서가 스스로 "계획 본문과 어긋나면 이 문서가
이긴다"고 밝히는데, 그 문장을 읽으려면 이미 그 문서를 펴야 한다.

**읽는 순서.** 위가 이긴다. 아래를 먼저 읽어도 되지만, 판단은 위로 올라가 확인한다.

| 층 | 어디 | 무엇 |
|---|---|---|
| 1 | `decisions/`, `*-rules.md` | 확정 규칙. 이미 정해진 것. 여기가 이긴다 |
| 2 | `decisions/ADR-*.md` | 판단과 근거. 왜 그렇게 정했나 |
| 3 | `design/`, `specs/` | 설계. 무엇을 만들기로 했나 |
| 4 | 코드 옆 머리말, 스키마 | 지금 도는 것. **1~3과 어긋날 수 있다** |
| 5 | `reports/`, `plans/`, `HANDOFF-*` | 그때의 기록. 지금이 아니다 |

4가 5보다 위인 이유는 4는 실제로 돌고 5는 안 돌기 때문이다. 4가 1과 어긋나면
**1이 맞고 4가 낡은 것**이다 — 09-28 머리말이 그랬다.

**한 번에 하나씩 확인하는 순서**

1. 그 주제의 확정 규칙이 있나 (`grep -rl "이 문서가 이긴다\|확정 규칙" docs/`)
2. 코드가 진실인 자리(스키마, 상수)를 뽑아 문서와 **일대일로 맞대 본다**
3. 운영 데이터를 실제로 파싱해 센다. 문서가 말하는 모양이 실물과 같은지
4. 고친 뒤 그 대조를 테스트나 검사로 남긴다

**막고 있는 것**

- `scripts/doc_claims.py` — 문서가 이름을 댄 파일이 지금도 있는지 전 저장소를
  훑는다. 현행 문서와 기록 문서를 갈라 보여주고, 레포를 건너 가리킨 것은
  낡음으로 세지 않는다. 09-28 첫 실행이 설계 22의 옛 자기 참조와
  `traffic-analytics.md`가 **"따로 클론하지 않는다"고 못 박은 배포 미러 경로**로
  안내하던 것을 잡았다.
- `tests/test_doc_claims.py` — 무엇을 안 집는지를 고정한다. 오탐이 많으면
  아무도 안 보고, 안 보는 검사는 없는 것과 같다(§3).
- mono `docs/design/README.md`의 상태 표, `CHANGE-PROPAGATION.md`의 전파 묶음.

**아직 없는 것.** 문서가 이름을 댄 **함수와 상수**는 안 본다. 경로만 본다.
그리고 층위(1~5)는 이 표에만 있고 기계가 강제하지 않는다 — 새 문서가 어느
층인지는 폴더 이름으로만 갈린다.

## §16. 세션이 이미 있는 것을 못 읽는다

§6과 §15가 수집기와 문서의 일이라면, 이것은 그 문서를 읽는 **에이전트 세션**의 일이다.
2026-09-06~10-15 세션 대화 기록에서 사용자가 바로잡은 순간을 모았다. 메인 82건, sub와 WSL 36건, 메인 자기 점검 9건이고 자기 점검은 메인 82건과 일부 겹친다.
근거 표는 [`AGENT-FAILURES.md`](AGENT-FAILURES.md)에 있다.

**결론.** 정본 목록은 한 곳(`claude-harness/MANIFEST.toml`)에 있고 매 세션 AGENTS 두 개와 rules가 주입된다.
그런데 HARNESS, ROUTINE-SPEC, ADR, 백로그, 핸드오프는 "필요할 때 읽음"이라 **읽을 계기가 없다.** 세션은 결정, 스크립트, 원장 원문이 있는데도 그 자리에 닿지 않았다.

**왜 되풀이되나.**

- 정본은 모여 있지만 "필요할 때 읽음" 층을 언제 읽는지가 없다. 매 세션 주입되는 것은 짧은 규칙뿐이고, 결정과 기록은 세션이 스스로 찾아가야 한다.
- 지침(ponytail, 메모리 `feedback_autonomy`)은 있다. 그러나 지침은 읽혀야 작동하고, 제안과 질문에는 걸리는 검사가 없다.
- 핸드오프는 수신 확인이 없다. 받는 세션이 안 읽어도 아무도 모른다.
- 결정의 주인을 가르지 않는다. 팀원 몫, 에이전트 몫을 사용자에게 넘긴다.

**제안하거나 묻기 전에 찾는 순서**

1. 원문: 원장 `raw_text`, 화면 덤프. 판단할 글자가 이미 거기 있는지 본다.
2. 결정: `git grep`으로 `docs/decisions/`, `docs/REFACTOR-BACKLOG.md`, `docs/setup/ROUTINE-SPEC.md`, 이 문서를 찾는다.
3. 구현: `scripts/`, `capture/`에서 같은 일을 하는 파일을 찾고 머리말을 읽는다.
4. 넘어온 일: `_dev/handoff-*.md`와 메모리 `handoff-*`의 "넘길 말".
5. 결정의 주인: 사용자, 팀원, 에이전트 가운데 누구인가. 문서를 쓴 쪽이나 올린 쪽이 정할 일은 사용자에게 묻지 않는다.

찾은 곳과 결과를 한 줄로 적고 나서 제안한다. 못 찾았으면 "찾은 곳: …, 없음"이라고 쓴다.

**핸드오프, 요약을 쓰는 쪽 규칙(2026-10-27).** 위는 읽는 쪽 규칙이다. 신규 세션에 프로젝트를 설명하는 요약을 쓰는 쪽에는 규칙이 없어, 센 적 없는 숫자와 출처가 섞인 문장이 그대로 나갔다([AGENT-FAILURES §5](AGENT-FAILURES.md)).

1. 줄마다 출처를 붙인다. `읽음(전문)`, `읽음(일부, 범위)`, `주입된 컨텍스트에서 옮김`, `이름으로 추정` 넷 중 하나다. 추정은 사실 문장에 섞지 않고 따로 모은다.
2. "읽은 범위 / 안 읽은 범위" 절을 둔다. 사용자가 묻기 전에 먼저 쓴다.
3. 숫자는 센 명령과 결과를 같이 적는다(`ls -d wt-* | wc -l` → 16). 못 셌으면 "약"이라 쓴다.
4. 저장소 이름, 경로, 커밋 같은 고유명은 파일에서 복사한다. 기억으로 쓰지 않는다(10-22에 `2026-to-discount-tracker`를 지어냈다).
5. 사실마다 `파일:줄`을 붙인다. 못 붙이면 추정이다.
6. 받는 쪽은 `- 받음: <식별값> (<시각>)`을 남긴다(위 "인계 수신").
7. 관련 있는 것만 추리고 정본 위치 하나를 적는다. 세션 새로고침용 정본은 한 곳이다.
8. 이슈와 인계는 앞 대화 없이 읽혀야 한다.

이 규칙은 아직 문서뿐이다. 2026-10-27 사용자는 커밋 때만 도는 점검이면 세션 컨텍스트와 토큰에 영향이 없으니 붙여도 좋다고 했다(여기서 "쓰는 쪽"은 핸드오프를 쓰는 쪽이다). 다만 지금 `claude-harness/check.py`가 보는 핸드오프(`memory/handoff_*.md`) 셋에는 "읽은 범위" 절이 하나도 없어서, 점검을 먼저 걸면 모든 세션의 하네스 커밋이 막힌다. 대상 파일과 기존 파일에 절을 채우는 순서를 정한 뒤에 붙인다.
