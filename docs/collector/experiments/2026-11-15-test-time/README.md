# 1단계 시험 시간 줄이기 (WSL 이관 실험에서 갈라져 나옴)

- 작성: 2026-11-15~16, sub 윈도 세션(사용자 지시). 이슈 #320, 같이 고친 #319.
- 한 줄 요약: 1단계 시험이 느린 원인은 운영체제가 아니라 **코드 한 곳**이었다. `brands.yml`을 부를 때마다 다시 읽는 함수 하나가 시험 시간의 약 63%를 썼다. 그것을 고치고, 병렬 실행을 막던 시험 하나를 고치고, 1단계를 병렬로 돌린다.

## 1 어디서 시작했나: WSL 이관 실험

`docs/experiments/2026-11-15-wsl-migration/README.md`(이슈 #315)가 출발점이다.

1. WSL 세션이 윈도와 WSL의 경계에서 마찰을 겪었다(훅 멈춤, 인코딩, `gh.exe` 경로, worktree 메타). 그래서 "필요한 부분만 WSL로 옮기고 단계마다 합격 기준으로 평가하자"는 실험을 세웠다.
2. 단계 A(작업 환경 이관)의 기준 A-2는 "실제 트리에서 1단계 시험이 윈도의 0.5배 이하"였다. 리눅스 ext4는 361~369초, 윈도 NTFS는 521~544초였다. 비는 약 0.70이라 **미달**이고, 사전 규칙상 A는 기각됐다.
3. sub 세션이 같은 문서의 부록 3으로 독립 재검증했다. 순서를 윈도 → 리눅스로 바꾼 3쌍에서도 비는 0.67~0.78(중앙값 0.68)이었다. 재현됐다.
4. 사용자가 물었다. "0.68이면 괜찮지 않나? 시험 묶음이 뭐지?" 답은 이랬다. 1.47배 빠른 것은 사실이지만 회차로는 약 2.8분, 회차 벽시계의 3~5%다. 그러면 **시험 자체가 왜 9분이나 걸리나**가 다음 질문이 됐다.
5. 사용자가 A를 기각으로 닫았다(11-15 23:3x). WSL 세션은 E0-8에서 병렬 실행(`-n 4`)을 쟀다. 윈도 335초, 리눅스 261초였고, 시험 하나가 병렬에서만 실패했다(#319).

## 3 원인: `_canon_brand()`가 부를 때마다 `brands.yml`을 다시 읽는다

`build_export`를 원장 전체(25,632행)로 한 번 돌려 cProfile로 쟀다.

- 102.5초 중 99.99초가 `export_data._canon_brand` 176회였다. 그 안은 전부 `yaml.safe_load`(순수 파이썬 로더) 177회다.
- `_canon_brand`는 별칭표(별칭 → 대표명)를 돌려준다. `build_export` 안에서 브랜드마다, `drop_stale_monthly_notes`가 362번 부르는 자리에서도 부른다. 부를 때마다 파일을 읽고 파싱한다.
- `build_export`를 부르는 시험은 레코드가 한 줄이어도 0.5~1초를 이 파싱에 쓴다. 그래서 상위 몇 개 시험만 봐서는 안 보이고, 시험 수백 개에 퍼져 있었다. E0-8의 "느린 시험 12개가 22~31%뿐이라 한 곳을 고쳐서는 안 준다"는 해석은 이것 때문에 틀렸다. 한 곳이 63%였다.
- libyaml이 설치돼 있었다(`yaml.__with_libyaml__ = True`). 그런데 C 로더(`CSafeLoader`)는 쓰지 않았다.

확인 실험. 저장소 밖 플러그인으로 `_canon_brand`만 캐시하고, 같은 시각과 같은 부하에서 전체를 돌렸다.

| 조건 | 벽시계 | 결과 |
| --- | --- | --- |
| 그대로 | 703초 | 2498 통과 |
| `_canon_brand` 캐시 | 259초 | 2498 통과 |
| 느린 8개 파일만, 그대로 | 298초 | 162 통과 |
| 느린 8개 파일만, 캐시 | 52초 | 162 통과 |

## 6 운영에 미치는 영향

- 1단계는 모든 폰 단계보다 먼저 돈다. 그래서 1단계가 줄어든 만큼 회차가 그대로 준다.
- 8단계 `reflect_daily.py`(830줄)가 `export_data.py`로 원장 전체를 내보낸다. 같은 `_canon_brand` 경로라 8단계도 짧아질 것으로 본다(추정, 다음 회차 로그로 확인).
- 병렬 1단계는 #319의 경합을 0.2초 여유로만 막았다. 스레드 지연이 그보다 큰 PC면 다시 흔들린다. 그때는 가짜 시계로 순서를 정하게 바꾼다.

## 7 배운 것

- "느린 시험 상위 N개"만 보면 여러 시험에 조금씩 퍼진 공통 비용을 놓친다. 함수 단위 프로파일(cProfile)을 먼저 본다.
- 운영체제를 옮기는 비용과 이득을 따지기 전에, 느린 이유가 코드에 있는지부터 본다. 이번에는 코드 한 곳이 이관 이득(약 170초)보다 컸다.
- 병렬에서만 실패하는 시험은 공유 상태 말고 **시간 여유**도 의심한다. 진짜 스레드와 `sleep`으로 순서를 시험하면 부하에 따라 결과가 바뀐다.
