# 윈도 → WSL 점진 이관 실험

- 작성: 2026-11-15, WSL 수집 감시 세션(사용자 지시)
- 상태: E0 완료, A 준비, B와 C 대기
- 규칙: 합격 기준은 단계를 시작하기 전에 고정한다. 바꿀 때는 맨 아래 "기준 변경 기록"에 줄을 남긴다. 앞 단계가 **검증**이어야 다음 단계를 시작한다.
- 결론 표기: **검증**, **기각**, **판정 불가** 중 하나. 일부만 맞으면 "부분"을 붙이고 무엇이 부족한지 적는다.
- **다른 세션이 재검증하려면 부록 3부터 읽는다.** 가정은 부록 1, 환경과 현재 상태는 부록 2, 원자료와 출처는 부록 4, 결과 기록 양식은 부록 5다. 이 문서의 모든 측정은 작성자 한 세션이 했다(독립 재현 없음).

| 단계 | 한 줄 가설 | 상태 |
| --- | --- | --- |
| E0 사전 조사 | 전부 옮기면 IO가 월등히 빨라진다 | 부분 검증, 부분 기각(E0-2는 A-2 측정으로 보정) |
| A 작업 환경 | 세션 작업을 WSL ext4 복제본에서 하면 마찰이 줄고 빨라진다 | **A-2 미달로 사전 규칙상 기각**, 마찰 부분은 미실험(사용자 결정 대기) |
| B 폰 없는 단계 | 1단계 시험을 WSL에서 돌리면 회차가 의미 있게 줄어든다 | **판정 불가**(시작 조건 미충족: 낮 회차 기대 이득 약 3.3~3.6%, 전수조사 회차 약 4.9%, 기준 5%) |
| C 폰 접점 | USB로 WSL에 붙인 폰으로 수집 생애주기가 윈도와 같게 돈다 | 미실험(스파이크) |

용어. **NTFS**는 윈도의 파일시스템이고 지금 저장소(`<사용자 폴더>\_dev\...`)가 여기 있다. **ext4**는 리눅스의 파일시스템이고 WSL 안의 홈(`<WSL 홈>`)이 여기 있다. WSL이 `/mnt/c`로 윈도 파일을 열면 윈도와 리눅스 사이의 다리를 파일 하나마다 건너는 요청이 된다.

## 0 배경: 어떤 상황에서 기원했는가

수집 PC는 윈도 네이티브다. 작업 스케줄러 `discount-after-open`이 하루 세 번 전수 수집을 돌리고(시각의 정본은 `docs/setup/ROUTINE-SPEC.md`), 폰 5대가 USB로 윈도에 붙어 있다. 폰은 `adb.exe`, scrcpy, 윈도 내장 OCR(`scripts/ocr_ko.ps1`)로 다룬다. 윈도 PowerShell을 부르는 파일이 10개, scrcpy가 19개 파일에 나온다(2026-11-15 `grep` 집계, `mono`, `tests`, `docs` 제외). 이 문장은 처음에 14개와 33개로 적었으나 제외 정규식이 동작하지 않아 시험과 문서를 포함한 개수였다(정정 기록).

세션은 세 그룹이다. main과 sub는 윈도 네이티브(PowerShell 전제), WSL 그룹(이 문서의 작성자)은 WSL에서 `/mnt/c`의 저장소를 윈도 도구(`adb.exe`, `gh.exe` 래퍼)로 다룬다.

2026-11-14 밤부터 11-15 오후까지(약 18시간) WSL 세션이 윈도와 WSL의 경계에서 겪은 일이 이 실험의 기원이다(기준선 B0, 시각은 근사).

1. 11-14 23:43 하네스 커밋 훅 `memory-index.py`가 WSL에서 부른 PowerShell에서 stdin을 기다리며 9분 멈췄다.
2. 11-14 23:5x PowerShell에 환경변수가 안 넘어가 커밋이 빈 채 실패했다(`WSLENV` 필요).
3. 한글 출력이 cp949와 UTF-8이 섞여 여러 번 깨졌다.
4. 11-15 00:3x `gh.exe`가 WSL 작업 폴더의 현재 경로를 못 풀어 `not a git repository: (NULL)`로 실패했다.
5. 11-15 02:4x WSL에서 만든 `git worktree`의 메타를 윈도 git이 정리해(`prunable`) 고아 폴더 2개가 남았다. 삭제는 자동 판정이 막아 사용자가 직접 지웠다.
6. 하루 내내 `/mnt/c` 저장소에서 `git status`가 4~15초 걸렸다.
7. (11-14 인계 기록) WSL의 하네스 커밋 훅이 `python`, `pytest` 부재와 윈도 경로 의존으로 통과하지 못해 커밋을 PowerShell에 고정해야 했다.

사용자 지시의 흐름은 이렇다. "OS 차이와 마찰 최소화", 세션 통합 도구(노드텀)에 대한 관심, "adb만 윈도에 남기고 나머지를 WSL로 옮기면 IO가 월등히 빨라지는가"라는 질문이 이어졌고, 마지막에 "최대 효율을 위해 필요한 부분만 점진적으로 이관하고 단계별로 유효성을 평가하자, 제안 순서와 합격 기준과 골든케이스에 동의한다"로 정리됐다.

제약. 운영 수집은 하루 세 번 서버 반영까지 이어진다. 실패하면 영향이 크다. 그래서 시험 기간에 **수집 런타임(윈도 NTFS 작업 트리, 작업 스케줄러, 폰 접점)은 바꾸지 않는다.** 또 main과 sub 세션도 A 단계가 검증되기 전에는 바꾸지 않는다.

기존 결정 확인. `find_prior.py WSL 이관` 결과 결정 기록은 0줄이었다(2026-11-15).

## E0 사전 조사 (2026-11-15, 완료)

주의. E0는 **성공 기준을 실험 전에 적지 않았다.** 사후에 기준을 정하면 결과에 맞춰지므로 "판정" 대신 관측이 가설을 지지했는지만 적는다. 숫자는 대부분 1~2회 측정이라 확정이 아니다. 재현 스크립트는 같은 폴더의 `io_bench.py`, `run_pytest_linux.sh`다.

### E0-1 파일 입출력

1. 가설. WSL이 `/mnt/c`를 거치면 윈도 직접보다 크게 느리다. 근거는 WSL 세션에서 `git status`가 4초 넘게 걸리던 경험.
2. 실험. 같은 추적 파일 827개(42MB)로 읽기, 작은 파일 1000개 쓰기(`fsync`), `git status`를 세 조건에서 잰다. 윈도 직접(NTFS), WSL ext4, WSL에서 `/mnt/c`.
3. 관측.

| 조건 | 읽기 | 작은 파일 1000개 쓰기 | `git status` |
| --- | --- | --- | --- |
| 윈도 직접(NTFS) | 0.16초 | 2.02초 | 0.09~0.17초(정정, 아래) |
| WSL ext4 | 0.07초 | 5.52초 | 0.01초 |
| WSL에서 `/mnt/c` | 7.14초, 10.16초 | 9.60초, 12.14초 | 4.03초 |

   **정정(2026-11-15, sub 재검증과 재측정).** 처음 적은 윈도 `git status` 0.69초는 갓 만든 폴더에서 **1회** 호출한 콜드 값이었다. 같은 방법(n=10 중앙값)은 sub 0.088초, 작성자 재측정 0.142~0.170초(새 복제와 `cp -r` 복사본 모두, 첫 호출은 최대 1.1초)다. 인덱스 캐시 문제는 아니다. 윈도 읽기 0.16초는 예열 뒤 값이고 sub는 예열 뒤 0.24~0.29초, 갓 복제한 폴더의 첫 읽기는 7.7초(Defender 검사로 추정)로 쟀다.
   표본은 이 PC 한 대, 조건당 1~2회다. 첫 비교는 `/mnt/c` 쪽이 작업 트리 전체(341MB)라 조건이 달라서 폐기하고 같은 파일 묶음으로 다시 쟀다.
4. 결론. **검증**: `/mnt/c`를 거치면 읽기가 약 50배 느리다. **기각**: "WSL ext4가 윈도보다 항상 빠르다". `fsync` 쓰기는 ext4(가상 디스크)가 윈도 직접보다 2.7배 느렸다.

### E0-2 1단계 시험 묶음의 속도

1. 가설. 수집 1단계 묶음(`-m "not ci_only and not non_gate"`)은 리눅스 ext4에서 윈도보다 2배 이상 빠르다.
2. 실험. 같은 얕은 복제본(추적 파일만, `mono`와 `data/` 없음)을 같은 시각에 윈도(Python 3.14, NTFS)와 WSL(Python 3.12, `uv` 가상환경, ext4)에서 돌린다.
3. 관측. 리눅스 95.5초, 윈도 229.8초(2.4배). 둘 다 `9 failed, 2477 passed, 6 skipped`이고 실패 9건이 같다. 9건 중 5건은 `mono/web/src/offerLink.js` 없음 2건, `mono` 브랜드 별칭표 없음 1건, 원장 데이터 의존 2건이다. 4건은 원인을 못 가렸다. 표본은 1쌍이다.
4. 결론. **부분 검증**. 부족한 것: 반복 측정, 파이썬 버전 차이와 안티바이러스 영향의 분리, `mono`와 `data/`가 있는 실제 트리. 실제 수집 1단계(482~812초)와 같은 조건이 아니다. 리눅스 비호환 증거는 못 찾았다(같은 9건이 두 환경에서 똑같이 실패).
   **보정(2026-11-15 18:1x, A-2 측정).** `mono`와 `data/`를 넣은 실제 트리에서는 같은 커밋에서 9건 실패가 모두 사라졌고(2492 통과, 실패 0, 둘 다), 속도 비는 **2.4배가 아니라 약 1.43배**였다(리눅스 361~369초, 윈도 521~544초, 3쌍). 얕은 복제의 2.4배는 가벼운 시험 묶음이라 생긴 과대 추정이었다. 이 보정 전의 문장("리눅스 2.4배를 그대로 가정하면 회차당 약 6분", E0-6)은 쓰지 않는다.

### E0-3 adb 호출 비용

1. 가설. adb만 윈도에 남기고 나머지를 WSL로 옮기면 adb 호출이 경계를 넘어 느려진다.
2. 실험. `adb -s <노트20> shell true`를 30회, `exec-out screencap -p` 5회, `uiautomator dump` 3회를 경로별로 잰다.
3. 관측. `shell true` 1회의 지연이다. 1차 값은 호출당 **평균**, 재측정(18:3x)은 **중앙값**이라 지표가 섞여 있다.

| 경로 | `shell true` 1회 | 측정 |
| --- | --- | --- |
| 윈도 직접(PowerShell, 파이썬) | 평균 98~107ms, 재측정 중앙값 113~123ms(최대 544~946ms) | 4회 |
| WSL → `adb.exe`(래퍼) | 평균 173~182ms, 재측정 중앙값 232, 269, 307ms(최대 629~1603ms) | 6회 |
| 리눅스 adb 무선(WSL) | 48ms(평균) | 1회 |

| 경로 | `screencap` | `uiautomator dump` |
| --- | --- | --- |
| WSL → `adb.exe` | 479ms | 2.50초(USB) |
| 리눅스 adb 무선 | 390ms | 2.36초 |

4. 결론. **검증**(방향): 측정한 모든 경우에서 WSL → `adb.exe`가 윈도 직접보다 느렸다. 격차는 1차 약 +75ms에서 재측정 +120~190ms로 달라졌다. 확정 수치가 아니라 범위(약 +60~+195ms)로 쓴다. 독립 재현(sub, 약 1분 간격 3회, n=30): 윈도 직접 중앙값 92, 95, 100ms, WSL → `adb.exe` 175, 179, 160ms, 격차 +60~84ms, 꼬리 최대 249ms로 작았다. 꼬리 지연도 크다(최대 1.6초). 큰 작업(`dump`)은 폰이 지배해서 전송 경로와 거의 무관하다. 회차당 adb 호출 수는 세지 못해 총 영향은 모른다. 리눅스 adb가 빠른 것은 전송 방식이 아니라 프로세스 기동 비용 차이로 보인다(추정, 분리하지 못함). 재측정 때 폰은 비행기 모드였고(`airplane=1`) 1차 때 상태는 기록하지 못했다.

### E0-4 리눅스 adb로 WSL에서 폰 제어

1. 가설. 리눅스 adb로 WSL에서 폰을 제어할 수 있다.
2. 실험. 구글 `platform-tools` 37.0.1(체크섬이 구글 저장소 목록과 일치)을 `~/lab/pt`에 설치. USB와 무선 두 경로를 시험. 무선은 노트20 한 대만 `adb tcpip 5555`로 켜고 `adb usb`로 복구했다(5대 `device`, tcp 포트 속성 `0`, 5555 닫힘 확인).
3. 관측. USB는 폰이 안 보였다(`usbipd-win` 미설치). 무선은 `devices.json`의 주소(노트20 .20, A8 .9)가 폰의 실제 주소(.10, .14)와 달라 `No route to host`. 실제 주소로는 `Connection refused`(길은 열림, 포트가 닫힘). `tcpip` 켠 뒤 `unauthorized`. 원인은 리눅스 adb가 자동 생성한 키가 이미 있어 `cp -n`이 윈도 키를 덮어쓰지 못한 것. 키를 교체하자 `connected`. 5대 중 무선 주소가 설정된 폰은 2대뿐. 코드 `capture/fleet/agent.py` 89~96줄이 무선 연결로는 비행기 모드를 켜지 않는다("켜면 adb가 끊겨 끄지도 못한다").
4. 결론. **부분 검증**: 무선은 1대, 1회 확인. USB는 **판정 불가**(`usbipd` 필요). 무선만으로는 수집기의 비행기 모드 생애주기가 깨져 수집에는 못 쓴다.

### E0-5 ext4 복제본의 git 인증

1. 가설. WSL ext4 복제본에서 git 읽기와 push 인증이 된다. 전역 설정이 윈도 자격증명 관리자(`git-credential-manager.exe`)를 가리키기 때문.
2. 실험. 얕은 복제(GitHub), `git ls-remote`, `git push --dry-run`.
3. 관측. 복제 5.5초, `ls-remote` 3.7초, `push --dry-run` 성공, 원격에 시험 브랜치가 안 생김(0건).
4. 결론. **검증**(읽기, dry-run까지). 실제 push는 이 문서의 커밋으로 A 단계에서 확인한다. `gh`는 리눅스판이 없고(`~/bin/gh`는 `gh.exe` 래퍼) 미시험.

### E0-6 회차 시간에서 폰이 없는 단계의 비중

1. 가설. 폰 없는 단계(1, 1b, 5b, 8)는 회차 시간에서 작다. 그래서 이 단계만 빨라져도 회차는 조금만 준다.
2. 실험. `after-open-2026-11-15.log`의 `소요:` 줄 세 회차를 합산한다.
3. 관측(`e06_summarize.py`, 로그의 시작과 끝 시각으로 계산). 폰 없는 단계(1, 1b, 5b, 8)의 합과 벽시계 대비 비중은 00:37 전수조사 회차 795초 / 4496초 = **17.7%**, 08:30 낮 회차 569초 / 4834초 = **11.8%**, 14:05 낮 회차 659초 / 5030초 = **13.1%**다. 그중 1단계와 1b가 약 92%다. 1단계는 모든 폰 단계의 선행이라 줄이면 회차가 그대로 준다. 폰 단계의 최장 연쇄는 3 → 3s → 6 → 7로 약 4,000초다.
4. 결론. **검증**(작다, 다만 "약 11%"로 적었던 것을 낮 회차 11.8~13.1%로 정정한다). 당초 "리눅스 2.4배를 가정하면 회차당 약 6분"이라고 적었으나 A-2에서 실제 트리 비율이 0.70(1.43배)로 나와 1단계와 1b(낮 회차 523~608초)가 30% 줄면 **회차당 약 157~182초(벽시계의 3.2~3.6%)**, 전수조사 회차는 734초 × 30% = 약 220초(**4.9%**)로 보정한다(가정 G3: 1+1b가 대부분이라 같은 비율로 본다).

### E0-7 세션 통합 도구 조사

1. 가설. 윈도 네이티브 세션과 설정 폴더 3개를 한 화면에서 보고 지휘할 기존 도구가 있다.
2. 실험. 웹 검색과 공식 문서, 레포 README 직접 확인. 설치하지 않았다. 자사 제품 비교 글은 근거로 쓰지 않았다.
3. 관측.
   - 공식 에이전트 뷰(`claude agents`, 이 설치 2.1.325): `--json`이 이 설정 폴더(WSL 그룹) 세션만 보였다. 문서는 `CLAUDE_CONFIG_DIR`마다 별도 인스턴스라고 적는다. 터미널에서 직접 연 세션은 `/bg`로 백그라운드에 보내야 목록에 뜬다. 윈도 지원 문구는 못 찾았고 WSL도 안 나온다.

### E0-8 시험만 옮기거나 병렬로 돌리면 얼마나 빨라지나 (사후 탐색)

주의. 사용자 질문("시험만이라도 이관하면 빨라지는 것 아닌가")에 답하려고 **기준 없이** 잰 탐색이다. 그래서 판정은 관측의 해석까지만 쓴다. 원자료는 `results/e0-8-xdist.txt`.

1. 가설. (a) 시험만 WSL ext4로 옮기면 1단계가 빨라진다. (b) 이관이 아니라 병렬 실행(`pytest-xdist`, 4코어)이 더 큰 레버일 수 있다. (b)를 본 이유: 느린 시험 12개가 pytest 시간의 22~31%뿐이고 나머지 약 70%는 시험 약 2,500개가 평균 0.17초씩 나눠 쓰는 긴 꼬리라, 한 곳을 고쳐서는 안 줄고 코어를 쓰는 것이 맞아 보였다.
2. 실험. (a)는 A-2의 직렬 3쌍을 쓴다. (b)는 같은 시험 묶음에 `-n 4`를 붙여 리눅스 ext4와 윈도(임시 가상환경, 수집 트리에서 시험만)에서 1회씩 잰다. 수집(import)만 따로 2.0초로 쟀다.
3. 관측.

| 조건 | 소요 | 결과 |
| --- | --- | --- |
| 윈도 직렬(A-2) | 521~544초 | 2492 통과 |
| 리눅스 직렬(A-2) | 361~369초 | 2492 통과 |
| 리눅스 병렬 `-n 4` | 261초 | 2492 통과, 실패 0 |
| 윈도 병렬 `-n 4` | 335초 | 2497 통과, **1 실패** |

   윈도 병렬은 수집 트리가 그새 `8050ff44`로 바뀐 뒤라 시험이 2498개로 6개 많다(같은 커밋이 아님). 실패는 `test_run_routine_pool.py::test_preferred_phones_run_their_steps`(단계 4c 배정이 `PH1`이 아니라 `PH4`일 것을 기대)이고 같은 가상환경에서 **단독 실행하면 통과**했다(9초). 2026-11-14 인계 메모리에 같은 시험이 "전체 실행에서만 실패, 단독은 통과"로 이미 적혀 있다.
4. 결론. (a) **검증(작음)**: 시험만 옮기면 약 1.4배, 1단계 약 168초(2.8분)가 준다(B에서 이미 계산). (b) **부분 검증**: 병렬은 이관 없이 윈도에서도 1.6배 정도 빠르다(521~544초 → 335초). 리눅스에서는 1.4배(361 → 261초)다. 둘을 합치면 윈도 직렬 대비 약 2.0배다. 그러나 **병렬은 순서 의존 시험을 드러낸다.** 1단계는 실패하면 그 회차 수집을 통째로 막는 문이라(`[abort] 테스트가 깨졌다`) 병렬로 바꾸기 전에 그 시험부터 고쳐야 한다. 표본은 각 1회(윈도와 리눅스의 커밋이 다름)라 실패율은 모른다(판정 불가). 코어 4개에서 기대한 3배가 아니라 1.4~1.6배에 그친 이유는 분리하지 못했다(수집 시간은 2초라 아니다. 추정: 긴 시험 몇 개의 직렬 부분과 N100의 낮은 전 코어 속도).

### E0-9 세션 오케스트레이션 방법 재조사 (사후 탐색, 2026-11-15 23:4x)

1. 가설. A를 접은 뒤에도 세션 사이 마찰을 줄일 기존 도구나 기능이 있다.
2. 실험. 공식 문서 직접 읽기(`code.claude.com/docs/en/agents`, `cross-session-messaging`, `agent-view`)와 웹 검색. 설치하지 않았다. 이 PC에서 `ListAgents`만 한 번 호출했다.
3. 관측.
   - 공식 병렬 방식은 다섯 가지다: 서브에이전트(한 세션 안), 에이전트 뷰(`claude agents`, 백그라운드 세션 목록과 지휘), 에이전트 팀(실험, 기본 꺼짐, 리더가 조율), 프로젝트(클라우드, claude.ai 로그인 필요), 동적 워크플로(스크립트가 서브에이전트를 조율).
   - **세션 간 메시지(`ListAgents`와 `SendMessage`)가 이미 내장돼 있다.** 맥, 리눅스, WSL 2는 v2.1.224 이상, 네이티브 윈도는 v2.1.234 이상이고 켤 것이 없다. 같은 PC 안에서는 세션마다 소켓(윈도는 네임드 파이프)으로 직접 주고받는다. 받는 쪽이 쉬고 있으면 새 턴이 시작된다. 한 세션이 쉬거나 끝날 때 알림을 한 번 받을 수도 있다(`notify_when_idle`, v2.1.236 이상).
   - **한계(문서 원문): "WSL 2 안의 세션과 같은 컴퓨터의 네이티브 윈도 세션은 서로 닿지 않는다."** 다른 PC나 클라우드 세션은 Remote Control로 닿는데, claude.ai 로그인이 필요하고 API 키로는 안 된다. 이 PC에서 `ListAgents`는 "닿는 세션 없음"이었다(WSL 그룹 세션 하나만 떠 있었음).
   - 에이전트 뷰: `CLAUDE_CONFIG_DIR`마다 감독자가 따로라 설정 폴더 셋(main, sub, WSL)을 한 화면에 못 모은다(E0-7과 같음). 일반 터미널로 연 세션은 `/bg`로 백그라운드로 보내야 목록에 뜬다. `claude agents --json`에 `state`, `status`, `waitingFor`(권한 승인이나 입력 대기), `cwd`, `name`이 있다.
   - 서드파티(검색 요약만, 원문 미확인): Opcode(AGPL, 윈도 설치 파일 있음, 세션 브라우저에 가까움), CloudCLI(웹 UI), amux(웹 대시보드, 판매사의 자기 비교 글이라 편향 있고 윈도 언급 없음), ccmanager와 Jarvis와 Claude Squad(tmux나 유닉스 소켓 기반이라 윈도 네이티브 의심). 어느 것도 "윈도 네이티브 세션을 가져온다"는 문서를 못 찾았다.
4. 결론. **판정 불가(설치 시험 없음), 방향만 얻음.**
   - 지금 인계 파일 규약(id, 받음 줄)이 하는 일 중 **윈도 main과 sub 사이**는 내장 메시지로 대신할 수 있을 가능성이 있다. 두 세션이 같은 윈도 네이티브이고 같은 PC이기 때문이다(윈도 쪽 Claude Code 버전이 v2.1.234 이상인지와 설정 폴더가 달라도 서로 보이는지는 **미확인**).
   - **WSL 그룹과 윈도 그룹 사이는 내장 메시지로 못 닿는다.** 인계 파일이 계속 필요한 이유이고, 두 그룹이 갈라진 마찰의 구조적 원인이다. 이것이 WSL로 세션을 모으자는 주장의 가장 강한 근거가 될 수 있으나 측정한 적 없고 A는 이 가설로 평가하지 않았다. 필요하면 새 가설로 사전 등록한다.
   - 단기 비용 최저안은 E0-7과 같다: 설정 폴더마다 `claude agents --json`을 읽어 합치는 작은 스크립트(미시험).

## A 작업 환경 이관

### 1 가설

WSL 그룹 세션의 저장소 작업(복제, 시험, 커밋, push, PR)을 `/mnt/c`가 아니라 **WSL ext4 복제본과 리눅스 도구**에서 하면 윈도-WSL 경계 마찰이 줄고 시험과 git이 빨라진다.

고른 이유. E0-1(`/mnt/c` 읽기 50배 느림), E0-2(시험 2.4배), E0-5(push 인증 가능)가 방향을 지지하고, 기준선 B0의 마찰 7건이 모두 "WSL이 윈도 파일과 도구를 만지는 지점"에서 나왔다. 수집 런타임은 건드리지 않으므로 운영 위험이 작다.

### 2 실험

- 범위. WSL 그룹 세션 1개와 저장소 3개(tracker, mono, beggars-ops)의 ext4 복제본. `claude-harness`는 제외한다(2026-11-15 정정): 원격이 없고 main, sub, WSL 세 그룹의 설정 폴더가 심볼릭 링크와 정션으로 가리키는 정본이라 복제로 옮길 수 없다. 하네스 파일은 계속 NTFS에서 고친다. main과 sub 세션, 수집 런타임(NTFS 작업 트리, 작업 스케줄러)은 안 바꾼다.
- 준비. (A1) 전체 이력 복제 (A2) 리눅스 `gh`를 사용자 영역에 설치(체크섬 확인)하고 인증, 토큰은 출력하지 않는다 (A3) 시험은 ext4 복제본과 `uv` 가상환경 (A4) 마찰 사건은 `handoff_wsl.md`에 `마찰:` 줄로 한 줄씩 기록.
- 기간. 7일, 작업 흐름(커밋 → push → PR → CI 대기 → 병합) 10건 이상.
- 합격 기준(전부 사전 고정).

| # | 기준 | 측정 |
| --- | --- | --- |
| A-1 | 전체 이력 복제본에서 `git status` 중앙값 0.5초 이하 | 저장소 3개 각각 10회 이상(기준선: `/mnt/c` 4.03초, 전체 작업 트리 15초) |
| A-2 | `mono`와 `data/`가 있는 복제본에서 1단계 시험 묶음 소요가 윈도 NTFS 실제 트리의 0.5배 이하 | 같은 시각 3쌍. 통과와 실패 집합이 같아야 함 |

### 4 결론

**기각** (사전 판정 규칙 적용: A-1~A-3 중 하나라도 미달이면 기각). 미달 기준은 **A-2**다. 같은 커밋의 실제 트리에서 시험 소요 비가 중앙값 약 0.70(리눅스가 약 1.43배 빠름)으로 기준 0.5(2배)에 못 미쳤다. 통과 집합은 같아서 리눅스 비호환은 아니다. sub의 독립 재현(윈도 → 리눅스 순서, 비 중앙값 0.68)에서도 같은 판정이 나온다.

범위를 정확히 적는다. 이 기각이 **부정한 것**은 "시험이 2배 이상 빨라진다"뿐이다. git 속도(A-1)는 충족했다. 마찰 감소(A-3, A-4)는 아직 측정하지 않았다. 마찰 감소가 이관의 주된 이유이므로 이 기각만으로 A를 접으면 가장 중요한 부분을 안 본 채 닫는 셈이다.

**확정(2026-11-15 23:3x, 사용자): A는 기각으로 닫는다. A'는 만들지 않는다.** 이유: 수용할 근거가 약하다. 사전 기준 A-2(2배)가 미달이고, 독립 재현도 같은 판정이다. 주된 이유로 든 마찰 감소(A-3, A-4)는 측정하지 않았고, 측정 방법도 사후에 정의한 것이라 이관을 정당화하는 근거가 못 된다. 시험 병목은 sub 세션이 따로 개선 중이라 이 실험에서는 더 다루지 않는다(순서 의존 시험은 tracker #319). ext4 복제본(`~/work`)과 `~/lab`은 용량 부담이 없어 유지하되 운영에는 쓰지 않는다. 아래는 확정 전 열린 결정의 원문이다(기록 보존).

**열린 결정(사용자, 확정 전 원문).** 기준을 사후에 바꾸는 것은 결과에 맞추는 일이라 이 문서는 임의로 바꾸지 않는다. 선택지는 둘이다. (a) A를 기각으로 닫는다. (b) 별도 가설 **A'**(작업 환경 이관은 시험 속도가 아니라 마찰과 git 속도로 평가한다)를 새로 사전 등록하고 A-2를 빼고 A-1, A-3~A-6을 그대로 쓴다. (b)를 고르면 "기준 변경 기록"에 이유와 시각을 남기고, A의 기각 결론은 그대로 둔다. 어느 쪽이든 ext4 복제본 사용은 운영에 영향이 없어 계속해도 된다.

## B 폰 없는 단계를 WSL에서 호출

### 1 가설

수집 1단계 시험을 `wsl -e`로 WSL에서 돌리면 회차당 5분 이상 줄고 새 실패 모드가 없다.

고른 이유. E0-6이 상한을 정한다. 낮 회차의 약 11%라서 이득은 최대 7% 안팎으로 작다. 그래서 A가 검증된 뒤에 시작하고, 이득이 작으면 접는다.

### 2 실험

- 시작 조건. A가 **검증**이고, E0-6을 최근 10회차 중앙값으로 다시 재서 폰 없는 단계가 회차 벽시계의 5% 이상이다. 5% 미만이면 시작하지 않고 **판정 불가**로 닫는다.
- 방식. 운영 회차에 영향이 없게 **회차가 끝난 뒤** 같은 커밋에서 WSL 시험을 돌려 윈도 1단계 결과와 맞대는 섀도 실행으로 한다. 수집 트리는 NTFS에 둔다.
- 합격 기준.

| # | 기준 | 측정 |
| --- | --- | --- |
| B-1 | 통과와 실패 집합이 같은 회차 10/10 | 같은 커밋 기준 |
| B-2 | WSL 소요 중앙값이 윈도 1단계 소요의 0.4배 이하 | 10회차 |
| B-3 | 예약 실행 컨텍스트(무인)에서 `wsl` 호출 성공 10/10 | 작업 스케줄러에서 |
| B-4 | 윈도 재부팅 직후 첫 회차를 포함해 호출 성공 1회 이상 | 재부팅 후 5분 안 |
| B-5 | WSL 호출 실패 시 윈도 폴백으로 같은 시험을 돌려 회차 지연이 5분 이하 | 일부러 WSL을 끈 시험 1회 |

- 판정 규칙. B-1~B-5 전부 충족하면 **검증**. 하나라도 미달이면 **기각**. 기대 이득이 5% 미만이면 **판정 불가**로 닫는다.

### 3 관측

시작하지 않았다. 시작 조건 평가만 했다. A-2의 실제 트리 비율(0.70)로 보면 1단계가 윈도 531초에서 리눅스 363초로 줄어 회차당 약 168초(약 2.8분)다. 낮 회차 벽시계(08:30 회차 4834초, 14:05 회차 5030초)의 3.3~3.5%이고 시작 조건 5%에 못 미친다. 전수조사 회차는 1+1b 734초의 30%인 약 220초가 벽시계 4496초의 4.9%로 **기준에 가깝다.** (이 문단의 앞선 판본은 "전수조사 회차는 비율이 더 작다"고 적었으나 근거가 없었고 계산하니 반대였다. 정정 기록 참고.)

### 4 결론

**판정 불가**(시작 조건 미충족으로 닫는다). 가설이 틀렸다고 보는 것이 아니라 시험할 가치가 사전 기준(5%)에 못 미친다. A나 다른 이유로 회차의 폰 없는 단계 비중이 달라지면 다시 평가한다.

## C 폰 접점 스파이크

### 1 가설

`usbipd-win`으로 WSL에 붙인 폰 1대로 수집기의 생애주기(깨우기 → 비행기 모드 켜기와 끄기 → 앱 정리 → 단계 1개)가 윈도와 같은 결과로 돈다.

사전 기대. **작성자는 합격 가능성이 낮다고 본다.** 이유. 무선은 생애주기와 충돌하고(E0-4), USB 통과는 미시험이며, scrcpy(V50 깨우기, 땡겨요 링크 복사)와 윈도 OCR(`ocr_ko.ps1`)이 윈도 전제다. 그래도 스파이크로 확인하는 이유는 비용이 큰 결정을 추정만으로 닫지 않기 위해서다.

### 2 실험

- 범위. 폰 1대, 수집 정지 중 또는 수집 사이 빈 시간. 운영 수집과 겹치지 않게 인계 파일에 `잡음`을 먼저 적는다.
- 골든케이스(사용자 동의).
  - **G1 OCR 골든.** `capture/ocr.py`가 쓰는 입력의 실제 캡처 30장 이상. 릴레이 슈퍼딜 머리표("선착순 할인 쿠폰 오후 N시 오픈")와 허브 공유 버튼 크롭 등. **정답은 사람이 확정한 파서용 토큰**(시각 N시, "공유" 포함 여부)이다. 윈도 OCR 출력은 참고값이지 정본이 아니다. 지금 시험은 OCR을 가짜로 대체해서 실제 OCR 골든이 없으므로 이 세트를 먼저 만든다.
  - **G2 단계 골든.** 같은 폰과 같은 날 5단계(배민 쿠폰함) 또는 5y 출력 JSON을 정규화한 해시가 윈도 실행과 같다(덤프 방식 실험의 H6와 같은 방법).
  - **G3 생애주기 골든.** 깨우기, 비행기 모드 켜기와 끄기, 앱 정리의 상태 전이 순서와 성공 여부가 윈도 실행의 `fleet` 사건 기록과 같다.
- 합격 기준.

| # | 기준 | 측정 |
| --- | --- | --- |
| C-1 | 생애주기 무인 연속 3회 성공 | 같은 폰, 비행기 모드 켜기와 끄기 포함 |
| C-2 | 윈도와 WSL 재부팅 뒤 사람 개입 없이 5분 안에 폰이 다시 붙음 | 재부팅 1회 |

## 5 기능이나 도구에 대해 배운 것

**WSL과 파일시스템**
- `/mnt/c`(윈도 디스크)는 파일 하나마다 윈도와 리눅스 사이의 다리를 건넌다. 작은 파일이 많은 작업(`git status`, 시험 수집)에서 50배까지 느려진다. WSL ext4는 읽기가 빠르지만 `fsync` 쓰기는 가상 디스크라 윈도 직접보다 느렸다.
- WSL 네트워크 기본값은 NAT(`.wslconfig` 없음)다. NAT에서도 LAN의 폰까지 닿는다. `Connection refused`는 길이 열렸고 포트만 닫혔다는 뜻이고, `No route to host`는 주소가 틀렸다는 뜻이다.
- WSL에서 `adb.exe` 같은 윈도 실행 파일을 부르면 호출마다 약 75ms가 더 든다.
- 얕은 복제본(추적 파일만)으로 잰 속도는 실제 트리의 속도를 과대 평가한다. 시험 묶음이 가볍고 `mono`와 `data/` 없이는 일부 시험이 실패한다. 속도 비교는 실제 트리와 같은 커밋으로 번갈아 여러 쌍을 재야 한다(A-2에서 2.4배가 1.43배로 바뀜).
- 같은 시험을 윈도에서 돌리면 약 520~540초, 리눅스 ext4에서 약 360초다(실제 트리). 수집 1단계의 482~812초와 같은 범위다.
- WSL의 `sudo`는 이 환경에서 비밀번호가 필요해 `apt` 설치가 안 된다. `unzip`과 `python3-venv`(`ensurepip`)도 없다. 사용자 영역 설치로 풀었다(`uv` 단일 실행 파일, `python3 -m zipfile`).

**git, gh**
- WSL의 전역 `credential.helper`가 윈도 `git-credential-manager.exe`를 가리켜서 WSL ext4 복제본도 GitHub 인증이 된다.
- WSL이 만든 `git worktree`의 메타는 윈도 git이 정리한다(`prunable`). 폴더만 고아로 남는다.
- `gh`는 윈도 실행 파일 래퍼라 WSL 경로와 현재 폴더를 못 푼다. `--body-file`에는 윈도 경로를 줘야 한다.
- PR 병합은 `/approve` 댓글 워크플로(`wf-approve`, squash)다. 자동 판정이 지시 범위를 벗어난 병합과 폴더 통째 삭제를 막는다.

**adb와 폰**
- 무선 adb는 폰이 `adb tcpip`로 켜져 있어야 하고(`service.adb.tcp.port`가 `0`이면 꺼짐), 재부팅하면 꺼진다. `devices.json`의 무선 주소는 DHCP로 바뀌어 오래된 값이었다.
- 새 adb 호스트는 키가 달라 `unauthorized`가 된다. 기존 키를 `cp -n`으로 복사하면 이미 있는 자동 생성 키를 못 덮는다(`--remove-destination` 필요).
- 수집기는 무선 연결로 비행기 모드를 켜지 않는다. USB가 전파 차단에도 살아남기 때문이다.

**PowerShell과 환경 변수**
- WSL에서 `powershell.exe`를 부를 때 stdin을 닫지 않으면(`</dev/null`) 파이썬 훅이 stdin을 기다리며 멈춘다.
- 환경변수는 `WSLENV`에 적어야 윈도로 넘어간다.
- 출력 인코딩은 `[Console]::OutputEncoding`과 `PYTHONUTF8`을 맞춰야 한다.

**Claude Code와 도구**
- `claude agents --json`은 읽기 전용 목록(프로세스를 남기지 않음)이고 설정 폴더마다 따로 보인다.
- 에이전트 뷰의 "막힘(blocked)"은 사람이 답할 것(질문, 권한, 만료된 로그인)을 기다리는 상태다.
- `uv`는 sudo 없이 가상환경과 패키지 설치가 되어 이 시험의 파이썬 환경을 5초 안에 만들었다.
- 노드텀은 라이선스(BUSL-1.1)와 윈도 베타 한계가 있고, 같은 이름 포크가 많아 설치 전에 정본을 확인해야 한다.

**수집 운영**
- 작업 스케줄러에서 `예약된 작업 상태: 사용`이면 켜진 것이다. 도는 프로세스를 끊어도 예약은 남는다.
- 프로세스를 이름 패턴으로 찾아 종료할 때(`pgrep -f`) 내 셸의 명령줄도 걸린다. 스크립트 파일로 쓰고 PID로 종료해야 한다(exit 144로 확인).
- 1단계는 모든 폰 단계의 선행이다. 그래서 1단계 단축은 회차 길이에 그대로 반영된다.

## 부록 3 재검증 절차 (윈도 세션과 WSL 세션이 각자 돌릴 수 있게)

### 3-0 시작 전에 지킬 것

1. **수집 시각을 피한다.** 예약 작업이 켜져 있다(시각은 `docs/setup/ROUTINE-SPEC.md`). 폰이나 수집 트리를 쓰는 측정은 그 시각 전후 30분 안에 하지 않는다. 시작 전 인계 파일(`memory/handoff_*.md`)에서 `잡음` 줄과 `collect_trial` 잠금을 확인하고, 폰을 잡으면 자기 인계 파일에 `잡음`을 먼저 적는다.
2. **수집 트리(`<사용자 폴더>\_dev\delivery-discount-tracker`)에서 `pull`, `checkout`, 파일 수정을 하지 않는다.** HEAD가 바뀌면 다음 수집 코드가 바뀐다. 이 트리에서는 시험(`pytest`)을 돌리는 것까지만 한다. 문서는 `git fetch` 없이 GitHub에서 읽거나 임시 폴더에 복제해서 읽는다.
3. **폰 설정을 바꾸는 명령을 쓰지 않는다.** `adb tcpip`, `adb usb`, 비행기 모드 변경, 앱 설치와 삭제 금지. 읽기 전용(`shell true`, `getprop`, `settings get`)만 쓴다. E0-4는 폰 설정을 바꿨던 실험이라 재현하지 않고 사실 확인만 한다(3-8).
4. **비밀 값을 출력하지 않는다.** `~/.android/adbkey`는 있는지만 확인한다. `gh` 토큰과 `<슬랙 키 파일>`는 열지 않는다.
5. **push, PR, 이슈 생성을 하지 않는다.** 결과는 새 파일(부록 5 양식)로 저장하고 커밋 여부는 사용자에게 묻는다.
6. 윈도 세션은 **PowerShell**을 쓴다. 윈도에서 돌릴 스크립트에는 **한글을 넣지 않는다**(BOM 없는 UTF-8 `.ps1`은 PowerShell 5.1이 ANSI로 읽어 깨진다. sub 재검증에서 한글 주석이 있는 스크립트가 깨졌다). 파이썬 스크립트나 영문만 쓴다. 한글 파일은 `Set-Content`와 `Out-File`로 쓰지 말고 Write 도구로 쓴다(인코딩). PowerShell 5.1의 `*>` 리다이렉트 파일은 UTF-16이라 읽을 때 `Get-Content`를 쓰거나 WSL에서 `iconv -f utf-16 -t utf-8`로 읽는다.
7. `wsl.exe -e bash -lc '... && ...'` 한 줄은 일부 PowerShell 도구에서 따옴표가 깨진다(sub 재검증). 깨지면 명령을 `.sh` 파일로 쓰고 `wsl.exe -e bash <파일>`로 돌린다.
8. WSL에서 `powershell.exe`를 부르면 stdin을 닫는다(`</dev/null`). 안 닫으면 파이썬 훅이 멈춘다. 환경변수는 `WSLENV`에 적어야 넘어간다.
9. 이 문서와 스크립트를 읽는 방법(수집 트리를 안 건드림): `gh api repos/nn98/delivery-discount-tracker/contents/docs/experiments/2026-11-15-wsl-migration/README.md -H "Accept: application/vnd.github.raw"` 또는 임시 폴더에 얕은 복제.
