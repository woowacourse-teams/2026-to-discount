# 수집 장애 기록: 증상에서 조치까지

수집이 깨지는 방식은 대개 **틀린 값이 나오는 게 아니라 값이 조용히
사라지는 것**이다. 순회는 정상 종료하고 "성공 N / 실패 0"을 찍는다.
그래서 증상만 보고 원인을 찾을 수 있게 여기 모은다.

새 장애를 겪으면 **증상 한 줄, 확인 명령, 원인, 조치**를 같은 모양으로
덧붙인다. 판단이 걸린 것은 ADR로 빼고 여기서는 링크만 건다.

여기 쌓인 것들이 **같은 모양으로 되풀이되는 이유**는
[HARNESS.md](../HARNESS.md)에 패턴으로 정리돼 있다. 새 장애를 적기 전에 그 문서에서
같은 패턴을 먼저 찾아보면, 고칠 자리가 이 화면이 아니라 그 패턴을 막는
장치일 때가 많다.

## 빠른 점검 (무엇이 이상하면 여기부터)

**폰을 잡기 전에 먼저. 지금 뭐가 돌고 있나.** 예약 실행이 도는 중이면
내가 띄운 앱을 그쪽이 앞으로 끌어간다. 그리고 **몇 시간째 안 끝난 것이
있는지**를 시작 시각으로 본다(§8: 멈춘 실행은 아무 출력도 안 남긴다).

```powershell
Get-CimInstance Win32_Process -Filter "Name like '%python%'" |
  Select-Object ProcessId, CreationDate, CommandLine | Format-Table -AutoSize
# 오래 매달린 게 있으면 무엇을 기다리는지 자식 프로세스로 본다
Get-CimInstance Win32_Process -Filter "ParentProcessId=<PID>" | Select-Object Name, CommandLine
```

```bash
python check_brands.py            # 미등록 브랜드 / 엔티티 깨진 이름 / 카테고리 미기입 / searchAliases 미기입
python scripts/deploy_export.py   # 로컬과 서버 건수·최신 시각 비교 (미리보기)
python -m pytest tests/ -q        # 판독 회귀
```

CI(GitHub Actions)가 로컬 pytest보다 넓게 본다. mono의
`generate_project_structure.py --check`와 api의 `BrandCatalogTest`는
tracker 저장소 pytest가 전혀 모르는 규칙이다. **로컬이 초록이어도 배포가
막힐 수 있다**(아래 두 항목이 실제로 그랬다). 커밋 전에:

```bash
cd mono && python scripts/generate_project_structure.py --check
```

## 2026-11-18: 서버 업로드 큐에 반영 실패 배치가 있어 8단계가 실패한다 (#373)

- 증상: 8단계 FAIL. 로그에 `서버 업로드 큐에 반영 실패 배치 N건이 있어 더 올리지 않는다`(올리기 전 큐 점검) 또는 `업로드 반영 실패: 배치 … 단계 … 사유 …`(reload 409). 대기 폴더 경유 업로드(`DEPLOY_OPERATIONS_BACKUP_LOCK=1` 또는 콘솔 스위치)가 켜졌을 때만 난다. 방치하면 같은 묶음의 뒤 배치가 전부 쌓이기만 한다.
- 담당: **수집 PC 운영자**. 8단계 실패 알림을 받은 사람이 그날 안에 푼다(다음 회차 8단계 전).
- 확인: 로그 줄의 배치 번호, 묶음, 실패 단계(`failureStage`), 사유. 서버 큐는 `collector_upload.queue_status`가 읽는다(`_ssh.queue_blockers`가 같은 함수로 failed 배치만 고른다).
- 조치(기본 `--retry`): 반영 단계 실패(`reload` 등)이고 배치 데이터가 맞으면 `python3 <서버>/ops_backup_upload.py --retry 배치번호`. 서버 일시 장애가 대부분이다.
- 조치(`--replace`): 배치 **데이터가 틀렸을 때만**(검증 단계 실패, 원장 정정이 필요한 값) 원장을 고치고 다시 올린 뒤 `--replace 실패번호 새번호`로 나중 업로드가 대신하게 한다. 검증 단계 실패는 `--retry`로 안 풀린다.
- 막는 것: 8단계 두 안내(`scripts/_ssh.blocked_message`, `banner_server.reload_server`의 409)가 같은 담당·기준 줄(`_ssh.QUEUE_OWNER_HINT`)을 내고 `tests/test_staged_upload.py`가 그 줄을 고정한다.

## 2026-11-13: 요기요 캐러셀 또는 행사 페이지를 못 읽는다 (#162)

- 증상: 6단계가 SUSPECT, 사유 `요기요 캐러셀 못 훑음(<종류>)`, `요기요 행사 N곳 못 읽음`, `링크 정리 필요`, `요약 줄 없음`. 로그에 `capture_failed: yogiyo 할인/혜택 탭을 못 찾았다`, `행사 페이지가 안 열렸다`. 못 읽은 날은 배너를 그대로 둔다.
- 확인: 로그 줄의 종류(`blank` 트리 없음 · `outside` 앱 밖 · `error` 오류 알림 · `loading` 웹 내용이 안 옴 · `other_page` 그려졌는데 기대한 꼴이 아님)와 증거 그림 `captures/_evidence/yogiyo-event-*.png`, `yogiyo-tab-*.png`(같은 이름의 `.xml`이 뷰 트리). `data/yogiyo_events.json`의 `fail_days`, `last_ok`.
- 조치: `outside`, `blank`는 폰 상태(화면 꺼짐, 다른 앱)다. 탭 찾기는 한 번 다시 띄워 본다. `loading`이 늘면 기다림(30초)을 본다. `other_page`가 쌓이면 화면 구조가 바뀐 것이니 증거로 탭 찾는 방식을 바꾼다(설계 §8). 닫힌 행사 링크는 `python scripts/yogiyo_events.py retire <주소>`.
- 원인: 2026-11-04 15:55 세 줄의 원인은 화면이 안 남아 가리지 못했다. 이번 변경 뒤의 실패부터 종류가 남는다.

## 2026-11-03: 슬랙에 "비행기 모드를 못 껐습니다"가 뜬다 (#120)

- 증상: 수집 마무리 뒤 슬랙 경고 `<폰>: 수집을 마쳤는데 비행기 모드를 못 껐습니다(상태: 켜짐|못 읽음)`. 수집 결과(`FAIL=`)는 그대로다.
- 확인: `adb -s <기기> shell settings get global airplane_mode_on` (`1`이면 켜짐), `adb -s <기기> shell "dumpsys power | grep mWakefulness="`.
- 조치: 사람이 빠른 설정에서 비행기 모드를 끈다. 다음 수집의 준비 단계가 다시 켜므로 수집은 안 막힌다.
- 원인(A8, 2026-11-03 실측): 안드로이드 8은 `cmd connectivity airplane-mode`가 없어(`No shell command implementation.`) 타일을 눌러야 하는데, 화면이 Asleep이면 타일을 못 누른다. `finish`가 먼저 깨우도록 고쳤다. 그래도 뜨면 깨우기 실패(`화면을 못 깨웠습니다` 꼬리)를 본다.

## 2026-11-13: adb 한 명령 시간 초과로 단계 전체가 다시 돈다 (#158)

- 증상: 단계 로그에 `[adb-retry] <기기> <명령> 시간 초과(60초) - get-state=…`. 같은 단계의 `-retry.log`가 있고 시간이 두 배로 늘어 SUSPECT가 된다(2026-11-04 3단계 V50: 첫 시도 18분 버림, 재시도 81분).
- 확인: `grep -rn "adb-retry" logs/steps/<날짜>/`. `get-state=device`가 아니면 기기가 죽은 것이라 재시도 없이 올라간다. `재시도 성공`이면 읽기 한 번이 흡수된 것이다. `입력이라 다시 안 보냄`이면 호출자가 화면으로 확인한다(`_open_visible_cards` 뒤로가기만).
- 조치: 찍힌 뒤에도 `-retry.log`가 있으면 이 변경이 못 막은 것이다. 입력 호출자(탭 등)가 `AdbInputUnconfirmed`로 죽은 경우이니 설계 `docs/specs/issue-158-*.md` §8의 후속을 연다. 같은 기기에서 자주 찍히면 adb 연결 원인을 따로 본다.

## 2026-09-07: api Build and Deploy가 두 번 연달아 실패했다 (로컬 pytest는 초록)

**증상.** GitHub Actions에서 `nn98/delivery-discount-api`의
"Build and Deploy"가 빌드 단계에서 실패. tracker 저장소 `pytest`는
전부 통과한 채로 커밋, 푸시했다.

**확인.**
```bash
python check_brands.py   # "searchAliases 비어 있음 N곳" 줄이 뜨면 이것
```

**원인.** `BrandCatalogTest.everyBrandHasNonBlankSearchAliases`가
`brands.yml`의 모든 브랜드에 비어 있지 않은 `searchAliases`를 강제한다.
클립보드로 딥링크를 받아 자동 생성한 브랜드 19곳은 `links`만 있고
`searchAliases`가 아예 없었다. 카테고리, 별칭은 "사람이 판단할 몫"이라
비워 두는 정책인데, `searchAliases`까지 같이 비어 문제가 됐다.

**조치.** `catch_link.py`가 새 브랜드를 만들 때 `searchAliases: [<표제어>]`
한 줄을 자동으로 넣도록 고쳤다. 지어내지 않으면서 검사를 통과하는
가장 안전한 값이다. 기존 19곳은 표제어에서 실제로 나오는 조각만
써서 채웠다(공백 제거형, `&`로 이어진 표제어를 양쪽으로 쪼갠 것).
`tests/test_brands_yml_matches_api_invariants.py`가 실제 `brands.yml`에
대고 이 규칙을 커밋 전에 확인한다.

**교훈.** api, web 쪽 불변식은 tracker의 pytest가 모른다. 언어 경계를
넘는 CI 규칙은 데이터를 바꿀 때마다 로컬에서 흉내 낼 별도 테스트가
있어야 한다. 없으면 "로컬 초록, 배포 빨강"이 반복된다.

## 2026-09-07: 화면에 쿠폰이 있는데 `tiers 0`으로 적힌다

**증상.** 치킨마루 결과가 `tiers []`, `exceptions ["17,000원 이상 주문 시 사용 가능"]`.
스크린샷에는 `3,000원 할인 쿠폰`이 또렷하다.

**확인.** `exceptions`는 있는데 `tiers`가 빈 브랜드를 먼저 본다. 시트는
읽혔고 금액만 못 뽑은 상태다.
```bash
python - <<'PY'
import json,io
d=json.load(io.open("captures/baemin_links_2026-09-07.json",encoding="utf-8"))
for b,r in d.items():
    if r.get("exceptions") and not r.get("tiers"):
        print(b, r["exceptions"])
PY
```

**원인.** 쿠폰명과 조건이 노드 두 개로 쪼개져 오는데, 시트 정규식이 XML
원문에만 걸려 있어 두 값 사이에 XML 속성이 끼면 안 맞았다.

**조치.** 원문과 "노드를 이어붙인 문자열" **양쪽**에 걸고 겹침만 뺀다 →
[ADR-026](../decisions/ADR-026-screen-shapes-are-a-union-with-regression-cases.md).

## 2026-09-07: 판독을 고쳤더니 다른 브랜드가 되레 줄었다

**증상.** 1차 순회에서 `bhc: tiers 1`이던 곳이 2차에서 `tiers 0`.

`tests/capture/test_baemin_coupon_shapes.py`에 묶었다 → ADR-026.

## 2026-09-07: 브랜드 이름에 `&amp;`가 박혀 화면에서 사라진다

**증상.** 원장에 `굽네치킨&amp;피자`. `brands.yml`의 `굽네치킨`과 안 맞아
그 브랜드만 화면에서 빠진다. 눈으로는 잘 안 띈다.

**원인.** 웹뷰는 노드 `text`에 HTML 원문을 담고, uiautomator가 그것을 **또**
이스케이프해서 `&amp;amp;`로 내보낸다. 한 번만 풀면 `&amp;`가 남는다.

**조치.** `capture.common.node_text`가 더 안 바뀔 때까지 푼다. 이미 들어간
행은 그 행의 `brand`만 정정한다. append-only 원장이지만 이것은 오기록
정정이라 새 행을 덧붙이면 같은 브랜드가 두 번 세어진다. 고치기 전 백업을
`data/_retired/backups/log.jsonl.bak-<시각>-entity`로 남긴다.

## 2026-09-07: 별칭이 있는데도 로고가 "없음"으로 뜬다

**증상.** `brands.yml`에 `aliases: [유가네닭갈비, 유가네찜닭]`이 버젓이
있는데 화면에는 유가네닭갈비 로고가 안 뜨고 첫 글자로 대체된다.

**확인.**
```bash
python -c "
import io, os, re, yaml
data = yaml.safe_load(io.open('mono/api/src/main/resources/brands.yml', encoding='utf-8'))['brands']
have = {os.path.splitext(f)[0] for f in os.listdir('mono/web/public/logos') if f.endswith('.png')}
def sanitize(n): return re.sub(r'[^a-zA-Z0-9가-힣]+', '_', n).strip('_')
for n in sorted(data):
    if sanitize(n) not in have:
        print(n, '->', sanitize(n) + '.png')
"
```

**원인 둘.**
1. **파일명이 옛 이름 그대로였다.** 표제어가 `유가네찜닭` → `유가네닭갈비`로
   바뀔 때 로고 파일명은 안 따라갔다. 프론트는 표제어로만 찾으므로 별칭이
   있어도 소용없다.
2. **더 일반적인 함정**. 표제어에 공백, `&`가 있으면 프론트(`logos.jsx`의
   `brandLogoSrc`)는 그 문자를 `_`로 바꾼 파일명을 요청한다. 표제어를
   그대로 파일명에 쓰면(예: `백종원의 미정국수&덮밥.png`) 파일은 있는데
   화면에는 안 뜬다.

**조치.** 파일명은 항상 `scripts/extract_brand_logos.sanitize()`(=
`logos.jsx`의 치환과 동일)를 거친 것이어야 한다 →
[ADR-027](../decisions/ADR-027-extract-logos-from-captured-screens-not-favicons.md).
옛 이름 파일은 `mono/_retired/logos/`로 옮기고 새 이름으로 다시 채운다.
회귀는 `tests/test_logo_filename_matches_frontend.py`.

## 2026-09-13: 같은 행사가 날마다 새 배너로 쌓이고, 그 부작용으로 라이브에서 사라졌다

**증상.** 어제와 같은 핫딜인데 미리보기가 매번 "새로 올린다"라고 한다.
서버 `banners.yml`이 65장까지 불었고, 그중 어제 올린 bhc, 홍콩반점
배너가 화면에 안 보인다.

**확인.**
```bash
ssh ... 'cat <서버>/delivery-discount-api/data/banners.yml' > /tmp/b.yml
python -c "
import yaml, collections, sys; sys.path.insert(0,'.')
from scripts.banner_routine import deal_slug
bs = yaml.safe_load(open('/tmp/b.yml', encoding='utf-8'))['banners']
print([b['id'] for b in bs if b.get('endsOn') and b.get('startsOn') and b['endsOn'] < b['startsOn']])

print({k: len(v) for k, v in by.items() if len(v) > 1})"
```

**원인.** 배너 id에 날짜가 박혀 있다(`f"{slug}-{today:%Y%m%d}"`). 같은
행사가 이어져도 오늘 id가 어제와 달라서 견주는 쪽이 **항상** "새로
올린다"가 된다. `previous_for()`가 조건(minOrder, extra)은 물려받게
돼 있었는데, 배너 자체를 물려받는 자리가 없었다.

쌓이기만 하면 지저분할 뿐인데 **자충수가 났다.** 새 id가 생기면 어제 id가
"화면에 없는 배너"가 되어 `endsOn`이 어제로 접힌다. 같은 날 루틴이 두 번
돌면 그날 만든 배너에도 그게 걸려 시작보다 끝이 앞선 행이 남는다:

    빽다방아이스아메리카노100원딜-20260911   09-11 -> 09-10
    bhc-20260912                        09-12 -> 09-11
    홍콩반점0410-20260912                 09-12 -> 09-11

서버는 그런 배너를 아예 안 내려보낸다. 오류도 안 나고 조용히 사라진다.

**조치.** `continuing()`/`reuse_continuing()`. 앱, 이름, 금액, 기간 문구가
같고 **어제(또는 오늘) 끝나는** 배너가 있으면 새로 만들지 않고 그 id를
물려 쓰고 `endsOn`만 오늘로 늘린다. 금액이 바뀌면 이어지는 게 아니라 새
행사다(처갓집 8,000 -> 7,000 전례). 며칠 전에 끝난 것은 안 되살린다. 안 한 행사를 하는 것으로 만든다.

**순서가 중요하다.** 기간을 먼저 늘려야 `today_banners()`에 잡힌다. 늘리기
전에 견주면 이어 쓰기로 정해 놓고도 "새로 올린다"가 되어 같은 id가 두 줄
된다.

**이미 쌓인 중복은 그대로 둔다.** `banners.yml` 머리말이 "지난 행사는
지우지 말고 그냥 둬도 된다"고 정해 놨고, 09-02와 09-04처럼 떨어진 날짜는
실제로 따로 한 행사라 소급해서 합치면 거짓이 된다.

## 2026-09-13: 이어 쓰기를 넣었는데 하나도 안 걸렸다 (원인 셋)

**증상.** `continuing()`을 넣고 돌렸는데 여전히 "새로 올린다" 넷.

**원인 1. 금액, 기간으로 맞췄다.** 그 두 필드가 **바로 사람이 다듬는
자리**다. 서버 실측:

    피자-20260912         period: 오전 11시 오픈   (수집값: 선착순)
    빽다방-20260912        amount: 7,000/1,900원   (사람이 두 딜을 합쳤다)
    baemin-targetdeal-…   amount: BHC, 홍콩반점 8,000원 / period: 타겟딜

문구까지 따지면 **사람이 손댄 배너는 절대 안 이어지고** 그 옆에 기계가
만든 중복이 한 장 더 선다. 같은 행사인지는 이름이 정하고, 문구가 누구
것인지는 스냅샷(`human_edited`)이 정한다. 한자리에서 둘 다 판단하려 한
것이 잘못이었다.

**원인 2. id를 앱이 부른 라벨에서 뽑았다.** 09-12에 앱이 피자헛 카드를
"피자"라고만 찍어 `피자-20260912`가 됐고, 09-13에 "피자헛"으로 돌아오자
`피자헛-20260913`이 됐다. 같은 행사가 앱의 변덕으로 남남이 된다(§4).
`resolve_hotdeal_brand()`가 이미 `("피자헛", None)`을 주고 있었는데 안
쓰고 있었다. 지금은 **판정된 브랜드+메뉴**에서 뽑는다.

**원인 3. 사람은 기계와 다르게 묶는다.** 화면의 빽다방 카드는 두 장인데
사람은 한 장에 `7,000/1,900원`으로 합쳐 뒀다. 이름으로 이으면 `빽다방`은
이어지지만 `빽다방아이스아메리카노100원딜`이 새로 서서 반쪽짜리가 하나 더
생긴다. `already_covered_by_human()`이 그걸 막는다.

**덤으로 나온 것 둘.**

- **미리보기가 거짓말을 했다.** 적용은 `human_edited`로 건너뛰는데
  미리보기는 스냅샷을 안 봐서 "고침: amount 'BHC, 홍콩반점 8,000원' ->
  ..."을 찍었다. 이 저장소에서 사람 배너를 덮은 사고가 실제로 있었으니,
  그 보고를 본 사람은 또 덮인다고 읽는다. `diff_all`이 스냅샷을 본다.
  다만 **무엇이 어긋나 있는지는 계속 보여준다**(`(안 바꾼다)` 표시).
- **한 실행이 서로 반대되는 말을 했다.** 이어 붙여 `endsOn`을 오늘로
  늘리니 "오늘 끝나는 배너"에 걸려 만료 검사를 또 받았다. 바깥에서
  개수만 걸렀더니 "4장"이라 쓰고 6줄을 찍었다. `extend_expiring()`이
  자기가 다시 훑기 때문이다. 함수까지 `skip_ids`를 넘긴다.

**남는 것.** `피자-20260912`는 옛 slug라 한 번은 안 이어진다. 오늘 밤
만료되고 `피자헛-20260913`이 새로 선다. 앞으로는 안 생긴다.

**치웠다(2026-09-13).** `scripts/fix_backwards_banner_dates.py --apply`로
되돌아간 3장의 `endsOn`을 `startsOn`과 같게 맞췄다. 지운 게 아니라 그날
하루짜리로 적은 것이다. 지금 0장이고, 원인을 막았으니 다시 걸릴 게 없어야
정상이다. 걸리면 `continuing()` 쪽이 깨진 것이다.

적용 결과: `bannersOk: True, banners: 7, unknownBrands: []`. 사람이 쓴
`baemin-targetdeal-20260912`(BHC, 홍콩반점 8,000원)와
`빽다방-20260912`(7,000/1,900원)는 문구 그대로 남았다.
