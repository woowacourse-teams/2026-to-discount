# 핸드오프: 수집기 캐시 정리 (2026-09-30)

수집 스크립트를 맡은 세션에 넘긴다. 이 세션은 원인 분석과 허브 키 한 건만 고쳤다. 나머지는 폰을 쓰는 확인이 필요해서 스크립트 세션이 진행한다.

## 배경

2026-09-30 15:50 쿠팡이츠 행사 배너 8장이 옛 허브(`V5_HUB_0928`, 일부는 `V5_HUB_0921`)로 연결돼 있었다. 사용자가 새 링크(`https://share.coupangeats.com/EJjKSiCSG6b`)를 알려 줘 콘솔 편집으로 8장을 모두 바꿨다. 재적재(reload)는 정상이다.

수집기가 이 변화를 못 잡은 이유는 캐시 둘이다.

- **허브 키 캐시**(`captures/.coupangeats-hub-key`): 캐시된 키로 허브가 열리면 그대로 썼다. 옛 허브는 새 허브가 나온 뒤에도 며칠씩 "종료"가 안 뜨고 열린다. 그래서 09-28에 찾은 키를 사흘째 썼다.
- **배너 이어받기**(`carry_over_open_banners`): 전날 배너를 복사하면서 링크도 그대로 옮겼다. `coupangeats-random-chicken-20260928`이 09-21 허브를 계속 달고 있던 이유다.

## 이미 한 것

- 허브 키 캐시를 그날 것만 믿게 했다(tracker `65fe191`, `capture/coupangeats_hub.py`의 `_cached_key`). 날이 바뀌면 홈에서 다시 줍는다. 테스트 `tests/capture/test_coupangeats_hub_cache.py`.
- 실기기 확인은 아직이다. 다음 실행에서 허브 키가 새로 잡히는지(캐시 파일 수정 시각이 그날인지), 홈 탭 경로가 깨지지 않는지 본다.

## 캐시를 둘지 정하는 기준

값이 바뀌었을 때 캐시가 스스로 알아채면 둔다. 알아채지 못하면 사용자에게 틀린 정보가 나가니, 다시 확인하는 비용을 감수한다. 판단 질문은 셋이다.

1. 캐시가 낡으면 사용자에게 틀린 정보(링크, 금액, 조건)가 나가는가.
2. 캐시가 낡았다는 신호를 스스로 받는가. 예를 들어 실패하면 다시 줍는가, 옛 값도 멀쩡히 동작하는가.
3. 다시 확인하는 비용이 한 번 실행에 몇 분 안인가.

1이 예이고 2가 아니오면 캐시를 없애거나 수명을 둔다. 3의 비용이 크면 수명을 하루나 주 단위로 정한다.
