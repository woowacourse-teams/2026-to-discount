# ADR-038. 화면 덤프 방식은 (폰, 단계)마다 측정으로 켜고, 쿠폰함은 딥링크로 들어간다

- 날짜: 2026-11-11
- 상태: 확정 (사용자 결정 2026-11-11 16시, 이슈 #252, 상위 #248)
- 관련: ADR-037(기기 도메인과 측정 배정), ADR-011(화면 진입은 딥링크로), 경과 보고 [`docs/research/2026-11-11-dump-way-progress.md`](../research/2026-11-11-dump-way-progress.md), 가설 대장 [`docs/research/2026-11-11-dump-way-hypotheses.md`](../research/2026-11-11-dump-way-hypotheses.md)

## 맥락

화면 트리를 읽는 방식(`dump_way`)의 후보가 셋이 됐다.

| 후보 | 방식 | 강점 | 약점 |
| --- | --- | --- | --- |
| 기존(`adb`) | 덤프마다 `uiautomator dump` 프로세스 | 모든 폰, 모든 화면에서 결과의 기준 | 한 번 2~3초(V30 6~15초). 움직이는 화면에서 idle을 못 얻어 빈 트리, V50 요기요 홈 454초(H5) |
| 패치 u2 | uiautomator2 서버에 웹뷰 건너뛰기를 지운 jar(PR #246) | 덤프 0.1~0.5초 | 웹뷰가 막 뜬 순간마다 물러섬(4a 곳마다 1회, A8 93회). 이득이 작다 |
| fdump | 자체 상주 덤퍼(`capture/fleet/fdump.py`, PR #258) | 덤프 0.02~0.2초, 결과가 기존과 같음, 물러섬 0 | Android 9(V30) 요기요 4c에서 활성 창 루트 null이 52번씩 이어짐(H9) |

측정(경과 보고 4절):

- **쿠폰함, 브랜드관, 허브에서 fdump는 기존과 결과가 같고 단계 시간이 0.41~0.83배다**(노트20, V50, G6, A8. A8은 재부팅 뒤 0.76배, 4.10절).
- **쿠폰함은 딥링크로 들어가면 홈을 건너뛴다.** 12/12 성공, V50 배민 홈 경로는 3/6(하단 배너가 탭을 덮음). 배민 딥링크+fdump 32~34초 대 홈 경로+기존 88~112초(4.4, 4.8절).
- **한 폰 한 방식 제약은 프로세스 단위다.** 서버가 떠 있는 동안 같은 폰의 기존 덤프가 충돌한다. 그런데 예약 수집은 단계마다 프로세스를 따로 띄우고(`scripts/run_routine.py` 994행) 단계 이름을 `ROUTINE_STEP`으로 넘기며(608행), 서버는 프로세스가 끝날 때 꺼진다. 그래서 **같은 폰이라도 단계마다 다른 방식을 쓸 수 있다.**
- 같은 폰의 같은 방식도 단계마다 갈린다. V30 fdump는 5y 10/10인데 4c는 빈 트리 43~57%, V30 4a는 덤프 방식과 무관하게 무너진다(H8, H9).

사용자 결정(11-11): 딥링크가 되는 곳은 딥링크를 정본 진입점으로 삼고, 안 되는 곳만 홈 경로로 우회한다. 배너, 팝업은 누르지 않고 딥링크를 다시 쏜다.

## 결정

### 1. 후보는 기존과 fdump 둘로 한다

패치 u2(PR #246)는 병합하지 않고 닫는다. **브랜치 `fix/u2-webview-fallback`과 main의 원판 u2 경로(`dumpers.u2_dump`)는 지우지 않고 남긴다**(사용자 11-11: 닫되 남겨 둔다). fdump가 어떤 칸에서 막히면(예: V30 4c) 다시 꺼낼 후보다. fdump가 결과, 속도, 물러섬에서 모두 앞서 지금은 켜지 않는다.

### 2. 선택 단위는 (폰, 단계)

- 측정 저장소의 `dump_way`는 그 폰의 기본값, 새 키 `dump_way_steps`(`{"5y": "fdump", "4c": "adb"}`)는 단계별 덮어쓰기다. 덤프는 `ROUTINE_STEP`으로 칸을 찾는다. 값이 없으면 기존 방식(ADR-037 결정 2의 "측정이 없으면 막지 않는다").
- 한 프로세스 안에서는 한 폰에 한 방식만 쓴다. 4a처럼 한 프로세스가 여러 폰을 쓰는 단계도 폰마다 따로 고른다.
- 값은 사람이 아니라 측정과 판정(3절)이 쓴다. 판정 도구는 `probe --dump`를 단계 단위로 넓힌 것(구현 PR).

### 3. 켜는 판정 규칙 (칸 하나 = 폰 하나 × 단계 하나)

**표본:** 같은 날, 재부팅 뒤, 후보와 기존을 번갈아 각 3회 이상. 몇 시간 연속 측정한 폰은 느려진다(A8 덤프 중앙 0.43초 대 재부팅 뒤 0.06초, H13).

**통과 조건(모두):**

1. 결과 같음: 산출 JSON 해시가 같거나 항목 대조로 같다. 계정 상태가 바뀌는 단계(3 허브, 5a)와 "오늘 만료" 쿠폰처럼 순서와 무관하게 오락가락하는 한 장은 차이로 세지 않는다(4.8절 버거킹 와우).
2. 단계 시간 중앙값 ≤ 기존 1.0배.
3. 실패 횟수 ≤ 기존. **실패**는 단계 rc≠0, 판독 실패 수 증가, 결과 불일치다. 빈 트리는 실패가 아니라 덤프 지표로 본다.
4. 끝난 뒤 폰에 덤프 서버 0개.

**물러섬은 실패로 세지 않는다.** 물러섬은 후보가 덤프 한 번을 못 떠 그 한 번만 기존으로 다시 뜨는 것이라 결과를 망치지 않는다. 대신 그 칸의 덤프 중 물러섬이 10%를 넘으면 탈락시킨다(이득이 사라진다). **(사용자 결정 필요: 10%)**

**기준값의 출처:** 결과 같음과 단계 시간 1.0배는 11-11 00시에 정한 판정 기준을 그대로 쓴다. 실측은 fdump 0.41~0.83배라 가장 나쁜 칸에도 17% 여유가 있다. 3회 이상은 재부팅 전후로 같은 폰 값이 갈린 실측(H13)에서 왔다. 물러섬 10%는 실측 근거가 없는 출발값이다(fdump 실측 물러섬 0).

**덤프 한 번 중앙값 ≤ 0.7배**는 통과 조건이 아니라 참고 지표로 낮춘다. 단계 시간의 대부분이 앱 도착 대기라(4.10절) 덤프만 빨라도 단계는 덜 준다.

**화면 단위 측정(`probe --dump`)의 글자 겹침은 판정에서 뺀다.** 후보와 기존을 차례로 뜨는 사이 화면이 바뀌어 낮게 나온다(#260, 노트20 배민 0.77). 화면 단위 측정은 "그 폰에서 후보가 붙는가(n/n 성공)"만 본다.

### 4. 쿠폰함 진입은 딥링크가 정본

- 5(배민 `baemin://./couponbox`), 5y(요기요 `yogiyolink://move.page/my_yogiyo/coupon`), 5a(쿠팡이츠 `coupangeats://PromotionCode`)는 딥링크로 들어간다.
- 도착 확인은 화면의 양성 신호(보유 쿠폰 문구, 쿠팡이츠는 현재 화면 `CouponManagementActivity`, `dumpsys window` 기준)다. 10초 안에 안 닿으면 딥링크를 다시 쏘고(배너, 팝업을 누르지 않음), 끝내 안 닿으면 홈 경로로 우회한다.
- 들어가기 전에 화면을 깨운다(측정 결함: 꺼진 화면에서 시작해 6회 실패).

### 5. 롤아웃 순서

폰 성능순으로 켜고, 그 폰에서 **측정을 통과한 칸만** 켠다(사용자 11-11 확정). 단계마다 프로세스와 판정이 따로라 한 폰에 여러 칸을 같이 켜도 문제 칸을 가를 수 있고, 단계를 가장 많이 맡는 폰부터 켜야 단축이 크다.

| 순서 | 폰 | 켜는 칸(덤프 방식 fdump) | 근거 |
| --- | --- | --- | --- |
| 1 | 노트20, V50 | 노트20: 5, 5y, 5a, 4a, 3(허브), 6(배너 대조, 11-11 사용자 승인: 기존 덤프 138번에 489초가 단계의 절반 이상. 제안서를 서버에 올리는 단계라 따로 재지 않고 되돌림 기준으로 감시). V50: 5, 5y, 4a. V50 5a는 11-11 16시 측정이 통과하면 넣는다. V50 허브는 측정 뒤 | 칸마다 결과 같음, 단계 0.41~0.74배 |
| 2 | G6, A8 | 4a. 다른 단계는 측정 뒤 | 0.83배, 0.76배(A8 재부팅 뒤) |
| 3 | V30 | 5, 5y | 5y 10/10(기존 2/10) |
| 보류 | V30 | 4c, 4a | 빈 루트 고침(`fix/fdump-v30-null-root`)과 4c 화면 이동 문제(#263)가 풀린 뒤 3절로 다시 판정 |

**11-12 전수 측정 뒤 운영 상태**(측정 표는 [경과 보고 4.11절](../research/2026-11-11-dump-way-progress.md)): 사용자 승인으로 V30 5y, 5a, 3 / A8 5, 5y / G6 5y, 5를 fdump로 켰다. 노트20 5와 V50 5는 되돌린 채 둔다. 2, 4b, 4c, 4d(노트20 4d는 확인 전)는 모든 폰에서 기존 덤프다. u2는 후보에서 뺐다(사용자 11-12, 코드와 브랜치는 남김).

**딥링크 진입(4절)은 덤프 방식과 떼어 따로 켠다**(사용자 11-11 동의). 같은 회차에 진입 경로와 덤프 방식을 함께 바꾸면 문제가 났을 때 원인을 못 가른다. 순서 1이 정기 회차에서 넘어가는 조건을 채운 뒤 노트20, V50의 5, 5y, 5a에 딥링크 진입을 켜고(구현 PR, #256), 그다음 순서 2로 간다.

**다음 순서로 넘어가는 조건:** 그 칸을 켠 뒤 정기 회차 1회에서 판정기(`check_routine`) PASS, 그 단계 덤프 기록(`logs/dumps`)의 빈 트리 비율이 기존 이하, 회차 뒤 서버 0개. 증거는 회차 보고서와 덤프 기록 경로를 이슈에 남긴다.

### 6. 롤백

**켜는 기준(3절)은 엄격하게, 되돌리는 기준은 넉넉하게 잡는다.** 운영은 실측 때보다 폰이 오래 돌고 동시에 돌아 느려질 수 있다(사용자 11-11). 흔들림 한 번에 끄면 켜고 끄기를 오간다.

| 운영 감시 지표(켠 칸, 그 단계 기준선 대비) | 되돌림 |
| --- | --- |
| 판정기 FAIL이고 원인이 덤프 방식 | **한 번에 즉시** |
| 결과 불일치(같은 회차 다른 폰, 또는 기존으로 다시 뜬 값과 다름) | **한 번에 즉시**. 정확성은 늦추지 않는다 |
| 단계 시간 > 기존 기준선의 1.2배 | 정기 회차 **2회 연속**일 때 |
| 빈 트리 비율 > 기존 + 5%p | 2회 연속일 때 |
| 물러섬 > 덤프의 20% | 2회 연속일 때 |

기존 기준선은 켜기 전 정기 회차 3회의 그 칸 단계 시간과 빈 트리 비율의 중앙값이다.


- **칸 하나:** 측정 저장소에서 그 폰의 `dump_way_steps[단계]`(또는 `dump_way`)를 `adb`로 바꾼다. 다음 덤프부터 적용, 배포 없음.
- **자동:** 후보가 덤프 한 번을 못 뜨면 그 한 번은 기존으로 물러선다(이미 있음).
- 딥링크 진입은 도착 실패 시 홈 경로로 자동 우회하므로 따로 끄지 않는다.

### 7. 예약 수집 재개는 덤프 방식 전환과 떼어 낸다

- 지금 그대로(`dump_way` 전부 `adb`) 재개할 수 있다. 재개는 사용자가 한다(`Enable-ScheduledTask -TaskName discount-after-open`).
- 재개 전 확인: 수집 사본이 main 최신, 1단계 시험 통과. 기존 덤프 총 상한 90초(PR #258)의 V30 영향(H17)은 재개 첫 회차의 V30 덤프 기록으로 본다.
- 롤아웃 1단계는 재개 뒤 정기 회차가 한 번 PASS한 다음에 켠다(기준선 확보).

## 결과

- 구현 PR(이 ADR 승인 뒤):
  1. `dump_way_steps`와 `ROUTINE_STEP` 조회(`capture/common.py` `_dump_way`), 단계 단위 판정 도구.
  2. 쿠폰함 딥링크 진입(5, 5y, 5a) 운영화(#256).
- 갱신할 문서(#254): `docs/setup/ROUTINE-SPEC.md`(쿠폰함 진입), `docs/setup/DEVICE-MATRIX.md`, `docs/setup/device-setup.md`, `docs/specs/2026-11-06-device-fleet-design.md`(전략 표의 덤프 칸), `AGENTS.md`(필요하면 한 줄).
- 뒤집는 조건: 기존 덤프가 앱 업데이트로 빨라지거나, fdump가 어떤 화면에서 기존과 다른 결과를 내는 사례가 나오면 그 칸부터 3절로 다시 판정한다.
