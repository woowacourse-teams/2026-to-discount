# 개발 워크플로 실제 이슈 후보 (2026-10-22)

설계 119 워크플로(이슈에서 병합까지 자동화)를 실제 기능으로 시험할 후보다. 인계 문서는 [`HANDOFF.md`](HANDOFF.md).

## 고르는 기준

- mono의 `web/` 또는 `api/` 하나만 고친다. 구현 세션은 영역 라벨이 정한 폴더만 만진다.
- PR 하나로 끝나고 테스트로 확인된다.
- 운영 서버 쓰기, 폰, 새 화면 문구 결정이 없다. 셋 다 세션이 혼자 끝낼 수 없다.
- 실제로 쓸모가 있다. 시험만을 위한 테스트 추가는 #128, #131, #133에서 세 번 했다.

## 후보

### A1. 브랜드 링크 검사 테스트 (api, 권장 첫 시험)

- **무엇:** `api/src/main/resources/brands.yml`의 `links`를 실제 파일로 검사하는 테스트를 더한다.
  - 키는 원장 앱 값(`baemin`, `ddangyo`, `coupangeats`, `yogiyo` 등)만 쓴다.
  - 값은 `https://`이고 앱별 공유 링크 도메인이다(배민은 `s.baemin.com`).
- **왜:** 2026-10-21 노랑통닭 배민 링크에 확인 없이 다른 도메인 주소를 넣었다가 고쳤다(PR #118). 이런 실수를 배포 전에 막는다. 같은 파일의 `searchAliases` 필수 검사(`BrandCatalogTest`)가 배포 실패를 막은 전례가 있다.
- **시험하는 것:** api 구현자 첫 실행, JDK 설치와 `./gradlew test`.
- **위험:** 지금 링크 중 규칙에 안 맞는 것이 있으면 테스트가 바로 빨갛다. 설계 단계에서 현재 값을 먼저 세어 보게 한다. 도메인 목록은 지금 파일에 있는 값에서 뽑는다.

### A2. api README에 Jackson 3 코딩 규칙 한 줄 (api, 작음)

- **무엇:** `api/README.md`의 "고칠 때"에 Jackson 3 규칙(`tools.jackson` import, `JacksonException`, `@MockitoBean`)을 ADR-012 링크와 함께 한 줄로 넣는다.
- **왜:** 규칙이 ADR-012에만 있다는 지적이 2026-10-14 콜드 체크에서 나왔다. 지금은 mono `AGENTS.md`에 파싱 예외 한 줄만 있다.
- **시험하는 것:** 문서만 바꾸는 이슈에서 설계와 구현이 과하게 일하지 않는지 본다.
- **위험:** 너무 작아 워크플로 비용(세션 셋)이 아깝다. A1이 막힐 때 대신 쓴다.

### W. 웹 후보

- 지금 백로그에서 위 기준을 모두 맞는 웹 일은 찾지 못했다. 웹 일 대부분이 새 문구 결정이나 프리뷰 승인을 먼저 요구한다.
- 웹 경로(프리뷰 주소, 360px 스크린샷 링크)는 사용자가 겪은 화면 불편 하나를 이슈로 받아 시험한다.

## 진행 방식

1. 이슈를 템플릿으로 열고 영역 라벨과 `ready`를 단다. 설계 세션이 돈다.
2. 오케스트레이션 세션이 설계 초안 PR을 읽고 문제를 이슈 댓글로 남긴다. 괜찮으면 사람에게 `/approve-design`을 넘긴다.
3. api 이슈의 구현은 PR #135(JDK 설치) 병합 뒤에 시작한다.
4. 단계마다 실행 결과, 턴 수, 거부 내역을 확인한다. 결과는 mono `docs/design/119-dev-workflow-asbuilt.md`와 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)에 적는다.
