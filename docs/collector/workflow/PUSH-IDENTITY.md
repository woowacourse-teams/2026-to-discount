# 워크플로의 push 신분과 검사 연결

설계 119 워크플로(이슈에서 병합까지 자동화)를 mono와 tracker에 붙이며 겪은 "누가 push하느냐에 따라 검사와 다음 워크플로가 깨어나는지"를 정리한다. 2026-10-21~22 기록이다. 사건별 시행착오는 [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)에 있다.

## 결론

- 세션의 커밋을 저장소에 올리는 push와 PR 병합은 **GitHub App 토큰**으로 한다. 기본 토큰(`GITHUB_TOKEN`)으로 하면 기존 검사와 다음 워크플로가 깨어나지 않는다.
- 검사 결과는 **그 검사를 깨운 이벤트의 커밋**에 붙는다. PR 화면에 검사가 뜨려면 PR 브랜치 커밋을 만든 push가 검사를 깨워야 한다.
- main 보호는 mono에서 저장소 규칙이 하고, 규칙을 쓸 수 없는 tracker에서는 워크플로 구조가 한다. 세션은 커밋만 하고, push는 워크플로 단계가 `feat/<이슈번호>-` 브랜치로만 한다.

## 용어

- **기본 토큰(`GITHUB_TOKEN`):** 워크플로 실행마다 GitHub이 자동으로 주는 토큰. 그 실행이 끝나면 버려진다.
- **App 토큰:** GitHub App(이 프로젝트는 `2026-to-discount`)의 개인 키로 실행 중에 만드는 짧은 수명 토큰. 액션 `actions/create-github-app-token`이 만든다. 시크릿은 App 번호(`WF_APP_ID`)와 개인 키(`WF_APP_PRIVATE_KEY`).
- **신분:** push나 병합을 한 주체. 기본 토큰이면 `github-actions[bot]`, App 토큰이면 App 봇(`2026-to-discount[bot]`), 사람이면 그 계정.
- **검사:** PR에 붙는 기존 워크플로. mono는 `check-web`, `check-api`, tracker는 `tests.yml`.

## 규칙 1: 기본 토큰이 만든 이벤트는 워크플로를 깨우지 않는다

GitHub은 워크플로가 서로를 끝없이 부르지 않도록, 기본 토큰으로 생긴 push, PR, 병합 이벤트로는 다른 워크플로를 시작하지 않는다(수동 실행과 `workflow_dispatch`, `repository_dispatch`는 예외). App 토큰이나 사람 토큰으로 생긴 이벤트는 평소처럼 워크플로를 깨운다.

이 프로젝트에서 이 규칙이 걸린 자리는 둘이다.

| 자리 | 기본 토큰이면 | App 토큰으로 바꾼 뒤 |
| --- | --- | --- |
| 구현 세션의 push | 검사(`check-web` 등)가 안 돎. 결과 댓글에 모을 검사가 없고 `/approve` 병합 근거가 빔 | push가 검사를 깨워 PR head 커밋에 붙음(mono PR #129, 2026-10-21) |
| `/approve` 병합 | 병합돼도 요약 워크플로(`pull_request closed`)가 안 깨어남 | 병합이 요약을 깨움(mono PR #132, #134) |

## 규칙 2: 검사는 그 실행의 커밋에 붙는다

검사 결과(check run)는 검사를 돌린 실행의 커밋(`GITHUB_SHA`)에 붙는다. PR 화면의 Checks 탭은 PR head 커밋에 붙은 검사만 보여 준다.

- 댓글(`issue_comment`)로 시작한 실행의 커밋은 기본 브랜치(main)의 최신 커밋이다. 이벤트가 커밋이 아니라 댓글이기 때문이다.
- 그래서 "댓글로 시작한 구현 워크플로가 검사를 직접 불러 돌리는" 방식은 검사를 main 커밋에 붙인다. PR 화면에는 안 뜬다.

### 시행착오: 검사를 불러 쓰기(A안, 버림)

- **한 것:** 기본 토큰 push가 검사를 못 깨우니, 구현 워크플로가 기존 검사 워크플로를 `workflow_call`로 불러 돌리게 했다(mono PR #127 첫 판). 검사 코드를 복제하지 않으려는 선택이었다.
- **결과:** 검사는 돌았지만 결과가 댓글 실행의 커밋, 곧 main 커밋에 붙었다. 결과 댓글 워크플로가 그 결과를 따로 끌어오느라 경로가 둘로 갈렸다. 일반 PR 검사와 구현 직후 검사가 다른 길을 탔다.
- **판단:** 문제의 뿌리는 검사를 부르는 방식이 아니라 push 신분이었다. 검사 워크플로를 원래대로 되돌리고 push 신분만 App 토큰으로 바꿨다(B안). 이후 검사는 일반 PR과 같은 길로 PR head 커밋에 붙는다.

## 규칙 3: push 명령을 누가 치든 신분은 checkout 토큰이 정한다

- `actions/checkout`에 App 토큰을 주면 그 토큰이 git 자격으로 저장된다. 이후 그 작업 폴더의 `git push`는 App 신분으로 나간다.
- 세션이 `git push`를 치든, 세션 뒤 워크플로 단계가 치든 신분은 같다. 검사가 PR head에 붙는 것도 같다.
- tracker는 이 성질을 이용해 세션에서 push 권한을 뺐다(아래). 규칙 2의 A안처럼 검사가 main 커밋에 붙는 일과는 관계가 없다.

## 규칙 4: App이 일으킨 실행은 Claude 액션이 기본으로 거부한다

- App 토큰으로 병합하면 요약 워크플로를 일으킨 주체가 App 봇이다.
- `claude-code-action`은 봇이 일으킨 실행을 기본으로 거부한다. 로그: `Workflow initiated by non-human actor: 2026-to-discount (type: Bot)`.
- 요약 워크플로에만 `allowed_bots: "2026-to-discount"`로 이 App 하나를 허용했다. 모든 봇을 여는 `*`는 쓰지 않는다.
- 같은 이유로, 실패한 실행을 "다시 돌리기"는 원래 실행의 워크플로 파일을 쓴다. 수정은 다음 병합에서 처음 확인된다.

## 규칙 5: main 보호는 저장소에 따라 다르게 한다

| | mono | tracker |
| --- | --- | --- |
| 저장소 | 조직, 공개 | 개인, 비공개 |
| 저장소 규칙, 브랜치 보호 | 씀: PR 필수, 관리자만 예외, 강제 push와 삭제 금지 | 못 씀. 무료 요금제 비공개 저장소는 API가 403 "Upgrade to GitHub Pro" |
| 세션 허용 도구 | `git push` 전체. main은 규칙이 막음 | `git push` 없음. 세션은 커밋만 |
| push 하는 곳 | 세션 | 세션 뒤 워크플로 단계. 브랜치 이름이 `^feat/<이슈번호>-[a-z0-9-]+$`일 때만 그 브랜치로 |
| 설계 초안 PR | 세션이 엶 | 워크플로 단계가 push 뒤에 엶 |

## App 준비

- **설치 범위:** App `2026-to-discount`의 소유자는 개인 계정(nn98)이고 조직(woowacourse-teams)에도 설치돼 있다. 설치 범위가 "어느 계정이든"이라, 개인 계정 저장소(tracker)에도 설치할 수 있다. 첫 안내에서 "조직에만 설치된다"고 한 것은 틀렸다(2026-10-22).
- **설치는 저장소마다 확인한다:** 시크릿이 맞아도 App이 그 저장소에 설치돼 있지 않으면 토큰 단계가 `Not Found - get-a-repository-installation`으로 실패한다. tracker 첫 실행(이슈 #10, 2026-10-22 10:44)이 이것으로 실패했다.
- **권한:** Contents 쓰기, Pull requests 쓰기, Checks 읽기, Workflows 쓰기. Workflows 쓰기는 `.github/workflows/`를 건드리는 커밋을 push할 때 필요하다. 웹훅은 끈다(실행 중 토큰만 만드는 용도).
- **개인 키:** 만들 때 한 번만 내려받는다. 시크릿에 넣을 때 줄바꿈이 깨지면 `Invalid keyData ... asn1 ... wrong tag`로 실패한다(mono, 2026-10-21). 따로 연 PowerShell에서 `Get-Content 키.pem -Raw | gh secret set WF_APP_PRIVATE_KEY -R <저장소>`로 넣는다.
- **시크릿은 다시 볼 수 없다:** 다른 저장소로 옮길 때 값을 꺼낼 수 없다. App 번호는 App 설정 화면에서 다시 보고, 개인 키와 Claude 토큰은 남겨 둔 파일이 없으면 새로 만든다. 새로 만들어도 이전 키와 토큰은 계속 동작한다(Claude 토큰은 추정).
- **대화창 `!`로 시크릿을 넣지 않는다:** 입력을 받지 못해 빈 값이 저장된다(mono, 2026-10-21 두 번).

## 실패 처리의 저장소 지정

- 토큰 단계처럼 checkout 전에 실패하면 작업 폴더가 git 저장소가 아니다. 이때 `gh issue edit` 같은 명령은 저장소를 몰라 `not a git repository`로 실패한다. `blocked` 라벨과 원인 댓글이 안 붙는다.
- job 수준에 `GH_REPO: ${{ github.repository }}`를 둔다. mono `0471afe6`(2026-10-21)에서 고쳤고, tracker 이식 때 설계 워크플로에서 빠져 첫 실행에서 다시 겪었다(`904448d`).

## 세션 뒤 push의 인증 (2026-10-22)

tracker는 세션에게 push를 빼고 세션 뒤 워크플로 단계가 push한다(규칙 5). 첫 실행(이슈 #10, 10:58)에서 그 단계가 `Invalid username or token`으로 실패했다.

- **원인(추정):** Claude 액션이 끝나면서 checkout이 저장해 둔 git 자격을 지운다. mono는 세션이 액션 안에서 push해서 드러나지 않았다.
- **확인한 것:** 같은 실행에서 App 토큰 단계, 세션(37턴, 거부 0건), 설계 문서 보관은 통과했다. 실패는 push 단계 하나였다.

### 방법 비교

| 방법 | 내용 | 장점 | 단점 | 유효성 |
| --- | --- | --- | --- | --- |
| 1. push 단계에서 자격 다시 세우기 | App 토큰으로 git 자격을 그 단계에서 다시 설정하고 push | 단계가 가장 적다 | 워크플로 코드가 토큰 값을 직접 다룬다. 로그 마스킹에 기대야 한다 | GitHub 문서의 일반 방식이라 동작할 것(추정). 이 세션에서 쓰려다 안전 판정에 막혀 시험하지 않았다 |
| 2. 패치 보관 뒤 다시 checkout (채택) | 세션 커밋을 `format-patch`로 러너 임시 폴더에 두고, App 토큰으로 checkout을 다시 한 뒤 `am`으로 적용해 push | 토큰을 직접 다루지 않는다. 자격은 checkout 액션이 정식으로 세운다. 브랜치 이름 검사와 main 보호 구조가 그대로다. 그사이 main이 앞서도 패치가 그 위에 얹힌다 | 단계가 둘 늘고 checkout을 한 번 더 한다(수십 초). 그사이 같은 파일을 누가 바꾸면 패치가 충돌해 실패한다(그때는 실패 처리가 `blocked`를 단다) | 로컬 bare 저장소로 시험 통과(커밋 2개 보관, main이 앞선 상태에서 적용, push, `main`과 대문자 이름 거부). 실제 실행 통과: 이슈 #10 11:03~11:07, 초안 PR #12가 App 신분 push로 열림 |
| 3. 세션에게 push 돌려주기 | mono처럼 세션이 액션 안에서 push | mono에서 검증된 방식. 단계가 가장 단순 | tracker에는 저장소 규칙이 없어 main 보호가 프롬프트 지시에만 기댄다 | 동작은 확실(mono PR #129, #134). 보호가 약해 tracker에는 쓰지 않음 |
