# 개발 워크플로 구축 중 막힌 것

mono 설계 [119](../../mono/docs/design/119-dev-workflow.md)(이슈에서 병합까지 개발 워크플로 자동화)를 2026-10-21에 만들면서 예상하지 못한 실패를 모두 적는다. 사건마다 증상, 확인한 것, 가설, 선택지, 선택, 결과를 순서대로 둔다. 원인을 확인하지 못한 문장에는 "추정"을 붙였다. 같은 문제가 다시 나오면 해당 사건에 횟수를 더한다. 짝 문서는 로컬 규칙 [`LOCAL-RULES.md`](LOCAL-RULES.md)다. push 신분, App 토큰, 검사 연결의 원리는 [`PUSH-IDENTITY.md`](PUSH-IDENTITY.md)에 따로 정리했다.

최종 상태(mono main `86728ecb`): 이슈 #133 → PR #134에서 설계, 구현, 검사, 병합, 요약, 이슈 닫기까지 사람 댓글 두 번(`/approve-design`, `/approve`)으로 끝까지 돌았다.

## 어디서 막을지 정하는 기준

문제가 생기면 먼저 이 문서에 적는다. 막는 장치는 아래 기준으로 고른다.

| 조건 | 막는 자리 | 예 |
| --- | --- | --- |
| 워크플로 안에서 생기고 기계로 판정된다 | 워크플로 단계 | 결과물 확인 단계, 거부 내역 로그 |
| 세션의 명령 습관에서 생긴다 | 워크플로 프롬프트와 역할 파일 | 명령은 하나씩, `--body-file` |
| 저장소 설정이 원인이다 | 저장소 설정(사람이 바꾼다) | main 규칙, 워크플로 기본 권한 |
| 여러 세션에서 2회 이상 나온다(빈발), 며칠 넘게 남는다(지속), 규칙끼리 부딪친다(충돌) | 하네스(`claude-harness/rules`, 훅) | 경로 없는 커밋 차단 훅 |

하네스는 모든 로컬 세션에 걸리므로 비용이 크다. 한 번 나온 문제는 이 문서와 그 자리의 단계로 막고, 위 셋 중 하나가 되면 하네스로 올린다.

## 1단계: 설계 세션(`design-session.yml`)

시험 이슈 #121에서 다섯 번, #123에서 세 번, #125에서 한 번 돌렸다.

### 1-1. 빈 시크릿으로 인증 실패 (1~2회차)

- **증상:** 1회차 실행이 Claude 단계에서 `Environment variable validation failed`로 끝났다. 로그의 `CLAUDE_CODE_OAUTH_TOKEN:` 값이 비어 있었다.
- **확인한 것:**
  - 시크릿은 04:43에 등록돼 있었다.
  - 값이 있는 시크릿은 로그에 `***`로 찍힌다. 빈칸으로 찍혔으니 저장된 값이 빈 문자열이다.
  - 워크플로의 시크릿 이름과 액션 입력 이름은 맞았다.
- **가설:** 시크릿 등록을 대화창 `! gh secret set …`으로 안내했다. 대화창 `!` 명령은 키보드 입력을 받지 못하므로 값을 묻는 단계가 빈 값으로 넘어갔다.
- **2회차:** 05:11:02에 다시 등록한 뒤 05:11:36에 돌렸다. 같은 증상이 나왔다. 다시 등록할 때도 `!`를 쓴 것으로 보여 가설과 맞았다.
- **선택지:** 따로 연 PowerShell 창에서 `gh secret set`, 또는 GitHub 웹 화면에서 등록.
- **선택:** 사용자가 웹 화면에 붙여 넣었다.
- **결과:** 3회차에서 인증을 통과했다.
- **같이 확인된 것:** 1회차 실패로 라벨 트리거, 라벨 단 사람 권한 검사, 입력 파일 만들기, 실패 시 `blocked` 라벨과 댓글이 동작했다.
- **막는 자리:** 안내 습관. 값을 입력받는 명령은 `!`로 안내하지 않는다.

### 1-2. 턴 상한 초과, 결과물 없음 (3회차, 실행 `39548942620`)

- **증상:** 34턴, 환산 0.43달러를 쓰고 턴 상한 30을 넘겨 끝났다. 세션은 스스로 "성공"을 보고했다. 그런데 `feat/121-*` 브랜치, 초안 PR, `인계:` 댓글이 모두 없었다.
- **확인한 것:** `permission_denials_count: 3`. 어떤 명령이 거부됐는지는 로그에 없었다. 워크플로가 `show_full_output: false`로 세션 출력을 숨겼기 때문이다.
- **가설(추정):** 허용 목록과 맞지 않은 명령이 거부됐고, 세션이 다른 방법을 찾다가 턴을 다 썼다.
- **선택지:**
  1. 세션 전체 출력을 켜고 다시 돌린다.
  2. 출력은 숨긴 채, 실행 결과 파일에서 거부된 도구와 턴 수만 뽑아 로그에 남긴다.
- **선택:** 상한을 50으로 올리고 전체 출력을 켜려 했다. 자동 판정이 전체 출력 켜기를 `Code That Leaks When Run`으로 막았다(공개 저장소 로그에 세션 출력이 남는다). 그래서 2번을 택했다. 이 단계가 지금의 "거부된 도구와 턴 수" 단계다.
- **결과:** 4회차부터 거부된 명령 원문을 볼 수 있었다.

### 1-3. push 허용 패턴 불일치, 명령 묶기 (4회차, 실행 `39550741133`)

- **증상:** 16턴 만에 "성공"으로 끝났다. 설계 내용은 좋았다(대안 3개 비교, 번지는 범위 분석). 그런데 push 4번이 모두 거부돼 결과물이 하나도 남지 않았다. 설계 문서는 실행 환경과 함께 사라졌다.
- **확인한 것(거부 내역 단계 출력):**
  - `git push -u origin feat/121-banner-…`가 허용 패턴 `Bash(git push -u origin feat/:*)`와 맞지 않았다.
  - `cd … && git checkout … && cat > … <<EOF`처럼 묶은 명령이 거부됐다.
- **가설(추정):** 패턴 끝 `:*`는 띄어쓰기 뒤에 붙는 인자만 허용한다. `feat/` 바로 뒤에 이어지는 브랜치 이름은 맞지 않는다. 허용 목록은 명령 하나 단위로 맞추므로 묶은 명령은 통째로 맞지 않는다.
- **더 큰 문제:** 결과물이 없는데 실행이 "성공"으로 끝나 `blocked`도 붙지 않았다. 세션의 자기 보고를 믿으면 실패를 놓친다.
- **선택지:**
  - A. `Bash(git push:*)`로 넓히고 main은 저장소 규칙(ruleset `25524211`)으로 막는다.
  - B. 브랜치 이름별로 패턴을 더 정교하게 쓴다.
- **선택:** A. 브랜치 이름은 세션이 정하므로 B는 다시 어긋난다. main 보호는 이미 저장소 규칙이 한다. 함께 넣은 것:
  - 프롬프트: 셸 명령은 하나씩, 파일은 Write 도구로.
  - 설계 문서를 실행 결과물(Artifacts)로 14일 보관. push가 실패해도 문서가 남는다.
  - 결과물 확인 단계: 브랜치, PR, `인계:` 댓글 중 하나라도 없으면 실패로 처리한다.
- **막힌 것:** 허용 범위를 넓히는 수정을 자동 판정이 `Security Weaken`으로, 그 커밋을 `Self-Modification`으로 막았다. 사용자가 커밋(`132538b2`)과 push를 직접 했다.
- **결과:** 5회차(실행 `39553756039`)에서 처음 끝까지 통과했다. 29턴, 브랜치 `feat/121-banner-ends-today-label`, 초안 PR #122, 인계 댓글, 보관 문서 3.4KB.

### 1-4. 여러 줄 본문 `gh pr create` 거부 (5회차)

- **증상:** 5회차에서 거부가 1번 있었다. 줄바꿈이 많은 본문을 `--body "…"`로 붙인 `gh pr create`였다. 세션이 다시 시도해 PR은 열렸다.
- **가설(추정):** 줄바꿈이 든 명령은 명령 단위 허용 목록과 맞지 않는다.
- **선택:** 프롬프트에 "본문은 Write로 파일을 만들고 `--body-file`로 넘긴다"를 넣었다(mono `37190d7f`). 턴 상한은 시험 결과(29~34턴)에 맞춰 50으로 확정했다.

### 1-5. 셸 허용 범위 논의와 토큰 노출 방어

5회차 뒤 사용자는 명령 모양마다 규칙을 붙이는 방식이 무거워진다고 지적했다.

- **낸 안:** 명령 단위 목록을 버리고 셸 전체를 연다. 경계는 실행 환경으로 삼는다(작업마다 버려지는 가상 머신, 저장소 한정 토큰, main 규칙, Claude 토큰 말고는 시크릿 없음).
- **막힘:** 자동 판정이 설계 문서 수정부터 `Security Weaken`, `Create Unsafe Agents`로 막았다. 이유는 이슈 본문에 숨은 지시가 Claude 토큰을 밖으로 보내게 할 수 있다는 것이었다.
- **분석:** 셸 전체를 열면 위험이 0에서 생기는 것이 아니라 이미 있는 위험이 조금 늘어난다고 봤다(추정). 지금 허용 목록(Read, Write, 댓글 작성)으로도 토큰 유출 경로가 남기 때문이다. 자세한 경로는 공개 문서에 적지 않는다. 결론은 "명령 모양 제한만으로는 안전하지 않으니, 피해 크기를 줄이는 쪽(액션 방어, 운영 규칙)에 기댄다"였다.
- **선택:** 명령 단위 목록은 유지한다. 대신 액션에 있는 방어인 `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB: 1`(셸 명령 환경에서 시크릿을 지우는 설정)을 켰다(`527243a8`).
- **검증 시도:** 셸에서 토큰 변수 개수만 세는 점검 워크플로를 쓰려 했다. 자동 판정이 `Containment Escape`로 막았다. 의도와 무관하게 시크릿 추출 시도와 같은 모양이라 맞는 판정으로 보고 우회하지 않았다. 대신 다음 설계 실행의 액션 로그로 격리 상태를 보기로 했다.

### 1-6. 격리 설정이 셸을 통째로 죽임 (#123, 3회)

1-5에서 켠 `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB: 1`이 기본 러너에서 셸을 막았다. 격리는 추가 도구를 요구했다.

- **1회차(실행 `39560773828`):** 액션이 격리에는 bubblewrap(리눅스 프로세스 격리 도구)이 필요한데 없다며 설치 단계에서 멈췄다. Claude는 뜨지도 못했고 실행 전체가 실패했다.
- **2회차:** job 맨 앞에 `bubblewrap` 설치 단계를 넣었다(사용자가 커밋·push). 설치와 격리는 정상이었고 19턴을 거부 없이 돌았다. 그런데 push를 안 해 브랜치, PR, `인계:` 댓글이 없었다. 전체 출력이 꺼져 있어 이유가 로그에 없었다. 격리가 git에 영향을 줬는지 확인하려고 전체 출력을 켜기로 했다.
- **3회차(실행 `39565906665`, 전체 출력):** 세션 보고에 원인이 남았다. 격리 샌드박스가 `socat`(프로세스 간 통신 중계 도구)을 요구하는데 없어 세션의 Bash 명령이 전부 실패했다. 설계 문서조차 못 썼다. 결과물 확인 단계가 실패로 잡았다(의도대로).
- **선택지:**
  1. 설치 줄에 `socat`을 더해 격리를 살린다.
  2. 격리를 끄고, `ready`는 본문을 읽은 사람만 단다는 운영 규칙에만 기댄다.
- **선택:** 2번. 공개 저장소라 노출을 크게 걱정하지 않기로 했고, 격리를 살리려고 러너에 도구를 쌓는 것보다 운영 규칙이 가볍다. 격리(ENV_SCRUB, bubblewrap)와 전체 출력을 모두 걷어 5회차 정상 상태로 되돌렸다(`24e5447b`). push 허용, 설계 문서 보관, 결과물 확인, `--body-file` 안내는 남겼다.
- **결과:** 이슈 #125에서 다시 돌려 브랜치 `feat/125-*`, 초안 PR #126, 인계 댓글까지 정상으로 나왔다. 1단계 확정.

### 1-7. 재실행 시 `blocked` 때문에 skip (#123)

- **증상:** `ready`를 다시 달았는데 워크플로가 통째로 건너뛰었다(`skipped`).
- **원인:** 앞 실패에서 붙은 `blocked`가 남아 있었다. 워크플로 조건이 `blocked`면 돌지 않는다.
- **처리:** 재실행은 `blocked`와 `ready`를 함께 뗀 뒤 `ready`를 다시 단다. 설계 문서의 재실행 안내가 이미 이 순서다. 한 줄로 떼지 않고 `ready`만 다시 달아 반복됐다.
- **막는 자리:** 재실행 절차(문서에 이미 있음). 라벨 조작을 자동 판정이 막는 경우가 있어 사용자가 직접 단다.

## 2단계: 구현·검사·병합

### 2-1. 봇 기본 토큰 push가 검사를 안 깨움

- **증상:** 구현 세션이 기본 토큰(GITHUB_TOKEN)으로 push하면 `check-web`/`check-api`가 깨어나지 않는다. 그러면 결과 댓글에 모을 검사가 없고 병합 근거도 빈다.
- **원인:** GitHub은 기본 토큰이 만든 커밋으로는 워크플로를 다시 깨우지 않는다(순환 방지).
- **선택지:**
  - A. 검사를 복제하지 않고 기존 `check-web`/`check-api`를 `workflow_call`로 재사용한다.
  - B. push 신분을 GitHub App 토큰으로 바꿔 검사가 PR head 커밋에 자연히 붙게 한다.
- **1차 선택 A → 실패:** 재사용은 했으나 검사 결과가 PR head가 아니라 댓글 실행의 sha(main)에 붙었다. result-comment가 그걸 억지로 끌어오느라 경로가 둘로 갈려 깨지기 쉬워졌다. 사용자가 피하려던 "누더기"가 됐다.
- **2차 선택 B:** App `2026-to-discount`를 설치하고(사용자), `actions/create-github-app-token`으로 짧은 수명 토큰을 만들어 checkout에 쓴다. 트리거는 그대로 `/approve-design` 댓글이고, push 신분만 App으로 바꾼다. 검사 파일은 원복하고 `workflow_call` 우회를 걷었다.
- **결과:** 실행 `39580206113`에서 PR head(`eb9a4e1`)에 check, gitleaks, Vercel, shot 검사가 붙어 돌았다. 목표였던 검사 연결이 됐다.
- **남은 죽은 코드:** `result-comment.yml`의 단순 복귀 수정을 자동 판정이 막아, 아무도 호출하지 않는 `workflow_call`/`CALLED` 부분이 남았다. `check_suite` 트리거는 살아 있어 동작에는 영향이 없다.

### 2-2. App 개인 키 형식 오류 (사용자 조치)

- **증상:** App 토큰 만들기 단계가 `Invalid keyData`, `asn1 ... wrong tag`로 실패했다.
- **원인:** `WF_APP_PRIVATE_KEY` 값이 PEM으로 안 읽혔다. BEGIN/END 줄이나 줄바꿈이 빠진 경우다. `WF_APP_ID`는 정상이었다.
- **처리:** 따로 연 PowerShell에서 `Get-Content 키.pem -Raw | gh secret set WF_APP_PRIVATE_KEY`로 파일째 다시 넣었다.

### 2-3. checkout 전 실패가 저장소를 몰라 `blocked` 못 닮

### 4-7. 새 pull_request 워크플로가 열린 PR에서 안 돎 (mono #150, 리뷰 단계)

- **증상:** 리뷰 워크플로(`review-session.yml`)를 병합한 뒤 #150 초안을 풀었는데 실행이 하나도 생기지 않았다(실행 수 0).
- **원인:** `pull_request` 이벤트는 PR의 병합 시험 커밋(`refs/pull/<번호>/merge`)에 든 워크플로로 돈다. #150의 병합 시험 커밋이 리뷰 워크플로 병합 전에 만들어져 파일이 없었다(`contents?ref=refs/pull/150/merge` 404).
- **조치:** `gh pr update-branch 150`으로 main을 받아 병합 시험 커밋을 새로 만들게 한 뒤 초안을 다시 풀자 돌았다(실행 `39798878407`, 줄 지적 4건).
- **다음에:** 새 `pull_request` 워크플로는 그 뒤에 만든 PR이나 브랜치를 갱신한 PR에서만 돈다.

## 안전 가드에 막혔을 때 대응법

자동 판정과 별개로, 응답 자체를 안전 분류기가 끊는 경우가 있다(도구 오류나 API 오류가 아니다. 응답 일부가 잘리고 끝난 도구 호출은 반영되지 않는다). 이 문서를 쓰는 중 실제로 한 번 끊겼고, 다음 순서로 원인을 좁혀 우회했다.

1. **끊긴 자리를 특정한다.** 분류기는 이유를 알려 주지 않는다. 직전까지 쓴 내용과 쓰려던 내용을 보고, 무엇이 위험하게 읽혔는지 가설을 세운다. 이번에는 "토큰이 공개 경로로 나가는 절차를 단계로 적은 부분"과 "격리를 푸는 조건을 이어 쓴 부분"이 붙어 추출 안내처럼 읽힌 것이 원인이었다(추정).
2. **쪼갠다.** 전체를 한 번에 다시 쓰지 않는다. 내용을 작은 편집 여러 개로 나눠 하나씩 반영한다. 통과한 덩어리와 막힌 덩어리가 갈려, 끊는 자리가 바로 드러난다.
3. **막힌 덩어리만 바꾼다.** 사실과 결론은 남기고, 위험을 재현하는 구체 절차만 뺀다. "무엇이 위험한가, 무엇을 골랐나, 결과가 어땠나"는 기록 목적에 충분하다. "어떻게 하면 뚫리나"는 뺀다.
4. **우회를 규칙으로 남긴다.** 같은 끊김이 또 나지 않게, 이 절처럼 대응법을 문서에 적는다. 분류기 판단에 동의하면(실제 위험이면) 우회하지 않고 멈춘다. 오탐이면 목적을 지키는 같은 효과의 방법으로 진행한다.

- **훅 오탐:** 훅은 목적을 지키는 장치다. 오탐이면 훅의 목적을 지키는 같은 효과의 방법으로 진행하고 보고한다. 같은 오탐이 두 번 나오면 훅을 고친다.
- **셸 허용 범위:** 명령 단위 허용 목록을 유지한다. 셸 전체를 여는 안은 자동 판정이 막았고, 명령 모양 제한만으로 안전해지지도 않는다. 대신 피해 크기를 줄이는 쪽(운영 규칙 `ready`, 공개 저장소 전제)에 기댄다.
- **격리:** 기본 러너에서 `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`는 추가 도구(bubblewrap, socat) 없이 못 쓴다. 쓰려면 러너에 도구를 쌓아야 한다. 공개 저장소라 끄고 운영 규칙에 기대기로 했다.

## 하네스로 올릴 후보

지금은 없다. 위에서 두 번 이상 나온 것은 자동 판정의 병합·자기승인 거부뿐이고, 이건 사람 승인 관문이 의도대로 동작한 것이라 막을 대상이 아니다.
