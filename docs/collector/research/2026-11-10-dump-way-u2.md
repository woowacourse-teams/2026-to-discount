# 화면 덤프를 uiautomator2로 바꾼 기록 (2026-11-10)

결론: u2는 덤프 한 번의 평균을 최대 97배(V30 요기요 29.1초 → 0.6초) 줄였지만, **배민 쿠폰함(웹뷰) 화면에서 트리를 훨씬 적게 줘서 5단계가 실패했다.** 그래서 같은 날 19:30에 V30, V50, 노트20의 `dump_way`를 `adb`로 되돌렸다. 방식을 측정값 `dump_way`로 고르는 구조(PR #244, 병합 `69576ce`)는 남아 있고 지금은 5대 모두 `adb`라 동작이 이전과 같다. u2를 다시 켜려면 화면 종류별 동등성 검증이 먼저다(6절).

이 문서는 배경, 원인 확인, 조치, 결과, 평가를 쓴다. 숫자는 이 저장소의 로그와 실측에서 가져왔고, 직접 확인하지 못한 것은 "추정" 또는 "미확인"으로 적었다.

## 1. 배경

- 4c(요기요 전수조사)가 V30에서 90분 상한(`STEP_TIMEOUT`)에 반복해서 끊겼다. 11-09 18:08 회차 4c 4,931초, 11-10 00:09 회차 5,400초(끊김), 11-10 03:56 회차 5,400초(끊김).
- 풀(run_routine.Pool)은 4c 후보 순서를 `V50 > A8 > 노트20 > V30 > G6`으로 두고, 앞선 폰이 바쁘면 빈 폰이 먼저 집는다. 그래서 V30이 4c를 반복해서 집었다.
- 4c가 끊기면 요기요 구간(`CU픽업`, `세븐픽업` 등)이 원장에 못 들어가고, 8단계 서버 업로드 가드("서버에 있는 상세가 사라진다")가 막아서 웹 화면은 옛 값으로 남았다(11-09부터).

## 2. 원인 확인

### 2.1 관측 (V30, 11-10 15:27~15:30, 166초)

adb 프로세스 목록을 0.15초 간격으로 읽기만 했다(폰에 명령을 안 보냄).

| 항목 | 값 |
| --- | --- |
| adb 명령 | 131회 |
| `uiautomator dump` | 47회 |
| dump가 성공해서 `cat ui.xml`까지 간 것 | 13회 |
| 빈 트리로 재시도한 dump | 34회(72%) |
| 화면 동작(tap, back) | 4회 |
| 동작 1회당 dump | 약 12회, 약 41초 |

### 2.2 코드

`capture/common.py` `_dump_adb`(옛 `_dump_ui`)는 첫 dump가 트리를 못 주면 재시도 사다리를 돈다. 대기 0.5초 ×6회, 1, 2, 3초, 압축 5초, 그다음 (3초 + 3초 압축) ×4. 트리가 계속 비면 한 번의 `dump_ui`가 최대 35초 이상 걸린다. 사다리 안에서 `KEYCODE_UNKNOWN`(활동 시각만 갱신)을 보낸다.

코드 주석은 "서브 폰은 null root가 열에 일곱 번꼴", "Android 9의 알려진 결함, 화면이 잠잠해질 틈을 더 준다"고 적고 있다.

### 2.3 원인 (추정)

요기요 홈에는 카운트다운(`14:41` 등)과 롤링 배너가 있다. 화면이 계속 움직이면 uiautomator가 idle(화면이 잠잠한 상태)을 얻지 못해 빈 트리를 돌려준다고 본다. 이 마지막 연결은 코드 주석과 화면에서 이은 추정이고, uiautomator의 오류 문구는 직접 확인하지 못했다.

## 3. 조치

### 3.1 변경 (PR #244)

- `capture/fleet/dumpers.py` 추가: u2 서버 연결, 상태 표시줄과 알림 창 노드 제거(`strip_system_windows`), 서버 종료(`pkill -f com.wetest.uia2` 포함). u2가 실패하면 서버를 끄고 기존 방식으로 물러선다.
- `capture/common.py`의 `_dump_ui`: 측정값 `dump_way`가 `u2`인 폰만 u2로 뜬다. 값이 없으면 기존 방식(설계 2.3 규칙 1의 예외: 빈 값으로 폰을 빼면 수집 전체가 멈춘다).
- `capture/fleet/probe.py` `--dump`: 폰마다 앱 4개를 새로 띄워 기존 덤프와 u2를 4번씩 비교하고 `dump_way`, `dump_stats`를 쓴다.
- `requirements.txt`: `uiautomator2==3.7.1`(2026-10-23 릴리스).
- 시험 11건(`tests/test_fleet_dumpers.py`).

### 3.2 판정 규칙

u2 성공률 90% 이상, 평균 시간이 기존의 0.7배 이하, 안정 글자(기존 덤프 두 번에서 둘 다 나온 글자)가 u2에도 85% 이상. 앱 중 하나라도 미달이면 `adb`(폰 하나에 방식 하나: u2 서버가 켜져 있으면 같은 폰의 기존 덤프가 충돌한다).

### 3.3 설치

폰에 앱은 설치하지 않았다. u2 3.x는 `u2.jar`를 `app_process`로 실행하는 방식이다(`pm list packages`에 uiautomator 관련 패키지가 없음). 수집 PC에는 시스템 Python 3.14에 `uiautomator2 3.7.1`을 설치했다.

### 4.4 배민 쿠폰함 실패와 되돌림

- 5단계가 노트20(u2)과 V50(u2)에서 모두 "쿠폰을 한 장도 못 읽었다"로 실패했다(19:18~19:20). 재배정 한도(한 번)가 끝나 이 회차 배민 쿠폰함 값은 갱신되지 않았다.
- A/B(노트20, 같은 화면): adb는 입구 화면 노드 228개, 카드 글자 44개, 카드 뒤집은 뒤 노드 455개로 "보유쿠폰 9장"을 읽었다. u2는 69개, 8개, 24개이고 쿠폰 카드 목록이 대부분 빠졌다.
- 해결 시도: 트리 깊이 `max_depth` 50 → 200(69노드 그대로), 노드 수가 같아질 때까지 기다리기(99노드)로는 안 됐다. 원인은 u2가 이 웹뷰 목록의 안쪽 노드를 못 가져오는 것으로 보이지만 추정이다.
- 조치: 19:30에 V30, V50, 노트20 `dump_way`를 `adb`로 되돌렸다. 이후 프로세스부터 적용되고, 폰의 u2 서버는 0개다.
- 첫 실측은 앱 홈 화면만 비교했고(글자 겹침 0.87~1.00), 웹뷰 쿠폰함 같은 깊은 화면을 안 봤다. PR #244 본문이 이를 "미확인"으로 적었고 그것이 그대로 터졌다.

## 5. 평가

### 5.1 효과가 확인된 것

- V30 덤프가 한 자릿수 초 → 1초 미만이 됐다. 4c가 90분 상한에 끊기던 것이 753초에 끝났다.
- 정상 폰(V50, 노트20)도 덤프가 3초 안팎 → 0.5초 안팎이 됐고, 이 폰들이 쓰는 단계(3, 3s, 5a, 6, 4a의 V50 몫)의 소요가 줄었다.
- 방식을 측정값으로 고르므로 폰을 바꾸거나 OS가 바뀌면 `probe --dump`로 다시 잴 수 있다.

### 5.2 효과가 불충분하거나 확인 못 한 것

- **V30 4c가 읽은 양(4.5절):** 이번 회차 V30 4c는 브랜드 40곳(판독 실패 4)이고, 15:01 회차 노트20 4c는 45곳(판독 실패 3)이다. 5곳 적다. 주소별 값도 크게 다르다(V30 `창원` 2, `솔데스크` 27, 노트20 `창원` 23). 앞 주소에서 읽은 브랜드를 건너뛰는 규칙 때문에 읽는 순서가 주소별 값을 흔들 수 있어서, 읽기 결함인지 순서 차이인지는 브랜드 목록을 대조해야 안다(미확인).
- **A8, G6:** u2 이득이 작아 adb로 남았다. G6 4a는 이번 회차에도 평균 4.6초에 10초 이상이 15회(최대 18.7초)다. 앱마다 방식을 고르는 구조가 이득일 수 있다.
- **큰 웹뷰 화면:** 쿠팡이츠 허브 긴 스크롤, 배민 쿠폰 시트처럼 기존 덤프가 SIGKILL(137)로 죽던 화면에서 u2가 어떤지는 글자 겹침만 보았고 판독 값 대조는 안 했다.

### 5.3 과정에서 낸 문제 (기록)

- **수집 단계와 실험이 겹침:** V30을 "비어 있다"고 보고 u2 실험을 돌리는 동안 풀이 V30에 4f와 5y를 배정해서 부딪혔다(11-10 16:19, 16:32 부분 실패 알림 2건). 풀이 다른 폰으로 재배정해 끝났지만 제 판단이 틀렸다. 이후 수집이 도는 동안은 풀이 배정할 수 있는 폰에서 실험하지 않는다.
- **u2 서버가 폰에 남음:** `stop_uiautomator`가 서버를 못 꺼서 V30에 `app_process` 2개가 남았다. 직접 종료했고 `dumpers.stop_all`에 `pkill`을 넣었다.
- **측정 오류:** 기존 덤프와 u2를 번갈아 뜨면 서버가 켜진 동안 기존 덤프가 충돌해 서로 실패한다(첫 측정에서 배민 u2가 0/4). 앱마다 기존 4번, u2 4번을 따로 뜨도록 고쳤다. 글자 겹침도 움직이는 내용(카운트다운)에 흔들려 요기요가 0.72로 나왔고, "기존 덤프 두 번에서 둘 다 나온 글자" 기준으로 바꿔 1.00이 됐다.
- **작업 폴더 연결 소실:** 작업 폴더(`wt-u2`)의 git 연결 정보가 중간에 사라져 커밋을 수집 PC 저장소의 임시 인덱스로 만들었다. 원인은 수집 쪽 정리로 추정하고 확인하지 못했다.

### 5.4 서브에이전트 사후 검토에서 확인한 코드 문제 (PR #244 후속)

읽기 전용 검토를 돌렸고, 아래 항목을 코드나 로그로 직접 다시 확인했다.

- `u2_dump`가 노드 0개 트리(`<hierarchy rotation="0" />`)를 성공으로 돌려준다. V30 로그 18:47:21, 18:51:22에 `nodes:0, empty:false`가 있다. 4.2절의 "빈 트리 0"은 "u2 150회 시험에서는 0, 실수집에서는 노드 0개 2건"으로 고쳐 읽는다.
- `u2_dump`가 예외 때 `_devices.pop`을 먼저 해서, 뒤이은 `stop_all`이 그 폰의 서버를 안 죽인다. 한 폰의 실패가 다른 u2 폰의 서버까지 `stop_all` 한다.
- `strip_system_windows`가 시스템 UI 노드를 지워서, 시스템 창을 읽는 `common.py`의 `_tap_system_ok`와 `tiles.py`의 `toggle_tile`이 u2 폰에서 못 읽는다.
- V30의 측정값 `dumps.baemin`이 11-09 02:16 값(False)이라 V30이 2, 4a, 4g 후보에서 계속 빠진다(`probe --act` 재측정 필요).
- 느린 덤프 전제의 상수: `load_factor`는 켜진 폰 5대에 없어 지금 ×1이라 손볼 것이 없다. `wait_for_*` 폴링 간격(1~3초)은 u2에서 불필요하게 느슨하다.
