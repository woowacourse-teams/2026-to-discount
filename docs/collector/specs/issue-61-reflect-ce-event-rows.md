- **읽지 못한 것**: `logs/steps/2026-10-23/3.log`, `8.log`, 그날 `captures/coupangeats-weekly-2026-10-23.json`, `data/log.jsonl` 10:47 이후 행. 이 체크아웃에 없다(로그·captures는 수집 PC에만 있다). 그래서 **"행사 행이 왜 안 들어갔나"의 원인은 확정하지 못했다.** 2절에 가설과 가르는 법을 둔다.

## 1. 지금 코드가 하는 일

- `coupangeats_weekly.main`은 `out_records`에 `random_event_records(merged, …)`와 `fixed_event_records(merged, …)`를 이어 붙여 **고정 쿠폰과 같은 파일**(`coupangeats-weekly-<날짜>.json`)에 쓴다(755~756행). 행사 행의 `section`은 `릴레이 슈퍼딜 > 스페셜 특가`(확정액)와 `위클리 슈퍼딜 > 이벤트 쿠폰`(랜덤).
- `reflect_daily.sources`는 그 파일 하나를 출처 "쿠팡이츠 허브 고정 쿠폰"(단계 3)으로 통째로 `decide`에 넣는다. 행사 행이 파일에 있으면 같이 들어갈 구조다. **행사 행을 따로 세는 줄이 없다.**
- 그래서 이슈의 "행사 갈래 줄이 없음"은 코드가 그렇게 짜여 있어 생긴 결과다. 이슈 제목("원장에 안 넣는다")은 아직 증명되지 않았다. 코드상 연결은 이미 있을 수 있다.
- `217c517`(10:24)이 `fixed_event_records`를 넣었고 10:47 실행은 그 뒤라 새 코드로 돌았다. `a9e2853`(11:38)은 그 뒤에 `merge_events`가 안 보인 행사도 남기게 했다.

## 2. 원인 가설 (확정 못 함)

10:47에 네 브랜드 행이 안 들어간 이유로 가능한 것:

| 가설 | 그러면 로그에 보이는 것 | 이 설계가 고치나 |
|---|---|---|
| H1 `held_by_human`이 보류. 10:22~23 손 입력이 네 브랜드의 오늘 대표(`manual`) | 허브 줄의 `보류` 수에 4가 섞임. 이슈는 `넣음 27`만 인용했다 | 줄을 갈라 보이게만 한다. **동작은 옳다(규칙 유지가 이슈 요구).** 내일은 손 행이 어제 것이라 안 막힌다 |
| H2 파일에 행사 행이 없음. 3단계의 `merged`에 `won`이 없었거나(`KFC 5,000원` 로그 값이 `won`으로 안 담김) 하루 행사 파일이 덮임 | 파일에 `section == 릴레이 슈퍼딜 > 스페셜 특가` 행 0개 | 갈라서 **0건을 0건이라고 못 믿게** 하는 가드(4.2)를 건다. 원인 자체(수집)는 이 이슈 밖 |
| H3 `plan`이 거부(`invalid`)해 출처 전체 보류 | `거부 N` 줄 | 갈라 두면 행사가 허브 고정 27건을 끌고 내려가지 않는다(4.3) |
| H4 중복 판정 | `중복` 수 | 아님. `captured_at`이 `_stagger`로 실행마다 다르다 |

**구현자가 맨 먼저 할 일:** 수집 PC에서 10-23 `coupangeats-weekly-2026-10-23.json`을 열어 네 브랜드 행사 행이 있는지, `python scripts/reflect_daily.py 2026-10-23`(미리보기)를 돌려 어느 가설인지 가른다. 결과를 PR 본문에 적는다. H2면 이 PR은 가드와 줄만 넣고 **수집 쪽 원인은 새 이슈**로 뺀다.

## 3. 비판: 이슈 요구를 그대로 받으면 안 되는 곳

1. **"반영 목록에 갈래를 연결"은 이미 연결돼 있을 수 있다.** 새 출처를 만들어 같은 파일을 두 번 읽으면 같은 행이 두 번 후보가 된다. 갈래는 **같은 파일을 section으로 나누는 것**이어야 한다. 허브 출처에서 행사 행을 빼고 행사 출처에 넣는다. 합치면 원본과 같아야 한다(테스트 T3).
2. **갈라서 줄이 생기는 것만으로는 끝 조건이 못 된다.** `넣음 0 · 보류 0 · 중복 0`도 줄은 찍힌다. 파일에 행사 행이 있어야 하는 날 0건이면 그것이 "미관측"인지 "관측했는데 없음"인지 줄만으로 모른다(AGENTS "먼저 알 것"). 그래서 4.2의 양성 신호가 필요하다.
3. **출처 단위 전부-아니면-전무가 이득이 된다.** 행사 행 하나가 `validate_record`에 걸리면 지금은 허브 고정 27건까지 보류된다. 갈라 두면 행사만 보류된다. 반대로 고정 쿠폰이 거부되면 행사는 들어간다. 의도한 격리다.

## 4. 결정

### 4.1 출처 분리

- `reflect_daily.sources`가 3단계 파일을 한 번 읽고 `section`으로 나눈다. 행사 구역은 `store.EVENT_SECTION`(확정액)과 `export_data.EVENT_CARD_SECTIONS`(두 구역)의 어느 쪽을 쓸지: **`EVENT_CARD_SECTIONS`를 쓴다.** 랜덤 행사 행(`위클리 슈퍼딜 > 이벤트 쿠폰`)도 같은 파일에서 오고 이슈 #55가 두 구역을 한 묶음으로 다룬다. 이슈 문구는 확정액만 말하지만 랜덤만 허브 쪽에 남기면 갈래가 반쪽이다.
- 이름 `쿠팡이츠 행사`, 단계 표식 `3e`(이슈의 출력 줄 이름과 같음). 판정은 3단계 PASS를 그대로 따른다(`verdicts["3"]`). `check_routine.judge`에 `3e`를 새로 만들지 않는다. 3이 PASS가 아니면 두 출처가 같이 건너뛴다.
- `ROUTINE-SPEC.md` §3.2 원장 출처 표에 `3e` 행을 더한다. `tests/test_reflect_sources.py`가 표와 코드를 대조하므로 안 더하면 실패한다(의도).
- 사람 보류 규칙은 `decide`를 그대로 쓴다. 바꾸지 않는다.

### 4.2 양성 신호: "행사 0건"을 믿기 전에

`reflect_daily`가 행사 출처의 입력이 비었을 때(파일은 있는데 행사 구역 행 0개) `captures/coupangeats-hub-events-<날짜>.json`을 본다. 거기에 `won`이나 `cap`이 있는 행사가 있는데 weekly 파일에 그 브랜드의 행사 행이 없으면 `[suspect] 8 쿠팡이츠 행사: 하루 행사 파일에 N곳(브랜드…)이 있는데 허브 파일에 행이 없다`를 찍는다. 반영은 막지 않는다(고정 쿠폰은 들어간다). 보고서 비고 칸에도 적는다.

- 하루 행사 파일도 없으면 "행사를 못 읽었다(미관측)"로 적고 `넣음 0`이라고만 하지 않는다. 줄 모양: `쿠팡이츠 행사: 넣음 0 · 보류 0 · 중복 0 · 거부 0  ← 행사 입력 없음(하루 행사 파일 없음)`.
- 이 신호는 H2를 다음 날부터 로그에서 바로 가르게 한다.

### 4.3 출력과 보고

- 반영 줄: `쿠팡이츠 행사: 넣음 N · 보류 N · 중복 N · 거부 N`(기존 줄 모양 유지. 이슈의 3항 모양에 `거부`가 하나 더 붙는다. `check_routine`의 거부 파서(342행)와 맞추기 위함).
- `report_md` 표에 출처 한 줄이 자동으로 늘어난다. `daily_state.skipped_files`에 `"쿠팡이츠 행사"`를 더한다(출처가 건너뛰어질 때 `stage_suspect` 관측을 만들려면 이름이 있어야 한다. 안 더하면 건너뛴 날 행사 브랜드가 `uncollected`로 조용히 빠진다).

### 4.4 원장

- `data/log.jsonl`을 직접 고치지 않는다. 기존 `append_record`로 새 관측만 더한다(append-only). 정정은 삭제가 아니다. 10-23에 이미 손으로 넣은 행은 그대로 둔다.
- 10-23 재반영은 이 설계의 범위가 아니다. 이미 지난 날이고 손 행이 있다. 필요하면 사람이 `--apply`로 판단한다.

## 6. 테스트 (결론을 박는다)

`tests/test_reflect_ce_events.py`(새 파일)

- **T1 끝 조건**: 10-23 모양의 weekly 파일 픽스처. KFC 7,000, BHC 6,000, 호식이두마리치킨 7,000, 후라이드참잘하는집 7,000 행은 `fixed_event_records`가 만든 것으로 만든다(손으로 쓰지 않음, #55와 같은 방식). 고정 쿠폰 행 몇 건과 함께 `sources`→`decide`를 돌려 `쿠팡이츠 행사` 출처의 `ingest`에 네 브랜드가 있다.
- **T2 사람 보류 유지**: 같은 브랜드의 오늘 `manual` 행이 대표일 때 행사 행은 `held`. 어제 `manual`이면 `ingest`.
- **T3 분할 무손실**: 허브 출처 + 행사 출처의 행을 합치면 원본 파일 행과 같다(중복·누락 없음). 두 출처에 같은 행이 없다.
- **T4 격리**: 행사 행 하나가 `validate_record`에 실패해도 허브 고정 출처는 `ingest`가 남고 `skipped_all`이 아니다.
- **T5 양성 신호**: (가) 하루 행사 파일에 `won` 있는 브랜드가 있고 weekly에 행이 없음 → `[suspect]` 줄. (나) 하루 행사 파일 없음 → 줄에 "행사 입력 없음"이 붙고 `넣음 0`만 찍지 않음. (다) 행사 행 있음 → suspect 없음. 그리고 `check_routine`의 8단계 판정이 새 줄에서 깨지지 않음.
- **T6 출력 줄**: `main`(tmp ROOT, 미리보기)을 돌려 stdout에 `쿠팡이츠 행사: 넣음 4 · 보류 0 · 중복 0 · 거부 0`.
- **T7 daily_state**: 3이 PASS가 아니라 행사 출처가 건너뛰어진 날, `build_daily_state`가 행사 브랜드를 `stage_suspect`로 센다.
- 기존 `tests/test_reflect_sources.py`는 표에 `3e` 행을 더하면 통과.

끝 조건 둘째("다음 정규 수집 8단계 로그에 행사 갈래 줄")는 테스트로 못 박는 것이 T6이고, 실제 확인은 다음 예약 뒤 `8.log`를 읽어 한다. **병합 전에 확인할 수 없다.**
