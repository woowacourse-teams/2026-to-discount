# 설계: 5b SUSPECT의 사유가 브랜드 단위면 나머지 쿠폰함 건을 반영한다 (이슈 #103)

- 상태: 설계 (구현 전)
- 영역: **export** (폰 불필요. 판정기, 빌더, reflect, 시험만 바꾼다. 이미 찍힌 캡처 파일로 다 시험된다)
- 읽은 것: 이슈 입력, `AGENTS.md`, `mono/docs/CHANGE-PROPAGATION.md`, `scripts/check_routine.py` 5b 절(264~282행), `scripts/build_ce_couponbox_records.py` `store_cross_check`와 `main`(277~393행), `scripts/reflect_daily.py` `sources`와 `report_md`(152~218, 325~360행), `docs/specs/issue-75-*.md`(형식 참고).
- **읽지 않은 것(구현자가 먼저 읽는다):** `docs/setup/ROUTINE-SPEC.md` §2~3, `docs/setup/CROSS-CHECK-VERDICTS.md`, `docs/specs/issue-49-*.md`, `issue-53-*.md`, `reflect_daily.py` 본문 중 `main`과 판정 인자 처리, `export_data.py`의 `couponbox_residual`. 이슈 입력이 가리키는 `logs/steps/2026-11-03/5b.log`와 `reports/routine-2026-11-03.md`는 이 러너에 없어서 **로그 원문을 못 봤다.**

## 1. 이슈를 그대로 받으면 안 되는 곳

1. **"제외 1건"과 `[suspect]`는 다른 것이다.** 판정기의 `제외`는 빌더가 레코드 하나를 뺀 줄(`^\s+제외\s`)을 센 값이다. SUSPECT를 만든 것은 `[suspect]` 줄(매장 혜택 교차검증 실패)이다. 이슈 제목의 "브랜드 2곳"은 `[suspect]` 2줄이다. 제외 1건은 사유가 아니다. 구현은 `[suspect]` 줄만 본다.
2. **빌더는 이미 그 브랜드를 뺀 파일을 낸다.** `lost_hub` 브랜드는 쿠폰함에도 매장 혜택에도 쿠폰이 없어서 `coupangeats_couponbox_records_<날짜>.json`에 행이 애초에 없다(`build`는 `[suspect]`를 찍기만 하고 레코드를 거르지 않는다, 364~370행). 그래서 "제외 브랜드만 보류"는 새로 거를 행이 없다. 필요한 것은 **reflect가 SUSPECT 파일을 받아도 되는 조건**이다.
3. **판정기가 사유를 문자열로만 남긴다.** `check_routine`은 `[suspect]` 줄 글자를 `note`에 붙일 뿐이고, `reflect_daily.sources`는 `verdicts.get("5b") == "PASS"`만 본다(183행). 사유가 브랜드 단위인지 전체인지 가르는 기계 판독 값이 없다. 로그 문구를 정규식으로 다시 읽으면 문구가 바뀔 때 조용히 "전체 보류"나 "무조건 반영"으로 기운다. 구조 값이 필요하다(3번).

## 2. 어떤 사유가 전체를 막고 어떤 사유가 브랜드만 막는가

| 사유 | 지금 판정 | 새 판정 | 이유 |
| --- | --- | --- | --- |
| 입력 없음, 허브 캡처 없음, 파일 없음, Traceback | FAIL | **그대로 FAIL** | 이슈 끝조건. 건드리지 않는다 |
| `k == 0` (확정된 쿠폰 없음, 허브 대조 실패 의심) | SUSPECT | **그대로 SUSPECT, 통째로 보류** | 이슈 끝조건의 "허브 못 읽음". 쿠폰이 0건이면 브랜드 단위로 갈라 반영할 것이 없다 |
| `허브 확정액 0곳` (허브는 있는데 확정액을 하나도 못 읽음) | 지금 SUSPECT가 아니다(`k`가 있으면 PASS 경로) | 이번 범위 밖. 후속에 적는다(10번) | 이 이슈가 만든 틈이 아니다 |
| `[suspect]`의 상태가 `lost_hub`이고, 아래 상한 안 | SUSPECT | **SUSPECT 유지 + 나머지 반영** | 한 브랜드의 시트에서 허브로 못 돌아온 것. 다른 브랜드 행은 별개로 관측됐다 |
| `[suspect]`의 상태가 `lost_hub`이 아닌 것(기록 없음 등) | SUSPECT | **통째로 보류** | 어떤 상태인지 모르는 실패는 브랜드 단위라고 증명할 수 없다. 알려진 상태만 열어 둔다(허용 목록, 거부 목록 아님) |
| `lost_hub`이 상한을 넘음 | SUSPECT | **통째로 보류** | 여러 브랜드가 연달아 허브를 잃었으면 허브 자체가 흔들린 것이다. 이슈의 "허브 못 읽음" 쪽으로 본다 |

**상한(숫자는 구현자가 정하고 사용자에게 확인):** 제안은 `lost_hub` 브랜드가 3곳 이하이고 매장 상태 기록 전체의 20% 미만일 때만 브랜드 단위로 본다. 11-03의 2곳은 들어간다. 근거는 11-03 한 건뿐이라 약하다. **리뷰 포인트.**

### 반영해도 되는 양성 신호 (넷이 모두 참일 때만)

1. 5b 판정이 SUSPECT이고, 사유가 `[suspect]` 줄뿐이다(`k == 0` 사유가 없다).
2. `k > 0`이고 레코드 파일이 오늘 날짜로 있다.
3. 빌더가 남긴 구조 값(3번)에서 모든 실패 상태가 허용 목록(`lost_hub`)에 있고 상한 안이다.
4. 구조 값의 `status_total`(상태 기록 개수)이 0보다 크다. 상태 파일이 비거나 없어서 `[suspect]`가 0줄인 것은 "문제 없음"이 아니라 미관측이므로, 이 경로는 원래 PASS 판정이 하던 일이고 새 규칙과 무관하다(양성 신호가 없는 PASS를 새로 만들지 않는다).

하나라도 거짓이면 지금처럼 통째로 건너뛴다. 기본값이 "막는다"다.

## 3. 구조 값: 빌더가 사유를 파일로 남긴다

- 빌더 `main`이 `captures/coupangeats_couponbox_suspects_<날짜>.json`을 쓴다. 내용: `{"failed": [{"brand": ..., "status": ...}], "status_total": N}`. `store_cross_check`의 `failed` 목록을 그대로 쓴다(글자를 다시 만들지 않는다).
- 상태 파일이 없어서 교차검증을 안 돈 날에는 이 파일을 **쓰지 않는다.** 파일 없음은 "관측 안 함"이고 reflect는 허용 경로를 열지 않는다. `failed: []`인 날은 쓸 수 있으나 그때는 SUSPECT가 아니므로 쓸모없다. 단순함을 위해 `failed`가 비면 쓰지 않는다.
- 판정기는 판정 문자열을 바꾸지 않는다. SUSPECT는 SUSPECT로 남고 `note`에 `[부분 반영 가능]`을 붙이지 않는다(판정기와 reflect가 각자 판단하면 두 곳이 갈린다. 규칙은 한 함수에 둔다).
- 규칙 함수 `partial_ok(day, verdicts) -> (bool, list[str])`를 `reflect_daily.py`에 둔다. 위 양성 신호 넷을 구조 값과 레코드 파일로만 판단하고, (가능 여부, 보류 브랜드 이름들)을 돌려준다. `sources`의 5b 줄이 `PASS` 또는 `(SUSPECT and partial_ok)`일 때 파일을 읽는다.
- 요기요 쿠폰함이 이미 SUSPECT를 받아들이는 선례가 있다(184~187행). 같은 방식으로 "SUSPECT의 의미를 알 때만 받는다"를 따른다. 다른 점은 요기요는 SUSPECT 전부를 받고, 이쪽은 구조 값으로 사유를 확인한 뒤에만 받는다.

## 4. 보고서에 이름으로 남긴다

`reflect_daily.report_md`의 원장 반영 표에서 쿠팡이츠 쿠폰함 줄 비고에 `부분 반영: 보류 브랜드 2곳`을 쓰고, 표 아래에 절을 하나 더한다:

```
### 보류한 브랜드 — 5b SUSPECT, 매장 혜택을 못 읽었고 쿠폰함에도 없다
- 쿠팡이츠 쿠폰함: 떡참 떡볶이&치킨 (lost_hub)
- 쿠팡이츠 쿠폰함: 세븐일레븐 (lost_hub)
```

이름과 상태가 나와야 한다. 숫자만 쓰면 이 프로젝트가 한 번씩 거짓이었던 방식이다. 통째로 보류한 날은 지금 문구("단계가 PASS가 아니거나 파일 없음 → 통째로 건너뜀")를 그대로 둔다. 둘이 문구로 갈려야 사람이 "부분"과 "전체"를 구분한다.

## 8. 원장 append-only

- 이 변경은 원장에 쓰는 **조건**만 넓힌다. 쓰는 방식(`ingest`의 append, 중복 판정, 사람이 오늘 넣은 같은 브랜드는 보류)은 안 바뀐다.
- `lost_hub` 브랜드의 기존 행은 지우지도 덮지도 않는다. 오늘 관측이 없을 뿐이다. 이 브랜드를 오늘 새 관측으로 "없음"이라고 쓰지 않는다.
- **확인할 것(읽지 않음):** 쿠폰함 출처에서 브랜드가 사라지면 `export_data.couponbox_residual`이 그 브랜드 오퍼를 내리는지. 이슈 본문은 "하루 건너뛰면 어제 값이 남는다"고 하니 PASS 날과 SUSPECT 날에 `lost_hub` 브랜드의 export 결과가 같아야 한다. 구현자는 이 동치를 시험(T11)으로 박는다: 같은 입력에서 그 브랜드의 오퍼가 부분 반영 날에도 사라지지 않는다. 안 맞으면 구현을 멈추고 사용자에게 알린다.

## 9. 하지 않는 것

1. 다른 출처(배민, 요기요, 허브 고정, 행사)의 SUSPECT 처리.
2. `[suspect]` 줄 문구, `check_routine` 판정 문자열 변경.
3. `data/targeted_skip.json`(ADR-035)과 `lost_hub` 브랜드의 관계. 타겟 건너뜀은 따로 읽는다.
4. 수집 코드(3단계의 매장 혜택 읽기) 수정. `lost_hub`이 왜 났는지는 이 이슈 범위 밖이다.
5. 폰을 잡는 일. 시험은 캡처 픽스처로만 돈다.
