# 선착순 배너 제안에서 타겟 건너뛰기 브랜드를 빼고, 승인 대기와 자동 여부를 문서와 맞춘다 (이슈 #102)

영역: `export`. 폰이 필요 없다. 이미 수집된 `captures/coupangeats-firstcome-<날짜>.json`을 읽어 제안을 만드는 순수 함수(`scripts/banner_ce.py`)를 고친다.

## 1. 문제

- 11-03 6단계 제안 16건 중 선착순 9건이 전부 `[승인 필요]`다. 네네치킨(5,000원, 17시), 호식이두마리치킨(5,000원, 15시)은 `data/targeted_skip.json`의 상시 건너뛰기 브랜드다. 원장에는 안 들어가는데 배너 제안에는 들어 있다. 승인하면 타겟 쿠폰이 공개 배너로 나간다.
- `banner_ops.py` 머리말은 쿠팡이츠 선착순 오픈을 자동 반영 대상이라고 쓴다. 코드는 `propose_ce_ops`의 `add`를 `auto=False`로 만들고(`scripts/banner_ce.py:539`), 시험도 그것을 박는다(`tests/test_banner_routine.py:1061`은 배민, `tests/test_banner_ops.py:99`, `:347`은 쿠팡이츠). 문서와 코드가 어긋난다.
- 오퍼 경로(`first_come_records`, 금액 제한 없음)와 배너 경로(`FIRST_COME_MIN_AMOUNT` 5,000원 이상)가 같은 쿠폰을 둘 다 세운다.

## 2. 사실과 미확인

확인한 것(코드):

- 타겟 건너뛰기를 읽는 곳은 `scripts/reflect_daily.py`(`read_skip`, `skip_path`)뿐이다. `banner_ce.py`는 이 목록을 모른다. 이슈 1번의 원인이다.
- 6단계가 찍는 `[승인 필요]`는 제안 쪽 `op["auto"]`를 그대로 찍은 것이다(`scripts/banner_routine.py:855`). 실제 자동 반영은 제안서를 올린 뒤 **서버가** 판정하고(`post_proposal`, `banner_routine.py:935~941` 주석: beggars-ops `ops_apply.auto_apply`), 결과를 `자동 반영(되풀이 배너): N건` 줄로 따로 찍는다.
- 그러므로 `[승인 필요]` 줄은 "서버가 자동으로 반영하지 않았다"의 증거가 아니다. 같은 로그에 `자동 반영` 줄이 있는지 봐야 한다.

미확인(이 러너에는 `logs/steps/2026-11-03/6.log`와 beggars-ops 코드가 없다):

- 11-03 6단계 로그에 `자동 반영` 줄이 있었는지.
- 서버 `auto_apply`가 `coupangeats-open-*` 배너를 어떤 기준(id 접두, `auto` 값, 그 밖)으로 되풀이 배너로 보는지.

구현자는 먼저 위 둘을 확인한다(§4 단계 0). 결과가 §5 분기를 정한다.

## 4. 변경

### 단계 0: 증거 확인 (구현 전)

- 11-03 `6.log`, `/ops/proposals/2026-11-03.json`에서 `자동 반영` 줄과 `auto.applied` 유무를 본다.
- 결과를 PR 본문 "설계 변동" 또는 확인 절에 적는다. 못 구하면 **미확인**으로 적고 §5의 (가)를 따른다.

### 변경 1: 건너뛰기 브랜드 제외

- `propose_ce_ops`에서 `opens`(`best_by_brand` 정리 직후, `carry_over_open_banners` 호출 전)에서 `targeted_skip["coupangeats"]`의 브랜드를 뺀다.
- 목록은 `reflect_daily.read_skip`을 재사용한다. 순환 import가 나면 읽기 함수만 작은 모듈로 옮긴다. 두 번째 구현을 만들지 않는다.
- 브랜드 비교는 원장 쪽과 같은 규칙(`reflect_daily`가 쓰는 정규화)을 쓴다. 배너 쪽 `_collected`의 부분 일치를 쓰지 않는다. 부분 일치는 "BBQ"가 다른 브랜드를 삼키는 식으로 틀릴 수 있다.
- 호출부가 목록을 넘기게 한다(기본값 없음 금지가 아니라, 시험이 임시 폴더를 쓰도록 인자로 받는다. `skip_path()`를 import 때 굳히지 않는다는 11-01 교훈).

### 양성 신호 (없다를 말하기 전에)

"제안서에 건너뛰기 브랜드가 없다"는 목록을 못 읽어도 참이 된다. `read_skip`은 파일이 없거나 깨지면 빈 목록을 돌려준다(원장 쪽에서는 의도된 안전 방향이지만 배너 쪽에서는 반대다. 빈 목록이면 타겟이 공개된다).

- 6단계 로그에 한 줄을 남긴다: `타겟 건너뛰기: 쿠팡이츠 N곳 읽음, 선착순에서 뺀 것: <이름들>|없음`.
- `N == 0`이고 `data/targeted_skip.json`이 존재하면 `[suspect]`(읽었는데 비었다)로 찍는다. 파일이 없거나 JSON이 깨졌으면 `[suspect] 목록 못 읽음`을 찍고 제안은 그대로 만든다(전부 막으면 선착순 알림이 통째로 멈춘다). 목록을 못 읽은 날의 제안은 사람이 승인 전에 눈으로 본다.
- `check_routine.py`가 이 줄을 보는지는 `ROUTINE-SPEC.md` 단계 6 성공 신호에 맞춰 구현자가 정한다. 줄 이름을 바꾸면 판정기와 같이 고친다.

### 변경 2: 승인 대기와 자동 여부를 한 곳에 맞춤

§5 분기에 따른다. 어느 쪽이든 `[승인 필요]` 표시가 서버 판정이 아니라 제안 쪽 값이라는 것을 `banner_routine.py` 출력 문구나 `banner_ops.py` 머리말에 적는다.

### 변경 3: 역할 문서

`docs/specs/2026-11-02-coupangeats-first-come-not-an-offer.md`에 §7을 추가한다(구현자가 쓴다).

- 오퍼 경로: 비교용. 금액 제한 없음, 그날 `expires_at`, 구역 `위클리 슈퍼딜 > 선착순 특가`. 건너뛰기 브랜드는 `reflect_daily`가 막는다.
- 배너 경로: 알림용. 5,000원 이상, 시각별 묶음, 건너뛰기 브랜드는 변경 1이 막는다.
- 겹침: 둘 다 `firstCome`으로 서는 브랜드가 있다. 서버가 하나로 합친다는 가정(REFACTOR-BACKLOG #13, 서버 `withFirstComeTier`)은 11-04 화면 확인 전까지 가정이다(§6).
- 이 문서 §1의 "원장에는 안 넣는 것이 지금 설계다"는 §0이 이미 뒤집었다. §7에서 한 번 더 가리킨다.

## 5. 선착순 배너 승인 대기 (할 일 2) 분기

비판: 이슈는 "자동이어야 하는데 왜 `auto: false`인가"로 시작하지만, 자동으로 바꾸는 것이 맞는지가 먼저다. 이 배너는 타겟 쿠폰이 새어 나온 적이 바로 이번에 확인됐다. 건너뛰기 목록은 사람이 알아챈 타겟만 안다. 새 타겟은 한 번 공개된 뒤에야 목록에 들어간다. 자동 반영은 그 한 번을 사람 눈 없이 지나간다.

- (가) 11-03에 서버가 자동 반영하지 않았거나 확인 못 함: **코드는 `auto=False` 그대로 둔다.** `banner_ops.py` 머리말의 "예외로 되풀이 배너(쿠팡이츠 선착순 오픈)는 서버가 자동 반영"을 현실에 맞게 고친다. 서버가 자동 처리하는 범위는 beggars-ops 정본을 확인해 쓰고, 확인 못 한 부분은 쓰지 않는다. `tests/test_banner_ops.py`에 "쿠팡이츠 선착순 add는 `auto`가 False"를 이미 있는 시험과 함께 머리말 인용으로 묶는다.
- (나) 서버가 `coupangeats-open-*`를 자동 반영했는데 로그만 `[승인 필요]`였다: 로그 문구를 고친다. 제안 쪽 `auto`가 아니라 서버 응답(`auto.applied`)을 근거로 "자동 반영됨 / 승인 대기"를 나눠 찍는다. 자동 반영이 기본 정책인지는 사용자가 정한다(§8).

어느 분기든 이번 PR에서 `auto`를 `True`로 바꾸지 않는다.

## 6. 오퍼와 배너 겹침: 11-04 확인 (할 일 3, 끝 조건 3)

코드 변경 없이 관측으로 닫는다. 서버 합치기는 mono 소관이라 tracker 시험으로 박을 수 없다.

- 11-04 00:01 이후 운영 API에서 선착순 브랜드(예: 단독 선착순 브랜드 하나, 상시 오퍼에 합쳐진 브랜드 하나)를 조회해 같은 (브랜드, 앱)에 `firstCome` 오퍼가 **정확히 하나**이고, 구간 금액이 겹쳐 두 번 나오지 않는지 본다.
- 양성 신호: 조회 결과에 그 브랜드의 오퍼가 1건 이상 있어야 "중복 없음"을 말할 수 있다. 0건이면 미관측이다(수집이 그날 선착순을 못 읽은 날일 수 있다. 10-30~11-01이 그랬다).
- 중복이 보이면 mono에 이슈를 만든다(후속 조치). 이번 PR에서 tracker가 한쪽 경로를 끄지 않는다.

## 7. 시험 (결론을 박는 자리)

`tests/test_banner_routine.py` 또는 `tests/test_banner_ce_targeted_skip.py`(새 파일이면 `check_routine`류 목록이 시험 파일 목록을 따로 갖는지 확인):

1. 건너뛰기 목록에 네네치킨, 호식이가 있고 오늘 선착순에도 있으면 `propose_ce_ops`의 `add` 어디에도 그 이름이 없다. 같은 입력에 다른 브랜드(KFC 등)는 남는다. 목록을 비우면 둘 다 나온다(시험이 걸러 내는 쪽이 실제로 작동함을 증명).
2. 전날 배너에 건너뛰기 브랜드가 있어도 오늘 이어쓰기(`carry`)로 되올라가지 않는다.
3. 건너뛰기 브랜드가 빠진 뒤 남은 묶음의 `notify`가 하나로 맞고(`unify_group_notify`), `firstCome == "issue"`가 남는다.
4. 목록 파일이 없을 때와 깨졌을 때 제안은 그대로 나오고 `[suspect]` 줄이 찍힌다. 존재하는데 0곳이면 `[suspect]`다.
5. 앱이 다른 같은 이름(배민의 같은 브랜드 항목)은 쿠팡이츠 선착순에서 빠지지 않는다.
6. `banner_ops.py` 머리말의 자동 반영 문장과 `propose_ce_ops`의 `add` `auto` 값이 어긋나면 실패하는 시험(분기 (가)일 때). 문서만 고치고 끝내지 않는다.
7. `ROUTINE-SPEC.md` 단계 6이 새 로그 줄을 말하면 `check_routine`이 그 줄을 읽는 시험.

점검 명령은 `docs/HARNESS.md` §11(CI가 로컬보다 넓다. 별칭표 없이 도는 줄까지).
