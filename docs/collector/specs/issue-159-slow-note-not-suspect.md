# 설계: 시간 지연 표식은 판정을 바꾸지 않고, 상한에 끊긴 실행만 막는다 (이슈 #159)

- 상태: 설계 (구현 전)
- 영역: **export** (폰 불필요. `scripts/check_routine.py`, `scripts/reflect_daily.py`, 시험, `ROUTINE-SPEC.md`만 바꾼다. 수집 코드와 `run_routine.py`는 안 고친다. 이유는 3번)
- 읽은 것: 이슈 입력, `AGENTS.md`, `.claude/agents/designer.md`, `docs/workflow/LOCAL-RULES.md`, `mono/docs/CHANGE-PROPAGATION.md`(절 제목), `scripts/run_routine.py`(시간 상한, `slow_note`, `run_cmd`, `_attempt` 재시도), `scripts/check_routine.py`(`_section`, `judge` 전체), `scripts/reflect_daily.py`(`partial_ok`, `sources`, `main`의 출처 반복), `capture/coupangeats_store_benefits.py` `probe`, `scripts/build_ce_couponbox_records.py` `STATUS_WORDS`, `docs/specs/issue-103-*.md`, `docs/setup/ROUTINE-SPEC.md` 단계 3과 5b 줄.
- **읽지 않은 것:** 11-04 15:55 회차의 `logs/steps/2026-11-04/3.log`, `5b.log`, `reports/routine-2026-11-04.md`. 이 러너에 없다. 그래서 **5b가 왜 통째로 막혔는지는 로그로 확인하지 못했다**(4번).

## 1. 이슈를 그대로 받으면 안 되는 곳

1. **"SUSPECT의 사유를 가리지 않는다"는 절반만 맞다.** 실제 길은 이렇다.
   - `run_routine.run_cmd`가 상한의 85%를 넘기면 단계 로그에 `slow_note()` 줄을 넣는다. 글자는 `[suspect] 3 시간 지연: 상한 90분의 85%(76분)를 넘겼다 — 곧 끊긴다`.
   - `check_routine` 3단계는 `"[suspect] 3 " in s`로 SUSPECT를 낸다(171행). 이 검사는 원래 **수집기**가 찍는 릴레이 여는 시각 의심(`capture/coupangeats_hub.py` 675, 684행)을 잡으려던 것이다. 러너가 찍은 시간 지연 줄이 같은 머리말이라 같이 걸렸다.
   - 즉 사유를 "가리지 못한" 게 아니다. **러너의 줄과 수집기의 줄이 같은 머리말을 써서 판정기가 둘을 구분할 구조가 없다.**
2. **같은 충돌이 3단계만의 일이 아니다.** 시간 지연 줄을 줍는 판정이 여럿이다.

   | 단계 | 줍는 정규식 | 시간 지연 줄이 들어오면 | 원장 반영을 막나 |
   | --- | --- | --- | --- |
   | 3 | `"[suspect] 3 " in s` | SUSPECT | **막는다**(허브 고정 쿠폰, 행사 둘 다. `sources` 225행) |
   | 3w | `^\s*\[(?:suspect\|fail)\]` | SUSPECT | 안 막음 |
   | 3s | `^\s*\[suspect\]` | SUSPECT | 안 막음 |
   | 4 (4a~4g 한 구획) | `^\s*\[suspect\]` | SUSPECT | 안 막음 |
   | 5b | `^\s*\[suspect\]` | SUSPECT | **막는다**(`partial_ok`도 안 열림. 사유 파일에 시간 지연이 없다) |
   | 5y | `^\[suspect\] 5y ` | SUSPECT | 안 막음(5y는 SUSPECT도 받는다) |
   | 8 | `^\[suspect\] 8 ` | SUSPECT | 해당 없음 |
   | 2, 5, 5a, 6, 7 | `[suspect]`을 안 본다 | 그대로 | 그대로 |

   그래서 3단계만 예외로 빼면 다음 달 5b나 다른 단계에서 같은 일이 난다. 고치는 자리는 **판정기 앞단 한 곳**이다(3번).
3. **"끊긴 실행은 지금처럼 막는다"는 지금 양성 신호로 막고 있지 않다.** `run_cmd`는 끊기면 `[timeout] N분을 넘겨 끊었다` 줄을 남기고 rc 124를 돌려준다. 그런데 `check_routine`은 `[timeout]`을 어디서도 읽지 않는다(검색 0건). 지금 FAIL은 "파일 없음"이나 "요약 줄 없음"으로 우연히 난다. 15:55 회차가 끊겨도 같은 날 08:30 회차의 `captures/coupangeats-weekly-<날짜>.json`이 남아 있으므로 "파일 있음"은 이 회차가 끝까지 돌았다는 신호가 아니다. 끊김은 `[timeout]` 줄 하나로 직접 FAIL로 만든다.
4. **5b의 `lost_hub`는 다른 결이다.** 시간 지연은 러너 시계의 말이고 값은 온전하다. `lost_hub`는 수집기의 말이고, 그 브랜드의 값이 실제로 없다. #103이 이미 "브랜드 3곳 이하, 상태 기록의 20% 미만"이면 나머지를 반영하도록 열었다(`partial_ok`). 11-04에 왜 안 열렸는지는 로그가 없어 모른다. 근거 없이 상한을 넓히지 않는다. 대신 **`partial_ok`가 왜 안 열었는지를 보고서에 이름으로 남겨** 다음 회차부터 사람이 읽을 수 있게 한다(5번).
   - 가능한 사유: 3단계가 오래 돌며 `허브를 다시 못 열어 남은 N곳을 읽지 못했다`(`probe` 148행)가 나서 남은 브랜드가 전부 `lost_hub`로 적혔으면 상한을 넘는다. 이 경우 통째로 막는 것이 #103의 뜻("허브 자체가 흔들렸다")과 맞다. **확인하지 않은 가정이다.**

## 2. 판정 규칙

러너가 단계 출력에 덧붙이는 줄(시간 지연, 끊김, 재시도)은 **판정기 앞단이 먼저 읽고 단계별 판정에서는 지운다.** 단계별 판정은 수집기가 찍은 줄만 본다.

| 러너 줄 | 지금 | 새 판정 | 이유 |
| --- | --- | --- | --- |
| 시간 지연(`slow_note()`의 출력) | 위 표의 단계에서 SUSPECT | **판정은 그대로**(단계별 판정 결과를 따른다). 근거 칸 끝에 `· 시간 지연(상한 90분의 85% 넘김)`을 붙인다 | 완주했고 성공 신호가 다 있으면 값은 온전하다. 경고는 사라지지 않고 근거 칸으로 옮겨진다 |
| 끊김(`[timeout] N분을 넘겨 끊었다`) | 읽지 않음. 파일 유무로 우연히 FAIL | **FAIL**. 근거 `상한 N분에 끊김 — <원래 근거>` | 1-3번. 같은 날 앞 회차 파일이 남아 있어도 막는다 |
| 성공한 재시도(`[retry] … - 성공`) | `_section`이 그 뒤만 본다 | 그대로 | 첫 시도의 시간 지연이나 실패는 판정에 안 들어간다. 시간 초과는 재시도하지 않으므로(`_attempt` 476행) `[timeout]`이 성공한 재시도 앞에 숨는 경우는 없다 |

수집기가 찍는 `[suspect]`(릴레이 여는 시각, `lost_hub`, 배민 시간 예산 소진, 링크 수확 0건 등)는 지금처럼 SUSPECT다. 수집기가 제 시간 예산 때문에 일찍 멈춘 경우(`full_audit` 940행 `[suspect] 4 배민 시간 예산 …`)도 수집기 줄이므로 그대로 SUSPECT로 남는다. 이번에 바뀌는 것은 **러너가 찍은 줄**뿐이다.

## 3. 구현 자리: 판정기 앞단 하나, 러너는 안 고친다

### 고르는 안

`check_routine.py`에 러너 줄을 읽는 함수 하나를 둔다.

- `runner_notes(section) -> (cleaned, slow, timed_out)`
  - `slow`: 시간 지연 줄의 (상한 분, 퍼센트) 또는 None.
  - `timed_out`: `^\[timeout\] (\d+)분을 넘겨 끊었다$` 줄의 상한 분 또는 None.
  - `cleaned`: 시간 지연 줄을 뺀 구획. `[timeout]` 줄은 단계 판정이 쓰지 않으므로 빼도 되고 둬도 된다(구현자가 고른다).
- 시간 지연 줄은 `run_routine.slow_note()`가 만드는 **모양 전체**로 짚는다: `^\[suspect\] (\S+) 시간 지연: 상한 (\d+)분의 (\d+)%`. `[suspect]`만으로나 `시간 지연`만으로 짚지 않는다.
- `_section`이 돌려주는 구획에서 시간 지연 줄을 빼는 것은 `_section` 안에서 한다. `_section`은 `reflect_daily`(`hot_state`, 2단계 구역, 재판정)도 쓰므로 한 곳에서 빼면 모두에게 같이 적용된다. `judge`는 단계마다 원본 구획을 따로 읽어 `slow`와 `timed_out`을 얻는다(예: `_section(log, step, raw=True)` 인자, 또는 별도 함수. 구현자가 고른다).
- `judge` 끝에 한 번 돈다: 단계마다 `timed_out`이면 FAIL로 바꾸고, `slow`면 근거에 덧붙인다. 단계별 블록 안에 흩어 넣지 않는다.
- 4단계 구획은 4a~4g 여섯이 한 구획이다(`run_routine.SECTION_OF`). 시간 지연 줄의 단계 이름(`4a`)과 구획 이름(`4`)이 다르다. 근거에는 줄의 단계 이름을 쓴다(`· 4a 시간 지연(…)`).

### 버린 안

- **`run_routine.slow_note()`의 머리말을 `[slow]`로 바꾼다.** 구조상 더 깔끔하다. 버린 이유:
  - `run_routine.py`는 예약 수집이 부르는 코드다. `AGENTS.md` 규칙상 다음 예약 전에 수집 PC에서 그 단계를 `--skip`으로 골라 돌려야 하고 클라우드 러너에서 끝나지 않는다.
  - 11-04처럼 이미 쓰인 로그는 옛 머리말이다. 판정기가 옛 모양을 어차피 읽어야 재판정(`reflect_daily` 475행 이하)이 맞는다. 그러면 두 모양을 다 읽는 코드가 남는다.
  - 머리말을 바꾸는 일은 후속으로 둔다(9번). 이 설계의 판정기는 두 모양을 다 읽게 짜면 후속이 판정기를 다시 고칠 일이 없다.
- **3단계만 `시간 지연`이 든 줄을 빼고 SUSPECT를 낸다.** 1-2번 표의 다른 단계가 남는다. 글자 일부로 짚는 방식이라 문구가 바뀌면 조용히 다시 SUSPECT가 된다.
- **`reflect_daily`가 SUSPECT 사유를 다시 읽어 시간 지연만이면 받는다.** 판정과 반영의 규칙이 두 곳으로 갈린다. #103 설계 3번이 같은 이유로 버린 길이다.

## 4. 반영 쪽은 고칠 것이 없다

`reflect_daily.sources`는 판정 결과만 본다. 3단계가 PASS로 나오면 허브 고정 쿠폰과 행사가 지금 그대로 들어간다. `reflect_daily`의 3단계 관련 코드는 바꾸지 않는다.

## 5. 5b: 부분 반영을 안 연 사유를 남긴다

- `partial_ok`가 False를 돌려줄 때 **사유 코드**를 같이 돌려준다. 코드는 구조 값에서 나온다.

  | 코드 | 조건 |
  | --- | --- |
  | `not_suspect` | 5b가 SUSPECT가 아님(PASS, FAIL, 없음) |
  | `no_records` | 레코드 파일이 없거나 0건 |
  | `no_suspects_file` | 사유 파일 없음(관측 안 함) |
  | `bad_suspects_file` | 사유 파일을 못 읽음, 칸 없음 |
  | `empty` | `failed`가 비었거나 `status_total` ≤ 0 |
  | `other_status` | `lost_hub`이 아닌 상태가 섞임. 그 상태 이름들을 같이 낸다 |
  | `over_cap` | `lost_hub`이 3곳 초과이거나 20% 이상. 몇 곳 / 몇 곳 중인지 같이 낸다 |

- 돌려주는 모양은 구현자가 고른다(세 번째 값, 또는 작은 dataclass). 부르는 자리는 `sources` 230행과 `main` 694행 두 곳이다.
- `main`의 건너뜀 줄과 보고서 원장 반영 표의 쿠팡이츠 쿠폰함 비고에 사유를 쓴다. 예: `건너뜀(단계 5b = SUSPECT, 부분 반영 안 함: over_cap lost_hub 9곳 / 26곳)`. 다른 출처의 건너뜀 문구는 안 바꾼다.
- 상한(3곳, 20%)과 허용 목록은 **안 바꾼다.** 사유가 보고서에 쌓인 뒤 사용자가 정한다.

## 7. "없다 / 0 / 통과"의 양성 신호

| 자리 | 조용히 거짓이 되는 때 | 양성 신호 |
| --- | --- | --- |
| 3단계 PASS(시간 지연 날) | 시간 지연 줄을 지웠더니 아무 줄도 안 남아 PASS | 단계별 성공 신호(파일, `고정 쿠폰 N곳` N ≥ 1, 카드 합 10 이상)가 여전히 필요하다(T7) |
| 끊김 없음 | `[timeout]` 줄이 없다 = 끝까지 돌았다로 읽음 | `[timeout]`은 끊김의 양성 신호다. 끊기지 않은 날의 PASS는 지금처럼 성공 줄이 증명한다. 둘을 같이 본다(T2, T5) |
| 파일 있음 | 같은 날 앞 회차 파일 | 끊김이면 파일 유무와 무관하게 FAIL(T2) |
| 시간 지연 줄 인식 | `slow_note` 문구가 바뀌어 판정기가 못 알아보고 다시 SUSPECT로 막음, 또는 반대로 수집기 줄을 시간 지연으로 오인 | 생산자 함수로 맞대기(T6). 모양 전체로 짚는다(3번) |
| 5b 건너뜀 | "건너뜀(단계 5b = SUSPECT)"만 보이고 왜인지 모름 | 사유 코드와 곳 수(T9, T10) |
| 경고가 사라짐 | 시간 지연이 SUSPECT에서 빠져 사람이 못 봄 | 근거 칸에 남는다. 보고서 단계 판정 표에 그대로 찍힌다(T1) |

## 8. 원장 append-only

- 원장에 쓰는 **조건**만 바뀐다. 3단계가 시간 지연만 있는 날에 PASS가 되어 허브 고정 쿠폰과 행사 행이 들어간다. 쓰는 방식(`ingest`의 append, 중복 판정, 사람이 오늘 넣은 같은 브랜드는 보류, `targeted_skip`)은 안 바뀐다.
- 반대 방향도 있다. 끊긴 회차가 지금 우연히 PASS를 받던 길(앞 회차 파일 + 남은 요약 줄)이 있었다면 그 회차는 이제 반영되지 않는다. 지우는 것이 아니라 새 행을 안 쓰는 것이라 원장에 남은 행은 그대로다.
- 11-04 15:55 회차의 값을 뒤늦게 넣는 일은 이 설계 범위 밖이다. 다음 회차가 새 관측을 쓴다. 꼭 넣어야 하면 사람이 `reflect_daily --pass 3`으로 한다(이미 있는 길).
