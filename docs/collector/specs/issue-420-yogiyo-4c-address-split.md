# 이슈 #420 설계: 4c 요기요 전수조사 주소 분할

출처: https://github.com/nn98/delivery-discount-tracker/issues/420 (본문이 정본, 이 파일은 같은 내용을 설계 브랜치에 둔 것). 사용자 승인 2026-11-18.


4c(요기요 전수조사)를 폰 한 대가 저장 주소를 차례로 도는 구조에서, 폰 여러 대가 주소를 하나씩 꺼내 가는 공용 큐로 바꿈. 배민 4a의 폰 분산(#66, `_SharedLinks`, `AUDIT_HELPERS`, 도중 합류)과 같은 틀. 폰이 한 대뿐이면 지금 동작 그대로.

## 배경

- 4c는 폰 한 대가 `scripts/full_audit.py` `audit_yogiyo`에서 저장 주소(회사, 창원, 솔데스크, 돼지, 집, 마산, 우테코, 제이펜션 등)를 차례로 읽음. 90분 상한(`STEP_TIMEOUT_LONG["4c"]`)에 끊긴 기록: 11-10 두 번, 11-16 08:30(45곳 읽고 끊김, 5y까지 건너뜀). 대응은 V30 제외(덤프가 3~4배 느림)와 이어 읽기(PR #328)였고 분할은 아님.
- 분할 제안은 10-13 인계(`handoff-guard-vanishing-offers-20261013.md` 36~41행)에 한 번 있었고 구현 없음. 막힌 이유는 "폰 둘이 같은 명령을 돌리면 주소가 겹치고 `audit-<날짜>.json`과 `yogiyo_address_stats.json`이 마지막 실행으로 덮임".
- 폰 사이 주소 번짐 우려는 풀림:
  - 11-11 사용자 확인(가설 H20 기각): 한 폰에서 주소를 바꿔도 다른 폰에 영향 없음. 저장 주소 목록만 계정에 묶여 같고 선택된 주소는 폰마다 따로.
  - 11-14 이슈 #269: 노트20과 V50이 같은 계정으로 동시에 주소를 바꿔 20초 간격 4회 확인에서 번짐 없음. PR #302 본문에 4대 동시 시험에서 4대 모두 읽힘.
  - 11-18 23시 실측: 같은 계정의 폰 6대가 쿠팡이츠, 배민, 땡겨요, 요기요를 같은 시각에 열었고 모두 로그인 유지(요기요는 깨어 있던 4대 확인).
- **확인 못 한 것(추정으로 둠):** 요기요 폰 4대가 몇 시간 동시에 주소를 바꿔 가며 읽을 때의 번짐과 세션. 11-07 창원 2곳만 읽힌 원인(#263, #147 열림)은 동시 사용 없이도 났고 미해결.

## 설계

### 1. 단위는 주소 하나

- 큐 항목은 주소 이름. 폰이 하나 꺼내 `select_saved_address` → `open_discount_tab` → `sweep_brand_coupons`로 그 주소의 목록을 읽음.
- 이름 순서(`yogiyo_addresses.json`, 건너뛰기 기준 `yogiyo_address_stats.json`)는 지금 규칙 그대로. 건너뛰는 주소(지난번 새 브랜드 0, 월요일, 매월 1일, `--all-addresses`는 전부)는 큐에 안 넣음.
- 폰에 없는 주소는 그 폰이 도로 큐에 돌려주고 `tried`에 적어 다른 폰이 맡음(`_SharedLinks.view(serial)`의 `tried`와 같은 방식). 저장 주소 목록은 폰마다 한 번 읽어 기억(`phone_labels_once`, #224).

### 2. 폰 고르기

- `NEEDS["4c"]`에 `share=True`, `JOINABLE`에 4c 추가. 4a가 쓰는 `AUDIT_HELPERS`와 도중 합류 파일(`AUDIT_JOIN`)을 `audit_yogiyo`가 읽음.
- 후보는 지금 4c 후보와 같음(요기요 membership + 덤프 가능). V30은 `exclusions`로 계속 뺌.
- 후보가 한 대면 지금 경로(단일 폰, 순차)를 그대로 탐. 폰이 늘어도 단계 이름, 상한, 이어 읽기(`RESUME_ON_TIMEOUT`)는 그대로.

### 3. 겹치는 브랜드 건너뛰기와 주소 귀속

지금은 앞 주소에서 읽은 브랜드를 뒤 주소에서 안 열고(`skip=frozenset(merged)`), 한 브랜드의 `target_address`는 그 브랜드를 처음 읽은 주소. 순서가 고정이라 결과가 매번 같음. 병렬이면 어느 폰이 먼저 읽느냐로 귀속이 흔들림.

- 읽기는 병렬, **귀속은 병합 때 정함**: 한 브랜드를 여러 주소가 읽었으면 이름 순서에서 가장 앞선 주소 것을 씀. 나머지 항목은 버림.
- 건너뛰기는 최선 노력: 큐에서 꺼낼 때 다른 폰이 이미 끝낸 주소들이 읽은 브랜드만 건너뜀(끝낸 주소 단위로만 공유). 읽는 도중 다른 폰의 진행은 보지 않음. 겹쳐 열리는 만큼 시간이 늘지만 값은 같음.
- 주소별 통계(`new`, `got`, `brands`, `base`)는 병합 뒤 이름 순서로 계산해 한 번에 씀. 폰 스레드는 파일을 쓰지 않음(10-13 인계가 막혔던 지점: `audit-<날짜>.json`, `yogiyo_address_stats.json` 덮임).

### 4. 진행 파일과 중간 저장

- `progress.json`은 브랜드마다 쓰는 지금 방식을 유지하되 잠금 하나로 직렬화(임시 파일 후 교체는 그대로). 끊겨도 다음 실행이 남은 곳만 읽음.
- 폰마다 마지막에 기본 주소(이름 순서 첫째)로 되돌리는 `finally`는 폰별로 실행.

### 5. 실패와 시간

- 주소 하나가 두 번 실패하면 다른 폰이 한 번 더 맡음(`_collect_parallel`과 같은 규칙). 그래도 실패면 지금처럼 `[suspect]`를 남기고 그 주소의 지난번 브랜드는 "안 봤다"로 처리(`PARTIAL_ADDRESS_BRANDS`).
- 폰 하나가 끊기면(`wait_for_device` 실패, 화면 꺼짐) 그 폰의 남은 주소는 큐에 남아 다른 폰이 가져감.
- 기대 효과: 주소가 8곳이고 폰이 3대면 읽는 시간이 대략 1/3~1/2(**추정**, 겹침 건너뛰기 손실과 폰별 덤프 속도 차이 때문. 구현 뒤 실측으로 채움).

### 6. 하지 않는 것

- 땡겨요(4b, 4d)와 쿠팡이츠 탭 분할은 별도 이슈. 4d는 수확 목록이 폰, 시각마다 달라 사전에 나눌 수 없음(#399).
- 주소 목록 자체의 정본화(`yogiyo_addresses.json` 4곳 vs 폰에서 읽은 8곳)는 이 변경에서 바꾸지 않음.
- 요기요 낮은 읽기 원인 조사(#263, #147)와 기준값 2099 사고(#227)는 따로.

- [ ] 첫 정기 회차 4c: 소요 시간과 폰별 읽은 주소를 비교해 이슈에 적음. 읽은 브랜드 수가 지난 4회 범위 안.
