# 설계: 쿠팡이츠 확정액 행사 구간과 쿠폰함 구간을 한 오퍼로 합친다 (이슈 #56)

- 상태: 설계 (구현 전)
- 영역: **export.** 폰이 필요 없다. 병합 규칙(`store.py`)과 테스트만 고친다.
- 읽은 것: 이슈 입력, `data/log.jsonl` 2026-10-23 쿠팡이츠 KFC 행 8건(15352, 15391, 15531, 15569, 15575, 15578, 15583, 15587행), `store.py`(`_prefer`, `_same_coupon`, `MERGEABLE_DETAIL`, `offer_key`, `_same_day_other_source`), `scripts/coupangeats_weekly.py`의 `fixed_event_records`, `check_deploy.py`의 `classify_detail` 머리말, 설계 `issue-38-coupangeats-tier-offer-loss.md`, `mono/docs/CHANGE-PROPAGATION.md` 묶음 목록.
- 읽지 못한 것: `check_deploy.classify_detail` 본문 후반(구간 비교부), `export_data.build_export` 전문, mono `Offer.preferredOver`/`withDetailFrom`과 `offer-cases.json`, 가드 막힘 당시 로그(이슈 #54). 구현자가 읽고 확인한다.

## 1. 원인 (원장 행으로 확인한 것)

이슈는 "다른 갈래라 합쳐지지 않는 것으로 봄(추정)"이라 적었다. 원장을 읽어 보니 추정이 맞고, 막는 자리는 `store._prefer`다.

2026-10-23 KFC 쿠팡이츠 행(`offer_key`가 `(coupangeats, KFC)`로 같은 것):

| 시각 | 구역 | 금액 | tiers | 비고 |
|---|---|---|---|---|
| 01:10, 09:37 | 위클리 슈퍼딜 > 브랜드 할인 | 5,000 | 5,000(19,000원 이상, 월 1회) | 허브 |
| 01:49, 09:42 | 쿠폰함 보유쿠폰 | 5,000 | 5,000(19,000원 이상, 배달, 월 1회) | 만료 10-25 |
| 10:22:50 | 릴레이 슈퍼딜 > 스페셜 특가 | 7,000 | 없음 | `fixed_event_records` 자동 행 |
| 10:23:43 | 같은 구역 | 7,000 | 7,000 / 5,000 두 구간 | **사람이 직접 넣은 행**(`manual`) |

(`랜덤` 7,000원 두 행은 `offer_key`가 달라 여기 오지 않는다. 하나는 `misread`로 제외됐다.)

- 자동 행만 있으면: 7,000원 행과 5,000원 행은 같은 날 다른 자리에서 읽혔고 금액이 다르다. `_prefer`의 "같은 날 다른 자리" 분기가 큰 쪽(7,000)을 세운다.
- 이긴 쪽을 세운 뒤 `_same_coupon`이 금액 비교로 거짓이라 `MERGEABLE_DETAIL`(tiers 포함)이 한 글자도 안 옮겨진다. 5,000원 구간이 사라진다.
- 지금 내보내기에 두 구간이 보이는 것은 10:23:43 사람 행이 마지막으로 이기기 때문이다. 다음 자동 수집이 새 7,000원 행을 쓰면 사람 행은 더 이른 시각이라 다시 5,000원 구간이 빠진다. **이슈 #54가 `--accept-loss KFC`로 넘긴 상태가 매일 되풀이될 수 있다.**
- 금액이 다르면 다른 쿠폰이라는 `_same_coupon`의 근거(2026-07-31 훌랄라: 12,100원 한정 쿠폰의 메뉴 조건이 5,000원 오퍼에 붙음)는 맞다. 그 가드는 그대로 둔다. 구간 합치기는 **상세를 옮기는 일이 아니라 구간 목록의 합집합**으로 따로 다룬다.

## 2. 결정

1. `_prefer`의 "같은 날 다른 자리, 금액이 다른 확정 오퍼" 분기에서, 이긴 쪽 대표값(금액, 구역, 시각, badge 등)은 지금 그대로 두고 **구간(tiers)만 합집합으로 만든다.** `_same_coupon`은 바꾸지 않는다. `MERGEABLE_DETAIL`의 다른 필드(최소주문, 조건)는 금액이 다르면 계속 안 옮긴다.
2. 합치는 규칙(새 함수 `_fold_tiers(winner, loser)`):
   - 각 쪽의 구간 목록은 `tiers`가 있으면 그것, 없으면 `[{amount, min_order, membership}]` 한 개(대표 금액 자체)로 본다. 최소주문이 `None`인 것은 `None`으로 둔다(0으로 바꾸지 않는다).
   - 같은 `(amount, min_order, membership)`는 하나로 접는다. 접을 때 `channel`, `note`처럼 더 많이 채워진 쪽을 남긴다(쿠폰함의 `channel: 배달`).
   - 정렬은 금액 내림차순. 이긴 쪽 대표 금액의 구간이 맨 앞이다.
   - `tier_mode`는 이긴 쪽을 따른다(`exclusive`).
3. 합치는 대상은 아래를 모두 만족하는 쪽뿐이다. 하나라도 어기면 합치지 않는다(지금 동작과 같다).
   - 두 레코드 `platform == coupangeats`. 다른 앱은 이번에 넣지 않는다(§3).
   - 둘 다 `_is_confirmed`이고, `excluded`가 없고, `sold_out`이 아니다.
   - `_same_day_other_source`가 참(같은 날, 다른 자리 또는 5분 안). 날이 다르면 옛 쿠폰이라 합치지 않는다.
   - 지는 쪽 만료일(`expires_at`)이 이긴 쪽 캡처 날보다 앞이 아니다. 만료된 구간을 되살리지 않는다.
4. 합친 결과의 `tiers`는 **원장에 쓰지 않는다.** 읽는 쪽(`latest_per_brand`)에서만 만든다(§7).
5. 선착순(`offer_key` 3번째 칸이 `선착순`)과 랜덤은 키가 달라 이 분기에 오지 않는다. 그대로 둔다.

## 4. "없다 / 0 / 통과"의 양성 신호

| 자리 | 지금 "없다"가 뜨는 때 | 양성 신호 |
|---|---|---|
| "구간이 합쳐졌다" 결론 | 이긴 행 tiers가 `None`인 것과 합칠 게 없던 것이 같아 보인다 | 테스트가 지는 쪽 행의 구간 집합을 먼저 단언하고, 내보낸 구간이 그 집합을 포함하는지(차집합이 빈지) 본다 |
| 가드 "막히지 않음" | 로컬 내보내기에 서버와 같은 키가 없으면 가드가 그 키를 건너뛴다(`candidates`가 없으면 `continue`) | KFC가 내보내기에 **존재**하고 구간이 둘이라는 단언을 먼저 하고, 그 뒤에 `classify_detail`의 소실 줄이 KFC를 포함하지 않는다는 단언 |
| 합치지 않은 경우 | 조건 하나를 어겨 합치지 않은 것과 후보가 없던 것이 같아 보인다 | 아래 T3은 어긴 조건마다 "합치지 않음" 결과를 따로 단언 |

## 5. 원장 append-only

- 원장(`data/log.jsonl`)은 읽기만 한다. 10-23 사람 행(10:23:43)과 자동 행은 그대로 둔다.
- 합집합은 `latest_per_brand`가 내보낼 때 계산하는 값이다. 원장에 새 행이나 수정 행을 쓰지 않는다.
- 고정물은 원장 행을 `tests/fixtures/`로 **복사한** 사본이다.

## 6. 테스트 (결론을 박는 곳)

파일 이름은 구현자가 정한다(제안: `tests/test_ce_fixed_tier_merge.py`). 옛 코드에서 먼저 빨갛게 확인한다.

- **T1 KFC 10-23 재현 (끝 조건 1):** 고정물 = 09:37 허브 5,000, 09:42 쿠폰함 5,000, 10:22:50 자동 7,000 (**10:23:43 사람 행을 넣지 않는다**). `latest_per_brand` 결과의 `(coupangeats, KFC)` 항목이 `amount == 7000`이고 `tiers`가 `[7000(최소주문 None, coupangEats), 5000(19000, coupangEats, 월 1회)]`.
- **T1b 순서 무관:** 같은 행을 모든 순열로 넣어도 같은 결과.
- **T2 사람 행 포함:** 10:23:43 행까지 넣어도 구간이 둘이고 중복이 없다(접기).
- **T3 합치지 않는 경우(조건마다 하나):** 다른 날의 행 / 다른 앱 / `excluded` 행 / `sold_out` 행 / 만료된 쿠폰함 행 / `needs_review` 행 — 각각 구간이 7,000 하나이거나 이긴 쪽 원래 tiers 그대로.
- **T4 월 1회 표식:** 합친 구간의 `note: 월 1회`가 `drop_stale_monthly_notes`를 거친 뒤에도 달 목록과 맞게 남거나 지워진다(기존 규칙 그대로). 합집합이 새 `note`를 만들어 내지 않는다.
- **T5 내보내기와 가드 (끝 조건 2):** T1 고정물을 `build_export`에 넣은 결과를 입력으로, 서버 쪽에 10-23 KFC 두 구간이 있다고 두고 `check_deploy.classify_detail`을 부른다. KFC 존재 단언 뒤 소실 줄에 KFC가 없다. 구현자가 서버 값 형식을 `tests/test_check_deploy.py`에서 따라 쓴다.
- **T6 영향 측정:** 전체 원장을 옛 코드와 새 코드로 `latest_per_brand`에 넣어 **내용이 달라진 항목**을 표로 뽑아 PR 본문에 싣는다. 쿠팡이츠 아닌 앱이 하나라도 달라지면 실패(조건 3의 platform 가드가 새는 것). 쿠팡이츠 항목 중 KFC 외에 바뀐 브랜드(예: 자담치킨 6,000 허브와 4,000 월간쿠폰)는 구간이 맞는지 사람이 본다.
- **T7 API 일치:** §3 표대로 `offer-cases.json`을 읽은 결과를 PR 본문에 적는다.

## 7. 끝 조건

- T1~T5 통과. T1은 옛 코드에서 실패.
- 내보내기 미리보기(`export_data` 미리보기 명령)에서 KFC가 가드에 막히지 않는다. 폰과 서버 없이 T5로 대신하고, 미리보기 출력도 PR 본문에 붙인다.
- 순수 export 변경이라 `collect_trial.ps1` 실수집 시험은 필요 없다.
- 변경 전파표의 같은 묶음 자리를 PR 본문에 "넣음 / 안 넣음 + 이유"로 적는다.

## 8. 하지 않는 것

1. 원장 행의 수정, 삭제, 새 행 쓰기.
2. `_same_coupon`과 `MERGEABLE_DETAIL`의 변경(금액이 다르면 최소주문과 조건을 안 옮기는 규칙).
3. 쿠팡이츠 외 앱의 구간 합치기.
4. 구간 수 감소를 소실로 보는 가드 보강(#50).
5. `tiers` 모양 변경과 `export.json` 공개 계약 변경.
6. mono 코드 수정.

## 9. 리뷰에서 물을 것

- 쿠팡이츠 안에서 같은 날 금액이 다른 확정 오퍼는 모두 "한 오퍼의 구간"으로 봐도 되는가. 예: 허브 6,000원과 쿠폰함 4,000원. **이 설계는 그렇다고 가정했다(미확인).** 아니라면 합치는 조건을 `fixed_event_records` 구역(`릴레이 슈퍼딜 > 스페셜 특가`)에 한정한다. T6 표가 이 가정을 가른다.
- `expires_at`이 서로 다른 구간을 한 항목에 두면 항목 만료일은 이긴 쪽 값이다. 쿠폰함 5,000원은 10-25에 끝나는데 7,000원 행은 만료일이 없다. 구간별 만료를 표현할 자리가 없어 **끝난 구간이 남을 수 있다(미확인).** 조건 3의 만료 가드가 캡처 시점에만 걸린다는 한계를 구현자가 확인한다.
