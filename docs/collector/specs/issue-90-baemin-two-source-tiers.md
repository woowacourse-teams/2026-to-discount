# 설계: 배민 한 브랜드의 브랜드관 행과 쿠폰함 행 구간을 한 오퍼로 합친다 (이슈 #90, #80 대체)

- 상태: 설계 (구현 전)
- 영역: **export** (폰 불필요). 병합 규칙(`store.py`)과 테스트만 고친다.
- 읽은 것: 이슈 입력, `store.py`(`_prefer` 219~284행, `_same_day_other_source`, `_tiers_foldable`, `_fold_tiers`, `_fold_event_and_box`, `latest_per_brand`), `tests/test_same_day_other_source.py` 앞부분, `check_deploy.py` 함수 목록, 설계 `issue-56-*.md`, `issue-50-*.md`, `issue-27-*.md`, `mono/docs/CHANGE-PROPAGATION.md`(배민 grep 1줄).
- 읽지 못한 것 (구현자가 읽고 확인한다):
  - 도미노피자, 자담치킨 배민 원장 행의 구간 내용. 원장 줄이 길어 이 세션에서 필드를 뽑지 못했다. 아래 §1의 원인은 이슈 근거와 코드에서 **추론한 것**이다.
  - `check_deploy.classify_detail` 본문, `export_data.build_export` 전문, `build_baemin_couponbox_records.py` 본문.
  - 배민 `브랜드관 쿠폰` 행을 만드는 빌더(구역 이름이 이슈에만 있고 코드에서 확인 못 함).
  - mono `Offer.preferredOver`/`withDetailFrom`과 `offer-cases.json`.

## 1. 원인 (추론, 구현자가 원장으로 확인)

- 배민은 `offer_key`가 `(baemin, 브랜드)` 하나다. 같은 날 `브랜드관 쿠폰` 행과 `쿠폰함 보유쿠폰`(또는 다른 구역) 행이 금액이 다르면 `_prefer`의 "같은 날 다른 자리" 분기가 **큰 금액 쪽을 세운다**.
- 구간 합집합(`_fold_tiers`)은 `_tiers_foldable`이 쿠팡이츠의 행사 구역과 쿠폰함 조합만 허용해서 배민은 타지 않는다(#56이 의도적으로 쿠팡이츠로 한정했다).
- 그래서 내보내기 구간은 그날 어느 행이 이겼는지에 달린다. 이슈의 도미노피자: 서버는 `[9000, 5000]`, 어떤 회차는 9,000만 가진 행이 이겨 5,000 구간이 빠진다. 5,000원은 10-19 뒤로도 `브랜드관 쿠폰`에 11번 다시 보였으니(11-02 17:32까지) **살아 있는 구간**이다. 자담치킨 3,000원은 10-20~10-25 `쿠폰함 보유쿠폰`에 다시 보였다.
- 가드(#71)는 막는 게 옳았다. #80의 "두 회차 연속 없음이면 통과"는 구간이 계속 다시 보이는 이 모양을 못 푼다. 가드를 풀어 주는 쪽이 아니라 **내보내기가 구간을 잃지 않게** 하는 쪽이 맞다.

## 2. 비판: 이슈가 열어 둔 선택지

이슈는 "합집합 또는 브랜드관 우선"을 예로 든다.

1. **브랜드관 우선은 안 쓴다.** 구간이 있는 쪽을 고정으로 세우면 반대 출처에서만 보이는 구간(자담치킨 3,000은 쿠폰함에서 보였다)이 같은 이유로 빠진다. 출처가 바뀌어도 같은 병이 남는다.
2. **합집합을 택한다.** #56이 이미 같은 문제를 쿠팡이츠에서 합집합으로 풀었고, 대표값(금액, 구역, 시각)은 지금처럼 큰 쪽이 서며 구간 목록만 합친다. 새 규칙을 만들지 않고 기존 `_fold_tiers`를 재사용한다.
3. **위험:** 합집합은 끝난 구간을 되살릴 수 있다. #56의 만료 가드(구간 `expires_at`이 상대 캡처 날보다 앞이면 안 합침)를 그대로 가져온다. 만료일이 없는 배민 행은 가드가 못 건다. 이 구멍은 §6 T3과 §9 질문 1로 드러낸다.
4. **위험:** 배민은 일반 쿠폰과 배민클럽 쿠폰이 별개 오퍼다(청년피자 일반 4,000과 클럽 7,500, #56 §3). 합집합 키 `(amount, min_order, membership)`에서 membership이 `None`(브랜드관은 표시 없음)과 `"club"` 값(쿠폰함)이 다르면 같은 쿠폰이 둘로 보인다. 이것은 합집합의 기존 동작이고 구간이 둘로 남을 뿐 정보는 잃지 않는다. 대신 중복처럼 보이는지 T5로 본다.

## 3. 결정

1. `_tiers_foldable`에 배민 조합을 더한다: 두 레코드 모두 `platform == baemin`이고, 구역 하나가 `브랜드관 쿠폰`, 다른 하나가 `쿠폰함`으로 시작한다. 확정, 비제외, 비소진, 만료 가드 조건은 쿠팡이츠와 같다. 구역 이름은 상수(`BRAND_HALL_SECTION` 등)로 한 곳에 둔다.
2. "다른 출처" 둘의 쌍은 `latest_per_brand`의 `events`/`boxes` 풀을 일반화해(앱별 구역 판정 함수) 만든다. 풀은 키별로 **가장 늦은 행** 하나라서, 그날 두 출처를 다 봤을 때만 합쳐진다.
3. 합칠 때 대표값은 그대로, 구간만 합친다(`_fold_event_and_box`). 같은 날 조건은 기존대로: 두 풀 행과 결과 행이 모두 같은 날이어야 한다.
4. 합친 값은 원장에 쓰지 않는다. 읽을 때만 만든다.
5. 쿠팡이츠 동작은 한 글자도 바꾸지 않는다(기존 #56 시험이 그대로 통과).

### 남는 구멍 (결정이 못 닫는 것)

그날 한 출처만 읽은 회차는 합칠 짝이 없어 여전히 구간이 빠진다. 같은 날 안에서는 풀이 늦은 행을 기억하므로 앞선 회차의 다른 출처 행이 짝이 된다. **날을 넘긴 경우**(어제만 본 출처)는 합치지 않는다. 이것을 맞다고 보는지는 §9 질문 2.

## 4. 폭발 반경 (CHANGE-PROPAGATION)

표의 배민 줄은 125행(`banner_routine.brand_min_orders()`와 `previous_for`)뿐이다. 구간 병합 자체를 다룬 줄은 표에 없다. 코드로 쟀다.

| 자리 | 넣는가 | 이유 |
| --- | --- | --- |
| `store._tiers_foldable`, `latest_per_brand` | **넣는다** | 원인 |
| `tests/` 신규 | **넣는다** | §6 |
| 묶음 1 확실성(`certainty-cases.json`) | 확인 | 구간이 늘면 확정액과 최소주문 입력이 바뀐다. 대표 금액은 안 바뀐다. 구현자가 배민 구간 케이스를 읽어 PR 본문에 적는다 |
| 125행 배민 최소주문 출처(`brand_min_orders`) | 확인 | export.json의 tiers를 읽는지 구현자가 읽는다. 읽기만 한다 |
| API `Offer.preferredOver`/`withDetailFrom` | 안 넣음, 확인 | ADR-016은 병합 목록의 글자 일치를 요구한다. export.json은 키마다 한 항목이라 API는 합쳐진 항목을 받는다. `offer-cases.json`에 같은 날 금액이 다른 배민 두 레코드 케이스가 있는지 구현자가 읽고, 있으면 mono 이슈를 올린다(mono는 읽기용이라 이 PR에서 못 고친다) |
| `check_deploy.py` | 안 넣음 | 합친 구간이 들어오면 서버 구간이 보존돼 소실이 아니다. 가드는 풀지 않는다 |
| `--accept-loss`, `#80`의 "두 회차 연속" 통과 | 안 넣음 | #80을 닫는다. 가드 완화는 하지 않는다 |
| 요기요, 땡겨요 | 안 넣음 | 같은 문제의 증거가 없다. T6이 번지는지만 잰다 |
| `tiers` 모양, 공개 계약 | 안 넣음 | 키 추가 없음. 필요해지면 구현을 멈추고 알린다 |

## 5. 원장 append-only

원장을 읽기만 한다. 합집합은 `latest_per_brand`가 계산하는 값이다. 새 행이나 수정 행을 쓰지 않는다. 시험 고정물은 원장 행을 `tests/fixtures/`로 **복사한** 사본이다.

## 6. "없다 / 0 / 통과"의 양성 신호

| 자리 | 조용히 거짓이 되는 때 | 양성 신호 |
| --- | --- | --- |
| "구간이 합쳐졌다" | 이긴 행의 tiers가 None이라 합칠 게 없던 것과 합쳤다는 것이 같아 보임 | 시험이 지는 쪽 행의 구간 금액 집합을 먼저 단언하고, 내보낸 구간이 그 집합을 포함하는지 본다 |
| 가드 "막히지 않음" | 로컬 내보내기에 서버와 같은 키가 없으면 가드가 그 키를 건너뜀 | 도미노피자가 내보내기에 **존재**하고 구간이 `9000`, `5000`임을 먼저 단언한 뒤 소실 줄에 없음을 단언 |
| 합치지 않은 경우 | 조건을 어겨 안 합친 것과 후보가 없던 것이 같아 보임 | T3이 어긴 조건마다 "합치지 않음"을 따로 단언 |
| 구역 이름 판정 | 앱 문구가 바뀌면(`브랜드관 쿠폰`) 조용히 합치지 않음 | 이름만이 아니라 시험이 빌더가 실제로 찍는 구역 문자열을 상수와 대조한다. 빌더를 못 찾으면 구현을 멈추고 알린다 |

## 7. 테스트 (결론을 박는 곳)

파일 이름은 구현자가 정한다(제안: `tests/test_baemin_two_source_tiers.py`). 구현 전에 T1이 빨갛게 나오는지 먼저 확인한다.

- **T1 도미노피자 재현:** 같은 날 `브랜드관 쿠폰` 5,000과 쿠폰함(또는 이슈가 말한 다른 구역) 9,000을 넣는다. `latest_per_brand`의 `(baemin, 도미노피자)` 항목이 `amount == 9000`이고 구간에 9,000과 5,000이 둘 다 있다. 실제 구역 이름은 원장 복사 고정물로 쓴다.
- **T1b 순서 무관:** 같은 행을 모든 순열로 넣어도 결과 같음.
- **T2 자담치킨 모양:** 3,000원 구간이 쿠폰함에서만 보이는 날에도 브랜드관 행과 합쳐져 구간이 유지됨.
- **T3 합치지 않는 경우 (조건마다 하나):** 다른 날 / 다른 앱 / 다른 구역 조합(브랜드관과 위클리 등) / `excluded` / `sold_out` / `needs_review` / 만료된 구간. 각각 이긴 쪽 원래 구간 그대로.
- **T4 쿠팡이츠 불변:** 기존 `tests/test_same_day_other_source.py`와 #56 시험이 그대로 통과.
- **T5 중복 점검:** membership이 `None`인 브랜드관 5,000과 `club` 5,000 쿠폰함이 만나면 구간이 어떻게 나오는지 단언하고 PR 본문에 적는다.
- **T6 영향 측정:** 전체 원장을 옛 코드와 새 코드로 `latest_per_brand`에 넣어 내용이 달라진 항목을 표로 PR 본문에 싣는다. 배민 외 앱이 하나라도 달라지면 실패. 배민 항목은 구간이 맞는지 사람이 본다. 도미노피자와 자담치킨이 표에 있어야 한다.
- **T7 가드 연결:** T1 결과를 `build_export`에 넣고 서버에 `[9000, 5000]`이 있다고 두어 `check_deploy.classify_detail`의 소실 줄에 도미노피자가 없음(존재 단언 먼저).

## 8. 끝 조건

- T1~T7 통과, T1은 옛 코드에서 실패.
- 내보내기 미리보기에서 도미노피자와 자담치킨이 가드에 막히지 않음. 폰과 서버 없이 T7로 대신하고 출력을 PR 본문에 붙인다.
- 순수 export 변경이라 `collect_trial.ps1` 실수집 시험은 필요 없다.
- 변경 전파표의 같은 묶음 자리를 PR 본문에 "넣음 / 안 넣음 + 이유"로 적는다.
- 이 PR이 병합되면 #80을 닫는다.

## 9. 사용자에게 물을 것

1. 배민에서 같은 날 브랜드관 구간과 쿠폰함 구간은 모두 "한 오퍼의 구간"으로 봐도 되는가. **이 설계는 그렇다고 가정했다(미확인).** 아니면 합치는 구역 쌍을 더 좁힌다. T6이 가른다.
2. 날을 넘겨 한 출처만 읽은 날은 구간이 빠져도 되는가. 아니라면 "어제 본 출처 구간을 만료일 전까지 이월"이 필요하고, 그건 별도 설계(만료일 없는 배민 구간의 수명 규칙)가 먼저다.
3. 구간이 정말 끝난 쿠폰(만료일을 모르는 배민 구간)이 합집합 때문에 남는 위험을 받아들이는가. 지금은 "다시 보인 구간만" 합치므로 한 번도 안 보인 구간은 생기지 않는다.

## 10. 하지 않는 것

1. 원장 행의 수정, 삭제, 새 행 쓰기.
2. 업로드 가드 완화, `--accept-loss` 변경, "두 회차 연속 없음 통과"(#80) 도입.
3. 쿠팡이츠 동작 변경, 요기요와 땡겨요 확대.
4. `tiers` 모양과 공개 계약 변경, mono 수정.

## 11. 범위 점검

한 PR에서 리뷰 가능하다: `store.py` 조건 하나와 풀 일반화, 시험 한 파일, 영향 측정 표. 영역은 `export`.
