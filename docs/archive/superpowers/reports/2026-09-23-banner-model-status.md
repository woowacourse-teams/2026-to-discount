## 검토가 잡은 것 중 운영에 영향을 줬을 것

여덟 건이다. 전부 테스트는 초록인 상태에서 나왔다.

**자사 배너가 최고 할인이 됐다.** `platform: own`에 정액이 있으면 확실성이 `EXACT`라
정렬 기여액으로 잡히고 최고 배지가 붙었다. 적립은 더 나빴다. `Offer.from`이 `kind`를
`DISCOUNT`로 박아서 백억커피 네이버페이 적립이 확정 3,000원 할인으로 섰다. 배달앱에서
받을 수 없는 값으로 그 브랜드가 다른 브랜드보다 위에 선다.

**마지막 날 59초가 잘렸다.** 날짜를 시각으로 옮기며 `23:59`로 채웠는데 옛 날짜 비교는
그날 23:59:59까지 살아 있었다. 애매함을 없애려다 더 작은 애매함을 만들었다.

**묶음 대표가 우선순위가 아니라 id로 뽑혔다.** 카드의 금액, 링크, 최소주문, 색을 대는
대표가 id 문자열 순서로 정해졌다. 픽스처에서 두 순서가 우연히 같아 테스트가 못 잡았다.

**`soldOut`을 `untilSoldOut`으로 옮기면 뜻이 뒤집힌다.** 앞은 "이미 소진됨", 뒤는 "소진될
때까지 유효"다. 처갓집양념치킨 배너가 소진 표시를 잃고 살아 있는 쿠폰으로 다시 뜰
뻔했다.

**일괄 변환이 화면 문구를 통째로 바꿨을 것이다.** 변환한 파일을 실제 API에 통과시켜
글자를 맞대니 123행 중 네 칸이 전부 같은 배너가 0건이었다.

**콘솔이 새 모양을 아예 못 만들었다.** `amount`를 textarea로 둬서 `{won: 8000}`이 문자열로
저장되고 화면에 그대로 가격으로 찍혔다. 일괄 변환을 접은 뒤라 콘솔이 유일한 입구인데
그 입구가 막혀 있었다.

**정상 배너가 발행 거부됐다.** `COPY_FIELDS`의 30자 상한이 구조 값에 걸려
`{"won": [1000, 8000], "random": true, "kind": "cashback"}`가 49자로 막혔다.

**값 없는 배너가 나갈 문이 셋이었다.** `won` 범위의 최댓값이 비었을 때, 금액 칸을 비웠을
때, 생성 시 금액을 안 적었을 때. 셋 다 조용히 통과해서 가격 없는 배너가 됐다.

## 실패하고 되돌린 것

**내 지시가 만든 회귀 셋.** 브랜드 가드를 고치며 원격의 알림 발송 기능을 서버에서
덮어썼다(체크섬으로 잡아 복구). 같은 가드를 고치며 낡은 소스 체크아웃을 가리켜 KFC와
굽네치킨&피자 배너를 막았다(도는 jar를 읽게 고침). 콘솔 스키마를 고치며 생성 시 금액
검사를 문구만 바꾸라고 했는데 구현자가 통째로 지워 금액 없는 배너가 생성 가능해졌다.

**기존 테스트의 픽스처를 고쳐 초록으로 만든 일 두 번.** Task 6의 `extra: 랜덤`과 Task 8의
보류 `최대`다. 둘 다 회귀 신호를 지운 것이라 되돌리고 새 테스트로 덮었다.

**규칙이 두 군데로 갈라지는 일 세 번.** 전부 Task 8 안에서다. 문자열 비교와 죽은 인자,
가드와 함수 본문, 가짜 인자로 검사 재사용. 셋 다 그 시점에는 안 틀리지만 나중에 한쪽만
고치면 조용히 어긋난다.

**한 번에 못 끝낸 검증.** Task 11에서 서버 파일을 안 썼다. 문구 대조가 일괄 변환을
접게 만들었고, 그게 이 작업에서 가장 값진 실패다.

## 고치면서 알게 된 것

**테스트가 초록인 것과 의도가 지켜지는 것은 다르다.** 여덟 건 전부 그랬다. 판정표가
30가지 중 8가지만 덮었고, 59초 오차를 재는 테스트가 없었고, 묶음 픽스처에서 두 순서가
우연히 같았다. 그래서 검토 규칙에 "구현을 상수 반환 스텁으로 바꾸면 이 테스트가
실패하나"를 매번 넣게 했다.

**규칙은 한 곳에만 적혀야 한다.** 웹과 API가 특정메뉴 쿠폰을 서로 다르게 다루고 있던 게
이 재설계의 출발점이었는데, 고치는 과정에서 같은 병을 세 번 새로 만들었다. 가짜 인자를
넘겨 남의 검사를 재사용하는 것도 같은 병이다.

**파이썬으로 다시 구현해 비교하면 아무것도 증명 못 한다.** 자기 코드가 자기 코드와 같다는
말일 뿐이다. 실제 API를 통과시켜 글자를 맞댄 것이 일괄 변환의 문제를 잡았다.

**숫자를 먼저 세면 계획이 바뀐다.** 배너 103장 중 95장이 만료였다. 일괄 변환은 사용자가
보는 것을 하나도 안 바꾸면서 문구가 어긋날 위험만 만든다. 세기 전에는 2단계가 이 계획의
핵심이라고 생각했다.

**권위 있는 사본이 무엇인지 매번 확인해야 한다.** 브랜드 카탈로그를 세 번 틀렸다. 오퍼
목록(`/api/brands`)을 봤다가, 낡은 소스 체크아웃을 봤다가, 도는 jar에 정착했다.

**구현자 보고를 근거로 쓰면 안 된다.** 검토자가 코드에서 다시 확인하게 하자 구현자가
스스로 주장을 철회하는 일이 나왔다("고쳤다"던 버그가 재현이 안 됐다). 보고와 코드가
어긋나는 것 자체를 지적으로 올리게 한 뒤로 이런 게 걸린다.

**검사는 양쪽으로 틀릴 수 있다.** 정당한 걸 거부하면 운영자가 코드 고칠 때까지 발행을
못 하고, 못 거부하면 깨진 배너가 그대로 나간다. Task 13의 검사 넷을 아카이브 103장과
라이브 104장에 전부 돌려보고 나서야 배포했다.

**확정 규칙을 한 파일로 모으니 반복이 줄었다.** 2026-09-23 09:08에 `RULES.md`를 만들고
모든 지시문이 그것을 먼저 읽게 한 뒤로, 같은 판정을 다시 설명할 일이 없어졌다. 지금
10개 절이고 실행 중에 두 번 늘었다.

## 남은 이슈

### 다음 작업이 반드시 처리할 것

- **Task 16, 17.** `web/src/filters.js`의 `comparable`과 `bestConfirmedAmount`에 자사와
  `kind` 축이 없다. 서버만 고쳐서는 최고 배지가 안 바뀐다. 이것이 ADR-016이 말하는
  양쪽이 함께 움직여야 하는 지점이고, 지금 절반만 움직인 상태다.
- **Task 17, 18.** 자사 정률 배너는 금액이 null이라 칩에 "금액 미확인"이 뜬다. 웹이
  정률을 그릴 수 있게 되면 없어진다.

  모양으로 계속 남기로 했다. 지울 수 있는 건 옛 모양을 쓰는 길뿐이고 읽는 길은 남아야
  한다. 작업을 다시 쪼개야 한다.

### 지연 처리한 사소 지적 9건

`fromQualifier`가 모르는 값을 조용히 `EXACT`로 떨어뜨리는 것, `BannerAmount`의 두 칸
목록 음수와 뒤집힌 조합에 테스트가 없는 것, `Banner.build()`가 `startsAt`과 `endsAt`을
둘 다 검사하지 않는 것, `BannerText.amount(null)`이 오버로드 사이에서 모호한 것, 문구
길이 상한을 `BannerText`가 안 막는 것, 옛 경로와 새 경로가 같은 문구를 내는지 견주는
테스트가 없는 것, 보관본 파일 이름과 채취 날짜가 다른 것, 보관본 README가 배너 수 차이의
이유를 안 적은 것, 변환기가 미지의 칸 이름을 안 찍는 것이다.

전부 최종 검토에서 다시 본다.

### 구조적으로 남은 것

- **`banners.yml`의 id 유일성이 코드에만 있다.** Task 13이 적용 시점 검사를 넣었지만
  파일 자체를 검증하는 것은 없다. 손으로 직접 파일을 고치면 안 걸린다.
- **`apply_edits`와 `apply_proposal`에 끝에서 끝까지 도는 테스트가 없다.** 순수 함수
  단위 테스트만 있어서 배선이 끊어져도 초록이다. Task 13 검토가 임시 파일 하나면
  된다고 했다.
- **콘솔 JS 테스트가 소스를 문자열로 뽑아 돌린다.** 진짜 동작을 태우기는 하는데 함수를
  화살표 문법으로 다시 쓰거나 서식만 바꿔도 깨진다. 빨갛게 깨지는 방향이라 배포를
  막지는 않는다.
