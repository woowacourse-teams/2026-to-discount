# API 부하 테스트 설계와 개선 전 측정 보고서

상태: 사용자 요청으로 개선 후 측정 보류. 개선 전 3회 완료, 개발 서버 임시 설정 원복 확인.
설계: [api-load-test.md](../design/api-load-test.md).

## 예상 트래픽과 목표의 근거

운영 Nginx 접근 로그의 최근 7일을 집계했다. 최초 관측은 2026-10-07 17:43:21 KST이며
API 경로의 모든 상태 코드와 OPTIONS를 포함한다. 별도 홍보나 출시 계획은 없다.

| 관측 항목 | 값 |
|---|---:|
| 전체 API 요청 | 35,496건 |
| 최대 1분 요청 | 93건, 평균 약 1.55 RPS |
| 최대 1초 요청 | 30건 |
| brands 정상 GET | 6,629건 |
| banners 정상 GET | 6,281건 |

- 예상 지속 부하 10 RPS: 관측 최대 분당 요청량에 약 6.5배 여유를 둔 실험값.
- 비교 부하 30 RPS: 관측한 순간 유입이 계속 이어지는 상황을 검증하기 위한 값.
- 30 RPS는 실제 지속 트래픽 예측값이 아니다. 전체 API 피크를 두 조회 경로에 집중시킨 조건이다.
- 운영과 개발 사양 차이가 크므로 동일 개발 환경의 개선 효과를 판단하며 운영 처리량으로 환산하지 않는다.

목표는 경로별 p95 300ms 이하, p99 1,000ms 이하, 실패율 0.1% 미만, 미발행 요청 0이다.
홈 조회의 초기 지연 예산과 실패 방지 기준으로 정한 제안값이며 기존 운영 SLO는 아니다.
개선 판정 기준은 병목 경로 p95 중앙값 20% 이상 감소 또는 실패 제거와 목표 충족이다.
다른 경로 p95 10% 초과 악화, 응답 내용 변경과 실패율 증가는 허용하지 않는다.

## 부하 시나리오와 도구

| 항목 | 조건 |
|---|---|
| 대상 | 개발 HTTPS의 GET /api/brands 및 GET /api/banners |
| 비율 | 50:50, iteration 한 번에 GET 한 건, RPS는 두 경로 합계 |
| 생성 방식 | k6 constant-arrival-rate, 응답 지연 중에도 목표 요청 도착률 유지 |
| 워밍업 | 2 RPS 2분, 비교 통계에서 제외 |
| 탐색 | 2, 10, 30, 60, 100 RPS, 단계별 최대 3분 |
| 전후 비교 | 30 RPS 5분씩 3회, 측정 사이 2분 회복 |
| 비교 VU | 사전 할당 60, 상한 200 |
| 타임아웃 | 요청당 5초, 실패 요청도 집계 |
| 관측 도구 | k6, Python 실행기, Actuator 및 Micrometer, Alloy 및 Grafana Cloud, JFR |

전체 요청 시간은 호출 직전부터 완료까지 `client_elapsed` Trend로 측정한다.
연결과 TLS 대기를 제외하는 `http_req_duration`과 구분한다.
HTTP 200과 기대 JSON 구조를 검사하며 이벤트 저장, 설문, 알림과 관리 요청은 제외한다.
JFR은 탐색 30 RPS에서 90초만 수집했고 반복 비교에서는 사용하지 않았다.

최근 30초 실패율 1% 이상 및 실패 5건 이상, p99 3초 초과 지속 60초,
가용 메모리 10% 미만 지속 30초 등을 중단 조건으로 설정했다.
미발행 요청, 감시 실패, JAR 및 데이터 변경, 서비스 재시작도 중단 또는 비교 무효 사유다.
생성기가 맥북에 있으므로 측정 중 잠자기에 들어가면 해당 회차는 무효로 처리해야 한다.
실행 절차는 [load-tests/README.md](../../api/load-tests/README.md)에 기록했다.

## 실험 환경

- 개발 전용 HTTPS API, brands 및 banners 50:50. 요청별 전체 지연을 k6 Trend로 측정.
- 생성기: 사용자 macOS arm64 컴퓨터, k6 2.3.0 및 Python 3.11.
- 서버: Linux arm64, 2 vCPU, 메모리 약 3.8GB, Java 21.
- JVM: Xms256m, Xmx1536m. 서비스 MemoryMax=2560M.
- 기준 코드: dev ae66ad3, 기준 JAR SHA-256 `5e6d16c385c9d684415e9451da5e1e565d4d7eee632f44740e1777ae5fca3fd0`.
- export 및 banners 파일은 매 15초 해시로 변경 감시. 실행 중 서비스 재시작도 감시.
- 운영 부하와 운영 배포는 하지 않았다.

## 탐색 결과

| 합계 RPS | brands p95 | banners p95 | 결과 |
|---|---:|---:|---|
| 2 | 108ms | 67ms | 3분 완료, 실패와 미발행 0 |
| 10 | 107ms | 66ms | 3분 완료, 실패와 미발행 0 |
| 30 | 108ms | 66ms | 3분 완료, 실패와 미발행 0 |
| 60 | 109ms | 70ms | 3분 완료, 실패와 미발행 0 |
| 100 | 비교 제외 | 비교 제외 | 연결 및 TLS 지연, 타임아웃, SSH 감시 실패로 중단 |

100 RPS는 약 23초 동안 완료 1,547건과 dropped_iterations 275건을 기록했다.
brands 실패율은 약 83.5%, banners는 약 84.7%이며 p95는 타임아웃 5초에 도달했다.
해당 구간에 Nginx가 받은 brands 및 banners 요청은 약 250건이고 완료 상태는 200이었다.
API MainPID는 유지됐고 NRestarts=0, 회복 후 API HTTP 200과 SSH 접근을 확인했다.
감시 실패 시 실행기가 k6를 종료했고 예정된 반복 측정 큐도 취소했다.

요청 다수가 Nginx에 도달하지 못하고 연결 및 TLS 단계 지연이 크므로
100 RPS를 API의 처리 한계나 코드 병목 증거로 해석하지 않는다.
네트워크 경로 또는 생성 환경의 정확한 원인은 미확정이다. 30 RPS의 유효 반복 측정으로 비교한다.

## 개선 후보의 근거

- 실제 brands 응답은 gzip 요청에도 Content-Encoding이 없으며 본문 153,967바이트다.
- 같은 본문의 gzip 계산 크기는 12,820바이트로 약 91.7% 작다. 이는 적용 전 계산값이다.
- 10 RPS에서 brands의 평균 HTTP 시간은 48.28ms, 본문 수신은 22.09ms로 약 46%다.
- 같은 실행의 banners 평균 본문 수신은 0.08ms다.
- 30 RPS JFR 실행 샘플은 263건이며 Jackson 직렬화 스택은 70건, 브랜드 비교 스택은 29건이다. 분류는 서로 배타적이지 않으며 요청 지연의 직접 비율로 해석하지 않는다.

병목 개선 대상은 압축되지 않은 큰 조회 JSON의 전송 비용이다. 도메인 비교 캐시는 추가하지 않는다.
본문 크기와 수신 시간에서 개선 여지를 확인했다. CPU 포화나 GC가 주요 병목이라는 증거는
확보하지 않았으며, 압축이 동일 부하의 p95를 유의미하게 낮추는지는 아직 검증하지 않았다.
API의 JSON 압축 협상을 활성화하고, gzip을 지원하지 않는 클라이언트의 원문 응답을 유지한다.
구현 위치는 [application.yml](../../api/src/main/resources/application.yml)이며
`server.compression`을 활성화하고 대상 application/json, 최소 크기 2KB로 설정했다.
전후 비교에서는 JAR을 교체하지 않고 구현 후보와 동일한 압축 환경변수 3개만 임시 적용한다.
측정 후 원래 개발 서버 설정으로 복원한다. 후보의 application.yml 설정은 이후 정상 배포 대상으로 남긴다.

## 회귀 검증

- 기존 설정에서는 새 gzip 통합 테스트 1건이 실패해 미적용을 검출했다.
- 압축 후보에서 gzip 협상, Unicode 원문 일치, identity 응답, 알려진 작은 응답의 압축 생략 3건 통과.
- 전체 API 테스트 431개와 ./gradlew test build 통과.
- 시간 파싱, 최근 실패 집계, 메모리 중단, 감시 실패 시 프로세스 종료 등 감시 테스트 8개 통과.
- 기존 Check API의 Gradle 테스트와 새 감시 테스트 실행 단계로 CI 회귀 검증을 연결했다. GitHub에서의 새 브랜치 CI 실행은 아직 미수행이다.

| 테스트 위치 | 검증 내용 | 로컬 결과 |
|---|---|---|
| [JsonCompressionIntegrationTest.java](../../api/src/test/java/com/discounttracker/web/JsonCompressionIntegrationTest.java) | 실제 HTTP 서버의 gzip 협상, Unicode 원문, identity 응답, 작은 본문 압축 생략 | 3개 통과 |
| [test_guard.py](../../api/load-tests/test_guard.py) | 집계 및 중단 조건, 감시 실패 시 생성기 종료 | 8개 통과 |

실행 명령과 실제 결과:

정확성 회귀를 CI에 연결했으며 환경 의존적인 부하 수치는 일반 CI 합격 조건에 넣지 않았다.

## 전후 비교

30 RPS로 5분씩 개선 전 3회 측정 완료. 모든 회차의 실패율과 dropped_iterations는 0이다.

| 회차 | brands p95 / p99 | banners p95 / p99 |
|---|---:|---:|
| 1 | 107 / 115ms | 63 / 80ms |
| 2 | 107 / 116ms | 64.05 / 81ms |
| 3 | 107 / 113ms | 64 / 81ms |

기준 측정의 서버 관측 구간은 2026-10-14 18:37~18:56 KST다.
각 회차의 요청 수는 9,001건, 9,001건, 9,000건으로 총 27,002건이다.
실제 요청률은 모두 약 30 RPS였고 brands p50은 39ms, banners p50은 10ms였다.
brands p95 중앙값은 107ms, 범위 107~107ms이며 banners 중앙값은 64ms, 범위 63~64.05ms다.
회차별 k6 수신량은 약 697.6~697.7MB이며 본문 외 전송량도 포함한다.
가용 메모리 비율의 관측 최솟값은 72.0%였다.
모든 회차가 제안 목표를 충족했지만 이 결과만으로 포화 병목이 확인됐다는 뜻은 아니다.

기준 측정 전후 JAR 및 데이터 해시, 서비스 PID, 재시작 횟수, 임시 설정이 동일했다.
후보 적용 확인에서 실제 본문은 153,967바이트에서 13,390바이트로 약 91.3% 감소했고 JSON 원문은 동일했다.
개선 후 워밍업을 완료하고 첫 회차 도중 사용자가 측정을 미뤄달라고 요청해 실행기를 중단했다.
해당 회차는 무효이며 개선 효과 비교에 사용하지 않는다. 종료 코드 105와 KeyboardInterrupt를 기록했다.
이후 임시 systemd 설정을 제거했고 개발 서비스 active, API 및 Actuator 지표 HTTP 200을 확인했다.
실행 중인 k6와 비교 실행기가 없는 것도 확인했다. 개선 효과는 아직 확정하지 않는다.

| 항목 | 개선 전 | 개선 후 | 확인 조건 |
|---|---:|---:|---|
| 실제 brands 본문 크기 | 153,967바이트 | 13,390바이트 | 같은 JAR 및 데이터, 로컬 조회에서 압축 설정 전후 확인 |
| 응답 내용 | 기준 JSON | 동일 JSON | 압축 해제 후 내용 및 원문 해시 확인 |
| brands p95 중앙값 | 107ms | 미측정 | 30 RPS 5분 3회 비교는 개선 후 미완료 |
| banners p95 중앙값 | 64ms | 미측정 | 동일 조건 비교는 개선 후 미완료 |
| 실패 및 미발행 | 0 | 미확정 | 중단된 후보 회차는 비교에서 제외 |

본문 크기 약 91.3% 감소는 적용 점검 결과이며 부하 상태의 지연 개선율이 아니다.
동일 조건 전후 성능 비교와 GitHub CI 실제 실행이 남아 있어 전체 태스크는 아직 완료로 판단하지 않는다.

원시 자료는 `api/load-tests/results/20261014/`에 보존했다. 큰 NDJSON은 Git 추적에서 제외한다.
단계별 summary, NDJSON, 서버 및 생성기 스냅샷, 압축 적용 결과와 JFR 샘플을 포함한다.

### SSH 대체 경로 사전 점검

- [PR #77](https://github.com/woowacourse-teams/2026-to-discount/pull/77)을 dev에 병합했다.
  API, 구조 검사 및 시크릿 검사가 통과했고 개발 배포도 성공했다.
- [개발 배포](https://github.com/woowacourse-teams/2026-to-discount/actions/runs/38558761081) 기준 SHA는
  `c6466207eefe5711143a5e7e203d1a2040f84a67`이다. 원래 기준 측정 이후 배포가 바뀌었다.
- [러너 점검](https://github.com/woowacourse-teams/2026-to-discount/actions/runs/38558790514)에서
  개발 서비스 active, 지표 HTTP 200, brands 본문 153,967바이트 및 원문 해시 일치를 확인했다.
- Content-Encoding은 없었고 Python sudo 권한은 거부됐다. 러너는 임시 압축 설정을 적용 및 원복할 수 없다.
  점검은 실패로 종료했으며 부하 발행이나 압축 설정 변경은 수행하지 않았다.
- 개선 후 측정을 위해서는 관리자 설치 경로를 마련하거나 개선 코드를 정상 개발 배포로 적용해야 한다.
  보호 환경은 dev만 허용하고 그 보호 규칙은 유지했다.
- 사용자는 개선 후만 GitHub 러너에서 측정하도록 요청했다. 이를 실행하더라도 기존 맥북 결과와는
  생성기 및 네트워크가 다르므로 차이를 압축의 인과 효과로 확정하지 않는다.

재개 시 데이터 및 JAR 해시, 영업 날짜, 생성기와 네트워크 조건을 확인한다.
조건이 같으면 개선 후 워밍업과 3회 측정을 처음부터 수행하고 달라졌으면 기준도 다시 측정한다.
이후 경로별 지연, 실패, 전송량, CPU, heap 및 GC를 비교한다. 후보는 비교 후 다시 원복한다.
