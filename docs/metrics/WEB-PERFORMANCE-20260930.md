# 검색 노출과 첫 화면 속도 개선 기록 (2026-09-30)

검색 결과 문구를 다듬고, 첫 화면 속도를 측정하며 고쳤다. 홈(`/`)은 성능 점수가 43에서 50으로, 첫 화면의 가장 큰 요소가 뜨는 시간이 7.3초에서 5.6초로 좋아졌다(운영, 모바일). 그 뒤 여러 실험은 효과가 없어 되돌렸다. 브랜드 페이지에서 찾은 화면 흔들림 문제는 방문 비중이 작아 우선순위를 낮춘다.

## 전제

- **이 서비스는 사실상 한 페이지짜리다.** 최근 30일 방문자 4,823명 중 4,735명(98.2%)이 홈(`/`)으로 들어왔고, 브랜드 페이지(`/brand/<이름>`)는 88명(1.8%)이다(PostHog `$pageview`, 봇 제외, 2026-10-01 조회). 개선의 기준은 홈이다.
- **검색 순위에 들어가는 속도 값은 실제 방문자의 기록이다.** 구글은 크롬 사용자들이 실제로 겪은 값을 28일 모아, 방문의 75% 지점 값을 본다(Core Web Vitals, 구글의 웹 품질 지표). 이 문서의 측정 도구(Lighthouse, 구글이 만든 웹 성능 점검 도구) 점수는 실험실 값이라 순위에 직접 들어가지 않는다. 개선 방향을 잡는 데 쓴다.

## 용어

| 용어 | 뜻 |
|---|---|
| LCP(최대 콘텐츠 표시 시간) | 첫 화면에서 가장 큰 글자나 그림이 뜨기까지 걸린 시간. 좋음 기준 2.5초 이하 |
| TBT(총 차단 시간) | 페이지가 뜨는 동안 브라우저가 계산에 묶여 터치나 클릭에 반응하지 못한 시간의 합 |
| CLS(누적 레이아웃 이동) | 이미 보이던 요소가 예고 없이 자리를 옮긴 정도. 읽던 글이 갑자기 아래로 내려가는 현상을 수치로 잰 것. 좋음 기준 0.1 이하 |
| 사전 렌더링 | 사이트를 빌드할 때 검색엔진이 읽을 HTML을 미리 만들어 두는 방식. 지금은 브랜드 목록 요약을 넣어 둔다 |
| 교체 렌더링 | 브라우저가 JS를 받으면 사전 렌더링 HTML을 버리고, React가 화면을 처음부터 다시 그리는 방식. 지금 이 서비스가 쓴다 |
| SSR(서버 사이드 렌더링) | 빌드 때(또는 서버에서) React로 **실제 앱 화면**을 HTML로 만들어 보내는 방식. 브라우저는 받은 화면을 그대로 보여 준다 |
| 하이드레이션 | SSR로 받은 화면을 버리지 않고, 그 위에 클릭 같은 동작만 연결하는 단계. 다시 그리지 않으므로 요소가 자리를 옮기지 않는다 |
| 로딩 자리표시 | 데이터가 오기 전에 카드 모양만 회색으로 그려 두는 빈 틀. 옆으로 빛이 지나가는 애니메이션이 있다 |
| 경쟁 상태 | 두 작업의 순서가 실행할 때마다 달라져 결과가 갈리는 상황 |

## 배경

- 파비콘과 검색 결과 문구가 오래된 상태로 노출됐다. 서비스 이름이 제목("배달앱 할인모음")과 공유 미리보기("오늘의할인")에서 달랐다.
- 이전에 JS만으로 화면을 그리던 방식은 HTML 본문이 비어 검색 노출에서 밀렸다. 그래서 사전 렌더링과 교체 렌더링으로 바꾸고, 카드를 12장씩 나눠 그리는 방식을 넣었다.

## 문제

1. 검색 결과 문구가 서비스 이름, 날짜, 원본 브랜드명("토핑몬스터피자TMPPIZZA") 나열로 어지러웠다.
2. 홈의 첫 화면이 느렸다. 운영 모바일 측정으로 성능 43, LCP 7.3초, TBT 2.2초였다.
3. 측정하면서 드러난 문제가 둘 있었다.
   - 측정 방문이 사람 방문으로 분석 지표에 찍혔다.
   - 브랜드 페이지에서 간헐적으로 큰 레이아웃 이동(0.8)이 났다.

## 가설과 실행

### 1. 검색 결과 문구

- **가설:** 제목과 설명에 사람들이 실제로 검색하는 말(배민 쿠폰, 최고 할인, 선착순, 멤버십)을 넣으면 검색 유입이 는다.
- **실행:**
  - 제목을 "배달앱 할인모음 - 배민, 쿠팡이츠, 요기요, 땡겨요 최고 할인 쿠폰 비교"로 바꿨다.
  - 설명에서 날짜와 원본 브랜드명을 빼고 검색어를 넣었다.
  - 브랜드 페이지 제목에는 그 브랜드가 실제로 있는 앱만 적었다.
  - 커밋은 `73b9fcc`, `38c62d0`, `57d567b`, `af53d0a`다.
  - "실시간"은 넣지 않았다. 수집이 하루 세 번이라 사실과 다르다.
- **관측:** 효과는 검색엔진이 다시 수집한 뒤 서치콘솔 실적에서 본다. 아직 관측 전이다.

### 2. 홈 첫 화면 속도

측정 도구가 짚은 원인은 다섯 가지였다.
- 이미 그린 카드를 12장이 더해질 때마다 전부 다시 그렸다.
- GA4가 첫 화면보다 먼저 시작됐다.
- 분석 도구 PostHog의 SDK(85KB)를 첫 화면 동안 받았다.
- LCP 요소인 맨 위 배너는 JS가 다 돈 뒤에야 요청됐다.
- 배너가 늦게 끼어들며 아래 목록을 밀어냈다.

| 실행 | 커밋 | 결과 |
|---|---|---|
| 카드를 다시 그리지 않게 고정(React memo), GA4를 로드 뒤로, 화면 밖 카드는 그리기를 미룸 | `dbafc78` | 유지 |
| 배너를 JS보다 먼저 요청, 배너가 오기 전 자리를 잡아 둠 | `469dfab` | 유지 |
| 화면 밖 카드 그리기 미룸을 7번째 카드부터만 적용 | `ea202f9` | 앞 커밋이 첫 화면 카드까지 미뤄 브랜드 페이지 CLS를 0.14에서 0.45로 올렸다. 바로 고쳤다 |
| PostHog SDK를 로드 뒤 한가할 때 받음, 시트와 대화상자는 필요할 때 받음 | `fb7df3e` | 유지 |

운영 측정(모바일, 3회 중앙값):

| 시점 | 성능 | LCP | TBT | CLS |
|---|---|---|---|---|
| 개선 전 | 43 | 7.3초 | 2,239ms | 0.12 |
| 개선 후 | 50 | 5.6초 | 1,919ms | 0.04 |

### 3. 효과가 없어 되돌린 실험

모두 10회 측정의 중앙값과 사분위 범위(가운데 50%가 퍼진 폭)로 판정했다. 범위가 겹치면 효과가 없다고 봤다.

| 실험 | 결과 |
|---|---|
| 카드 채우기를 페이지 로드 뒤로 미룸(`6c7f2ba`) | 홈 LCP가 5.6초에서 7.0초로 늦어졌다. `d5a7000`으로 되돌렸다 |
| 카드를 24장씩, 간격 없이, 400ms 간격으로 채움 | 지금 방식(12장씩, 150ms)과 차이가 없었다 |
| 카드를 한 번에 전부 그림 | TBT가 1,158ms에서 1,812ms로 확실히 나빠졌다. 나눠 그리는 기존 판단이 맞았다 |
| 사전 렌더링 목록과 카드에 배치 계산 격리 CSS 적용 | TBT가 두 배로 늘었다 |
| "최고" 배지 테두리의 색이 계속 도는 애니메이션을 멈추거나 두 번만 돌게 함 | 홈과 브랜드 모두 차이가 없었다 |
| 로딩 자리표시의 빛 지나가는 애니메이션을 끔 | 차이가 없었다 |

- **이전 기록과의 관계:** 카드를 스크롤할 때 그리는 방식은 2026-09-01에 세 번 실패한 기록이 있다(`web/src/App.jsx` 주석). 그래서 이번에는 시도하지 않았다.
- **추적에서 본 것:** 성능 추적(trace, 브라우저가 한 일을 시간순으로 적은 기록)에서 계속 도는 애니메이션이 화면 다시 그리기를 2천 번 넘게 일으켰다. 그래도 점수에는 영향이 없었다.

### 4. 측정 방문이 지표에 섞인 문제

- **무엇이:**
  - 2026-09-30 17~20시 측정 약 80회가 PostHog와 GA4에 사람 방문으로 찍혔다.
  - 이 시간대 방문자가 평소의 세 배로 늘었다.
  - `?dev=1` 표시는 우리 서버가 PostHog로 넘기는 것만 막았다. GA4와 Vercel Analytics는 브라우저가 직접 보내서 걸러지지 않았다.
- **조치:**
  - 서버가 `Chrome-Lighthouse`, `HeadlessChrome` 사용자 에이전트를 봇으로 적게 했다(`38615a4`).
  - 개발 표시나 측정 도구면 GA4와 Vercel Analytics를 시작하지 않게 했다(`d321d34`).
  - PostHog 그래프에 그 구간을 표시했다(`7dd7cea`).
- **남은 것:** 그날 기록을 분석에서 뺄 제외 코호트는 PostHog 키의 쓰기 권한이 없어 아직 못 만들었다.

### 5. 브랜드 페이지의 간헐적 레이아웃 이동

- **관측:**
  - 같은 코드를 운영 주소와 프리뷰 주소에서 각 10회 쟀다.
  - 세 버전 모두 20~40%의 실행에서 CLS가 0.78~0.81로 튀었다. 나머지는 0.03~0.04였다.
  - 이동한 요소는 매번 본문 전체(`#root > main`)였다.
  - 홈은 10회 모두 0.03이었다.
- **원인(경쟁 상태):**
  - 브랜드 페이지를 열면 사전 렌더링 HTML이 먼저 도착한다.
  - 브라우저가 그 HTML을 **먼저 화면에 그린 뒤** React가 교체하면, 본문 전체가 자리를 옮겨 큰 레이아웃 이동으로 잡힌다.
  - React가 **그리기 전에** 교체하면 화면에 한 번만 그려져 이동이 없다.
  - 둘 중 무엇이 먼저 일어나는지는 그때의 네트워크와 CPU 상태로 정해져서, 실행마다 결과가 갈린다.
  - 3회 측정만으로는 드러나지 않았다. 10회에서 실행별 값을 보고서야 확인했다.
- **SSR이 이 문제를 없애는 이유:**
  - SSR은 사전 렌더링 HTML 자리에 실제 앱 화면을 넣는다.
  - 브라우저는 그 화면을 버리지 않고 하이드레이션으로 동작만 붙인다. 교체가 없으니 순서가 어떻든 요소가 자리를 옮기지 않는다.
- **판단:** 브랜드 페이지 방문은 전체의 1.8%다. 홈에서는 이 현상이 관측되지 않았다. 그래서 이 문제만으로 SSR을 하지는 않는다.

## 후속 (2026-10-01~10-02)

이 문서 뒤에 홈을 서버 렌더링(SSR)으로 바꿨고, 반응성과 검색 노출을 더 고쳤다. 렌더링 결정과 성능 수치의 자세한 근거는 [web/ADR-003](../../web/docs/decisions/ADR-003-home-ssr.md)에 있다.

### 측정 방법을 바꿨다

- Lighthouse 기본값인 시뮬레이션(느린 4G와 CPU 4배 감속을 계산으로 가정)은 글꼴 전송을 첫 화면 대기로 계산해 최대 콘텐츠 표시 시간(LCP)을 2~3배 부풀렸다. 같은 실행의 실제 관측값은 1.3초 안팎이었다.
- 그래서 판정은 실제 속도 제한(`--throttling-method=devtools`, 네트워크와 CPU를 실제로 늦춤)으로 하고, 번갈아 12회 잰 뒤 같은 회차끼리 짝지어 개선 회차 수를 센다.
- 프리뷰는 우회 헤더 대신 쿠키 방식(`x-vercel-set-bypass-cookie`)으로 연다. 헤더 방식은 jsdelivr 글꼴 요청까지 깨뜨려 글꼴 없는 조건으로 쟀다.

## 학습

- **측정 방식:** 시뮬레이션 값은 글꼴처럼 큰 외부 파일을 첫 화면 대기로 계산해 부풀린다. 판정은 실제 속도 제한으로 하고, 시뮬레이션 값은 참고로만 쓴다.
- **측정 횟수:** 3회 중앙값은 우연을 효과로 읽게 한다. 10회 이상 재고, 실행별 값과 사분위 범위를 같이 본다.
- **측정 시간대:** 같은 코드도 오후와 밤의 LCP가 5.6초와 3.5초로 달랐다. 비교할 버전은 같은 시간대에 번갈아 잰다.
- **로컬 측정의 한계:** 로컬 서버는 압축이 없고 느려 레이아웃 이동 값이 운영과 크게 달랐고, 회귀 하나를 놓쳤다. 레이아웃 이동은 프리뷰나 운영에서만 판정한다.
- **측정의 부작용:** 측정도 방문이다. 측정 전에 분석 도구 전부에서 빠지는지 확인한다.
- **기록 먼저:** 과거에 실패한 방식(스크롤 기반 카드 로딩)은 코드 주석에 남아 있었다. 실험 전에 기록을 읽어 같은 길을 되풀이하지 않는다.
