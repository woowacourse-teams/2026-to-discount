# SEO 실행 목록 — 무엇을 어디서 어떻게 고치나

2026-08-28 라이브(`beggars-five.vercel.app`)를 8개 항목으로 감사한 결과를
**작업 단위로** 옮긴 것이다. 진단은 요약만 두고, 각 항목은 고칠 파일과
검증 명령까지 적는다.

이 프로젝트에는 지키기로 한 원칙이 있고, 그 원칙과 부딪히는 권고는
**반려**로 따로 모았다([§반려한 권고](#반려한-권고)). SEO 점수를 올리자고
"모르는 값을 지어내지 않는다"를 깨지 않는다.

**SEO를 처음 보는 사람은 [5분 요약](#5분-요약)과 [용어 사전](#용어-사전)을
먼저 읽으면 나머지가 읽힌다.** 각 작업 항목은 "왜 이게 문제인가"(설명) →
근거 수치 → 고칠 파일 → 검증 명령 순으로 되어 있으니, 설명만 훑고
넘어가도 무엇을 하는지는 잡힌다.

## 5분 요약

### 검색엔진은 우리 사이트를 어떻게 보나

구글 같은 검색엔진은 사람이 아니라 **프로그램**을 보낸다. 이 프로그램을
크롤러라고 부른다. 크롤러가 페이지 주소로 요청을 보내면 서버는 HTML을
돌려주는데, 크롤러는 **일단 그 HTML만 읽는다.** 우리 사이트처럼 React로
만든 페이지는 브라우저에서 자바스크립트가 실행되어야 화면이 완성되는데,
크롤러는 그 실행을 나중에 하거나 아예 안 하기도 한다. 그래서 **자바스크립트가
돌기 전의 HTML에 무엇이 들어 있느냐**가 검색에서는 거의 전부다.

이 프로젝트는 그걸 이미 알고 대비해 뒀다. 빌드가 끝난 뒤
`web/scripts/prerender.mjs`가 완성된 HTML에 검색엔진용 본문을 따로 끼워
넣는다. 그래서 자바스크립트 없이 주소만 열어도 브랜드 이름과 할인 금액이
텍스트로 다 보인다. 이 부분은 잘 되어 있다.

문제는 그다음이다. 크롤러는 페이지를 **링크를 타고 다니며** 발견한다.
A 페이지에 B 페이지로 가는 링크가 있으면 B를 찾아가고, 그러면서 "A가 B를
가리킬 만큼 B가 쓸모 있다"는 신호도 같이 전달된다. 반대로 아무도 링크하지
않는 페이지는 **존재해도 없는 것과 크게 다르지 않다.** 주소를 직접 알려주면
(사이트맵) 찾아가기는 하지만, 그 페이지가 사이트 안에서 얼마나 중요한지
알 방법이 없어 뒤로 밀린다.

그리고 검색엔진은 페이지를 찾은 뒤 "이걸 검색 결과에 넣을 가치가 있나"를
따로 판단한다. 내용이 실한지, 만든 사람이 믿을 만한지, 화면이 빨리 뜨는지가
그 판단에 들어간다. 요즘은 AI 검색(구글 AI Overviews, ChatGPT 검색,
Perplexity)이 답변에 인용할 출처를 고르는 과정도 여기 얹힌다.

### 지금 우리 상태 한 줄

**브랜드 페이지 110장을 잘 만들어 놨는데, 홈에서 그리로 가는 링크가 하나도
없어서 크롤러가 따라갈 길이 없다.**

숫자로 보면 이렇다.

```
$ curl -s https://beggars-five.vercel.app/ | grep -c '<a '
0
```

홈 HTML에 링크(`<a>` 태그)가 **0개**다. 같은 HTML 안에 108개 브랜드 이름과
할인 금액이 텍스트로 전부 들어 있는데도 그렇다. 내용이 없는 게 아니라
**연결이 없다.**

이게 이 문서의 §1이고, 여덟 개 감사 중 **다섯 개가 각각 독립적으로**
1순위로 꼽은 항목이다. 공수는 가장 낮다.

### 점수

각 점수가 무엇을 재는지 한 줄씩 붙였다. 100점 만점이고 절대 기준은 아니다 —
"어디가 약한지"를 비교하는 용도다.

| 항목 | 점수 | 무엇을 재나 | 한 줄 |
|---|---|---|---|
| 기술 | 78 | 크롤러가 페이지를 문제없이 읽고 색인할 수 있는가 | 사이트맵·robots·canonical·프리렌더 색인성 모두 정상 |
| 콘텐츠 | 58 | 내용이 실하고 만든 주체가 믿을 만한가 | 신뢰 신호는 강한데 권위 신호가 거의 없다 |
| GEO(AI 검색) | 46 | AI 검색이 답변에 우리를 인용할 근거가 있는가 | 접근은 되는데 인용될 근거가 없다 |
| 성능 | 36 | 화면이 얼마나 빨리 뜨고 조작에 반응하는가 | LCP 18.8초 |
| SXO(홈) | 33 | 검색으로 들어온 사람이 원하는 걸 찾아가는가 | 홈이 링크 그래프의 막다른 길이다 |
| 사이트맵 | 조건부 통과 | 사이트맵 파일이 규격에 맞고 쓸 만한가 | 형식은 정상, 규모 확인이 형식상 필요 |

성능 36점이 가장 낮지만 **1순위는 §1(내부 링크)이다.** 성능은 이미 발견된
사람들의 체감 문제이고, 링크는 **발견 자체가 안 되는** 문제라서 앞선다.

## 용어 사전

이 문서에 실제로 나오는 것만 모았다. 각 항목마다 우리 프로젝트에서 어디에
해당하는지 붙였다.

### 크롤링과 색인

**크롤러(봇)** — 검색엔진이 웹페이지를 수집하려고 보내는 프로그램. 구글은
Googlebot, AI 쪽은 GPTBot·ClaudeBot·PerplexityBot 등이 있다.
*우리 프로젝트*: `robots.txt`가 `Allow: /`라 전부 허용 중이다.

**색인(인덱싱)** — 크롤러가 가져온 페이지를 검색엔진이 자기 데이터베이스에
넣는 것. 색인되지 않으면 검색 결과에 절대 안 나온다. 크롤링됐다고 반드시
색인되는 건 아니다 — 내용이 부실하면 수집만 하고 버린다.

**크롤 예산(crawl budget)** — 검색엔진이 한 사이트에 쓰는 크롤링 자원의
총량. 무한하지 않다. 중요하지 않아 보이는 페이지가 많으면 정작 중요한
페이지를 늦게 본다.
*우리 프로젝트*: 111개 URL이라 예산 자체가 문제 되는 규모는 아니다.

**내부 링크** — 같은 사이트 안의 페이지끼리 거는 링크. 크롤러가 페이지를
발견하는 주된 경로이자, "이 페이지가 중요하다"는 신호를 전달하는 통로다.
*우리 프로젝트*: 브랜드 상세 → 홈, 브랜드 상세 → 형제 브랜드는 있는데
**홈 → 브랜드 상세가 없다.** 이게 §1이다.

**앵커(`<a href>`)** — HTML에서 링크를 만드는 태그. 크롤러는 이 태그만
링크로 인식한다. 자바스크립트로 클릭 시 이동시키는 `<button>`은 링크로
안 본다.
*우리 프로젝트*: 오퍼 칩은 제대로 `<a href>`다. 문제는 프리렌더 블록의
브랜드 이름이 그냥 `<h3>` 안 평문이라는 것.

**사이트맵(sitemap.xml)** — 사이트에 있는 페이지 주소 목록을 XML로 적어 둔
파일. 링크로 발견하기 어려운 페이지를 검색엔진에 직접 알려주는 보조 수단이다.
링크를 대체하지는 못한다.
*우리 프로젝트*: `prerender.mjs`가 빌드 때 111개 URL(홈 1 + 브랜드 110)로
생성한다.

**robots.txt** — 크롤러에게 "어디를 봐도 되고 어디는 보지 마라"를 알려주는
파일. 사이트맵 위치도 여기 적는다.
*우리 프로젝트*: `prerender.mjs:303` 부근에서 생성하고, 전체 허용에
사이트맵 주소를 선언한다.

**canonical** — 같은 내용이 여러 주소로 접근될 때 "이게 대표 주소다"를
알려주는 태그. 중복 콘텐츠로 오해받는 걸 막는다.
*우리 프로젝트*: 홈·브랜드 상세 모두 자기 자신을 가리키게 잘 들어가 있다.

### 렌더링

**SSR / SSG** — SSR(Server-Side Rendering)은 요청이 올 때마다 서버가 HTML을
만들어 주는 것, SSG(Static Site Generation)는 빌드할 때 미리 HTML을 만들어
두는 것. 둘 다 크롤러가 자바스크립트 없이도 내용을 볼 수 있게 한다.
*우리 프로젝트*: 둘 다 안 쓴다. Vite에 프리렌더 기능이 없고, `variant.js`가
모듈을 불러오는 순간 `localStorage`를 읽어서 서버에서는 실행 자체가 안 된다.

**프리렌더** — 우리가 택한 절충안. 빌드가 끝난 뒤 스크립트가 완성된 HTML
파일에 검색엔진용 본문을 끼워 넣는다.
*우리 프로젝트*: `web/scripts/prerender.mjs`가 그 스크립트다.
`.seo` 클래스로 감싼 블록이 그것이고, `robots.txt`·`sitemap.xml`·
브랜드 상세 110장도 여기서 같이 만든다.

**하이드레이션(hydration)** — 미리 만들어 둔 HTML 위에 자바스크립트가
붙어서 실제로 동작하는 화면이 되는 과정.
*우리 프로젝트*: 하이드레이션되면 React가 `#root` 안을 자기 내용으로 덮으므로
프리렌더 블록은 사라진다. **그래서 프리렌더 블록을 고쳐도 실사용자 화면은
안 바뀐다** — 이게 §1의 위험이 낮은 이유다.

### 콘텐츠 평가

**씬 콘텐츠(thin content)** — 내용이 부실해서 검색 결과에 넣을 가치가 낮다고
판단되는 페이지. 단어 수만의 문제는 아니고 "여기서만 얻을 수 있는 게
있느냐"가 핵심이다.
*우리 프로젝트*: 표본 5장 중 3장이 앱 1개짜리라 본문이 100~150단어다.
다만 계근상 페이지처럼 구간표와 계산식까지 든 경우가 있어 단순히 얇다고
보기는 어렵다. §7이 이 문제를 다룬다.

**도어웨이 페이지(doorway page)** — 검색 유입만 노리고 기계적으로 찍어낸,
사실상 같은 내용의 페이지들. 구글이 명시적으로 제재하는 유형이다.
*우리 프로젝트*: 브랜드 110장이 자동 생성이라 형식상 의심 대상이지만,
각 페이지가 실제로 다른 데이터(브랜드·앱·금액·조건)를 담고 있어 실질은
다르다. 사이트맵 감사가 "조건부 통과"를 준 이유가 이것이다.

**E-E-A-T** — Experience(직접 경험), Expertise(전문성),
Authoritativeness(권위), Trustworthiness(신뢰). 구글이 콘텐츠 품질을
평가할 때 쓰는 네 축이다.
*우리 프로젝트*: Trustworthiness는 강하다(비영리·비제휴 고지, 확인일 표기,
"미확인"을 감추지 않음). Authoritativeness가 8/25로 가장 낮다 — 누가
만들었는지가 어디에도 없다. §8이 이걸 다룬다.

### AI 검색

**GEO(Generative Engine Optimization)** — AI가 답변을 생성할 때 우리
페이지를 출처로 인용하게 만드는 최적화. 기존 SEO가 "검색 결과에 노출"이라면
이건 "AI 답변에 인용"이 목표다.
*우리 프로젝트*: 46점. 크롤러 접근은 되는데 인용될 근거(누가 만들었나,
자기완결적인 문단이 있나)가 약하다.

**llms.txt** — AI 크롤러에게 사이트 성격과 데이터 갱신 주기를 알려주는
텍스트 파일. `robots.txt`의 AI 버전 비슷한 것인데, 차단이 아니라 설명이
목적이다. 아직 표준은 아니다.
*우리 프로젝트*: 없다(404). §6이 이걸 만든다.

**IndexNow** — 페이지가 바뀌었을 때 검색엔진에 "지금 바뀌었다"고 즉시
알리는 프로토콜. Bing·네이버·Yandex가 지원한다. 크롤러가 다시 올 때까지
기다리지 않아도 된다.
*우리 프로젝트*: 미구현. 데이터가 매일 바뀌는 사이트라 효과가 클 수 있다.
§10.

### 성능 — Core Web Vitals

구글이 사용자 체감 속도를 재려고 정한 세 가지 지표다. 검색 순위에도 쓰인다.

**LCP(Largest Contentful Paint)** — 화면에서 가장 큰 콘텐츠가 그려질 때까지
걸린 시간. **2.5초 이하가 "좋음"**, 4초 초과가 "나쁨".
*우리 프로젝트*: **18.8초.** 기준의 7배가 넘는다.

**INP(Interaction to Next Paint)** — 사용자가 뭔가를 누른 뒤 화면이 반응할
때까지 걸린 시간. 200ms 이하가 "좋음". (예전에 쓰던 FID를 대체했다.)
*우리 프로젝트*: 실험실에서는 직접 못 재서 TBT를 대리 지표로 썼다.
TBT가 4,952ms라 INP도 나쁠 것으로 본다.

**CLS(Cumulative Layout Shift)** — 페이지가 로딩되는 동안 요소가 갑자기
움직여서 사용자가 엉뚱한 걸 누르게 되는 정도. 0.1 이하가 "좋음".
*우리 프로젝트*: 0.09로 통과. 이건 문제없다.

**TBT(Total Blocking Time)** — 자바스크립트가 메인 스레드를 붙잡고 있어서
사용자 입력에 반응 못 하는 총 시간.
*우리 프로젝트*: 4,952ms. 긴 작업이 17개 있고 가장 긴 게 1.28초다.

**DOM 노드** — HTML 요소 하나하나. 많을수록 브라우저가 레이아웃을 계산하는
데 오래 걸린다. 1,500개 이하 권장.
*우리 프로젝트*: **5,633개.** 권장치의 3.7배. 브랜드 카드를 전부 한꺼번에
그려서다.

### 기타

**JSON-LD / 구조화 데이터** — 페이지 내용을 기계가 이해할 수 있는 형식으로
따로 적어 두는 것. "이 페이지는 조직 소개다", "이건 웹사이트다" 같은 걸
명시한다. 검색 결과에 별점·가격 같은 게 붙는 리치 결과의 근거가 된다.
*우리 프로젝트*: **0건.** §3에서 넣는데, 넣으면 안 되는 타입이 있다.

**og:image** — 카카오톡·슬랙 등에 링크를 붙여넣었을 때 뜨는 미리보기
이미지를 지정하는 태그.
*우리 프로젝트*: 없다. 공유해도 썸네일이 안 뜬다. §5.

## 이 프로젝트가 지키는 제약

작업 항목을 읽기 전에 알아야 할 것들이다. 여기 어긋나는 개선안은 아무리
SEO 점수가 올라도 하지 않는다.

**"모르는 값을 지어내지 않는다"** — 이 프로젝트의 최상위 원칙이다. 값을
못 읽었으면 화면에 "미확인"이라고 쓴다. 비어 있다는 사실 자체가 사용자에게
필요한 정보라고 보기 때문이다. *SEO에서 걸리는 지점*: "브랜드 페이지가
얇으니 설명을 늘려라"는 흔한 권고인데, 우리에게는 없는 할인을 서술로
채우라는 말이 되어 반려다. 대신 §7처럼 **없다는 사실을 명시**하는 방향으로
간다.

**ADR-014 — 상한만 정해진 쿠폰은 확정 금액으로 적지 않는다** — 쿠팡이츠
랜덤박스처럼 "최대 5,000원" 식으로만 알 수 있는 쿠폰이 있다. 그걸
5,000원이라고 적으면 사용자가 못 받을 금액을 약속하는 셈이다. *SEO에서
걸리는 지점*: §4가 이 원칙을 프리렌더 요약 문장에도 적용하는 작업이다.

**ADR-015 — 공개된 경로로만 수집하고, 비영리·비제휴임을 화면에 고지한다** —
로그인 없이 누구나 보는 화면만 수집하고, 우리가 각 배달앱의 공식 서비스가
아니라는 걸 페이지에 명시한다. *SEO에서 걸리는 지점*: `Product`/`Offer`
구조화 데이터가 이것과 정면으로 부딪힌다. 자세한 건 §3과 반려 목록에 있다.

**ADR-016 — 정렬 판정이 두 곳에 있다** — 어떤 금액이 "확정"이고 정렬에
쓰이는지를 판정하는 로직이 백엔드
(`BrandComparisonService.confirmedSortingAmount()`)와 프론트
(`web/src/filters.js`) **양쪽에** 있다. 한쪽만 고치면 카드 정렬과 카드 안
"최고 할인" 표식이 서로 다른 답을 낸다. *SEO에서 걸리는 지점*: 프리렌더는
**세 번째 소비자**다. §4를 할 때 세 곳이 같은 규칙을 따르는지 봐야 한다.

**qualifier 체계** — 오퍼 금액에 붙는 확실성 표식이다. `행사`(확정),
`최대`(상한이라 실제로는 더 적을 수 있음), `최적`(쿠폰을 겹쳤을 때 나오는
값), `특정메뉴`(메뉴 한정) 네 가지가 있다. 같은 "5,000원"이라도 표식에 따라
의미가 다르고, `최대`는 정렬에서 빠진다. *이 카테고리에서 드문 전문성
신호*라고 콘텐츠 감사가 평가했다.

**미러 토폴로지 — 개별 배포 저장소에 직접 커밋하지 않는다** — 사람은
모노레포에만 커밋하고, `mirror-deploy-repos.yml`이 `rsync`로 배포용 개별
저장소에 밀어 넣는다. 개별 저장소에 직접 커밋하면 다음 미러 때 조용히
지워진다. web은 Vercel이 자동 배포하고, api는 사람이 수동으로
실행(`workflow_dispatch`)한다.

**Vite에는 SSR/프리렌더 기능이 없다** — 그래서 빌드 후 스크립트로 HTML에
본문을 끼워 넣는 절충을 택했다. `web/src/variant.js`가 모듈 로드 시점에
`localStorage`를 읽어서 서버 환경에서는 실행 자체가 안 되는 것도 이유다.
Next(SSG)로 옮기는 건 `docs/TECH-CHOICES.md`가 플랜B로 적어 뒀지만, 아직
프리렌더로 안 해 본 것이 남아 있어 지금은 아니다.

## 사이트맵 제출 현황

### 지금 상태

사이트맵 파일 자체는 **이미 정상 동작 중**이다.

```
$ curl -s -o /dev/null -w "%{http_code} %{size_download}\n" \
    https://beggars-five.vercel.app/sitemap.xml
200 23792
```

`robots.txt`도 사이트맵 위치를 선언하고 있다.

```
$ curl -s https://beggars-five.vercel.app/robots.txt
User-agent: *
Allow: /

Sitemap: https://beggars-five.vercel.app/sitemap.xml
```

**즉 구글은 이미 스스로 사이트맵을 찾아갈 수 있다.** 서치콘솔 제출은
색인의 필수 조건이 아니다.

### 그러면 제출은 왜 하나

두 가지를 얻는다.

- **속도** — 매일 데이터가 바뀌는 사이트인데, 크롤러가 자기 일정대로 오길
  기다리면 반영이 늦다.
- **리포트** — 111개 중 몇 장이 색인됐고 무엇이 왜 제외됐는지를 서치콘솔이
  사이트맵 단위로 보여준다. 이게 없으면 브랜드 페이지 110장이 실제로
  먹히는지 확인할 방법이 없다. §1을 하고 나서 효과를 재려면 이 리포트가
  있어야 한다.

### 제출은 사람이 해야 한다

**자동화 불가.** 구글 서치콘솔 API를 쓰려면 OAuth 자격증명이 필요한데
설정돼 있지 않고, 계정 로그인 자체가 사람이 할 일이다.

등록할 때 주의할 점이 하나 있다. `beggars-five.vercel.app`은 Vercel이
주는 서브도메인이라 **우리가 DNS 레코드를 만질 수 없다.** 그래서
서치콘솔의 "도메인" 방식(DNS TXT 레코드로 확인)은 **반드시 실패한다.**
**"URL 접두어" 방식을 고르고 "HTML 태그"로 확인**해야 한다.

확인용 메타 태그는 이미 라이브에 배포돼 있다(2026-08-28 실측 확인).

| 검색엔진 | 토큰 | 위치 |
|---|---|---|
| 구글 | `n8r_pJ6JqfkW0hjLy9vZAhWp-cgCQ3NXcQrXzfE-tWc` | `web/index.html` |
| 네이버 | `8bbb93cfe5d6ba787b1954e5237e75f56767180d` | `web/index.html` |

순서:

1. 서치콘솔에서 **URL 접두어**로 `https://beggars-five.vercel.app/` 추가
2. 확인 방법에서 **HTML 태그** 선택 → 이미 배포돼 있으므로 바로 확인 누름
3. 좌측 메뉴 `Sitemaps` → `sitemap.xml` 입력 → 제출
4. 네이버 서치어드바이저도 같은 방식(사이트맵 제출 칸이 따로 있다)

### 계정 없이 되는 대안

[§10 IndexNow](#10-indexnow를-붙인다)는 계정 로그인 없이 동작한다. 키 파일을
사이트에 두고 HTTP 요청 한 번을 보내는 방식이라 자동화가 된다. 다만 구글은
IndexNow를 지원하지 않는다 — Bing·네이버·Yandex용이다. 구글 쪽은 위의
수동 제출이 필요하다.

## 1. 홈 프리렌더 본문에 브랜드 상세 링크를 넣는다

**공수 낮음.** 다섯 감사(기술·SXO·콘텐츠·GEO·사이트맵)가 **각각 독립적으로**
1순위로 꼽은 하나다.

### 왜 이게 문제인가

크롤러는 링크를 타고 다니며 페이지를 발견하고, 링크를 통해 "이 페이지가
중요하다"는 신호도 전달한다. 우리는 브랜드 페이지 110장을 정성껏 만들어
놨는데, 홈에서 그 페이지로 가는 링크가 하나도 없다. 크롤러 입장에서는
사이트맵에 주소가 적혀 있으니 찾아가긴 하지만, "이 페이지가 사이트 안에서
얼마나 중요한지"를 판단할 근거가 전혀 없다.

내용이 없어서가 아니다. 홈 HTML 안에는 108개 브랜드 이름과 앱별 할인 금액이
텍스트로 다 들어 있다. **텍스트는 있는데 그걸 감싸는 링크가 없을 뿐이다.**

### 근거

```
$ curl -s https://beggars-five.vercel.app/ | grep -c '<a '
0
$ curl -s https://beggars-five.vercel.app/ | grep -c 'brand/'
0
```

브랜드 상세 페이지 쪽은 이미 제대로 돼 있다 — 홈 복귀 링크와 같은 분류
형제 브랜드 링크가 `prerender.mjs:244,253`에 있다. 홈만 빠졌다.

### 안 고치면

브랜드 페이지 110장이 계속 사이트맵으로만 발견된다. 색인은 될 수 있어도
검색 순위에서는 계속 뒤로 밀린다. §3·§4·§6·§7로 그 페이지들의 품질을
올려도 발견 경로가 약해서 효과가 반감된다.

### 오해하기 쉬운 것 — 버튼이 문제가 아니다

"링크 대신 버튼을 써서 그렇다"로 읽으면 틀린 데를 고치게 된다.

| 요소 | 실제 | 판정 |
|---|---|---|
| 오퍼 칩 | `<a href>` (`web/src/App.jsx` `OfferChip`) | **정상.** 커스텀 스킴은 같은 탭으로 여는 처리까지 돼 있다 |
| 브랜드 펼침 | `<button aria-expanded>` | **정상.** 이동이 아니라 토글이라 시맨틱하게 맞다 |
| 홈 `.seo` 블록의 브랜드명 | `<h3>` 안의 평문 | **여기가 문제** |

오퍼 칩의 `<a>`는 하이드레이션 후에 생기고, 그것도 전부 **외부 앱으로
나가는 링크**다. 내부 링크가 아니다. 고칠 곳은 프리렌더 블록 하나다.

### 어디를 고치나

`web/scripts/prerender.mjs` — `brandBlock()`의 `<h3>` 한 줄.

```js
// 지금 (line 65 부근)
`        <h3>${esc(b.name)}${cat ? ` <span>${esc(cat)}</span>` : ''}</h3>`,
```

브랜드명을 `<a>`로 감싼다. slug 생성 함수 `slugOf()`가 이미 같은 파일
165행에 있고, 브랜드 상세 페이지 URL을 만들 때 이미 쓰고 있다(221·253·322·329행).
새 데이터도 새 로직도 필요 없다 — 같은 함수를 홈 쪽에서도 부르면 된다.
`.seo a` 스타일도 `BOOT_STYLE`에 이미 있다(110행).

footer의 `수록 브랜드:` 목록(128행)은 그대로 둔다. 108개를 전부 링크로
만들면 같은 목적지로 가는 앵커가 페이지당 216개가 되어 오히려 링크 가치가
희석된다.

### 원칙과 충돌하지 않는 이유

콘텐츠를 새로 만드는 게 아니다. 브랜드명 텍스트도, slug도, 대상 페이지도
이미 전부 존재한다. 이미 있는 텍스트를 앵커로 감싸는 것뿐이라
"모르는 값을 지어내지 않는다"와 무관하다.

**실사용자 화면은 안 변한다.** 하이드레이션되면 React가 `#root`를 덮으므로
프리렌더 블록은 사라진다. 링크를 보는 건 크롤러와, JS가 붙기 전 첫 페인트를
본 사람뿐이다.

### 검증

```bash
cd web && npm run build
grep -c 'href="/brand/\|href="https://beggars-five.vercel.app/brand/' dist/index.html   # 108 근처
```

배포 후:

```bash
curl -s https://beggars-five.vercel.app/ | grep -c '<a '   # 0이 아니어야 한다
```

## 2. LCP 18.8초를 줄인다

**공수 높음.** 넷으로 쪼갤 수 있고, 순서대로 하면 각각 독립적으로 값이 난다.

### 왜 이게 문제인가

LCP 18.8초는 **사용자가 주소를 연 뒤 화면에서 가장 큰 콘텐츠가 그려질
때까지 18.8초가 걸린다**는 뜻이다. 구글 기준으로 2.5초 이하가 "좋음",
4초 초과가 "나쁨"이다. 우리는 기준의 7배가 넘는다. 대부분의 사람은 그 전에
나간다.

TBT 4,952ms는 그 5초 가까이 동안 **자바스크립트가 메인 스레드를 붙잡고
있어서 아무 조작도 안 먹힌다**는 뜻이다. 그래서 INP(누른 뒤 반응까지의
시간)도 나쁠 것으로 본다.

측정값(Lighthouse 13, 모바일 에뮬레이션, 실험실):

```
LCP  18.8초   Poor   (기준 2.5초)
CLS  0.09     Good
TBT  4,952ms  → INP도 Poor로 예상(긴 작업 17개, 최대 1.28초)
```

CrUX 필드 데이터는 없다(구글 API 키 미설정). 실험실 값이라 실제 사용자
체감과 다를 수 있고, INP는 실험실에서 직접 못 잰다 — TBT를 대리 지표로 썼다.

### 안 고치면

검색 순위에서 직접 감점된다(Core Web Vitals는 순위 신호다). 그보다 큰 건
사용자 이탈이다 — 이건 SEO만의 문제가 아니라 `docs/USER-BEHAVIOR.md`가
기록한 **첫 화면 무동작 57.9%**와 이어진다. 그중 일부는 데이터가 도착하기
전에 나간 것으로 보인다. `prerender.mjs`의 `BOOT_STYLE` 주석이 이미 같은
얘기를 하고 있다.

### 2-1. 폰트 2.06MB (공수 낮음, 효과 가장 큼)

**왜 문제인가**: 페이지에서 받는 파일 중 **가장 큰 단일 리소스가 폰트
하나(2.06MB)**다. 게다가 "렌더블로킹"이라 이 파일을 다 받기 전에는 브라우저가
화면을 그리기 시작하지 못한다. 외부 CDN(jsdelivr)에서 받으므로 그 서버까지
왕복하는 시간도 얹힌다.

`web/index.html`이 jsdelivr에서 Pretendard **variable 전체**를 렌더블로킹
`<link rel="stylesheet">`로 받는다.

```html
<!-- web/index.html:12-14 -->
<link rel="preconnect" href="https://cdn.jsdelivr.net" crossorigin />
<link rel="stylesheet" as="style" crossorigin
  href="https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable.css" />
```

한글 서브셋 고정 웨이트 `woff2`를 `web/public/`에 두고 자체 호스팅한다.
`font-display: swap`을 명시하고 `<link rel="preload">`로 바꾼다. 외부
도메인 왕복이 사라져 `preconnect`도 같이 걷는다.

> `font-display: swap`은 "폰트가 아직 안 왔으면 일단 기본 글꼴로 보여주고
> 나중에 바꿔 끼워라"는 뜻이다. 글자가 안 보이는 시간이 사라진다.

검증: `curl -sI <자체호스팅 폰트 URL> | grep -i content-length` — 2MB에서
수백 KB로 떨어져야 한다.

### 2-2. 브랜드 리스트 가상화 (공수 높음, 근본 원인)

**왜 문제인가**: 브랜드 카드를 **전부 한꺼번에 그린다.** 화면에 보이는 건
몇 개뿐인데 110개 브랜드의 카드와 그 안의 오퍼 칩까지 전부 DOM에 만든다.
브라우저는 그 5,633개 요소의 위치와 크기를 전부 계산해야 하고, 거기에만
5.9초가 든다. "가상화"는 **화면에 보이는 것만 그리고 스크롤하면 갈아 끼우는**
기법이다.

DOM 노드 **5,633개**(권장 1,500의 3.7배). Style/Layout에만 5.9초가 들고
`index-*.js` 안에서 forced reflow가 384ms·205ms씩 걸린다. LCP와 INP 양쪽에
가장 크게 작용하는 단일 원인이다.

`web/src/App.jsx`의 브랜드 카드 목록에 창(window) 렌더링을 넣는다.
**다만 이건 새 의존성을 들이는 결정**이라 별도 판단이 필요하다 —
`web/package.json`의 런타임 의존성은 지금 4개뿐이고, `docs/TECH-CHOICES.md`가
"상태 관리 라이브러리가 없다. 전역 상태가 필요한 지점이 없다"고 적어 둔
기조와 맞물린다. `content-visibility: auto` 같은 CSS 네이티브 수단을 먼저
재 보고, 모자랄 때 라이브러리로 간다.

> `content-visibility: auto`는 브라우저에게 "화면 밖 요소는 레이아웃 계산을
> 건너뛰어라"라고 알려주는 CSS 한 줄이다. 라이브러리 없이 되는지 먼저 본다.

검증: DevTools에서 DOM 노드 수, 또는 `document.querySelectorAll('*').length`.

### 2-3. 계측 스크립트를 크리티컬 패스에서 뺀다 (공수 낮음)

**왜 문제인가**: "크리티컬 패스"는 화면이 뜨기까지 반드시 거쳐야 하는
요청들의 사슬이다. 지금은 분석 도구(PostHog)가 **정작 필요한 데이터
요청(`api/brands`)보다 앞에** 끼어 있다. 사용자에게 아무 값도 주지 않는
스크립트 때문에 할인 데이터가 늦게 도착한다.

```
index.js → posthog.js → api/brands → posthog beacon    총 6.9초
```

GTM 172KB(43% 미사용) + PostHog 57KB(55% 미사용)가 메인 스레드에서
약 1.5초를 먹고, PostHog이 `api/brands` **앞에** 끼어 있다.

PostHog 초기화를 첫 페인트 이후(`requestIdleCallback`)로 미루고,
`api/brands`·`api/banners`를 JS 번들과 병렬로 당긴다(현재는 번들 로드 뒤에
걸려 약 1.3초 손해).

리전 이동은 답이 아니다 — PostHog 클라우드는 US(버지니아)·EU(프랑크푸르트)
둘뿐이라 한국에서는 EU가 더 멀다. 대신 같은 오리진 프록시를 이미 넣었다
(`web/vercel.json`의 `/ph/*` rewrite, `docs/DEV-ENVIRONMENT.md` 참고).
TLS 핸드셰이크가 서울 엣지에서 끝난다.

### 2-4. 이미지 (공수 중간)

**왜 문제인가**: 브랜드 로고 이미지를 112개 받는데 합쳐서 1.78MB다. PNG라
용량이 크고, 화면 아래에 있어 당장 안 보이는 것까지 전부 미리 받는다.

이미지 요청 112개 1.78MB. 로고 PNG가 개당 92~208KB다
(`web/public/logos/`). WebP/AVIF로 바꾸고 접힘선 아래는 `loading="lazy"`,
`width`/`height`를 고정해 CLS 여지를 없앤다.

> `loading="lazy"`는 "화면에 가까워지면 그때 받아라"는 표시다.
> `width`/`height`를 미리 적어 두면 이미지가 도착하기 전에도 브라우저가
> 자리를 비워 둬서 레이아웃이 튀지 않는다(CLS 방지).

## 3. JSON-LD를 넣는다 — WebSite와 Organization만

**공수 낮음.** 현재 홈·브랜드 상세 모두 `application/ld+json` **0건**이다.

### 왜 이게 문제인가

검색엔진은 HTML을 읽어서 내용을 짐작하지만, 구조화 데이터(JSON-LD)를 넣으면
**짐작이 아니라 명시적으로** 알려줄 수 있다. "이 사이트의 이름은 무엇이고,
어떤 언어이고, 누가 만들었다"를 기계가 읽는 형식으로 적어 두는 것이다.
AI 검색은 특히 이걸 중요하게 본다 — GEO 46점의 원인 중 하나다.

### 안 고치면

검색엔진과 AI가 우리 사이트의 정체를 HTML 본문에서 추론해야 한다. 인용
후보로 고를 때 구조화 데이터가 있는 경쟁 사이트에 밀린다.

### 어디를 고치나

`web/scripts/prerender.mjs`의 `metaTags()`(141행)와 `brandPage()`(215행)에
`<script type="application/ld+json">`를 추가한다. 값은 이미 그 함수들이
들고 있는 것(서비스명, URL, 설명, 언어)만 쓴다.

```json
{ "@context": "https://schema.org", "@type": "WebSite",
  "name": "오늘의할인", "url": "…", "inLanguage": "ko-KR" }
```

`Organization`의 `logo`는 **실제 이미지 파일이 준비된 뒤에** 넣는다.
현재 파비콘은 `index.html`에 인라인 SVG data URI라 구글이 요구하는
로고 사양(최소 112×112px 실제 파일)을 못 채운다. 없는 URL을 미리 적지 않는다.

### 넣으면 안 되는 것

구조화 데이터는 "많이 넣을수록 좋다"가 아니다. **페이지가 실제로 하는 일과
어긋나는 마크업은 위험하다.**

| 타입 | 왜 안 되나 |
|---|---|
| `Product` / `Offer` / `AggregateOffer` | 페이지 footer가 **"판매 서비스가 아니며, 거래 관계가 없습니다"**라고 스스로 밝힌다(`prerender.mjs:129`, ADR-015가 요구한 고지다). 실제 거래가 이 페이지에서 일어나지 않는데 상품·가격 마크업을 달면 구조화 데이터가 페이지 기능과 불일치한다 — 무시되면 다행이고, 최악은 리치 결과 무효화다 |
| `SearchAction` | 검색이 URL 쿼리에 반영되지 않는 순수 클라이언트 상태다. `target` 템플릿(`?q={search_term}`)이 실제로 동작하지 않는다. 검색 상태를 URL에 싣도록 앱을 바꾸기 전에는 넣지 않는다 |
| `FAQPage` | 페이지에 FAQ 콘텐츠 자체가 없다. 구글이 2026-05-07에 FAQ 리치 결과를 전 사이트 대상으로 내렸으므로 새로 만들 이유도 없다 |

## 4. 브랜드 상세 소개 문장이 qualifier를 반영하게 한다

**공수 낮음.** 이 프로젝트가 가진 가장 특징적인 강점이 요약 문장에서만
새고 있다.

### 왜 이게 문제인가

우리는 금액마다 확실성 표식(`qualifier`)을 붙인다. `행사`는 확정 금액,
`최대`는 상한이라 실제로는 더 적게 받을 수 있다는 뜻이다. 이 구분이 이
프로젝트의 핵심 강점이고, 콘텐츠 감사도 "이 카테고리에서 드문 전문성
신호"라고 평가했다.

그런데 **브랜드 페이지의 소개 문장(검색 결과에 그대로 노출되는 그
문장)만 이 구분을 무시한다.** 상한 금액을 확정 금액인 것처럼 요약에
쓴다. 검색 결과에서 그 문장을 보고 들어온 사람이 실제로는 더 적은 금액을
받게 된다.

### 근거

```js
// web/scripts/prerender.mjs:218,220
const best = Math.max(...offers.map((o) => o.amount))
const desc = `${b.name}… 최대 ${won(best)}. …`
```

`qualifier`를 안 본다. BBQ 페이지의 실제 데이터는 배민 7,000원(`행사`,
확정)과 쿠팡이츠 5,000원(`최대`, 상한)인데, 소개 문장은 둘 중 큰 값만 뽑아
"최대 7,000원"이라고 쓴다. 어느 쪽이 확정이고 어느 쪽이 상한인지 구분이
사라진다.

같은 파일의 본문 쪽은 이미 제대로 한다 — `offerLine()`(49행)과
`offerSection()`(189행)이 `qualifier`를 괄호로 붙인다. 요약 문장만 빠졌다.

### 안 고치면

검색 결과 미리보기에 틀린 금액이 나간다. SEO 점수 이전에 **정확성 문제**다.
ADR-014가 막으려던 바로 그 상황이 검색 유입 경로에서만 계속 일어난다.

### 어디를 고치나

`web/scripts/prerender.mjs`의 `brandPage()` — `best` 계산에서
`qualifier === '최대'`인 오퍼를 제외한다. 제외하고 나서 남는 확정 오퍼가
없으면 금액을 요약에 쓰지 않는다.

이건 API가 이미 하고 있는 판정과 같은 규칙이다
(`api/src/main/java/com/discounttracker/comparison/BrandComparisonService.java`의
`confirmedSortingAmount()` — `"최대"`면 `null`을 돌려 정렬에서 뺀다).

### 원칙과 충돌하지 않는 이유

오히려 원칙을 지키러 가는 쪽이다. ADR-014가 "상한만 정해진 쿠폰은 금액을
확정값으로 적지 않는다"고 정했고 `qualifier` 체계가 그걸 구현했는데,
프리렌더 요약 문장만 그 체계 밖에 있었다.

### 주의 — ADR-016

정렬·대표값 판정은 **api와 web 양쪽에 있다**(`confirmedSortingAmount()`와
`web/src/filters.js`). 프리렌더는 세 번째 소비자다. 세 곳이 같은 답을 내야
카드 정렬, 카드 안 "최고 할인" 표식, 검색 결과 요약이 서로 어긋나지 않는다.

### 검증

```bash
cd web && npm run build
grep -o 'content="BBQ[^"]*"' dist/brand/BBQ.html | head -1
```

`최대` qualifier가 붙은 금액이 요약에 안 나와야 한다.

## 5. og:image를 넣는다

**공수 낮음.** 홈·브랜드 상세 모두 `og:image`·`twitter:image`가 없어
공유 시 썸네일이 안 뜬다. `twitter:card`도 `summary`로 잡혀 있다.

### 왜 이게 문제인가

카카오톡·슬랙·트위터에 링크를 붙여넣으면 보통 미리보기 카드가 뜬다. 그
이미지를 지정하는 게 `og:image`인데, 없으면 텍스트만 나오거나 아무것도 안
뜬다. 클릭률이 눈에 띄게 떨어진다. 우리 서비스는 "이 할인 봐라"고 공유될
성격이라 이 손실이 작지 않다.

### 안 고치면

공유 링크가 밋밋하게 나가서 클릭이 덜 일어난다. 홍보 채널을 통한 유입이
그만큼 줄어든다.

### 어디를 고치나

정적 이미지 **1장**을 `web/public/`에 두고 전 페이지 공통으로 건다
(`prerender.mjs`의 `metaTags()`와 `brandPage()` head).

브랜드별 동적 이미지는 만들지 않는다 — 카드 데이터가 매일 바뀌므로
브랜드별 이미지는 매일 무효화된다. 하루 1회 배치 구조에서 유지비만 늘고,
캐시된 옛 금액이 소셜에 남으면 오히려 틀린 값을 퍼뜨린다.

## 6. llms.txt를 만든다

**공수 낮음.** `/llms.txt` 404. AI 크롤러(GPTBot·ClaudeBot·PerplexityBot 등)는
`robots.txt`가 전체 허용이라 접근 자체는 되지만, 사이트 성격과 데이터
갱신 주기를 알릴 채널이 없다.

### 왜 이게 문제인가

AI 검색이 답변에 출처를 인용할 때, 그 사이트가 무엇이고 데이터가 얼마나
최신인지 알면 인용 판단이 쉬워진다. `llms.txt`는 그걸 적어 두는 파일이다.
`robots.txt`가 "들어와도 되냐"를 다룬다면 이건 "우리가 무엇이냐"를 다룬다.
아직 공식 표준은 아니지만 비용이 거의 없다.

### 안 고치면

AI 검색이 우리 사이트의 성격을 본문에서 추론해야 한다. GEO 46점이 그대로
간다.

### 어디를 고치나

`web/scripts/prerender.mjs`의 `main()`에서 `robots.txt`를 쓰는 자리(303행)
바로 옆에 같은 방식으로 쓴다. 내용은 서비스 목적, 데이터 출처(실기 캡처),
하루 1회 갱신, 비영리·비제휴 고지 — 전부 이미 사실로 확정된 것들이다.

ADR-015가 요구한 고지를 기계가 읽는 형식으로 한 번 더 두는 셈이다.

검증: `curl -s https://beggars-five.vercel.app/llms.txt | head -5`

## 7. 브랜드 상세에 "다른 앱에는 없다"를 명시한다

**공수 낮음.** 표본 5장 중 3장이 앱 1개짜리다. 본문이 100~150단어라
얇아 보이는데, 실제로는 계근상 페이지처럼 구간표와 계산식까지 든 경우가 있다.

### 왜 이게 문제인가

브랜드 페이지에 할인이 있는 앱만 나열하고 나머지 앱은 **언급 자체를 안
한다.** 그래서 읽는 사람이 "다른 앱에는 확인해 봤는데 없더라"인지 "다른
앱은 아직 안 봤다"인지 구분할 수 없다. 검색엔진 입장에서도 페이지가
불완전해 보인다.

흔한 SEO 권고는 "단어 수를 늘려라"인데, 우리에게 그건 **없는 할인을 서술로
지어내라**는 말이 되어 반려다. 대신 "확인했는데 없었다"는 **사실**을 적는다.

### 안 고치면

앱 1개짜리 페이지가 계속 얇아 보인다. 씬 콘텐츠로 판정되면 색인에서
빠질 수 있다.

### 어디를 고치나

`prerender.mjs`의 `brandPage()`에서 `offers`에 없는 플랫폼을 한 줄로 적는다.

> 쿠팡이츠·요기요·땡겨요에서는 이 브랜드 할인을 확인하지 못했습니다(2026-08-28 기준).

### 원칙과 충돌하지 않는 이유

**"비어 있다는 사실도 데이터"를 실행하는 것**이다. `docs/TECH-CHOICES.md`가
"모르는 값을 지어내지 않는다. 화면엔 미확인으로 드러낸다"고 적은 그
원칙 그대로다. 없는 할인을 서술로 채우는 것과 정반대 방향이다.

문구는 "없다"가 아니라 "확인하지 못했다"로 쓴다 — 하루 1회 배치라
수집 시점 이후에 생긴 할인은 우리가 모른다.

## 8. 저자·연락 수단을 한 줄 노출한다

**공수 낮음.** E-E-A-T 항목 중 Authoritativeness가 8/25로 가장 낮다.
`og:type=article`인데 `author` 메타도 저자 소개도 없다.

### 왜 이게 문제인가

검색엔진은 "누가 썼는지 알 수 없는 페이지"를 낮게 본다. 특히 금액 정보처럼
틀리면 사용자가 손해를 보는 내용은 더 그렇다.

역설적인 건 **우리가 실제로는 강한 근거를 갖고 있는데 그게 안 보인다는
것**이다. 확인일, 품절 상태, "오전 11시 오픈" 같은 값은 사람이 매일 실제
휴대폰으로 앱을 열어 캡처하지 않으면 나올 수 없는 정보다. 그런데 그 사실이
어디에도 문장으로 적혀 있지 않아서, 읽는 사람이 데이터 배열을 보고 추론해야
한다.

### 안 고치면

E-E-A-T 최약점이 그대로 간다. 검색엔진도 AI도 우리를 인용할 근거를 못 찾는다.

### 어디를 고치나

`prerender.mjs`의 footer(129·258행)에 이미 비영리·비제휴 고지가 있다.
그 옆에 두 가지를 더한다:

- 확인일·상태 필드가 무엇인지 한 문장 — "확인일과 품절 여부는 사람이 각 앱
  화면을 직접 열어 캡처한 값입니다."
- 제보/문의 수단 한 줄(이메일 또는 저장소 이슈 링크)

새 사실을 주장하는 게 아니라 이미 있는 필드가 왜 존재하는지 설명하는
메타 문장이다.

## 9. 보안 헤더를 붙인다

**공수 낮음.** `Strict-Transport-Security`는 이미 있는데(Vercel 기본)
`Content-Security-Policy`·`X-Content-Type-Options`·`X-Frame-Options`·
`Referrer-Policy`·`Permissions-Policy`가 전부 없다.

### 왜 이게 문제인가

보안 헤더는 브라우저에게 "이 페이지에서 이런 건 하지 마라"를 알려주는
HTTP 응답 헤더다. 예를 들어 `X-Frame-Options`는 다른 사이트가 우리 페이지를
프레임 안에 몰래 띄워 클릭을 가로채는 걸 막는다. 정적 정보 사이트라 실제
위험은 낮지만, 없을 이유도 없다.

**SEO 점수와 직접 관계는 없다.** 공수가 낮아 같이 처리하는 항목이다.

### 안 고치면

당장 문제는 없다. 클릭재킹이나 MIME 스니핑 같은 기본 방어선이 없는 상태가
계속된다.

### 어디를 고치나

`web/vercel.json`에 `headers` 절을 추가한다. 지금 이 파일에는 `rewrites`만
있다.

`Access-Control-Allow-Origin: *`이 전역으로 열려 있는 것도 같이 본다 —
정적 정보 사이트라 위험은 낮지만 넓힐 이유도 없다.

검증: `curl -sI https://beggars-five.vercel.app/ | grep -i "content-security\|x-frame\|x-content-type"`

## 10. IndexNow를 붙인다

**공수 낮음.** 미구현.

### 왜 이게 문제인가

우리 사이트의 값은 **데이터가 매일 바뀐다는 것**이다. 그런데 바뀐 걸
검색엔진에 알릴 방법이 크롤러가 다시 오길 기다리는 것뿐이다. IndexNow는
"지금 이 주소들이 바뀌었다"고 HTTP 요청 한 번으로 알리는 프로토콜이다.
Bing·네이버·Yandex가 지원한다(구글은 미지원).

### 안 고치면

오늘 바뀐 할인이 검색 결과에 반영되기까지 며칠 걸린다. 매일 갱신하는
노력의 상당 부분이 검색 쪽에서는 안 보인다.

### 어디를 고치나

키 파일을 `web/public/`에 두고, 배포 후 sitemap URL 목록을 한 번 POST한다.
빌드 훅이나 `banner_routine.py`가 `/api/reload`를 부르는 자리 옆이 붙일 곳이다.

`sitemap.xml`이 `changefreq: daily`, `lastmod` 매일 갱신으로 되어 있어
IndexNow와 신호가 일관된다.

네이버 서치어드바이저와 시너지가 있다 — verification 메타는 이미 배포돼
있다(`web/index.html`).

**선행 조건**: 구글 서치콘솔·네이버 서치어드바이저 소유 확인이 아직
안 끝났다. 사람이 로그인해서 눌러야 한다. `beggars-five.vercel.app`은
Vercel 서브도메인이라 DNS TXT를 우리가 못 만지므로 **"URL 접두어" +
"HTML 태그"** 방식으로 등록한다(도메인 방식은 실패한다). 자세한 건
[§사이트맵 제출 현황](#사이트맵-제출-현황) 참고.

## 11. 사이트맵 lastmod를 실제 변경분만 갱신한다

**공수 중간. 급하지 않다.**

### 왜 이게 문제인가

`lastmod`는 "이 페이지가 마지막으로 바뀐 날짜"를 검색엔진에 알려주는
값이다. 지금은 111개 URL 전부 같은 날짜가 들어간다 — 빌드한 날짜를 그대로
쓰기 때문이다. 실제로는 할인이 안 바뀐 브랜드도 매일 "오늘 바뀜"으로
나간다. 검색엔진이 이걸 알아채면 **`lastmod`를 아예 안 믿게 된다.**

### 안 고치면

`lastmod` 신호가 무시된다. 실제로 바뀐 페이지도 우선 크롤링을 못 받는다.
당장 큰 손해는 아니다.

### 어디를 고치나

`prerender.mjs:337` 부근. 전날 `export.json`과 비교해 실제로 값이 달라진
브랜드만 오늘 날짜를 주고 나머지는 이전 `lastmod`를 유지한다. 다만 이걸
하려면 전날 스냅샷을 어딘가 들고 있어야 한다 — DB가 없는 구조라 파일 하나를
더 두는 셈이다. 효과 대비 비용을 재 보고 결정한다.

`priority`·`changefreq`는 구글이 무시한다. 지워도 되지만 해가 없어
우선순위 밖이다.

## 12. 터치 타겟을 키운다

**공수 낮음.** SEO가 아니라 사용성이다. 감사에서 같이 나와 여기 둔다.

### 왜 이게 문제인가

"터치 타겟"은 손가락으로 누를 수 있는 영역의 크기다. 사람 손가락 끝은
대략 44~48px 넓이라서 그보다 작으면 정확히 누르기 어렵다.

| 요소 | 현재 | 권장 |
|---|---|---|
| 배너 페이지네이션 점 | **14×14px** | 44~48px |
| 앱 필터 라벨 캡슐 | 46×**19px** | 44px 이상 |
| 배너 닫기 | 24×24px | 44px |

배너가 자동 전환(4.3초)되므로 지나간 딜로 돌아가려면 14px 점을 정확히
눌러야 한다. 사실상 못 누른다.

### 안 고치면

배너를 되돌려 보려는 사람이 실패한다. 배너 클릭률(최근 7일 12.1%)이 낮은
원인 중 하나일 수 있다.

### 어디를 고치나

시각 크기는 두고 `padding`으로 히트 영역만 넓히면 디자인을 안 건드린다.

`h1`이 1×1px `sr-only`라 접힘선 위에 서비스 정체성이 시각적으로 없는
것도 같이 나왔다. 첫 화면 무동작 57.9%와 연결해 볼 여지가 있지만,
근거가 감사 의견 하나뿐이라 **A/B로 확인할 항목**이지 바로 고칠 항목이
아니다.

> `sr-only`는 "화면에는 안 보이지만 스크린 리더에는 읽히는" 상태를 만드는
> 관용적인 CSS다. 접근성 목적으로는 맞지만, 그 결과 눈으로 보는 사람에게는
> 서비스 이름이 첫 화면에 안 나온다.

## 13. `/brand/*.html`과 앱 본체를 잇는다

**공수 중간. 판단이 필요하다.**

### 왜 이게 문제인가

브랜드 상세는 크롤러용으로 따로 만든 정적 페이지다. 실제 앱(React SPA)에는
그 주소가 라우트로 등록돼 있지 않다. 그래서 검색으로 브랜드 페이지에 들어온
사람이 "이 서비스 전체를 써 보자"로 자연스럽게 넘어가지 못한다.
확장자 없는 `/brand/열정국밥`은 404다.

### 안 고치면

검색 유입이 생겼을 때 그 사람들이 브랜드 페이지 한 장만 보고 나간다.
**지금은 유입 자체가 거의 없어서 손실이 작다** — 그래서 우선순위가 낮다.

### 어디를 고치나

지금도 완전한 막다른 길은 아니다 — "네 앱 전체를 한 화면에서 비교하기 →"
링크가 홈 해시(`/#브랜드명`)로 간다(`prerender.mjs:244`). 이게 실제로 그
브랜드 카드로 스크롤/펼침되는지는 **확인 필요**하다. 안 되면 그 해시를
처리하는 쪽이 라우터를 붙이는 것보다 훨씬 싸다.

`docs/TECH-CHOICES.md`가 "화면이 여러 페이지가 됨 → 라우터를 붙인다"를
플랜B로 적어 뒀다. 아직 그 조건은 아니다.

## 반려한 권고

감사에서 나왔지만 하지 않기로 한 것들. 나중에 같은 권고가 다시 오면
여기를 먼저 본다.

**이 목록이 있는 이유**: SEO 권고는 일반적인 사이트를 전제로 나온다.
우리 사이트는 판매를 하지 않고, 데이터를 지어내지 않기로 했고, 자동
생성 페이지의 성격이 다르다. 그래서 "보통은 맞는 조언"이 여기서는 틀리는
경우가 있다.

| 권고 | 왜 남들은 하라고 하나 | 왜 우리는 안 하나 |
|---|---|---|
| `Product`/`Offer` 스키마 | 할인·가격 정보를 다루는 페이지라면 상품 구조화 데이터를 넣어 검색 결과에 가격을 노출시키는 게 보통 이득이다 | **우리는 판매자가 아닌데 판매자인 척하는 마크업이 된다.** 페이지 footer가 스스로 "판매 서비스가 아니며, 거래 관계가 없습니다"라고 밝히고 있고(ADR-015가 요구한 고지), 실제 거래는 배달앱에서 일어난다. 구조화 데이터가 페이지의 실제 기능과 어긋나면 구글이 무시하거나 — 최악의 경우 — 리치 결과 자격 자체를 박탈한다. 고지 문구와 마크업이 서로 반대말을 하는 상태가 된다 |
| `SearchAction` | 사이트에 검색창이 있으면 구글 검색 결과에 검색창을 같이 띄워 주는 기능이 있다 | 우리 검색은 URL에 반영되지 않는 순수 클라이언트 상태다. `target` 템플릿(`?q={검색어}`)이 실제로 아무 데도 안 간다. **동작하지 않는 기능을 동작한다고 마크업하는 것**이라 안 넣는다 |
| 브랜드별 og:image | 페이지마다 다른 미리보기 이미지를 주면 공유 클릭률이 올라간다 | 데이터가 매일 바뀌어 이미지가 매일 무효화된다. 더 나쁜 건 **소셜 플랫폼이 이미지를 캐시한다는 것** — 어제 금액이 박힌 이미지가 계속 돌아다니며 틀린 값을 퍼뜨린다. 정적 1장(§5)으로 간다 |
| 브랜드 페이지 단어 수 늘리기 | 얇은 페이지는 색인에서 빠지기 쉬우니 설명을 보강하라는 건 표준적인 조언이다 | **없는 할인을 서술로 채우게 된다.** "모르는 값을 지어내지 않는다"를 정면으로 어긴다. 대신 §7(부재를 사실로 명시)로 간다 — 이건 단어도 늘고 원칙도 지킨다 |
| Next(SSG) 전환 | SPA의 SEO 한계를 근본적으로 푸는 정공법이다 | `docs/TECH-CHOICES.md`가 "SEO가 목표가 됨"을 플랜B 조건으로 적어 두긴 했다. 다만 **프리렌더로 아직 안 해 본 것이 남아 있다**(§1·§3·§4·§6). 프레임워크를 갈아엎기 전에 그걸 다 하고, 그러고도 모자랄 때 꺼낸다 |
| `FAQPage` | 자주 묻는 질문을 구조화하면 검색 결과에 접었다 펼 수 있는 항목이 붙는다 | FAQ 콘텐츠 자체가 없다. 게다가 **구글이 2026-05-07에 FAQ 리치 결과를 전 사이트 대상으로 내렸다** — 이제 그 SERP 기능 자체가 없어서 새로 만들 이유가 사라졌다 |
| AI 크롤러 차단(CCBot 등) | 콘텐츠가 AI 학습에 무단으로 쓰이는 걸 막으려는 사이트가 늘고 있다 | 지금 전체 허용이다. **GEO(AI 검색 인용) 점수를 올리려는 판에 막을 이유가 없다.** 학습 이용을 막고 싶어지면 그때 결정한다 — 되돌릴 수 있는 결정이다 |

## 뒤집을 조건

지금의 판단이 언제 바뀌는지를 미리 적어 둔다. 결론보다 **전제**가 조용히
바뀌는 게 문서가 낡는 주된 이유라서다.

| 조건 | 대응 |
|---|---|
| §1·§3·§4·§6을 다 하고도 검색 유입이 안 늘어남 | 프리렌더의 한계다. `docs/TECH-CHOICES.md` 플랜B대로 Next(SSG)를 꺼낸다 |
| 검색 유입이 실제로 생김 | `/brand/*` 진입자가 앱 본체로 못 넘어가는 §13이 그때 실제 손실이 된다. 지금은 유입 자체가 없어 순위가 낮다 |
| 브랜드가 수백 개가 됨 | 사이트맵 분할과 §11(lastmod 차등)이 선택이 아니라 필수가 된다 |
| 실제 거래·제휴가 생김 | `Product`/`Offer` 스키마 반려가 풀린다. 동시에 ADR-015의 고지 문구를 다시 써야 한다 |
| 검색 상태를 URL에 싣게 됨 | `SearchAction` 반려가 풀린다 |
| CrUX 필드 데이터가 쌓임 | §2의 근거가 실험실 값에서 실측으로 바뀐다. 우선순위를 그때 다시 잰다 |
