# 기술 선택과 근거

무엇을 골랐고, 왜 골랐고, **무엇이 아쉬운지**를 적는다. 결정의 원본은 각
파트의 ADR이고 여기는 요약이다 — 어긋나면 ADR을 믿는다.

## 한눈에

| 파트 | 스택 | 한 줄 이유 |
|---|---|---|
| tracker | Python + ADB CLI | 앱 화면을 읽는 데 JVM이 필요 없다 |
| api | Java 17 + Spring Boot 3.3 | 팀이 공유하는 기준이 가장 명확하다 |
| web | React 18 + Vite 5 | 팀이 이미 쓰던 도구. 서버가 필요한 기능이 없다 |

---

## tracker

**Python.** ADB에 필요한 건 "명령 실행하고 결과 받기"뿐이다. Windows와
리눅스 양쪽에서 JVM·빌드툴 없이 돈다.

**Kotlin/Java를 안 썼다.** 유리해지는 지점이 UiAutomator 계측인데, 그건
요소를 resource-id로 찾는 방식이다. 화면을 매번 다시 읽기로 했으니 그 이점이
생기지 않고 APK 빌드 파이프라인만 남는다.

**앱 내부 API를 안 쓴다.** 판독 비용은 없어지지만 토큰 추출·만료 갱신을
떠안는다. 비공개 API라 예고 없이 바뀌고 약관 위반 소지도 있다.

**USB 실기로 캡처한다.** 에뮬레이터 탐지(Play Integrity)를 피한다. ADB
인터페이스가 같아서 코드는 기기 종류를 모른다 — `serial`만 다르다.

### 한계

- **화면이 바뀌면 깨진다.** 앱 UI 변경을 코드가 미리 알 방법이 없다.
- **사람이 붙어야 한다.** 기기 연결·로그인·수동 캡처가 자동화 밖에 있다.
- **수집이 하루 단위다.** 실시간이 아니고, 앱이 값을 바꿔도 다음 수집까지
  모른다.

### 플랜 B

| 조건 | 대응 |
|---|---|
| 특정 앱 자동화가 계속 깨짐 | 그 앱만 수동 캡처 + 비전 판독으로 내린다 (이미 배민 외 3개가 이 상태) |
| 수집 빈도를 올려야 함 | 브랜드 우선순위를 잘라 전수 대신 상위 N개만 돈다 |
| 앱이 공식 API를 열어줌 | 판독을 걷어낸다. 지금 거절한 건 비공개 API지 공개 API가 아니다 |

## api

**Java 17 + Spring Boot 3.3.** 팀이 공유하는 컨센서스와 컨텍스트가 가장
명확하다. 각자 개발 기준을 세워 온 전제 위에서 서로의 코드를 읽을 수 있다.

**도메인 객체가 규칙을 들고 있다.** 이게 이 스택을 고른 실질적 이유고, 코드로
확인된다.

| 객체 | 들고 있는 규칙 |
|---|---|
| `OfferRecord` | `status()` · `isExpired()` · `liveTiers()` · `amountAsOf()` |
| `Offer` | `preferredOver()` · `withDetailFrom()` |
| `BrandComparison` | `hasConfirmed()` · `byBestDiscount()` |

`BrandComparisonService`는 80줄이고 조립만 한다. 빈약한 모델에 뚱뚱한 서비스를
얹은 구조가 아니다.

**DB가 없다.** 데이터 137건, 하루 한 번 갱신. 파일로 충분하다.

**브랜드 지식은 `brands.yml` 하나.** 브랜드 추가가 가장 잦은 변경인데 예전엔
네 군데 수정 + 프론트 재배포가 필요했다.

**방문 측정은 자체 서버 JSONL.** 제3자에게 안 넘기면 고지할 것도 적어진다.
원장과 같은 모양이라 `jq` 한 줄로 집계된다.

### 한계

- **단일 서버, 단일 인스턴스.** 죽으면 화면이 빈다. 헬스체크만 있고 이중화는
  없다.
- **파일 저장이라 동시 쓰기를 못 버틴다.** 지금은 쓰는 주체가 배포 하나뿐이라
  문제가 안 된다.
- **원장에 "종료"를 적을 자리가 없다.** 그래서 `export_data.py`를 그대로
  돌리면 끝난 프로모션이 되살아난다. 만료는 API가 요청 시점에 거르는 것으로
  덮고 있다.

### 플랜 B

| 조건 | 대응 |
|---|---|
| 데이터가 수천 건이 됨 | SQLite → Postgres. 지금 구조는 파일 읽어 메모리에 캐시하는 것뿐이라 교체 지점이 `OfferRepository` 하나다 |
| 쓰기 주체가 늘어남 | 파일 드롭을 버리고 쓰기 API를 연다 |
| 가용성이 문제가 됨 | 응답이 정적에 가까우므로 CDN 캐시가 먼저다. 이중화는 그 다음 |

## web

**React.** 팀이 이미 쓰던 도구다. 이 규모에선 학습 비용이 가장 큰 변수고,
기획자도 익숙해서 화면 얘기가 바로 통한다. 웹앱·네이티브로 넓힐 여지도
남는다 — **다만 지금은 안 쓴다, 열어둔 선택지다.**

**Vite.** "Vercel이라서"가 아니다. Vercel은 CRA·Next·Vite를 똑같이 지원해서
그건 Vite만의 이유가 못 된다. 실제 이유:

- **서버가 필요한 기능이 하나도 없다.** 라우터도 SSR도 API 라우트도 안 쓴다
  (브랜드 링크는 URL 해시). Next의 값어치가 전부 안 쓰는 기능에 있고, 안 쓰는
  기능은 비용으로만 남는다.
- **설정이 없다.** `vite.config.js`가 6줄이다.
- **산출물이 평범한 정적 `dist/`다.** Vercel에 묶이지 않는다. "Vercel이라서
  Vite"가 아니라 **"Vite라서 어디든 상관없다"**가 실제로 얻은 것이다.
- CRA는 React 팀이 더 이상 권하지 않는다.

**백엔드 주소를 소스에 고정했다.** 상대경로+프록시와 `VITE_API_BASE_URL` 둘 다
빌드 모드에 따라 조용히 실패했다 — fetch가 자기 자신에게 나가 빈 화면이 되는데
에러로 안 잡혔다.

**상태 관리 라이브러리가 없다.** 전역 상태가 필요한 지점이 없다.

### 한계

- **SEO가 사실상 없다.** `index.html`에 `description` 하나뿐이고 본문은
  클라이언트에서 그려진다. 검색 유입이 안 잡힌다.
- **로컬 개발에서 로컬 API를 안 부른다.** 주소가 고정이라 `src/api.js`를
  손으로 바꿔야 한다.
- **네이티브 확장은 아직 말뿐이다.** RN 코드도 계획서도 없다.

### 플랜 B

| 조건 | 대응 |
|---|---|
| **SEO가 목표가 됨** | Vite를 버리고 Next(SSG)로 간다. 이 결정이 뒤집히는 가장 유력한 조건이다 |
| 백엔드가 둘 이상이 됨 | 고정 주소를 걷고 빌드 타임 주입으로 되돌린다. 그때는 실패가 조용하지 않도록 부팅 시 검증을 붙인다 |
| 화면이 여러 페이지가 됨 | 라우터를 붙인다. 지금 해시 방식은 카드 하나 공유용이라 페이지가 늘면 안 버틴다 |
| 네이티브를 실제로 함 | React Native. React를 고른 이유 중 하나가 이거였으니 그때 값을 받는다 |

## 관통하는 원칙

**모르는 값을 지어내지 않는다.** 비어 있다는 사실도 데이터다. 화면엔
"미확인"으로 드러낸다.

**공개된 경로로만 수집한다.** 로그인 없이 누구나 보는 화면만 쓰고, 자동
접근을 거부하는 곳은 우회하지 않는다.

**되돌리기 어려운 판단은 ADR로 남긴다.** 결론만이 아니라 **전제**와 **뒤집을
조건**을 적는다. ADR이 낡는 건 대부분 결론이 틀려서가 아니라 전제가 조용히
바뀌어서다.
