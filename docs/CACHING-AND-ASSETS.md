# 캐시 헤더와 자산 전달 방식

배거스 웹(`mono/web`)이 브라우저에 자산을 어떻게 전달하고, 각 자산에 어떤 캐시 수명을 주는지 정리한다. 2026-09-21 기준 배포 상태를 그대로 옮겼다. 이 문서 하나만 읽고도 다음 세 가지를 판단할 수 있게 쓴다. 새 자산을 어느 칸에 넣을지, 왜 로고는 파일이고 플랫폼 아이콘은 번들인지, 어떤 상황에서 지금 방식을 쓰면 안 되는지.

## 배경

배거스 웹은 Vercel(정적 파일과 서버리스 함수를 호스팅하는 서비스)에 올라간다. Vercel의 무료 한도 가운데 먼저 닿는 것은 전송량이 아니라 **Edge Requests(엣지 요청 수)** 다. 2026-09-07에 이 한도의 75퍼센트를 썼다는 경고를 받았다. 경고 시점의 요청 구성을 보면 이미지 요청이 압도적이었다. 브랜드 카드 하나마다 브랜드 로고 한 장과 배달앱 아이콘 네 장이 붙고, 목록에는 카드가 수십 개 깔린다.

여기서 두 가지 작업이 나왔다. 하나는 자산마다 캐시 수명을 다르게 주어 재요청을 없애는 것이고, 다른 하나는 작은 아이콘을 파일이 아니라 자바스크립트 번들 안에 넣어 요청 자체를 없애는 것이다.

## 현재 캐시 헤더

캐시 헤더는 `mono/web/vercel.json`의 `headers` 항목이 경로별로 지정한다. Cache-Control(브라우저와 중간 캐시에 응답을 얼마나 오래 보관해도 되는지 알려주는 HTTP 헤더)의 값은 네 구간으로 갈린다.

| 경로 | Cache-Control | 수명 |
|---|---|---|
| `/`, `/brand/(.*)` | `public, max-age=600, must-revalidate` | 10분 |
| `/logos/(.*)` | `public, max-age=2592000, immutable` | 30일 |
| `/platform-icons/(.*)` | `public, max-age=2592000, immutable` | 30일 |
| `/assets/(.*)` | `public, max-age=31536000, immutable` | 1년 |

각 값의 뜻은 다음과 같다.

- `max-age=N`: N초 동안은 서버에 묻지 않고 브라우저가 가진 사본을 쓴다.
- `must-revalidate`: `max-age`가 지나면 반드시 서버에 다시 물어야 한다. 네트워크가 끊겼다는 이유로 오래된 사본을 쓰는 것을 금지한다.
- `immutable`: `max-age` 안에서는 재검증 요청조차 보내지 말라는 뜻이다. 사용자가 새로고침을 눌러도 브라우저는 서버에 묻지 않는다.

구간을 이렇게 나눈 이유는 주소가 바뀌는 방식이 자산마다 다르기 때문이다.

`/assets/`에 들어가는 자바스크립트와 CSS는 Vite(웹 빌드 도구)가 파일 이름에 내용 해시를 넣는다. 2026-09-21 배포본은 `index-B5ypMhsG.js`다. 내용이 바뀌면 이름이 바뀌므로 옛 주소가 가리키는 파일은 영원히 그대로다. 1년 `immutable`이 안전하다.

HTML은 반대다. 주소가 `/`로 고정인데 내용은 배포마다 바뀐다. 새 배포의 HTML은 새 번들 이름을 가리키므로, HTML이 낡으면 사용자는 옛 자바스크립트를 계속 쓴다. 그래서 10분으로 짧게 두고 `must-revalidate`를 붙였다. 배포 후 최대 10분 안에 모든 방문자가 새 HTML을 받는다.

로고와 배달앱 아이콘은 주소가 고정이고 내용은 가끔 바뀐다. 두 성질이 충돌하므로 별도 장치가 필요하다. 다음 절이 그 장치다.

## 브랜드 로고: 매니페스트와 내용 해시 쿼리

`public/logos/`에는 브랜드 로고 PNG 168장이 있고 전체 용량은 3.6메가바이트다. 예전에는 로고가 있든 없든 브랜드마다 `/logos/<이름>.png`를 요청했다. 이 방식에 두 가지 문제가 있었다.

첫째, 로고가 없는 브랜드는 404(요청한 파일이 없다는 HTTP 응답)를 받는다. 그런데 `/logos/(.*)`에 `immutable` 30일이 걸려 있으므로 **404 응답 자체가 30일 캐시된다**. 2026-09-11에 빽다방 로고를 새로 올렸는데, 그 전에 방문했던 브라우저는 30일 동안 로고 대신 첫 글자 대체 표시를 계속 봤다. 로고를 올려도 브라우저가 서버에 묻지 않으니 알 길이 없다.

둘째, 없는 로고를 요청하는 것만으로 Edge Requests가 소모된다. 한도를 요청 수로 세는 서비스에서 확실한 낭비다.

해결책은 빌드 시점에 매니페스트(자산 목록과 버전을 적어 둔 표)를 굽는 것이다. `scripts/build-logo-manifest.mjs`가 `npm run build`의 첫 단계로 돌면서 다음을 한다.

1. `public/logos/*.png`를 모두 읽는다.
2. 파일 내용을 해시(같은 내용이면 같은 값, 내용이 바뀌면 다른 값이 나오는 짧은 문자열)해 앞 8자를 딴다.
3. `src/logoManifest.js`에 `{ "브랜드명": "해시" }` 형태로 적는다.

화면에서 로고 주소를 만드는 `src/logoSrc.js`의 `brandLogoSrc()`는 매니페스트를 먼저 본다.

- 매니페스트에 이름이 없으면 `null`을 돌려준다. 화면은 `<img>`를 아예 그리지 않는다. 요청이 0이므로 404도 없고 캐시될 404도 없다.
- 있으면 `/logos/BBQ.png?v=e18b3347` 형태로 요청한다. 쿼리 문자열이 주소의 일부이므로, 파일을 교체하면 해시가 달라지고 주소가 달라져 30일 `immutable` 캐시를 비켜 간다. 파일이 그대로면 주소가 같아 캐시를 그대로 쓴다.

2026-09-21 실측으로 `https://beggars-five.vercel.app/logos/BBQ.png?v=e18b3347`는 `Cache-Control: public, max-age=2592000, immutable`, `X-Vercel-Cache: HIT`, `Age: 11446`을 돌려준다. 설계대로 동작한다.

## 배달앱 아이콘: WebP 변환과 base64 인라인

배민, 쿠팡이츠, 땡겨요, 요기요 아이콘 네 장은 파일이 아니라 자바스크립트 번들 안에 문자열로 들어 있다. `scripts/build-platform-icons.py`가 다음 순서로 굽는다.

1. `public/platform-icons/*.png`를 Pillow(파이썬 이미지 처리 라이브러리)로 연다.
2. RGBA로 변환한다. 투명 배경을 유지하기 위해서다.
3. 긴 변이 90픽셀을 넘으면 90픽셀로 줄인다. 화면에 45픽셀로 그리므로 고해상도 화면의 2배 밀도까지만 담는다.
4. WebP(PNG보다 같은 품질에서 파일이 작은 이미지 형식)로 다시 인코딩한다. 품질 88, 압축 강도 6을 쓴다.
5. WebP 바이트열을 base64(임의의 바이너리를 문자 64종으로만 표현하는 인코딩)로 바꾼다.
6. `data:image/webp;base64,<문자열>` 형태의 데이터 URL로 만들어 `src/platformIcons.js`에 객체 리터럴로 적는다.

화면에서는 `<img src={PLATFORM_ICON_DATA[key]}>`로 쓴다. 데이터 URL은 이미지 내용을 주소 안에 그대로 담으므로 브라우저가 서버에 요청을 보내지 않는다.

측정값은 이렇다. 원본 PNG 네 장 합계는 31킬로바이트, 변환 후 `src/platformIcons.js`는 13,453바이트다. WebP 변환으로 줄어든 양이 base64가 더한 약 33퍼센트 팽창분보다 크다. 이 13킬로바이트는 메인 번들(2026-09-21 배포본 229킬로바이트)에 포함되어 한 번만 내려간다.

브랜드 로고 168장에는 같은 방법을 쓰지 않는다. 이유는 다음 절에서 다룬다.

## 로고를 추가하면 번들 전체가 다시 내려가는가

절반은 그렇다. 서로 다른 층에 있는 두 해시를 구분해야 한다.

**로고 내용 해시(`?v=...`)는 전체 재다운로드를 일으키지 않는다.** 오히려 그 반대 목적으로 만들었다. 해시가 바뀐 로고 한 장만 새로 받고, 나머지 167장은 30일 캐시를 그대로 쓴다.

**번들 파일명 해시는 전체 재다운로드를 일으킨다.** `src/logoManifest.js`(5,951바이트)는 `src/logoSrc.js`가 import하고, Vite는 이 의존 관계를 따라 매니페스트를 메인 번들에 인라인한다. 로고 한 장을 추가하면 매니페스트에 한 줄이 늘고, 메인 번들의 내용이 바뀌고, 파일 이름의 해시가 바뀐다. `/assets/`는 `immutable`이지만 주소가 달라졌으므로 모든 방문자가 229킬로바이트짜리 새 번들을 받는다. 6킬로바이트 남짓을 고치려고 229킬로바이트를 버리는 셈이다.

지금은 이 비용을 감수한다. 근거는 두 가지다. 첫째, 로고 추가는 거의 항상 코드 변경과 같은 배포에 실린다. 그 배포가 어차피 번들을 갈아치우므로 추가 비용이 0이다. 둘째, 로고만 추가하는 배포를 따로 하지 않는다.

이 전제가 깨지면, 즉 로고만 바꾸는 배포가 잦아지면 분리할 값이 생긴다. 분리 방법은 매니페스트를 번들에서 빼서 `/logo-manifest.json` 같은 별도 정적 파일로 내보내고 `max-age=600` 정도를 주는 것이다. 비용은 방문마다 요청 한 번이 늘어난다는 점이고, 이득은 로고 추가가 번들을 무효화하지 않는다는 점이다. Edge Requests 한도가 다시 문제가 되는 상황에서는 이 교환이 손해일 수 있으므로, 바꾸기 전에 두 값을 실제로 재고 결정한다.

## 위험, 한계, 적용하면 안 되는 상황

### immutable

`immutable`은 회수할 수 없는 약속이다. 응답이 브라우저에 한 번 저장되면 `max-age` 동안 서버는 그 브라우저에 개입할 방법이 없다. Vercel 캐시를 비워도 소용없다. 사용자 브라우저 안의 사본이기 때문이다.

다음 경우에는 쓰지 않는다.

- 주소가 고정인데 내용이 바뀔 수 있는 자산. HTML, `/api/` 응답, 버전 표시가 없는 이미지가 여기 해당한다.
- 404가 정상적으로 발생할 수 있는 경로. 404 응답도 캐시 대상이다. 2026-09-11 빽다방 사례가 이 함정이다. 이 경로에 `immutable`을 유지하려면, 지금처럼 없는 자산은 요청조차 하지 않도록 매니페스트로 막아야 한다.
- 버전 토큰을 내용이 아니라 빌드 시각이나 커밋 해시에서 만드는 경우. 내용이 같아도 배포마다 주소가 바뀌어 캐시가 매번 무효화된다. 토큰은 반드시 파일 내용에서 파생해야 한다.

### base64 인라인

데이터 URL은 base64 때문에 원본보다 약 33퍼센트 커지고, 그만큼이 모든 방문자의 최초 다운로드에 더해진다. 대략의 손익 분기는 "요청 하나를 아끼는 값"과 "늘어난 바이트" 사이에 있다. 요청 하나의 값은 연결 수립과 헤더 왕복을 포함해 수백 바이트에서 1킬로바이트 남짓에 해당한다. 자산 하나가 10킬로바이트를 넘어가면 대부분 인라인이 손해다.

다음 경우에는 쓰지 않는다.

- 자산 수가 많은 경우. 브랜드 로고 168장, 3.6메가바이트를 인라인하면 첫 화면이 뜨기 전에 3.6메가바이트를 받아야 한다.
- 화면 밖에 있는 자산. 인라인하면 지연 로딩(`loading="lazy"`)이 무의미해진다. 번들은 보이든 안 보이든 전부 내려간다.
- 자주 바뀌는 자산. 자산이 바뀔 때마다 번들 해시가 바뀌어 번들 전체가 무효화된다.
- 개별 캐시 수명이 필요한 자산. 번들에 들어가는 순간 번들의 수명을 따른다.

부수 효과도 있다. 데이터 URL 이미지는 디코딩이 주 스레드에서 일어나고, 콘텐츠 보안 정책(CSP)을 쓴다면 `img-src`에 `data:`를 허용해야 하며, 번들 파싱 시간이 늘어난다. 13킬로바이트 규모에서는 무시할 수 있고, 메가바이트 규모에서는 무시할 수 없다.

### 10분 HTML과 must-revalidate

`must-revalidate`는 네트워크가 느리거나 끊긴 상황에서 오래된 HTML을 쓰는 것을 금지한다. 대안으로 `stale-while-revalidate`(만료된 사본을 먼저 보여주고 뒤에서 갱신하는 지시자)를 쓰면 체감 속도가 빨라지지만, 배포 직후 옛 HTML이 사라진 번들 주소를 가리켜 화면이 비는 위험이 생긴다. 지금 조합인 "HTML은 짧게, 해시가 붙은 자산은 영구"가 이 위험을 피하는 표준 구성이다.

### 매니페스트 방식의 한계

매니페스트는 빌드 시점의 스냅샷이다. 여기서 두 가지 운영상의 함정이 나온다.

- `public/logos/`에 파일을 올리고 빌드를 돌리지 않으면 화면에 나오지 않는다. `brandLogoSrc()`가 `null`을 돌려주기 때문이다. 로고를 추가하면 `npm run build`를 반드시 돌린다.
- 파일 이름 규칙(`logoFileName()`)이 어긋나면 파일이 있어도 매니페스트 키와 맞지 않아 조용히 사라진다. 공백과 특수문자는 밑줄로 치환한다. ADR-027이 이 규칙을 다루며, 2026-09-07에 실제로 로고가 안 나오는 사고가 있었다.

## 아직 손대지 않은 곳

API 서버(`bebeggars.duckdns.org`)의 `/api/brands` 응답에는 캐시 헤더도 압축도 없다. 2026-09-21 실측으로 응답 본문은 81,137바이트이고, `Accept-Encoding: gzip`을 보내도 같은 크기가 돌아온다. `Content-Encoding` 헤더가 없으므로 nginx(API 앞단의 웹 서버)에서 gzip이 꺼져 있다.

브랜드 목록은 방문자마다 매번 내려가는 가장 큰 단일 응답이다. nginx에서 gzip을 켜고 `ETag`(응답 내용의 지문. 내용이 그대로면 서버가 304를 돌려주어 본문 전송을 건너뛴다)를 붙이면 전송량이 크게 줄어든다. JSON은 반복이 많아 gzip 압축률이 보통 4배에서 5배 사이다. 적용 여부는 사용자 결정 대기 중이다.

## 정리된 규칙

새 자산을 추가할 때 다음 순서로 판단한다.

1. 주소에 내용 해시가 들어가는가. 들어가면 `/assets/`와 같이 1년 `immutable`.
2. 주소가 고정이고 내용이 바뀔 수 있는가. 그러면 짧은 `max-age`와 `must-revalidate`. HTML이 이 경우다.
3. 주소가 고정인데 긴 캐시를 주고 싶은가. 그러면 매니페스트로 버전 쿼리를 붙이고, 없는 자산은 요청하지 않도록 막는다. 로고가 이 경우다.
