# 혜택 칩: 네이버페이, 포장, 적립, 자사 행사 (설계)

2026-11-26. 사용자 요청: 네이버페이 전용 분류, 포장, 적립, 자사 행사 탭을 새 화면으로 설계한다. 이미 쓰던 네이버페이 현장결제 적립 배너 구조를 그대로 쓴다. 사용자는 이 설계를 질문 없이 자체 판단으로 진행하라고 했다. 그래서 승인 단계는 콜드 리뷰 서브에이전트가 대신한다.

## 1. 무엇을 풀려는가

- 지금 홈은 배달앱 할인을 견주는 화면이다. 매장에서 네이버페이로 결제하는 행사, 포장 전용 행사, 적립과 캐시백 행사, 브랜드 자체 앱의 행사도 오퍼로 서기는 한다(`BannerOffers`). 하지만 사용자가 그것만 모아 볼 길이 없다.
- 레퍼런스(2026-11-25 시작):
  - 더벤티: 네이버페이 QR 현장결제 50% 할인, 최대 1만 원, 하루 1회, 기간 중 3회.
  - 설빙: 네이버페이 포인트나 머니로 9,900원 이상 결제하면 50% 적립, 1인 최대 3만 원.
  - 네이버페이 공식 블로그 글은 가져오지 못했다.
- 성공 기준:
  - 홈의 칩 하나로 그 종류 오퍼만 남는다.
  - 칩마다 공유할 수 있는 주소가 있다.
  - 배달앱 "최고 할인" 비교 규칙은 그대로다.

## 2. 고른 길과 버린 길

| 길 | 내용 | 판단 |
|---|---|---|
| A. 특수 칩 확장 (채택) | `SPECIAL_CATEGORIES`(한정, 랜덤)에 네이버페이, 포장, 적립, 자사를 더한다. 주소 `?c=<키>`로 칩을 미리 고른 채 연다 | 이미 있는 거르기, 숨김, 정렬 경로를 그대로 탄다. 카드 그리기를 두 벌 두지 않는다 |
| B. 별도 페이지 `/naverpay/` | 사전 렌더된 새 경로에 행사 목록을 둔다 | 카드, 필터, 계측이 두 벌이 된다. 유입이 확인되면 A의 `?c=` 주소를 사전 렌더 경로로 감싸는 것으로 시작한다 |
| C. 홈 위 탭 줄 | 분류 줄 위에 "배달 / 현장 / 포장" 탭 줄을 새로 둔다 | 상단 바 실험(2026-09) 결론과 어긋나고, 360px에서 줄이 하나 더 생긴다 |

## 3. 칩 정의 (오퍼 단위, 앞에서부터 이 순서)

| 키 | 이름 | 고르는 값 | 비고 |
|---|---|---|---|
| `firstCome` | 한정 | `firstCome === true` | 지금 그대로 |
| `random` | 랜덤 | `certainty === 'random'` | 지금 그대로 |
| `naverpay` | 네이버페이 | `via === 'naverpay'` | 새 칸 `via` |
| `pickup` | 포장 | `channelOf(o) === '포장'` 또는 `channel === '포장'` | 원장은 구간 `channel`, 배너는 새 칸 `channel` |
| `reward` | 적립 | `kind`가 `cashback` 또는 `points` | 새 칸은 없다 |
| `own` | 자사 행사 | `platform === 'own'` | 새 칸은 없다 |

- 칩은 지금처럼 맞는 오퍼가 하나라도 있을 때만 보인다(`visibleCategories`). 오늘 해당 오퍼가 없는 칩은 사라진다. 골라 둔 칩은 오퍼가 줄어도 남는다.
- 메뉴 바는 칩을 하나만 고른다(`TopBarB.toggleCategory`). 새 칩도 같다.
- 칩 키는 `brand.category` 값과 겹치면 안 된다. `naverpay`, `pickup`, `reward`, `own`은 brands.yml 분류에 없다. 테스트로 박는다.

## 4. 서버 변경 (api)

- `Offer`에 칸 둘을 더한다.
  - `via`: String, 배너의 `via`를 그대로 싣는다. 원장 오퍼는 null이다.
  - `channel`: String, 배너 `spec.channel`을 싣는다("배달" 또는 "포장"). 원장 오퍼는 null이다. 원장의 포장은 지금처럼 구간 `channel`로 남는다.
- `OfferRecord` 빌더에 두 칸을 더하고 `BannerOffers.common`에서 채운다.
- 계약 `api/src/test/resources/contracts/offer-cases.json`: `offerKeys`와 모든 `cases[].offer`에 `via`, `channel`(null)을 더한다. tracker `contracts/offer-cases.json`은 바이트 동일 사본이라 tracker PR로 그대로 복사한다(CHANGE-PROPAGATION 11절).
- 신규 판정, 최고 할인 비교, 알림은 바꾸지 않는다. `via`와 `channel`은 표시와 거르기 전용이다.

## 5. 웹 변경 (web)

- `filters.js`:
  - `SPECIAL_CATEGORIES`와 `SPECIAL_MATCH`에 네 키를 더한다.
  - 칩 순서는 위 표 순서다.
- `App.jsx`:
  - 첫 렌더 뒤 `?c=naverpay`처럼 키 하나를 읽는다. 아는 특수 키일 때만 `filters.categories`에 넣는다.
  - 모르는 키는 버린다.
  - 서버 렌더는 기본 필터 그대로라 하이드레이션 어긋남이 없다(`homePhoto`와 같은 방식).
- `App.jsx`의 effect 하나가 `filters.categories`가 바뀔 때마다 `history.replaceState`로 `?c=`를 맞춘다. 분류를 비우는 길(뒤로 가기, 초기화, 검색, 시트)을 한 곳에서 받기 위해서다. 다른 검색 값과 해시는 남긴다. `?c=`로 들어오면 첫 뒤로 가기는 칩만 푼다(기존 `useBackClose` 동작).
- 계측: 칩 선택 이벤트는 기존 분류 칩 이벤트를 그대로 쓴다(키만 새것). 새 이벤트 이름은 없다.
- 카드 아이콘은 이번에 바꾸지 않는다. 칩으로 고른 화면에서 이미 네이버페이 행사만 남기 때문이다.
- 글자(COPY-STYLE): 칩 이름은 "네이버페이", "포장", "적립", "자사 행사"다. 360px에서 칩 줄은 가로 스크롤이라 넘쳐도 된다(`useScrollMore`).

## 6. 데이터 (운영 영향, 별도)

- 레퍼런스 두 행사는 배너로 들어가야 칩에 뜬다. 배너는 beggars-ops 운영 서버에 사람이 올린다. 그래서 이 PR에 넣지 않는다.
- 아래 두 줄을 보고에 따로 올려, 사용자가 ops 배너 화면에서 넣게 한다.
  - `theventi-npay-20261125`: brand 더벤티, platform own, via naverpay, amount `{percent: 50}`, cap 10,000원, note "하루 1회, 기간 3회, 매장 QR결제", 11-25 00:00 ~ 11-27 23:59:59.
  - `sulbing-npay-20261125`: brand 설빙, platform own, via naverpay, amount `{percent: 50, kind: points}`, minOrder 9,900원, note "1인 최대 3만 원 적립, 매장 결제만", 11-25 00:00 ~ 11-29 23:59:59.
- 더벤티, 설빙이 `brands.yml`에 없으면 그 등록은 직접 반영 핫픽스 대상이다(WORKFLOW 7절). 구현 때 확인한다.
- 자동 수집(브랜드 이벤트 페이지 크롤)은 이번 범위 밖이다. 링크 점검 방향(메모리 `project_offer_link_check_direction`)과 같이 따로 정한다.

## 7. 오류와 빈 상태

- `via`나 `channel` 칸이 없는 옛 응답에서는 해당 칩이 안 보인다. 맞는 오퍼가 0건이기 때문이다. 화면이 깨지지 않는다.
- `?c=`에 칩이 있는데 오늘 오퍼가 0건이면, 지금 골라 둔 칩 규칙대로 칩은 남고 빈 목록 안내가 뜬다. 안내는 기존 빈 상태 글자를 쓴다.
