# 배너 모델 재설계 요약

작성 2026-09-24. 2026-09-22 18:46에 시작해 2026-09-24 00:20에 운영 배포까지 끝난 작업의
한 장짜리 요약이다. 나중에 다시 볼 때 이 문서 하나만 읽으면 되도록 쓴다. 세부는 아래
"문서 지도"가 가리키는 네 문서에 있다.

## 배경

배너(웹 상단에 도는 행사 알림 띠)와 오퍼(브랜드 카드에 뜨는 개별 할인)가 서로 다른
모델을 쓰고 있었다. 같은 특정메뉴 쿠폰을 API는 비교 대상으로 올리고 웹은 내렸다. 규칙이
두 곳에 갈라져 적혀 있었던 탓이다. 배너의 `amount`는 문자열이라 금액을 비교할 수 없었고,
조건과 기간이 문구와 데이터 양쪽에 중복으로 들어가 서로 어긋났다.

## 무엇이 바뀌었나

**배너가 오퍼를 낳는다.** 배너 하나가 화면(screen)과 오퍼(offer) 양쪽으로 나간다. 배너에
`comparable`이 서면 그 배너는 브랜드 카드에 오퍼로도 선다.

**금액에 구조가 생겼다.** `BannerAmount`가 `won`(단일 또는 두 칸 범위), `percent`,
`kind`(discount, cashback, points), `random`, `capped`를 담는다. 문자열 파싱이 사라졌다.

**확실성 축이 생겼다.** `Certainty`는 exact, capped, random, menuOnly, percent 다섯이다.
최고 할인 후보는 `certainty == EXACT`이면서 비교 가능한 것만이다. 이 규칙은
`OfferComparison.java` 한 곳에만 있고 웹의 `filters.js`가 같은 판정표를 따른다. 판정표
30가지는 `docs/contracts/certainty-cases.json` 한 파일에서 Java 테스트와 JS 테스트가 함께
읽는다.

**유형과 자격이 분리됐다.** 적립은 `limit`이 아니라 `kind`다. 멤버십은 대상 자격이다.
선착순(`firstCome`)과 대상 한정(`targeted`)은 별도 칸이다.

**시각이 들어갔다.** 기간이 날짜가 아니라 `startsAt`, `endsAt` 시각이다. 마지막 날
포함 여부를 매번 틀리던 문제를 없앴다.

**묶음은 개발자가 정한다.** 같은 조건이어도 `group`으로 묶거나 떼어 놓을 수 있다. 백엔드는
그룹 값만 실어 보내고 웹이 묶어 그린다.

## 배포 뒤 확인

2026-09-24 운영 API 응답에서 `certainty` 분포는 exact 134, menuOnly 1, capped 2다.
훌랄라참숯바베큐치킨의 특정메뉴 12,100원은 비교액 4,999원으로 눌렸고, 백억커피 자사
적립 10,000원과 요편의점 최대 5,000원은 비교액이 비었다. 설계대로다.

`beggars-five.vercel.app`을 360px 폭으로 찍어 눈으로 확인했다. 청년피자 10,000원이 맨
위에 서고 특정메뉴 배너는 올라오지 않는다. 백억커피 배너에 `적립` 포스트잇이 붙어
있고, 칩 좌상단 배지 줄(5%할인, 배민클럽)이 기울어진 채로 한 줄에 선다. 사용자가
프리뷰에서 지적한 두 문제는 둘 다 사라졌다.

## 실패와 학습

**테스트가 초록인 것과 의도가 지켜지는 것은 다르다.** 운영에 영향을 줬을 결함 여덟 건이
전부 초록인 상태에서 나왔다. 자사 적립이 확정 할인으로 서서 최고 배지를 가져가는 것,
마지막 날 59초가 잘리는 것, 묶음 대표가 우선순위 아닌 id로 뽑히는 것이 그런 예다. 그
뒤로 검토 규칙에 "구현을 상수 반환 스텁으로 바꾸면 이 테스트가 실패하나"를 넣었다.

**규칙은 한 곳에만 적혀야 한다.** 이 재설계의 출발점이 규칙이 두 곳에 갈라진 것이었는데,
고치는 과정에서 같은 병을 세 번 새로 만들었다. 전부 Task 8 안에서다. `comparable(...)`을
함수로 뽑고 나서야 끝났다.

**숫자를 먼저 세면 계획이 바뀐다.** 배너 103장 중 95장이 만료였다. 일괄 변환은 사용자가
보는 것을 하나도 안 바꾸면서 문구만 어긋나게 할 위험이 있었다. 실제 API에 통과시켜
글자를 맞대니 123행 중 일치가 0건이었다. 2단계를 통째로 접었다.

**권위 있는 사본을 매번 확인해야 한다.** 브랜드 가드를 세 번 틀렸다. 오퍼
목록(`/api/brands`)을 봤다가, 낡은 소스 체크아웃을 봤다가, 도는 jar의 `brands.yml`에
정착했다. 그 사이에 반올림피자와 KFC 배너가 거부됐다.

**배포 순서가 기능이다.** API와 웹이 함께 움직여야 하는 변경에서 웹을 먼저 올리면
사용자에게 정렬 붕괴로 보인다. API 먼저, 확인 뒤 웹이다.

**기존 테스트의 픽스처를 고쳐 초록으로 만들면 안 된다.** 두 번 있었고 둘 다 되돌렸다.
회귀 신호를 지우는 일이다.

**확정 규칙을 한 파일로 모으니 반복이 줄었다.** `RULES.md`를 만들고 모든 구현자 지시문이
그것을 먼저 읽게 한 뒤로 같은 판정을 다시 설명할 일이 없어졌다.

## 남은 일

- **사소 지적 17건 분류.** `fromQualifier`가 모르는 값을 조용히 `EXACT`로 떨어뜨리는 것,
  `Banner.build()`가 `startsAt`과 `endsAt`을 둘 다 검사하지 않는 것, 네이버페이 아이콘과
  색이 빠진 것, `key={o.platform}` 중복 키, `EventBanner.jsx`의 `'own'` 문자열 상수화,
  `App.jsx:484` 최고 금액 계산식 중복이 대표적이다.
- **`banners.yml` 파일 자체의 id 유일성 검증이 없다.** 적용 시점 검사만 있어서 파일을
  손으로 고치면 안 걸린다.
- **`apply_edits`와 `apply_proposal`에 끝에서 끝까지 도는 테스트가 없다.** 배선이 끊어져도
  초록이다.
- **자사 오퍼의 `브랜드 자체` 라벨은 개발자 확정이 필요하다.** 새 노출 문구라 세션이
  정하지 않는다.
- **반올림피자 쿠팡이츠 최소주문 16,900원은 잠정값이다.**
- **옛 모양을 쓰는 길만 지운다.** 만료 배너 95장이 옛 모양으로 남기로 했으므로 읽는
  길은 남는다. 원래 Task 19였던 "옛 모양 읽기 제거"는 폐기했다.
