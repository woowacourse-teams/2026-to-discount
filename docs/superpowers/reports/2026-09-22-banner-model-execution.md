# 배너 모델 재설계 실행 보고

작성 2026-09-22. 대상 브랜치 `feat/banner-model`. 계획 문서
`docs/superpowers/plans/2026-09-22-banner-model.md`, 설계 문서
`docs/superpowers/specs/2026-09-22-banner-model-design.md`.

## 배경

배너(웹 상단에 뜨는 당일 행사 카드)의 데이터 모양을 바꾼다. 배너 한 건을 브랜드
하나로 고정하고, 묶음을 `group` 칸으로 명시하고, `qualifier` 한 칸이 겸하던 세 질문을
`certainty`와 `kind`로 가른다. 작업 19개를 다섯 단계로 나눴다.

실행 방식은 작업마다 새 하위 에이전트를 붙이고, 그 결과를 다른 에이전트가 검토하고,
지적이 남으면 고치고 다시 검토하는 반복이다. 이 문서는 그 과정에서 무엇이 나왔는지
남긴다. 코드가 어떻게 생겼는지는 git 기록이 말하므로 여기서는 검토가 무엇을 잡았고
왜 그렇게 정했는지만 적는다.

## 격리

운영에 닿는 경로가 없다. 작업은 별도 작업트리의 `feat/banner-model` 브랜치에서만
돌고, 이 브랜치는 원격에 없으며 추적 브랜치도 없다. 배포 미러
(`.github/workflows/mirror-deploy-repos.yml`)는 `main` 푸시에서만 도므로
`nn98/delivery-discount-api`도 `nn98/delivery-discount-web`도 움직이지 않는다.
구현자와 검토자 지시문에는 푸시 금지와 작업 디렉터리 고정을 매번 넣는다.

## 선행 충돌 점검

작업을 시작하기 전에 계획 19개를 서로 맞대어 봤다. 공유 파일과 인터페이스마다 한 줄씩
확인했고 세 가지가 나왔다.

### 계획대로 하면 API가 네 작업 동안 컴파일되지 않는다

Task 5가 `BannerSpec`에서 `items`와 `amountRange`를 지우는데, 그 둘을 읽는
`Banner.brandAmounts()`와 `Banner.compoundTiers()`를 고치는 작업이 계획 3,419줄
어디에도 없었다. 그대로 하면 Task 5부터 Task 8까지 빌드가 깨져서 작업마다 테스트를
돌리고 커밋한다는 규칙 자체가 성립하지 않는다.

조치: 두 칸의 삭제를 Task 19(정리)로 옮겼다. Task 19가 이미 옛 모양 읽기를 지우는
작업이라 제자리다. 이 판정을 Task 4, 5, 6, 7, 8 지시문에 매번 넣어 구현자가 계획
본문을 따라 지우지 않게 했다.

### Task 16이 받는 값을 Task 15가 안 적었다

`OWN` 상수를 Task 15의 코드가 만들지만 인터페이스 칸에 빠져 있었다. 구현에는 영향이
없어 계획 본문은 두고 Task 15 지시문에 명시하기로 했다.

### 전역 제약이 없는 작업을 가리킨다

웹 작업 순서를 PlatformBadge, 플랫폼 필터, 묶음 렌더로 못박았는데 4단계에 묶음 렌더
작업이 없다. 서버가 묶음을 접어 한 장으로 내려보내므로 웹이 묶을 일이 없다. 구속력
있는 것은 `PlatformBadge`가 플랫폼 필터보다 먼저라는 것 하나뿐이다. 어기면 배포 즉시
흰 화면이 된다.

## 작업별 기록

### Task 1. 확실성과 종류 열거값

초기: `Certainty`(다섯 값)와 `AmountKind`(세 값)를 만들고 옛 `qualifier`에서 오는
대응을 붙인다.

결과: 커밋 `d75cded`. 테스트 4건.

검토: 스펙 통과, 품질 승인. 지적 없음.

문제: 없음. 다만 `schema.py`의 허용 목록이 늘어나면 `fromQualifier`가 새 값을 조용히
`EXACT`로 떨어뜨리는데 잡아낼 테스트가 없다는 관찰이 남았다.

조치: 계획이 지시한 동작이라 그대로 두고 지연 항목으로 기록했다.

### Task 2. 비교 규칙과 판정표

초기: 최고 후보인가와 정렬에 얼마로 기여하나를 한 곳에 모으고, 웹과 API가 같이 읽는
판정표 `docs/contracts/certainty-cases.json`을 만든다.

결과: 커밋 `6efde9a`에서 시작해 수정 네 번을 거쳐 `30de933`.

**1회차. 판정표가 30가지 중 8가지만 덮었다.** 계획이 8줄짜리 JSON을 그대로 지시했다.
이 파일에 맡긴 일이 웹과 API가 다시 어긋나는 것을 막는다인데, 그 둘은 이미 한 번
어긋나 있다. 웹은 특정메뉴 쿠폰을 정렬에서 빼고 API는 4,999원으로 눌러 남긴다.
22가지를 안 적은 표는 다음 어긋남을 못 잡는다. 표를 30가지로 채우게 했다.

**2회차. 표를 채웠더니 표를 지키는 것이 없었다.** 테스트가 `cases.size() >= 8`로
세고 있어서 30줄을 요구해놓고 22줄을 지워도 통과했다. 열거값 곱집합으로 기대 집합을
만들어 실제 집합과 비교하게 했다. `assertEquals(30, ...)`보다 낫다. 중복 한 줄과 누락
한 줄이 상쇄되는 것을 잡고, 나중에 값이 하나 늘면 스스로 따라간다.

**3회차. gradle이 표를 테스트 입력으로 안 봤다.** JSON만 고치면 `./gradlew test`가
UP-TO-DATE로 건너뛰었다. 플래그를 기억해야 도는 가드는 가드가 아니다.
`api/build.gradle`에 입력으로 선언하게 했다.

**4회차. 그 선언이 운영 배포를 멈출 결함을 드러냈다.** 미러가 `api/`를
`nn98/delivery-discount-api`의 루트로 밀고, 그 저장소에는 `docs/`가 없다. 저장소 밖을
가리키는 입력에 하드 실패가 나서 `test` 태스크가 통째로 죽고, 그 저장소의 배포가
`./gradlew build`로 테스트까지 돌리므로 API 배포가 멈춘다. 선언을 고쳐도 테스트가
런타임에 같은 경로를 읽어 또 실패한다.

판정: 파일이 없으면 판정표 테스트만 건너뛴다. 강제는 mono 저장소의 CI가 한다. 미러는
배포 전용이고, 웹과 API가 한 저장소에 같이 있는 곳은 mono뿐이라 어긋남은 거기서만
생긴다. 확인은 `docs`를 잠시 치우고 전체 빌드를 돌려서 했다. 빌드 성공, 판정표 테스트
2건만 건너뜀, 나머지 37개 스위트 실패 0.

### Task 3. 배너 금액 한 덩이

초기: 문자열, 숫자 목록, 범위 세 모양이던 금액을 `BannerAmount` 한 record로 접는다.

결과: 커밋 `4b93992`, 수정 한 번을 거쳐 `20c89f9`. 테스트 7건에서 11건으로.

검토: 스펙 통과. 품질에서 조용히 틀린 값을 통과시키는 구멍 둘이 나왔다.

문제: `banners.yml`은 운영 서버에서 사람이 손으로 고치고 재배포 없이 반영되는 파일이다.
이 record가 말없이 받아들이는 값이 그대로 화면의 가격이 된다.

- `{won: [5000, null], percent: 30}`이 통과했다. 생성자가 `wonMax`와 `percent`만 보는데
  상한이 열린 범위라 `wonMax`가 null이다. won이든 percent든 하나만이라는 불변식을
  생성자가 스스로 안 지켰다.
- 음수를 검사하지 않았다. `{won: -5000}`이 그대로 들어가 음수 할인이 된다.

방어 분기가 테스트 없이 나간 것이 둘을 안 보이게 했다.

조치: percent는 어떤 won 값과도 같이 못 서게 하고, 세 칸 모두 음수를 거부하되 메시지에
칸 이름과 값을 적게 했다. 잘못된 모양 아홉 가지를 테스트로 덮었다. `{won: 0}`은 허용으로
갔다. 0은 음수가 아니고 0원 배너가 뜻이 있는지는 콘솔이 판단할 일이다.

### Task 4. 배너 새 칸, 날짜에서 시각으로

초기: `Banner`에 `group`, `via`, `amountSpec`, `targeted`, `firstCome`, `untilSoldOut`을
더하고 `startsOn`, `endsOn`을 `startsAt`, `endsAt` 시각으로 옮긴다.

결과: 커밋 `06b6dd0`, 수정 한 번을 거쳐 `e4c0809`.

검토: 스펙 통과. Important 하나.

문제: 마지막 날 59초가 잘렸다. 날짜 편의 메서드가 `23:59`로 채워서 23:59:01부터 만료로
쳤는데, 옛 날짜 비교는 그날 23:59:59까지 살아 있었다. 날짜를 시각으로 옮긴 이유가
그날 포함인지를 없애는 것이었는데 더 작은 오차를 새로 만든 셈이다.

조치: `23:59:59`로 채우게 했다. 끝을 배타로 바꾸는 방법도 있었지만 승인된 설계가
`T23:59`를 그날 끝으로 못박아서 그 뜻을 바꾸지 않는 쪽을 골랐다. 23:59:30, 23:59:59,
다음날 00:00 경계를 테스트로 덮었다. Task 11의 변환기도 같은 값을 써야 해서 원장에
넘겼다.

구현자가 브리프와 부딪힌 지점도 하나 있었다. 브리프가 `activeOn(LocalDate)` 삭제를
지시했는데 그러면 `BannerCatalog`가 깨진다. 살려두고 본문만 새 접근자로 다시 써서
`BannerCatalog`와 `BrandComparisonService`가 손대지 않고도 컴파일된다.

### Task 5. 구조 칸에서 문구 만들기

초기: 화면에 나가는 `amount`, `period`, `extra`와 오퍼의 조건 줄을 구조 칸에서 만든다.
생성된 문구는 사람이 손으로 적던 문구와 글자까지 같아야 한다. 나중에 살아 있는 파일을
변환할 때 그 일치가 유일한 안전장치다.

결과: 커밋 `33429b5`. 테스트 8건. 수정 없이 통과.

검토: 스펙 통과, 품질 승인. 지적 셋은 전부 사소 등급이다.

- `BannerText.amount(null)`은 `BannerSpec` 판과 `BannerAmount` 판 사이에서 모호해
  컴파일되지 않는다. 지금 호출부는 전부 타입이 있어 무해하지만 뒤 작업이 밟을 수 있다.
- 문구 길이 상한을 `BannerText`가 막지 않는다. 옛 경로도 같아서 회귀는 아니고 강제는
  `ops_apply.py`가 한다.
- 옛 경로와 새 경로가 같은 입력에 같은 문구를 내는지 견주는 테스트가 없다. Task 19가 옛
  경로를 지울 때까지 조용히 갈라질 수 있다.

조치: 셋 다 지연 항목으로 기록하고 최종 검토에서 다시 보기로 했다.

### Task 6. 두 모양 읽기와 묶음 접기

초기: `BannerCatalog`가 옛 모양과 새 모양을 둘 다 읽고, 같은 `group` 값을 가진 배너를 한
장으로 접는다.

결과: 커밋 `6bd3eaf`, 수정 한 번을 거쳐 `437a8a7`. 묶음 테스트 8건, 전체 295건.

구현자가 스스로 우려 셋을 달아 올렸고 검토가 셋 다 정당하다고 확인했다.

- 다섯 칸짜리 `BannerSpec`이 `limit`을 안 실어서 `BrandComparisonService.isRandom()`의
  `spec().limit()` 분기가 죽었다. 구현자가 테스트 픽스처에 `extra: 랜덤`을 넣어 초록으로
  만든 것은 정당한 적응이지만, `limit: random`만 적고 문구에 랜덤이 없는 배너는 Task 8이
  새 칸을 물릴 때까지 랜덤 표식을 잃는다. Task 8에 넘겼다.
- 새 `thenComparing(Banner::id)` 동점 처리는 묶음 접기를 결정적으로 만들기 위해 필요하다.
- `BrandCatalog`를 빈 자원으로 만든 것은 다른 배너 테스트들과 같은 방식이다.

문제: 묶음 카드의 대표가 우선순위가 아니라 id로 뽑혔다. `activeMembers()`가 구성원
전원의 `priority`를 묶음 최솟값으로 덮은 뒤 정렬하므로 묶음 안에서는 우선순위가 항상
동점이고, 정렬이 `endsAt`을 거쳐 `id`로 떨어진다. 카드의 금액, 링크, 최소주문, 색을 대는
대표가 id 문자열 순서로 정해졌다. 테스트가 못 잡은 이유는 픽스처에서 두 순서가 우연히
같아서다.

조치: 대표를 우선순위 덮어쓰기 전의 원래 값에서 뽑게 했다. 화면 정렬용 덮어쓰기는
그대로 둔다. id 순서와 우선순위 순서를 일부러 엇갈린 테스트를 추가해, 되돌리면 실패하는
것까지 확인했다.

재검토가 기존 구멍 하나를 더 짚었다. `banners.yml`의 id 유일성을 아무 데서도 검사하지
않는다. 같은 id가 둘이면 대표의 우선순위가 파일 순서에 달린다. 이번 회귀가 아니라
Task 13(적용 시점 검사)으로 넘겼다.

### Task 7. 오퍼가 확실성과 종류를 싣는다

초기: `Offer`에 `certainty`와 `kind`를 더한다. 원장(`data/log.jsonl`)은 안 고치고 읽을 때
`qualifier`에서 끌어낸다.

결과: 커밋 `604f3c3`. 테스트 3건, 전체 298건. 수정 없이 통과.

검토: 스펙 통과, 품질 승인, 지적 0. 검토자가 원장 옛 행 처리를 코드에서 직접 확인했다.
`qualifier`가 null이든 빈 문자열이든 공백이든 모르는 값이든 전부 `EXACT`로 떨어지고
예외 경로가 없다. 두 병합 지점의 19개 필드를 선언 순서와 하나씩 맞대어 누락과 뒤바뀜이
없는 것도 확인했다.

## 검토를 더 세게 하기로 한 이유와 방법

여기까지 검토가 실제로 잡은 것들이 한 결이다. 판정표 8/30, 59초 만료, 묶음 대표가 id로
뽑히는 것. 셋 다 테스트는 초록인데 의도가 안 지켜진 경우이고, 셋 다 픽스처가 우연히
맞아떨어져 안 보였다.

2026-09-22 23:26 사용자 지시로 Task 8부터 검토자 지시문에 여섯 가지를 매번 넣는다.

1. 구현자 보고를 근거로 쓰지 않는다. 모든 주장을 코드에서 다시 확인하고 파일과 줄을 댄다.
   보고와 코드가 어긋나면 그 자체가 지적이다.
2. 요구사항마다 깨뜨릴 방법을 먼저 찾는다. 깨뜨리는 입력을 구체적으로 적고 코드로
   추적한다. 못 깨뜨렸으면 그렇게 적는다.
3. 테스트마다 구현을 상수 반환 스텁으로 바꿔도 통과하는지 묻는다. 통과하면 지적이다.
4. 새로 만든 분기마다 그것을 타는 테스트가 있는지 센다.
5. 바뀐 함수의 호출부를 전부 찾아 다른 자리에서 뜻이 달라지지 않는지 본다.
6. 틀렸을 때 화면에 무엇이 잘못 뜨는지 한 줄로 적는다.
