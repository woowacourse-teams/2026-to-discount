# 사용자 이벤트 분석 — 가설, 적용, 관찰

> 받은 피드백: *"이벤트 분석 도구 도입만으로 기술적 요구사항을 충족했다고 보기 어렵다. 어떤 도구를 도입할지 조사한 내용만 있고 기술적 활동은 없어 보인다."*
>
> **맞는 지적이다.** 앞선 문서는 "PostHog를 골랐다"까지였다. 도구 선정은 조사지 기술 활동이 아니고, 무엇보다 *적용 전 상태*와 *기대 결과*가 없었다.

**이 문서의 주장**: 데이터를 *모으는* 문제는 도구가 풀어준다. 모인 데이터에서 *믿을 수 있는 신호를 뽑는* 문제는 도구가 풀어주지 않는다. 그쪽에 든 공학과, 세운 가설 중 무엇이 맞고 무엇이 틀렸는지가 내용이다.

**서비스 소개** — 배달의민족·쿠팡이츠·요기요·땡겨요 네 앱의 브랜드 할인을 한 화면에서 견주는 페이지. 로그인이 없고, 사용자는 카드를 보고 앱 딥링크로 나간다. 그래서 **전환 = 링크 이동(`offer_link_click`)**이고, 그 뒤는 우리가 볼 수 없다.

---

## 1. 적용 전 상태

### 1.1 처음에 있던 것

```
브라우저                          서버
────────                        ─────
analytics.js  ──POST /api/events──▶  EventController ──▶ events.jsonl
  이벤트 이름과 몇 개 속성                받은 것을 적는다
```

이벤트를 파일에 쌓기만 했다. **쌓인 것을 읽는 방법은 그때그때 `jq` 한 줄**이었다. 질문이 생길 때마다 셸 파이프를 새로 조립했고, 그 파이프는 세션이 끝나면 사라졌다.

### 1.2 그래서 겪은 문제

| # | 문제 | 어떻게 드러났나 |
|---|---|---|
| P1 | 프론트가 보내는 이벤트를 서버가 조용히 버렸다 | 필터 시트·담아보기 이벤트 **6종**이 서버 화이트리스트에 없어 전량 폐기. A/B가 답하려던 질문이 그 이벤트에 걸려 있었다 |
| P2 | 이벤트 속성이 말없이 잘렸다 | 속성 상한이 6개인데 필터 맥락이 4~6개를 먼저 먹어, 배너의 `position`이 밀려 유실 |
| P3 | 이벤트 유실 | `page_exit`은 브라우저가 닫히는 순간 보낸다. 실패하면 그걸로 끝, 재시도할 데가 없었다 |
| P4 | 개발자 트래픽이 실사용자에 섞였다 | 방문자 43명 중 **8명(19%)**이 표시 없는 개발 트래픽 |
| P5 | 소수가 지표를 통째로 흔들었다 | "1인당 링크이동"으로 b안이 2배 나은 것처럼 보였다 |
| P6 | 판단을 수집 시점에 굳혀 되돌릴 수 없었다 | 개발 트래픽 추정 규칙이 틀렸는데 이미 그 속성으로 SaaS에 나갔다 |
| P7 | 같은 판정이 세 곳에 복사돼 있었다 | Java·JS·셸 스크립트. 도구마다 다른 숫자가 나왔다 |

## 2. 가설 — 무엇이 어떤 변화를 만들 것이라 예상했나

적용 전에 넷을 세웠다. **둘은 실측이 뒤집었다.** 뒤집힌 과정이 이 문서에서 가장 값이 나간 부분이다.

| 가설 | 예상한 변화 | 결과 |
|---|---|---|
| **H1 유실** — 전송·수집을 PostHog 단독 책임으로 고정하면 유실이 준다 | 경로가 하나면 실패 지점도 하나 | ❌ **반증** |
| **H2 중복** — 단독 책임으로 고정하면 중복이 없다 | 경로가 하나면 같은 이벤트가 두 번 들어올 수 없다 | ⚠️ **부분 성립** |
| **H3 개발 트래픽** — 개발자 플래그 + 서버사이드 필터로 걸러낸다 | 지표에서 우리가 빠진다 | ⚠️ **부분 성립** |
| **H4 사용자 편향** — 고유 식별자로 이상행동을 식별해 배제·한정한다 | 소수가 지표를 흔드는 것을 막는다 | ✅ **성립** |

각 가설의 검증은 §4에서 수치와 함께 적는다.

## 3. 적용 — 기존 방식, 한 일, 달라진 것

### 3.1 이벤트 계약을 코드가 지키게 (P1, P2)

**기존 방식.** 서버는 공개 쓰기 엔드포인트라 아무 이벤트나 받으면 안 된다. 그래서 이름 화이트리스트를 뒀다. 문제는 **프론트에 새 이벤트를 추가할 때 서버 목록에 넣는 걸 사람이 기억해야 했다**는 것이다. 잊으면 에러가 아니라 **조용한 폐기**다. 프론트는 200을 받고, 원장에는 아무것도 안 남는다.

실제로 필터 바텀시트와 담아보기 화면을 올린 뒤 여섯 종(`filters_apply`, `filter_sheet_open`, `cart_toggle`, `cart_view_toggle`, `cart_clear`, `membership_toggle`)이 그렇게 사라지고 있었다.

**한 일.** 프론트 소스에서 `track('...')` 호출을 정적 추출해 서버 화이트리스트와 대조하는 검사를 `npm test`에 넣었다.

```js
// web/scripts/verify-analytics-event-contract.mjs
// 소스를 정규식으로 훑어 정적 호출을 뽑고, EventController.java의
// ALLOWED_EVENTS와 양방향으로 맞춘다 — 한쪽에만 있으면 실패한다.
const staticCalls = [...contents.matchAll(/\btrack\s*\(\s*(['"])([^'"]+)\1/g)]
```

속성 상한은 원인이 **순서**였다. 필터 맥락 6종(`fCategory` `fPlatforms` `fSearch` `fCart` `fSaved` `fSort`)이 이벤트 자기 값보다 앞에 붙어 상한을 먼저 먹었다. 순서를 뒤집고 상한을 8로 올렸다 — 넘치면 맥락이 먼저 떨어지도록.

```js
// web/src/analytics.js — 이벤트 고유 값이 먼저다. 서버가 앞에서부터 세어 자른다
props: { ...props, ...filterContext }
```

**달라진 것.**

| | 전 | 후 |
|---|---|---|
| 서버가 받는 이벤트 | 13종 (6종 폐기 중) | **19종** |
| 배너 `position` | 상한에 잘려 유실 | 보존 |
| 새 이벤트 추가 시 | 사람이 두 곳을 기억 | 잊으면 **CI가 실패** |

이 검사는 이후에도 값을 했다. 검색 제출 이벤트(`brand_search_submitted`)를 추가한 PR에서 서버 목록 갱신이 빠졌다면 머지 전에 걸렸을 것이고, 실제로 그 PR은 두 곳을 같이 고쳤다.

### 3.2 전달 실패를 견디는 큐 (P3, H1)

**기존 방식.** 브라우저가 이벤트를 서버로 보내고, 서버가 PostHog로 넘긴다. 넘기다 실패하면 그 이벤트는 없어진다. 특히 `page_exit`은 탭이 닫히는 순간이라 재시도할 브라우저가 이미 없다.

**한 일.** 두 층에서 막았다.

*브라우저 층* — `page_exit`은 `navigator.sendBeacon`으로 보낸다. 비콘은 프리플라이트를 못 하므로 `text/plain`으로 와야 하고, 그래서 서버가 **같은 엔드포인트로 json과 text/plain을 둘 다 받게** 했다(`application/json`이면 프리플라이트가 걸려 조용히 유실된다).

*서버 층* — PostHog 전달을 파일 기반 outbox로 만들었다.

```
PostHogOutbox              enqueue → 임시파일에 쓰고 원자적 move
                           실패하면 재시도 카운트 올리고 큐에 남김
                           누적 실패 → dead-letter 디렉터리로
                           역직렬화 실패 → 격리(quarantine), 큐 전체를 막지 않음
PostHogForwardingWorker     주기적으로 배출
```

**달라진 것.** PostHog가 잠깐 죽어도 이벤트는 디스크에 남아 있다가 나중에 나간다. 그리고 **PostHog로 못 보낸 이벤트도 원장에는 이미 적혀 있다** — 이게 H1을 뒤집은 지점이다(§4.1).

### 3.3 원장을 권위 있는 기록으로, SDK는 그 위에 (P6)

**기존 방식(그리고 H1·H2가 제안한 방식).** 브라우저 → PostHog 직송. 저장·조회·대시보드를 전부 SaaS에 맡긴다. 서버가 할 일이 없어 단순하다.

**한 일.** 모든 제품 이벤트를 **한 번 만들어 두 곳으로 부친다.** 같은 객체, 같은 `eventId`다.

```js
// web/src/analytics.js — 이벤트 하나가 서버 큐와 PostHog로 동시에 간다
function enqueue(event, scheduleFlush = true) {
  queue.push(event)          // → POST /api/events → events.jsonl
  fanOutToPostHog(event)     // → PostHog SDK 직송
  ...
}
```

#### SSOT는 "유일한 저장소"가 아니라 "충돌하면 이기는 쪽"이다

SDK 값을 버리지 않는다. 그래서 "원장이 SSOT"라는 말에는 **범위**가 붙어야 한다.

> **원장은 "우리가 정의한 제품 이벤트 19종"에 대한 권위 있는 기록이다.**
> 그 범위 안에서 숫자가 갈리면 원장이 이긴다. 범위 밖은 원장에 아예 없다.

원장이 권위를 갖는 근거는 "더 많이 갖고 있어서"가 아니라 **원본이 변형 없이 남아 재계산이 되기 때문**이다. 서버는 받은 것을 그대로 적고 아무 판단도 굳히지 않는다. PostHog로 나가는 값은 매퍼를 통과하며 이미 해석이 섞인다(이벤트 이름 변환, 속성 선별, dev 제외).

#### 두 저장소가 실제로 갖는 것

| | 원장 `events.jsonl` | PostHog |
|---|---|---|
| 제품 이벤트 19종 | 전부 (dev 포함) | dev 제외분만 |
| `$web_vitals` (성능) | **없음** | 있음 (SDK 자동) |
| `$pageleave` | **없음** | 있음 (SDK 자동) |
| 세션 결합·person 프로필 | 없음 (`sessionId` 원값만) | 있음 |
| 원본 재계산 | 가능 | 불가 (보낸 시점 속성이 박힘) |
| 리텐션·퍼널 UI | 없음 (`experiments.py`로 계산) | 있음 |

**완전한 상위집합은 아니다.** 원장에만 있는 것(dev 트래픽, PostHog 전달이 끝내 실패한 이벤트)이 있고, PostHog에만 있는 것(SDK 자동 계측, 그리고 서버 배치 flush 전에 탭이 죽어 원장에 못 닿은 이벤트)도 있다. 그래서 "원장이 전부를 갖는다"가 아니라 **"겹치는 범위에서 원장이 권위를 갖는다"**가 정확한 표현이다.

#### 그래서 SDK는 무슨 역할인가

셋이다. 전부 원장이 원리적으로 못 하는 일이다.

**① 우리가 안 만든 계측** — `$web_vitals`, `$pageleave`. 성능 신호는 브라우저 API를 SDK가 대신 읽어준다. 직접 만들 수 있지만 만들 이유가 없다.
```
autocapture: false            임의 클릭은 안 받는다 — 계약에 없는 이벤트가 섞이면
                              화이트리스트를 둔 의미가 없어진다
capture_performance: web_vitals   성능만 받는다
```

**② 질문을 아직 모를 때의 탐색 인터페이스** — `experiments.py`는 **미리 정의한 질문**만 답한다(`compare`, `funnel`, `paths`…). 리텐션 코호트를 처음 보고 싶을 때 PostHog는 클릭 몇 번이고, 우리 도구는 코드를 새로 써야 한다. 실제로 리텐션은 PostHog 인사이트로 먼저 봤고, 거기서 이상하다 싶은 지점을 원장으로 다시 계산해 확정했다.

**③ 세션·프로필 결합** — SDK가 세션을 묶고 person을 관리한다. 원장은 `visitorId`·`sessionId` 원값만 갖는다.

#### 역할이 갈리는 지점 한 줄

```
탐색은 PostHog에서, 판정은 원장에서.
```

PostHog에서 "여기 뭔가 있다"를 찾고, 결론으로 발표할 숫자는 원장으로 다시 낸다. §4.1이 왜 그래야 하는지를 보여준다.

#### 이중 경로의 대가

경로가 둘이라 **중복 제거가 필요해진다.** `eventId`(클라이언트가 만든 UUID)를 PostHog `$insert_id`로 이어 붙였다. 유효한 UUID면 재전송에도 유지하고, 구버전·잘못된 값만 서버가 보완한다.

```java
// EventController.eventId() — 36자 UUID면 그대로, 아니면 서버가 새로 발급
if (parsed.toString().equalsIgnoreCase(candidate)) return candidate;
```

### 3.4 개발 트래픽 판별 (P4, H3)

**기존 방식.** 두 겹으로 걸렀다.

1. `?dev=1`을 연 브라우저에 `localStorage.dk_dev`를 심고, 그 브라우저의 이벤트에 `dev: true`를 붙인다.
2. 표시가 빠진 것을 잡으려고 **서버가 이벤트를 넘길 때** `device == "desktop" AND 뷰포트 폭 < 400px`이면 `dev_suspect: true`를 붙인다. 데스크톱 브라우저 창을 좁혀 놓은 것 = 반응형 확인이라는 추론이었다.

1번이 필요한 이유는 실측이 있다 — 방문자 43명 중 8명(19%)이 표시 없는 개발 트래픽이었다. `localStorage`는 브라우저·프로필·시크릿창마다 별개라 기기가 여럿이면 일부만 걸린다.

**한 일 — 그리고 2번이 틀렸다는 것을 찾아낸 과정.**

이상 신호는 이거였다: **걸러낸 무리의 전환율이 남긴 쪽보다 높다.**

```
dev_suspect로 걸러낸 365명   전환율 41.9%
남긴 쪽                      전환율 33.9%
```

개발자가 실사용자보다 링크를 더 많이 누를 이유가 없다. 원장으로 직접 파고들었다.

```
걸러낸 무리의 폭 분포   384(3203)  360(1337)  368(133)  320(83)   전부 안드로이드 폰 폭
걸러낸 무리의 93%       세션 내내 폭이 하나:  [384]  또는  [360]
진짜 개발자(dev=true)   [390,1280]  [849,1283]  [1309,1554,1745,1862]  ← 창을 조절한다
```

원인은 `device` 판정이 `matchMedia('(hover: hover)')`라는 것이었다. **일부 안드로이드 브라우저가 `hover: hover`를 보고한다.** 그래서 폰이 desktop으로 잡히고, 폰 폭은 당연히 400 미만이라 규칙에 걸렸다.

새 규칙: **한 세션 안에서 뷰포트 폭이 여러 개이고 그중 최대가 800px 이상이면 개발자.** 창을 조절해 가며 본 흔적이다. 폰은 세션 내내 폭이 하나다.

여기서 중요한 건 규칙 자체가 아니라 **판정을 어디서 하느냐**다. 새 규칙은 한 사람의 이벤트를 전부 모아야 내릴 수 있다 — 이벤트 하나만 보는 서버·브라우저에서는 **원리적으로 불가능하다.** 그래서 추정을 수집 경로에서 **걷어내고** 집계 한 곳으로 옮겼다.

```java
// PostHogEventMapper — 판정 로직을 지우고 이유를 남겼다
/* 개발 트래픽 추정은 여기서 하지 않는다. (…) 세션 전체를 봐야 갈린다.
   이벤트 하나만 보는 여기서는 알 수 없는 판단이라 원장을 통째로 읽는
   scripts/experiments.py 한 곳에만 둔다. */
```

**달라진 것.**

| | 전 | 후 |
|---|---|---|
| 개발자로 판정 | 2,496명 중 455명 | 2,531명 중 **93명** |
| 그중 오탐 | **368명 (안드로이드 폰 사용자)** | 0 |
| 판정 위치 | 수집 시점(되돌릴 수 없음) | 집계 시점(다시 셀 수 있음) |
| 규칙 사본 | 3곳 (Java·JS·셸) | **1곳** |

### 3.5 분석 도구를 직접 만듦 (P5, P7, H4)

**기존 방식.** 질문이 생기면 `jq` 파이프를 조립했다. 문제가 셋이었다 — 파이프가 사라진다, 판정 규칙이 스크립트마다 다시 적힌다, 그리고 **통계가 없다.** "a가 33%, b가 38%"까지는 나오는데 그게 우연인지 아닌지를 말할 방법이 없었다.

**한 일.** `scripts/experiments.py` — 원장을 방문자 단위로 접고 질문별 명령을 둔다.

| 명령 | 답하는 질문 |
|---|---|
| `audit` | 개발 트래픽 판정이 사람을 잡아먹고 있지 않나 |
| `features` | 어떤 기능이 쓰이고 어떤 게 죽었나 (침투율 + 최근 7일 + 수명) |
| `compare --by` | 갈래별 차이가 우연인가 (variant / 신규·재방문 / 폭 / 유입 / 기간) |
| `funnel` | 어디서 새는가 (**시각순**, 세션 범위) |
| `paths` | 실제로 밟은 순서는 무엇인가 |
| `power` | 이 차이를 증명하려면 몇 명이 필요한가 |
| `top` | 어떤 브랜드·배너·위치가 먹혔나 |

통계는 직접 구현했다.

- **두 비율 z검정** — 차이가 우연일 확률
- **Wilson 신뢰구간** — 정규근사는 0%/100%에서 폭이 0이 된다. 표본이 두 자릿수인 갈래가 흔해서 필요했다
- **검정력 기반 표본 크기** — "몇 명 더 모아야 하나"

`--selftest`가 계산을 고정한다(z값, Wilson 경계, 퍼널 순서 역전, 중복 접기).

**집계 단위를 방문자로 못박은 것이 H4의 구현이다.** 한 사람이 몇 번 누르든 1로 센다. `visitorId`가 고유 식별자 역할을 하고, 헤비 유저 한 명이 갈래 지표를 통째로 들어올리는 것을 구조적으로 막는다.

### 3.6 A/B 실행 기반

**기존 방식.** 없었다. 화면을 바꾸면 전후 비교뿐이었고, 그 사이 홍보·요일·프로모션이 전부 섞였다.

**한 일.**

```js
// web/src/variant.js — visitorId를 FNV-1a 해시해서 즉시 배정
export const uiVariant = (() => {
  const forced = override()            // ?variant=a|b (QA·리뷰용)
  if (forced) return forced
  const { visitorId } = getAnalyticsContext()
  if (!visitorId) return 'a'           // localStorage가 막혔으면 기존 화면
  return VARIANTS[hash(visitorId) % VARIANTS.length]
})()
```

서버나 SDK에 물어보고 그리면 답이 올 때까지 무엇을 그릴지 모른다. 일단 한쪽을 그렸다 갈아끼우면 **첫 화면이 눈앞에서 바뀌고, 그 깜빡임 자체가 실험을 오염시킨다.** 그래서 즉시 결정한다. 대신 비율을 원격에서 못 바꾸는 것을 감수했다.

`variant`는 모든 이벤트에 실린다. **서버 매퍼와 브라우저 SDK 양쪽에서 같은 이름으로** 넘긴다 — 한쪽이 빠지면 원장엔 남아도 PostHog 퍼널이 두 안을 구분하지 못한다.

`data-variant`를 루트에 새겨 CSS가 두 안을 서로 덮지 않게 했다.

## 4. 관찰 — 가설 검증

### 4.1 H1(유실): PostHog 단독이 낫다 → **반증**

**확인 방법.** 두 저장소의 같은 이벤트를 날짜별로 나란히 센다.

**관찰.** 단독 책임으로 갔다면 잃었을 것이 셋이다.

*① 재시도할 데가 없다.* PostHog 전달이 실패하면 SaaS 쪽엔 아무것도 안 남는다. 지금은 실패해도 **원장에는 이미 적혀 있고**, outbox가 나중에 다시 보낸다. 유실을 막은 것은 "경로를 하나로 줄인 것"이 아니라 **"실패를 견디는 층을 하나 더 둔 것"**이었다.

*② 되돌릴 수 없다.* §3.4의 오탐이 결정적이었다. `dev_suspect`가 틀렸다는 것을 알았을 때:

```
원장     원본이 그대로 있어 새 규칙으로 다시 셌다 → 368명 복구
PostHog  보낸 시점의 속성이 박혀 있어 불가능
```

**PostHog 단독이었다면 368명은 영영 사라진 채였다.** 심지어 틀렸다는 사실조차 못 봤을 것이다 — 오탐을 발견한 단서가 "걸러낸 무리의 전환율이 더 높다"는 비교였는데, 그 비교를 하려면 걸러낸 쪽 원본이 있어야 한다.

*③ 지표가 실제로 갈렸다.*
```
2026-08-20 실측
  PostHog  방문자 a 18명 / b 25명
  원장     방문자 a 13명 / b 22명
```

**결론.** 유실 방지의 핵심은 책임 주체를 하나로 고정하는 것이 아니라 **원본 보존 + 재시도 큐**였다. 가설을 버리고 이중 기록으로 갔다.

### 4.2 H2(중복): PostHog 단독이면 중복이 없다 → **부분 성립**

**가설이 옳은 부분.** 경로가 하나면 같은 이벤트가 두 번 들어올 수 없다. 이중 기록을 택한 순간 중복 제거는 **우리가 갚아야 할 대가**가 됐다. 그래서 `eventId` → `$insert_id`를 붙였다.

**가설이 틀린 부분.** 실측된 중복은 이중 경로 때문이 아니었다.

```
brand_expand    원장   PostHog
      08-05      208      416    2.0x
      08-06       89      170    1.9x
      08-07       39       39    1.0x   ← 여기부터 일치
```

`brand_expand` 2,679행 중 `$insert_id`가 있는 건 **62개뿐**이었다. 원인은 초기 historical import가 07-29~08-06 구간에 두 번 들어간 것이고, 그때는 `eventId`가 도입되기 전이라 PostHog가 중복을 못 걷었다.

**즉 이 중복은 단독 책임이었어도 똑같이 났다.** 그리고 **원장과 나란히 세지 않았으면 존재조차 몰랐다.** 이중 기록이 중복을 만든 게 아니라 중복을 *발견하게* 해줬다.

**결론.** 중복 방지는 경로 수가 아니라 **멱등 키(idempotency key)**의 문제다. 단독 경로였어도 `$insert_id`는 필요했다. 다만 방문자 수는 안 부푼다(같은 사람이 두 번 세지는 게 아니라 이벤트가 두 벌) — 건수를 쓰는 지표만 조심하면 된다는 것도 이때 알았다.

### 4.3 H3(개발 트래픽): 플래그 + 서버사이드 필터 → **부분 성립**

**성립한 부분.** 명시 플래그(`?dev=1`)는 확실하다. 지금도 첫 번째 겹으로 쓴다. PostHog로는 아예 안 넘어간다.

**틀린 부분.** **서버사이드 필터로는 원리적으로 안 된다.** 서버는 이벤트 하나만 본다. "이 사람이 개발자인가"는 그 사람의 이벤트를 전부 모아야 답할 수 있는 질문이다.

이벤트 단위로 답하려고 만든 규칙이 정확히 그래서 틀렸다 — `device`와 `viewport` 두 값만으로 판정했고, 그 조합이 안드로이드 폰과 겹쳤다.

```
                       옛 규칙(이벤트 단위)      새 규칙(세션 단위)
판정 근거              device + viewport 1개     한 사람의 폭 집합
안드로이드 폰 384px    개발자 ❌                  사람 ✓
개발자 [390,1280]      일부만 걸림                개발자 ✓
오탐                   368명                      0
```

**결론.** 필터의 위치가 규칙의 정확도를 제한한다. 판정에 필요한 정보가 모이는 곳에서 판정해야 한다. 우리 경우 그곳은 수집이 아니라 집계였다.

### 4.4 H4(사용자 편향): 고유 식별자로 이상행동 배제 → **성립**

**확인 방법.** 같은 A/B 데이터를 총합 기준과 방문자 기준으로 각각 집계해 비교한다.

**관찰.**
```
2026-08-24 실측
  1인당      a 0.37   b 0.74     b가 두 배로 보인다
  전환율     a 18.7%  b 18.1%    차이 없음 (p=0.89)
  중앙값     a 1회    b 1회
  최다 1명   a 15회   b 43회     ← b 총 115회 중 43회가 한 사람
```

**한 사람이 갈래 하나의 결론을 뒤집고 있었다.** `visitorId`로 묶어 방문자 단위로 세면 이 왜곡이 구조적으로 사라진다.

**어떻게 막았나.** 이상치를 골라 빼지 않는다. `load()`가 원장을 `visitorId`로 접고, 비교할 때 **횟수를 안 보고 0인지 아닌지만** 본다.

```python
# experiments.py cmd_compare — 한 사람이 43번 눌러도 1이다
groups[name][0] += 1              # 분모: 사람
hits = v.events[args.goal]
if hits:
    groups[name][1] += 1          # 분자: 사람
    groups[name][2].append(hits)  # 횟수는 버리지 않고 진단용으로 따로
```

**결론.** 가설대로 됐다. 다만 구현은 "이상행동을 식별해 배제"가 아니라 **"집계 단위를 사람으로 바꿔 배제가 필요 없게"** 하는 쪽이 나았다 — 누구를 이상치로 볼지 정하는 판단(그 자체로 편향이 들어간다)을 아예 안 해도 된다.

**한 가지 더 배운 것.** 전환율만 내면 왜곡은 안 생기지만 **왜곡이 있었는지를 눈치챌 단서가 사라진다.** 애초에 오독을 잡아낸 것이 중앙값과 최다 한 명이었는데, 셸 스크립트를 정리하면서 그 진단이 같이 없어졌다가 다시 넣었다. 지금은 같은 표에 나온다.

```
집단        방문자   전환    전환율   95% 구간      중앙  최다1명
  a           228     76    33.3%   27.5~39.7%      1      29
  b           220     85    38.6%   32.4~45.2%      2     106
```

전환율은 33.3 대 38.6으로 멀쩡한데 최다 한 명이 106회다. 총합으로 봤으면 b가 압도적으로 보였을 값이다. 한 사람이 그 집단 전체 행동의 25% 이상을 차지하면 경고 줄을 따로 찍는다.

**막지 못하는 방향도 있다.** `visitorId`는 `localStorage` 난수다. 한 사람이 여러 방문자로 **쪼개지는** 오염(브라우저 데이터 삭제, 시크릿창, 기기 여럿)은 이 방식으로 못 막는다. 봇 판별도 아직 없다 — 지금 규모에서는 큰 문제로 안 보이지만, "사람 단위로 셌으니 안전하다"가 아니라 "몰리는 방향만 막았다"가 정확하다.

## 5. 관찰 — 도구가 실제로 뽑아낸 제품 신호

가설 검증과 별개로, 위 기반이 없었으면 못 봤을 것들.

### 5.1 방법론 오류 두 개를 찾아 고쳤다

**① 순서를 안 본 퍼널.** "각 이벤트를 언젠가 했나"로 세면 흐름이 아니라 교집합이다. 링크를 먼저 누르고 나중에 분류를 바꾼 사람이 통과한다.
```
같은 네 단계의 마지막 도달
  139명(순서 무시)  /  81명(시각순)  /  44명(같은 세션 + 시각순)
```

**② 없는 흐름을 가정한 퍼널.** `page_view → category_change`로 세면 "78% 이탈"로 읽힌다. 실제 경로를 세어 보니 그건 이탈이 아니라 **분류 변경이 필수 단계가 아닐 뿐**이었다.
```
세션 4,933개 — 첫 3동작
  (아무것도 안 함)                    2867  58.1%   ← 진짜 이탈
  offer_link_click 곧바로              647  13.1%   필터도 펼침도 안 거침
  category_change 뒤 이탈              228   4.6%
  offer_link_click > brand_expand       41   0.8%   펼침이 링크 '뒤'
```
`brand_expand`는 전 단계가 아니라 **사후 확인 행동**이었다. 퍼널 단계로 놓으면 안 되는 이벤트다.

### 5.2 08-19 개편이 재방문자만 반토막 냈다

```
            08-10~18      08-19~24     검정
재방문      34.8%      →  18.0%        z=-5.28  p<0.00001   유의
신규        17.6%      →  20.6%        z= 1.11  p=0.27      변화 없음
```

신규는 오히려 올랐다. "익힌 조작 경로가 통째로 바뀐 것"이라는 해석과 맞고, 이벤트 구성이 뒷받침한다 — `brand_expand`가 08-14 51건에서 08-16 7건으로 죽었다(카드 헤더에서 펼침 트리거를 걷은 커밋과 시점이 일치).

홍보일(07-31·08-05·08-10·08-18·08-24)을 빼면 신호가 **더 선명해진다.**
```
홍보일 제외   재방문 34.6% → 13.7%   z=-5.74
```
홍보일은 전환율이 다른 날이 아니라 **모수 구성이 다른 날**이다(재방문 비중 28% vs 64%). 합쳐 보면 UI 변화가 아니라 그날 홍보를 했는지를 보게 된다.

### 5.3 어떤 기능이 죽었나

```
기능                      건수  사용자  침투율  최근7일

membership_open            371    289   11.9%    0.0%   ← 제거됨

```

침투율만 보면 죽은 기능을 못 잡는다 — 한 달 누적이라 예전에 잘 쓰이던 것도 높게 남는다. **최근 7일을 나란히 둬야 갈린다.** 담아보기 기능은 이 표를 근거로 껐다.

### 5.4 A/B는 "판정 불가"로 결론냈다 — 그것도 결과다

```
a  228명  33.3%   95% 구간 27.5~39.7%
b  220명  38.6%   95% 구간 32.4~45.2%
z=1.17  p=0.24
상대 15% 차이를 잡으려면 갈래당 1,443명 필요 (현재 228/220)
```

표본이 모자란 것을 "차이 없음"으로 발표하지 않는다. 도구가 필요한 표본 수를 같이 내주기 때문에 **얼마나 모자란지**를 말할 수 있다.

### 5.5 검색 신호가 사실상 없었다는 것을 알았다

```
모수 2,438명
fSearch가 실린 이벤트를 가진 사람   18명 (0.7%)   첫 등장 2026-08-20
```

`fSearch`는 맥락 prop이라 **검색하고 아무것도 더 안 누르면 아예 안 남는다.** 불리언이라 몇 글자 쳤는지, 결과가 0건이었는지도 모른다. 자동완성을 얹기 전에 기준선이 필요하다는 판단으로 `brand_search_submitted`(`inputLength`·`resultCount`·`submitMethod`)를 먼저 배포했다.

---

## 6. 배운 점

**① 데이터 파이프라인의 버그는 조용하다.** 화이트리스트에 없는 이벤트, 상한에 잘린 prop, 오탐하는 판정 규칙 — 전부 에러 없이 사라진다. **계측은 테스트가 필요한 코드다.**

**② 수집 시점에 판단을 굳히지 말 것.** 무엇이 개발 트래픽인지는 나중에 바뀐다. 원본을 남기고 판단은 집계에서 한다. H1을 뒤집은 것이 이 원칙이다.

**③ 필터의 위치가 규칙의 정확도를 제한한다.** 이벤트 하나만 보는 곳에서는 이벤트 하나로 답할 수 있는 질문만 풀린다. 억지로 풀려 들면 368명 같은 오탐이 난다.

**④ 같은 판정이 여러 곳에 있으면 반드시 갈린다.** 단일 출처로 모으는 것이 규칙의 정확도보다 먼저다.

**⑤ 통계보다 앞에 오는 것은 "그 흐름이 실제로 존재하는가"다.** 퍼널을 그리기 전에 경로를 세어야 한다.

**⑥ "유의하지 않다"와 "차이가 없다"는 다르다.** 표본 크기 계산을 같이 내지 않으면 구분할 수 없다.

**⑦ 반증된 가설이 확증된 가설보다 많은 것을 가르쳤다.** H1·H2를 그대로 밀었으면 368명 오탐도, PostHog 초기 구간 2배 중복도 못 봤다.

---

## 7. 다음 행동

- **표본이 되는 실험만 세운다.** 현재 트래픽(하루 60~250명)으로는 상대 30% 이상 차이만 잡힌다. 그보다 작은 개선은 A/B 대신 퍼널·경로로 판단한다.
- **첫 화면 이탈 58%**를 다음 과제로. 지금까지 본 것 중 가장 큰 단일 손실이다.
- **08-19 개편 중 무엇이 재방문자 경로를 막았는지** 좁힌다(그날 커밋 19건, `brand_expand` 소실이 유력).
- **홍보일 제외를 도구 기본값으로** 옮길지 정한다. 지금은 매번 기억해서 빼야 한다.
- **자동완성 기준선을 쌓는다.** `brand_search_submitted`가 먼저 배포됐고, 순수 제출 데이터가 모인 뒤에 기능을 올려야 전후 비교가 성립한다.
