# 사용자 이벤트 분석 — 무엇을 만들었고 무엇이 달라졌나

> 받은 피드백: *"이벤트 분석 도구 도입만으로 기술적 요구사항을 충족했다고 보기 어렵다. 어떤 도구를 도입할지 조사한 내용만 있고 기술적 활동은 없어 보인다."*
>
> **맞는 지적이다.** 앞선 문서는 "PostHog를 골랐다"까지였다. 도구 선정은 조사지 기술 활동이 아니고, 무엇보다 *적용 전 문제*가 없었다. 이 문서는 그 뒤에 실제로 만든 것과, 그것이 없었다면 못 봤을 신호를 적는다.

**한 줄 요약**: 데이터를 *모으는* 문제는 도구가 풀었지만, 모인 데이터에서 *믿을 수 있는 신호를 뽑는* 문제는 도구가 풀어주지 않았다. 그쪽에 든 공학이 이 문서의 내용이다.

---

## 0. 전체 그림

```
브라우저                     서버                        분석
─────────                  ─────                      ────
analytics.js   ──batch──▶  EventController      ──▶  events.jsonl (원장·단일 진실)
  이벤트 계약               화이트리스트 검증                    │
  eventId(UUID)            props 화이트리스트                  ▼
  variant 배정             레이트 리밋              scripts/experiments.py
  filterContext            ipHash(날짜별 솔트)        개발 트래픽 판정
      │                          │                   방문자 단위 집계
      │                          ▼                   Wilson CI · z검정
      └──직접 전송──▶  PostHogOutbox ──▶ PostHog       표본 크기 · 퍼널 · 경로
                       (파일 큐, 재시도,               (탐색용)
                        dead-letter)
```

핵심 구조 결정 하나: **원장이 단일 진실이고 PostHog는 탐색용이다.** 이유는 §2.2에서 값을 했다.

## 1. 적용 전 상태 — 무엇이 문제였나

계측을 붙였다고 분석이 되지는 않았다. 실제로 겪은 것들:

| # | 문제 | 어떻게 드러났나 |
|---|---|---|
| P1 | 프론트가 보내는 이벤트를 서버가 조용히 버렸다 | 필터 시트·담아보기 이벤트 **6종**이 화이트리스트에 없어 전량 폐기. 정작 A/B가 답하려던 질문이 그 이벤트에 걸려 있었다 |
| P2 | 이벤트 속성이 말없이 잘렸다 | `MAX_PROPS=6`에 배너의 `position`이 밀려 유실. 배너 위치별 효과를 못 쟀다 |
| P3 | 같은 이벤트가 두 경로로 가는데 중복 제거가 없었다 | 서버 릴레이 + 브라우저 SDK. 건수가 배로 셀 수 있었다 |
| P4 | 개발자 트래픽이 실사용자에 섞였다 | 방문자 43명 중 **8명(19%)**이 표시 없는 개발 트래픽. 표본이 수십 명일 때 결론이 뒤집힌다 |
| P5 | 지표를 잘못 읽는 방법론 문제 | "1인당 링크이동"으로 b가 2배 나은 것처럼 보였다. 실제로는 115클릭 중 43이 한 사람 |
| P6 | 판단을 수집 시점에 굳혀 되돌릴 수 없었다 | 개발 트래픽 추정 규칙이 틀렸는데, SaaS에 이미 그 속성으로 박혀 나갔다 |
| P7 | 분석할 때마다 일회성 스크립트를 새로 썼다 | 같은 판정 규칙이 3곳에 복사돼 도구마다 다른 숫자가 나왔다 |

**공통점**: 전부 "도구를 골랐다"로는 안 풀리고, 코드를 써야 풀리는 문제다.

## 2. 적용 — 실제로 만든 것

### 2.1 이벤트 계약을 코드로 강제 (P1, P2)

서버는 공개 쓰기 엔드포인트다. 아무거나 받으면 안 되지만, 화이트리스트를 두면 **프론트와 어긋나는 순간 조용히 사라진다**. 그 어긋남을 사람이 아니라 테스트가 잡게 했다.

```
api  EventController.ALLOWED_EVENTS   19종 화이트리스트
     MAX_BATCH 20 · MAX_TEXT 120 · MAX_PROPS 8 · 레이트 리밋 분당 120
web  scripts/verify-analytics-event-contract.mjs
     소스에서 track('...') 호출을 정적 추출해 서버 목록과 대조 (양방향)
```

`npm test`가 세 검사를 돌린다 — 이벤트 계약, `eventId` 동작, PostHog 어댑터 동작.

P2는 순서 문제이기도 했다. 필터 맥락 6종이 이벤트 자기 값보다 앞에 붙어 상한에 먼저 자리를 먹고 있었다. **이벤트 고유 값을 앞으로 보내고** 상한을 8로 올렸다 — 넘치면 맥락이 먼저 떨어지도록.

```js
// analytics.js — 이벤트 고유 값이 먼저다. 서버가 앞에서부터 세어 자른다
props: { ...props, ...filterContext }
```

### 2.2 이중 기록과 되돌릴 수 있는 판단 (P3, P6)

**자체 원장(`events.jsonl`)이 단일 진실, PostHog는 탐색용.** 서버는 받은 것을 그대로 적고 아무 판단도 굳히지 않는다.

이 결정이 실제로 값을 한 사건 — §3.3의 개발 트래픽 오탐. 규칙이 틀린 걸 알았을 때 **원장은 원본이 남아 있어 다시 셀 수 있었고, PostHog는 보낸 시점의 속성이 박혀 있어 불가능했다.**

전달은 유실되면 안 되므로 파일 기반 outbox를 뒀다:

```
PostHogOutbox    enqueue → 원자적 파일 쓰기(임시파일 + move)
                 재시도, 실패 누적 시 dead-letter, 깨진 파일 격리
PostHogForwardingWorker  주기적으로 배출
```

중복 제거(P3)는 `eventId`(클라이언트 UUID) → PostHog `$insert_id`로 잇는다. 유효한 UUID면 재전송에도 유지하고, 구버전·잘못된 값만 서버가 보완한다.

### 2.3 분석 도구를 직접 만듦 (P5, P7)

같은 판정 규칙이 Java·JS·셸 세 곳에 복사돼 있었다. **집계에 필요한 판단을 한 파일로 모았다.**

`scripts/experiments.py` — 원장을 방문자 단위로 접고 다음을 낸다.

| 명령 | 답하는 질문 |
|---|---|
| `audit` | 개발 트래픽 판정이 사람을 잡아먹고 있지 않나 |
| `features` | 어떤 기능이 쓰이고 어떤 게 죽었나 (침투율 + 최근 7일 + 수명) |
| `compare --by` | 갈래별 전환율 차이가 우연인가 (variant / 신규·재방문 / 폭 / 유입 / 기간) |
| `funnel` | 어디서 새는가 (**시각순**, 세션 범위) |
| `paths` | 실제로 밟은 순서는 무엇인가 |
| `power` | 이 차이를 증명하려면 몇 명이 필요한가 |
| `top` | 어떤 브랜드·배너·위치가 먹혔나 |

통계는 직접 구현했다 — 두 비율 z검정, Wilson 신뢰구간(작은 표본에서 정규근사가 0%/100%에서 무너진다), 검정력 기반 표본 크기. `--selftest`가 계산을 고정한다(z값, Wilson 경계, 퍼널 순서 역전, 중복 접기).

**집계 단위를 방문자로 못박은 것**이 P5의 답이다. 한 사람이 몇 번 누르든 1로 센다.

### 2.4 A/B 인프라

```
variant.js   visitorId를 FNV-1a 해시 → 즉시 배정
             ?variant=a|b 로 강제 (QA·리뷰용)
             data-variant 를 뿌리에 새겨 CSS가 두 안을 안 덮게
```

서버·SDK에 물어보고 그리면 첫 화면이 눈앞에서 갈아끼워진다 — **그 깜빡임 자체가 실험을 오염시킨다.** 그래서 즉시 결정한다. 대신 비율을 원격에서 못 바꾸는 것을 감수했다.

`variant`는 모든 이벤트에 실린다. 서버 매퍼와 브라우저 SDK **양쪽**에서 같은 이름으로 넘긴다 — 한쪽이 빠지면 원장엔 남아도 PostHog 퍼널이 두 안을 구분하지 못한다.

### 2.5 개인정보 경계를 테스트로 못박음

검색 계측을 붙일 때 자유 입력이 들어온다. 원문을 안 받는 것을 규칙이 아니라 **테스트**로 만들었다.

```java
// EventControllerTest — 전화번호가 섞여 들어와도 남지 않는다
props {"inputLength":"4","resultCount":"2","submitMethod":"enter",
       "query":"010-1234-5678","unexpected":"raw"}
→ 원장에 남는 것: inputLength, resultCount, submitMethod 뿐
```

`brand_search_submitted`만 props 화이트리스트를 따로 건다. `ipHash`는 날짜별 솔트라 하루가 지나면 되돌릴 수 없다.

## 3. 관찰 — 무엇이 달라졌나

### 3.1 잃고 있던 데이터를 되찾았다

| | 전 | 후 |
|---|---|---|
| 서버가 받는 이벤트 | 13종 (6종 폐기 중) | 19종 |
| 배너 `position` | 상한에 잘려 유실 | 보존 |
| 검색 신호 | `fSearch` 불리언, **18명(0.7%)**에게만 | `brand_search_submitted` + 길이·결과수·제출방식 |

검색은 특히 컸다. `fSearch`는 맥락 prop이라 **검색하고 아무것도 더 안 누르면 아예 안 남았다.** 한 달 통틀어 18명이 전부였다.

### 3.2 방법론 오류 세 개를 찾아 고쳤다

**① 1인당 총합의 함정**
```
1인당      a 0.37   b 0.74     b가 두 배로 보인다
전환율     a 18.7%  b 18.1%    차이 없음 (p=0.89)
최다 1명   a 15회   b 43회     ← b 총 115회 중 43회가 한 사람
```

**② 순서를 안 본 퍼널** — "각 이벤트를 언젠가 했나"로 세면 흐름이 아니라 교집합이다. 같은 네 단계의 마지막 도달이:
```
139명(순서 무시) / 81명(시각순) / 44명(같은 세션 + 시각순)
```
링크를 먼저 누르고 나중에 분류를 바꾼 사람이 통과하고 있었다.

**③ 없는 흐름을 가정한 퍼널** — `page_view → category_change`로 세면 "78% 이탈"로 읽힌다. 실제 경로를 세어 보니 그건 이탈이 아니라 **분류 변경이 필수 단계가 아닐 뿐**이었다.
```
세션 4,933개
  (아무것도 안 함)                    2867  58.1%   ← 진짜 이탈은 여기
  offer_link_click 곧바로              647  13.1%   필터도 펼침도 안 거침
  offer_link_click > brand_expand       41   0.8%   펼침이 링크 '뒤'에 온다
```
`brand_expand`는 전 단계가 아니라 **사후 확인 행동**이었다. 퍼널 단계로 놓으면 안 되는 이벤트다.

### 3.3 판정 규칙이 실사용자를 걸러내고 있었다

개발 트래픽 추정 규칙 `device == "desktop" AND 폭 < 400px`이 **안드로이드 폰 사용자 368명**을 개발자로 몰아냈다. `device`를 `matchMedia('(hover: hover)')`로 정하는데 일부 안드로이드 브라우저가 `hover:hover`를 보고한다.

발견한 단서는 **걸러낸 무리의 전환율이 남긴 쪽보다 높다**는 것이었다(41.9% vs 33.9%).
```
걸러낸 무리 폭 분포   384(3203) 360(1337) 368(133) 320(83)   전부 폰 폭
걸러낸 무리의 93%    세션 내내 폭이 하나: [384] 또는 [360]
진짜 개발자의 폭      [390,1280]  [849,1283]  [1309,1554,1745,1862]
```

**고친 방식이 요점이다.** 새 규칙(세션 안에서 창 폭이 여러 개이고 최대 ≥800px)은 한 사람의 이벤트를 전부 모아야 내릴 수 있다 — 이벤트 하나만 보는 서버·브라우저에서는 **원리적으로 불가능한 판단**이다. 그래서 추정을 수집 경로에서 걷어내고 집계 한 곳에만 뒀다. 규칙이 또 바뀌어도 과거 데이터를 다시 셀 수 있다.

부수적으로 PostHog의 07-29~08-06 건수가 **2배**인 것도 이때 드러났다(초기 import 중복, `$insert_id` 도입 전이라 dedupe 불가). 원장과 나란히 세지 않았으면 못 봤다.

### 3.4 실제로 뽑아낸 제품 신호

**08-19 개편이 재방문자만 반토막 냈다.**
```
            08-10~18      08-19~24     검정
재방문      34.8%      →  18.0%        z=-5.28  p<0.00001   유의
신규        17.6%      →  20.6%        z= 1.11  p=0.27      변화 없음
```
신규는 오히려 올랐다. "익힌 조작 경로가 통째로 바뀐 것"이라는 해석과 맞는 모양이고, 이벤트 구성이 뒷받침한다 — `brand_expand`가 08-14 51건에서 08-16 7건으로 죽었다(카드 헤더에서 펼침 트리거를 걷은 커밋과 일치).

홍보일(07-31, 08-05, 08-10, 08-18, 08-24)을 빼면 신호가 **더 선명해진다**. 홍보일은 전환율이 다른 게 아니라 **모수 구성이 다르다**(재방문 비중 28% vs 64%).
```
홍보일 제외   재방문 34.6% → 13.7%   z=-5.74
```

**기능별 사용량 — 무엇이 죽었나**
```
기능                      건수  사용자  침투율  최근7일
brand_expand              1323    372   15.3%    1.2%   ← 죽음
membership_open            371    289   11.9%    0.0%   ← 제거됨
cart_toggle                327     73    3.0%    7.8%
filter_sheet_open           21     12    0.5%    1.3%   ← 시트가 안 열린다
cart_clear                   2      2    0.1%    0.2%
```
침투율만 보면 죽은 기능을 못 잡는다(한 달 누적이라 예전에 잘 쓰이던 것도 높게 남는다). 최근 7일을 나란히 둬야 갈린다. **담아보기는 이 표를 근거로 껐다.**

**A/B는 "판정 불가"로 결론냈다 — 그것도 결과다.**
```
a  228명  33.3%   27.5~39.7%
b  220명  38.6%   32.4~45.2%
z=1.17  p=0.24
상대 15% 차이를 잡으려면 갈래당 1,443명 필요 (현재 228/220)
```
표본이 모자란 것을 "차이 없음"으로 발표하지 않는다. 도구가 필요한 표본 수를 같이 내주기 때문에 **얼마나 모자란지**를 말할 수 있다.

## 4. 배운 점

**① 데이터 파이프라인의 버그는 조용하다.** 화이트리스트에 없는 이벤트, 상한에 잘린 prop, 오탐하는 판정 규칙 — 전부 에러 없이 그냥 사라진다. **계측은 테스트가 필요한 코드다.** 양방향 계약 검사와 `--selftest`를 둔 이유다.

**② 수집 시점에 판단을 굳히지 말 것.** 무엇이 개발 트래픽인지, 무엇이 전환인지는 나중에 바뀐다. 원본을 그대로 남기고 판단은 집계에서 한다. 이 원칙 하나가 368명 오탐을 되돌릴 수 있게 했다.

**③ 같은 판정이 여러 곳에 있으면 반드시 갈린다.** 규칙이 틀렸을 때 세 곳이 각각 다른 숫자를 내고 있었다. 단일 출처로 모으는 것이 정확도보다 먼저다.

**④ 통계보다 앞에 오는 것은 "그 흐름이 실제로 존재하는가"다.** 퍼널을 그리기 전에 경로를 세어야 한다. 아니면 없는 이탈을 만들어 놓고 그걸 고치려 든다.

**⑤ "유의하지 않다"와 "차이가 없다"는 다르다.** 표본 크기 계산을 같이 내지 않으면 이 둘을 구분할 수 없다.

## 5. 다음 행동

- **표본이 되는 실험만 세운다.** 현재 트래픽(하루 60~250명)으로는 상대 30% 이상 차이만 잡힌다. 그보다 작은 개선은 A/B 대신 퍼널·경로 단계로 판단한다.
- **08-19 개편 중 무엇이 재방문자 경로를 막았는지** 좁힌다. `brand_expand` 소실이 유력하지만 그날 커밋이 19건이다.
- **첫 화면 이탈 58%**를 다음 과제로 잡는다. 지금까지 본 것 중 가장 큰 단일 손실이다.
- **홍보일 제외를 도구 기본값으로** 옮길지 정한다(지금은 매번 기억해서 빼야 한다).
- **자동완성 도입 전 기준선을 쌓는다.** `brand_search_submitted`를 먼저 배포했고, 순수 제출 데이터가 모인 뒤에 기능을 올려야 전후 비교가 성립한다.
