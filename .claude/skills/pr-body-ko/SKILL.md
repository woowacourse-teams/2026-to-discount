# PR 본문 쓰기

읽는 사람은 코드를 열지 않는다. 절 제목과 각 항목의 첫 문장만 읽어도 무엇이 왜 바뀌었는지 알 수 있게 쓴다.

## 0. 문장

- 조사와 서술어 꼬리를 줄이고 명사형으로 끝낸다.
  - `~하기 위해서다` → `~위함`
  - `reload한다` → `reload`
  - `찍지 않았다` → `찍지 않음`
- 줄여서 뜻이 바뀌거나 주어가 흐려지면 줄이지 않는다.
- 한 PR 안에서는 끝맺음을 하나로 맞춘다.
- 한 문장이 두 가지 일을 말하거나 쉼표가 둘을 넘으면 하위 목록으로 나눈다.
- 지시대명사("이것", "위 항목", "해당")를 쓰지 않는다. 대상의 이름을 쓴다.
- 추상어("개선", "정리", "강화", "보완")로 끝내지 않는다. 무엇이 어떻게 달라졌는지 쓴다.
- 쓰지 않는 말: "핵심적으로", "원활한", "효과적으로", "~를 통해", "~에 대응", "A가 아니라 B".
- 중의적인 말을 쓰지 않는다. 범위나 조건을 나타낼 때 특히 조심한다.
  - 나쁜 예: `(앱, 브랜드) 항목을 뺌` (앱 또는 브랜드로 읽힌다)
  - 좋은 예: `앱과 브랜드가 둘 다 같은 항목만 뺌. 다른 앱의 같은 브랜드는 남음`
- 영어 용어, 파일 이름, 프로젝트 안에서만 쓰는 말은 처음 나올 때 괄호 안에 우리말 풀이를 붙인다.
  - 예: `export(서버가 공개 API로 내보내는 오퍼 파일)`, `reload(API가 파일을 다시 읽음)`
- 예시는 읽는 사람이 맥락 없이 이해할 수 있을 때만 든다. 이 대화나 이 팀만 아는 사례를 예시로 쓰지 않는다.
- 확인하지 않은 내용은 본문에 섞지 않는다. `리뷰 포인트`나 `후속 조치` 절로 옮기고 **굵게** 표시한다.

## 1. 제목

`[분야] 종류: 설명`

- 분야는 대문자로 쓴다. 예: `CONSOLE`, `API`, `WEB`, `COLLECT`, `INFRA`, `DOCS`.
- 종류는 feat, fix, refactor, test, docs, chore 중 하나다.
- 설명은 무엇이 가능해지는지를 한 구절로 쓰고, 명사형으로 끝낸다.

## 2. 절 순서와 틀

아래 순서를 따른다. 해당 없는 절은 뺀다.

### 개요

첫 줄에 한 줄 정의와 링크를 둔다.

`(기능 이름): (어디)에서 (무엇)을 (어떻게) 구현. [설계](링크), [짝 PR](링크)`

- 링크는 병합 전후 모두 열리면 된다.

### 배경

- 첫 줄은 `(상황)에서 (필요) 인지.`로 쓴다.
- 다음 줄에 `[설계](링크) 요약:`을 두고, 결정을 하위 목록으로 두세 개 적는다.

### 추가/변경

항목마다 `**(요소) (추가|변경|삭제):** (어디)에 (무엇). (무엇) 보존. (무엇) 개선.`으로 쓴다.

- 첫 문장만 읽어도 무엇이 생겼는지 알 수 있어야 한다.
- 세부 동작은 하위 목록으로 단다.
- 파일 이름은 첫 문장 뒤 괄호에 둔다.

좋은 예: `**제외 API 추가:** 운영 콘솔 서버에 오퍼를 공개 목록에서 빼는 요청 추가. 뺀 원본은 별도 파일에 보존해 되살릴 수 있음.`
나쁜 예: `**제외 API:** ops_apply.py 수정.`

항목이 넷을 넘거나 하위 목록이 붙으면 요약과 상세로 나눈다.

- 절 맨 위에 항목마다 첫 문장만 한 줄씩 목록으로 둔다.
- 하위 목록을 포함한 전체 내용은 그 아래 접기 블록에 둔다.

```
- **제외 API 추가:** 운영 콘솔 서버에 오퍼를 공개 목록에서 빼는 요청 추가.
- **오퍼 탭 추가:** 운영 콘솔에 오퍼 목록과 제외 버튼 화면 추가.

<details><summary>상세</summary>

(항목별 전체 내용과 하위 목록)

</details>
```

### 설계 변동

설계와 다르게 한 것만 적는다.

```
- **(변동 제목)**
  - 기존: ...
  - 변동: ...
  - 이유: ...
  - 근거: ...
```

### 확인

- 항목마다 `Given ... / When ... / Then ...` 한 줄로 쓴다.
- Then 끝 괄호에 확인 수단을 붙인다. 예: `(테스트 통과)`, `(스크린샷)`, `(서버 조회 2026-10-22)`.
- 하지 못한 확인은 `**미확인:**`으로 따로 적는다.
- 항목이 넷을 넘으면 추가/변경 절과 같이 나눈다. 맨 위에는 `(무엇을) 확인: (결과)` 요약 한 줄씩 두고, Given/When/Then 전체는 접기 블록에 둔다. 미확인 항목은 요약에 남긴다.

## 2-1. 다시 쓸 때

본문 전체를 다시 쓰지 않는다. 처음 본문은 그대로 두고, 반영하거나 바꾼 부분만 본문 아래에 이어 붙인다.

- 붙이는 단위는 `### 변경 N (날짜): 한 구절 요약`이다. 그 아래에 바꾼 절과 내용만 쓴다. 예: `- 추가/변경: 세션 push 권한 삭제. …`
- 앞 본문의 내용과 어긋나게 됐으면, 어긋난 줄을 고치지 말고 변경 절에 `기존: … → 변경: …`으로 적는다.
- 처음 본문과 다시 쓴 본문의 차이가 아주 큰 경우(구조를 새로 짜는 경우)만 처음 본문을 접기 블록으로 남긴다(2026-10-22 사용자: 그때는 전후 차이가 커서 남긴 것).

### 영향

아래 세 제목으로 나누고, 제목마다 완결된 문장을 목록으로 쓴다.

- **달라지는 것:** `(누구)의 (무엇)이 (어떻게) 된다.`
- **고려한 것:** `(무엇)을 고려함. (이유) 때문.`
- **병합 조건:** 함께 병합해야 할 PR, 배포 때 바뀌는 설정.

### 후속 조치

- 병합 뒤 할 일을 목록으로 쓴다. 각 항목에 무엇을 확인하면 끝인지 적는다.
- 항목 하나가 이슈 하나가 된다. 첫 `:` 앞이 이슈 제목이 되므로 `(일 이름): (할 일과 끝 조건)`으로 쓴다.
- 병합되면 `followup-issues` 워크플로가 이 절을 읽어 이슈를 만들고 PR에 목록 댓글을 단다. tracker와 mono 둘 다 같다.
- 이슈를 만드는 세션의 규칙:
  - 같은 일인 항목은 한 이슈로 묶는다. 이미 만든 항목(본문의 `followup:` 표식)은 다시 만들지 않는다.
  - 고칠 곳의 저장소에 만든다. 수집, 원장, 내보내기는 tracker(`export`, `collect`), 웹은 mono `web`, 서버는 mono `api`. 영역이 없으면 라벨을 비운다.
  - 설계 세션은 이슈 본문만 읽고 출처 PR을 열 수 없다. 본문에 개요, 배경, 할 일, 끝 조건, 참고(출처 PR)를 쓴다.
  - mono는 공개 저장소다. 서버 경로, 비공개 파일 이름, 비밀값을 쓰지 않는다.

### 리뷰 포인트

- 리뷰어가 예/아니요나 한 줄로 답할 수 있는 질문만 둔다.
- 확인하지 않은 가정은 여기에 **굵게** 둔다.

## 3. 마치기 전

- 절 제목과 각 항목 첫 문장만 읽고도 이해되는지 본다.
- 사실은 커밋, 테스트 출력, 설계 문서, 서버 조회에서만 가져온다.
- 긴 문장이 남았으면 목록으로 나눈다.
- 본문 끝에 저장소가 정한 생성 표기를 붙인다.
